Step 1Why GPUs

1.1Why GPUs: latency, throughput and power

  • Two designs CPU: big control and caches, few strong ALUs, low latency. GPU: thousands of small ALUs, small control, high throughput.
  • Latency and throughput Latency = time for one job. Throughput = jobs ÷ time. FPS = 1000 ÷ ms per frame. Batch time = ⌈N ÷ C⌉ × time per round.
  • Power P ∝ α C V² f. Higher clock needs higher voltage, so power explodes. GPUs use many cores at a moderate clock.
  • Peak Peak = FLOPs per tick per core × clock × cores. FMA = 2 FLOPs. T4 ≈ 8.1, A100 FP32 ≈ 19.5 TFLOP/s.
  • Hardware spectrum CPU → GPU → FPGA → ASIC: less flexible, more efficient. TPU and NPU are ASIC style AI accelerators. The CPU is always the host.
  • Latency and throughputLatency = time to finish ONE job
    Throughput = jobs finished ÷ time taken
  • Time for a batchT = ⌈N ÷ C⌉ × (time per round)
  • Dynamic powerPdyn ∝ α · C · V² · f
  • Peak work per secondpeak = (FLOPs per tick per core) × f × cores
  • Trap GPU does not mean "always faster". A GPU wins only when there is enough independent work to keep thousands of small units busy. For a single small task the CPU usually wins.
  • Exam A GPU never runs alone. The CPU boots the machine, runs the serial parts and launches GPU work. This is why the time to copy data between them matters so much (chapter 1.2).

1.2Speedup, the PCIe trip and Amdahl's law

  • Speedup S = old ÷ new. Count copy in + kernel + copy out. Copy time = bytes ÷ bandwidth (PCIe about 12 to 16 GB/s).
  • Amdahl S(N) = 1 ÷ ((1 − P) + P/N). Ceiling 1 ÷ (1 − P). Efficiency S ÷ N. Back: P = (1 − 1/S) ÷ (1 − 1/N).
  • Part speedup Speeding a part p by s gives 1 ÷ ((1 − p) + p/s). Speed up the biggest part first.
  • Gustafson Scaled speedup N − (1 − P)(N − 1) when the problem grows with N (weak scaling).
  • Keep data on the GPU Copy once, run many kernels, copy back once. Small jobs have a break even size below which the CPU wins.
  • SpeedupS = old time ÷ new time
  • Total GPU timeTGPU = Tcopy in + Tkernel + Tcopy out
  • Amdahl's lawS(N) = 1 ÷ [ (1 − P) + P ÷ N ]
  • The ceilingSmax = 1 ÷ (1 − P)
  • Gustafson's law (scaled speedup)Sscaled = N − (1 − P)(N − 1)
  • Trap Keep data on the GPU across many kernel launches. Copy in once, run all time steps, copy out once. Copying every step can turn a 158 times speedup into 12 times (workbook P1.3.5).
  • Trap P is a fraction of the time on one processor, not a fraction of the lines of code. A tiny loop that runs for 90 percent of the time gives P = 0.9.
  • Exam In an exam, Amdahl is the default unless the question says the problem grows with the number of processors.

1.3First GPU workloads: heat simulation and convolution

  • Heat rule T_new = T + α(up + down + left + right − 4T) + βQ. 1-D uses −2T. Updates = cells × steps.
  • Why parallel Each cell needs only old neighbour values, so one thread per cell. Keep two buffers (old and new).
  • Stability Explicit scheme: α ≤ 1/2 in 1-D, 1/4 in 2-D, 1/6 in 3-D, or values blow up.
  • Convolution cost Normal H W Cin Cout K². Separable H W Cin K² + H W Cin Cout. Ratio (K² + Cout) ÷ (K² Cout) → 1/K².
  • Same pattern Heat updates and convolutions are stencils: each output reads a small neighbourhood. Tiling with halos speeds them up later.
  • 2-D update rule (5 points)Tnew = T + α (up + down + left + right − 4T) + βQ
  • Normal convolutionmults = H × W × Cin × Cout × K × K
  • Saving ratioseparable ÷ normal = (K² + Cout) ÷ (K² × Cout)
  • Trap A GPU heat code must keep two buffers. If threads wrote into the same grid they read from, some would read a neighbour's new value and some its old value, and the answer would depend on timing.

Step 2The CUDA programming model

2.1Your first CUDA program

  • Host and device Host = CPU + RAM, device = GPU + its DRAM. Separate memories, so copy with cudaMemcpy (or use unified memory).
  • Recipe cudaMalloc, cudaMemcpy H2D, kernel<<<blocks, threads>>>, cudaMemcpy D2H, cudaFree. blocks = (n + B − 1) / B.
  • Qualifiers __global__ void kernel (host launches), __device__ helper (device only), __host__ default. Kernels cannot return values.
  • Guard if (i < n) because the last block can overhang the array.
  • Asynchronous Launch returns at once. cudaMemcpy and cudaDeviceSynchronize wait. Check errors with cudaGetLastError after a launch.
  • Exam Quiz 1 question 6: the correct kernel signature is __global__ void. A kernel cannot return a value, because thousands of threads run it and the launch returns to the host at once without waiting. Results go back through memory. __shared__ is a memory space, not a function qualifier.
  • Trap The order of the six lines is not guaranteed. Blocks may run in any order, so block 1 can print first. Never write code that depends on the order blocks run in.

2.2Threads, blocks and grids: indexing in 1-D, 2-D and 3-D

  • Global index i = blockIdx.x × blockDim.x + threadIdx.x. Blocks = (N + B − 1)/B. Guard i < N. Idle = blocks × B − N.
  • 2-D col = bx·Bx + tx, row = by·By + ty, index = row × width + col. Grid = (⌈W/Bx⌉, ⌈H/By⌉), guard both.
  • Linear order thread = tx + ty·Bx + tz·Bx·By (x fastest). Warps are cut from this order.
  • Backwards block = ⌊g ÷ per block⌋, leftover = g mod per block, x = leftover mod Bx, y = ⌊leftover ÷ Bx⌋.
  • Grid stride Start at i = idx, keep going while i < n, and add blockDim.x × gridDim.x each time. A fixed grid then covers any N.
  • Global indexi = blockIdx.x × blockDim.x + threadIdx.x
  • Blocks neededblocks = ⌈N ÷ B⌉ = (N + B − 1) ÷ B
  • Pixels in an imagecol = blockIdx.x × blockDim.x + threadIdx.x
    row = blockIdx.y × blockDim.y + threadIdx.y
    memory position = row × width + col
  • Position to one number (x fastest)thread = tx + tyBx + tzBxBy
    block = bx + byGx + bzGxGy
    global = block × (threads per block) + thread
  • Exam Exams love going backwards. Always divide by the number of threads per block first, then split the leftover with mod and divide, x first.
  • Trap In matVecMul neighbouring threads read A[i × N + j] for the same j, which are N floats apart. That is a strided, uncoalesced read (chapter 3.2). A transposed layout or one warp per row is faster for large N.

2.3SMs, warps and hiding latency

  • Mapping Thread → core lane, warp → scheduler, block → one SM for life, grid → whole GPU.
  • Warps warps = ⌈B/32⌉, warp = ⌊t/32⌋, lane = t mod 32, t = x + y·Bx. Efficiency B ÷ (32 × warps).
  • Little's law In flight = latency × throughput. Warps = that ÷ 32. Bytes in flight = bandwidth × latency.
  • Latency hiding Zero cost warp switching because registers stay on chip. Need many warps or independent instructions.
  • Registers Registers per thread = file ÷ threads. 65,536 on modern SMs. Too many spill to slow local memory.
  • Warps per blockwarps = ⌈B ÷ 32⌉
  • Warp and lane of thread twarp = ⌊t ÷ 32⌋, lane = t − 32 × warp
  • Little's lawjobs in flight = latency (ticks) × throughput (jobs per tick)
  • Trap In class it was said that grids sit inside cores. It is the other way round: a thread runs on a core, a block on one SM, and a grid across all SMs.

2.4Occupancy: how many warps fit on an SM

  • Occupancy Active warps ÷ max warps per SM. Blocks = min(warp limit, block limit, register limit, shared memory limit).
  • Block limit Small blocks hit the block cap. Smallest block for 100 percent = max threads ÷ max blocks (A100: 64).
  • Registers Per warp = ⌈32r ÷ 256⌉ × 256. Blocks = ⌊⌊65,536 ÷ per warp⌋ ÷ warps per block⌋.
  • Shared memory Blocks = ⌊pool ÷ (bytes + 1 KB reserved)⌋ on CC 8.x.
  • Not the goal Enough warps to hide latency is enough. Measure achieved occupancy in Nsight Compute.
  • Occupancyoccupancy = active warps per SM ÷ maximum warps per SM
  • Blocks that fitblocks = min(warp limit, block limit, register limit, shared memory limit)
  • Registers per warpper warp = ⌈(r × 32) ÷ 256⌉ × 256
  • Register limit in blocksblocks = ⌊⌊65,536 ÷ per warp⌋ ÷ warps per block⌋
  • Shared memory limitblocks = ⌊shared memory per SM ÷ (bytes per block + reserved)⌋

Step 3GPU memory

3.1The GPU memory hierarchy

  • Spaces Register (thread), local (thread, in DRAM), shared (block), global (all, host, until cudaFree), constant (all, read only).
  • Q8 Visible to all SMs for the whole application: global memory. L2 is a cache, not a space.
  • Constant 64 KB, host writes with cudaMemcpyToSymbol, broadcast when a warp reads one address.
  • Host memory Pageable malloc, pinned cudaMallocHost (needed for async overlap), managed cudaMallocManaged with prefetch.
  • Copies Copy time = bytes ÷ bandwidth. PCIe is far slower than device DRAM. Copy once, reuse many times.
  • Copy timet = bytes ÷ bandwidth
  • Trap Local memory is not near the thread. "Local" means private. It lives in device DRAM and is only cached on chip.
  • Exam A memory space is something you name and address. A cache is a hardware copy of global data that fills and empties by itself. This difference decides questions like Q8.

3.2Coalescing: reading global memory well

  • Sectors Warp loads are coalesced into 32 byte sectors. Efficiency = 32 × element ÷ (sectors × 32).
  • Strides Floats: stride 1 → 4 sectors, 2 → 8, 4 → 16, ≥ 8 → 32. Misaligned start adds a sector.
  • Row major Let threadIdx.x move along the row. Q5 store B[x·h + y] touches 32 segments.
  • Sector model Useful bandwidth ≈ stride 1 bandwidth ÷ min(s, 8). T4 206 GB/s at stride 1.
  • Fixes SoA instead of AoS, float4 loads, and shared memory tiles for transposes.
  • Bytes the warp wantsuseful = 32 × element size
  • Efficiencyefficiency = useful bytes ÷ (sectors × 32)
  • Sector modeluseful bandwidth ≈ (stride 1 bandwidth) ÷ min(s, 8)

3.3Shared memory and bank conflicts

  • Shared memory __shared__, one copy per block, fill then __syncthreads() then read. extern __shared__ size is the third launch value.
  • Banks 32 banks × 4 bytes. bank = ⌊byte ÷ 4⌋ mod 32. Different words in one bank take turns.
  • Conflicts Stride s gives gcd(s, 32) ways. Same word is a broadcast, no conflict.
  • Padding Tile [32][33] makes column reads conflict free for 128 extra bytes.
  • Layout Let lanes write consecutive words: powers example 1024 passes against 32.
  • Bank of an addressbank = ⌊byte address ÷ 4⌋ mod 32
  • Conflict for stride sways = gcd(s, 32)
  • Trap __syncthreads() must be reached by every thread of the block. Putting it inside an if that only some threads enter can hang the block or give wrong results.

Step 4Numbers and performance limits

4.1Floating point numbers on the GPU

  • Format value = (−1)^S × 1.f × 2^(E − bias). Float 1/8/23 bias 127, double 1/11/52 bias 1023.
  • Exact Exact in binary only when the denominator is a power of 2. 5.6 is stored as 5.599999904632568.
  • Add Align exponents, add mantissas, normalise, round. Not associative: compare with a tolerance.
  • FMA a × b + c with one rounding, one instruction, counted as 2 FLOPs.
  • Formats FP16 1/5/10 (max 65,504), BF16 1/8/7, TF32 1/8/10. Epsilon = 2^−mantissa bits.
  • IEEE-754 valuevalue = (−1)S × 1.f × 2E − bias
  • Trap The lecture 5 notes give 1.00101₂ = 1.5625. Adding the bits gives 1 + 0.125 + 0.03125 = 1.15625 = 37/32, which is the value the workbook uses.
  • Exam A GPU reduction adds numbers in a different order from a CPU loop, so float sums can differ in the last digits. That is expected. Compare float results with a tolerance, never with ==.

4.2FLOPs, bandwidth and the roofline

  • FLOPs Matmul 2n³, k × k filter 2k² per output. Peak = SMs × cores × 2 × clock. FMA = 2 FLOPs.
  • Bandwidth GB/s = (read + written bytes) ÷ 10⁹ ÷ s. Count both directions.
  • AI FLOPs ÷ bytes. SAXPY 1/6, plain matmul 0.25, perfect reuse n/8 float, n/16 double.
  • Roofline Attainable = min(peak, AI × B). Ridge = peak ÷ B. Left memory bound, right compute bound.
  • Time bound t ≥ max(FLOPs ÷ peak, bytes ÷ bandwidth). Memory bound kernels gain nothing from more cores.
  • Matrix multiply n × nFLOPs = 2n³
  • Peak of a GPUpeak = SMs × cores per SM × 2 (FMA) × clock
  • BandwidthGB/s = (bytes read + bytes written) ÷ 10⁹ ÷ seconds
  • Arithmetic intensityAI = FLOPs ÷ bytes moved to or from DRAM
  • Attainable speedattainable = min(peak FLOP/s, AI × bandwidth)
  • Ridge pointAIridge = peak ÷ bandwidth
  • Exam For a memory bound kernel, doubling the maths units changes nothing. Only more bandwidth or more reuse helps. Doubling Fermi's cores gives plain matrix multiply no gain.

Step 5Parallel patterns

5.1Parallel reduction

  • Tree log₂ n levels, n − 1 additions, 1 + levels barriers. 1024 → 10 levels, 11 barriers.
  • Pairing Sequential (t < s, s halves) packs active threads: only levels with s < 32 split a warp.
  • Barrier rule Every thread must reach every __syncthreads(). Never put it inside a divergent if.
  • Grid One atomicAdd per block (⌈n/B⌉ atomics) or repeated launches until one value is left.
  • Shuffles __shfl_down_sync with offsets 16 to 1 sums a warp in 5 steps without shared memory.
  • Levelslevels = ⌈log₂ n⌉
  • Additionstotal additions = n − 1
  • Atomics neededone per block = ⌈n ÷ B⌉

5.2Tiled matrix multiplication

  • Plain 2N loads per thread, 2N³ total (not N² as slide 8 says). Q2: 524,288 per block.
  • Tiled ⌈N/T⌉ phases, 2⌈N/T⌉ loads per thread, 2N³/T total. Q3: 32,768 per block.
  • Barriers Sync after loading the tile and again before the next phase. Q4: without them both a and b happen (answer 3).
  • Ragged Pad out of range loads with 0 and guard the store. n = 5, T = 4: 4 blocks, 39 idle.
  • Limits T² ≤ 1024 threads so T ≤ 32. Shared memory 8T² bytes. AI ≈ T/4.
  • Loads per thread (plain)2N
  • Loads per block (plain)threads per block × 2N
  • Phasesphases = ⌈N ÷ T⌉
  • Loads per thread (tiled)2 × ⌈N ÷ T⌉
  • Total loads (tiled)2N²⌈N ÷ T⌉ = 2N³ ÷ T when T divides N
  • Trap Lecture 7 slide 8 states the plain kernel reads Width² values. Each of the Width² threads reads 2 × Width values, so the total is 2 × Width³.

5.3Stencils, halos and heat simulation

  • Stencil Each output from a fixed neighbour pattern. 2-D: ±1, ±W. 3-D: ±1, ±N, ±N².
  • Halo Tile B + 2R. Reads per output (B + 2R)/B against 2R + 1. Barrier after loading.
  • 3-D tiles AI = 13(T − 2)³/(4T³) ≤ 3.25. Halo share 57.8 percent at T = 8. Memory bound.
  • Heat Tnew = (1 − 6λ)T + λΣ6. Weights must add to 1 (slide 14 used 0.25 + 0.6). Stable for λ ≤ 1/6.
  • Ping-pong Read the old grid, write the new grid, swap pointers.
  • Neighbours in 2-DN = i − W, S = i + W, W = i − 1, E = i + 1
  • Neighbours in 3-D± 1, ± N, ± N²
  • Tile sizeB + 2R values
  • Global reads per output(B + 2R) ÷ B with the tile, 2R + 1 without
  • With T × T × T tilesAI(T) = 13 × (T − 2)³ ÷ (4T³)
  • Halo share(T³ − (T − 2)³) ÷ T³
  • 3-D explicit heat stepTnew = (1 − 6λ) T + λ × (sum of 6 neighbours)
  • Stabilityλ ≤ 1/6 in 3-D, 1/4 in 2-D, 1/2 in 1-D
  • Trap Lecture 6 slide 14 uses 0.25 for the centre and 0.1 for each of the 6 neighbours. They add to 0.85, so a field of 100 drops to 85 every step. With neighbour weight 0.1 the centre must be 1 − 6 × 0.1 = 0.4.

5.4Convolution and Sobel edge detection

  • Size out = ⌊(W + 2P − K)/S⌋ + 1. Same padding P = (K − 1)/2.
  • Work MACs = out² K² Cin Cout. FLOPs = 2 × MACs.
  • Sobel Gx, Gy 3 × 3. M1 = |Sx| + |Sy| clamped to 255. Weights in constant memory.
  • Tiles Tile (B + 2r)², loads per output (B + 2r)²/B², best saving 1 − 1/K².
  • Correction Sharpening 30 with 25, 35, 20, 40 gives 30, not 35. Smooth slopes do not change.
  • Output sizeout = ⌊(W + 2P − K) ÷ S⌋ + 1
  • Workmultiply-adds = out² × K² × Cin × Cout
  • Edge strengthM1 = |Sx| + |Sy|, M2 = √(Sx² + Sy²)
  • Tile sideB + 2r, with r = (K − 1) ÷ 2
  • Loads per output(B + 2r)² ÷ B²
  • Trap Lecture 8 sharpens the pixel 30 at (2, 1) to 35. With neighbours 25, 35, 20 and 40 the result is 5 × 30 − 120 = 30. On a smooth slope sharpening changes nothing.

5.5Scan, compaction and histograms

  • Scan Inclusive y_i = x_0 + … + x_i. Exclusive starts at 0 and stops before x_i.
  • Algorithms Hillis and Steele: log₂ n steps, n log₂ n − (n − 1) adds. Blelloch: 2 log₂ n steps, 2(n − 1) adds.
  • Race Never scan in place in one step. Double buffer or barrier between read and write.
  • Compaction Exclusive scan of keep flags gives each kept value its output slot.
  • Histogram Atomics per bin. Privatise in shared memory, merge with at most blocks × bins global atomics.
  • Inclusive scanyi = x0 + x1 + … + xi
  • Exclusive scanyi = x0 + … + xi−1, y0 = 0
  • Privatised (shared memory) histogramglobal atomics = blocks × bins at most
  • Trap Updating one array in place with buf[t] += buf[t − off] is a race: thread t may read buf[t − off] after thread t − off has already added to it. Double buffering or a barrier between the read and the write fixes it.

Step 6Execution and overlap

6.1Warp divergence and warp scheduling

  • Divergence Inside a warp only. Time = sum of used path lengths. Efficiency = lane ticks ÷ (32 × time).
  • Q9 tid % 4 == 1 → lanes 1, 5, …, 29, sum 120.
  • Avoid it Branch on warp number, use selects, keep data dependent branches short.
  • Schedulers RR waits together, GTO spreads loads (best = (instructions − 1) + L), two level in between.
  • Hiding Warps = ⌈(W + c) ÷ c⌉. More ILP per warp means fewer warps needed.
  • Warp timetime = sum of the lengths of every path at least one lane takes
  • Efficiencyefficiency = (sum over lanes of their path length) ÷ (32 × warp time)
  • Best possible finishfinish ≥ (total instructions − 1) + L
  • Warps to hide a waitwarps = ⌈(W + c) ÷ c⌉

6.2Streams, asynchrony and overlap

  • Async Launches and cudaMemcpyAsync return at once. cudaMemcpy and the synchronise calls block the CPU.
  • Streams In order inside a stream, overlap across streams. Async copies need pinned memory.
  • Pipeline Equal stages: (N + 2)t, speedup 3N/(N + 2) < 3. Unequal: fill + N × slowest stage.
  • Danger Not kernels overwriting each other in one stream, but the CPU reading before the GPU is done.
  • Events cudaEventRecord marks a point. ElapsedTime for timing, StreamWaitEvent for cross stream order.
  • Serialt = N × (tin + tkernel + tout)
  • Overlapped, equal stages tt = (N + 2) × t, speedup 3N ÷ (N + 2)
  • Trap In class it was said that asynchrony is dangerous because a second kernel could overwrite the first. Work in one stream always runs in order. The real danger is the CPU reading or reusing a host buffer before the GPU has finished with it. Synchronise before reading results.

Step 7Synchronisation

7.1Race conditions and locks

  • Three steps counter++ is load, add, store. Other threads can come between them.
  • Counting orders (n × s)! ÷ (s!)ⁿ. Two threads: 20, three threads: 1680. Only the serial orders are correct.
  • Three rules Mutual exclusion, progress, bounded waiting. Breaking them gives two inside, deadlock, starvation.
  • Dekker attempts 1 fails progress (strict turns), 2 fails mutual exclusion (not deadlock), 3 deadlocks.
  • Peterson flag[me] = 1, turn = other, wait while flag[other] and turn == other. Correct, with fences on real hardware.
  • N threads Bakery: tickets plus id, first come first served. Filter: N − 1 gates, starvation free but not bounded.
  • Orders of n threads with s steps each(n × s)! ÷ (s!)n
  • Three threads, three steps9! ÷ (3!)3 = 1680
  • Trap The unsafe result is not guaranteed to be 1. It depends on how the hardware schedules the threads. A race means the answer is unpredictable, which is worse than always wrong.
  • Exam Slide 8 says attempt 2 can deadlock. It cannot: a thread sets its flag only after passing its loop, so nobody waits after the flags are set. The real flaw is that both can pass the check, which breaks mutual exclusion. The class also concluded that the three attempts suffer from the same drawback. They fail in three different ways: attempt 2 checks too early, attempt 3 claims too early, attempt 1 is safe but too rigid.
  • Exam In class the conclusion was that the deadlock danger is still looming. That is not correct. With reads and writes that happen in program order, Peterson meets all three rules. Swapping steps 1 and 2 (turn first, then flag) does break mutual exclusion, so the order matters.
  • Exam Slide 3 says the Filter lock has bounded waiting. It is starvation free (every waiting thread gets in in the end), but a thread can be overtaken any number of times at a gate, so there is no fixed bound r. The Bakery lock is the one with first come, first served order.

7.2Barriers, atomics and GPU locks

  • Barrier against lock __syncthreads(): all threads of one block meet. Lock: one thread at a time, only those who want it wait.
  • Who shares Registers: nothing. Shared memory: __syncthreads(). Global across blocks: atomics, locks or a new kernel.
  • atomicCAS lock Spin on atomicCAS(&l, 0, 1) until it returns 0, do the work, call __threadfence(), then atomicExch(&l, 0). One thread per block takes it.
  • Privatisation Count in shared memory, then one global atomicAdd per block. 10 × 256: 2560 global atomics become 10.
  • Priority counter Same level runs together, levels get skipped, and non resident blocks can deadlock. grid.sync() needs a cooperative launch.
  • Compare and swapold = *p, if old = cmp then *p = v, return old
  • Largest cooperative gridblocks ≤ (blocks per SM) × (number of SMs)
  • Trap Every thread of the block must reach every __syncthreads(). A barrier inside an if that only some threads enter is undefined behaviour: the kernel may hang, or seem to work and give wrong results. The reduction chapter shows the lecture 12 example.
  • Exam The slide's critical_kernel lets every thread call acquire_lock. Before Volta (2017) the 32 lanes of a warp move in lock step. One lane wins the lock, but the warp keeps running the spin loop for the losers and never lets the winner reach release_lock, so the kernel hangs. Newer GPUs avoid the hang, but the lock then makes every thread of the grid wait in a single line, which is very slow. Take the lock with one thread per block, and add a fence before the release.
  • Exam In the block priority code of slide 7, the counter must be read as volatile or atomically, or the compiler may move the read out of the loop and spin for ever. CUDA does not promise which blocks are running or in what order they start. That this code usually works is luck.

Step 8Tensor cores and fast matmul

8.1Low precision numbers and quantisation

  • The formula x = (−1)^s × 1.m × 2^(e − bias), bias = 2^(E−1) − 1, gap after 1.0 = 2^−M.
  • Range against detail Exponent bits give range, mantissa bits give detail. FP16 overflows at 65,504, BF16 keeps FP32 range with about 2 to 3 digits.
  • Which format FP32 master weights, BF16 training, FP16 with loss scaling, TF32 for FP32 code on tensor cores, INT8 or FP8 for inference.
  • Wide accumulator Narrow inputs, FP32 sums. In FP16, 2048 + 1 = 2048.
  • Quantisation q = round(x ÷ s) + z, x̂ = s(q − z). Symmetric INT8: s = R ÷ 127. Error at most s ÷ 2 unless clipped.
  • Fewer bytes, higher intensityAI = FLOPs ÷ bytes
  • Value of a normal numberx = (−1)s × 1.m1m2…mM (binary) × 2e − bias
  • Biasbias = 2E − 1 − 1
  • Quantiseq = clip(round(x ÷ s) + z, qmin, qmax)
  • Bring backx̂ = s × (q − z)
  • Exam Slide 11's bars (TF32, FP16 and BF16 at 4 times, FP8 at 8, FP4 at 16) are labelled illustrative. On an A100, TF32 is 8 times and FP16 16 times the FP32 CUDA core rate. Always use the data sheet of the GPU in front of you.

8.2Tensor cores, GEMM and WMMA

  • Math limited test AI = ops ÷ bytes > peak ÷ bandwidth. A100 FP16 ridge ≈ 201.
  • FC layer AI = N_in N_out B ÷ (N_in B + N_in N_out + N_out B). 4096 layer: 4096B ÷ (4096 + 2B), math limited from batch 223.
  • GEMM 2MNK FLOPs. Convolution: M = out channels, N = batch × output pixels, K = in channels × filter size (implicit GEMM).
  • Tensor core peak SMs × TCs × FMAs per clock × 2 × clock. V100 125, A100 312, H100 989 TFLOP/s.
  • WMMA One warp per 16 × 16 tile, fragments, load_matrix_sync, mma_sync (8192 FLOPs), store_matrix_sync. FP16 in, FP32 sum.
  • Waves waves = ⌈blocks ÷ (SMs × blocks per SM)⌉, efficiency = n ÷ (W × waves). 217 blocks on 108 SMs: 67 percent.
  • Math limited whenops ÷ bytes > BWmath ÷ BWmem
  • 4096 × 4096 layerAI = 4096 B ÷ (4096 + 2B)
  • Peak of the tensor corespeak = SMs × tensor cores per SM × FMAs per clock × 2 × clock
  • Waveswaves = ⌈blocks ÷ (blocks per SM × SMs)⌉
  • Wave efficiencyn ÷ (W × ⌈n ÷ W⌉), with W = blocks per wave
  • Exam Slide 16 says shared memory is used for the matrix C. In real kernels such as CUTLASS, C stays in registers during the main loop and only passes through shared memory when it is written out at the end.

8.3How fast matmul kernels are built

  • Speed of light H100 SXM BF16: 132 × 4 tensor cores × 1024 FLOPs × 1.83 GHz ≈ 989 TFLOP/s. Power throttling lowers the real ceiling.
  • Naive kernel Coalesced order 3171 GFLOP/s (43 ms), swapped order 243 GFLOP/s (565 ms). 13 times from one index.
  • Tile intensity AI = (2 ÷ b) B_M B_N ÷ (B_M + B_N). Square is best. FP32 T × T: T ÷ 4. BF16: T ÷ 2.
  • Hopper TMA copies tiles, swizzle slot = chunk XOR row, wgmma on 4 warps, producer and consumer warp groups.
  • Ladder 32 (no tensor cores) to 317 (tensor cores + TMA) to 764 TFLOP/s, about 77 percent of peak.
  • Intensity of a BM × BN tileAI = (2 ÷ b) × BMBN ÷ (BM + BN)
  • Square FP32 tile T × TAI = T ÷ 4
  • Exam With the numbers used here (756 TFLOP/s BF16 on the PCIe card, 2.0 TB/s) the ridge is about 378 FLOP/byte. The blog quotes about 410 with slightly different specs. Either way a kernel needs hundreds of FLOPs per DRAM byte, so tiles must also be reused through L2 and shared memory.

Step 9Tools and Python on the GPU

9.1Debugging and profiling CUDA code

  • Order of tools Check every call. Wrong: compute-sanitizer, printf, cuda-gdb. Slow: nsys, then ncu on the hot kernel.
  • Sanitizer tools memcheck (bounds), racecheck (shared memory races), initcheck (uninitialised reads), synccheck (bad barriers).
  • cuda-gdb Build with -g -G. set cuda break_on_launch application, cuda block (1,0,0) thread (31,0,0), p x.
  • Reading a report Time = cycles ÷ clock. SM active ÷ elapsed shows idle SMs. Both units under 60 percent: latency bound, read the stall reasons.
  • PTX and SASS PTX is virtual and portable (%ctaid.x, ld.global), SASS is the real code (S2R, LDG, FADD, STG). See them with nvcc -ptx, cuobjdump -sass.
  • Trap This program usually runs without any message. The stray writes land in memory the program happens to own, so nothing crashes. That is exactly why out of bounds bugs are dangerous and why the sanitizer comes first.
  • Exam Slide 6 says threads 0 to 21 write out of bounds. Thread i writes data[i + 10], so even thread 0 writes data[10], one past the end. All 32 threads write out of bounds, to indices 10 to 41.

10.2Challenge problems

  • Batch threshold n × n layer: AI = nB ÷ (n + 2B). A100 4096: 223. H100 4096: 345. A100 1024: 330.
