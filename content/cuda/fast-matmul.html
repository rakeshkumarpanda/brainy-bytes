Lesson 1 of 6

The H100 and its speed of light

The blog that lecture 9 recommends builds a matmul for the H100 step by step. First, the machine.

PartH100 SXM5
SMs132 (the full chip has 144, some are switched off)
Each SM4 quadrants, each with a warp scheduler, FP32 units, a tensor core and load and store units
Warps issuing per clock4 per SM (one per quadrant), out of up to 64 resident
Registers64K 32 bit registers per SM
Shared memory and L1up to 228 KB per SM, the same SRAM split by configuration
L250 MB, shared by all SMs
HBM380 GB at about 3.35 TB/s

Only 4 warps per SM issue in a given clock, but 64 can wait their turn. The extra warps hide memory latency, as in the scheduling chapter. A block should have at least 4 warps so all four schedulers have work.

Why the memory pyramid exists: SRAM (registers, caches) needs 6 transistors per bit, so it is fast but small. DRAM needs one transistor and one capacitor per bit, so it is dense, cheap and slow. Opening a DRAM row is the expensive part, and reading neighbouring columns of an open row is cheap. That is the physical reason for coalescing.

Workbook 9.4: H100 SXM5 BF16 peak
  1. Tensor cores: 132 × 4 = 528.
  2. Each does 512 BF16 FMAs = 1024 FLOPs per clock.
  3. 528 × 1024 × 1.83 × 10⁹.
  4. ≈ 989 TFLOP/s
Remember
Under a heavy matmul the H100 reaches its 700 W power limit and lowers its clock. At 1.5 GHz the peak is 989 × 1.5 ÷ 1.83 ≈ 811 TFLOP/s, so a kernel at 750 TFLOP/s is at about 92.5 percent of what is reachable.
Lesson 2 of 6

The naive kernel and a 13 times lesson

One thread per output, blocks of 32 × 32 threads, N = 4096. The only difference between the two kernels below is which index the x thread number feeds.

naive.cu
__global__ void matmul_fast_order(const float *A, const float *B, float *C, int N) {    int row = blockIdx.y * blockDim.y + threadIdx.y;    int col = blockIdx.x * blockDim.x + threadIdx.x;     // neighbouring threads take neighbouring columns    if (row < N && col < N) {        float acc = 0.0f;        for (int k = 0; k < N; ++k)            acc += A[row * N + k] * B[k * N + col];       // B along a row: coalesced        C[row * N + col] = acc;    }} __global__ void matmul_slow_order(const float *A, const float *B, float *C, int N) {    int row = blockIdx.x * blockDim.x + threadIdx.x;     // neighbouring threads take neighbouring rows    int col = blockIdx.y * blockDim.y + threadIdx.y;    if (row < N && col < N) {        float acc = 0.0f;        for (int k = 0; k < N; ++k)            acc += A[row * N + k] * B[k * N + col];       // A with a stride of N: not coalesced        C[row * N + col] = acc;    }}
What each marked line does and why
  1. Line 3int col = blockIdx.x * blockDim.x + threadIdx.x; // neighbouring threads take neighbouring columnsThreads next to each other in a warp take columns next to each other.
  2. Line 7acc += A[row * N + k] * B[k * N + col]; // B along a row: coalescedB[k * N + col] is read at consecutive addresses across the warp, and A[row * N + k] is the same address for the whole warp: both are cheap.
  3. Line 8C[row * N + col] = acc;The writes to C are consecutive too.
  4. Line 13int row = blockIdx.x * blockDim.x + threadIdx.x; // neighbouring threads take neighbouring rowsNow neighbouring threads take neighbouring rows.
  5. Line 18acc += A[row * N + k] * B[k * N + col]; // A with a stride of N: not coalescedA[row * N + k] jumps N floats between neighbouring threads, so every thread needs its own memory sector.
KernelMeasured on H100Time for 2 × 4096³ FLOPs
x feeds the column (coalesced)3171 GFLOP/s43 ms
x feeds the row (uncoalesced)243 GFLOP/s565 ms, 13 times slower

One line of index arithmetic costs 13 times. The rule from the coalescing chapter: what matters is what neighbouring threads read at the same moment, not what one thread reads over time.

Going deeper: Tile quantisation and PTX against SASS

A 33 × 33 matrix with 32 × 32 tiles needs 2 × 2 tiles: 4096 threads for 1089 outputs, so 73 percent of threads do nothing. In the SASS of the naive kernel, ptxas unrolled the loop 16 times and moved all loads to the top so they overlap with the FMAs. Researchers have gained 15 percent by rewriting SASS by hand to avoid bank conflicts.

Lesson 3 of 6

Tiles: more work per byte

The naive kernel has an arithmetic intensity of 0.25 (2 FLOPs per 8 bytes loaded). It reaches 3.17 TFLOP/s only because the caches serve repeated loads. To get further, each block keeps a tile of A and of B in shared memory and reuses them.

Intensity of a BM × BN tileExam favourite
AI = (2 ÷ b) × BMBN ÷ (BM + BN)
b = bytes per number. BK cancels, so only the tile shape matters.
Square is best
BM + BN ≥ 2√(BMBN)
For a fixed area the sum is smallest when BM = BN (AM-GM).
Square FP32 tile T × TExam favourite
AI = T ÷ 4
32 × 32: 8. 128 × 128: 32. BF16 doubles these: AI = T ÷ 2.

Thread tiling. The same idea one level down: each thread keeps a TM × TN block of results in registers. Per k step it loads TM + TN numbers from shared memory and does TM × TN FMAs.

thread_tile.cu
// Inner loop of a thread tile: each thread keeps TM x TN results in registerstemplate <int TM, int TN>__device__ void thread_tile(const float *As, const float *Bs, float acc[TM][TN],                            int ty, int tx, int BK, int BM, int BN) {    float a[TM], b[TN];    for (int k = 0; k < BK; ++k) {        for (int i = 0; i < TM; ++i) a[i] = As[k * BM + ty * TM + i];   // A is stored transposed in shared memory        for (int j = 0; j < TN; ++j) b[j] = Bs[k * BN + tx * TN + j];        for (int i = 0; i < TM; ++i)            for (int j = 0; j < TN; ++j)                acc[i][j] += a[i] * b[j];                               // TM x TN FMAs from TM + TN loads    }}
What each marked line does and why
  1. Line 2template <int TM, int TN>TM and TN are fixed at compile time so the arrays stay in registers.
  2. Line 7for (int i = 0; i < TM; ++i) a[i] = As[k * BM + ty * TM + i]; // A is stored transposed in shared memoryA is stored transposed in shared memory so these reads are contiguous and can use 128 bit loads.
  3. Line 9for (int i = 0; i < TM; ++i)An outer product of a column of A and a row of B.
  4. Line 11acc[i][j] += a[i] * b[j]; // TM x TN FMAs from TM + TN loadsTM × TN FMAs for TM + TN loads. 8 × 8 gives 64 FMAs for 16 loads.

The blog's best kernel before tensor cores uses 128 × 128 block tiles with BK = 16, thread tiles of results in registers, 128 bit loads, and two __syncthreads() per k step. This is warp tiling. It reaches about 32 TFLOP/s on the H100, the best the plain FP32 cores manage in the blog, and far below what tensor cores offer.

In the exam
With the numbers used here (756 TFLOP/s BF16 on the PCIe card, 2.0 TB/s) the ridge is about 378 FLOP/byte. The blog quotes about 410 with slightly different specs. Either way a kernel needs hundreds of FLOPs per DRAM byte, so tiles must also be reused through L2 and shared memory.
Lesson 4 of 6

Hopper tricks: TMA, swizzling, wgmma, pipelines

TMA (tensor memory accelerator) is a copy engine inside each SM. One thread asks it to move a whole 64 × 64 tile from global to shared memory. A barrier in shared memory counts the bytes that arrive, so the waiting threads continue only when the whole tile has landed.

Swizzling solves bank conflicts. A 128 byte row is 8 chunks of 16 bytes, and each chunk covers 4 banks. Reading one column of 8 rows hits the same 4 banks 8 times. Store chunk c of row r in slot c XOR r instead, and the column spreads over all 8 slots.

swizzle.cu
// 128 byte swizzle: XOR the row within a group of 8 rows (bits 7 to 9) into the 16 byte chunk index (bits 4 to 6)__device__ __forceinline__ unsigned swizzle128(unsigned byte_offset) {    unsigned row8 = (byte_offset >> 7) & 7;    return byte_offset ^ (row8 << 4);}
What each marked line does and why
  1. Line 3unsigned row8 = (byte_offset >> 7) & 7;Bits 7 to 9 of the byte offset give the row inside a group of 8 rows of 128 bytes.
  2. Line 4return byte_offset ^ (row8 << 4);XOR the row into bits 4 to 6, the index of the 16 byte chunk. Applying it twice gives back the original offset.
Worked XOR example
  1. Row 5, chunk 2: 010 XOR 101 = 111 = 7, stored in slot 7.
  2. Row 5, chunk 7: 111 XOR 101 = 010 = 2.
  3. So chunks 2 and 7 of row 5 swap places.
  4. XOR with a fixed value is its own inverse

wgmma. On Hopper a warp group (4 warps, 128 threads) issues asynchronous tensor core instructions of shape m64nNk16. A 64 × 64 output needs four m64n64k16 calls for K = 64, and the accumulator is spread as 64 × 64 ÷ 128 = 32 FP32 registers per thread.

Producer and consumer pipeline. One warp group only issues TMA loads into a ring of shared memory buffers. One or two other warp groups only run tensor core maths. Two barriers per buffer (full and empty) keep them in step. This is the stream overlap idea from chapter 6.2, inside one SM.

Lesson 5 of 6

The performance ladder

Each step fixes one bottleneck. Step through the numbers reported in the blog for BF16 on an H100.

The biggest jump, from 32 to 317 TFLOP/s, is simply using tensor cores fed by TMA. Everything after that keeps the tensor cores busy: bigger tiles (higher AI), overlap (pipelines), no idle SMs (persistent kernels), better cache reuse (clusters, Hilbert order) and cheaper waiting (faster barriers). The final 764 TFLOP/s is about 77 percent of the 989 peak, on par with cuBLAS.

From intuition to research

One idea, four depths

Build the fastest kitchen: first stop the waiter running back and forth (coalescing), then keep ingredients on the counter (tiles), then hire the stamping machine (tensor cores), then make sure it never waits (pipelines).

Naive coalesced 43 ms, uncoalesced 565 ms. Tile AI = (2 ÷ b) BMBN ÷ (BM + BN). H100 BF16 peak 989, ridge about 378. Swizzle slot = chunk XOR row.

Profile each step in Nsight Compute: memory throughput, bank conflicts, tensor core utilisation, stall reasons. Change one thing at a time and keep the numbers.
