Lesson 1 of 6

A workflow for wrong or slow code

GPU bugs are hard to see. Thousands of threads run at once, errors appear later than the line that caused them, and a wrong write often does not crash. Lecture 12 gives a fixed order of tools.

  1. Check every callWrap each CUDA call in a check and call cudaGetLastError after each launch.
  2. Wrong result?compute-sanitizer first, then printf on a few threads, then cuda-gdb.
  3. Slow?Nsight Systems for the whole timeline, then Nsight Compute on the slowest kernel.
  4. Measure againChange one thing and re-measure.
bad_mem.cu
#include <cstdio>#include <cstdlib> #define CUDA_CHECK(call)                                                   \    do {                                                                   \        cudaError_t err = (call);                                          \        if (err != cudaSuccess) {                                          \            fprintf(stderr, "CUDA error %s at %s:%d\n",                    \                    cudaGetErrorString(err), __FILE__, __LINE__);          \            exit(1);                                                       \        }                                                                  \    } while (0) __global__ void badAccess(int *data) {    int i = threadIdx.x;    data[i + 10] = i;                                 // writes data[10] to data[41]    if (i < 2) printf("thread %d writes index %d\n", i, i + 10);} int main() {    int *d;    CUDA_CHECK(cudaMalloc(&d, 10 * sizeof(int)));     // valid indices 0 to 9 only    badAccess<<<1, 32>>>(d);    CUDA_CHECK(cudaGetLastError());                   // errors in the launch itself    CUDA_CHECK(cudaDeviceSynchronize());              // errors while the kernel ran    CUDA_CHECK(cudaFree(d));    return 0;}
What each marked line does and why
  1. Line 4#define CUDA_CHECK(call) \A macro so that every call reports the file and line where it failed.
  2. Line 6cudaError_t err = (call); \Every CUDA runtime call returns an error code.
  3. Line 9cudaGetErrorString(err), __FILE__, __LINE__); \cudaGetErrorString turns the code into readable text.
  4. Line 12} while (0)The do and while (0) wrapper makes the macro behave like one statement.
  5. Line 16data[i + 10] = i; // writes data[10] to data[41]The bug from lecture 12: thread i writes index i + 10.
  6. Line 17if (i < 2) printf("thread %d writes index %d\n", i, i + 10);printf works inside kernels. Filter it, or thousands of threads flood the output.
  7. Line 22CUDA_CHECK(cudaMalloc(&d, 10 * sizeof(int))); // valid indices 0 to 9 onlyOnly 10 ints are allocated.
  8. Line 24CUDA_CHECK(cudaGetLastError()); // errors in the launch itselfCatches errors in the launch itself, such as too many threads per block.
  9. Line 25CUDA_CHECK(cudaDeviceSynchronize()); // errors while the kernel ranCatches errors that happen while the kernel runs. Kernel errors show up only at a synchronising call.

Device printf output is buffered on the GPU and printed at the next synchronisation. The order between threads is not fixed. Setting CUDA_LAUNCH_BLOCKING=1 makes every launch synchronous, so an error is reported at the launch that caused it.

Common mistake
This program usually runs without any message. The stray writes land in memory the program happens to own, so nothing crashes. That is exactly why out of bounds bugs are dangerous and why the sanitizer comes first.

compute-sanitizer

compute-sanitizer runs your program and watches every memory access. It has four tools.

ToolFindsExample in this course
memcheck (default)out of bounds or misaligned accesses, bad frees, leaksbadAccess above
racecheckshared memory races (a missing __syncthreads)unsafe_inc in chapter 7.2
initcheckreads of global memory that was never writtenreading cudaMalloc memory before setting it
synccheckillegal barriers (a __syncthreads inside a divergent if)the reduction in chapter 5.1
Run the tools
nvcc -g -lineinfo bad_mem.cu -o bad_memcompute-sanitizer ./bad_memcompute-sanitizer --tool racecheck ./unsafe_inccompute-sanitizer --tool initcheck ./a.outcompute-sanitizer --tool synccheck ./reducecompute-sanitizer --leak-check full ./a.out

Lesson 3 of 6

Stepping through a kernel with cuda-gdb

cuda-gdb is the GNU debugger extended to GPUs. You can stop inside a kernel, step line by line, print device variables, and switch the focus to any block, thread, warp or lane. Compile with -g (host) and -G (device). -G turns off most device optimisations, so debug builds are slow.

bounds_bug.cu
#define N 64 __global__ void boundsBugAdd(const int *a, const int *b, int *c) {    int x = blockIdx.x * blockDim.x + threadIdx.x;    c[x + 1] = a[x] + b[x];            // bug: writes one element too far} __global__ void boundsFixedAdd(const int *a, const int *b, int *c) {    int x = blockIdx.x * blockDim.x + threadIdx.x;    if (x < N) c[x] = a[x] + b[x];     // fixed index and a guard}
What each marked line does and why
  1. Line 4int x = blockIdx.x * blockDim.x + threadIdx.x;x is the global thread index.
  2. Line 5c[x + 1] = a[x] + b[x]; // bug: writes one element too farThe bug: c[x + 1]. The last thread writes one element past the end.
  3. Line 10if (x < N) c[x] = a[x] + b[x]; // fixed index and a guardThe fix: write c[x] and guard with if (x < N), the standard pattern.
The session from the slides
nvcc -g -G bounds_bug.cu -o bounds_bugcuda-gdb ./bounds_bug(cuda-gdb) set cuda break_on_launch application(cuda-gdb) run(cuda-gdb) step(cuda-gdb) p x(cuda-gdb) cuda block (1,0,0) thread (31,0,0)(cuda-gdb) step(cuda-gdb) p x(cuda-gdb) info cuda threads
What the two prints show
p x in block 0, thread 0 prints 0
p x in block 1, thread 31 prints 63 (1 × 32 + 31)
Workbook 12.2: block 1, thread 31, blockDim 32
  1. x = 1 × 32 + 31 = 63.
  2. The thread writes c[x + 1] = c[64].
  3. The arrays hold 64 elements: indices 0 to 63.
  4. Index 64 is out of bounds

Breakpoints can be set by line (break 6), by file and line, by kernel name (break boundsBugAdd) or on every launch. info cuda warps and info cuda kernels list what is running.

Profiling with Nsight Systems and Nsight Compute

ToolShowsUse it
Nsight Systems (nsys)the whole program timeline: CPU, API calls, copies, kernels per stream, NVTX rangesfirst: which kernel or copy takes the time?
Nsight Compute (ncu)one kernel in depth: throughput, occupancy, traffic per memory level, stall reasons, rooflinesecond: why is that kernel slow?

Profile from the command line (works on Colab)

Stall reasons in Warp State Statistics tell you what the warps wait for: long scoreboard (global memory), barrier (__syncthreads), MIO throttle (shared memory pressure), not selected (another warp was chosen, which is fine). Other tools: CUDA events for timing a region, NVTX to name code ranges in the timeline, nvidia-smi for overall use, power and temperature, and CUPTI, the API all of these are built on.

Lesson 5 of 6

Reading PTX and SASS

nvcc compiles device code in two stages. PTX is a virtual assembly for an imaginary GPU with unlimited registers. It is readable and stable across generations. SASS is the real machine code of one GPU generation, produced from PTX by ptxas or by the driver at run time.

vec_add.cu
__global__ void vecAdd(const float *a, const float *b, float *c, int n) {    int i = blockIdx.x * blockDim.x + threadIdx.x;    if (i < n) c[i] = a[i] + b[i];}
What each marked line does and why
  1. Line 2int i = blockIdx.x * blockDim.x + threadIdx.x;The global index: blockIdx.x × blockDim.x + threadIdx.x.
  2. Line 3if (i < n) c[i] = a[i] + b[i];Guard, two loads, one add, one store.

Below is real PTX that a CUDA compiler (clang) produced for this kernel for sm_80. nvcc output looks very similar. Find each part of the C++ line in it.

vec_add.ptx
.visible .entry _Z6vecAddPKfS0_Pfi(	.param .u64 _Z6vecAddPKfS0_Pfi_param_0,	.param .u64 _Z6vecAddPKfS0_Pfi_param_1,	.param .u64 _Z6vecAddPKfS0_Pfi_param_2,	.param .u32 _Z6vecAddPKfS0_Pfi_param_3){	.reg .pred 	%p<2>;	.reg .b32 	%r<6>;	.reg .f32 	%f<4>;	.reg .b64 	%rd<11>; 	ld.param.u32 	%r1, [_Z6vecAddPKfS0_Pfi_param_3];	mov.u32 	%r2, %ctaid.x;	mov.u32 	%r3, %ntid.x;	mov.u32 	%r4, %tid.x;	mad.lo.s32 	%r5, %r2, %r3, %r4;	setp.ge.s32 	%p1, %r5, %r1;	@%p1 bra 	$L__BB0_2;	ld.param.u64 	%rd4, [_Z6vecAddPKfS0_Pfi_param_0];	ld.param.u64 	%rd5, [_Z6vecAddPKfS0_Pfi_param_2];	cvta.to.global.u64 	%rd6, %rd5;	ld.param.u64 	%rd7, [_Z6vecAddPKfS0_Pfi_param_1];	cvta.to.global.u64 	%rd8, %rd7;	cvta.to.global.u64 	%rd9, %rd4;	mul.wide.s32 	%rd10, %r5, 4;	add.s64 	%rd1, %rd6, %rd10;	add.s64 	%rd2, %rd8, %rd10;	add.s64 	%rd3, %rd9, %rd10;	ld.global.f32 	%f1, [%rd3];	ld.global.f32 	%f2, [%rd2];	add.f32 	%f3, %f1, %f2;	st.global.f32 	[%rd1], %f3;$L__BB0_2:	ret;}
What each marked line does and why
  1. Line 13ld.param.u32 %r1, [_Z6vecAddPKfS0_Pfi_param_3];Load the parameter n.
  2. Line 14mov.u32 %r2, %ctaid.x;%ctaid.x is blockIdx.x (CTA = cooperative thread array, the hardware name for a block).
  3. Line 15mov.u32 %r3, %ntid.x;%ntid.x is blockDim.x.
  4. Line 16mov.u32 %r4, %tid.x;%tid.x is threadIdx.x.
  5. Line 17mad.lo.s32 %r5, %r2, %r3, %r4;One multiply add builds the global index i.
  6. Line 18setp.ge.s32 %p1, %r5, %r1;Set a predicate: is i ≥ n?
  7. Line 19@%p1 bra $L__BB0_2;If so, jump to the end. This is the if (i < n) guard.
  8. Line 26mul.wide.s32 %rd10, %r5, 4;i × 4 bytes, widened to a 64 bit offset.
  9. Line 30ld.global.f32 %f1, [%rd3];Load a[i] from global memory.
  10. Line 31ld.global.f32 %f2, [%rd2];Load b[i].
  11. Line 32add.f32 %f3, %f1, %f2;The one useful instruction: the add.
  12. Line 33st.global.f32 [%rd1], %f3;Store c[i].
SASSMeaning
S2R R0, SR_CTAID.Xread a special register (blockIdx.x)
IMADinteger multiply add, for example the global index or an address
LDG.Eload from global memory with a 64 bit address
FADD, FFMAfloat add, fused multiply add
STG.Estore to global memory
ISETP, @P0 BRAcompare into a predicate, then a branch taken only where the predicate holds
See PTX and SASS yourself
nvcc -ptx -arch=sm_75 mat_mul.cunvcc -cubin -arch=sm_75 mat_mul.cunvdisasm mat_mul.cubincuobjdump -sass ./mm
Remember
Lecture 7 showed the PTX of the naive matmul: two ld.global loads for every mad. Global loads cost hundreds of cycles, the multiply add only a few. That is the case for tiling and shared memory, read straight from the compiler output.
Lesson 6 of 6

From intuition to research

One idea, four depths

A smoke alarm (CUDA_CHECK), a camera that watches every door (compute-sanitizer), a pause button (cuda-gdb) and a stopwatch with a map (Nsight).

Check every call. memcheck, racecheck, initcheck, synccheck. cuda-gdb with -g -G. nsys for the timeline, ncu for one kernel. Under 60 % on both units means latency bound.

Build with -lineinfo so Nsight Compute maps hot spots to source lines without -G. Use NVTX ranges. Compare against the roofline in ncu.

CUPTI lets you build your own tools. Research profilers attribute stalls to source lines and suggest fixes. Performance regression tests run ncu metrics in continuous integration.
