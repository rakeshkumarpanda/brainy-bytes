Lesson 1 of 5

Barrier or lock

There are two very different ways to make threads wait for each other.

A barrier such as __syncthreads() is a meeting point. Nobody in the block goes past it until everyone in the block has arrived. It is like a traffic light that stays red until the whole group is at the line.

A lock lets only one thread at a time into a critical section. The others wait outside, like a queue for a single restroom. Threads that do not need the section are not held up.

__syncthreads()Lock from atomicCAS
Purposeeveryone reaches a pointone at a time
Who waitsall threads of the blockonly threads that want the lock
Scopeone blockthe whole device (global memory), or shared memory
Typical usetiled matmul, reductions, stencilsglobal counters, shared queues, rare updates

The lecture ends with a simple rule: who shares a variable decides which tool you need.

Who shares the dataWhere it livesHow to synchronise
one threadregisters, local memorynothing
threads of one blockshared memory__syncthreads(), or shared atomics
threads of different blocksglobal memoryatomics, locks, or end the kernel and start another
Common mistake
Every thread of the block must reach every __syncthreads(). A barrier inside an if that only some threads enter is undefined behaviour: the kernel may hang, or seem to work and give wrong results. The reduction chapter shows the lecture 12 example.

Atomic instructions and the atomicCAS lock

An atomic operation reads, changes and writes a memory word as one step. No other thread can see or change the word in the middle. The hardware does this, so it is correct even with thousands of threads.

FunctionWhat it does as one stepReturns
atomicAdd(p, v)*p = *p + vthe old value
atomicSub, atomicMin, atomicMaxsubtract, keep the smaller, keep the largerthe old value
atomicExch(p, v)*p = vthe old value
atomicAnd, atomicOr, atomicXorbit operationsthe old value
atomicCAS(p, cmp, v)if *p == cmp then *p = vthe old value
Compare and swapExam favourite
old = *p, if old = cmp then *p = v, return old
If old = cmp, you won. Any other value means somebody else changed it first.

All threads try to change the lock from 0 to 1. Exactly one gets back 0 and goes in. Everyone else gets back 1 and tries again.

lock.cu
__device__ int lock = 0;                       // 0 = free, 1 = taken__device__ volatile int total = 0; __device__ void acquire(int *l) {    while (atomicCAS(l, 0, 1) != 0) ;          // try to change 0 into 1} __device__ void release(int *l) {    __threadfence();                           // writes in the critical section go first    atomicExch(l, 0);                          // free the lock} __global__ void add_block_sums(const int *part) {    if (threadIdx.x == 0) {                    // only one thread per block takes the lock        acquire(&lock);        total = total + part[blockIdx.x];      // the critical section        release(&lock);    }    __syncthreads();                           // the rest of the block waits here}
What each marked line does and why
  1. Line 2__device__ volatile int total = 0;volatile so the compiler reads total from memory each time and does not reuse a stale copy.
  2. Line 5while (atomicCAS(l, 0, 1) != 0) ; // try to change 0 into 1Spin until this thread is the one that changed 0 into 1.
  3. Line 9__threadfence(); // writes in the critical section go firstMake the writes of the critical section visible before anyone else can get the lock.
  4. Line 10atomicExch(l, 0); // free the lockatomicExch writes 0 as one step and frees the lock.
  5. Line 14if (threadIdx.x == 0) { // only one thread per block takes the lockOnly thread 0 of each block competes. 32 lanes of one warp spinning on the same lock could hang older GPUs.
  6. Line 16total = total + part[blockIdx.x]; // the critical sectionInside the lock one thread reads and writes total safely.
  7. Line 19__syncthreads(); // the rest of the block waits hereThe other threads of the block wait here for thread 0.
In the exam
The slide's critical_kernel lets every thread call acquire_lock. Before Volta (2017) the 32 lanes of a warp move in lock step. One lane wins the lock, but the warp keeps running the spin loop for the losers and never lets the winner reach release_lock, so the kernel hangs. Newer GPUs avoid the hang, but the lock then makes every thread of the grid wait in a single line, which is very slow. Take the lock with one thread per block, and add a fence before the release.

A plain CAS spin lock has no queue, so a thread can lose again and again. A ticket lock fixes this with two counters. It is the Bakery idea built from atomics.

ticket.cu
__device__ unsigned int next_ticket = 0;__device__ unsigned int now_serving = 0; __device__ void ticket_acquire() {    unsigned int my = atomicAdd(&next_ticket, 1);     // take a ticket    while (atomicAdd(&now_serving, 0) != my) ;        // an atomic read, until my number is called    __threadfence();} __device__ void ticket_release() {    __threadfence();    atomicAdd(&now_serving, 1);                       // call the next ticket}
What each marked line does and why
  1. Line 5unsigned int my = atomicAdd(&next_ticket, 1); // take a ticketatomicAdd returns the old value, so every thread gets a different ticket.
  2. Line 6while (atomicAdd(&now_serving, 0) != my) ; // an atomic read, until my number is calledAdding 0 is a way to read the counter atomically.
  3. Line 7__threadfence();The fence keeps reads in the critical section from running before the lock is held.
  4. Line 12atomicAdd(&now_serving, 1); // call the next ticketMoving the counter on lets the next ticket in, in arrival order.
Going deeper: Memory fences and their scope

A fence makes this thread's earlier writes visible before its later ones. __threadfence_block() covers the threads of the same block, __threadfence() the whole GPU, and __threadfence_system() the GPU and the CPU (for mapped host memory). A fence does not make anyone wait. It only fixes the order in which other threads can see the writes.

Lesson 3 of 5

Fewer atomics: privatisation

Atomics are always correct, but atomics on the same address are done one after another. Thousands of threads adding to one global counter form a long queue.

Lecture 12 shows the problem. In unsafe_inc every thread reads a shared variable, adds 1 and writes it back, so 10 threads in one warp give 1. The fix uses atomicAdd on the shared variable. With many blocks the best plan is privatisation: each block counts in its own shared memory first, then one thread adds the block total to global memory.

count_ones.cu
__global__ void count_ones(const int *x, int n, int *count) {    __shared__ int local;    if (threadIdx.x == 0) local = 0;    __syncthreads();    int i = blockIdx.x * blockDim.x + threadIdx.x;    if (i < n && x[i] == 1) atomicAdd(&local, 1);    // fast atomic inside the block    __syncthreads();    if (threadIdx.x == 0) atomicAdd(count, local);   // one global atomic per block}
What each marked line does and why
  1. Line 2__shared__ int local;One private counter per block, in fast shared memory.
  2. Line 3if (threadIdx.x == 0) local = 0;Start the block counter at 0, not at the global value. Otherwise blocks would count each other's work.
  3. Line 4__syncthreads();Everyone must see the 0 before adding.
  4. Line 6if (i < n && x[i] == 1) atomicAdd(&local, 1); // fast atomic inside the blockShared memory atomic: no lost updates and much cheaper than a global one.
  5. Line 7__syncthreads();Wait until all threads of the block have added.
  6. Line 8if (threadIdx.x == 0) atomicAdd(count, local); // one global atomic per blockOne global atomic per block instead of one per thread.
Workbook P10.2.5: 2²⁰ values, blocks of 1024, one atomic per block
  1. Blocks = 1,048,576 ÷ 1024 = 1024.
  2. Each block reduces its values in shared memory and does one global atomicAdd.
  3. One atomic per element would be 1,048,576.
  4. 1024 global atomics instead of 1,048,576
Remember
compute-sanitizer --tool racecheck finds races on shared memory, such as the unsafe_inc example. Run it whenever a result changes from run to run.

Priority locks and grid wide barriers

Lecture 11 builds a priority lock from one "now serving" counter, like the token display at a clinic. A thread waits until the counter equals its priority, works, and then adds 1.

ProblemWhyFix
Not mutual exclusionAll threads with the same priority pass together.Add a real lock inside each level.
Levels get skippedThree threads at level 2 each add 1, so the counter goes from 2 to 5.Move the counter on once per level, when the last thread of that level is done.
Deadlock by residencyIf the priority 0 blocks are not running yet because spinning blocks fill the GPU, nobody moves the counter.Do not spin on other blocks. Use a grid barrier or separate kernels.
StarvationA steady stream of high priority work keeps low priority work waiting.Ageing: raise the priority of work that has waited long.
In the exam
In the block priority code of slide 7, the counter must be read as volatile or atomically, or the compiler may move the read out of the loop and spin for ever. CUDA does not promise which blocks are running or in what order they start. That this code usually works is luck.

Cooperative groups name a group of threads (a warp tile, a block, a cluster or the whole grid) and synchronise exactly that group. grid.sync() is a barrier for every thread of the launch, which __syncthreads() cannot do.

grid_sync.cu
#include <cooperative_groups.h>namespace cg = cooperative_groups; __global__ void two_phase(float *a, float *b, int n) {    cg::grid_group grid = cg::this_grid();       // every thread of the launch    int i = grid.thread_rank();    if (i < n) a[i] = a[i] * 2.0f;               // phase 1    grid.sync();                                 // every block has finished phase 1    if (i < n) b[i] = a[(i + 1) % n];            // phase 2 reads results of other blocks} void launch(float *a, float *b, int n, int blocks, int threads) {    void *args[] = {&a, &b, &n};    cudaLaunchCooperativeKernel((void *)two_phase, blocks, threads, args);}
What each marked line does and why
  1. Line 5cg::grid_group grid = cg::this_grid(); // every thread of the launchA handle to every thread of the launch.
  2. Line 6int i = grid.thread_rank();The thread's number across the whole grid.
  3. Line 8grid.sync(); // every block has finished phase 1A barrier for the whole grid. Every block must be running at the same time for this to work.
  4. Line 9if (i < n) b[i] = a[(i + 1) % n]; // phase 2 reads results of other blocksNow it is safe to read values that other blocks wrote in phase 1.
  5. Line 14cudaLaunchCooperativeKernel((void *)two_phase, blocks, threads, args);A cooperative launch checks that all blocks fit on the GPU at once and fails otherwise.
Largest cooperative gridExam favourite

Lesson 5 of 5

From intuition to research

One idea, four depths

A class trip waits at the bus until every child is back. That is a barrier. The single key to the store room, passed from hand to hand, is a lock.

__syncthreads() for one block, atomics for different blocks. atomicCAS returns the old value. Take locks with one thread per block, fence before release, and prefer atomicAdd or privatisation to locks.

Measure contention: global atomics on one address are serialised. Replace with warp shuffles plus one atomic per warp or block. grid.sync() needs a cooperative launch with all blocks resident.

The PTX memory model gives acquire, release and scope to every atomic (cuda::atomic_ref in libcu++). Lock free queues, work stealing and split arrive and wait barriers (cuda::barrier, mbarrier on Hopper) build on these ideas.
