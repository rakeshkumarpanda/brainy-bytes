Lesson 1 of 6

When is a layer limited by maths?

Lecture 9 starts with a simple test. Work out how long the maths takes and how long the data takes. The slower one sets the pace.

Time for maths and for data
Tmath = ops ÷ BWmath, Tmem = bytes ÷ BWmem
With overlap, the larger one decides the speed.
Math limited whenExam favourite
ops ÷ bytes > BWmath ÷ BWmem
Left: the arithmetic intensity of the operation. Right: the ops per byte ratio of the GPU, the ridge point of the roofline.

A fully connected layer computes Y = WX. W is Nout × Nin, X is Nin × B, Y is Nout × B.

Work
ops = 2 Nin Nout B
Each output is a dot product of length Nin: one multiply and one add per term.
Bytes in FP16
bytes = 2 (Nin B + Nin Nout + Nout B)
Read X, read W, write Y.
4096 × 4096 layerExam favourite
AI = 4096 B ÷ (4096 + 2B)
Batch 1 gives about 1. The limit for a huge batch is 2048.
A100: from which batch is the layer math limited?
  1. Ridge = 312 × 10¹² ÷ 1.555 × 10¹² ≈ 201 FLOP/byte.
  2. Need 4096 B ÷ (4096 + 2B) > 201.
  3. 4096 B > 823,296 + 402 B, so 3694 B > 823,296.
  4. B > 222.9, so from a batch of 223

This is why a chatbot answering one user at a time is limited by memory bandwidth (batch 1, AI about 1), and why serving systems batch many users together and shrink weights to 8 or 4 bits. Training uses big batches and runs where tensor cores shine.

Lesson 2 of 6

Everything is a matrix multiply

GEMM (general matrix multiply) computes C ← αAB + βC with A of size M × K, B of size K × N and C of size M × N. It costs 2MNK FLOPs.

LayerMNK
Fully connectedoutput featuresbatchinput features
Convolution (implicit GEMM)output channelsbatch × output height × output widthinput channels × filter height × filter width
Attentionsequencesequence or head sizehead size or sequence

A convolution becomes a GEMM by cutting out every window of the picture and laying it out as a row. This is called im2col. Step through the worked example from the notes.

Workbook 9.2: RGB 224 × 224, 64 filters of 3 × 3, padding 1
  1. M = 64 output channels.
  2. N = 224 × 224 = 50,176 output pixels.
  3. K = 3 × 3 × 3 = 27.
  4. FLOPs = 2 × 64 × 50,176 × 27 = 173,408,256
Remember
im2col copies each pixel into up to 9 rows, so the matrix is 9 times bigger than the picture. Libraries such as cuDNN never build it in memory. They compute the addresses on the fly, which is why it is called implicit GEMM.
Lesson 3 of 6

Tensor cores and where their speed comes from

A tensor core computes a whole small matrix product D = A × B + C in one operation. On Volta each tensor core does a 4 × 4 × 4 product per clock: 64 fused multiply adds, where an ordinary CUDA core does 1.

Peak of the tensor coresExam favourite
peak = SMs × tensor cores per SM × FMAs per clock × 2 × clock
An FMA counts as 2 FLOPs.
GPUSMs × TCsFMAs per clockClockPeak
V100 FP1680 × 8641.53 GHz125 TFLOP/s
T4 FP1640 × 8641.59 GHz65 TFLOP/s (FP32: 8.1)
A100 FP16 / BF16108 × 42561.41 GHz312 TFLOP/s
A100 TF32108 × 41281.41 GHz156 TFLOP/s (FP32 CUDA cores: 19.5)
H100 SXM BF16132 × 45121.83 GHz989 TFLOP/s

On an A100, FP16 tensor cores are 16 times the FP32 CUDA cores. About 8 times comes from the hardware (TF32 against FP32) and 2 times from the narrower numbers. Both happen together.

Remember
Real kernels rarely see the data sheet peak. Under a heavy matmul an H100 hits its 700 W power limit and lowers its clock, so 750 TFLOP/s may be closer to what is reachable than 750 ÷ 989 = 76 percent suggests.
Going deeper: What Ampere added

BF16, TF32 and FP64 on tensor cores. cp.async copies global memory straight into shared memory while the SM keeps computing, which allows deep pipelines. Structured sparsity: if 2 of every 4 weights are zero, tensor cores can skip them for up to 2 times the speed. Libraries: cuBLAS, cuDNN, CUTLASS, cuSPARSE, cuFFT.

Lesson 4 of 6

Programming tensor cores with WMMA

WMMA (warp matrix multiply accumulate) lets the 32 threads of a warp work together on one 16 × 16 × 16 product. Each thread holds a piece of each matrix in its registers, called a fragment. Which piece is not specified, so code must never rely on it.

wmma_gemm.cu
#include <mma.h>#include <cuda_fp16.h>using namespace nvcuda;const int WM = 16, WN = 16, WK = 16;                         // shape of one mma_sync __global__ void wmma_gemm(const half *A, const half *B, float *C, int M, int N, int K) {    int warpM = (blockIdx.x * blockDim.x + threadIdx.x) / 32;  // tile row owned by this warp    int warpN = blockIdx.y * blockDim.y + threadIdx.y;         // tile column    if (warpM * WM >= M || warpN * WN >= N) return;            // the whole warp leaves together     wmma::fragment<wmma::matrix_a, WM, WN, WK, half, wmma::row_major> a_frag;    wmma::fragment<wmma::matrix_b, WM, WN, WK, half, wmma::col_major> b_frag;    wmma::fragment<wmma::accumulator, WM, WN, WK, float> c_frag;    wmma::fill_fragment(c_frag, 0.0f);     for (int k = 0; k < K; k += WK) {                           // walk along K        const half *a_tile = A + (warpM * WM) * K + k;          // A row major, leading dimension K        const half *b_tile = B + (warpN * WN) * K + k;          // B column major, leading dimension K        wmma::load_matrix_sync(a_frag, a_tile, K);        wmma::load_matrix_sync(b_frag, b_tile, K);        wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);         // c += a * b on the tensor cores    }    float *c_tile = C + (warpM * WM) * N + warpN * WN;    wmma::store_matrix_sync(c_tile, c_frag, N, wmma::mem_row_major);} void launch(const half *A, const half *B, float *C, int M, int N, int K) {    dim3 block(128, 4);                                         // 4 warps along x, 4 along y    dim3 grid((M / 16 + 3) / 4, (N / 16 + 3) / 4);    wmma_gemm<<<grid, block>>>(A, B, C, M, N, K);}
What each marked line does and why
  1. Line 1#include <mma.h>The WMMA API lives in the mma.h header, in the namespace nvcuda::wmma.
  2. Line 4const int WM = 16, WN = 16, WK = 16; // shape of one mma_syncThe fixed shape of one tensor core operation.
  3. Line 6__global__ void wmma_gemm(const half *A, const half *B, float *C, int M, int N, int K) {Inputs in half (FP16), output in float (FP32): mixed precision.
  4. Line 7int warpM = (blockIdx.x * blockDim.x + threadIdx.x) / 32; // tile row owned by this warpEach warp, not each thread, owns one 16 × 16 output tile. Dividing the x index by 32 numbers the warps.
  5. Line 9if (warpM * WM >= M || warpN * WN >= N) return; // the whole warp leaves togetherAll 32 threads of a warp must take part in every WMMA call, so out of range warps leave as a whole.
  6. Line 11wmma::fragment<wmma::matrix_a, WM, WN, WK, half, wmma::row_major> a_frag;The A tile fragment, stored row major.
  7. Line 13wmma::fragment<wmma::accumulator, WM, WN, WK, float> c_frag;The FP32 accumulator fragment, spread over the 32 threads' registers.
  8. Line 14wmma::fill_fragment(c_frag, 0.0f);Start the accumulator at 0. This is C in D = AB + C.
  9. Line 16for (int k = 0; k < K; k += WK) { // walk along KMarch along K, 16 at a time. This is the tiling loop of the matmul chapter.
  10. Line 17const half *a_tile = A + (warpM * WM) * K + k; // A row major, leading dimension KTop left corner of the current A tile. The last argument of load_matrix_sync is the leading dimension.
  11. Line 19wmma::load_matrix_sync(a_frag, a_tile, K);The warp loads the A tile into its fragment together.
  12. Line 21wmma::mma_sync(c_frag, a_frag, b_frag, c_frag); // c += a * b on the tensor coresOne call: 16³ = 4096 multiply adds = 8192 FLOPs on the tensor cores.
  13. Line 24wmma::store_matrix_sync(c_tile, c_frag, N, wmma::mem_row_major);Write the finished tile back to C in row major order.
  14. Line 28dim3 block(128, 4); // 4 warps along x, 4 along y128 × 4 threads = 16 warps = 16 output tiles per block.
Workbook 9.5: M = N = K = 4096, one warp per 16 × 16 tile
  1. Tiles: (4096 ÷ 16)² = 65,536.
  2. Steps along K: 4096 ÷ 16 = 256.
  3. Calls: 65,536 × 256 = 16,777,216.
  4. 16,777,216 × 8192 = 137,438,953,472 = 2 × 4096³ FLOPs

Real kernels give each block a bigger tile. In the slide a block of 8 warps computes a 128 × 128 tile: 2048 outputs per warp, 8 WMMA tiles per warp, and 64 FP32 accumulators per thread. Strips of A and B pass through shared memory, while the C tile stays in registers until the end.

In the exam
Slide 16 says shared memory is used for the matrix C. In real kernels such as CUTLASS, C stays in registers during the main loop and only passes through shared memory when it is written out at the end.

Lesson 5 of 6

Staircases: warp granularity and wave quantisation

Two effects make time jump in steps instead of growing smoothly.

Warp granularity
lane efficiency = T ÷ (32 ⌈T ÷ 32⌉)
33 threads need 2 warps: 51.6 percent of lanes used. 65 threads: 67.7 percent.
WavesExam favourite
waves = ⌈blocks ÷ (blocks per SM × SMs)⌉
One wave fills every SM once.
Wave efficiencyExam favourite
n ÷ (W × ⌈n ÷ W⌉), with W = blocks per wave
217 blocks on an A100: 217 ÷ 324 = 67 percent.
Workbook 9.6: 4096 × 4096 output on an A100, 216 blocks per wave
  1. 128 × 128 tiles: 32 × 32 = 1024 blocks, ⌈1024 ÷ 216⌉ = 5 waves.
  2. Efficiency 1024 ÷ 1080 = 94.8 percent.
  3. 128 × 256 tiles: 512 blocks, ⌈512 ÷ 216⌉ = 3 waves, 512 ÷ 648 = 79.0 percent.
  4. The bigger tile does more work per byte but wastes more of the last wave
Remember
Fixes: sizes that are multiples of 32 threads and of the wave size, a tile size that divides the problem evenly, persistent kernels, or stream-K, which splits the leftover work along K across the idle SMs (as CUTLASS does). The same effect exists on AMD GPUs.
Lesson 6 of 6

From intuition to research

One idea, four depths

An ordinary core is a person with a calculator doing one a × b + c at a time. A tensor core is a machine that multiplies two small grids of numbers in one go.

Math limited when AI > peak ÷ bandwidth. FC layer: AI = 4096B ÷ (4096 + 2B), math limited on an A100 from batch 223. Peak = SMs × TCs × FMAs × 2 × clock. One mma_sync = 8192 FLOPs.

Use cuBLAS or CUTLASS first. For your own kernel: 128 × 128 block tiles, warps of 16 × 16 fragments, FP32 accumulators, sizes that divide into full waves. Check tensor core use in Nsight Compute.

Hopper wgmma with TMA and warp specialisation, Blackwell tcgen05 with tensor memory, FlashAttention fusing softmax into the GEMM, and stream-K scheduling are the current research frontier.
