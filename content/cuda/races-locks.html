Why counter = counter + 1 goes wrong

To you it is one line. To the hardware it is three steps: load the value into a register, add 1 to the register, store the register back. When two threads do this at the same time, their steps can mix.

TimeThread 1Thread 2counter in memory
1load, r1 = 00
2load, r2 = 00
3r1 = 10
4r2 = 10
5store 11
6store 11, but it should be 2

A race condition is when the result depends on the timing of threads that share data and at least one of them writes. Step through it yourself. Change the number of threads and the order, and see how many updates are lost.

Orders of n threads with s steps eachExam favourite
(n × s)! ÷ (s!)n
Pick which thread takes each time slot. Steps inside one thread keep their order.
Two threads, three steps
6! ÷ (3! × 3!) = 20
Only the 2 fully serial orders give 2. That is 10 percent.
Three threads, three stepsExam favourite
9! ÷ (3!)3 = 1680
Only 3! = 6 serial orders give 3. That is about 0.4 percent.

Inside a GPU warp the threads run in lock step: all load, then all add, then all store. Every thread loads the same old value, so the result is just 1.

counter.cu
#include <cstdio> __global__ void unsafe_inc(int *c) {    *c = *c + 1;                       // load, add, store: three separate steps} __global__ void safe_inc(int *c) {    atomicAdd(c, 1);                   // one indivisible read, add and write} int main() {    int *d, h;    cudaMalloc(&d, sizeof(int));    cudaMemset(d, 0, sizeof(int));    unsafe_inc<<<1, 10>>>(d);    cudaMemcpy(&h, d, sizeof(int), cudaMemcpyDeviceToHost);    printf("unsafe: %d\n", h);    cudaMemset(d, 0, sizeof(int));    safe_inc<<<1, 10>>>(d);    cudaMemcpy(&h, d, sizeof(int), cudaMemcpyDeviceToHost);    printf("atomic: %d\n", h);    cudaFree(d);    return 0;}
What each marked line does and why
  1. Line 3__global__ void unsafe_inc(int *c) {Every thread reads the same counter, adds 1 and writes back. Updates are lost.
  2. Line 4*c = *c + 1; // load, add, store: three separate stepsThis single line becomes a load, an add and a store.
  3. Line 8atomicAdd(c, 1); // one indivisible read, add and writeatomicAdd does the read, the add and the write as one step that nobody can split.
  4. Line 15unsafe_inc<<<1, 10>>>(d);One warp of 10 threads. In lock step they all read 0.
  5. Line 19safe_inc<<<1, 10>>>(d);Same launch with the atomic version.
What it prints
unsafe: 1
atomic: 10
Common mistake
The unsafe result is not guaranteed to be 1. It depends on how the hardware schedules the threads. A race means the answer is unpredictable, which is worse than always wrong.

The critical section and Dekker's three attempts

A critical section is the piece of code that touches the shared data. Only one thread may run it at a time. Any correct solution must meet three rules.

RuleMeaningIf it breaks
Mutual exclusionAt most one thread is inside at any moment.Two threads change the data together.
ProgressIf the section is free and someone wants in, someone gets in. A thread that does not want in cannot block others.Deadlock, or waiting for a thread that has gone home.
Bounded waitingAfter I ask, others can go first only a limited number of times.Starvation: I wait for ever.

Think of one bathroom at a roadside restaurant. Never two people inside. If it is empty and someone waits, they go in. Nobody waits for ever while others keep jumping the queue.

Lecture 10 tries three simple ideas for two threads. Each uses busy waiting: a while loop that spins until it may go on. Pick an attempt below and choose a schedule of 0s and 1s (which thread takes the next step).

AttemptIdeaMutual exclusionProgressWhat goes wrong
1. Take turnsa shared turn variableyesnoStrict alternation. If thread 2 stops wanting in, thread 1 enters once and then waits for ever.
2. Check, then setlook at the other flag, then raise minenoyesBoth check before either sets. Both enter.
3. Set, then checkraise my flag, then lookyesnoBoth raise flags, then each waits for the other. Deadlock.
In the exam
Slide 8 says attempt 2 can deadlock. It cannot: a thread sets its flag only after passing its loop, so nobody waits after the flags are set. The real flaw is that both can pass the check, which breaks mutual exclusion. The class also concluded that the three attempts suffer from the same drawback. They fail in three different ways: attempt 2 checks too early, attempt 3 claims too early, attempt 1 is safe but too rigid.

The fix combines the flags of attempt 3 (safety) with the turn variable of attempt 1 (a tie breaker). Dekker found the first correct version in the 1960s.

dekker.cu
volatile bool flag[2] = {false, false};volatile int turn = 0; void dekker_enter(int me) {            // me is 0 or 1    int other = 1 - me;    flag[me] = true;                   // I want in    while (flag[other]) {              // the other wants in too        if (turn != me) {              // and it is not my turn            flag[me] = false;          // step back            while (turn != me) ;       // wait for my turn            flag[me] = true;           // try again        }    }} void dekker_leave(int me) {    turn = 1 - me;                     // give the turn away    flag[me] = false;}
What each marked line does and why
  1. Line 6flag[me] = true; // I want inRaise my flag first, as in attempt 3.
  2. Line 7while (flag[other]) { // the other wants in tooSomeone else also wants in, so there is a tie to break.
  3. Line 8if (turn != me) { // and it is not my turnThe turn variable breaks the tie, as in attempt 1.
  4. Line 9flag[me] = false; // step backLower my flag so the other thread can go in. This removes the deadlock of attempt 3.
  5. Line 10while (turn != me) ; // wait for my turnSpin until the turn comes back to me.
  6. Line 17turn = 1 - me; // give the turn awayOn the way out, hand the turn to the other thread.

Peterson's algorithm and why it is correct

Peterson (1981) found a shorter correct lock for two threads. Each thread says "I want in" and then "but you go first". Whoever said "you go first" last is the one who waits.

peterson.cu
__device__ volatile int flag[2] = {0, 0};__device__ volatile int turn = 0; __device__ void peterson_enter(int me) {    int other = 1 - me;    flag[me] = 1;                          // 1. I want in    turn = other;                          // 2. but you go first    __threadfence();                       // both writes visible before the reads below    while (flag[other] && turn == other) ; // 3. wait only if the other wants in and it is its turn} __device__ void peterson_leave(int me) {    __threadfence();                       // writes made inside the critical section go first    flag[me] = 0;                          // 4. done}
What each marked line does and why
  1. Line 6flag[me] = 1; // 1. I want inStep 1: raise my flag.
  2. Line 7turn = other; // 2. but you go firstStep 2: give the turn to the other thread. Both threads write turn, and the last writer waits.
  3. Line 8__threadfence(); // both writes visible before the reads belowA fence stops the hardware from letting the read below go ahead of the two writes above.
  4. Line 9while (flag[other] && turn == other) ; // 3. wait only if the other wants in and it is its turnStep 3: wait only while the other wants in and it is the other thread's turn.
  5. Line 13__threadfence(); // writes made inside the critical section go firstEverything written in the critical section must be visible before I lower my flag.
  6. Line 14flag[me] = 0; // 4. doneStep 4: lower my flag on the way out.
Proof of mutual exclusion
  1. Suppose both threads are inside. Each wrote its flag, then turn.
  2. Say P0 wrote turn last, so turn = 1 from then on.
  3. P1 set flag[1] before it wrote turn, which was before P0 wrote turn. So when P0 tested, flag[1] was true and turn was 1.
  4. Then P0 would still be waiting. Contradiction. The other case is the same with 0 and 1 swapped.
  5. At most one thread inside

Progress. If P1 does not want in, flag[1] is false and P0 walks straight in. If both want in, turn is 0 or 1, so exactly one of the two loop conditions is false. Somebody always gets in.

Bounded waiting. If P1 leaves and tries again at once, it first writes turn = 0, which makes itself wait and lets P0 go. So P0 waits for at most one turn of P1.

In the exam
In class the conclusion was that the deadlock danger is still looming. That is not correct. With reads and writes that happen in program order, Peterson meets all three rules. Swapping steps 1 and 2 (turn first, then flag) does break mutual exclusion, so the order matters.
Going deeper: Why volatile is not enough on real hardware

volatile only stops the compiler from keeping the variable in a register. Modern CPUs and GPUs may still reorder memory operations. A store can sit in a store buffer while a later load runs ahead. Then each thread reads the other flag as false before its own flag is visible, and both enter. You need a fence between the writes and the read: __threadfence() in CUDA, or std::atomic with sequential consistency in C++. In practice programmers use hardware atomic instructions, which is the next chapter.

Locks for N threads: Bakery and Filter

Peterson works for two threads. Lecture 11 shows two ways to handle N threads.

Lamport's Bakery lock. Like the ticket machine at a bakery counter: take a ticket one larger than any ticket in use and wait until every smaller ticket has been served. Two threads can pick the same number at the same moment, so equal tickets are broken by thread id.

Filter lock. N − 1 gates in a row. At each gate the thread that arrived last (the victim) waits while anyone else is at that gate or further. Each gate holds back at least one thread, so after N − 1 gates only one remains.

locks_n.cu
#define N 4volatile bool choosing[N];volatile int number[N]; void bakery_enter(int i) {    choosing[i] = true;    int m = 0;    for (int j = 0; j < N; j++) if (number[j] > m) m = number[j];    number[i] = m + 1;                 // a ticket one larger than any in use    choosing[i] = false;    for (int j = 0; j < N; j++) {        while (choosing[j]) ;          // j is still picking its ticket        while (number[j] != 0 &&               (number[j] < number[i] || (number[j] == number[i] && j < i))) ;    }} void bakery_leave(int i) { number[i] = 0; } volatile int level[N];volatile int victim[N]; static bool someone_at(int i, int k) {    for (int j = 0; j < N; j++)        if (j != i && level[j] >= k) return true;    return false;} void filter_enter(int i) {    for (int k = 1; k < N; k++) {      // N - 1 gates        level[i] = k;                  // I am at gate k        victim[k] = i;                 // I arrived last at this gate        while (someone_at(i, k) && victim[k] == i) ;    }} void filter_leave(int i) { level[i] = 0; }
What each marked line does and why
  1. Line 6choosing[i] = true;choosing[i] says that thread i is in the middle of picking a ticket.
  2. Line 9number[i] = m + 1; // a ticket one larger than any in useTake a ticket one larger than every ticket in use.
  3. Line 12while (choosing[j]) ; // j is still picking its ticketDo not compare with j while j is still picking. Its ticket might end up smaller than mine.
  4. Line 13while (number[j] != 0 &&Wait while j holds a smaller ticket, or the same ticket with a smaller id.
  5. Line 18void bakery_leave(int i) { number[i] = 0; }Leaving: throw the ticket away.
  6. Line 31level[i] = k; // I am at gate kI am now trying to pass gate k.
  7. Line 32victim[k] = i; // I arrived last at this gateI arrived last at gate k, so I am the one who waits if needed.
  8. Line 33while (someone_at(i, k) && victim[k] == i) ;Wait while someone else is at gate k or beyond and I am still the victim.
Filter: at most N − k threads get past gate k
  1. Gate 0: at most N threads, which is true.
  2. Assume at most N − k + 1 threads reach gate k − 1. Suppose all of them pass gate k.
  3. Let A be the last of them to write victim[k]. Every other one has level ≥ k, so A must wait. Contradiction.
  4. So at most N − k pass gate k. At the last gate k = N − 1 that is 1 thread.
  5. Mutual exclusion for N threads

Peterson2waits at most one turnconstant
BakeryNfirst come, first servedO(N), tickets grow without limit
FilterNstarvation free, but no fixed boundO(N²) checks in the worst case
In the exam
Slide 3 says the Filter lock has bounded waiting. It is starvation free (every waiting thread gets in in the end), but a thread can be overtaken any number of times at a gate, so there is no fixed bound r. The Bakery lock is the one with first come, first served order.

From intuition to research

One idea, four depths

Two people write the score on one whiteboard. Each reads 5, adds 1 and writes 6. One point is lost. They need a rule so that only one person holds the marker at a time.

counter++ is load, add, store. A critical section needs mutual exclusion, progress and bounded waiting. Dekker attempt 1 fails progress, 2 fails mutual exclusion, 3 deadlocks. Peterson and Bakery meet all three.

Prove locks by looking at who wrote a shared variable last. Check small cases by trying every interleaving, as the notes did (62 states for Peterson). On real hardware add fences or use atomics.

Model checkers such as TLA+ and SPIN explore every state of a lock. Weak memory models (C++, PTX) need careful proofs. Real systems use hardware compare and swap, ticket locks and queue locks such as MCS.
