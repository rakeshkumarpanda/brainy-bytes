Inside the JVM: how a Java program really runs

What happens between typing java Main and seeing output? This chapter follows a program through the class file, the class loaders, the memory areas, bytecode, the JIT compiler and the garbage collector, then shows the tools that make Java services fast and easy to diagnose: Flight Recorder, the AOT cache from Java 24 to 26, compact object headers and G1 everywhere in Java 27.

Part 1

🧭The journey of a Java program

The basics chapter showed the short version: javac makes bytecode and the JVM runs it. This chapter opens the JVM and looks at each stage, with real commands you can type. It is the knowledge that helps when a service starts slowly, eats memory, or crashes with an error that makes no sense.

Think of a theatre script translated once into a common language (bytecode). Every theatre (JVM) in the world can read it, and an actor who repeats a scene many times learns it by heart (JIT) so it gets faster each night.
Part 2

📄Inside a class file

A .class file is a small binary file with a fixed layout: a magic number, a version, a constant pool (all the names and literal values the class uses), the fields, the methods with their bytecode, and some attributes. The first four bytes are always CA FE BA BE.

Every class file starts with CAFEBABE · 🖥️ Run in a terminal · ☕ JDK 25
📄 Main.java
class Main {
    public static void main(String[] args) {
        System.out.println("Hello from bytecode");
    }
}
Terminal
$ javac Main.java
$ od -A d -t x1 -N 8 Main.class     # dump the first 8 bytes in hex
$ javap -v Main | grep -E "major|minor"
$ java Main
Terminal output
--- first 8 bytes of Main.class ---
0000000 ca fe ba be 00 00 00 45
0000008
--- the version javap reads ---
  minor version: 0
  major version: 69
Hello from bytecode

The next bytes hold the version. 0x45 is 69, which means Java 25. A Java 21 JVM refuses this file with UnsupportedClassVersionError, which is the error you see when a library was built with a newer JDK than the one in production. The fix is to run a newer JDK or build with javac --release 21.

Part 3

🚚Class loading: delegation and lazy initialisation

The JVM does not load every class at start. It loads a class the first time the code needs it. Three built in class loaders share the work, and each one asks its parent first. This rule, called parent delegation, is why nobody can sneak in a fake java.lang.String.

Which loader loaded each class · ▶ Runs · ☕ JDK 25
class Main {
    static String who(Class<?> c) {
        ClassLoader l = c.getClassLoader();
        return c.getSimpleName() + " -> " + (l == null ? "bootstrap" : l.getName());
    }

    public static void main(String[] args) throws Exception {
        System.out.println(who(String.class));
        System.out.println(who(java.sql.Connection.class));
        System.out.println(who(Main.class));
        System.out.println("parent of app: " + Main.class.getClassLoader().getParent().getName());

        try {
            Class.forName("com.shop.Ghost");
        } catch (ClassNotFoundException e) {
            System.out.println("ClassNotFoundException: " + e.getMessage());
        }
    }
}
Output
String -> bootstrap
Connection -> platform
Main -> app
parent of app: platform
ClassNotFoundException: com.shop.Ghost

Loading is followed by linking (verify, prepare, resolve) and then initialisation, when static fields get their values and static blocks run. Initialisation happens once, at the first real use, such as reading a static field or calling new. Step through the program to see exactly when it happens.

Classes are initialised lazily, once, on first real use · ▶ Runs · ☕ JDK 25
class Main {
    static class Config {
        static final String URL;
        static {
            System.out.println("Config is being initialised");
            URL = "https://shop.test";
        }
    }

    static class Unused {
        static { System.out.println("Unused is initialised"); }
    }

    public static void main(String[] args) {
        System.out.println("main starts");
        Unused[] none = new Unused[3];
        System.out.println("an array of Unused does not initialise Unused");
        System.out.println("first use: " + Config.URL);
        System.out.println("second use: " + Config.URL);
    }
}
Output
main starts
an array of Unused does not initialise Unused
Config is being initialised
first use: https://shop.test
second use: https://shop.test
ClassNotFoundException means code asked for a class by name and no loader found it. NoClassDefFoundError means the class was there when the code was compiled but is missing or failed to initialise at run time. Both usually point to a missing JAR on the classpath.
Part 4

🗄️The runtime memory areas

A running JVM divides its memory into areas with different jobs. Every thread has its own stack of frames, one frame per method call, holding that call's local variables. All objects live on the shared heap. Class data such as methods and the constant pool lives in metaspace, and JIT compiled machine code lives in the code cache.

Each method call gets its own stack frame · ▶ Runs · ☕ JDK 25
class Main {
    static int price(int qty) {
        int base = qty * 50;
        return withTax(base);
    }

    static int withTax(int amount) {
        int tax = amount / 10;
        return amount + tax;
    }

    public static void main(String[] args) {
        int total = price(3);
        System.out.println("total " + total);
    }
}
Output
total 165

Each thread's stack has a limited size, about 1 MB by default on 64 bit Linux and changeable with -Xss. Deep or endless recursion fills it.

StackOverflowError: one thread runs out of stack · ▶ Runs · ☕ JDK 25
class Main {
    static int depth = 0;

    static void dig() {
        depth++;
        dig();                 // no exit condition, every call adds a frame
    }

    public static void main(String[] args) {
        try {
            dig();
        } catch (StackOverflowError e) {
            System.out.println("StackOverflowError after more than 1000 frames: " + (depth > 1000));
        }
        System.out.println("the heap and the program are fine, only that thread's stack was full");
    }
}
Output

Part 5

🔢Bytecode and the operand stack

Bytecode instructions are one byte long, plus any operands, which is where the name comes from. The JVM is a stack machine: instructions take their inputs from a small operand stack in the current frame and push their results back onto it. Here is the real bytecode of a method that squares a number.

The bytecode of square · 🖥️ Run in a terminal · ☕ JDK 25
📄 Main.java
class Main {
    static int square(int x) {
        return x * x;
    }

    public static void main(String[] args) {
        long sum = 0;
        for (int i = 0; i < 200_000; i++) {
            sum += square(i % 1000);
        }
        System.out.println(sum);
    }
}
Terminal
$ javac Main.java
$ javap -c Main     # only the square method is shown here
Terminal output
  static int square(int);
    Code:
         0: iload_0
         1: iload_0
         2: imul
         3: ireturn

The first letter of many instructions tells the type: i for int, l for long, d for double, a for a reference. Calls use invokestatic, invokevirtual, invokeinterface, invokespecial and, for lambdas and string concatenation, invokedynamic.

Part 6

🔥The interpreter and the JIT compiler

HotSpot starts every method in the interpreter. It counts how often each method runs and how often each loop turns. When a method gets hot, the C1 compiler turns it into machine code quickly (tier 2 or tier 3, the second one also collects a profile). If it stays hot, the C2 compiler uses that profile to produce highly optimised code (tier 4), for example by inlining small methods into their callers.

Watching the JIT compile square · 🖥️ Run in a terminal · ☕ JDK 25
📄 Main.java
class Main {
    static int square(int x) {
        return x * x;
    }

    public static void main(String[] args) {
        long sum = 0;
        for (int i = 0; i < 200_000; i++) {
            sum += square(i % 1000);
        }
        System.out.println(sum);
    }
}
Terminal
$ javac Main.java
$ java -XX:+PrintCompilation Main | grep Main::square     # tidied with awk
Terminal output
tier 2: Main::square
tier 4: Main::square
tier 2: Main::square  (old version thrown away)
program printed 66566700000

That is why the first requests to a fresh Java service are slower than later ones, and why performance tests always include a warm up phase. If the profile turns out to be wrong, for example a branch that was never taken suddenly runs, the JVM throws away the optimised code (deoptimisation) and goes back to the interpreter for a while.

Never measure Java speed with one run of a loop and System.currentTimeMillis. Use JMH, the Java Microbenchmark Harness, which handles warm up, dead code removal and statistics for you.
Part 7

♻️Garbage collectors and object headers

The garbage collection chapter explained when an object becomes garbage. The JVM ships several collectors that differ in how they clean up. Most objects die young, so the heap is split into a young and an old generation and the young part is cleaned often and cheaply.

CollectorBest forFlag
G1the default: balanced pauses and throughput-XX:+UseG1GC
ZGCvery short pauses (under a millisecond) on large heaps, generational only since Java 24-XX:+UseZGC
Parallelbatch jobs that only care about throughput-XX:+UseParallelGC
Serialtiny heaps and single core tools-XX:+UseSerialGC

Up to Java 26 the JVM quietly picked Serial on a machine with one CPU or less than 1792 MB of memory, which surprised many teams running small containers. Java 27 (JEP 523) uses G1 everywhere.

Java 25 picks a collector from the machine size · 🖥️ Run in a terminal · ☕ JDK 25
📄 Main.java

}
Terminal

[0.004s][info][gc] Using G1

Every object also starts with a header that the JVM uses for locking, hashing and garbage collection. It used to be 12 bytes. Compact object headers shrink it to 8 bytes. They became a supported option in Java 25 (JEP 519) and are on by default in Java 27 (JEP 534). For apps with millions of small objects this saves real memory.

Compact object headers make small objects smaller · 🖥️ Run in a terminal · ☕ JDK 27
📄 Main.java
class Main {
    record Point(int x, int y) {}

    public static void main(String[] args) {
        Runtime rt = Runtime.getRuntime();
        System.gc();
        long before = rt.totalMemory() - rt.freeMemory();
        Object[] points = new Object[2_000_000];
        for (int i = 0; i < points.length; i++) points[i] = new Point(i, i);
        System.gc();
        long after = rt.totalMemory() - rt.freeMemory();
        // each array slot is a 4 byte compressed reference, so take those away
        long perPoint = Math.round((after - before - 4.0 * points.length) / points.length);
        System.out.println("bytes per Point object: about " + perPoint);
    }
}
Terminal
$ java -Xmx1g Main
$ java -Xmx1g -XX:-UseCompactObjectHeaders Main
Terminal output
Java 27 default (compact headers on):
bytes per Point object: about 16
-XX:-UseCompactObjectHeaders (the old 12 byte header):
bytes per Point object: about 24

A Point with two ints needs 8 bytes of fields. With the old header that is 12 + 8 = 20 bytes, rounded up to 24 because objects are aligned to 8 bytes. With compact headers it is 8 + 8 = 16 bytes, a third less.

Part 8

📹JDK Flight Recorder: see what really happened

JDK Flight Recorder (JFR) is built into the JVM and records events such as garbage collections, slow locks, file and socket reads, and CPU samples, with an overhead of about one percent. You can add your own events too, which turns JFR into a cheap timing tool for business steps like checkout.

Recording a custom event with JDK Flight Recorder · 🖥️ Run in a terminal · ☕ JDK 27
📄 Main.java
import jdk.jfr.*;

class Main {
    @Name("shop.Checkout") @Label("Checkout")
    static class CheckoutEvent extends Event {     // your own event type
        @Label("Order") String order;
        @Label("Items") int items;
    }

    public static void main(String[] args) throws Exception {
        for (int i = 1; i <= 3; i++) {
            CheckoutEvent e = new CheckoutEvent();
            e.begin();
            Thread.sleep(20 * i);                  // pretend to call the payment service
            e.order = "ORD-" + i;
            e.items = i;
            e.commit();
        }
        System.out.println("3 checkouts done");
    }
}
Terminal
$ java -Ddb.password=hunter2 -Dshop.region=eu -XX:StartFlightRecording:filename=rec.jfr Main
$ jfr print --events shop.Checkout rec.jfr
$ jfr print --events jdk.InitialSystemProperty rec.jfr
Terminal output
3 checkouts done
--- one Checkout event ---
shop.Checkout {
  startTime = 10:15:02.181 (2026-10-24)
  duration = 22 ms
  order = "ORD-1"
  items = 1

Look at the last lines. Recordings often travel to other teams or support tickets, so Java 27 (JEP 536) redacts values that look like secrets before they are written. Keys matching patterns such as *password*, *token*, *secret* and *api*key* become [REDACTED]. The patterns can be changed with -XX:FlightRecorderOptions:redact-key=....

On a live server you do not need to restart anything: jcmd <pid> JFR.start duration=60s filename=prod.jfr records for a minute, and JDK Mission Control or jfr print opens the file.
Part 9

⚡Faster startup with the AOT cache

Each time a Java program starts, the JVM loads, verifies and links the same classes again. Project Leyden fixes that with an ahead of time cache. You run the app once as a training run, and the JVM saves the loaded and linked classes, and since Java 25 the method profiles too, into a cache file. Later starts read the cache instead of doing the work again.

An AOT cache in two commands (Java 25) · 🖥️ Run in a terminal · ☕ JDK 25
📄 Main.java
import java.net.URI;
import java.net.http.HttpRequest;
import java.time.Duration;
import java.util.stream.*;

class Main {
    public static void main(String[] args) {
        var req = HttpRequest.newBuilder(URI.create("https://shop.test/api")).GET().build();
        var words = Stream.of("pay", "cart", "login").sorted().collect(Collectors.joining(","));
        System.out.println(req.method() + " " + words + " " + Duration.ofSeconds(90));
    }
}
Terminal
$ jar cf app.jar Main.class     # the cache works with classes from JAR files
$ java -XX:AOTCacheOutput=app.aot -cp app.jar Main     # training run
$ java -Xlog:class+load -cp app.jar Main | grep -vc "shared objects file"
$ java -XX:AOTCache=app.aot -Xlog:class+load -cp app.jar Main | grep -vc "shared objects file"
Terminal output
--- 1. training run writes the cache ---
GET cart,login,pay PT1M30S
AOTCache creation is complete: app.aot (about 10 MB)
--- 2. classes loaded the slow way, without and with the cache ---
54
2

Without the cache, dozens of classes had to be found and parsed from the JDK image. With the cache almost none were. The JEP authors measured 42 percent faster startup for both a small stream program and the Spring PetClinic demo. Java 24 added the cache (JEP 483), Java 25 made it a single command and stored method profiles (JEP 514 and JEP 515), and Java 26 lets it work with any collector, including ZGC (JEP 516).

Use the same JDK and the same classpath for training and production. If they differ, the JVM simply ignores the cache and starts the normal way.
Part 10

🎬Real world scenario: a service that misbehaves in a small container

The situationA test reporting service runs fine on laptops, but in a 1 CPU, 1 GB container it starts slowly, pauses for long stretches and is sometimes killed for using too much memory.

The first step is always to ask the JVM how it was started. A small health check endpoint can report it.

A health check that reports how the JVM was started · ▶ Runs · ☕ JDK 25
import java.lang.management.*;

class Main {
    public static void main(String[] args) {
        RuntimeMXBean rt = ManagementFactory.getRuntimeMXBean();
        System.out.println("JVM: " + rt.getVmName() + " " + Runtime.version().feature());
        System.out.println("CPUs the JVM can use: " + Runtime.getRuntime().availableProcessors());
        for (GarbageCollectorMXBean gc : ManagementFactory.getGarbageCollectorMXBeans()) {
            System.out.println("collector: " + gc.getName());
        }
    }
}
Output
JVM: Java HotSpot(TM) 64-Bit Server VM 25
CPUs the JVM can use: 4
collector: G1 Young Generation
collector: G1 Concurrent GC
collector: G1 Old Generation

This run is on a build machine with several CPUs, so it shows G1. On Java 25 in the 1 CPU container the same check would show the Serial collector (named Copy and MarkSweepCompact), and the default heap would be only a quarter of the memory. The team sets the flags on purpose instead of trusting the defaults:

ProblemFlag or tool
Heap too small or too large for the container-XX:MaxRAMPercentage=75
Serial collector picked on a small machine-XX:+UseG1GC, or move to Java 27
Slow first start-XX:AOTCache=app.aot from a training run
Too much memory for many small objectscompact object headers (default in Java 27)
Nobody knows where time goesjcmd <pid> JFR.start and a custom event per report
Crash with no clues-XX:+HeapDumpOnOutOfMemoryError
