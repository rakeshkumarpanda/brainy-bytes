Part 1

🏭Executors: tasks instead of threads

The multithreading chapter created threads by hand. Real programs rarely do that. They hand tasks to an ExecutorService, which owns a pool of threads and reuses them, the way a restaurant gives orders to a fixed team of cooks instead of hiring a cook per order.

ExecutorService, Callable and Future · ▶ Runs · ☕ JDK 25
import java.util.*;
import java.util.concurrent.*;

class Main {
    public static void main(String[] args) throws Exception {
        // try-with-resources (Java 19+): close() waits for every task, then shuts the pool down
        try (ExecutorService pool = Executors.newFixedThreadPool(3)) {
            Callable<String> login = () -> { Thread.sleep(200); return "login PASS"; };
            Callable<String> search = () -> { Thread.sleep(100); return "search PASS"; };
            Callable<String> cart = () -> { Thread.sleep(150); return "cart FAIL"; };

            Future<String> f = pool.submit(login);                 // one task, a result later
            System.out.println("submitted, done yet? " + f.isDone());
            System.out.println(f.get());                           // waits for the result

            for (Future<String> r : pool.invokeAll(List.of(search, cart))) {   // many tasks, wait for all
                System.out.println(r.get());
            }
        }
        System.out.println("pool closed");
    }
}
Output
submitted, done yet? false
login PASS
search PASS
cart FAIL
pool closed
FactoryGives
newFixedThreadPool(n)n threads, extra tasks wait in a queue
newCachedThreadPool()creates threads as needed, reuses idle ones
newScheduledThreadPool(n)run later or every few seconds
newVirtualThreadPerTaskExecutor()Java 21: a new virtual thread for every task
A Callable returns a value and may throw. A Runnable does neither. Future.get() waits for the value, so call it as late as possible.

🏁Race conditions and four fixes

When two threads change the same data without coordination, the result depends on timing. That is a race condition. It is the most common reason for a test that fails "only sometimes on CI".

A race condition: two threads, one counter · Not run on this page
class Main {
    static int count = 0;
    public static void main(String[] args) throws Exception {
        Runnable work = () -> { for (int i = 0; i < 1_000_000; i++) count++; };
        Thread a = new Thread(work), b = new Thread(work);
        a.start(); b.start(); a.join(); b.join();
        System.out.println(count);       // expected 2000000
    }
}
What happens

Prints a different number on almost every run, such as 1183342 or 1529871, and very rarely 2000000. count++ is really three steps (read, add one, write), and two threads interleave them, so updates are lost. Because the result changes from run to run, it is not run on this page.

The fixes all make the read, change and write happen as one unit that other threads cannot split.

Four correct ways to count from many threads · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;
import java.util.concurrent.locks.*;

class Main {
    static int syncCount = 0;
    static synchronized void inc() { syncCount++; }

    public static void main(String[] args) throws Exception {
        AtomicInteger atomic = new AtomicInteger();
        LongAdder adder = new LongAdder();                  // fastest under heavy contention
        ReentrantLock lock = new ReentrantLock();
        int[] locked = {0};

        Runnable work = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                inc();
                atomic.incrementAndGet();
                adder.increment();
                lock.lock();
                try { locked[0]++; } finally { lock.unlock(); }   // always unlock in finally
            }
        };
        try (var pool = Executors.newFixedThreadPool(4)) {
            for (int t = 0; t < 4; t++) pool.submit(work);
        }
        System.out.println("synchronized  " + syncCount);
        System.out.println("AtomicInteger " + atomic.get());
        System.out.println("LongAdder     " + adder.sum());
        System.out.println("ReentrantLock " + locked[0]);
    }
}

tryLock with a timeout · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;
import java.util.concurrent.locks.*;

class Main {
    public static void main(String[] args) throws Exception {
        ReentrantLock seat = new ReentrantLock();
        CountDownLatch held = new CountDownLatch(1);

        Thread booker = new Thread(() -> {
            seat.lock();
            try { held.countDown(); Thread.sleep(500); }      // holds the seat for half a second
            catch (InterruptedException e) { }
            finally { seat.unlock(); }
        });
        booker.start();
        held.await();

        // tryLock with a timeout: give up instead of waiting forever (one way to avoid deadlocks)
        if (seat.tryLock(100, TimeUnit.MILLISECONDS)) {
            try { System.out.println("got the seat"); } finally { seat.unlock(); }
        } else {
            System.out.println("seat busy, try another one");
        }
        booker.join();
        System.out.println("after the first booking: " + (seat.tryLock() ? "free" : "busy"));
    }
}
Output
seat busy, try another one
after the first booking: free

👁️Visibility and the Java memory model

Each CPU core keeps its own cache, and the compiler may reorder instructions. So a value written by one thread is not guaranteed to be seen by another, unless there is a happens-before relationship between them. The Java Memory Model (JSR 133) defines those relationships.

volatile makes a change visible to other threads · ▶ Runs · ☕ JDK 25
class Main {
    static volatile boolean running = true;     // without volatile the loop may never see the change

    public static void main(String[] args) throws Exception {
        Thread poller = new Thread(() -> {
            long checks = 0;
            while (running) checks++;
            System.out.println("poller saw the stop signal");
        });
        poller.start();
        Thread.sleep(200);
        running = false;                        // a write to a volatile happens-before every later read of it
        poller.join(2000);
        System.out.println("poller alive? " + poller.isAlive());
    }
}
Output
poller saw the stop signal
poller alive? false
These create happens-before
Unlocking a monitor or lock, then locking the same one
Writing a volatile field, then reading it
Thread.start(), and everything a thread did before another thread's join() returns
Putting into a concurrent collection, then taking it out
volatile fixes visibility, not atomicity. volatileCount++ still loses updates.

🗄️Concurrent collections

A normal HashMap shared by threads can lose entries or, in old Java versions, even loop forever. The java.util.concurrent collections are built for sharing.

ConcurrentHashMap and CopyOnWriteArrayList · ▶ Runs · ☕ JDK 25
import java.util.*;
import java.util.concurrent.*;

class Main {
    public static void main(String[] args) throws Exception {
        ConcurrentHashMap<String, Integer> hits = new ConcurrentHashMap<>();
        List<String> log = List.of("/cart", "/login", "/cart", "/pay", "/cart", "/login");

        try (var pool = Executors.newFixedThreadPool(3)) {
            for (int round = 0; round < 1000; round++) {
                for (String path : log) pool.submit(() -> hits.merge(path, 1, Integer::sum));   // atomic read, add and write
            }
        }
        System.out.println(new TreeMap<>(hits));

        // check then act must be one atomic call, not get followed by put
        hits.computeIfAbsent("/search", p -> 0);
        hits.compute("/search", (p, n) -> n + 5);
        System.out.println("/search " + hits.get("/search"));

        CopyOnWriteArrayList<String> listeners = new CopyOnWriteArrayList<>(List.of("slack", "email"));
        for (String l : listeners) listeners.add("sms-" + l);    // safe: the loop reads a snapshot
        System.out.println(listeners);
    }
}
Output
{/cart=3000, /login=2000, /pay=1000}
/search 5
[slack, email, sms-slack, sms-email]
The bug to look for in code reviews is "check then act": if (!map.containsKey(k)) map.put(k, v). Between the check and the put, another thread can get in. Use putIfAbsent, computeIfAbsent or merge, which do both in one atomic step.

A BlockingQueue connects producers and consumers. put waits when the queue is full and take waits when it is empty, so a fast producer cannot flood a slow consumer.

Producer and consumer with a BlockingQueue · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;

class Main {
    public static void main(String[] args) throws Exception {
        BlockingQueue<String> jobs = new ArrayBlockingQueue<>(2);    // a small queue: put waits when it is full
        String STOP = "STOP";

        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    String job = jobs.take();                          // waits when the queue is empty
                    if (job.equals(STOP)) break;
                    System.out.println("  processed " + job);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        consumer.start();
        for (String order : new String[]{"ORD-1", "ORD-2", "ORD-3", "ORD-4"}) {
            jobs.put(order);
        }
        jobs.put(STOP);                                               // a "poison pill" ends the consumer
        consumer.join();
        System.out.println("all orders processed");
    }
}
Output
  processed ORD-1
  processed ORD-2
  processed ORD-3
  processed ORD-4
all orders processed

🚦Synchronizers: latches and semaphores

Synchronizers coordinate threads. A CountDownLatch lets threads wait until a count reaches zero, such as "start the tests when the database, cache and API are ready". A Semaphore hands out a fixed number of permits, which is a simple way to limit how many calls hit a server at once.

CountDownLatch and Semaphore · ▶ Runs · ☕ JDK 25
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

class Main {
    public static void main(String[] args) throws Exception {
        // CountDownLatch: wait until 3 services report ready
        CountDownLatch ready = new CountDownLatch(3);
        for (String s : List.of("db", "cache", "api")) {
            new Thread(() -> { sleep(100); ready.countDown(); }).start();
        }
        ready.await();
        System.out.println("all 3 services ready, start the tests");

        // Semaphore: at most 2 calls at the same time, like a rate limit on a test account
        Semaphore permits = new Semaphore(2);
        AtomicInteger now = new AtomicInteger(), peak = new AtomicInteger();
        try (var pool = Executors.newFixedThreadPool(6)) {
            for (int i = 0; i < 6; i++) pool.submit(() -> {
                permits.acquireUninterruptibly();
                try { peak.accumulateAndGet(now.incrementAndGet(), Math::max); sleep(100); now.decrementAndGet(); }
                finally { permits.release(); }
            });
        }
        System.out.println("6 calls made, never more than " + peak.get() + " at once");
    }

    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
}
Output
all 3 services ready, start the tests
6 calls made, never more than 2 at once
Also in the toolbox: CyclicBarrier (wait for each other, then all continue, and reuse it), Phaser (a flexible barrier with phases) and Exchanger (two threads swap objects).

🔮CompletableFuture

Future.get() blocks. CompletableFuture (Java 8) lets you describe what to do when the result arrives: transform it, combine it with another, or recover from an error, without blocking a thread while you wait.

CompletableFuture: run calls in parallel and combine them · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;

class Main {
    static String call(String what, long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
        return what;
    }

    public static void main(String[] args) {
        long t0 = System.currentTimeMillis();
        String a = call("price", 400), b = call("stock", 600), c = call("reviews", 300);
        System.out.println("one after another: " + a + ", " + b + ", " + c + " in about " + round(t0) + " ms");

        t0 = System.currentTimeMillis();
        var price = CompletableFuture.supplyAsync(() -> call("price", 400));
        var stock = CompletableFuture.supplyAsync(() -> call("stock", 600));
        var reviews = CompletableFuture.supplyAsync(() -> call("reviews", 300));
        String page = CompletableFuture.allOf(price, stock, reviews)
            .thenApply(v -> price.join() + ", " + stock.join() + ", " + reviews.join())
            .join();
        System.out.println("in parallel:       " + page + " in about " + round(t0) + " ms");

        String combined = price.thenCombine(stock, (p, s) -> p + "+" + s).thenApply(String::toUpperCase).join();
        System.out.println(combined);
    }

    static long round(long t0) { return Math.round((System.currentTimeMillis() - t0) / 100.0) * 100; }
}
Output
one after another: price, stock, reviews in about 1300 ms
in parallel:       price, stock, reviews in about 600 ms
PRICE+STOCK
Errors and timeouts: exceptionally, handle, completeOnTimeout and orTimeout · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;

class Main {
    public static void main(String[] args) {
        CompletableFuture<Integer> broken = CompletableFuture.supplyAsync(() -> {
            if (true) throw new IllegalStateException("inventory service down");
            return 5;
        });
        System.out.println(broken.exceptionally(e -> {                       // a fallback value
            System.out.println("recovered from: " + e.getCause().getMessage());
            return 0;
        }).join());

        System.out.println(broken.handle((v, e) -> e == null ? "ok " + v : "failed").join());   // sees both

        CompletableFuture<String> slow = CompletableFuture.supplyAsync(() -> {
            try { Thread.sleep(2000); } catch (InterruptedException e) { }
            return "late answer";
        });
        System.out.println(slow.completeOnTimeout("cached answer", 200, TimeUnit.MILLISECONDS).join());  // Java 9
        try {
            CompletableFuture.supplyAsync(() -> { try { Thread.sleep(2000); } catch (InterruptedException e) { } return 1; })
                .orTimeout(200, TimeUnit.MILLISECONDS).join();
        } catch (CompletionException e) {
            System.out.println("orTimeout: " + e.getCause().getClass().getSimpleName());
        }
    }
}
Output
recovered from: inventory service down
0
failed
cached answer
orTimeout: TimeoutException

🪶Virtual threads (Java 21)

A normal (platform) thread is a real operating system thread with about a megabyte of stack, so a server can afford a few thousand. A virtual thread (JEP 444, final in Java 21) is managed by the JVM and costs a few hundred bytes when idle, so millions are fine. When a virtual thread blocks on I/O, the JVM parks it and gives its carrier thread to someone else.

Virtual threads: ten thousand blocking tasks at once · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;
import java.util.stream.*;

class Main {
    public static void main(String[] args) throws Exception {
        Thread v = Thread.ofVirtual().name("checker").start(() -> System.out.println("virtual? " + Thread.currentThread().isVirtual()));
        v.join();

        long t0 = System.currentTimeMillis();
        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {        // one new virtual thread per task
            IntStream.range(0, 10_000).forEach(i -> exec.submit(() -> {
                Thread.sleep(1000);                                            // blocking I/O stand-in
                return i;
            }));
        }
        long secs = Math.round((System.currentTimeMillis() - t0) / 1000.0);
        System.out.println("10000 tasks that each wait 1 s finished in about " + secs + " s");

        t0 = System.currentTimeMillis();
        try (var exec = Executors.newFixedThreadPool(100)) {                  // the classic way: a pool of 100
            IntStream.range(0, 1_000).forEach(i -> exec.submit(() -> { Thread.sleep(1000); return i; }));
        }
        secs = Math.round((System.currentTimeMillis() - t0) / 1000.0);
        System.out.println("1000 tasks on 100 platform threads took about " + secs + " s");
    }
}
Output
virtual? true
10000 tasks that each wait 1 s finished in about 1 s
1000 tasks on 100 platform threads took about 10 s
Rules for virtual threads: create one per task and never pool them, keep using plain blocking code (no callbacks needed), limit access to scarce resources with a Semaphore instead of a small pool, and do not expect speed ups for pure calculation. Since Java 24 (JEP 491), synchronized blocks no longer pin a virtual thread to its carrier.

🌳Structured concurrency and scoped values

Structured concurrency treats a group of subtasks as one unit: they start inside a block, and the block does not end until all of them are done. If one fails, the others are cancelled. No thread is left running in the background by accident. It is still a preview (JEP 533, seventh preview in Java 27), with a new API since Java 25. In Java 27 join() reports a failed subtask with the familiar ExecutionException, and the joiner that returns the first good answer is called anySuccessfulOrThrow.

Structured concurrency (preview in Java 27) · ▶ Runs · ☕ JDK 27 preview
import java.util.concurrent.*;
import java.util.concurrent.StructuredTaskScope.*;

void main() throws Exception {
    // Java 27 preview (JEP 533): subtasks live and die together, like the lines of a method
    try (var scope = StructuredTaskScope.open()) {
        Subtask<String> user = scope.fork(() -> { Thread.sleep(200); return "Asha"; });
        Subtask<Integer> cart = scope.fork(() -> { Thread.sleep(300); return 3; });
        scope.join();                                   // waits for both, fails if either fails
        IO.println(user.get() + " has " + cart.get() + " items in the cart");
    }

    try (var scope = StructuredTaskScope.open()) {
        Subtask<String> ok = scope.fork(() -> { Thread.sleep(2000); return "slow but fine"; });
        Subtask<String> bad = scope.fork(() -> { Thread.sleep(100); throw new IllegalStateException("payment service down"); });
        scope.join();
    } catch (ExecutionException e) {                   // Java 27: join throws ExecutionException
        IO.println("failed fast: " + e.getCause().getMessage() + ", and the slow sibling was cancelled");
    }

    // A different joiner: the first successful answer wins, like asking two mirrors
    try (var scope = StructuredTaskScope.open(Joiner.<String>anySuccessfulOrThrow())) {
        scope.fork(() -> { Thread.sleep(500); return "mirror-eu"; });
        scope.fork(() -> { Thread.sleep(100); return "mirror-in"; });
        IO.println("fastest mirror: " + scope.join());
    }
}

Scoped values (JEP 506, final in Java 25) share a value, such as a request id or the current user, with every method called inside a block, without passing it as a parameter. Unlike ThreadLocal, the value cannot be changed by callees, it disappears when the block ends, and it is cheap to share with millions of virtual threads.

Scoped values instead of ThreadLocal (final in Java 25) · ▶ Runs · ☕ JDK 25
import java.util.concurrent.*;

class Main {
    // Java 25: a scoped value is set for one block of code and every method it calls, then it is gone
    static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

    static void log(String msg) {
        System.out.println("[" + (REQUEST_ID.isBound() ? REQUEST_ID.get() : "no-request") + "] " + msg);
    }
    static void loadCart() { log("loading cart"); }
    static void pay() { log("charging card"); }

    public static void main(String[] args) {
        ScopedValue.where(REQUEST_ID, "req-7f3a").run(() -> {
            log("checkout started");
            loadCart();                                   // no need to pass the id down every method
            ScopedValue.where(REQUEST_ID, "req-7f3a/retry").run(Main::pay);   // rebound for an inner block only
            log("checkout done");
        });
        log("outside any request");
    }
}
Output
[req-7f3a] checkout started
[req-7f3a] loading cart
[req-7f3a/retry] charging card
[req-7f3a] checkout done
[no-request] outside any request

🎬Real world scenario: a fast smoke test

The situationAfter every deployment, a team checks 300 product endpoints. Done one after another, it takes over a minute. A pool of 10 threads still takes about 10 seconds, and nobody wants to tune pool sizes.
Real world: a smoke test of 300 endpoints on virtual threads · ▶ Runs · ☕ JDK 25
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

class Main {
    record Check(String endpoint, int status, long ms) {}

    // Stand in for an HTTP call: the result depends only on the endpoint, so the report is the same every run
    static Check probe(String endpoint) throws InterruptedException {
        int n = Math.abs(endpoint.hashCode());
        long ms = 100 + n % 400;
        Thread.sleep(ms);
        int status = n % 17 == 0 ? 503 : n % 11 == 0 ? 404 : 200;
        return new Check(endpoint, status, ms);
    }

    public static void main(String[] args) throws Exception {
        List<String> endpoints = new ArrayList<>();
        for (int i = 1; i <= 300; i++) endpoints.add("/api/v1/products/" + i);

        Semaphore limit = new Semaphore(50);                      // be kind to the server: 50 at a time
        Map<Integer, AtomicInteger> byStatus = new ConcurrentSkipListMap<>();
        Queue<Check> failures = new ConcurrentLinkedQueue<>();
        long t0 = System.currentTimeMillis();

        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            for (String e : endpoints) exec.submit(() -> {
                limit.acquire();
                try {
                    Check c = probe(e);
                    byStatus.computeIfAbsent(c.status(), s -> new AtomicInteger()).incrementAndGet();
                    if (c.status() != 200) failures.add(c);
                } finally { limit.release(); }
                return null;
            });
        }
        long secs = Math.round((System.currentTimeMillis() - t0) / 1000.0);
        System.out.println("checked " + endpoints.size() + " endpoints in about " + secs + " s");
        System.out.println("by status: " + byStatus);
        failures.stream().sorted(Comparator.comparing(Check::endpoint)).limit(3)
            .forEach(c -> System.out.println("  " + c.status() + " " + c.endpoint()));
    }
}
Output
checked 300 endpoints in about 2 s
by status: {200=256, 404=27, 503=17}
  404 /api/v1/products/105
  503 /api/v1/products/11
  404 /api/v1/products/117

Each endpoint gets its own virtual thread, a Semaphore keeps the load at 50 calls at a time, and the results go into concurrent collections. The code reads like a simple loop, finishes in a few seconds, and the report is sorted so it is the same on every run.
