Assertions

An assertion is a check you leave in the code to catch your own mistakes during development and testing. It costs nothing in production, because assertions are switched off unless you turn them on.

Part 1

🔍Why assertions

A quick way to debug is to add System.out.println lines and remove them later. Forget one, and it prints in front of real users. Assertions solve this. You write a check once and leave it in the code. During development you run with assertions enabled. In production they stay disabled by default, so they do nothing and cost almost nothing.

Purpose

Catch programmer mistakes: situations that should be impossible if the code is correct.

Not for

Checking user input or anything outside your control. Those need real if checks and exceptions.

Assertions arrived in Java 1.4 (2002), and assert became a keyword at the same time.
Part 2

🔑assert as a keyword

Before Java 1.4, assert was an ordinary identifier, so old code could name a variable or method assert. Since 1.4 it is a reserved keyword, and such code no longer compiles.

assert cannot be a variable name · ❌ Does not compile
class Main {
    public static void main(String[] args) {
        int assert = 10;
        System.out.println(assert);
    }
}
❌ Compile error
as of release 1.4, 'assert' is a keyword, and may not be used as an identifier
Old exam questions ask what happens when you compile this with very old -source settings. Modern compilers no longer accept source levels that old, so in practice assert is always a keyword.
Part 3

✌️The two forms

Simple form

Syntax
assert condition;

If assertions are enabled and the condition is false, the JVM throws AssertionError. If the condition is true, nothing happens.

Run with java -ea Main · 💥 Crashes at run time
class Main {
    public static void main(String[] args) {
        int marks = 120;
        assert marks <= 100;
        System.out.println("marks: " + marks);
    }
}
💥 Runtime error
Exception in thread "main" java.lang.AssertionError

The same program without -ea skips the check completely:

Run with java Main · ▶ Runs
class Main {
    public static void main(String[] args) {
        int marks = 120;
        assert marks <= 100;
        System.out.println("marks: " + marks);
    }
}
Output
marks: 120

Augmented form

Syntax
assert condition : expression;

The second expression becomes the error's message, which makes the failure easier to understand. It can be any expression that produces a value. Java converts it to a String.

A message explains what went wrong · 💥 Crashes at run time
class Main {
    public static void main(String[] args) {
        int marks = 120;
        assert marks <= 100 : "marks must be at most 100, got " + marks;
        System.out.println("marks: " + marks);
    }
}
💥 Runtime error
Exception in thread "main" java.lang.AssertionError: marks must be at most 100, got 120
The second expression is evaluated only when the condition is false.
The message is not built when the check passes · ▶ Runs
class Main {
    static String expensive() {
        System.out.println("building message");
        return "details";
    }
    public static void main(String[] args) {
        int x = 5;
        assert x > 0 : expensive();
        System.out.println("check passed");
    }
}
Output
check passed
The second part must produce a value · ❌ Does not compile
class Main {
    static void log() { }
    public static void main(String[] args) {
        int x = 5;
        assert x > 10 : log();
    }
}
❌ Compile error
'void' type not allowed here
Part 4

🎚️Enabling and disabling

Assertions are controlled when you start the program, not when you compile it.

FlagLong formEffect
-ea-enableassertionsenable in all your classes
-da-disableassertionsdisable in all your classes (the default)
-esa-enablesystemassertionsenable inside Java's own library classes
-dsa-disablesystemassertionsdisable inside Java's library classes

Each flag can target one class or one package. Three dots after a package name mean "this package and all its sub-packages".

java -ea Main                          enable everywhere in your code
java -ea:Payment Main                  enable only in class Payment
java -ea:com.shop... Main              enable in com.shop and all its sub-packages
java -ea:com.shop... -da:com.shop.ui... Main
                                       enable in com.shop except com.shop.ui
java -ea -da:Main Main                 enable everywhere except class Main
Flags are applied from left to right, and a more specific flag wins over a general one.
java -ea -da:Main Main · ▶ Runs
// File: Main.java
public class Main {
    public static void main(String[] args) {
        assert false : "in Main";
        System.out.println("Main skipped its assertion");
        Checker.run();
    }
}
// File: Checker.java
public class Checker {
    static void run() {
        try {
            assert false : "in Checker";
            System.out.println("Checker skipped its assertion");
        } catch (AssertionError e) {
            System.out.println("Checker caught: " + e.getMessage());
        }
    }
}
Output
Main skipped its assertion
Checker caught: in Checker

Are assertions on right now

A neat trick with a side effect inside assert · ▶ Runs
class Main {
    public static void main(String[] args) {
        boolean enabled = false;
        assert enabled = true;                        // assignment, runs only when enabled
        System.out.println("assertions enabled: " + enabled);
    }
}
Output
assertions enabled: true
This is the only common case where a side effect inside assert is acceptable, because its purpose is to detect the setting itself.
Part 5

📍Where to use them and where not

SituationUse assertWhy
Arguments of a public methodNoCallers outside your control can pass anything. Validation must always run, so throw IllegalArgumentException.
Arguments of a private methodYesOnly your own code calls it, so a bad value means your bug.
Command line argumentsNoThey come from the user, so they need real checks.
A default case that should never happenYesassert false documents and checks the impossible case.
Code with side effects in the conditionNoThe program would behave differently when assertions are off.
Public: always validate. Private: assert. · ▶ Runs
class Main {
    public static double average(int[] marks) {
        if (marks == null || marks.length == 0)
            throw new IllegalArgumentException("need at least one mark");
        return sum(marks) / (double) marks.length;
    }
    private static int sum(int[] marks) {
        assert marks != null;                          // our own code guarantees this
        int s = 0;
        for (int m : marks) s += m;
        return s;
    }
    public static void main(String[] args) {
        System.out.println(average(new int[]{80, 90, 70}));
    }
}
Output
80.0
The impossible default case finds a real bug · 💥 Crashes at run time
class Main {
    static String direction(int turns) {
        switch (turns % 4) {
            case 0: return "north";
            case 1: return "east";
            case 2: return "south";
            case 3: return "west";
            default:
                assert false : "impossible remainder: " + turns % 4;
                return "?";
        }
    }
    public static void main(String[] args) {
        System.out.println(direction(5));
        System.out.println(direction(-3));
    }
}
Output before the crash
east
💥 Runtime error
Exception in thread "main" java.lang.AssertionError: impossible remainder: -3

The author believed turns % 4 is always 0 to 3. The assertion proves otherwise: in Java, the remainder of a negative number is negative. Math.floorMod(turns, 4) is the fix.

A side effect that disappears

Without -ea the list never shrinks · ▶ Runs
import java.util.*;
class Main {
    public static void main(String[] args) {
        List<String> queue = new ArrayList<>(List.of("a", "b"));
        assert queue.remove("a");                      // wrong: real work inside assert
        System.out.println(queue);
    }
}
Output
[a, b]
With -ea this prints [b]. Without it, [a, b]. Never put work the program needs inside an assertion.
Part 6

💥AssertionError

AssertionError is a child of Error, so it is unchecked. Catching it is legal, but it is bad practice: an assertion failure means the program is in a state its author believed impossible.

Legal to catch, but rarely wise · ▶ Runs
class Main {
    public static void main(String[] args) {
        try {
            assert 2 + 2 == 5 : "maths is broken";
        } catch (AssertionError e) {
            System.out.println("caught " + e.getClass().getSimpleName() + ": " + e.getMessage());
            System.out.println("is an Error? " + (e instanceof Error));
        }
    }
}
Output
caught AssertionError: maths is broken
is an Error? true
Test libraries such as JUnit have their own methods, for example assertEquals(expected, actual). They always run and report failures through the test runner. They are not the same as the Java assert keyword, though they share the idea.
