Garbage Collection

In C you must free every block of memory yourself. In Java the garbage collector does it for you. Your job is smaller but still important: stop pointing at objects you no longer need, so the collector is allowed to reclaim them.

Part 1

♻️Why a garbage collector

Every object you create with new lives in an area of memory called the heap. Memory is limited, so space taken by objects nobody uses any more must be given back. In older languages the programmer did this by hand, and forgetting caused memory leaks that slowly filled the memory.

Java runs a garbage collector (GC) inside the JVM. It finds objects that can no longer be reached from your running code and frees their memory.

Reachable

Some chain of references from a live variable, a static field or a running thread leads to the object. It stays.

Unreachable

No such chain exists. The object is eligible for garbage collection and may be removed at any time.

An object is eligible for GC when it has no reachable reference. Being eligible does not mean it is removed at once. The JVM decides when to collect.
Part 2

🎯Four ways to make an object eligible

To watch an object without keeping it alive, these examples use a WeakReference. Its get() method returns the object while it exists, and null after the collector has removed it.

1. Set the reference to null

Nullifying the only reference · ▶ Runs
import java.lang.ref.WeakReference;
class Main {
    public static void main(String[] args) throws Exception {
        Object report = new byte[1_000_000];
        WeakReference<Object> watch = new WeakReference<>(report);
        System.gc();
        System.out.println("while referenced, alive: " + (watch.get() != null));
        report = null;                                  // no reference left
        System.gc();
        Thread.sleep(100);
        System.out.println("after report = null, alive: " + (watch.get() != null));
    }
}
One possible output (the collector decides the timing)
while referenced, alive: true
after report = null, alive: false

2. Point the reference somewhere else

Reassigning the reference · ▶ Runs
import java.lang.ref.WeakReference;
class Main {
    public static void main(String[] args) throws Exception {
        StringBuilder s1 = new StringBuilder("first");
        WeakReference<Object> watch = new WeakReference<>(s1);
        s1 = new StringBuilder("second");               // "first" has no reference now
        System.gc();
        Thread.sleep(100);
        System.out.println(s1 + ", old object alive: " + (watch.get() != null));
    }
}
One possible output (the collector decides the timing)
second, old object alive: false

3. Objects created inside a method

Local variables disappear when the method returns. Objects referred to only by those locals become eligible. If the method returns a reference and the caller keeps it, that object stays.

Which objects survive the method call · ▶ Runs
class Box {
    String name;
    Box(String name) { this.name = name; }
}
class Main {
    static Box make() {
        Box a = new Box("a");
        Box b = new Box("b");
        return b;                                       // only b escapes
    }
    public static void main(String[] args) {
        Box kept = make();
        System.out.println("kept " + kept.name + ", a is eligible now");
        make();                                         // result ignored
        System.out.println("second call: both objects are eligible");
    }
}
Output
kept b, a is eligible now
second call: both objects are eligible

4. Island of isolation

Objects may still refer to each other and yet be unreachable from outside. Such a group is called an island of isolation. Java's collector traces reachability from live roots, so the whole island is eligible.

Two objects pointing at each other · ▶ Runs
import java.lang.ref.WeakReference;
class Node {
    Node partner;
}
class Main {
    public static void main(String[] args) throws Exception {
        Node x = new Node(), y = new Node();
        x.partner = y;
        y.partner = x;                                  // a cycle
        WeakReference<Node> wx = new WeakReference<>(x), wy = new WeakReference<>(y);
        x = null;
        y = null;                                       // nothing outside points in
        System.gc();
        Thread.sleep(100);
        System.out.println("x alive: " + (wx.get() != null) + ", y alive: " + (wy.get() != null));
    }
}
One possible output (the collector decides the timing)
x alive: false, y alive: false
A cycle of references does not keep objects alive. If none of them is reachable from outside, all of them are eligible.
Java's collector does not count references at all. It starts from the live roots and marks everything it can reach. Anything left unmarked is garbage, cycles included.
Part 3

🙋Requesting a collection

You can ask the JVM to run the garbage collector in two ways. Both do the same thing.

Two ways to ask
System.gc();                    // static method, the usual way
Runtime.getRuntime().gc();      // through the Runtime object
It is only a request. The JVM may run a collection, delay it or ignore it. A JVM started with -XX:+DisableExplicitGC ignores every such call.

Runtime is a singleton: there is exactly one Runtime object for the running JVM. You cannot create one with new. You get it with the factory method Runtime.getRuntime().

Runtime has a private constructor · ❌ Does not compile
class Main {
    public static void main(String[] args) {
        Runtime r = new Runtime();
    }
}
❌ Compile error
Runtime() has private access in Runtime
Always the same object · ▶ Runs
class Main {
    public static void main(String[] args) {
        Runtime r1 = Runtime.getRuntime();
        Runtime r2 = Runtime.getRuntime();
        System.out.println(r1 == r2);
    }
}
Output
true
Well written programs almost never call System.gc(). The JVM usually knows better when to collect. It is useful in small experiments like the ones on this page.
Part 4

📊Looking at memory with Runtime

MethodReturns
maxMemory()the most heap the JVM will ever try to use, in bytes (set by -Xmx)
totalMemory()heap currently reserved from the operating system
freeMemory()the part of totalMemory not used by objects right now
availableProcessors()number of processors the JVM may use
used memory = totalMemory − freeMemory
Measure the heap before and after · ▶ Runs
class Main {
    public static void main(String[] args) {
        Runtime r = Runtime.getRuntime();
        long mb = 1024 * 1024;
        System.out.println("max heap: " + r.maxMemory() / mb + " MB");
        System.gc();
        long before = r.totalMemory() - r.freeMemory();
        int[][] grid = new int[1000][1000];               // about 4 MB of ints
        long after = r.totalMemory() - r.freeMemory();
        System.out.println("grid uses about " + Math.round((after - before) / (double) mb) + " MB");
        System.out.println("rows: " + grid.length);
    }
}
One possible output (exact numbers depend on the machine)
max heap: 64 MB
grid uses about 4 MB
rows: 1000

This program was started with java -Xmx64m Main, so the maximum heap is 64 MB. One million int values take 1,000,000 × 4 bytes ≈ 4 MB.

When the heap is full

If the collector cannot free enough space for a new object, the JVM throws OutOfMemoryError. It is an Error, not an Exception: programs normally do not catch it.

Asking for 800 MB inside a 32 MB heap · 💥 Crashes at run time
class Main {
    public static void main(String[] args) {
        long[] huge = new long[100_000_000];              // 100 million × 8 bytes
        System.out.println(huge.length);
    }
}
💥 Runtime error
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
Part 5

🧹finalize and Cleaner

Early Java let a class override finalize(), a method the collector would call once before removing an object. It is now deprecated for removal (since Java 18), because it is slow, unpredictable and can bring dead objects back to life.

The old way, do not use in new code
@Override
protected void finalize() throws Throwable {
    System.out.println("cleaning up");
}
Classic facts that still appear in exams: the collector calls finalize at most once per object, any exception thrown by finalize during collection is ignored, and calling obj.finalize() yourself is just a normal method call that does not free memory.
An explicit finalize() call is an ordinary call · 💥 Crashes at run time
class Job {
    @SuppressWarnings("removal")
    @Override
    protected void finalize() {
        System.out.println("finalize called by hand");
        int x = 10 / 0;
    }
}
class Main {
    @SuppressWarnings("removal")
    public static void main(String[] args) {
        new Job().finalize();                            // the exception is not ignored here
    }
}
Output before the crash
finalize called by hand
💥 Runtime error
Exception in thread "main" java.lang.ArithmeticException: / by zero

The modern way: close it yourself

For files, sockets and database connections, do not wait for the collector at all. Implement AutoCloseable and use try-with-resources, so cleanup happens at a known moment.

Cleanup at a predictable time · ▶ Runs
class Connection implements AutoCloseable {
    Connection() { System.out.println("open"); }
    void send(String m) { System.out.println("send " + m); }
    public void close() { System.out.println("closed"); }
}
class Main {
    public static void main(String[] args) {
        try (Connection c = new Connection()) {
            c.send("hello");
        }
        System.out.println("after the block");
    }
}
Output
open
send hello
closed
after the block

As a safety net for code that forgets to close, Java 9 added java.lang.ref.Cleaner. It runs a cleanup action after the object becomes unreachable, without the problems of finalize.

A Cleaner action runs after collection · ▶ Runs
import java.lang.ref.Cleaner;
class Main {
    static final Cleaner CLEANER = Cleaner.create();
    public static void main(String[] args) throws Exception {
        Object buffer = new byte[1_000_000];
        CLEANER.register(buffer, () -> System.out.println("buffer cleaned"));
        buffer = null;
        System.gc();
        Thread.sleep(200);
        System.out.println("done");
    }
}
One possible output (the collector decides the timing)
buffer cleaned
done
The cleanup action must not refer to the object it watches. If it did, the object would stay reachable and never be cleaned.
Part 6

🆕Modern collectors and good habits

The JVM ships with several collectors. You choose one with a command line flag. Their behaviour depends on the JVM vendor and version, which is why the language rules only promise when an object becomes eligible, not when it is collected.

CollectorFlagGood for
G1 (default since Java 9)-XX:+UseG1GCmost applications, balanced pauses
ZGC-XX:+UseZGCvery large heaps with pauses of about a millisecond
Parallel-XX:+UseParallelGCbatch jobs that care about total throughput
Serial-XX:+UseSerialGCsmall heaps and single processor machines

Most collectors are generational. New objects start in the young generation, which is collected often because most objects die young. Objects that survive several collections move to the old generation, which is collected less often.

Memory leaks still happen in Java

The collector frees only unreachable objects. If your code keeps references it no longer needs, those objects stay forever. The usual causes:

Growing static collections

A static List or Map that only ever gets new entries.

Forgotten listeners

Objects registered for events and never removed.

Unbounded caches

Caches with no size limit or expiry.

Unclosed resources

Streams and connections that are never closed.

A leak in a few lines · ▶ Runs
import java.util.*;
class Main {
    static List<byte[]> history = new ArrayList<>();      // lives as long as the program
    static void handle(int request) {
        history.add(new byte[10_000]);                     // kept forever by mistake
    }
    public static void main(String[] args) {
        for (int i = 0; i < 1000; i++) handle(i);
        System.out.println(history.size() + " buffers still reachable, about "
            + history.size() * 10_000 / 1_000_000 + " MB that can never be freed");
    }
}
Output
1000 buffers still reachable, about 10 MB that can never be freed
