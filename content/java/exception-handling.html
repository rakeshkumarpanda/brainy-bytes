Exception Handling

Things go wrong: files vanish, networks drop, users type letters where numbers belong. Exception handling lets a program stop gracefully, or carry on with plan B, instead of crashing in a heap.

Part 1

🌧️What is an exception

An exception is an unwanted, unexpected event that disturbs the normal flow of a program: a file that is missing, a division by zero, a number typed as text.

Exception handling does not repair the problem. It gives the program an alternative path, so it can recover, or at least end gracefully and release what it was holding.

Plan B when the file is missing · ▶ Runs
import java.io.*;
class Main {
    public static void main(String[] args) {
        try {
            new FileReader("london-office.txt");          // plan A
            System.out.println("Reading the London file");
        } catch (FileNotFoundException e) {
            System.out.println("London file missing, using the local copy");   // plan B
        }
        System.out.println("Program ends normally");
    }
}
Output
London file missing, using the local copy
Program ends normally
Part 2

📚The runtime stack and default handling

The JVM gives every thread its own runtime stack. Each method call pushes a stack frame, and each return pops it.

When an exception happens:

  1. The method creates an exception object with three things: the name, a description and the stack trace (where it happened).
  2. It hands the object to the JVM, which looks for a matching catch in that method.
  3. If there is none, the method ends abnormally, its frame is removed, and the JVM checks the caller. This is propagation.
  4. If nobody catches it, even main ends, and the default exception handler prints the details and stops the thread.
See the propagation path · ▶ Runs
class Main {
    static void doMoreStuff() { System.out.println(10 / 0); }
    static void doStuff() { doMoreStuff(); }
    public static void main(String[] args) {
        try {
            doStuff();
        } catch (ArithmeticException e) {
            System.out.println("Caught: " + e);
            for (StackTraceElement f : e.getStackTrace())
                System.out.println("  at " + f.getMethodName());
        }
    }
}
Output
Caught: java.lang.ArithmeticException: / by zero
  at doMoreStuff
  at doStuff
  at main
Nobody catches it: the default handler takes over · 💥 Crashes at run time
class Main {
    static void doMoreStuff() { System.out.println(10 / 0); }
    static void doStuff() { doMoreStuff(); }
    public static void main(String[] args) { doStuff(); }
}
💥 Runtime error
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Main.doMoreStuff(Main.java:2)
	at Main.doStuff(Main.java:3)
	at Main.main(Main.java:4)
When a program has several threads, only the thread that failed stops. The others keep running.
Part 3

🌳The exception hierarchy

Throwable is the root of everything that can be thrown. It has two children.

Exception

Usually caused by the program or its inputs, and usually recoverable. Example: a missing file, so use another file.

Error

Usually caused by a lack of system resources, and usually not recoverable by your code. Example: the JVM runs out of memory.

Part 4

✅Checked and unchecked exceptions

The compiler checks some exceptions to make sure you handle them. These are checked exceptions. The rest are unchecked.

RuntimeException, Error and all their children are unchecked. Everything else is checked.
A checked exception must be handled or declared · ❌ Does not compile
import java.io.*;
class Main {
    public static void main(String[] args) {
        PrintWriter pw = new PrintWriter("notes.txt");
    }
}
❌ Compile error
unreported exception FileNotFoundException; must be caught or declared to be thrown
Whether an exception is checked or unchecked is decided by the compiler, but every exception happens at run time. "Checked" never means "happens at compile time".

Fully and partially checked

A checked exception is fully checked if all its children are checked too, like IOException. It is partially checked if some children are unchecked. Only two exist: Exception and Throwable.

ExceptionKind
IOExceptionfully checked
RuntimeExceptionunchecked
InterruptedExceptionfully checked
Errorunchecked
Throwablepartially checked
ArithmeticExceptionunchecked
Exceptionpartially checked
FileNotFoundExceptionfully checked
Part 5

🧤try and catch

Put the risky code in try and the handling code in catch.

Without and with try catch · ▶ Runs
class Main {
    public static void main(String[] args) {
        System.out.println("statement 1");
        try {
            System.out.println(10 / 0);
            System.out.println("never printed");
        } catch (ArithmeticException e) {
            System.out.println(10 / 2);
        }
        System.out.println("statement 3");
    }
}
Output
statement 1
5
statement 3

Control flow

Java snippet
try { stmt1; stmt2; stmt3; } catch (X e) { stmt4; } stmt5;
CaseRunsEnding
No exception1, 2, 3, 5normal
Exception at stmt2, catch matches1, 4, 5normal
Exception at stmt2, catch does not match1abnormal
Exception at stmt4 or stmt5whatever ran before italways abnormal
  • After an exception inside try, the rest of the try block is skipped, even if the catch matches. So keep only the risky lines inside try.
  • An exception inside a catch block or after the try statement is not protected by that try.

Several catch blocks

Different problems deserve different handling, so one try can have many catch blocks. The order matters: children first, parents last.

The most specific catch wins · ▶ Runs
class Main {
    public static void main(String[] args) {
        String[] inputs = {"10", "ten", null};
        for (String in : inputs) {
            try {
                System.out.println(100 / Integer.parseInt(in.trim()));
            } catch (NumberFormatException e) {
                System.out.println("not a number: " + in);
            } catch (NullPointerException e) {
                System.out.println("no input at all");
            } catch (Exception e) {
                System.out.println("something else: " + e);
            }
        }
    }
}
Output
10
not a number: ten
no input at all
Parent before child · ❌ Does not compile
class Main {
    public static void main(String[] args) {
        try { System.out.println(10 / 0); }
        catch (Exception e) { }
        catch (ArithmeticException e) { }
    }
}
❌ Compile error
exception ArithmeticException has already been caught

Part 7

🧹finally

Clean-up code, such as closing a file or a database connection, must run whether things went well or not. Put it in finally. It runs after the try, with or without an exception, caught or not.

finally runs in every case · ▶ Runs
class Main {
    static void attempt(String in) {
        try {
            System.out.println("result " + 100 / Integer.parseInt(in));
        } catch (ArithmeticException e) {
            System.out.println("caught " + e.getMessage());
        } finally {
            System.out.println("finally for " + in);
        }
    }
    public static void main(String[] args) {
        attempt("5");
        attempt("0");
        try { attempt("x"); } catch (NumberFormatException e) { System.out.println("outer caught it"); }
    }
}
Output
result 20
finally for 5
caught / by zero
finally for 0
finally for x
outer caught it

return and finally

Even a return inside try or catch waits for finally. If finally itself returns, its value wins.

finally overrides the return · ▶ Runs
class Main {
    static int m() {
        try {
            System.out.println("try");
            return 777;
        } finally {
            System.out.println("finally");
            return 999;
        }
    }
    public static void main(String[] args) { System.out.println(m()); }
}
Output
try
finally
999
A primitive return value is already decided · ▶ Runs
class Main {
    static int m() {
        int x = 10;
        try {
            return x;          // 10 is saved as the return value here
        } finally {
            x = 20;            // too late to change what is returned
        }
    }
    public static void main(String[] args) { System.out.println(m()); }
}
Output
10
The only thing that stops finally is the JVM itself shutting down, for example System.exit(0).
System.exit skips finally · ▶ Runs
try {
    System.out.println("try");
    System.exit(0);
} finally {
    System.out.println("finally");
}
Output
try
Returning from finally hides exceptions and confuses readers. Use finally for clean-up only.

🔤final, finally and finalize

WordWhat it isPurpose
finala modifierno extending, no overriding, no reassigning
finallya block after tryclean-up related to a try
finalize()a method of Objectclean-up the garbage collector once called before destroying an object. Deprecated since Java 9, do not use it
finally is preferred over finalize because you know exactly when it runs. Nobody can predict when, or even whether, the garbage collector calls finalize.
Part 9

🪆Nested try catch finally

A try block can contain another try. The inner catch handles what it can, and anything else bubbles to the outer catch. Both finally blocks always run, inner first.

Which catch handles what · ▶ Runs
class Main {
    static void run(String label, int divisor, String text) {
        System.out.println("-- " + label);
        try {
            try {
                System.out.println(10 / divisor);
                System.out.println(Integer.parseInt(text));
            } catch (ArithmeticException e) {
                System.out.println("inner catch: " + e.getMessage());
            } finally {
                System.out.println("inner finally");
            }
        } catch (NumberFormatException e) {
            System.out.println("outer catch: not a number");
        } finally {
            System.out.println("outer finally");
        }
    }
    public static void main(String[] args) {
        run("all good", 2, "7");
        run("divide by zero", 0, "7");
        run("bad number", 2, "seven");
    }
}
Output
-- all good
5
7
inner finally
outer finally
-- divide by zero
inner catch: / by zero
inner finally
outer finally
-- bad number
5
inner finally
outer catch: not a number
outer finally
try must be followed by catch or finally (or both). catch and finally cannot appear without a try. A try with resources may stand alone.
Part 10

🎯throw

Sometimes you create an exception object yourself and hand it to the JVM. That is what throw does.

Throwing your own exception · ▶ Runs
class Main {
    static void withdraw(int balance, int amount) {
        if (amount > balance) throw new IllegalArgumentException("Insufficient funds: need " + amount + ", have " + balance);
        System.out.println("Withdrew " + amount);
    }
    public static void main(String[] args) {
        withdraw(500, 200);
        try { withdraw(500, 900); } catch (IllegalArgumentException e) { System.out.println(e.getMessage()); }
    }
}
Output
Withdrew 200
Insufficient funds: need 900, have 500
  • Statements right after a throw are unreachable and do not compile.
  • You can only throw Throwable types.
  • throw null compiles but throws a NullPointerException.
Nothing can follow a throw · ❌ Does not compile
throw new ArithmeticException("bye");
System.out.println("hello");
❌ Compile error
unreachable statement
throw null · 💥 Crashes at run time
throw null;
💥 Runtime error
Exception in thread "main" java.lang.NullPointerException: Cannot throw exception because "null" is null
Part 11

📤throws

If a method can raise a checked exception and does not want to handle it, it must say so with throws. The responsibility moves to the caller.

Delegating to the caller · ▶ Runs
class Main {
    static void nap() throws InterruptedException {
        Thread.sleep(10);
        System.out.println("woke up");
    }
    public static void main(String[] args) throws InterruptedException {
        nap();
    }
}
Output
woke up
  • throws is only needed for checked exceptions. For unchecked ones it is optional.
  • It only convinces the compiler. It does not prevent the exception from ending the program.
  • It works for methods and constructors, and only with Throwable types.
If a try block can never throw a fully checked exception, a catch for it does not compile. Catching Exception, Throwable or any unchecked exception is always allowed.
Catching something that cannot happen · ❌ Does not compile
import java.io.*;
class Main {
    public static void main(String[] args) {
        try { System.out.println("hello"); }
        catch (IOException e) { }
    }
}
❌ Compile error
exception IOException is never thrown in body of corresponding try statement
KeywordMeaning
trythe risky code
catchthe handling code
finallythe clean-up code
throwhand an exception object to the JVM yourself
throwspass the responsibility to the caller
Part 12

🧑‍🎨Custom exceptions

Your own problems deserve their own names, like InsufficientFundsException or TooYoungException. Create them by extending an existing exception class.

  • Extend RuntimeException for an unchecked exception (the usual choice today).
  • Extend Exception for a checked one, when the caller really must decide what to do.
A marriage bureau with rules · ▶ Runs
class TooYoungException extends RuntimeException {
    TooYoungException(String msg) { super(msg); }
}
class TooOldException extends RuntimeException {
    TooOldException(String msg) { super(msg); }
}
class Main {
    static void register(int age) {
        if (age < 21) throw new TooYoungException("Please wait a few more years");
        if (age > 60) throw new TooOldException("The age limit has passed");
        System.out.println("Registered at age " + age);
    }
    public static void main(String[] args) {
        for (int age : new int[]{25, 18, 70}) {
            try { register(age); }
            catch (TooYoungException | TooOldException e) {
                System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
            }
        }
    }
}
Output
Registered at age 25
TooYoungException: Please wait a few more years
TooOldException: The age limit has passed

Part 14

🆕Modern exception handling

try-with-resources (Java 7)

Resources declared in the brackets after try are closed automatically, in reverse order, even if an exception happens. No finally needed. Any class that implements AutoCloseable works.

Automatic closing, last opened first closed · ▶ Runs
class Res implements AutoCloseable {
    private final String name;
    Res(String name) { this.name = name; System.out.println("open " + name); }
    public void close() { System.out.println("close " + name); }
}
class Main {
    public static void main(String[] args) {
        try (Res db = new Res("database"); Res file = new Res("file")) {
            System.out.println("working");
            throw new IllegalStateException("oops");
        } catch (IllegalStateException e) {
            System.out.println("caught " + e.getMessage());
        }
    }
}
Output
open database
open file
working
close file
close database
caught oops

The resources are closed before the catch block runs. Resource variables are effectively final, and if close() also throws, that exception is attached as a suppressed exception instead of being lost.

Multi-catch (Java 7)

One catch can handle several unrelated exceptions with |. The types must not be parent and child of each other.

Parent and child in one multi-catch · ❌ Does not compile
try { System.out.println(10 / 0); }
catch (ArithmeticException | RuntimeException e) { }
❌ Compile error
Alternatives in a multi-catch statement cannot be related by subclassing
Alternative ArithmeticException is a subclass of alternative RuntimeException

Helpful NullPointerException messages (Java 14)

Modern JVMs say exactly what was null, which saves a lot of guessing.

It names the culprit · 💥 Crashes at run time
String[] names = new String[2];
System.out.println(names[1].length());
💥 Runtime error
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because "names[1]" is null
