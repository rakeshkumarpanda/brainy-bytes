The word polymorphism joins the Greek poly (many) and morph (form). In code, it means the same call can behave differently depending on the arguments or on the object.

Part 2

🎯Overloading and method mapping

Overloading is compile time polymorphism: the compiler fixes which method runs. When no overload matches the argument types exactly, it widens the arguments and picks the most specific overload that fits. The session's example passes two byte values to sum with long, int and short versions: sum(short, short) wins because short is the nearest widening.

byte  → short → int → long → float → double
char  →         int → long → float → double      (char never widens to short)
If two overloads fit equally well, for example sum(int, long) and sum(long, int) called with sum(1, 2), the call is ambiguous and does not compile.
Part 3

🌳Inheritance and its types

A child class extends a parent and gets its fields and methods without rewriting them. Every class without an extends silently extends Object. Inheritance models an is-a relationship: an IPhone is a SmartMobile, which is a Mobile.

A class can extend only one class. class C1 extends P1, P2 is a compilation error. If both parents had a method with the same name, the child would not know which to inherit: the diamond problem. Java allows multiple inheritance only through interfaces.

Part 4

🔄Method overriding

Overriding gives a child its own version of a parent method with the same name and the same parameters. Which version runs is decided at run time by the actual object, so it is called runtime polymorphism or dynamic binding.

RuleDetail
SignatureSame name and parameter list. A different list is overloading, not overriding
Return typeSame, or a subtype (covariant return)
AccessSame or wider. A public method cannot become protected in the child
Cannot overridestatic (hidden instead), final and private methods
@OverrideOptional, but the compiler then checks that a parent method really exists. A typo such as Os() becomes an error instead of a silent new method
Part 5

⬆️super and the order of construction

super refers to the parent part of the current object. super.method() calls the parent version of an overridden method, super.field reads a hidden parent field, and super(…) picks a parent constructor.

Every constructor starts by running a parent constructor. If you do not write super(…) or this(…) as the first line, the compiler inserts super(). So building an IPhone15 runs Phone, then SmartPhone, then IPhone15. If the parent has no no-argument constructor, the child must call super(…) with arguments, or it does not compile.
Part 6

🔃Upcasting, downcasting and instanceof

Upcasting (implicit)

Mobile3 m = new Iphone3(); A child object in a parent reference. Always safe. Only the members the parent declares can be called, but overridden methods still run the child version.

Downcasting (explicit)

Iphone3 i = (Iphone3) m; A parent reference back to a child type. It compiles, and works only if the object really is an Iphone3. Otherwise the JVM throws ClassCastException.

The session's DownCasting program writes (Iphone5) new Mobile5(). It compiles, then fails at run time, because a plain Mobile5 object never becomes an iPhone. Use instanceof before casting, or Java 16 pattern matching: if (m instanceof Iphone3 i) i.processor();

Part 8

🔌Interfaces

An interface is a contract: a list of methods a class promises to provide. A class can implement several interfaces, which is how Java offers multiple inheritance safely.

MemberWhat Java assumes
Method without a bodypublic abstract, so implementing methods must be public
Variablepublic static final, a constant that must be initialised
default method (JDK 8)Has a body and is inherited. A class may override it
static method (JDK 8)Called as Mobile6.test1() only, never through an object
Objectsnew Mobile6() is a compilation error
When two interfaces give the same default method, the class must override it and may pick a version with Wifi.super.connect(). Python resolves the same clash with its method resolution order, and JavaScript combines behaviour with mixins.
Part 9

💊Encapsulation with getters and setters

Encapsulation wraps data and the code that changes it in one class, and hides the data with private. Other classes go through public getters (read) and setters (write), so the class can check every change, keep a field read only by leaving out its setter, or change how it stores data without breaking callers.

Testers meet encapsulation in the Page Object Model: WebElements are private fields of a page class, and tests call public methods such as login(user, pass) instead of touching locators directly.
