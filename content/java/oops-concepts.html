Part 1

🙈Data hiding

Data hiding means outsiders cannot touch an object's data directly. They have to go through methods, and those methods can check every request. In Java you hide data by making fields private.

A bank account that guards its balance · ▶ Runs
class Account {
    private double balance;                       // hidden
    public void deposit(double amount) {
        if (amount <= 0) { System.out.println("Rejected: " + amount); return; }
        balance += amount;
    }
    public double getBalance() { return balance; }
}
class Main {
    public static void main(String[] args) {
        Account a = new Account();
        a.deposit(500);
        a.deposit(-100);                          // validation catches it
        System.out.println(a.getBalance());
    }
}
Output
Rejected: -100.0
500.0
Direct access is refused · ❌ Does not compile
class Account { private double balance; }
class Main {
    public static void main(String[] args) {
        new Account().balance = 1_000_000;
    }
}
❌ Compile error
balance has private access in Account
The main gain is security: nobody can set a negative balance or skip the checks.
Part 2

🎭Abstraction

Abstraction means showing what something does while hiding how it does it. An ATM shows "withdraw" and "check balance", and hides the network calls and database updates behind the screen.

  • Security: the inner workings stay private.
  • Easy change: the inside can be rewritten without disturbing any user.
  • Easy use: users learn a few services instead of every detail.

Java achieves abstraction with interfaces and abstract classes, as shown in the previous chapter.

Callers know the service, not the engine · ▶ Runs
interface Maps {
    String route(String from, String to);
}
class FastMaps implements Maps {
    public String route(String from, String to) {
        return from + " → " + to + " (shortest path computed with secret sauce)";
    }
}
class Main {
    public static void main(String[] args) {
        Maps m = new FastMaps();                 // the caller only knows Maps
        System.out.println(m.route("Home", "Office"));
    }
}
Output
Home → Office (shortest path computed with secret sauce)
Part 3

💊Encapsulation

Encapsulation wraps data and the code that works on it into one unit, a class. Every Java class is encapsulated. When it also hides its data (data hiding) and offers services instead (abstraction), we get the full benefit.

Encapsulation = Data hiding + Abstraction

The usual pattern is private fields with public getter and setter methods. The cost is a little more code, which also makes the program slightly longer to write.

Tightly encapsulated classes

A class is tightly encapsulated when every field is private, including inherited ones. Whether it has getters and setters, and whether those are public, does not matter.

Java snippet
class A { private int x = 10; }          // tightly encapsulated
class B extends A { int y = 20; }        // not: y is not private
class C extends A { private int z = 30; } // tightly encapsulated
If the parent class is not tightly encapsulated, no child can be either, because the child inherits the non-private field.
Part 4

👨‍👧IS-A relationship (inheritance)

The IS-A relationship is inheritance, written with extends. A Dog IS-A Animal, so it gets everything an Animal has. The big win is code reuse.

What a child gets and what a parent can hold · ▶ Runs
class Animal {
    void eat() { System.out.println("eating"); }
}
class Dog extends Animal {
    void bark() { System.out.println("woof"); }
}
class Main {
    public static void main(String[] args) {
        Dog d = new Dog();
        d.eat();              // inherited
        d.bark();
        Animal a = new Dog(); // a parent reference can hold a child object
        a.eat();
    }
}
Output
eating
woof
eating
StatementAllowed
Parent methods called on a child objectyes
Child methods called on a parent objectno
Parent reference holding a child objectyes
Child methods through a parent referenceno, the compiler only knows the parent type
Child reference holding a parent objectno
A parent reference does not know child methods · ❌ Does not compile
class Animal { }
class Dog extends Animal { void bark() { } }
class Main {
    public static void main(String[] args) {
        Animal a = new Dog();
        a.bark();
    }
}
❌ Compile error
cannot find symbol
symbol:   method bark()

Rules

  • Every class has Object as its root. A class that extends nothing extends Object directly.
  • A class can extend only one class. Two parents with the same method would leave the child confused, which is the "diamond problem". Interfaces avoid it because they had no implementation to fight over.
  • Cyclic inheritance is not allowed: class A extends B and class B extends A do not compile, and neither does class A extends A.
Two parents are not allowed · ❌ Does not compile
class A { } class B { }
class C extends A, B { }
❌ Compile error
'{' expected
A class cannot be its own parent · ❌ Does not compile
class A extends A { }
❌ Compile error
cyclic inheritance involving A
Part 5

🚗HAS-A relationship

HAS-A means one object holds a reference to another. A Car HAS-A Engine. There is no special keyword, you just declare a field. It also reuses code, without the tight bond of inheritance.

A car that has an engine · ▶ Runs
class Engine { String start() { return "vroom"; } }
class Car {
    private final Engine engine = new Engine();     // HAS-A
    void drive() { System.out.println("Engine says " + engine.start()); }
}
class Main {
    public static void main(String[] args) { new Car().drive(); }
}
Output
Engine says vroom

Composition (strong)

The part cannot live without the whole. A university and its departments: close the university and the departments vanish.

Aggregation (weak)

The part lives on its own. A department and its professors: close the department and the professors still exist.

"Favour HAS-A over IS-A" is common advice. Use inheritance only when the child truly is a kind of the parent.
Part 6

✒️Method signature

A method's signature is its name plus the types of its parameters, in order. The return type is not part of it. The compiler uses signatures to find the right method.

Java snippet
public static int m1(int i, float f)   →   signature: m1(int, float)

Two methods with the same signature cannot live in one class, even if the return types differ.

Same signature, different return type · ❌ Does not compile
class Main {
    public void m1(int i) { }
    public int m1(int x) { return 10; }
}
❌ Compile error
method m1(int) is already defined in class Main
Part 7

🎚️Overloading

Methods are overloaded when they share a name but have different parameter lists. The compiler picks one by looking at the argument types at compile time, so overloading is called compile-time or static polymorphism.

One name, three methods · ▶ Runs
class Main {
    static void print(int i)    { System.out.println("int: " + i); }
    static void print(double d) { System.out.println("double: " + d); }
    static void print(String s) { System.out.println("String: " + s); }
    public static void main(String[] args) {
        print(10); print(10.5); print("ten");
    }
}
Output
int: 10
double: 10.5
String: ten

How the compiler picks

  1. Look for an exact match.
  2. If none, widen the argument step by step (byte → short → int → long → float → double, and char → int) and look again.
  3. If still none, try boxing (int → Integer).
  4. Last of all, try a var-arg method.
  5. If two candidates remain equally good, the call is ambiguous and does not compile.
Automatic promotion · ▶ Runs
class Main {
    static void m(int i)   { System.out.println("int"); }
    static void m(float f) { System.out.println("float"); }
    public static void main(String[] args) {
        m('a');     // char widens to int
        m(10L);     // long widens to float
    }
}
Output
int
float
double cannot shrink · ❌ Does not compile
class Main {
    static void m(int i)   { }
    static void m(float f) { }
    public static void main(String[] args) { m(10.5); }
}
❌ Compile error
no suitable method found for m(double)
method Main.m(int) is not applicable
(argument mismatch; possible lossy conversion from double to int)
method Main.m(float) is not applicable
(argument mismatch; possible lossy conversion from double to float)

The most specific method wins

null prefers the child type · ▶ Runs
class Main {
    static void m(Object o) { System.out.println("Object"); }
    static void m(String s) { System.out.println("String"); }
    public static void main(String[] args) {
        m(new Object());
        m("hi");
        m(null);    // String is more specific than Object
    }
}
Output
Object
String
String
Two unrelated candidates for null · ❌ Does not compile
class Main {
    static void m(String s)        { }
    static void m(StringBuilder b) { }
    public static void main(String[] args) { m(null); }
}
❌ Compile error
reference to m is ambiguous
both method m(String) in Main and method m(StringBuilder) in Main match
Overload resolution looks at the reference type, never the runtime object. With m(Animal) and m(Monkey), the call m(a) where Animal a = new Monkey(); picks m(Animal).
Reference type decides · ▶ Runs
class Animal { } class Monkey extends Animal { }
class Main {
    static void m(Animal a) { System.out.println("Animal version"); }
    static void m(Monkey m) { System.out.println("Monkey version"); }
    public static void main(String[] args) {
        Animal a = new Monkey();
        m(a);
        m(new Monkey());
    }
}
Output
Animal version
Monkey version
Part 8

🔁Overriding

A child overrides a parent method by declaring the same signature with its own body. Which body runs is decided at run time, by the actual object. That is why overriding is called runtime polymorphism, dynamic method dispatch or late binding.

The object decides · ▶ Runs
class Parent {
    void marry() { System.out.println("Parent picks the match"); }
}
class Child extends Parent {
    void marry() { System.out.println("Child picks the match"); }
}
class Main {
    public static void main(String[] args) {
        Parent p = new Child();
        p.marry();
    }
}
Output
Child picks the match

Rules

  1. Same name and same parameter types.
  2. The return type must be the same, or a child type of it for objects (covariant return, since Java 5). Primitives must match exactly.
  3. private methods are not visible in the child, so a child method with the same name is a new method, not an override.
  4. final methods cannot be overridden.
  5. Access can stay the same or get wider, never narrower. public stays public.
  6. The child may not throw a broader checked exception. Unchecked exceptions are free.
Covariant return type · ▶ Runs
class Parent { Object get() { return "parent"; } }
class Child extends Parent {
    @Override String get() { return "child"; }
}
class Main {
    public static void main(String[] args) {
        System.out.println(new Child().get().length());
    }
}
Output
5
Narrower access · ❌ Does not compile
class Parent { public void m() { } }
class Child extends Parent { protected void m() { } }
❌ Compile error
m() in Child cannot override m() in Parent
attempting to assign weaker access privileges; was public
Broader checked exception · ❌ Does not compile
class Parent { void m() throws java.io.IOException { } }
class Child extends Parent { void m() throws Exception { } }
❌ Compile error
m() in Child cannot override m() in Parent
overridden method does not throw Exception
Primitive return must match · ❌ Does not compile
class Parent { int m() { return 1; } }
class Child extends Parent { long m() { return 1; } }
❌ Compile error
m() in Child cannot override m() in Parent
return type long is not compatible with int

Static methods are hidden, not overridden

If both parent and child have the same static method, the reference type decides which one runs. This is method hiding.

Hiding versus overriding · ▶ Runs
class Parent {
    static void s() { System.out.println("Parent static"); }
    void i() { System.out.println("Parent instance"); }
}
class Child extends Parent {
    static void s() { System.out.println("Child static"); }
    void i() { System.out.println("Child instance"); }
}
class Main {
    public static void main(String[] args) {
        Parent p = new Child();
        p.s();     // reference type: Parent
        p.i();     // object type: Child
    }
}
Output
Parent static
Child instance

Variables are never overridden

Fields are resolved by the reference type at compile time, even when the child declares a field with the same name.

Fields follow the reference · ▶ Runs
class Parent { String x = "parent field"; }
class Child extends Parent { String x = "child field"; }
class Main {
    public static void main(String[] args) {
        Parent p = new Child();
        System.out.println(p.x);
        System.out.println(((Child) p).x);
    }
}
Output
parent field
child field
Write @Override above every overriding method. If you misspell the name, the compiler tells you instead of quietly creating a new method.

Part 10

🦎Polymorphism

Polymorphism means "many forms": one name, different behaviour depending on the situation. Java has two kinds.

Compile-time

Overloading, and method hiding. The compiler decides.

Runtime

Overriding. The JVM decides by looking at the real object.

The everyday benefit: write code against a parent type, and it keeps working for every child, including children written later.

One loop, many shapes · ▶ Runs
abstract class Shape { abstract double area(); }
class Circle extends Shape { double r; Circle(double r) { this.r = r; } double area() { return Math.PI * r * r; } }
class Rect extends Shape { double w, h; Rect(double w, double h) { this.w = w; this.h = h; } double area() { return w * h; } }
class Main {
    public static void main(String[] args) {
        List<Shape> shapes = List.of(new Circle(1), new Rect(2, 3));
        for (Shape s : shapes) System.out.printf("%s %.2f%n", s.getClass().getSimpleName(), s.area());
    }
}
Output
Circle 3.14
Rect 6.00
The three pillars of OOP are encapsulation (security), polymorphism (flexibility) and inheritance (reusability).
Part 11

🧊Static control flow

When a class is loaded, Java runs its static parts in three steps:

  1. Identify every static member, top to bottom. Each static variable starts with its default value.
  2. Run static variable assignments and static blocks, in the order they are written.
  3. Run main.
Predict the order first · ▶ Runs
class Main {
    static int i = 10;
    static {
        m1();
        System.out.println("first static block");
    }
    public static void main(String[] args) {
        m1();
        System.out.println("main method");
    }
    static void m1() { System.out.println(j); }
    static { System.out.println("second static block"); }
    static int j = 20;
}
Output
0
first static block
second static block
20
main method

The first line prints 0 because j has been identified but not yet assigned. A variable in that state is called read indirectly, write only (RIWO).

During RIWO you may read a variable through a method (indirectly) but not by name directly. A direct read before the declaration is an "illegal forward reference".
Direct read during RIWO · ❌ Does not compile
class Main {
    static { System.out.println(x); }
    static int x = 10;
}
❌ Compile error
illegal forward reference

Parent and child

Loading a child class loads the parent first. So the parent's static flow runs completely, then the child's, then main.

Parent static first · ▶ Runs
class Base {
    static { System.out.println("Base static block"); }
}
class Derived extends Base {
    static { System.out.println("Derived static block"); }
    public static void main(String[] args) { System.out.println("Derived main"); }
}
Output
Base static block
Derived static block
Derived main
Use a static block for one-time setup when the class loads, such as loading a native library or filling a lookup table.
Part 12

🏗️Instance control flow

Every time you create an object, Java runs these steps:

  1. Identify instance members, top to bottom (with default values).
  2. Run instance variable assignments and instance blocks, in the order they are written.
  3. Run the constructor.
Instance flow for one object · ▶ Runs
class Main {
    int i = 10;
    { m1(); System.out.println("first instance block"); }
    Main() { System.out.println("constructor"); }
    public static void main(String[] args) {
        Main t = new Main();
        System.out.println("main");
    }
    void m1() { System.out.println(j); }
    { System.out.println("second instance block"); }
    int j = 20;
}
Output
0
first instance block
second instance block
constructor
main

The full picture with a parent

Everything together · ▶ Runs
class Parent {
    static { System.out.println("1. Parent static"); }
    { System.out.println("3. Parent instance block"); }
    Parent() { System.out.println("4. Parent constructor"); }
}
class Child extends Parent {
    static { System.out.println("2. Child static"); }
    { System.out.println("5. Child instance block"); }
    Child() { System.out.println("6. Child constructor"); }
    public static void main(String[] args) {
        new Child();
        System.out.println("--- second object ---");
        new Child();
    }
}

Static parts run once per class. Instance parts run for every object, parent first, then child.

Part 13

🔨Constructors

Creating an object is not enough. It also needs its starting values. A constructor runs automatically at creation to do exactly that.

Two constructors, two students · ▶ Runs
class Student {
    String name; int roll;
    Student(String name, int roll) { this.name = name; this.roll = roll; }
    Student() { this("Unknown", 0); }          // calls the other constructor
}
class Main {
    public static void main(String[] args) {
        Student a = new Student("Priya", 101);
        Student b = new Student();
        System.out.println(a.name + " " + a.roll + ", " + b.name + " " + b.roll);
    }
}
Output
Priya 101, Unknown 0

Rules

  1. The name must match the class name exactly.
  2. There is no return type, not even void. Add one and it becomes an ordinary method that just happens to share the class name.
  3. Allowed modifiers are only the four access levels.
  4. If you write no constructor, the compiler adds a default constructor with no parameters, whose only line is super();. If you write any constructor, no default is added.
  5. The first line of every constructor is super(...) or this(...). If you write neither, the compiler inserts super();. You cannot use both, and they are allowed only as the first line of a constructor.
  6. Constructors can be overloaded, but they are not inherited, so they cannot be overridden.
void makes it a method, not a constructor · ▶ Runs
class Main {
    void Main() { System.out.println("method"); }
    public static void main(String[] args) {
        Main m = new Main();         // default constructor, prints nothing
        m.Main();                    // the method runs only when called
    }
}
Output
method
Parent has no no-arg constructor · ❌ Does not compile
class Parent { Parent(int x) { } }
class Child extends Parent { }
❌ Compile error
constructor Parent in class Parent cannot be applied to given types;
required: int
found:    no arguments
reason: actual and formal argument lists differ in length

The child's default constructor calls super(), but Parent only has Parent(int). Fix it by calling super(10) in a child constructor, or by adding Parent().

Constructors calling each other in a circle · ❌ Does not compile
class Main {
    Main() { this(10); }
    Main(int i) { this(); }
}
❌ Compile error
recursive constructor invocation
super() must be first · ❌ Does not compile
class Main {
    Main() {
        System.out.println("hello");
        super();
    }
}
❌ Compile error
call to super must be first statement in constructor
Constructors and instance blocks both run at object creation. The instance blocks run first, then the constructor body.
Part 14

☝️Singleton classes

A singleton class allows only one object. Runtime is one: Runtime.getRuntime() always returns the same object. Singletons save memory when every user can share one object, such as a configuration or a connection pool.

How to build one

  1. Make the constructor private, so nobody outside can call new.
  2. Keep one private static instance.
  3. Offer a public static method that returns it.
One object, however many times you ask · ▶ Runs
class Config {
    private static final Config INSTANCE = new Config();
    private Config() { System.out.println("Config created"); }
    static Config get() { return INSTANCE; }
}
class Main {
    public static void main(String[] args) {
        Config a = Config.get();
        Config b = Config.get();
        System.out.println(a == b);
        System.out.println(Runtime.getRuntime() == Runtime.getRuntime());
    }
}
Output
Config created
true
true
Lazy version: create on first use · ▶ Runs
class Logger {
    private static Logger instance;
    private Logger() { System.out.println("Logger created"); }
    static synchronized Logger get() {
        if (instance == null) instance = new Logger();
        return instance;
    }
}
class Main {
    public static void main(String[] args) {
        System.out.println("before first use");
        Logger.get(); Logger.get();
    }
}
Output
before first use
Logger created
The same idea makes "doubleton" classes (two objects) and pools. And a private constructor alone also stops a class from being extended, because a child must call it.
Part 15

🧷Coupling and cohesion

Coupling: how much classes depend on each other

Tight coupling means a change in one class breaks others. Aim for loose coupling: depend on interfaces, not on concrete details.

Cohesion: how focused one class is

A class that does one clear job has high cohesion. One giant class that logs in, sends mail and prints reports has low cohesion.

Good design = loose coupling + high cohesion
Loose coupling through an interface · ▶ Runs
interface Notifier { void send(String msg); }
class Sms implements Notifier { public void send(String m) { System.out.println("SMS: " + m); } }
class Email implements Notifier { public void send(String m) { System.out.println("Email: " + m); } }
class OrderService {
    private final Notifier notifier;                    // depends on the interface only
    OrderService(Notifier n) { notifier = n; }
    void placeOrder() { notifier.send("Order placed"); }
}
class Main {
    public static void main(String[] args) {
        new OrderService(new Sms()).placeOrder();
        new OrderService(new Email()).placeOrder();     // no change inside OrderService
    }
}
Output
SMS: Order placed
Email: Order placed

Casting an object reference changes the type of the reference, never the object itself.
