🧒 In plain words

A big suite is slow when tests run one by one. Running them side by side, on one machine or many, makes it fast, as long as the tests do not get in each other's way.

Part 1

👷Workers: tests at the same time

🧒 Beginner friendly

A suite of 400 tests that takes 2 seconds each needs over 13 minutes in a row. Run 4 at a time and it needs about 3. Each runner does this with workers: separate processes or threads, each with its own browser.

What happens

Four tests ran on two workers at once, and the output shows which worker took which test. Each worker has its own browser, and each test still gets its own fresh page, so the tests cannot see each other. In Playwright Test the workers are separate processes. pytest-xdist also starts processes, named gw0 and gw1. JUnit uses threads inside one JVM, so each class gets its own Playwright on its own thread.

Playwright Test runs files in parallel and the tests inside a file in order. fullyParallel: true lets every test run on any worker, which balances the load better.
Part 2

🧱Parallel tests must not share data

Each test gets its own page and its own cookies, so the browser side is already separate. The danger is data outside the browser: the same user account, the same database row, the same file. Two tests that change it at the same time can break each other in ways that fail only sometimes.

The best fix is to give each test its own data: a new person with a unique name, a fresh account, a test id in the file name. When a few tests really must share something, tell the runner they must not overlap.

package com.brainy;

import com.google.gson.JsonParser;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.RequestOptions;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.parallel.ResourceLock;
import java.util.Map;

import static org.junit.jupiter.api.Assertions.assertEquals;

@UsePlaywright(ShopOptions.class)
public class AddMeeraTest {
  @Test
  @ResourceLock("people")              // never at the same time as another test holding "people"
  void addMeera(Page page) {
    System.out.println("add Meera: start");
    int before = JsonParser.parseString(page.request().get("/api/people").text()).getAsJsonArray().size();
    page.request().post("/api/people", RequestOptions.create().setData(Map.of("name", "Meera", "email", "meera@shop.example")));
    int after = JsonParser.parseString(page.request().get("/api/people").text()).getAsJsonArray().size();
    assertEquals(before + 1, after);
    System.out.println("add Meera: done");
  }
}

What happens

The two tests that count people never overlapped: one finished before the other started, while the products test ran next to them. Playwright Test calls this a test lock (new in version 1.63). JUnit has the same idea in @ResourceLock. pytest-xdist has no lock, but a group sends tests to one worker, which runs them one after the other.

⚠️
Playwright Test also has a serial mode, test.describe.configure({ mode: 'serial' }), where the tests in a file run in order and the rest are skipped after a failure. The Playwright docs advise against it: isolated tests are faster and easier to retry.
Part 3

🔁Retries and flaky tests

A flaky test passes and fails on the same code. A retry runs a failed test again. If it passes the second time, the runner reports it as flaky, so the run stays green but the problem stays visible.

A flaky test that passes on the second try · ✅ mvn test ran
📄 src/test/java/com/brainy/OfferTest.java
package com.brainy;

import com.microsoft.playwright.*;
import com.microsoft.playwright.assertions.LocatorAssertions;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.*;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

// Surefire reruns this class from the start, so it opens and closes Playwright itself.
public class OfferTest {
  private static int attempt = 0;      // the rerun happens in the same JVM
  static Playwright playwright;
  static Browser browser;
  BrowserContext context;
  Page page;

  @BeforeAll
  static void launch() {
    playwright = Playwright.create();
    browser = playwright.chromium().launch();
  }

  @BeforeEach
  void newPage() {
    context = browser.newContext(new Browser.NewContextOptions().setBaseURL("http://localhost:4173"));
    page = context.newPage();
  }

  @Test
  void theOfferShowsUp() {
    attempt++;
    System.out.println("attempt " + attempt);
    page.navigate("/widgets");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Load offers")).click();
    // Flaky on purpose: the first try waits only 0.5 s, but the offer needs 1.2 s.
    double wait = attempt == 1 ? 500 : 5_000;
    assertThat(page.getByTestId("offer")).isVisible(new LocatorAssertions.IsVisibleOptions().setTimeout(wait));
  }

  @AfterEach
  void closeContext() {
    context.close();
  }

  @AfterAll
  static void close() {
    playwright.close();
  }
}

What happens

The first try failed, the retry passed, and the run still passed. Each runner marks the test so you notice: Playwright Test says 1 flaky, pytest says 1 rerun and Surefire says Flakes: 1. A flaky test is a bug in the test or the app, and the retry only hides it until someone fixes it. In our run, a Surefire rerun of a class that uses @UsePlaywright failed with Playwright connection closed, so the Java version opens and closes Playwright in its own @BeforeAll and @AfterAll.

Most teams turn retries on only in CI, for example retries: process.env.CI ? 2 : 0, and keep a list of flaky tests to fix. A retry also records a trace in Playwright Test when trace is on-first-retry, which is often the fastest way to find the cause.

What happens

The offer appears 1.2 s after the click. The default check waits up to 5 s, so the first test passed. The second test allowed only 1 s and failed, and the error names the timeout it used. The Pay now button is disabled for 1 s, and the click waited for it inside its own 3 s limit.

💡
When a check times out, the fix is almost never a bigger number. Ask what the page was waiting for. A longer timeout is right only when the app really is that slow, such as a report that takes 20 s to build.

test('shows five products', async ({ page }, testInfo) => {
  console.log(`${testInfo.title} on worker ${testInfo.parallelIndex}`);
  await page.goto('/products');
  await expect(page.getByRole('listitem')).toHaveCount(5);
});

test('finds the lamp', async ({ page }, testInfo) => {
  console.log(`${testInfo.title} on worker ${testInfo.parallelIndex}`);
  await page.goto('/products');
  await page.getByPlaceholder('Search products').fill('lamp');
  await expect(page.getByRole('listitem')).toHaveCount(1);
});

test('page 2 is the last page', async ({ page }, testInfo) => {
  console.log(`${testInfo.title} on worker ${testInfo.parallelIndex}`);
  await page.goto('/orders');
  await page.getByRole('button', { name: 'Next' }).click();
  await expect(page.getByText('Page 2 of 2')).toBeVisible();
});

What happens

Each command ran half of the suite, the way two CI machines would, one command each. Playwright Test splits with --shard. pytest needs a plugin, and pytest-split is shown here. Maven has no shard option, so teams give each machine its own classes with -Dtest, or its own tags with -Dgroups. The other machine would run mvn test -Dtest=OrdersTest.

🏢
Shards are balanced by test count, not by time. With fullyParallel: true, Playwright Test splits single tests, so the shards come out even. Without it, whole files are split, so keep files a similar size. pytest-split can balance by recorded durations.

The reporting chapter shows how the blob reports of each shard are merged into one HTML report, and the CI chapter shows the GitHub Actions matrix that starts the shards.
