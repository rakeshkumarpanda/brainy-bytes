Page objects and components

Keep tests readable and cheap to change. Put the locators and steps of each screen in a page object, the parts that repeat in components, and hand them to tests through fixtures.

🧒 In plain words

A page object is a class that knows one screen of the app. Tests ask it to sign in or add to cart, so when the screen changes, only the class changes.

Part 1

🤔Why page objects

🧒 Beginner friendly

Picture 200 tests that all sign in by filling the Email field. One day the label changes to Email address, and 200 tests fail. A page object is a class that holds the locators and steps for one screen. Tests call its methods, so a change to the screen means a change in one file.

Without page objectsWith page objects
locators copied into every testeach locator written once
a UI change breaks many filesa UI change is fixed in one class
tests read as clicks and fillstests read as steps: signIn, addToCart
new team members copy old testsnew tests reuse a small, named set of methods

package com.brainy.pages;

import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.options.AriaRole;

// Everything a test needs to know about the sign in page, in one place
public class LoginPage {
  private final Page page;
  public final Locator email;
  public final Locator password;
  public final Locator signInButton;
  public final Locator error;

  public LoginPage(Page page) {
    this.page = page;
    this.email = page.getByLabel("Email");
    this.password = page.getByLabel("Password");
    this.signInButton = page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Sign in"));
    this.error = page.getByRole(AriaRole.ALERT);
  }

  public void navigate() {
    page.navigate("/login");
  }

  public void signIn(String email, String password) {
    this.email.fill(email);
    this.password.fill(password);
    signInButton.click();
  }
}

Part 2

🧩Components for repeated parts

Some parts are not a page: the header on every screen, a product card shown five times, a date picker used in three forms. Give each one its own class, a component, and let page objects create them. A component takes a root locator and finds everything inside it.

Step 2: components for parts that repeat · ✅ mvn test ran

package com.brainy.components;

import com.microsoft.playwright.Locator;
import com.microsoft.playwright.options.AriaRole;

// One product card. Every locator starts from the card, so it never finds another product's button.
public class ProductCard {
  public final Locator root;
  public final Locator price;
  public final Locator button;

  public ProductCard(Locator root) {
    this.root = root;
    this.price = root.locator(".price");
    this.button = root.getByRole(AriaRole.BUTTON);
  }

  public void addToCart() {
    root.getByRole(AriaRole.BUTTON, new Locator.GetByRoleOptions().setName("Add to cart")).click();
  }
}

// The header is on every page, so it is a component, not a page
public class Header {
  public final Locator greeting;
  public final Locator cartCount;
  public final Locator signOut;

  public Header(Page page) {
    Locator root = page.getByRole(AriaRole.BANNER);
    this.greeting = root.locator("#hello");
    this.cartCount = root.getByTestId("cart-count");
    this.signOut = root.getByRole(AriaRole.LINK, new Locator.GetByRoleOptions().setName("Sign out"));
  }
}
📄 src/test/java/com/brainy/pages/ProductsPage.java
package com.brainy.pages;

import com.brainy.components.Header;
import com.brainy.components.ProductCard;
import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.options.AriaRole;

public class ProductsPage {
  private final Page page;
  public final Header header;
  public final Locator search;
  public final Locator cards;

  public ProductsPage(Page page) {
    this.page = page;
    this.header = new Header(page);
    this.search = page.getByPlaceholder("Search products");
    this.cards = page.getByRole(AriaRole.LISTITEM);
  }

  public void navigate() {
    page.navigate("/products");
  }

  public ProductCard card(String name) {
    return new ProductCard(cards.filter(new Locator.FilterOptions()
        .setHas(page.getByRole(AriaRole.HEADING, new Page.GetByRoleOptions().setName(name)))));
  }
}

What happens

All tests passed, and none of them creates a page object or signs in. Playwright Test builds productsPage on demand with test.extend, pytest does the same with fixtures in conftest.py, and JUnit uses a base class with a @BeforeEach method. @UsePlaywright is inherited, so the subclass needs no annotation of its own.

Part 4

📏Rules teams follow

Page objects can grow into a second, harder copy of the app. These rules keep them small and useful.

RuleWhy
one class per screen or componenteasy to find, small enough to read
locators by role, label or test idthey survive style changes, as the locators chapter showed
methods are user actions: signIn, addToCarttests read like steps, not clicks
checks live in teststhe test shows what it proves
no sleeps and no waits for timeoutsPlaywright actions and checks already wait
no test data inside the classpass it in, so one page object serves many tests
a method returns the next page object when the screen changessignIn() can return ProductsPage, so the flow is clear
🏢
Large suites sometimes add one more layer of business steps, such as checkout(user, items), built from page objects. Add it when you notice the same five page object calls in many tests, not before.
