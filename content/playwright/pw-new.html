🆕How Playwright changes, and how to keep up

🧒 Beginner friendly

Playwright ships a new version roughly every month or two. Each version comes with its own browser builds, so updating Playwright also updates the browsers you test with. This course uses 1.63.

VersionHighlights for testers
1.56Playwright Test Agents: planner, generator and healer. page.consoleMessages(), page.pageErrors() and page.requests()
1.57a Speedboard tab in the HTML report that shows the slowest tests, and Chrome for Testing builds instead of Chromium
1.58a timeline chart for merged reports, and old selectors such as _react removed
1.59page.screencast for videos with chapters and overlays, page.ariaSnapshot(), and npx playwright trace on the command line
1.60test.abort(), locator.drop() and HAR recording through tracing
1.61passkeys through browserContext.credentials, page.localStorage, and -G as a short form of --grep-invert
1.62retryStrategy, WebP screenshots, and npx playwright mcp bundled with Playwright
1.63test locks, locator.visible(), --add-reporter and a perfetto reporter
1.64page.webmcp, --shuffle, locator.within() and page.getByRef()

🏢
Read the release notes before updating, and update on a branch so CI shows what changed. Each release lists its breaking changes, such as page.accessibility removed in 1.57 and Node.js 16 support removed in 1.54.
Part 2

🧾A new feature in all four languages

Many new features arrive in every language at once. Here is one from 1.56 that makes debugging easier: the page remembers its recent console messages, errors and network requests, so a test can read them after the fact.

New in 1.56: read console messages, errors and requests at any time · ✅ mvn test ran
📄 src/test/java/com/brainy/CollectTest.java
package com.brainy;

import com.microsoft.playwright.ConsoleMessage;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

@UsePlaywright(ShopOptions.class)
public class CollectTest {
  @Test
  void readsConsoleMessagesAndPageErrorsAfterTheFact(Page page) {
    page.navigate("/widgets");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Write to the console")).click();
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Break the page")).click();
    page.waitForCondition(() -> !page.pageErrors().isEmpty());

    // New in 1.56: the page keeps its recent console messages, errors and requests, no listener needed
    for (ConsoleMessage m : page.consoleMessages()) System.out.println("console." + m.type() + ": " + m.text());
    for (String e : page.pageErrors()) System.out.println("page error: " + e);
    System.out.println("requests so far: " + page.requests().size());
    assertEquals(1, page.pageErrors().size());
  }
}

from playwright.sync_api import Page


def test_reads_console_messages_and_page_errors_after_the_fact(page: Page):
    page.goto("/widgets")
    page.get_by_role("button", name="Write to the console").click()
    with page.expect_event("pageerror"):
        page.get_by_role("button", name="Break the page").click()

    # New in 1.56: the page keeps its recent console messages, errors and requests, no listener needed
    for m in page.console_messages():
        print(f"console.{m.type}: {m.text}")
    for e in page.page_errors():
        print(f"page error: {e.message}")
    print(f"requests so far: {len(page.requests())}")
    assert len(page.page_errors()) == 1

What happens

The page kept the console messages and the error without any listener set up before. Earlier versions only offered page.on('console') and page.on('pageerror'), which miss anything that happened before the listener was added. The same three methods exist in every language: consoleMessages, pageErrors and requests. In Java a page error comes back as its message text.

🏢
Use pageErrors() at the end of a test to fail it when the page threw an error that the user never saw. It is a cheap check that catches broken scripts early.

🤖Playwright Test Agents

Since 1.56, Playwright ships three agent definitions: instructions plus Playwright tools that an AI coding assistant follows to write and maintain tests. You bring the assistant, such as Claude Code, VS Code with Copilot, Codex or OpenCode. Playwright provides the agents.

AgentReadsWrites
planneryour running app, starting from the seed testa Markdown plan in specs/
generatora plan from specs/test files in tests/, with each locator and check tried live
healera failing testa fixed test, or a skipped one when it believes the app itself is broken

🔌Playwright MCP: a browser for AI assistants

MCP, the Model Context Protocol, is a standard way to give an AI assistant tools. The Playwright MCP server gives it a real browser: open a page, read its accessibility snapshot, click, type and take screenshots. The assistant can then write a test in whatever language your project uses.

Playwright MCP for any assistant and any language · 📄 A configuration file, shown here
📄 .mcp.json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}
What happens

This is the configuration from the Playwright MCP README. Claude Code can also add it with claude mcp add playwright npx @playwright/mcp@latest. Since 1.62 the same server also ships inside Playwright as npx playwright mcp. The server works on the accessibility tree of the page, not on pixels, so the assistant sees roles and names, the same things good locators use.

Playwright MCPany assistant that speaks MCP, exploring an app and writing tests in any language

Part 5

🧐Using AI-written tests safely

An assistant can write a test in seconds, but the team still owns it. Review AI-written tests with the same rules as tests written by people.

CheckWhy
the test uses the framework: page objects, fixtures, test dataotherwise every generated test adds locators that someone must maintain
every check is meaningfula test that only checks that a heading is visible passes even when the feature is broken
no fixed waits and no force: truethey hide timing problems that real users meet
the healer did not hide a bugit may skip a test when the app looks broken. A skipped test needs a person to decide
the test fails when the feature breaksbreak the feature on purpose once, or change an expected value, and watch it go red
secrets stay out of prompts and plansplans and prompts are files and messages that other people and tools can read
🏢
Give the agents a seed test that signs in through your own fixtures. Generated tests then start from the same state as the rest of your suite.
