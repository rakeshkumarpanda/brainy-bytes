Part 1

✅Web-first assertions retry

🧒 Beginner friendly

An assertion checks that the page is the way it should be. Playwright assertions are web-first: they know the page is still changing, so they keep checking until the condition is true or the timeout ends. The default timeout is 5 seconds.

A web-first check against a plain read · ✅ mvn test ran
📄 src/test/java/com/brainy/RetryTest.java
package com.brainy;

import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Test;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
public class RetryTest {
  @Test
  void aWebFirstCheckWaitsAPlainReadDoesNot(Page page) {
    page.navigate("/widgets");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Load offers")).click();
    Locator offer = page.getByTestId("offer");      // shows up 1.2 s after the click

    System.out.println("isVisible() right now: " + offer.isVisible());   // a snapshot, no waiting
    assertThat(offer).isVisible();                                       // retries until it shows
    System.out.println("isVisible() after the check: " + offer.isVisible());
  }
}

What happens

Right after the click the offer is not there yet, so isVisible() says false. It reads the page once and returns. expect(...).toBeVisible() kept checking until the offer appeared. A test written as expect(await offer.isVisible()).toBe(true) would have failed here for no good reason.

⚠️
A rule that catches many flaky tests: never put await inside expect. Write assertThat(locator).isVisible(), not assertTrue(locator.isVisible())expect(locator).to_be_visible(), not assert locator.is_visible()await expect(locator).toBeVisible(), not expect(await locator.isVisible()).toBe(true)await expect(locator).toBeVisible(), not expect(await locator.isVisible()).toBe(true).

📚The assertions you will use every day

🧒 Beginner friendly

There is one assertion for each thing a user can notice. In JavaScript and TypeScript they start with to, in Python with to_, and in Java with is or has after assertThat.

Fifteen checks on the sign in page · ✅ mvn test ran
📄 src/test/java/com/brainy/ManyChecksTest.java
package com.brainy;

import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Test;
import java.util.regex.Pattern;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
public class ManyChecksTest {
  @Test
  void oneCheckForEachThingAUserCanNotice(Page page) {
    page.navigate("/login");
    assertThat(page).hasTitle("Sign in · Brainy Shop");
    assertThat(page).hasURL(Pattern.compile("/login$"));

    Locator email = page.getByLabel("Email");
    assertThat(email).isEmpty();
    assertThat(email).isEditable();
    assertThat(email).hasAttribute("type", "email");
    assertThat(email).hasRole(AriaRole.TEXTBOX);
    email.fill("asha@shop.example");
    assertThat(email).hasValue("asha@shop.example");
    assertThat(email).isFocused();

    assertThat(page.getByRole(AriaRole.CHECKBOX, new Page.GetByRoleOptions().setName("Remember me"))).not().isChecked();
    assertThat(page.getByRole(AriaRole.ALERT)).isHidden();
    Locator signIn = page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Sign in"));
    assertThat(signIn).isEnabled();
    assertThat(signIn).hasCSS("background-color", "rgb(22, 163, 74)");
    assertThat(signIn).isInViewport();
    assertThat(page.getByRole(AriaRole.FORM)).hasAccessibleName("Sign in");
    System.out.println("all 15 checks passed");
  }
}

What happens

Each check reads one thing a user or a screen reader can notice: the title, the address, an empty box, its type, a ticked box, a hidden error, the colour of a button. The colour comes back in the rgb form the browser computes, even though the style sheet says #16a34a.

Part 3

🔤Checking text and lists

🧒 Beginner friendly

Text checks are the most common checks of all. Both kinds ignore extra spaces and line breaks, so the layout of the HTML does not matter.

toHaveText and toContainText for one element and for lists · ✅ mvn test ran
📄 src/test/java/com/brainy/TextTest.java
package com.brainy;

import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.assertions.LocatorAssertions;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Test;
import java.util.regex.Pattern;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
public class TextTest {
  @Test
  void textChecksForOneElementAndForAList(Page page) {
    page.navigate("/products");
    Locator names = page.getByRole(AriaRole.LISTITEM).getByRole(AriaRole.HEADING);

    // A list: every element, in this order.
    assertThat(names).hasText(new String[] {"Coffee mug", "Desk lamp", "Gel pen", "Notebook", "Water bottle"});
    // A list: some elements contain these texts, in this order.
    assertThat(names).containsText(new String[] {"mug", "pen"});

    assertThat(page.getByRole(AriaRole.HEADING, new Page.GetByRoleOptions().setLevel(1)))
        .hasText("products", new LocatorAssertions.HasTextOptions().setIgnoreCase(true));
    assertThat(page.getByTestId("product-3")).containsText("₹1,299");
    assertThat(page.getByTestId("product-3")).hasText(Pattern.compile("Desk lamp.*Home"));

    page.getByRole(AriaRole.COMBOBOX, new Page.GetByRoleOptions().setName("Sort by")).selectOption("low");
    assertThat(names).hasText(new String[] {"Gel pen", "Notebook", "Coffee mug", "Water bottle", "Desk lamp"});
    System.out.println("sorted: " + names.allTextContents());
  }
}

What happens

With a list, toHaveText wants exactly these elements in exactly this order, which makes it a good check for sorting. toContainText with a list is looser: some elements, in this order, each containing a part of the text. A regular expression gives full control, and ignoreCase relaxes the case.

🙅Checking that something is not there

Put not in front of any assertion: assertThat(x).not().isVisible()expect(x).not_to_be_visible()expect(x).not.toBeVisible()expect(x).not.toBeVisible(). Negative checks retry too, so they wait for a spinner or an error message to go away.

Checks that something is gone · ✅ mvn test ran

package com.brainy;

import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Test;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
public class NegativeTest {
  @Test
  void negativeChecksWaitToo(Page page) {
    page.navigate("/products");
    assertThat(page.getByText("Loading products…")).not().isVisible();   // waits until it goes away
    assertThat(page.getByText("No products match your search")).hasCount(0);

    page.getByPlaceholder("Search products").fill("phone");
    assertThat(page.getByRole(AriaRole.LISTITEM)).hasText("No products match your search");
    assertThat(page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Add to cart"))).hasCount(0);
    assertThat(page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Add to cart"))).not().isAttached();
    System.out.println("nothing to buy when searching for phone");
  }
}

Part 6

🧽Soft assertions

A normal assertion stops the test at the first failure. A soft assertion records the failure and lets the test carry on, so one run tells you about every problem on the page. The test still fails at the end.

What happens

Two of the three checks are wrong on purpose. With soft checks the test still ran to the end, and the report lists both problems instead of only the first. Java has no soft assertions in Playwright, so the Java version uses assertAll from JUnit 5, which gives the same result.

🏢
Soft checks are handy for a page with many independent fields, such as an invoice or a profile. Do not use them for steps the rest of the test depends on, such as signing in.
Part 7

🔢Plain values, polling and blocks

Not everything is on the screen. For values you already hold, such as API data, use the normal checks of your language. They do not wait, because the value cannot change.

Plain checks on data you already have · ✅ mvn test ran

package com.brainy;

import com.google.gson.Gson;

import org.junit.jupiter.api.Test;
import java.util.ArrayList;
import java.util.List;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;
import static org.junit.jupiter.api.Assertions.*;

public class ValueTest {
  @Test
  void plainValueChecksForDataYouAlreadyHave(Page page) {
    APIResponse response = page.request().get("/api/products?delay=0");
    assertThat(response).isOK();                    // a Playwright check for API answers
    JsonArray products = new Gson().fromJson(response.text(), JsonArray.class);   // Gson comes with Playwright

    assertEquals(5, products.size());               // plain JUnit checks
    List<String> names = new ArrayList<>();
    for (JsonElement p : products) names.add(p.getAsJsonObject().get("name").getAsString());
    assertTrue(names.contains("Desk lamp"));
    assertEquals("Gel pen", products.get(0).getAsJsonObject().get("name").getAsString());
    assertTrue(products.get(2).getAsJsonObject().get("price").getAsInt() > 1000);
    int cheapest = Integer.MAX_VALUE;
    for (JsonElement p : products) cheapest = Math.min(cheapest, p.getAsJsonObject().get("price").getAsInt());
    System.out.println("cheapest: " + cheapest);
  }
}

What happens

The products came from the API, so they are plain data in your language and there is nothing to wait for. Each language uses its usual checks: expect(value) in Playwright Test, assert in Python and JUnit assertions in Java. Only the response check is a Playwright assertion.

Playwright Test also has ways to retry your own code.

expect.poll, toPass and expect.configure · ✅ Playwright Test ran
📄 tests/poll.spec.js
import { test, expect } from '@playwright/test';

test('expect.poll and toPass retry your own code', async ({ page }) => {
  await page.goto('/products');
  // Poll any value until it matches: here a count read with a plain call.
  await expect.poll(() => page.locator('li.card').count(), { timeout: 5000 }).toBe(5);

  // Retry a whole block until every check inside it passes.
  let tries = 0;
  await expect(async () => {
    tries++;
    const response = await page.request.get('/api/products?delay=0');
    expect(response.status()).toBe(200);
    expect(tries).toBeGreaterThanOrEqual(3);     // the first two tries fail on purpose
  }).toPass({ intervals: [100, 200, 500] });
  console.log('the block passed on try', tries);

  const slowExpect = expect.configure({ timeout: 10_000 });   // a copy of expect with other defaults
  await slowExpect(page.getByRole('heading', { level: 1 })).toHaveText('Products');
});

What happens

These three are part of Playwright Test, so they exist in JavaScript and TypeScript only. expect.poll keeps calling your function until the value matches, and toPass retries a whole block. In Python and Java, reach for a locator assertion or wait_for_function / waitForFunction instead.
