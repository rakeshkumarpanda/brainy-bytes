Part 1

🚦What CI does for your tests

🧒 Beginner friendly

Continuous integration, CI for short, means a server runs your tests every time someone pushes code or opens a pull request. Nobody has to remember to run them, and a change that breaks the shop is caught before it is merged. Continuous delivery, the CD, goes on to deploy the change when the checks are green.

On your laptopOn CI
the machineyours, with everything already installeda fresh machine for every run
the browserinstalled onceinstalled in every run, or already in a Docker image
the settingsa local .env filevariables and secrets in the CI settings
a failureyou watch it happenyou read the report, the logs and the trace afterwards
test.onlyhandy while debuggingmust fail the run
💡
The Playwright documentation sums CI up in three steps: make sure the machine can run browsers, install the packages and browsers, then run the tests. Everything in this chapter is a version of those three steps.
Part 2

🤖Running the suite the way the pipeline does

Most CI services set the environment variable CI=true. GitHub Actions and GitLab do it on every job. Jenkins and Azure Pipelines do not, so their pipeline files set it. The config reads it and changes a few settings:

Setting on CIWhy
forbidOnly: truea forgotten test.only stops the run instead of skipping the rest
retries: 2a test that fails once and then passes is reported as flaky, not hidden
a fixed number of workersCI machines are smaller than laptops. The Playwright docs suggest 1 for the most stable runs, or sharding for speed
JUnit XML and HTML reportersthe CI server reads the XML, and people read the HTML
trace: on-first-retryevery retried test leaves a trace to open later

What happens

The same seven tests passed, this time with the settings a pipeline uses. CI=true is what GitHub Actions and GitLab set on every job, and the config reads it: two workers, two retries, forbidOnly, and a JUnit XML file next to the HTML report. pytest wrote its JUnit file with --junitxml and spread the tests over two processes with -n 2 from pytest-xdist. Surefire writes its XML files for every run. Every CI server can read JUnit XML, which is why all four runs leave one behind.

A forgotten test.only fails the pipeline · 💥 ran for real, fails on purpose
📄 tests/products/sort.spec.ts
import { test, expect } from '../../src/fixtures/index';

test.describe('product sort', () => {
  test.only('the cheapest product comes first', async ({ productsPage }) => {   // left behind after debugging
    await productsPage.open();
    await expect(productsPage.cards.first()).toContainText('Gel pen');
  });
});

What happens

On a laptop, test.only would quietly run one test and report success. With CI=true the config turns on forbidOnly, and the whole run stops before any test starts. Without it, a pull request could pass CI having run one test out of seven.

🏢
pytest and TestNG have no test.only, so there is nothing to forbid. In pytest the closest mistake is leaving -k or a single file in the CI command, so keep the command in the workflow file and review changes to it.

What happens

These are the real workflow files of the four framework projects. GitHub runs them on every push to main and on every pull request. The steps are always the same five: get the code, install the language, install the packages, install the browser with its system libraries, run the tests, and keep the results even when tests fail.

LineWhat it does
on: push / pull_requestwhen the workflow runs
runs-on: ubuntu-latesta fresh Linux machine from GitHub
timeout-minutes: 30stops a job that hangs. Keep it above any global timeout in the test config
actions/checkoutgets the code of the commit
setup-node, setup-python, setup-javainstalls the language version
npm ci, pip install -r, mvninstalls the exact package versions from the lock or requirements file
playwright install --with-deps chromiumdownloads Chromium and installs the Linux libraries it needs
env: with secrets. and vars.hands settings and passwords to the tests
if: ${{ !cancelled() }}uploads the results even when tests failed, which is when you need them most
upload-artifactkeeps the report as a download on the run page
TriggerUse it for
push to mainchecking what was merged
pull_requestchecking a change before it is merged
schedule with crona nightly run of the full suite, for example in every browser
workflow_dispatcha Run workflow button for runs by hand
deployment_statustesting a preview or staging deployment once it is ready
🏢
In the repository settings, a branch rule can make this workflow a required check. Then a pull request cannot be merged while its tests are red.
Part 4

🔐Secrets and settings per environment

A pipeline needs the same settings as your laptop: the address of the app and the test passwords. They come from the CI settings, never from the code.

KindIn GitHubIn the workflowSeen in logs
a setting such as BASE_URLSettings, Secrets and variables, Actions, Variables${{ vars.BASE_URL }}yes
a passwordthe same page, Secrets${{ secrets.ASHA_PASSWORD }}no, GitHub masks it as ***

The framework reads both from the environment, with a local default. Here is what happens when the secret is wrong:

  public static final User RAVI = new User("ravi@shop.example", secret("RAVI_PASSWORD", "admin123"), "Ravi");

  private Users() {}

  private static String secret(String name, String fallback) {
    String value = System.getenv(name);
    return value == null || value.isEmpty() ? fallback : value;

What happens

The password came from the environment variable, so the framework signed in with the wrong one and the greeting never appeared. The wrong password test still passed, because it sets its own password. This is exactly what a team sees when a secret is missing or out of date in the CI settings: the sign in tests fail and everything else is fine. The fix is in the CI settings, not in the code.

⚠️
Secrets are not given to workflows that run for pull requests from forks, so a fork cannot read your passwords. Tests that need them are skipped or fail there, which is expected.
Part 5

🧩Shards with a matrix, and one merged report

A matrix starts the same job several times with different values. Give each copy a different shard and the suite runs on several machines at once. For Playwright Test, each shard saves a blob report, and a last job merges them into one HTML report.

Each matrix job runs its own part of the suite · ✅ ran for real

What happens

The loop does here, one after another, what the matrix does on GitHub at the same time on separate machines. Playwright Test split the seven tests into four and three, each shard saved a blob report, and merge-reports joined them into one result for the whole run. pytest-split split the tests into two groups. Maven has no shard option, so the Java matrix runs one test package per job with -Dtest, which also overrides the suite file.

Playwright TestpytestMaven with TestNG
split the suite--shard=1/2--splits 2 --group 1 (pytest-split)one package or suite per job
balanceby test count, with fullyParallelby stored durations with --store-durationsby hand
one reportblob reports, then merge-reportsone JUnit file per jobone Surefire folder per job
💡
fail-fast: false keeps the other shards running when one fails, so you see every failure in one run. The merge job uses if: !cancelled() for the same reason.

The smoke tests passed inside the official images, which already hold Chromium, Firefox, WebKit and every system library they need.
