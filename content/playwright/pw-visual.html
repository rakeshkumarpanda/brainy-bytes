Part 1

🖼️Visual comparisons

A test can click every button and still miss that the buttons turned red. A visual comparison takes a screenshot and compares it, pixel by pixel, with a picture saved earlier, called the baseline. Playwright Test has this built in as toHaveScreenshot.

What happens

The first command saved two pictures, products-chromium-linux.png and lamp-card-chromium-linux.png, next to the test file. The second run compared the page with them. The two tests that changed nothing passed. The third test made the buttons red, the way a bad style change would, and failed with the number of pixels that differ. Playwright saved the expected picture, the actual picture and a diff for the report.

OptionWhat it does
--update-snapshotssaves new baselines instead of comparing, after a change you meant to make
maxDiffPixels, maxDiffPixelRatiohow many pixels, or what share of them, may differ
thresholdhow different one pixel may be before it counts, from 0 to 1, default 0.2
mask: [locator]covers parts that change every run, such as a date or an advert, with a box
animations: "disabled"stops CSS animations so the picture is the same every time (the default)
stylePathadds a style sheet only while taking the picture, for example to hide a clock
🏢
Baselines depend on the operating system and the browser, which is why the file name ends in chromium-linux. Make them on the same system that runs the tests, usually the CI image or the Playwright Docker image, and commit them to the repository.
⚠️
toHaveScreenshot is part of Playwright Test. Python and Java have page.screenshot() to save a picture, but no comparison built in. Teams add a library for it or use a visual testing service. The aria snapshot below works in every language.
Part 2

🌳Aria snapshots

🧒 Beginner friendly

An aria snapshot describes a part of the page the way assistive technology sees it: each element's role, its name and its state, nested in YAML. Compare it with a saved version and you check the structure, not the pixels, so a new font or colour does not break it.

Check the structure of the page with an aria snapshot · ✅ mvn test ran
📄 src/test/java/com/brainy/StructureTest.java
package com.brainy;

import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Test;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
public class StructureTest {
  @Test
  void theMainMenuHasFourLinks(Page page) {
    page.navigate("/products");
    assertThat(page.getByRole(AriaRole.NAVIGATION, new Page.GetByRoleOptions().setName("Main"))).matchesAriaSnapshot("""
        - navigation "Main":
          - link "Products"
          - link "Feedback"
          - link "Widgets"
          - link "Orders"
        """);
  }

  @Test
  void theNotebookCardSaysItIsOutOfStock(Page page) {
    page.navigate("/products");
    System.out.println(page.getByTestId("product-4").ariaSnapshot());   // print it once, then paste it below
    assertThat(page.getByTestId("product-4")).matchesAriaSnapshot("""
        - listitem:
          - heading "Notebook" [level=3]
          - text: Stationery ₹60
          - button "Out of stock" [disabled]
        """);
  }
}

What happens

Both checks passed in every language. An aria snapshot is the page as a screen reader sees it: roles, names and states, written as YAML. The printed snapshot of the notebook card is the one pasted into the check, which is how most snapshots are written. Leaving out a part, such as the /url of each link, still matches, so a check only states what matters.

Part 3

♿Accessibility scans with axe

Many people use a screen reader, a keyboard only or high contrast. axe is an open source engine from Deque that checks a page against rules from WCAG, the web accessibility guidelines. Playwright runs it inside the page and gives you the list of problems.

Scan a page for accessibility problems with axe · 💥 mvn test ran, fails on purpose
📄 src/test/java/com/brainy/OffersAccessibilityTest.java
package com.brainy;

import com.deque.html.axecore.playwright.AxeBuilder;
import com.deque.html.axecore.results.AxeResults;
import com.deque.html.axecore.results.Rule;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import org.junit.jupiter.api.Test;

import java.util.List;

import static org.junit.jupiter.api.Assertions.assertEquals;

@UsePlaywright(ShopOptions.class)
public class OffersAccessibilityTest {
  @Test
  void theOffersPageHasNoAccessibilityProblems(Page page) {
    page.navigate("/a11y");
    AxeResults results = new AxeBuilder(page)
        .withTags(List.of("wcag2a", "wcag2aa"))      // the WCAG 2 A and AA rules
        .analyze();
    for (Rule v : results.getViolations()) {
      System.out.println(v.getId() + " (" + v.getImpact() + "): " + v.getNodes().size() + " element(s). " + v.getHelp());
    }
    assertEquals(List.of(), results.getViolations().stream().map(Rule::getId).toList());
  }
}

The scan failed on purpose, because the offers page was built with common mistakes. axe found the same two rule breaks in every language and listed each with how serious it is, how many elements break it and a one line help text. The JavaScript and Java libraries come from Deque, the makers of axe. The Python one, axe-playwright-python, is a community package with its own copy of axe, so its rule versions can lag a little behind.

Part 4

⏰Fake time with page.clock

Some pages change with the date or after a delay: a sale that starts at midnight, a session that ends after 5 minutes, a countdown. Waiting for the real time is slow or impossible. page.clock replaces the page's Date and timers with a fake clock that you control.

import com.microsoft.playwright.Page;

  @Test
  void theSaleIsNotLiveTheDayBefore(Page page) {

What happens

All three tests passed in well under a second each. setFixedTime made the page think it was 24 or 25 December 2026, so both sides of the sale date were tested without waiting for Christmas. install replaced the page timers, and runFor ran five minutes of them at once, so the idle sign out happened straight away.

MethodWhat it does
setFixedTime(time)Date.now() always returns this time. Timers still run normally.
install({ time })replaces Date and every timer. Call it before the page loads.
runFor("05:00")moves forward, firing every timer that falls due on the way
fastForward("05:00")jumps forward and fires due timers at most once, like a laptop waking from sleep
pauseAt(time), resume()stops time at a moment to check the page, then lets it run again
setSystemTime(time)changes the date without firing timers, like a user changing the system clock
💡
Use setFixedTime when the page only reads the date, and install with runFor when it uses setTimeout or setInterval. Either way the test runs in milliseconds and gives the same result on every day of the year.
