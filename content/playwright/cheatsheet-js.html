What Playwright is and how it works

Open chapter

What Playwright is and the jobs teams use it for, the official languages, a fact based comparison with Selenium and Cypress, a first script in four languages, how one call travels through the client library, the driver and the browser protocol with real DEBUG=pw:api, pw:channel and pw:protocol logs, a first test with JUnit, pytest and Playwright Test, a recorded sign in walk, and what a test runner does for every test.

Key ideas

  • You write steps Open, type, click, check.
  • Messages Each call becomes a small message. The driver is the same for every language.
  • Real browsers Real clicks and real typing. The page cannot tell it apart from a person.
  • It waits Visible, stable, enabled. No fixed sleeps, so far fewer flaky tests.
  • Remember Playwright drives real browsers through one driver, waits for elements before it acts, and works the same way in Java, Python, JavaScript and TypeScript.

Tips and traps

  • Common mistake
    People often ask for Playwright in C, C++ or Go. There is no official Playwright for C or C++. For Go there is a community project, playwright-go, which is not made by the Playwright team. This subject sticks to the official languages so that every example is supported and up to date.Lesson: What Playwright is
  • In real teams
    In many companies you will join a project that already uses Selenium. Knowing both is useful. Many teams move to Playwright one test suite at a time, because the ideas are close: find an element, act on it, check the result.Lesson: Why teams pick Playwright
  • Remember
    The driver is the same Node.js program for every language. This is why a new feature arrives in Java, Python, JavaScript and C# in the same release.Lesson: How one line travels to the browser
  • Remember
    The test asks for { page }. Playwright Test sees the name, makes a fresh context and page for this test and closes them afterwards. The baseURL in playwright.config makes /login mean http://localhost:4173/login.Lesson: From a script to a test

Browsers, contexts, pages and devices

Open chapter

Key ideas

  • Browser Start once, about 0.5 s. Shared by many tests.
  • Context A fresh, empty profile. Its own cookies, storage and permissions.
  • Page One tab. Tabs in a context share the login.
  • Emulation Size, locale, time zone, location. Set on the context, nothing on your computer changes.
  • Remember Start one browser, give every test a new context, and set what the site should see, such as a phone or a German user, with context options.

A persistent profile that survives a restart
main.mjs
import { chromium } from 'playwright';
import { mkdtempSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const profile = mkdtempSync(join(tmpdir(), 'shop-profile-'));

// First visit: a real profile folder on disk, like a person's Chrome profile.
let context = await chromium.launchPersistentContext(profile);
let page = context.pages()[0];
await page.goto('http://localhost:4173/');
await page.evaluate(() => localStorage.setItem('theme', 'dark'));
await context.close();

// Second visit with the same folder: the data is still there.
context = await chromium.launchPersistentContext(profile);
page = context.pages()[0];
await page.goto('http://localhost:4173/');
console.log('theme =', await page.evaluate(() => localStorage.getItem('theme')));
await context.close();

import { test, expect } from '@playwright/test';

test('moving around the shop', async ({ page }) => {
  await page.goto('/login', { waitUntil: 'domcontentloaded' });
  console.log('1.', page.url());

  await page.getByLabel('Email').fill('asha@shop.example');

  await page.goForward();
  await page.reload();
  await expect(page).toHaveURL(/\/products$/);
  console.log('4.', page.url(), '|', await page.title());

export class ShopApi {
  constructor(request) {
    this.request = request;
  }

  async signIn(user) {
    const response = await this.request.post('/api/login', { data: { email: user.email, password: user.password } });
    if (!response.ok()) throw new Error(`Sign in failed for ${user.email}: ${response.status()}`);
    return (await response.json()).token;
  }

  async addToCart(token, productId, qty = 1) {
    const response = await this.request.post('/api/cart', {
      data: { productId, qty },
      headers: { Authorization: `Bearer ${token}` },
    });
    if (!response.ok()) throw new Error(`Could not add product ${productId}: ${response.status()}`);
  }
}

// One line per test, then a short summary that a team could also send to chat or a dashboard
export default class SummaryReporter {
  passed = 0;
  failed = [];

  onBegin(config, suite) {
    console.log(`Starting ${suite.allTests().length} tests on ${config.workers} workers`);
  }

  onTestEnd(test, result) {
    const seconds = (result.duration / 1000).toFixed(1);
    if (result.status === 'passed') {
      this.passed++;
      console.log(`PASS  ${test.title} (${seconds} s)`);
    } else {
      this.failed.push(test.title);
      console.log(`FAIL  ${test.title} (${seconds} s)`);
    }
  }

  onEnd(result) {
    console.log(`${this.passed} passed, ${this.failed.length} failed, run ${result.status}`);
    for (const title of this.failed) console.log(`  to look at: ${title}`);
  }
}

New in 1.56: read console messages, errors and requests at any time
tests/collect.spec.js
import { test, expect } from '@playwright/test';

test('reads console messages and page errors after the fact', async ({ page }) => {
  await page.goto('/widgets');
  await page.getByRole('button', { name: 'Write to the console' }).click();
  await Promise.all([
    page.waitForEvent('pageerror'),
    page.getByRole('button', { name: 'Break the page' }).click(),
  ]);

  // New in 1.56: the page keeps its recent console messages, errors and requests, no listener needed
  for (const m of await page.consoleMessages()) console.log(`console.${m.type()}: ${m.text()}`);
  for (const e of await page.pageErrors()) console.log(`page error: ${e.message}`);
  console.log(`requests so far: ${(await page.requests()).length}`);
  expect(await page.pageErrors()).toHaveLength(1);
});
Run it: npx playwright test

Tips and traps

  • In real teams
    Read the release notes before updating, and update on a branch so CI shows what changed. Each release lists its breaking changes, such as page.accessibility removed in 1.57 and Node.js 16 support removed in 1.54.Lesson: How Playwright changes, and how to keep up
  • In real teams
    Use pageErrors() at the end of a test to fail it when the page threw an error that the user never saw. It is a cheap check that catches broken scripts early.Lesson: A new feature in all four languages
  • Common mistake
    The agents write Playwright Test code in TypeScript or JavaScript.Lesson: Playwright Test Agents
  • In real teams
    Give the agents a seed test that signs in through your own fixtures. Generated tests then start from the same state as the rest of your suite.Lesson: Using AI-written tests safely
