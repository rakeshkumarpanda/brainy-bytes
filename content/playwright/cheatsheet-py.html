What Playwright is and how it works

Open chapter

What Playwright is and the jobs teams use it for, the official languages, a fact based comparison with Selenium and Cypress, a first script in four languages, how one call travels through the client library, the driver and the browser protocol with real DEBUG=pw:api, pw:channel and pw:protocol logs, a first test with JUnit, pytest and Playwright Test, a recorded sign in walk, and what a test runner does for every test.

Key ideas

  • You write steps Open, type, click, check. In Java, Python, JavaScript or TypeScript.
  • Messages Each call becomes a small message. The driver is the same for every language.
  • Real browsers Real clicks and real typing. The page cannot tell it apart from a person.
  • It waits Visible, stable, enabled. No fixed sleeps, so far fewer flaky tests.
  • Remember Playwright drives real browsers through one driver, waits for elements before it acts, and works the same way in Java, Python, JavaScript and TypeScript.

Tips and traps

  • Common mistake
    People often ask for Playwright in C, C++ or Go. There is no official Playwright for C or C++. For Go there is a community project, playwright-go, which is not made by the Playwright team. This subject sticks to the official languages so that every example is supported and up to date.Lesson: What Playwright is
  • In real teams
    In many companies you will join a project that already uses Selenium. Knowing both is useful. Many teams move to Playwright one test suite at a time, because the ideas are close: find an element, act on it, check the result.Lesson: Why teams pick Playwright
  • Remember
    The driver is the same Node.js program for every language. This is why a new feature arrives in Java, Python, JavaScript and C# in the same release.Lesson: How one line travels to the browser
  • Remember
    The test asks for a page argument. pytest-playwright sees the name and gives the test a fresh page. The --base-url option in pytest.ini makes /login mean http://localhost:4173/login.Lesson: From a script to a test

Tips and traps

  • Common mistake
    Keep one Playwright version per project and update on purpose. Each Playwright release expects its own browser builds. After you update the package, run the install command again, or the tests stop with an error that says the browser executable does not exist.Lesson: Install Playwright in your language
  • In real teams

    Turn on format on save and a linter in your editor from day one.Lesson: Your editor

Key ideas

  • Browser Start once, about 0.5 s. Shared by many tests.
  • Context A fresh, empty profile. Its own cookies, storage and permissions.
  • Page One tab. Tabs in a context share the login.
  • Emulation Size, locale, time zone, location. Set on the context, nothing on your computer changes.
  • Remember Start one browser, give every test a new context, and set what the site should see, such as a phone or a German user, with context options.

import tempfile
from playwright.sync_api import sync_playwright

profile = tempfile.mkdtemp(prefix="shop-profile-")

with sync_playwright() as p:
    # First visit: a real profile folder on disk, like a person's Chrome profile.
    context = p.chromium.launch_persistent_context(profile)
    page = context.pages[0]
    page.goto("http://localhost:4173/")
    page.evaluate("localStorage.setItem('theme', 'dark')")

    page = context.pages[0]

    print("theme =", page.evaluate("localStorage.getItem('theme')"))

Tips and traps

  • In real teams
    Real projects use two contexts in one test for features with two people: a chat between a customer and a support agent, an admin approving an order while the customer waits, or two players in a game. Each person gets their own context.Lesson: Contexts keep tests apart
  • Common mistake
    Emulation catches most layout and touch bugs and costs nothing. Some bugs only show on real hardware, such as a keyboard covering a field or a slow phone. Many teams run emulated phones on every commit and real devices in a cloud service before a release.Lesson: Phones and tablets
  • Remember
    WebKit on Windows and Linux is the engine of Safari, not Safari itself. It catches most Safari bugs. For the last few percent, teams run a small smoke suite on real Safari on a Mac.Lesson: Chromium, Firefox and WebKit
  • Remember
    Close what you open. In a test runner the fixtures close contexts and pages for you. In a script, close the browser at the end, or use try with resources in Java and a with block in Python, so a crash does not leave browser processes running on the machine.Lesson: Profiles, closing and remote browsers

import re
from playwright.sync_api import Page, expect


def test_moving_around_the_shop(page: Page):
    page.goto("/login", wait_until="domcontentloaded")
    print("1.", page.url)

    page.get_by_label("Email").fill("asha@shop.example")
    page.get_by_label("Password").fill("s3cret")
    page.get_by_role("button", name="Sign in").click()
    page.wait_for_url("**/products")              # the app moves on by itself
    print("2.", page.url)

    print("3.", page.url)

    page.go_forward()
    page.reload()
    expect(page).to_have_url(re.compile(r"/products$"))
    print("4.", page.url, "|", page.title())

Open chapter

The same framework built and run in TypeScript, JavaScript, Python and Java: the runner finds the tests, the full suite passes, the smoke set runs alone, and every file is shown with why it is there.

from playwright.sync_api import APIRequestContext

from framework.data.users import User


# Fast set up through the API, so UI tests only click what they are testing
class ShopApi:
    def __init__(self, request: APIRequestContext):
        self.request = request

    def sign_in(self, user: User) -> str:
        response = self.request.post("/api/login", data={"email": user.email, "password": user.password})
        assert response.ok, f"Sign in failed for {user.email}: {response.status}"
        return response.json()["token"]

    def add_to_cart(self, token: str, product_id: int, qty: int = 1):
        response = self.request.post("/api/cart", data={"productId": product_id, "qty": qty},
                                     headers={"Authorization": f"Bearer {token}"})
        assert response.ok, f"Could not add product {product_id}: {response.status}"

import pytest

results = []


# pytest reports each test three times: setup, call and teardown. The call holds the result,
# and a failure while setting up is reported in the setup instead.
def pytest_runtest_logreport(report):
    if report.when == "call" or (report.when == "setup" and not report.passed):
        results.append(report)


def pytest_terminal_summary(terminalreporter):
    tr = terminalreporter
    tr.section("shop summary")
    for r in results:
        name = r.nodeid.split("::")[-1]
        tr.write_line(f"{'PASS' if r.passed else 'FAIL'}  {name} ({r.duration:.1f} s)")
    failed = [r.nodeid.split("::")[-1] for r in results if r.failed]
    tr.write_line(f"{len(results) - len(failed)} passed, {len(failed)} failed")
    for name in failed:
        tr.write_line(f"  to look at: {name}")
