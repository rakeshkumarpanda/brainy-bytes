Part 1

🏃One library, a runner per language

🧒 Beginner friendly

Playwright itself drives the browser. A test runner finds your tests, runs them, and reports the results. Each language uses the runner its developers already know.

LanguageTest runnerHow Playwright plugs in
JavaScript, TypeScriptPlaywright Test (@playwright/test)built in: fixtures, config, projects, retries, sharding, reporters, UI mode
Pythonpytestthe pytest-playwright plugin gives page, context and browser fixtures and CLI options
JavaJUnit 5 or TestNGJUnit 5: @UsePlaywright injects Page and friends (since 1.42). TestNG: you create them in hooks
C#NUnit, MSTest or xUnitbase classes such as PageTest give you Page
💡
Playwright Test was built by the Playwright team, so it has the most features out of the box. pytest, JUnit and TestNG need a plugin or a little code for the same things, which the next chapters show side by side.
Part 2

🗂️Grouping, tags and annotations

🧒 Beginner friendly

A real suite has hundreds of tests. Groups keep related tests together, tags let you run a slice such as the smoke tests, and annotations say why a test is skipped or expected to fail.

Group, tag, skip and mark known failures · ✅ mvn test ran
📄 src/test/java/com/brainy/ProductsPageTest.java
package com.brainy;

import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Tag;
import org.junit.jupiter.api.Test;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
@DisplayName("Products page")
public class ProductsPageTest {
  @Test
  @Tag("smoke")
  @DisplayName("shows five products")
  void showsFiveProducts(Page page) {
    page.navigate("/products");
    assertThat(page.getByRole(AriaRole.LISTITEM)).hasCount(5);
  }

  @Test
  @Tag("regression")
  @DisplayName("sorts by price")
  void sortsByPrice(Page page) {
    page.navigate("/products");
    page.getByLabel("Sort by").selectOption("low");
    assertThat(page.getByRole(AriaRole.LISTITEM).first()).containsText("Gel pen");
  }

  @Test
  @Disabled("the wish list is not built yet")
  void addsAProductToTheWishList(Page page) {
  }

  // JUnit has no "expected to fail". Teams disable the test and name the ticket: SHOP-42.
}

What happens

Four tests, one result each: two passed, one skipped, and one failed as expected. The test that is known to fail keeps the run green: Playwright Test shows its cross but counts it as passed, and pytest calls it xfailed. The day phones arrive it turns red, which reminds the team to remove the mark. JUnit has no such mark, so the Java class skips that case.

⚠️
A test.only left in the code silently skips every other test. Set forbidOnly in the CI config so such a run fails instead.

What happens

The same file, but only the smoke test ran. Playwright Test matches the tag in the title and tag list with --grep, pytest selects markers with -m, and Maven Surefire passes JUnit tags with -Dgroups. All three accept expressions, such as --grep-invert @slow, -m "smoke and not slow" or -Dgroups="smoke & !slow".

Part 4

🔁Parameterised tests

🧒 Beginner friendly

When the same steps should run with different data, write the steps once and feed them rows of data. Each row becomes its own test in the report.

One test, many rows of data · ✅ mvn test ran
📄 src/test/java/com/brainy/SearchTest.java
package com.brainy;

import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@UsePlaywright(ShopOptions.class)
public class SearchTest {
  @ParameterizedTest(name = "search for \"{0}\" finds {1}")
  @CsvSource({
      "mug, 1, Coffee mug",
      "o, 3, Coffee mug",
      "pen, 1, Gel pen",
      "BOTTLE, 1, Water bottle",
  })
  void search(String term, int count, String first, Page page) {   // the data first, then Page
    page.navigate("/products");
    page.getByPlaceholder("Search products").fill(term);
    Locator cards = page.getByRole(AriaRole.LISTITEM);
    assertThat(cards).hasCount(count);
    assertThat(cards.first()).containsText(first);
  }
}

Part 5

⚙️Configuration in one place

Settings that are the same for every test belong in one place, not in each test: the base URL, the browser, timeouts, retries, what to record on failure, and the devices to test.

Configuration that every test receives · ✅ mvn test ran
📄 src/test/java/com/brainy/ShopOptions.java
package com.brainy;

import com.microsoft.playwright.Browser;
import com.microsoft.playwright.junit.Options;
import com.microsoft.playwright.junit.OptionsFactory;

// Shared settings for every test class that says @UsePlaywright(ShopOptions.class)
public class ShopOptions implements OptionsFactory {
  @Override
  public Options getOptions() {
    return new Options()
        .setHeadless(true)
        .setBrowserName("chromium")
        .setBaseUrl("http://localhost:4173")
        .setContextOptions(new Browser.NewContextOptions()
            .setLocale("en-IN")
            .setTimezoneId("Asia/Kolkata"));
  }
}

What happens

One test ran as a desktop browser and as a phone, and both got the language and time zone from the configuration, not from the test. Chromium reports the time zone Asia/Kolkata by its older name Asia/Calcutta, which is the same zone. In Playwright Test, projects run the same tests with different settings. pytest-playwright takes the device from the command line, and Java uses one options class per setup.
