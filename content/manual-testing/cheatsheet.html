1.1

Software Testing Fundamentals

Open chapter

A bank asks a software company for an application. Developers write the code, test engineers check it against the requirement, and bugs travel back and forth until the product is stable. This page explains that loop and every word you need to talk about it.

Key ideas

  • What software is and who builds it Software is a business need of a customer, turned into a working program. A bank such as ICICI wants its customers to log in, check a balance, transfer money and apply for a loan. The bank is not a software company, so it hands this need to one.
  • What testing means There are three common definitions, and a good answer in an interview mentions all three:
  • Manual testing Manual testing is the process of testing an application as per the client requirement, done by a test engineer by hand, without any tool running the steps.
  • Automation testing Automation testing is testing an application with the help of a tool. A tester writes or records a test script once, and the tool runs it again and again.
  • Programming and scripting languages
  • White box, black box and gray box Testing is grouped by how much of the inside the tester can see.
  • The seven principles of testing These seven principles (as taught by ISTQB) explain why testers work the way they do.
  • Why a late bug costs more A mistake in the requirement that is found during a requirement review costs a short conversation. The same mistake found after release means changing the design, the code, the tests and the documents, then shipping again.
  • Who does what in a software company A tester's career usually grows from test engineer to senior test engineer, test lead and test manager, or towards automation engineer and SDET (software development engineer in test).
  • QA, QC and testing: three different jobs People often use these words as if they mean the same thing. They do not, and interviewers love to ask about the difference.
  • Test oracles and the tester mindset To call something a bug, a tester must know what the right result is. Whatever tells you the right result is called a test oracle . The requirement is the main one, but it is never complete, so good testers use several:

SDLC and its Models

Open chapter

Building software is like building a house: collect the need, check it is possible, design, build, test, hand over and maintain. The order is fixed, but how you walk through it is not. Each walk is called a model, and choosing the right one decides cost, speed and quality.

Key ideas

  • What SDLC is: build it like a house SDLC (Software Development Life Cycle) is the step by step procedure used to develop software. The notes compare it with building a house, because the steps line up almost exactly:
  • Service based and product based companies
  • The seven phases, one by one The HLD splits the application into modules . For Gmail: login, compose, inbox, sent items, outbox and logout. The LLD describes the objects inside each module. For the login page: the username box, the password box, the OK button and the Cancel button.
  • CRS, SRS and what makes a good requirement
  • The waterfall model The waterfall model is the basic model from which all the others grew. The phases run strictly one after another , and the output of one phase is the input of the next, like water falling down steps. It never flows back up.
  • The spiral model Waterfall's problem: an Excel like product with four modules (A: cells, B: operations, C: merging cells, D: macros), six months each, reaches the customer only after two years .
  • The prototype model The notes tell of a girl abroad who sees a photo of the boy before agreeing to meet him. The photo is a prototype : a sample that looks about 90% like the real thing.
  • The V and V model (V model) The V model pairs every document on the left with a level of testing on the right. While the left side is being written, testers review each document (verification) and prepare the test document for the matching level.
  • Agile and Scrum Agile is used in most companies today. The idea: build software quickly in small pieces, with the customer involved all the time . The notes show why.
  • Hybrid models and choosing a model A hybrid model combines two models to get the strengths of both. The usual pairs are spiral plus prototype (each module gets a prototype approved before it is built, module by module) and prototype plus V (a prototype is approved, then the V model's reviews ...
  • Kanban, scaled Agile and DevOps Scrum is not the only Agile way of working. Three more names appear in almost every job description today.
  • Where testing happens in each model Every model tests, but at different moments and in different amounts. Knowing this helps a tester plan, and it is a common interview question.

White Box Testing

Open chapter

Before a build ever reaches a tester, the developer checks the code line by line. White box testing looks inside: every path a call can take, every condition, every loop, the memory the code wastes and the time it takes. This page shows how it is done and why it matters to testers too.

Key ideas

  • What white box testing is White box testing (also called glass box, structural or unit testing) is testing the code itself, line by line, before the program is handed to the testers. It is done by developers, because they can see and understand the code.
  • Unit test programs A unit test program (UTP) is a small program that calls each function with chosen inputs and checks the result. When every UTP passes, the developer is confident the code is right and hands it over.
  • Path testing Path testing checks that every path through the code is executed at least once , so that each main function calls the right sub functions in the right order. Developers count the paths with respect to the code .
  • Condition testing Condition testing checks every condition for both its true and its false outcome. For a login: if the username and password are valid, show the home page, else show an error. One test with valid data and one with invalid data cover both outcomes.
  • Loop testing Loop testing checks that each loop runs exactly the number of times it should , and that it stops. The notes show three cases: a loop that runs fully, a loop left early with break , and a loop that must not run at all.
  • Statement and branch coverage Coverage measures how much of the code the tests actually ran:
  • Memory testing Memory testing checks that the code does not waste memory. The notes give an example: a game for an old Nokia phone had to fit in a tiny amount of memory, so every unused line had to go.
  • Response time testing Response time testing at code level finds the slow functions . A profiler such as Rational Quantify runs the code and shows which functions take the most time, drawn as thick lines in its call graph.
  • White box versus black box
  • Stronger coverage: MC/DC and mutation testing Statement and branch coverage show that code ran. Two stronger ideas check whether the tests would really notice a mistake.

Functional, Integration and System Testing

Open chapter

A tester first checks each field and button on its own, then the data that flows between modules, then the whole journey from login to logout. Around those three levels sit quick smoke checks, random ad hoc checks and the customer's own acceptance test. This page walks through all of them with the amount transfer and Gmail examples from the notes.

Key ideas

  • Black box testing and the amount transfer example A black box tester never looks at the code. Everything starts from the requirement, and every object on the screen is tested against it. The notes use an amount transfer page:
  • Functional testing Functional testing (also called component testing) checks each component of a module, or each module, individually and independently.
  • Integration testing Integration testing checks the data flow, or interface, between two or more modules. After user A transfers 5,000 to user B, A's balance must drop by 5,000 and B's must grow by 5,000.
  • Types of integration testing, stubs and drivers When a module is missing during incremental testing, a stand in is used. A stub is a dummy called module (top down: the top module calls a lower module that is not built yet).
  • System testing System testing checks the end to end flow of the whole application : every module a real user would pass through, from logging in to logging out.
  • Smoke testing Imagine a new build arrives and the testers start deep testing module by module. On day five they reach compose and find it completely broken: a blocker .
  • Ad hoc and exploratory testing Real users never read the manual. Ad hoc testing (also called monkey testing) uses the application randomly , the way an unpredictable user would, usually at the end once the planned testing is done. The notes show what it finds on the amount transfer page:
  • User acceptance testing, alpha and beta UAT is testing done by the customer before accepting the product , to make sure it suits their real business. Buying shoes is the same: you check for damage, try them on, and walk a few steps before paying.

3.2

Non-functional Testing

Open chapter

An application can do everything the requirement asks and still fail its users: it breaks on their browser, confuses them, or slows to a crawl when a thousand people log in at once. Non-functional testing measures how well the product works, once it already works.

Key ideas

  • What non-functional testing covers Functional testing asks whether each feature does what the requirement says. Non-functional testing asks how well the product does it: on which platforms, how easily, and how fast under real load.
  • Compatibility testing Compatibility testing checks the application on different software and hardware platforms, because real users do not all have the same machine.
  • Virtual machines and the compatibility process The notes compare three ways to get many platforms. Giving each tester one OS means nobody can check another. Installing several OS on each machine means restarting all day.
  • Usability testing Usability is user friendliness: important features are easy to reach, the language is easy to understand, the look and feel is consistent, navigation takes few steps, and the effort to learn is small.
  • Performance testing Performance testing checks how the application behaves when load is applied. Three factors matter:
  • Bottlenecks and tuning If the average response time is 6.3 seconds against a target of 5, there is a bottleneck . Performance bugs are not reproduced like functional bugs. They are analysed and tuned:
  • Load, stress, scalability, volume and soak At 1,000 users the system is now 2.5 seconds slower than before the stress. It did not recover, so the team looks for a memory leak.
  • The quality model: ISO/IEC 25010:2023 "Non functional" is a big bag. The international standard ISO/IEC 25010 sorts product quality into named characteristics, and its 2023 edition updated the list. Teams use it as a checklist so that no kind of quality is forgotten in the test plan.
  • Reliability, recovery and installation testing Users forgive a slow day. They do not forgive lost money or lost data. These tests check that the product keeps working, and comes back safely when something breaks.

Security, Accessibility, Localization and Mobile Testing

Open chapter

A login page can work perfectly and still let a stranger read your bank statement. A shop can sell well and still lock out a blind customer. This page covers the checks that protect people: security, accessibility, other languages and countries, mobile phones, and privacy.

Key ideas

  • Security testing: what it protects Security testing checks that the application protects its data and its users from people who want to misuse it. A functional tester asks "does it work for the right user?" A security tester also asks "what happens when the wrong user tries?"
  • The OWASP Top 10 (2025) for testers OWASP, the Open Worldwide Application Security Project, publishes a list of the ten most serious risks for web applications, based on data from thousands of real applications. The newest edition is the OWASP Top 10:2025 .
  • Accessibility: software for everyone Accessibility testing checks that people with disabilities can use the product. That includes people who are blind or have low vision, are deaf, cannot use a mouse, have tremors, dyslexia or memory problems.
  • How to test accessibility by hand Automated tools such as axe, Lighthouse and WAVE are a good first step, but they catch only part of the problems. They can see that an image has no alt text. They cannot tell that the alt text "image123" is useless. A manual pass is always needed.

  • Mobile app testing A phone is not a small computer. It moves between networks, runs on a battery, gets calls in the middle of a task, and comes in thousands of models. Mobile testing adds these questions to normal functional testing.
  • Privacy and data protection testing Laws now give people rights over their personal data, and products must prove they respect them. Testers check these rights like any other requirement.
