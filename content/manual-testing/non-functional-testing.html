Non-functional Testing

An application can do everything the requirement asks and still fail its users: it breaks on their browser, confuses them, or slows to a crawl when a thousand people log in at once. Non-functional testing measures how well the product works, once it already works.

Part 1

⚡What non-functional testing covers

Functional testing asks whether each feature does what the requirement says. Non-functional testing asks how well the product does it: on which platforms, how easily, and how fast under real load.

Non-functional testing starts once the product is functionally stable. Measuring the speed of a feature that still gives wrong answers wastes everyone's time.
Part 2

🖥️Compatibility testing

Compatibility testing checks the application on different software and hardware platforms, because real users do not all have the same machine.

Software

Operating systems (Windows, macOS, Linux, Android, iOS) and browsers (Chrome, Edge, Firefox, Safari, Opera), each in several versions.

Hardware

Different sizes and makes of RAM, hard disk, processor and graphics card, and on phones, screen sizes.

Testing every combination is impossible, so teams pick the most widely used platforms. Most compatibility bugs are visual. Pick a platform in the widget to see the typical problems.

Part 3

🧰Virtual machines and the compatibility process

The notes compare three ways to get many platforms. Giving each tester one OS means nobody can check another. Installing several OS on each machine means restarting all day. The practical answer is virtual machines: one powerful server hosts many operating systems, and testers connect to them over remote desktop.

  1. The customer gives functional and non-functional requirements, including the platforms to support.
  2. The team picks a base platform (the most used one) and does functional testing on it.
  3. Once stable, the end to end flows are run on every other platform through virtual machines.
  4. Compatibility issues go to developers, are fixed and retested.
Forward compatibilityBackward compatibility
Works on newer versions: Windows 10 to Windows 11, Chrome 120 to Chrome 130Works on older versions: Windows 11 to Windows 10, Android 14 to Android 11
Not every application needs it. An internal tool where all 1,000 employees use the same company laptop and browser can skip compatibility testing. A public site like a social network cannot.
Part 4

🙂Usability testing

Usability is user friendliness: important features are easy to reach, the language is easy to understand, the look and feel is consistent, navigation takes few steps, and the effort to learn is small.

Usability is judged against a checklist so that it does not depend on one person's taste:

  • Every page has Home, Logout and Help links
  • A breadcrumb shows where you are: Home >> Sales >> Market
  • Images have alternative text and buttons have a description on hover
  • Error messages say what to do, not just what went wrong
  • Fonts, colours and button positions are the same on every page

The process: identify the users' needs, derive the checklist, get it approved by the customer, run it on every page, and report the result.

Part 5

🚀Performance testing

Performance testing checks how the application behaves when load is applied. Three factors matter:

FactorMeaningExample target
Response timeTime the server takes to respond to a requestUnder 5 seconds
LoadNumber of users at the same time1,000 users
StabilityUsers working continuously over a period24 hours

A thousand testers clicking at once is costly and inaccurate, so tools such as LoadRunner, JMeter, Gatling or k6 simulate virtual users.

The average hides slow requests. Teams also report the 90th percentile: the time within which 90% of requests finished.
Part 6

🧪Bottlenecks and tuning

If the average response time is 6.3 seconds against a target of 5, there is a bottleneck. Performance bugs are not reproduced like functional bugs. They are analysed and tuned:

Where a bottleneck can beTypical tuning
CodeA slow loop or too many database calls
DatabaseA missing index, a heavy query
Server softwareThread pool or connection pool limits on the web or application server
HardwareToo little RAM or CPU
NetworkLow bandwidth, too many round trips
Part 7

📈Load, stress, scalability, volume and soak

TypeWhat is applied
Load testingLoad up to the desired level (1,000 users with a 5 second goal)
Stress testingLoad beyond the desired level, to see how and where it breaks
Scalability testingLoad increased or decreased step by step to find the limit
Stability testingThe desired load held for a long time
Volume testingA huge volume of data, such as millions of rows
Soak (endurance) testingLoad for a very long time on a minimal set up, to find leaks that appear only after hours

Little's law links the numbers: users = throughput × (response time + think time). With 1,000 users, a 5 second response and 15 seconds of think time, the server must handle 100020 = 50 requests per second.
