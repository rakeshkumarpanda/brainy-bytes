Test Case Design and Documents

A tester who keeps everything in their head forgets values, wastes time and tests differently every release. Test documents fix all three. This lesson builds them step by step: scenarios, test cases with real values chosen by proven techniques, review, traceability and the final report.

Part 1

📚Why test documents, and how they are made

😟 Without test documents

Testers forget values, every new tester starts from zero, and two testers test the same feature in two different ways.

🙂 With test documents

Nothing is forgotten, a new tester can start at once, and testing is consistent from release to release.

Test documents are written by testers before test execution, while developers are writing the business logic, so that they are ready when the first build arrives.

Part 2

🗺️Test scenarios

A test scenario is a high level, one or two line statement of something to test. Each one has a do part and a check part, and scenarios are written module by module. They help a tester understand the flow without worrying yet about exact values.

#DoCheck
1Enter a valid username and password and click OKThe home page is displayed
2Enter an invalid username or passwordAn error message is displayed
3Leave both fields blank and click OKAn error message is displayed
4Enter values and click CancelBoth fields are reset
5Log in with valid detailsThe username appears on the home page
6Compose a mail and send itA confirmation message is displayed
7Compose and send a mailIt is in the receiver's inbox and the sender's sent items
8Compose a mail and save it as a draftA confirmation message is displayed and the mail is in drafts
Product based companies usually write scenarios first. Service based companies often go straight to test cases.
Part 3

📋The test case template

A test case is a detailed document with the step by step procedure, the inputs and the expected result for every scenario. Each company has its own template, usually an Excel sheet supplied by the test lead. It has three parts:

PartFields
HeaderTest case name, type (FT, IT, ST), requirement number, module, status, severity, pre condition, test data, release, version, brief description
BodyStep number, description, inputs, expected result, actual result, status (pass if expected equals actual), comments
FooterAuthor, date, reviewed by, approved by

Severity of a test case

How important it is: critical, major or minor. If there is time for only 150 of 200 cases, severity decides which ones run.

Pre condition and test data

A pre condition is the minimum set up needed before running (for example, a valid login). Test data is the specific data used (for example, user Dinga, password Dingi).

A test case name follows a pattern such as Release_Version_Project_Module_Type, for example Cheeta_2.0_ICICI_AT_FT. Status is filled in only during execution: pass when every step behaves as expected, fail when some step does not, and partial when the main steps work and only minor ones fail.

The same test case run on three builds:

BuildStep resultsStatus
B001Pass, pass, pass, passPass
B002Pass, pass, pass, fail (a minor step)Partial
B003Pass, pass, fail (a main step), passFail
Part 4

🎯Error guessing, equivalence partitioning and boundary values

The hardest part of writing test cases is maximum test coverage with a small number of values. Three techniques from the notes:

TechniqueIdeaFor an amount from 5,000 to 50,000
Error guessing (EG)Guess values from experience: blank, decimals, letters, copy and paste6,000 ✓, 51,000 ✗, blank ✗, 12.50 ✗, "Ten" ✗
Equivalence partitioning (EP)Split inputs into classes that behave the same and test one value from eachOne valid (6,000) and two invalid (4,000 and 61,000)
Boundary value analysis (BVA)Bugs hide at the edges, so test each boundary and its neighbours4,999 ✗, 5,000 ✓, 5,001 ✓, 49,999 ✓, 50,000 ✓, 50,001 ✗

For a range [a, b], BVA tests a − 1, a, a + 1, b − 1, b, b + 1: four valid and two invalid values. EP has three forms:

Input typeEP ruleExample
RangeOne valid, two invalid (below and above)Amount 5,000 to 60,000: 6,000 ✓, 4,000 ✗, 61,000 ✗
SetOne valid, two invalidProduct id in {1 … 5}: 1 ✓, 0 ✗, 6 ✗
BooleanTrue and falseA true or false question: select each option once
Rules of thumb from the notes: for maximum coverage always add error guessing to any technique. Use BVA plus EG for ranges, EP plus EG for sets and booleans, and plain EG for simple fields such as "exactly 3 digits".

When the range has criteria: the general practice method

A loan of 1 to 7 lakh has different interest rates: 1 to 2 lakh at 5.68%, above 2 to 5 lakh at 3.29%, above 5 to 7 lakh at 1.99%. Testing only 1 lakh and 7 lakh misses the inner edges. Apply BVA to every band's boundary, then add EG.

The values a tester writes down for the loan field:

BandValues to testExpected result
Below the range99,999Loan amount should be 1 to 7 lakh
1 to 2 lakh1,00,000, 1,00,001, 1,99,999, 2,00,0005.68% interest
Above 2 to 5 lakh2,00,001, 2,00,002, 4,99,999, 5,00,0003.29% interest
Above 5 to 7 lakh5,00,001, 5,00,002, 6,99,999, 7,00,0001.99% interest
Above the range7,00,001Loan amount should be 1 to 7 lakh

That is 14 boundary values. Error guessing adds a blank field, the amount typed in words and decimals.

Part 5

🧮Decision tables, state transitions and pairwise testing

Three more techniques complete a tester's toolbox:

TechniqueUse it whenExample
Decision tableThe outcome depends on a combination of conditionsValid user? Valid password? Account locked? Each combination is one rule with one expected action
State transitionThe system moves between states and only some moves are allowedAn account: active, then locked after 3 wrong passwords, then active again after reset. A bug life cycle is another example
Pairwise (all pairs)Many parameters with many values make every combination impossibleOS × browser × language: cover every pair of values instead of every triple

Three yes or no conditions give 8 rules. Rules with the same action merge, so 5 test cases are enough (a dash means the condition does not matter):

Valid userValid passwordAccount lockedExpected result
Y-YAccount locked
YYNHome page
-NNInvalid username or password
NY-Invalid username or password
NNYInvalid username or password

Part 7

🔎Test case review

After every tester finishes writing, test cases are reviewed by another tester, for two reasons: accuracy (maximum coverage) and proper flow, so anyone can reuse them.

StepSeverityReview commentAuthor's response
HeaderCriticalPre condition missingNot fixed, with a reason: none is needed
5CriticalPositive values missing for FANFixed
9MajorNeed more positive valuesFixed
14MinorNeed more negative valuesFixed
22MinorSentence not clearFixed
Review ethics: aim for maximum coverage, point out mistakes rather than writing the solutions, review the content and not the author, and remember that both are responsible. If a scenario was never written and the reviewer missed it, both share the blame. If it was written but skipped while testing, the author is responsible.
Part 8

🧭The repository and the RTM

Approved test cases go into the test case repository, a central place created by the test lead. Once stored they are baselined: written, reviewed and approved, and not changed casually. Smoke test cases are not written separately. They are picked from the existing functional, integration and system cases.

The requirement traceability matrix (RTM) maps every requirement to its test cases. Without it, requirement 3 can slip through with no test case at all, and the customer finds the bug.

WhenWho
After test cases are reviewed and stored, before execution starts. Not while writing (incomplete) and not during review (cases may be rejected)Every tester for their own modules. The lead consolidates them for the release

A small RTM for ten requirements:

RequirementTest cases

R2TC03
R3No test case
R4TC04, TC05, TC06
R5TC07
R6TC08

R8TC11
R9TC12
R10TC13, TC14

Nine of ten requirements (90%) are covered. Test cases must be written for R3 before execution starts.

Drawback of the RTM: it only ensures that every requirement has at least one test case. It does not guarantee that all the test cases a requirement needs are there.

Good test cases

Advantages

They record the tester's knowledge, reach maximum coverage, keep testing consistent, save time for new testers, make testing process oriented instead of person oriented, and become the base for automation scripts.

Characteristics

Detailed with a proper flow, simple language, minimum steps with maximum coverage, and able to catch the maximum number of bugs.

Typical interview numbers from the notes: about 3 to 4 test cases written a day and 2 to 3 executed, depending on complexity, and roughly 90 to 120 test cases for a two to three month project.
Part 11

🎭Use case testing and checklist based testing

A use case describes how an actor (a user or another system) reaches a goal, step by step. It has a main flow where everything goes well, alternative flows where the user takes another valid path, and exception flows where something goes wrong. Use case testing writes at least one test for each flow.

FlowSteps of "Withdraw cash at an ATM"Test idea
MainInsert card, enter PIN, choose amount, take cash, take cardWithdraw ₹2,000 with enough balance
AlternativeChoose "other amount" instead of a quick amountWithdraw ₹1,500 using other amount
AlternativeAsk for a receiptReceipt shows the right amount and balance
ExceptionWrong PIN three timesCard is blocked with a clear message
ExceptionAmount above the balance"Insufficient balance", no cash, no debit
ExceptionCash not taken within 30 secondsCash is taken back and the account is not debited

Checklist based testing

Experienced testers keep checklists: short lists of things to verify, built from past bugs, standards and experience. A checklist does not give exact steps, so each tester applies it a little differently, which adds variety.

📝 Form checklist

Required fields marked, tab order, max length, paste, leading spaces, error next to the field, data kept after an error, double submit.

🔁 Every release checklist

Login and logout, password reset, main journeys, emails and SMS, mobile view, browser back button, session timeout.

Part 12

✨Writing test cases that others can run

A test case is written once and run many times, often by someone else. These habits make it useful for years.

MistakeExampleBetter
Vague stepEnter details and submitEnter amount 5,000 and account 1234567890, then click Transfer
Vague expected resultIt should workMessage "Transfer successful" and balance reduced by 5,000
Many checks in one caseTest login, transfer and logoutOne goal per case, so a failure points to one thing
Hidden dependencyUses the account created in case 12Preconditions list the data the case needs
Only happy pathsValid amounts onlyAdd boundaries, invalid classes and error recovery
Copied UI text that changesClick the blue buttonClick Transfer (the button name, not its look)

🎯 One clear goal

The title says what is checked: "Transfer is refused when the amount exceeds the daily limit".

🧱 Independent

Each case can run alone, in any order.

🔗 Traceable

Each case points to its requirement id, so the RTM stays honest.

♻️ Maintainable

Common steps such as login live in one place, and cases refer to them.

Read your own case as if you joined the team today. If you would need to ask a question to run it, the answer belongs in the case.
