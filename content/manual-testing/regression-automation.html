Regression, Retesting and Automation

Every change to the code can break something that used to work. Regression testing re-runs old test cases to prove it did not. This lesson shows how to pick which old cases to run, why that work moves to automation from the second release on, and how to tell the many look alike terms apart.

Part 1

🔁What regression testing is

Each new release adds features, removes some, or modifies others. All three mean the code changes, and any code change can break something that already worked.

Regression testing is re-executing old test cases across releases (or builds) to make sure that changes have not affected existing functionality. The old test cases that are picked again are regression test cases. They are taken from the repository, not written again.
ChallengeWhy
Finding the impact areaA change in one module can affect modules that look unrelated
TimeThe number of test cases grows every release, while the team often does not
AccuracyRunning the same cases again and again is monotonous, and attention drops
Part 2

🎚️Unit, regional and full regression

TypeWhat is testedWhen
Unit regressionOnly the changed featureA small, isolated change. Login changes from 3 letters to 3 digits, so only login cases are run
Regional regressionThe changes plus the impact area found by impact analysisThe usual case. A change in Compose is checked together with Inbox and Sent items
Full regressionThe changes plus every old featureMost of the product changed, or the application is life or machine critical. A release after three years with 70% of the code rewritten

Pick a changed module in the widget and compare how many test cases each type runs.

If an interviewer asks which regression you do, the usual answer is regional regression, with the impact area found by impact analysis.

No single person sees every impact, so three groups each send a report:

WhoKnowledge they bring
CustomerBusiness knowledge: which business flows use the changed feature
DevelopersCoding knowledge: which code calls the changed code
TestersProduct knowledge: which screens and flows the user sees together
Part 4

↩️Retesting versus regression

Regression happens at two levels. Across releases because of new or changed features, and across builds because of bug fixes: B001 has bugs, the developer changes the code to fix them, and on B002 the tester checks the fixes and the areas around them.

↩️ Retesting

Checking that a reported bug is really fixed. Only the failed test case is run again, similar to unit regression.

🔁 Regression

Checking the fix and the impact area, because the fix changed code that other features use.

Retesting answers "is this bug gone?". Regression answers "did the fix break anything else?". Both are done on every new build.
Part 5

🤖Why regression moves to automation

Regression is the most repetitive work in testing, which makes it the best candidate for automation. A tool runs the same steps in seconds, does not get bored, and can run every night.

Tool typeExamplesLicence
Functional testingSelenium, UFT (formerly QTP), WinRunner, SilkTest, Playwright, CypressSelenium, Playwright and Cypress are open source, UFT is licensed
Performance testingLoadRunner, JMeter, NeoLoad, WebLOAD, Gatling, k6JMeter, Gatling and k6 are open source, LoadRunner is licensed

From the notes: testing login by hand takes about an hour each time. Writing the script takes two hours once, then each run takes a minute. Move the slider to see when automation pays off.

Automate when there are multiple releases, many regression cycles or repetitive tasks. That normally starts from the second release, once there are stable old features to protect.
Part 6

⚙️The automation life cycle

  1. Release 1 is tested manually: 350 test cases, 4 testers, about 4 months.
  2. In release 2, the manual team writes and runs test cases for the new features, while the automation team turns the 150 regression cases into scripts.
  3. Three things are needed to write a script: the test case, a stable application and the tool.
  4. The scripts run on every new build. A failed script is checked manually first. If it is a real bug it is reported, and the script is run again after the fix.
  5. The cycle repeats until every automated regression case passes.
Part 7

🚧What cannot be automated

ReasonExamples
The feature is unstableNew features, or features that are still changing. A script written today breaks tomorrow
No technology supportCaptcha, a virtual keyboard, a one time password sent to a phone
Too complex or too humanFlows with many manual decisions, usability and look and feel, ad hoc testing
Automation does not replace testers. Someone still writes the test cases, reviews failures, and does the exploratory and usability testing that needs human judgement.
