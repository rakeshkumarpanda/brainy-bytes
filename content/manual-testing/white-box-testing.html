White Box Testing

Before a build ever reaches a tester, the developer checks the code line by line. White box testing looks inside: every path a call can take, every condition, every loop, the memory the code wastes and the time it takes. This page shows how it is done and why it matters to testers too.

Part 1

🔬What white box testing is

White box testing (also called glass box, structural or unit testing) is testing the code itself, line by line, before the program is handed to the testers. It is done by developers, because they can see and understand the code.

A program is made of variables (int a, float total) and functions (add(), sub(), mul()). A developer writes the code, tests it, and later fixes the bugs testers report. A classic white box bug: the calculator's plus key calls the wrong function, so 1 + 2 shows −1.

Checking every function by hand is slow, inaccurate and tedious. A real program has thousands of lines and is changed every day. So developers write code to test their code.
Part 2

🧾Unit test programs

A unit test program (UTP) is a small program that calls each function with chosen inputs and checks the result. When every UTP passes, the developer is confident the code is right and hands it over.

LanguageCommon unit testing tool
JavaJUnit, TestNG
.NET (C#)NUnit, xUnit, MSTest
Pythonpytest, unittest
JavaScriptJest, Mocha
  • When a test fails, the bug is fixed in the main program, never by changing the UTP to match the wrong answer.
  • When the requirement changes, the UTP must change too.
  • A UTP is reviewed by another person, because a wrong test passes wrong code.
  • The code goes to testers only when all UTPs pass.

⏱️ Time saving

Hundreds of checks run in seconds after every change.

🎯 Accuracy and reuse

The same checks run the same way every time, on every build.

Part 3

🛤️Path testing

Path testing checks that every path through the code is executed at least once, so that each main function calls the right sub functions in the right order. Developers count the paths with respect to the code. Testers think the same way about the application: every way a user can move through the screens.

Cyclomatic complexity

For a function's control flow graph, the number of independent paths is given by McCabe's formula:

M = E − N + 2P

where E is the number of edges, N the number of nodes and P the number of connected parts (1 for a single function). A simpler rule for one function: M = number of decisions + 1. A function with two if statements has M = 3, so at least 3 test cases are needed to cover its independent paths.

Part 4

🔀Condition testing

Condition testing checks every condition for both its true and its false outcome. For a login: if the username and password are valid, show the home page, else show an error. One test with valid data and one with invalid data cover both outcomes.

🔁Loop testing

Loop testing checks that each loop runs exactly the number of times it should, and that it stops. The notes show three cases: a loop that runs fully, a loop left early with break, and a loop that must not run at all. For a loop meant to run up to n times, test these counts:

IterationsWhy
0 (skip the loop)Empty input must not crash
1 and 2The first and second passes often hide set up mistakes
A typical value mThe normal case
n − 1, n and n + 1The edges, where off by one bugs live
Part 6

📊Statement and branch coverage

Coverage measures how much of the code the tests actually ran:

Statement coverage = statements executedtotal statements × 100% Branch coverage = branches takentotal branches × 100%

100% statement coverage does not guarantee 100% branch coverage. An if without an else can have every line run while its false side is never tested. Tools measure coverage automatically: JaCoCo for Java, coverage.py for Python and Istanbul (built into Jest) for JavaScript.

High coverage is a good sign, not a proof. Code can be fully covered by tests that check the wrong expected values.
Part 7

🧠Memory testing

Memory testing checks that the code does not waste memory. The notes give an example: a game for an old Nokia phone had to fit in a tiny amount of memory, so every unused line had to go. Developers use tools such as Rational Purify (for C and C++) to scan the code and report unused variables, unused functions and memory leaks with their line numbers.

Part 8

⏱️Response time testing

Response time testing at code level finds the slow functions. A profiler such as Rational Quantify runs the code and shows which functions take the most time, drawn as thick lines in its call graph. Today profilers are built into IDEs and languages (cProfile in Python, the Chrome DevTools profiler, Java Flight Recorder).

The notes give a neat example. 100 users log in and 99 of them type valid details. If the code checks for the invalid case first, almost every user pays for a useless check. Checking the common case first makes the code faster without changing what it does.

Typical questions: What is white box testing? What are its types? What is a unit test program and who writes it? Why do we need both white box and black box testing? The short answer to the last one: developers prove the code does what they wrote, testers prove it does what the customer asked.
