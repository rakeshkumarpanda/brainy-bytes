Software Testing Fundamentals

A bank asks a software company for an application. Developers write the code, test engineers check it against the requirement, and bugs travel back and forth until the product is stable. This page explains that loop and every word you need to talk about it.

Part 1

🏦What software is and who builds it

Software is a business need of a customer, turned into a working program. A bank such as ICICI wants its customers to log in, check a balance, transfer money and apply for a loan. The bank is not a software company, so it hands this need to one. The bank becomes the client or customer of that company.

The need is broken into modules, each a separate area of the application:

ModuleWhat the customer asked for
LoginUsername of 5 alphabets, password of 5 alphabets, an OK and a Cancel button
Account balanceShow the current balance of the logged in user
Amount transferMove money from one account to another
LoanApply for a loan and track it
LogoutEnd the session safely

Developers write the code in programming languages such as C, C++, C#, Java or .NET. Test engineers (TEs) then use the application exactly as a user would and check every behaviour against the requirement. When something does not match, the TE reports a bug, the developer fixes it, and the TE tests it again. The loop repeats until the application is stable: bug free and working as per the requirement.

Testing never stops at "it works for me". The question is always: does it behave exactly as the customer's requirement says?
Part 2

🔍What testing means

There are three common definitions, and a good answer in an interview mentions all three:

  1. Testing is checking the functionality of an application as per the customer requirement.
  2. Testing is checking an application with the intention of finding bugs.
  3. Testing is validating the software against the requirement document.

Before a test engineer can start, four things must be in hand:

📄 The requirement

The document (SRS) that says what each module must do.

🔗 The test URL

The address of the application installed on the test server.

🧩 Assigned modules

Which modules this TE owns, given by the test lead.

🗄️ DB schema

The table structure, so data shown on screen can be cross checked in the database.

Notice how one small requirement, "username of 5 alphabets", already needs many test values: exactly 5 letters, 4 letters, 6 letters, digits, a space, a blank field, copy and paste. Thinking of these values is the core skill of a tester.
Part 3

🙋Manual testing

Manual testing is the process of testing an application as per the client requirement, done by a test engineer by hand, without any tool running the steps. The TE reads the requirement, opens the application, enters values, clicks buttons and compares what happens with what should happen.

  • Manual testing is always done first. A feature has to be understood and stable before anyone can automate it.
  • The requirement must be clearly understood. A tester who misreads the requirement will pass wrong behaviour or report correct behaviour as a bug.
  • The result depends on the person: their understanding, attention and product knowledge.

👍 Where people do better

Judging look and feel, usability, new and changing features, exploring without a script, and catching things nobody wrote down.

👎 Where people struggle

Repeating the same 400 checks every release. It is slow, boring, and attention drops, so mistakes creep in.

Part 4

🤖Automation testing

Automation testing is testing an application with the help of a tool. A tester writes or records a test script once, and the tool runs it again and again. Automation is chosen when the work is repetitive, which is why it usually starts from the second release, when old features must be checked again.

Record and playback

The notes tell a story. King Raja loves Queen Rani's singing, but she cannot sing for him all day. So her song is recorded, and the recording plays whenever he wants. The recording is a "virtual Rani". A tool such as QTP works the same way: the tester performs the steps once while the tool records them, and the recording becomes a test script that plays back on every build.

⏱️ Time saving

A script that took 2 hours to create runs in about a minute every time after that.

🎯 Accuracy

A tool does not get bored on the 300th repetition, so it never skips a step.

♻️ Reuse

The same script runs on every build and every release.

😴 No monotony

People are freed from repeating the same checks and can test new features.

Part 7

📜The seven principles of testing

These seven principles (as taught by ISTQB) explain why testers work the way they do.

PrincipleWhat it means in practice
1. Testing shows the presence of defectsTesting can prove that bugs exist. It can never prove that none are left.
2. Exhaustive testing is impossibleEvery possible input is far too many to try, so we choose values smartly (boundary values, equivalence classes).
3. Early testing saves time and moneyReviewing the requirement finds mistakes before any code is written.
4. Defects cluster togetherA small number of modules usually contains most of the bugs.
5. The pesticide paradoxRunning the same tests forever stops finding new bugs. Tests must be reviewed and extended.
6. Testing is context dependentA banking app, a game and a heart monitor are tested very differently.
7. Absence of errors is a fallacyA bug free app that does not meet the user's need is still a failure.

A single 10 digit account number field already has 10¹⁰ = 10,000,000,000 possible values. Two such fields together have 10²⁰ combinations. That is why the rest of this course teaches you to pick a handful of values that represent all the others.

Part 8

💸Why a late bug costs more

A mistake in the requirement that is found during a requirement review costs a short conversation. The same mistake found after release means changing the design, the code, the tests and the documents, then shipping again. A widely quoted rule of thumb says the cost grows roughly like this:

Phase where the bug is foundRelative cost to fix
Requirement1×
Design5×
Coding10×
Testing20×
After release100×
This is the idea behind "shift left": involve testers from the very first phase, review every document, and catch defects where they are cheapest.

👥Who does what in a software company

RoleMain job
Business analyst (BA)Collects the requirement from the customer and writes it down (service based companies)
Product analyst (PA)Studies the market and decides what the product needs (product based companies)
ArchitectDesigns the high level structure: the modules and how they connect
Development managerPlans the low level design and leads the developers
DeveloperWrites the code and tests it with white box testing
Test engineerWrites test documents, executes tests, reports and retests bugs
Test lead and test managerPlan the testing, assign modules, review work, report quality
Build and release teamTurn the code into a build and install it on the servers
CustomerGives the requirement and finally accepts the product (UAT)

A tester's career usually grows from test engineer to senior test engineer, test lead and test manager, or towards automation engineer and SDET (software development engineer in test).
