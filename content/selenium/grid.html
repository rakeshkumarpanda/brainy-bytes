Lesson 1 of 3

When and why to use a Grid

So far every test started a browser on the same machine. Selenium Grid lets the same tests run on other machines, called nodes, many at the same time. The documentation names two reasons to use it: run tests in parallel against different browsers, versions and operating systems, and cut the time a suite takes.

Suite time on a GridExam favourite
total time = number of tests × average test timenumber of nodes
From the documentation: 15 tests of 45 s take 11 min 15 s on one node, 2 min 15 s on 5 nodes and 45 s on 15 nodes.

For a test, the Grid looks like one big remote driver. The test sends the same W3C requests as before, only to http://localhost:4444 or wherever the Grid runs. The Grid finds a node with a free slot for the requested browser, starts the session there, and passes every later command to that node.

Ask the Grid if it is ready and what it offers
GridStatus.java
import java.net.URI;import java.net.http.HttpClient;import java.net.http.HttpRequest;import java.net.http.HttpResponse;import java.util.List;import java.util.Map;import org.openqa.selenium.json.Json; public class GridStatus {    @SuppressWarnings("unchecked")    public static void main(String[] args) throws Exception {        HttpResponse<String> res = HttpClient.newHttpClient().send(            HttpRequest.newBuilder(URI.create("http://localhost:4444/status")).build(),            HttpResponse.BodyHandlers.ofString());        Map<String, Object> body = new Json().toType(res.body(), Json.MAP_TYPE);        Map<String, Object> value = (Map<String, Object>) body.get("value");        System.out.println("ready: " + value.get("ready") + ", " + value.get("message"));        List<Map<String, Object>> nodes = (List<Map<String, Object>>) value.get("nodes");        Map<String, Object> node = nodes.get(0);        System.out.println("nodes: " + nodes.size() + ", max sessions: " + node.get("maxSessions"));        for (Map<String, Object> slot : (List<Map<String, Object>>) node.get("slots")) {            System.out.println("slot: " + ((Map<String, Object>) slot.get("stereotype")).get("browserName"));        }    }}
  1. JSON gives back plain objects, so the casts are unchecked.
  2. The same endpoint a driver has, now answered by the Grid.
  3. Selenium ships its own JSON reader.
  4. Each slot can hold one session of this browser.

Real world scenario: Black Friday regression

A shop has 600 browser tests of about 40 seconds. On one machine the run takes 6 hours 40 minutes, too long to run before every release. On a Grid of 20 small nodes it takes about 20 minutes, so the team runs it on every merge, in Chrome, Firefox and Edge.

Lesson 2 of 3

Components, roles and ports

Grid 4 is built from six components. In a small Grid they all run in one process. In a large one each runs on its own machine. The documentation describes them like this:

ComponentJobDefault port
RouterEntry point for every request. New sessions go to the queue. Commands for existing sessions go straight to the right node, found through the Session Map4444
New Session QueueHolds new session requests in first in, first out order, with a timeout5559
DistributorKnows every node and its slots. Takes requests from the queue, finds a matching free slot and creates the session5553
Session MapRemembers which node runs which session id5556
NodeRuns the browsers. By default one slot per CPU for Chromium browsers and Firefox, one for Safari5555
Event BusMessages between the other components, cheaper than HTTP. Started first in a distributed Grid4442, 4443 and 5557
RoleCommandUse it for
Standalonejava -jar selenium-server-<version>.jar standaloneAll components in one process on one machine. Local debugging, quick suites, CI
Hub and Node... hub and ... node --hub http://<hub-ip>:4444The most used role. Combine machines with different systems and browsers behind one address
Distributed... event-bus, sessionqueue, sessions, distributor, router, nodeLarge Grids with more than 100 nodes, each component scaled on its own
Remember
A node registers by sending a message on the Event Bus, and the Distributor then calls it over HTTP to confirm. When hub and node are on different machines, the Event Bus ports 4442 and 4443 and the node port must be reachable.
Three tests, two slots: watch the queue
Queue.java
import java.net.URL;import java.util.ArrayList;import java.util.List;import java.util.concurrent.ExecutorService;import java.util.concurrent.Executors;import java.util.concurrent.Future;import org.openqa.selenium.chrome.ChromeOptions;import org.openqa.selenium.remote.RemoteWebDriver; public class Queue {    public static void main(String[] args) throws Exception {        long t0 = System.currentTimeMillis();        ExecutorService pool = Executors.newFixedThreadPool(3);        List<Future<String>> results = new ArrayList<>();        for (int i = 1; i <= 3; i++) {            int n = i;            results.add(pool.submit(() -> {                RemoteWebDriver driver = new RemoteWebDriver(new URL("http://localhost:4444"), new ChromeOptions());                long got = Math.round((System.currentTimeMillis() - t0) / 1000.0);                Thread.sleep(3000);                driver.quit();                return got + " s";            }));        }        List<String> times = new ArrayList<>();        for (Future<String> f : results) times.add(f.get());        pool.shutdown();        times.sort(null);        System.out.println("got a browser after: " + times);    }}
  1. Three threads, so three tests start at the same moment.
  2. Returns when the Grid has given this test a slot.
  3. Pretend the test takes 3 seconds.
  4. Frees the slot for the next request in the queue.
  5. Two at once, the third only after a slot was free.
Real output from this run (Selenium 4.51.0 with Chrome 153)
got a browser after: [2 s, 2 s, 5 s]

The Grid only had two free slots for three tests. Two got a browser straight away. The third waited in the New Session Queue until a test called quit and freed a slot. This is why every test must quit its session, pass or fail: a session left open keeps its slot until the session timeout, 300 seconds on this node.

Lesson 3 of 3

Remote sessions, metadata and files

Moving a test to the Grid changes one line: the driver is created with the Grid address instead of a local browser. Options still choose the browser and its settings. Capabilities that start with se: are Grid metadata. se:name shows the test name in the Grid UI instead of the session id.

Run a test on the Grid with a name and a file upload
OnTheGrid.java
import java.net.URL;import java.nio.file.Files;import java.nio.file.Path;import org.openqa.selenium.By;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeOptions;import org.openqa.selenium.remote.LocalFileDetector;import org.openqa.selenium.remote.RemoteWebDriver; public class OnTheGrid {    public static void main(String[] args) throws Exception {        ChromeOptions options = new ChromeOptions();        options.setCapability("se:name", "upload on the grid");        RemoteWebDriver driver = new RemoteWebDriver(new URL("http://localhost:4444"), options);        for (String k : new String[] {"browserName", "platformName", "se:name", "se:cdp"}) {            Object v = driver.getCapabilities().getCapability(k);            System.out.println(k + ": " + (k.equals("se:cdp") ? String.valueOf(v).replaceAll("[0-9a-f]{32}", "{id}") : v));        }        Path file = Files.writeString(Files.createTempDirectory("up").resolve("report.txt"), "hello grid");        driver.setFileDetector(new LocalFileDetector());        driver.get("https://www.selenium.dev/selenium/web/upload.html");        WebElement input = driver.findElement(By.id("upload"));        input.sendKeys(file.toAbsolutePath().toString());        System.out.println("attached: " + driver.executeScript("return arguments[0].files[0].name", input));        driver.quit();    }}
  1. Options say which browser you want. The Grid picks a node that has it.
  2. se: capabilities are Grid metadata. se:name shows in the Grid UI.
  3. The only change from a local test: a URL instead of a local driver.
  4. se:cdp is a DevTools address that goes through the Grid.
  5. Sends the local file to the node, which may be another machine.
  6. The browser on the node has the file.

Two capabilities came back from the Grid that a local driver does not return. se:name echoes the metadata. se:cdp is a DevTools address that runs through the Grid itself, so tools that need DevTools work even when the browser is on another machine. Chapter 6.2 uses it.

The file detector matters as soon as the node is another machine. sendKeys with a path on your laptop means nothing to a node in a data centre. With a local file detector the binding zips the file, sends it to the node, and types the path of the copy. On this Grid the node was the same machine, so it would also have worked without it. On a real Grid it would not.

One idea, four depths

A Grid runs your tests on other machines, many at once. Your test only changes the address it connects to.

The Router takes requests, the queue holds new ones, the Distributor finds a free slot on a node and the Session Map remembers where each session runs. Standalone, hub and node, or distributed decide how the components are deployed.

Slots are matched by capabilities. A request waits in the queue until a slot is free or the queue timeout passes. se: capabilities carry metadata, and se:cdp exposes DevTools through the Router.

The documentation recommends many small nodes over one large one, about one CPU and 1 GB of RAM per browser, and Docker for isolation. Large Grids use the distributed role, with GraphQL and observability from chapter 6.2.
