Navigate and ask where you are

Four commands move a tab around, and they match the buttons a person uses: the address bar, Back, Forward and Reload. Two more questions tell you where you ended up: the title and the current URL.

Navigate.java
import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class Navigate {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/web-form.html");        System.out.println("1 " + driver.getTitle());        driver.navigate().to("https://www.selenium.dev/selenium/web/xhtmlTest.html");        System.out.println("2 " + driver.getTitle() + " at " + driver.getCurrentUrl());        driver.navigate().back();        System.out.println("3 " + driver.getTitle());        driver.navigate().forward();        System.out.println("4 " + driver.getTitle());        driver.navigate().refresh();        System.out.println("5 " + driver.getTitle());        driver.quit();    }}
  1. Navigate To. The short form of driver.navigate().to(...).
  2. The long form does the same thing.
  3. Title and address of the page now showing.
  4. Press the Back button.
  5. Press the Forward button.
  6. Reload the current page.

History works the way it does for a person. A new get after going back throws away the pages that were ahead. Back on the first page does nothing at all, and raises no error, so a test that needs to know where it is should check the title or the URL.

Real world scenario: a login redirect

A test opens the account page of a shop. The shop is not logged in, so it redirects to the login page. The test checks current_url and sees /login?next=/account. After logging in it expects to land back on /account. Reading the address after each step is how the test proves the redirect works.

Common mistake
After refresh or any navigation, the elements you found before belong to the old page. Using them raises stale element reference. Find them again on the new page. Chapter 5.4 covers this error in depth.
Lesson 2 of 4

Window size and position

A page can look different at different sizes. A menu turns into a hamburger button on a narrow screen, and a table hides columns. The documentation reminds us that screen resolution can change how your application renders, so WebDriver lets you set the size and position of the window.

Set the window size and position, then read them back
WindowRect.java
import org.openqa.selenium.Dimension;import org.openqa.selenium.Point;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class WindowRect {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        WebDriver.Window window = driver.manage().window();        window.setSize(new Dimension(1024, 768));        window.setPosition(new Point(40, 30));        Dimension size = window.getSize();        Point where = window.getPosition();        System.out.println("size " + size.getWidth() + " x " + size.getHeight());        System.out.println("position " + where.getX() + ", " + where.getY());        driver.quit();    }}
  1. Every window command lives under manage().window().
  2. Restore the window and make it 1024 by 768 pixels.
  3. Move its top left corner to x 40, y 30 on the screen.
  4. Ask the browser for the size it really has.
Real output from this run (Selenium 4.51.0 with Chrome 153)

Common mistake
Maximize and minimize need a desktop window manager. On a bare Linux build server they can fail with an unknown error, which is what happened when this page was built. Setting an exact size with Set Window Rect or the --window-size switch works everywhere and gives the same layout on every machine.
Real world scenario: testing the mobile menu

A news site shows a full menu above 768 pixels and a hamburger button below. One test sets the window to 1280 by 800 and checks the full menu. Another sets it to 375 by 800 and checks that the hamburger opens the menu. Same page, two layouts, two sizes.

Lesson 3 of 4

Screenshots

A screenshot is the most useful thing a failed test can leave behind. WebDriver has two commands: Take Screenshot for the visible part of the page and Take Element Screenshot for one element. Both return a PNG encoded as base64 text, and each binding gives you helpers to save it.

Save a screenshot of the page and of one element
Screenshots.java
import java.io.File;import java.nio.file.Files;import java.nio.file.Path;import java.awt.image.BufferedImage;import javax.imageio.ImageIO;import org.openqa.selenium.By;import org.openqa.selenium.Dimension;import org.openqa.selenium.OutputType;import org.openqa.selenium.TakesScreenshot;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class Screenshots {    public static void main(String[] args) throws Exception {        WebDriver driver = new ChromeDriver();        driver.manage().window().setSize(new Dimension(1024, 768));        driver.get("https://www.selenium.dev/selenium/web/web-form.html");        File page = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE);        Files.copy(page.toPath(), Path.of("page.png"));        WebElement button = driver.findElement(By.cssSelector("button"));        File only = button.getScreenshotAs(OutputType.FILE);        Files.copy(only.toPath(), Path.of("button.png"));        for (String name : new String[] {"page.png", "button.png"}) {            BufferedImage img = ImageIO.read(new File(name));            System.out.println(name + ": " + img.getWidth() + " x " + img.getHeight());        }        driver.quit();    }}
  1. Take Screenshot of the viewport. Selenium writes a temporary PNG file.
  2. Copy it somewhere you will find it.
  3. Take Element Screenshot: just the area of the button.
  4. Open the PNG to read its size in pixels.
Real output from this run (Selenium 4.51.0 with Chrome 153)

Print a page to PDF

The W3C Print Page command turns the current page into a PDF. You describe the paper with PrintOptions and get the PDF back as base64. The documentation notes that Chromium browsers need headless mode for this.

Print the page to a PDF file
PrintPdf.java
import java.nio.file.Files;import java.nio.file.Path;import java.util.Base64;import org.openqa.selenium.Pdf;import org.openqa.selenium.PrintsPage;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.chrome.ChromeOptions;import org.openqa.selenium.print.PrintOptions; public class PrintPdf {    public static void main(String[] args) throws Exception {        ChromeOptions options = new ChromeOptions().addArguments("--headless=new");        ChromeDriver driver = new ChromeDriver(options);        driver.get("https://www.selenium.dev/selenium/web/web-form.html");        PrintOptions print = new PrintOptions();        print.setOrientation(PrintOptions.Orientation.LANDSCAPE);        Pdf pdf = ((PrintsPage) driver).print(print);        byte[] bytes = Base64.getDecoder().decode(pdf.getContent());        Files.write(Path.of("page.pdf"), bytes);        System.out.println("page.pdf starts with " + new String(bytes, 0, 5));        driver.quit();    }}
  1. Chromium prints to PDF only in headless mode.
  2. Paper settings: orientation, page ranges, size, margins, scale, background.
  3. The W3C Print Page command. The PDF comes back as base64 text.
  4. Decode it to the real bytes.
  5. Every PDF file starts with %PDF-.
Real output from this run (Selenium 4.51.0 with Chrome 153)

Real world scenario: archiving invoices

An accounts team must keep a copy of every invoice page the system shows on the last day of each month. A scheduled Selenium job logs in, opens each invoice and prints it to PDF in landscape with backgrounds on. No person clicks Print a hundred times.

One idea, four depths

You can tell the browser where to go, ask where it is, change its size, take a picture and print the page, all from code.

Each of these is one W3C command: Navigate To, Back, Forward, Refresh, Get Title, Get Current URL, Set Window Rect, Take Screenshot and Print Page. Images and PDFs travel as base64 text inside the JSON answer.

Navigation commands wait according to the page load strategy, but history and refresh can change the page under any element references you hold. Screenshots show the viewport only, so full page captures need a browser specific feature, such as Firefox full page screenshots.

WebDriver BiDi adds a browsingContext module with navigate, print and captureScreenshot commands that can also report navigation events as they happen. Chapter 6.2 introduces BiDi.
