WebDriver BiDi: the browser talks back

Everything so far followed one pattern: the test asks, the driver answers. The documentation calls this strict request and response, and it is exactly what you want for clicks and reads. It cannot tell you about something you did not ask for, such as a message the page logged or an error it threw a second ago.

WebDriver BiDi is a newer W3C protocol that adds a WebSocket next to the HTTP connection. Over it the browser can push events to the test the moment they happen. The Selenium team and the browser vendors build it together as a stable, cross browser replacement for the Chrome DevTools Protocol.

Hear console messages and page errors as they happen
BidiLog.java
import java.util.List;import java.util.concurrent.CopyOnWriteArrayList;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.bidi.module.LogInspector;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.chrome.ChromeOptions; public class BidiLog {    public static void main(String[] args) throws Exception {        ChromeOptions options = new ChromeOptions();        options.setCapability("webSocketUrl", true);        WebDriver driver = new ChromeDriver(options);        List<String> heard = new CopyOnWriteArrayList<>();        try (LogInspector inspector = new LogInspector(driver)) {            inspector.onConsoleEntry(e -> heard.add("console " + e.getLevel() + ": " + e.getText()));            inspector.onJavaScriptException(e -> heard.add("page error: " + e.getText()));            driver.get("https://www.selenium.dev/selenium/web/bidi/logEntryAdded.html");            for (String id : new String[] {"consoleLog", "consoleError", "jsException"}) {                driver.findElement(By.id(id)).click();            }            long end = System.currentTimeMillis() + 5000;            while (heard.size() < 3 && System.currentTimeMillis() < end) Thread.sleep(50);        }        heard.forEach(System.out::println);        driver.quit();    }}
  1. Ask for a BiDi WebSocket next to the normal HTTP connection.
  2. Events arrive on another thread, so use a thread safe list.
  3. Subscribes to log events. Closing it unsubscribes.
  4. Called for every console.log, console.error and so on.
  5. Called for every uncaught error in the page.
  6. Events are pushed, not returned, so wait until all three arrived.
Real output from this run (Selenium 4.51.0 with Chrome 153)
console info: Hello, world!
console error: I am console error
page error: Error: Not working

The test never asked for a log. It subscribed once, and each click made the browser push an event. Three different events arrived: a console message at level info, one at level error, and an uncaught JavaScript error. A test can now fail on any page error, even when the page still looks fine.

The Chrome DevTools Protocol

Before BiDi existed, Selenium gave access to the Chrome DevTools Protocol, the protocol Chrome DevTools uses to debug pages. The documentation is careful about it: CDP was not designed for testing and has no stable API, so features depend on the browser version. Selenium supports the three most recent Chrome versions for its generated CDP classes. The Java jars in this course carry v153, v154 and v155.

Send Chrome DevTools commands: read the version and change the time zone
Cdp.java
import java.util.Map;import org.openqa.selenium.JavascriptExecutor;import org.openqa.selenium.chrome.ChromeDriver; public class Cdp {    public static void main(String[] args) {        ChromeDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/blank.html");        Map<String, Object> version = driver.executeCdpCommand("Browser.getVersion", Map.of());        System.out.println("protocol " + version.get("protocolVersion") + ", " + version.get("product"));        String zone = "return Intl.DateTimeFormat().resolvedOptions().timeZone";        System.out.println("time zone before: " + ((JavascriptExecutor) driver).executeScript(zone));        driver.executeCdpCommand("Emulation.setTimezoneOverride", Map.of("timezoneId", "Asia/Kolkata"));        System.out.println("time zone after: " + ((JavascriptExecutor) driver).executeScript(zone));        driver.quit();    }}
  1. executeCdpCommand exists on Chrome and Edge drivers only.
  2. Any CDP method by name, with a map of parameters.
  3. Something WebDriver Classic has no command for.
Real output from this run (Selenium 4.51.0 with Chrome 153)

time zone before: UTC

Two lines show the point. Browser.getVersion returns information no W3C command gives. Emulation.setTimezoneOverride changed what the page believes its time zone is, without touching the machine. The page then reports Asia/Calcutta, because Chrome uses the older canonical name for the zone you set as Asia/Kolkata. This is how a test can check how a page shows times in India from a server in another country.

Grid features: GraphQL and endpoints

A Grid with many nodes needs a way to see what is going on. Besides the /status endpoint from chapter 6.1, the Grid answers GraphQL queries at /graphql. GraphQL lets you ask for exactly the fields you need, nothing more.

Ask the Grid exactly what you need with GraphQL
GridQuery.java
import java.net.URI;import java.net.URL;import java.net.http.HttpClient;import java.net.http.HttpRequest;import java.net.http.HttpResponse;import java.util.List;import java.util.Map;import java.util.stream.Collectors;import org.openqa.selenium.chrome.ChromeOptions;import org.openqa.selenium.json.Json;import org.openqa.selenium.remote.RemoteWebDriver; @SuppressWarnings("unchecked")public class GridQuery {    static final Json JSON = new Json();     static Map<String, Object> ask(String query) throws Exception {        String body = "{\"query\": \"" + query + "\"}";        String text = HttpClient.newHttpClient().send(            HttpRequest.newBuilder(URI.create("http://localhost:4444/graphql")).POST(HttpRequest.BodyPublishers.ofString(body)).build(),            HttpResponse.BodyHandlers.ofString()).body();        Map<String, Object> reply = JSON.toType(text, Json.MAP_TYPE);        return (Map<String, Object>) reply.get("data");    }     public static void main(String[] args) throws Exception {        String q = "{ grid { nodeCount, totalSlots, maxSession, sessionCount, sessionQueueSize } }";        System.out.println("idle: " + ask(q).get("grid"));        ChromeOptions options = new ChromeOptions();        options.setCapability("se:name", "graphql demo");        RemoteWebDriver driver = new RemoteWebDriver(new URL("http://localhost:4444"), options);        System.out.println("busy: " + ask(q).get("grid"));        Map<String, Object> info = (Map<String, Object>) ask("{ sessionsInfo { sessions { capabilities } } }").get("sessionsInfo");        List<Map<String, Object>> sessions = (List<Map<String, Object>>) info.get("sessions");        System.out.println("names: " + sessions.stream()            .map(x -> JSON.<Map<String, Object>>toType((String) x.get("capabilities"), Json.MAP_TYPE).get("se:name"))            .collect(Collectors.toList()));        driver.quit();    }}
  1. Selenium ships its own JSON reader.
  2. GraphQL over HTTP: one POST with the query as a string.
  3. The answer sits under data.
  4. Ask only for these fields.
  5. One session is running now.
  6. The se:name metadata is in the session capabilities.

One idea, four depths

BiDi lets the browser tell the test about events, such as console messages and page errors, the moment they happen. CDP gives Chrome only extras. GraphQL tells you what the Grid is doing.

Turn on BiDi with the webSocketUrl capability, then subscribe to log events. Use CDP commands by name for Chromium features with no W3C command. Query the Grid at /graphql for counts, sessions and the queue.

BiDi and CDP both use a WebSocket with commands and events, but BiDi is a W3C standard across browsers while CDP has no stability promise. On a Grid, se:cdp in the capabilities is the DevTools address routed through the Grid.

Selenium is moving its own implementation from Classic to BiDi while keeping compatibility. Network interception, authentication handlers and preload scripts are the next layer, and the Grid adds observability with tracing for each component.
