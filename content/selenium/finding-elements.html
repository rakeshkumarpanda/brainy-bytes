Find one or find many

Every Selenium binding has two find methods, and their only difference is how many results they return and what they do when nothing matches.

find element (singular)find elements (plural)
ReturnsOne element: the first match in page orderA list of every match, in page order
No matchRaises no such elementReturns an empty list
W3C commandFind ElementFind Elements
Use it forAn element that must be thereCounting, looping, or checking that something is absent
One element, all elements, and what happens when nothing matches
FindAll.java
import java.util.List;import org.openqa.selenium.By;import org.openqa.selenium.NoSuchElementException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class FindAll {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/locators_tests/locators.html");        List<WebElement> inputs = driver.findElements(By.tagName("input"));        System.out.println("inputs: " + inputs.size());        for (WebElement e : inputs) {            System.out.println("  " + e.getAttribute("type") + " " + e.getAttribute("name"));        }        List<WebElement> none = driver.findElements(By.id("email"));        System.out.println("email boxes: " + none.size());        try {            driver.findElement(By.id("email"));        } catch (NoSuchElementException e) {            System.out.println("findElement: NoSuchElementException");        }        driver.quit();    }}
  1. Plural: a List of every input, in page order.
  2. Walk the list like any Java list.
  3. No match: an empty list, never an error.
  4. Singular with no match: an exception.

Real world scenario: checking the search results

A test types "laptop" into a shop search and must check that exactly 20 results appear and that none says "Out of stock". It uses find elements on the result cards, checks the list has 20 entries, then loops over them reading each status. To check that an error banner is gone, it asks find elements for the banner and expects an empty list, which never raises.

Common mistake
find elements never waits for the first element to appear unless an implicit wait is set, and then it returns as soon as at least one matches. An empty list can mean the page is not ready yet. Chapter 4.1 shows how to wait properly.

Search inside an element

Instead of searching the whole page, you can first find a container and then search inside it. The documentation calls this evaluating a subset of the DOM. In Java and C# the driver, an element and a shadow root all implement the same SearchContext interface, which is why they share the find methods.

Search inside one element, and the XPath trap
Scope.java
import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class Scope {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/locators_tests/locators.html");        WebElement form = driver.findElement(By.tagName("form"));        System.out.println("inputs in form: " + form.findElements(By.cssSelector("input")).size());        System.out.println("links via //a: " + form.findElements(By.xpath("//a")).size());        System.out.println("links via .//a: " + form.findElements(By.xpath(".//a")).size());        WebElement last = form.findElement(By.id("lname"));        WebElement same = driver.findElement(By.cssSelector("form #lname"));        System.out.println("same element: " + last.equals(same));        driver.quit();    }}
  1. First find the parent element.
  2. Called on the form, CSS only looks inside it.
  3. The trap: // starts at the top of the document, so the link outside the form is found.
  4. The dot means start here. Now nothing outside the form counts.
  5. Two commands: find the form, then find inside it.
  6. The optimised version: one CSS selector, one command.
  7. Both references point at the same element.
Real output from this run (Selenium 4.51.0 with Chrome 153)

The second line of output is the most common XPath mistake in Selenium. An XPath that begins with // always starts at the top of the document, even when you call it on an element. Start with .// to search below the element. CSS selectors called on an element never have this problem.

The documentation also points out that a nested search costs two commands. When a single CSS selector such as form #lname can say the same thing, it is one command and slightly faster.

Remember
Searching inside a container is still very useful when the page repeats a pattern: the Delete button inside the third row of a table, or the price inside one product card. Find the row or card first, then the button inside it.

The shadow DOM

Modern components often hide their insides in a shadow DOM: a separate tree attached to an element, called the shadow host. The page can see the host but a normal search does not go inside it. That keeps the component styles and ids apart from the rest of the page, and it also hides them from Selenium.

  1. Find the hostA normal locator finds the element the shadow tree hangs from.
  2. Get its shadow rootGet Element Shadow Root. Selenium 4 and Chromium 96 or later.
  3. Search insideFind Element From Shadow Root with a CSS selector.
Reach into a shadow root
Shadow.java
import org.openqa.selenium.By;import org.openqa.selenium.InvalidArgumentException;import org.openqa.selenium.SearchContext;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class Shadow {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/shadowRootPage.html");        String box = "input[type='checkbox']";        System.out.println("from the page: " + driver.findElements(By.cssSelector(box)).size());        WebElement host = driver.findElement(By.cssSelector("custom-checkbox-element"));        SearchContext shadowRoot = host.getShadowRoot();        WebElement checkbox = shadowRoot.findElement(By.cssSelector(box));        System.out.println("from the shadow root: " + checkbox.getAttribute("type"));        try {            shadowRoot.findElement(By.xpath(".//input"));        } catch (InvalidArgumentException e) {            System.out.println("xpath in shadow root: " + e.getMessage().split("\n")[0]);        }        driver.quit();    }}
  1. The checkbox lives in a shadow tree, so a normal search finds nothing.
  2. The shadow host: the element the hidden tree is attached to.
  3. Get Element Shadow Root. A SearchContext, like the driver and an element.
  4. Search inside the shadow tree.
  5. XPath inside a shadow root.
  6. Chrome refuses it.
Real output from this run (Selenium 4.51.0 with Chrome 153)

from the shadow root: checkbox

Three facts show in this run. A search from the page cannot see the checkbox. A search from the shadow root can. And Chrome refused an XPath inside the shadow root with invalid argument. When this page was built, tag name was refused too, while id, name and class name worked because the binding sends them as CSS. Use CSS selectors inside shadow roots.

Remember
A shadow root can contain another shadow host. Then you repeat the two steps: get that host, get its shadow root, search again. Each level is one more pair of commands.

The active element

The active element is the element that has the keyboard focus right now: what would receive your typing. The W3C command Get Active Element returns it, and the bindings put it under switchTo().

Which element has the focus?
Active.java
import org.openqa.selenium.By;import org.openqa.selenium.Keys;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class Active {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/web-form.html");        System.out.println("at start: " + driver.switchTo().activeElement().getTagName());        driver.findElement(By.name("my-text")).click();        System.out.println("after click: " + driver.switchTo().activeElement().getAttribute("name"));        driver.switchTo().activeElement().sendKeys(Keys.TAB);        System.out.println("after Tab: " + driver.switchTo().activeElement().getAttribute("name"));        driver.quit();    }}
  1. Nothing is focused yet, so the active element is the body.
  2. Clicking a text box gives it the focus.
  3. Press Tab on whatever has the focus, as a user would.
  4. The focus moved to the next field.

This is how you test keyboard behaviour: that Tab moves through a form in a sensible order, that a dialog puts the focus on its first button, or that pressing Enter in a search box submits it. Keyboard users and screen reader users depend on that order.

One idea, four depths

Ask for one element or for all of them. Look inside a part of the page, inside a hidden component, or at the element that has the focus.

find element raises when nothing matches, find elements returns an empty list. Searches from an element stay inside it, except XPath that starts with //. Shadow roots need host, shadow root, then CSS.

Each search is a W3C command with its own endpoint: Find Element, Find Elements, Find Element From Element, Find Elements From Element, Get Element Shadow Root, Find Element From Shadow Root and Get Active Element. Fewer, more precise commands make suites faster.

The shadow root reference is its own web object with the key shadow-6066-11e4-a52e-4f735466cecf, like the element key in chapter 1.2. The W3C spec allows any strategy inside a shadow root, but browsers do not have to support XPath there, which is why portable tests use CSS.
