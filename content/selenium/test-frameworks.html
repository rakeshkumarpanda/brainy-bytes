Lesson 1 of 3

Selenium inside a test framework

Selenium drives the browser. It does not decide whether a test passed, it does not group tests, and it does not write a report. A test framework does that: JUnit 5 for Java, pytest for Python and Mocha for JavaScript are the ones the Selenium documentation uses in its own examples. The framework finds your tests, runs setup before each one and teardown after it, compares values with assertions and reports what passed and failed.

A first test class: a fresh browser for every test
WebFormTest.java
import static org.junit.jupiter.api.Assertions.assertEquals; import org.junit.jupiter.api.AfterEach;import org.junit.jupiter.api.BeforeEach;import org.junit.jupiter.api.Test;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class WebFormTest {    WebDriver driver;     @BeforeEach    void startBrowser() {        driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/web-form.html");    }     @Test    void pageHasTheRightTitle() {        assertEquals("Web form", driver.getTitle());    }     @Test    void submittingShowsReceived() {        driver.findElement(By.name("my-text")).sendKeys("Selenium");        driver.findElement(By.cssSelector("button")).click();        assertEquals("Received!", driver.findElement(By.id("message")).getText());    }     @AfterEach    void quitBrowser() {        driver.quit();    }}
  1. A field, so every method of this test can reach the driver.
  2. Runs before every test method.
  3. One test: one behaviour, one reason to fail.
  4. Expected value first in JUnit, then the actual one.
  5. Runs after every test, also when the test failed.

  4. Asking for a parameter called driver makes pytest run the fixture.
  5. A plain assert. pytest shows both sides when it fails.

example.spec.js
const { Builder, Browser, By } = require('selenium-webdriver');const assert = require('assert'); describe('Web form', function () {  let driver;   beforeEach(async function () {    driver = await new Builder().forBrowser(Browser.CHROME).build();    await driver.get('https://www.selenium.dev/selenium/web/web-form.html');  });   it('has the right title', async function () {    assert.strictEqual(await driver.getTitle(), 'Web form');  });   it('shows Received! after submit', async function () {    await driver.findElement(By.name('my-text')).sendKeys('Selenium');    await driver.findElement(By.css('button')).click();    assert.strictEqual(await driver.findElement(By.id('message')).getText(), 'Received!');  });   afterEach(async function () {    await driver.quit();  });});
  1. describe groups tests. Mocha gives every test a name.
  2. Runs before every test.
  3. One test.
  4. Node's own assert module. Actual first, then expected.
  5. Runs after every test, also when the test failed.

Remember
The Selenium documentation recommends a fresh browser for every test. Then no cookie, login or open dialog can leak from one test into the next, and the tests can run in any order or in parallel. It costs a browser start per test, a price that is almost always worth paying.
Real world scenario: the flaky Friday test

A team shares one browser across a whole test class to save time. One test logs out at the end, and on Friday the runner orders the tests differently: the logout test runs before the cart test, and the cart test fails with a login page. Nothing in the cart test is wrong. Moving the driver into a before each and after each pair makes the failure disappear for good.

Lesson 2 of 3

Data-driven tests

The login page has one form and many cases: right user and password, wrong password, unknown user. Copying the test three times means three places to fix when the form changes. A parameterized test writes the steps once and feeds them a table of data. The report shows one result per row.

One test, three rows of data
LoginTest.java
import static org.junit.jupiter.api.Assertions.assertEquals; import java.time.Duration;import org.junit.jupiter.api.AfterEach;import org.junit.jupiter.api.BeforeEach;import org.junit.jupiter.params.ParameterizedTest;import org.junit.jupiter.params.provider.CsvSource;import org.openqa.selenium.Alert;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.support.ui.ExpectedConditions;import org.openqa.selenium.support.ui.WebDriverWait; public class LoginTest {    WebDriver driver;     @BeforeEach    void open() {        driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/login.html");    }     @ParameterizedTest(name = "{0} / {1}")    @CsvSource({        "username, password, You have successfully logged in.",        "username, wrong, Please enter valid credentials",        "admin, password, Please enter valid credentials"    })    void login(String user, String password, String expected) {        driver.findElement(By.id("username-field")).sendKeys(user);        driver.findElement(By.id("password-field")).sendKeys(password);        driver.findElement(By.id("login-form-submit")).click();        Alert alert = new WebDriverWait(driver, Duration.ofSeconds(2)).until(ExpectedConditions.alertIsPresent());        assertEquals(expected, alert.getText());        alert.accept();    }     @AfterEach    void close() {        driver.quit();    }}
  1. The name shows the data of each run in the report.
  2. Each line is one run of the test: username, password, expected message.
  3. JUnit passes the columns in as parameters.
  4. The page answers with an alert.

example.spec.js
const { Builder, Browser, By, until } = require('selenium-webdriver');const assert = require('assert'); const rows = [  ['username', 'password', 'You have successfully logged in.'],  ['username', 'wrong', 'Please enter valid credentials'],  ['admin', 'password', 'Please enter valid credentials'],]; describe('Login', function () {  let driver;  beforeEach(async function () {    driver = await new Builder().forBrowser(Browser.CHROME).build();    await driver.get('https://www.selenium.dev/selenium/web/login.html');  });   for (const [user, password, expected] of rows) {    it(`${user} / ${password}`, async function () {      await driver.findElement(By.id('username-field')).sendKeys(user);      await driver.findElement(By.id('password-field')).sendKeys(password);      await driver.findElement(By.id('login-form-submit')).click();      const alert = await driver.wait(until.alertIsPresent(), 2000);      assert.strictEqual(await alert.getText(), expected);      await alert.accept();    });  }   afterEach(async function () {    await driver.quit();  });});
  1. Each row is one run of the test.
  2. Mocha has no data annotation. A loop that calls it() once per row does the same job.
  3. The page answers with an alert.

Look at each report. JUnit used the name pattern for every row and Mocha used the title built by the loop. pytest ran in quiet mode, so it printed one dot per row, three dots for three runs. Run it with -v and it lists each row with its data in the test id. When the second row fails one day, the report says which row, without opening the code.

Remember
Keep the data close to the test while it is small. When it grows, move it to a CSV or JSON file: JUnit has @CsvFileSource, and pytest and Mocha can read any file into the same list.
Lesson 3 of 3

A screenshot when a test fails

A red test in a report from the night run says what was expected, not what the page looked like. A screenshot taken at the moment of failure answers that. The trick is the order: the picture must be taken after the test failed but before the browser is closed. Each framework has its own place for that.

A failing test that saves a screenshot before the browser closes
ScreenshotOnFailure.java
import java.nio.file.Files;import java.nio.file.Path;import java.nio.file.StandardCopyOption;import org.junit.jupiter.api.extension.AfterTestExecutionCallback;import org.junit.jupiter.api.extension.ExtensionContext;import org.openqa.selenium.OutputType;import org.openqa.selenium.TakesScreenshot;import org.openqa.selenium.WebDriver; public class ScreenshotOnFailure implements AfterTestExecutionCallback {    @Override    public void afterTestExecution(ExtensionContext context) throws Exception {        if (context.getExecutionException().isPresent()) {            WebDriver driver = ((TitleTest) context.getRequiredTestInstance()).driver;            Path shot = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE).toPath();            Path target = Path.of("failure-" + context.getRequiredTestMethod().getName() + ".png");            Files.copy(shot, target, StandardCopyOption.REPLACE_EXISTING);            System.out.println("saved " + target + " " + (Files.size(target) > 0));        }    }}
  1. Called right after the test method, before any AfterEach method.
  2. Present only when the test threw, so only when it failed.
  3. Name the file after the test.
TitleTest.java

conftest.py
import os import pytestfrom selenium import webdriver  @pytest.hookimpl(wrapper=True, tryfirst=True)def pytest_runtest_makereport(item, call):    report = yield    setattr(item, "rep_" + report.when, report)    return report  @pytest.fixturedef driver(request):    driver = webdriver.Chrome()    yield driver    if request.node.rep_call.failed:        name = f"failure-{request.node.name}.png"        driver.save_screenshot(name)        print("saved", name, os.path.getsize(name) > 0)    driver.quit()

  2. Keep the report on the test item: rep_setup, rep_call and rep_teardown.
  3. Did the test body fail?
  4. Name the file after the test.
  5. Take the picture before quit.

One idea, four depths

A test framework runs your Selenium code as tests: setup before, the test, teardown after, and a pass or fail for each.

Start a fresh browser in the before each step and quit it in the after each step. Use parameterized tests for many rows of data and take a screenshot in the after step when the test failed.

Each framework has hooks at different points: JUnit extensions, pytest fixtures and hook functions, Mocha hooks with this.currentTest. Teardown runs whatever happened in the test, which is why quit belongs there.

Fixtures with a wider scope, such as one browser per worker, trade isolation for speed. Combine them with deleteAllCookies and a fresh page in a function scoped fixture, and with parallel runners such as pytest-xdist or JUnit parallel execution.
