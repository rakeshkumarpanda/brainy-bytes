Options and capabilities

When your code creates a driver, the binding sends New Session with a set of capabilities: the features you want the session to have. In Selenium 3 people wrote them into a DesiredCapabilities map. Since Selenium 4 you must use the browser Options classes: ChromeOptions, FirefoxOptions, EdgeOptions and SafariOptions. An Options object already knows its browserName, and it gives you named methods instead of string keys you could misspell.

Real world scenario: one test suite, two needs

On a laptop, a tester wants to watch Chrome click through the checkout. On the build server there is no screen, the window should be a fixed size so screenshots line up, and slow product images should not delay the tests. The test code is the same in both places. Only the Options object changes.

The standard W3C capabilities

CapabilityWhat it controlsDefault
browserNameWhich browser. Set for you by each Options class.set by the class
browserVersionWhich version. Selenium Manager can download it if missing.whatever is installed
platformNameThe operating system at the remote end. Matters most on Grid and in the cloud.the local OS
pageLoadStrategyWhen navigation commands return: normal, eager or none.normal
acceptInsecureCertsTrust expired or self signed TLS certificates.false
timeoutsScript, page load and implicit wait.30 s, 300 s, 0
unhandledPromptBehaviorWhat happens to an alert your code did not handle.dismiss and notify
proxySend browser traffic through a proxy server.none
setWindowRectWhether the browser supports resizing and moving windows.reported by the driver
strictFileInteractabilityStrict checks for hidden file inputs.off

Anything browser specific carries a vendor prefix. Chrome options travel as goog:chromeOptions, Firefox as moz:firefoxOptions. That is how command line switches such as --headless=new reach the browser.

Ask for a session with options, then read what the browser agreed to
SessionCaps.java
import org.openqa.selenium.Capabilities;import org.openqa.selenium.PageLoadStrategy;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.chrome.ChromeOptions; public class SessionCaps {    public static void main(String[] args) {        ChromeOptions options = new ChromeOptions();        options.addArguments("--headless=new");        options.addArguments("--window-size=1280,800");        options.setPageLoadStrategy(PageLoadStrategy.EAGER);        ChromeDriver driver = new ChromeDriver(options);        Capabilities caps = driver.getCapabilities();        System.out.println("browserName: " + caps.getBrowserName());        System.out.println("browserVersion: " + caps.getBrowserVersion());        System.out.println("platformName: " + caps.getPlatformName());        System.out.println("pageLoadStrategy: " + caps.getCapability("pageLoadStrategy"));        System.out.println("unhandledPromptBehavior: " + caps.getCapability("unhandledPromptBehavior"));        driver.quit();    }}
  1. An Options object describes the session you want. browserName is already set to chrome.
  2. A Chrome command line switch: run without a visible window.
  3. Another switch: the size of the browser window.
  4. A W3C capability: get() returns at DOMContentLoaded.
  5. New Session is sent with these capabilities.
  6. The capabilities the driver actually granted.
  7. The exact version of the browser that started.
  8. The operating system at the remote end.
  9. Our request was honoured.
  10. A default we did not set.

Remember
Each Options class can also take the binary path of a Chromium based browser, extensions, and excludeSwitches to turn off a default switch of chromedriver. The documentation lists them on the Chrome page. Use them only when you need them, because every extra setting is one more difference from what real users run.

Page load strategy

When you call get, WebDriver does not return the moment the address is sent. It waits for the page to reach a document.readyState. Which state it waits for is the page load strategy.

StrategyWaits until readyState isBrowser eventUse it when
normal (default)completeload: every image, font and style sheet is inYou want the safest behaviour
eagerinteractiveDOMContentLoaded: the HTML is parsed, images may still loadLarge images or ads slow the page and the test does not need them
noneanyonly the first download of the pageYou control every wait yourself

The documentation adds two warnings. First, complete does not mean the page is finished. A single page application can keep loading content with JavaScript long after the load event. Second, the strategy applies only to navigation by address. A click that leads to a new page is not covered, so your waits must handle that. The strategy applies to the whole session, so pick it once, in the Options.

Common mistake
Switching to eager or none to make tests faster is a trade. Every element that arrives later now needs an explicit wait, or the test becomes flaky. Chapter 4.1 shows how to write those waits.

The three session timeouts

Every session has three timeouts. They are W3C capabilities, so every browser has the same ones with the same defaults.

Implicit wait
0
How long Find Element keeps looking before it gives up with no such element. Zero means it checks once.
Page loadExam favourite
300,000 ms
Five minutes. How long a navigation may take before a timeout error.
Script
30,000 ms
Thirty seconds. How long an injected script may run before the script timeout error.
Read the three session timeouts, then trip one on purpose
SessionTimeouts.java
import java.time.Duration;import org.openqa.selenium.JavascriptExecutor;import org.openqa.selenium.ScriptTimeoutException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class SessionTimeouts {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        WebDriver.Timeouts t = driver.manage().timeouts();        System.out.println("implicit: " + t.getImplicitWaitTimeout());        System.out.println("pageLoad: " + t.getPageLoadTimeout());        System.out.println("script: " + t.getScriptTimeout());        t.scriptTimeout(Duration.ofSeconds(1));        driver.get("https://www.selenium.dev/selenium/web/blank.html");        try {            ((JavascriptExecutor) driver).executeAsyncScript("/* never calls its callback */");        } catch (ScriptTimeoutException e) {            System.out.println("Caught " + e.getClass().getSimpleName());        } finally {            driver.quit();        }    }}
  1. The timeouts of this session.
  2. Java prints a Duration. PT0S means zero seconds.
  3. PT5M is five minutes, which is 300,000 ms.
  4. PT30S is thirty seconds.
  5. Allow scripts only one second from now on.
  6. An async script must call its callback. This one never does.
  7. After one second the driver gives up with the W3C error script timeout.

In the exam
These timeouts belong to the browser session. Explicit waits such as WebDriverWait are different: they run in your code and poll the browser. Mixing an implicit wait with explicit waits can give surprising wait times, which chapter 4.1 explains.

The driver service

A local session has two programs: the browser and the driver. The Service classes manage the driver program: where its file is, which port it listens on, which arguments it gets and where its logs go. The documentation notes that a Service is only for local drivers. A remote session on a Grid has no local driver to manage.

Start the driver on a port you choose and ask if it is ready
DriverService.java
import java.net.URI;import java.net.http.HttpClient;import java.net.http.HttpRequest;import java.net.http.HttpResponse;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.chrome.ChromeDriverService; public class DriverService {    public static void main(String[] args) throws Exception {        ChromeDriverService service = new ChromeDriverService.Builder().usingPort(9600).build();        ChromeDriver driver = new ChromeDriver(service);        System.out.println("Driver URL: " + service.getUrl());        HttpRequest status = HttpRequest.newBuilder(URI.create("http://localhost:9600/status")).build();        String body = HttpClient.newHttpClient().send(status, HttpResponse.BodyHandlers.ofString()).body();        System.out.println("ready: " + body.contains("\"ready\":true"));        driver.quit();    }}
  1. A Service describes how to start chromedriver: here, on port 9600.
  2. Selenium starts chromedriver on that port, then opens a session.
  3. The address the binding sends its HTTP commands to.
  4. GET /status is a W3C command that needs no session.
  5. The driver says whether it can start new sessions.
  6. Ends the session and stops the service.

One idea, four depths

Options say what kind of browser you want. Service says how to start the little driver program. The driver class uses both.

Options become the capabilities of New Session. Service starts chromedriver on a port and the binding sends HTTP there. For a remote session you pass a URL instead of a Service.

Capability matching happens in two passes in W3C: alwaysMatch must hold, and one of the firstMatch entries is chosen. The Python binding, for example, sends your Options as alwaysMatch next to an empty firstMatch, as the real log in chapter 1.2 shows. The granted capabilities are the truth about the session, which is why logging them helps when a test passes locally and fails in CI.

The intermediary design means a Grid Router accepts New Session, picks a node whose stereotype matches the capabilities, and forwards the request. Chapter 6.1 follows that path, including the se: prefixed capabilities Grid adds.
