Read an error the right way

Every failure from a driver is one of the errors named in the W3C specification, such as no such element. Each language turns it into its own class, and the names are not always the same. The documentation keeps a table of them. These are the ones you will meet most:

W3C errorJavaPythonJavaScriptUsual cause and fix
no such elementNoSuchElementExceptionNoSuchElementExceptionNoSuchElementErrorWrong place, wrong time or a changed locator. Check the page, add an explicit wait, update the locator.
stale element referenceStaleElementReferenceExceptionStaleElementReferenceExceptionStaleElementReferenceErrorThe node was replaced, for example by a refresh or a re render. Find it again.
element click interceptedElementClickInterceptedExceptionElementClickInterceptedExceptionElementClickInterceptedErrorSomething covers the element: a sticky bar, a modal, an animation. Wait for it to go, or scroll.
element not interactableElementNotInteractableExceptionElementNotInteractableExceptionElementNotInteractableErrorHidden, zero size or not ready. Wait until visible and enabled.
invalid selectorInvalidSelectorExceptionInvalidSelectorExceptionInvalidSelectorErrorThe CSS or XPath is broken, or an XPath was passed to a CSS locator.
timeoutTimeoutExceptionTimeoutExceptionTimeoutErrorAn explicit wait ran out. The message says which condition.
script timeoutScriptTimeoutExceptionTimeoutExceptionScriptTimeoutErrorA script took longer than the script timeout.
unexpected alert openUnhandledAlertExceptionUnexpectedAlertPresentExceptionUnexpectedAlertOpenErrorAn alert was left open. Handle it where it opens.
no such windowNoSuchWindowExceptionNoSuchWindowExceptionNoSuchWindowErrorThe window was closed and the test did not switch back.
invalid session idNoSuchSessionExceptionInvalidSessionIdExceptionNoSuchSessionErrorThe session was quit or crashed. Look for a quit earlier in the test.
session not createdSessionNotCreatedExceptionSessionNotCreatedExceptionSessionNotCreatedErrorDriver and browser versions do not match, or the browser could not start.

Read a failure in this order: the error name, then the message, then the line of your code in the stack trace. The error name narrows the cause to one row above. The message often names the locator or the condition. The line tells you which step of the test failed, which can be one step after the real cause, as the forgotten alert in chapter 4.2 showed.

Remember
Search the error name together with the first line of the message. Ignore the long list of numbers under Stacktrace in Chrome messages. Those are addresses inside ChromeDriver, not your code.
Lesson 2 of 3

Stale elements and the element store

When you find an element, the driver does not send the element to your code. It stores the node in a table that belongs to the current browsing context, the window or frame you are in, and sends back an id for it. Every later command with that element sends the id back, and the driver looks it up in the table of the current context.

Make an element reference fail three ways, and fix each one
Stale.java
import org.openqa.selenium.By;import org.openqa.selenium.NoSuchElementException;import org.openqa.selenium.StaleElementReferenceException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class Stale {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/web-form.html");        WebElement box = driver.findElement(By.name("my-text"));        driver.navigate().refresh();        try {            box.sendKeys("x");        } catch (StaleElementReferenceException e) {            System.out.println("1. after refresh: " + e.getClass().getSimpleName());        }        box = driver.findElement(By.name("my-text"));        box.sendKeys("found again");        System.out.println("   fixed: " + box.getAttribute("value"));         driver.get("https://www.selenium.dev/selenium/web/iframes.html");        driver.switchTo().frame("iframe1");        WebElement email = driver.findElement(By.id("email"));        driver.switchTo().defaultContent();        try {            email.getAttribute("type");        } catch (NoSuchElementException e) {            System.out.println("2. outside its frame: " + e.getClass().getSimpleName());        }        driver.switchTo().frame("iframe1");        System.out.println("   fixed: " + email.getAttribute("type"));         driver.get("https://www.selenium.dev/selenium/web/blank.html");        try {            email.getAttribute("type");        } catch (NoSuchElementException e) {            System.out.println("3. after leaving the page: " + e.getClass().getSimpleName());        }        driver.quit();    }}
  1. The driver gives back a reference to this exact node.
  2. The page is rebuilt. The old node is gone, a new one with the same name takes its place.
  3. The fix: find it again.
  4. Found inside the frame.
  5. The reference is fine, but this context does not know it.
  6. The fix: switch back to the context where it was found.
  7. Leave the page completely.
  8. Go back to the page and find it again.

The run shows three different failures. After a refresh the id is still known, but its node has been removed from the page, so the driver reports stale element reference. Outside its frame, and after leaving the page, Chrome 153 reported no such element, because the id is looked up in a context that never stored it. The documentation groups all three under stale elements and gives the same fixes: find it again, or switch back to the right context first.

Logs: what the client sent and what the driver did

When an error makes no sense, look at the conversation itself. Two logs show it from both ends: the client log from your Selenium library, and the driver log from ChromeDriver.

Turn on the client log and see every command
ClientLog.java
import java.util.logging.Handler;import java.util.logging.Level;import java.util.logging.LogRecord;import java.util.logging.Logger;import java.util.logging.SimpleFormatter;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class ClientLog {    static final Logger HTTP = Logger.getLogger("org.openqa.selenium.remote.http.jdk.JdkHttpClient");     public static void main(String[] args) {        HTTP.setLevel(Level.FINE);        HTTP.addHandler(new Handler() {            public void publish(LogRecord r) {                String m = new SimpleFormatter().formatMessage(r);                if (m.startsWith("Executing request: ")) {                    String line = m.substring(19).replaceFirst("^\\((\\w+)\\)", "$1").replaceAll("/session/[0-9a-f]{32}", "/session/{id}");                    System.out.println(line.split(" \\{")[0]);                }            }            public void flush() {}            public void close() {}        });        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/blank.html");        driver.getTitle();        driver.quit();    }}
  1. Keep a reference, or Java may forget the level you set.
  2. Java logs at INFO by default. Request lines are written at FINE.
  3. A tiny handler that prints one line per request.
  4. The record holds a pattern plus values, so format it first.
  5. Hide the session id, which changes every run.
  6. Keep the method and path, drop the JSON body.

Common mistake
The documentation shows the JavaScript logger as getLogger("webdriver"). In selenium-webdriver 4.51 that name printed nothing in our run, while driver.http and driver.http.Executor printed every request. In pytest, the documentation adds that logs of passing tests are hidden unless you run pytest -s -p no:logging.
Ask ChromeDriver for its own log
DriverLog.java
import java.io.File;import java.nio.file.Files;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.chrome.ChromeDriverService;import org.openqa.selenium.chromium.ChromiumDriverLogLevel; public class DriverLog {    public static void main(String[] args) throws Exception {        File log = new File("chromedriver.log");        ChromeDriverService service = new ChromeDriverService.Builder()            .withLogFile(log)            .withLogLevel(ChromiumDriverLogLevel.DEBUG)            .build();        WebDriver driver = new ChromeDriver(service);        driver.get("https://www.selenium.dev/selenium/web/blank.html");        driver.quit();        for (String line : Files.readAllLines(log.toPath())) {            if (line.contains("] COMMAND ")) System.out.println(line.split("] COMMAND ")[1].split(" ")[0]);        }    }}

One idea, four depths

An error name tells you what kind of problem it is. Most failures are a locator, a missing wait, something covering the element, or a page that changed.

Match the error to its cause: no such element, stale, intercepted, not interactable, timeout. Find elements again after the page changes and switch back to the right context. Turn on logs when the cause is unclear.

The driver keeps an element store per browsing context. An id from another context is unknown there, and an id whose node left the document is stale. The client log shows each W3C request, the driver log shows each command the driver received.

The Grid adds its own logs per component, and BiDi can stream console messages and JavaScript errors from the page into the test, as chapter 6.2 shows.
