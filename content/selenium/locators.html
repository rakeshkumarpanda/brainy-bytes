The eight locator strategies

Before Selenium can click or type, it must find the element. A locator is the description you give it: "the input whose id is lname", "the first link that says Official". The documentation lists eight traditional strategies, all shown on its Contact Selenium example page, which this chapter uses too.

EightLocators.java
import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class EightLocators {    static void show(String how, WebElement e) {        System.out.println(how + " -> <" + e.getTagName() + "> " + e.getAttribute("value") + " " + e.getText());    }     public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/locators_tests/locators.html");        show("className", driver.findElement(By.className("information")));        show("cssSelector", driver.findElement(By.cssSelector("#fname")));        show("id", driver.findElement(By.id("lname")));        show("name", driver.findElement(By.name("newsletter")));        show("linkText", driver.findElement(By.linkText("Selenium Official Page")));        show("partialLinkText", driver.findElement(By.partialLinkText("Official")));        show("tagName", driver.findElement(By.tagName("a")));        show("xpath", driver.findElement(By.xpath("//input[@value='f']")));        driver.quit();    }}
  1. A helper that prints which element a locator found.
  2. The first element whose class list contains information.
  3. CSS: # means id, so the input with id fname.
  4. The element whose id attribute is lname.
  5. The element whose name attribute is newsletter.
  6. A link whose whole visible text matches.
  7. A link whose visible text contains Official.
  8. The first a element on the page.
  9. XPath: any input whose value attribute is f.

Only five reach the browser

The W3C protocol knows five strategies: css selector, link text, partial link text, tag name and xpath. So where do id, name and class name go? The binding turns them into CSS before sending. You saw it in chapter 1.2: Python sent [name="my-text"] for By.NAME. Python turns id into [id="lname"] and class name into .information.

Remember
find element (singular) returns the first match or raises no such element. find elements (plural) returns every match in page order, or an empty list. Chapter 3.2 covers the difference in detail.

CSS selectors and XPath

id and name only work when the page has them. For everything else you write a CSS selector or an XPath. Both describe a path through the page, in two different languages.

To findCSS selectorXPath
By id#fname//*[@id="fname"]
By class.information//*[contains(@class,"information")]
Tag with attributeinput[name="fname"]//input[@name="fname"]
Attribute starts witha[href^="https"]//a[starts-with(@href,"https")]
Attribute containsa[href*="selenium"]//a[contains(@href,"selenium")]
Direct childform > input//form/input
Any descendantform input//form//input
Second matching inputinput:nth-of-type(2)(//input)[2]
By visible textnot possible//label[text()="Last name:"]
The parentnot possible//input[@id="lname"]/..
Next siblinglabel + input//label[@for="lname"]/following-sibling::input[1]
Read a CSS selector from left to right
  1. form: start at a form element.
  2. >: go to its direct children only.
  3. input: keep the children that are inputs.
  4. [type="text"]: keep the ones whose type attribute is text.
  5. So form > input[type="text"] finds the First name and Last name boxes.

XPath has two forms. An absolute path starts at the root, such as /html/body/form/input[1]. It breaks as soon as anyone adds a div. A relative path starts with // and searches anywhere, such as //input[@name="fname"]. Use relative paths.

Open the playground, change any locator and run it. The element found is outlined on the page, and the log shows exactly what was sent to the driver.

Going deeper: How to test a selector before you use it

Open the page in Chrome, press F12 and go to the Console. document.querySelectorAll("form > input") lists what a CSS selector matches. $x("//label[text()='Last name:']") does the same for XPath. In the Elements panel, Ctrl+F also accepts both. If the browser finds it, Selenium will too, because the driver asks the same browser.

Relative locators

Selenium 4 added relative locators, first called friendly locators. They help when an element is hard to describe but easy to place: "the input below the Last name label". The documentation explains that Selenium uses the JavaScript function getBoundingClientRect() to learn the size and position of elements, then picks neighbours.

Relative.java
import static org.openqa.selenium.support.locators.RelativeLocator.with; import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class Relative {    static void show(String how, WebElement e) {        System.out.println(how + " -> " + e.getAttribute("outerHTML"));    }     public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/locators_tests/locators.html");        show("below last name label", driver.findElement(with(By.tagName("input")).below(By.cssSelector("label[for='lname']"))));        show("above lname", driver.findElement(with(By.tagName("input")).above(By.id("lname"))));        show("right of Male", driver.findElement(with(By.tagName("input")).toRightOf(By.cssSelector("input[value='m']"))));        show("below fname and above the checkbox", driver.findElement(with(By.tagName("input")).below(By.id("fname")).above(By.name("newsletter"))));        show("near Newsletter label", driver.findElement(with(By.tagName("input")).near(By.cssSelector("label[for='newsletter']"))));        driver.get("https://www.selenium.dev/selenium/web/login.html");        show("left of password", driver.findElement(with(By.tagName("input")).toLeftOf(By.id("password-field"))));        driver.quit();    }}

Look closely at the near line. You might expect the Newsletter checkbox, which sits right next to its label. The real run returned the Submit button. The relative locator code in the bindings explains why. near keeps every candidate whose box overlaps the anchor box grown by 50 pixels on each side, and both the checkbox and the button qualify. The candidates are then sorted by the distance between their centre and the centre of the anchor. The label text is wide, so its centre is closer to the Submit button underneath than to the checkbox at its right end. That is the honest lesson about relative locators: they depend on layout, so a different window size or a CSS change can change the answer. Use them when nothing better exists, and check what they return.

Common mistake
Each relative locator sends the page a script to run, so it is slower than a plain CSS selector. Prefer an id or a short CSS selector, and keep relative locators for elements with no good attributes.
Lesson 4 of 4

Choosing a good locator

A test is only as stable as its locators. The encouraged practices page of the documentation gives an order of preference.

From best to last resort
  1. A unique, stable id. Fast, short and clear. Preferred whenever the id is unique and predictable.
  2. A well written CSS selector. The preferred choice when there is no good id.
  3. XPath. Works as well as CSS and can match text, but the syntax is harder to debug and browsers do not tune it for speed.
  4. Link text and partial link text. Only work on links.
  5. Tag name. Dangerous for a single element, because pages have many of each tag. Useful with find elements.
Fragile locatorWhy it breaksBetter
/html/body/div[2]/form/input[3]Any new div or input shifts the path#lname
.btn.btn-primary.mt-3Styling classes change when the design changes[data-test="submit"]
//button[text()="Submit"]Breaks when the text is translated or rewordedAn id or a data attribute

Real world scenario: a test id agreement

A team keeps breaking tests whenever designers restyle buttons. They agree with the developers that every element a test touches gets a data-test attribute, such as data-test="checkout-pay". Tests use [data-test="checkout-pay"]. Designers can now change classes and text freely, and the tests keep passing.

In the exam
Keep locators in one place, apart from the steps that use them. The documentation recommends declaring them separately, which is exactly what a page object does. Chapter 5.2 shows the pattern.
One idea, four depths

A locator is directions to an element. Short, unique directions that do not depend on looks are the best.

id first, then CSS, then XPath. Avoid long absolute paths and styling classes. Relative locators help when an element has no good attribute.

id, name and class name compile to CSS in the bindings, so all of them run on the browser selector engine. Narrowing the scope, for example finding inside one form, cuts the work the browser does and the chance of a wrong match.

Locator stability is a contract between test and product code. Dedicated test attributes make that contract explicit and survive redesigns, translation and framework changes that rename generated ids.
