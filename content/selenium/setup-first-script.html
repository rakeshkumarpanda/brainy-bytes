Install Selenium for your language

Before any code runs you need two things on your machine: the Selenium library for your language and a browser. The third piece, the driver, is handled for you, as the next lesson shows.

JavaJava 11 (the jars are built for Java 11)A build tool. Add org.seleniumhq.selenium:selenium-java to Maven or Gradle.

The Selenium documentation points to the package pages for the current minimum, so check them when you upgrade. The versions above are what the 4.51.0 packages declare.

Java with Maven

The documentation shows the dependency for a Maven pom.xml. Maven downloads selenium-java and everything it needs when you build.

<dependency>
  <groupId>org.seleniumhq.selenium</groupId>

  <version>4.51.0</version>
</dependency>

With Gradle the same coordinates go in build.gradle as testImplementation 'org.seleniumhq.selenium:selenium-java:4.51.0'.

Use a virtual environment in Python and a package.json in JavaScript. Each project then pins its own Selenium version, so upgrading one project never breaks another.
Real world scenario: a new tester joins the team

Priya clones the test project on her first day. She runs mvn test, Maven reads the version from pom.xml and fetches selenium-java 4.51.0. She already has Chrome. She does not download chromedriver at all: the first test run asks Selenium Manager for it. Her setup takes minutes, and her machine runs the same Selenium version as everyone else.

Lesson 2 of 4

Selenium Manager finds the driver

Every browser needs its driver: chromedriver for Chrome, geckodriver for Firefox, msedgedriver for Edge. For years people downloaded the driver by hand and put it on the PATH. The documentation describes why that broke. Chrome is evergreen: it updates itself quietly. Your chromedriver 113 worked on Monday, Chrome updated to 115 on Tuesday, and every test failed with session not created: This version of ChromeDriver only supports Chrome version 113.

Since Selenium 4.6, every release ships Selenium Manager, the official driver manager. It is a small command line program written in Rust, built for Windows, Linux and macOS, and stored inside the library you installed. Your binding calls it only as a fallback, when you have not given a driver yourself.

Automated driver management, as the documentation lists it
  1. Browser version discovery. It runs a shell command such as google-chrome --version to learn which browser version is installed.
  2. Driver version discovery. It asks the browser vendor which driver version fits that browser.
  3. Driver download. It downloads the driver archive, unpacks it and stores it.
  4. Driver cache. Drivers live in ~/.cache/selenium. Next time the same driver is taken from there.

Since Selenium 4.11 it also manages browsers. If Chrome is missing, or you ask for a version you do not have through the browserVersion option, it downloads Chrome for Testing into the cache. Firefox followed in 4.12 and Edge in 4.14. Labels such as stable, beta, dev and canary work as versions too.

Common mistake
If you pass a driver path yourself, Selenium trusts you and never calls Selenium Manager. The documentation says that with Selenium 4.6 or newer you should not need to set a driver location at all. Delete old drivers from PATH and let Selenium Manager do the job.

Configuring it

Most people never configure Selenium Manager. When you must, for example behind a company proxy, there are three places, and the first one found wins:

  1. Command line argumentsWhat the binding passes, built from your browser options, such as --browser-version.
  2. se-config.tomlA file in the cache folder, for example proxy = "myproxy:8080".
  3. Environment variablesThe same key in capitals with SE_ in front, for example SE_PROXY or SE_OFFLINE.
SettingDefaultWhat it does
cache-path~/.cache/seleniumWhere drivers, browsers and metadata are stored
ttl3600 secondsHow long resolved versions are trusted before asking the vendor again
offlinefalseNo network requests or downloads at all
avoid-statsfalseSelenium Manager sends anonymous usage numbers to Plausible once a day. Set SE_AVOID_STATS=true to stop it.
proxynoneAn HTTP proxy for the downloads
Going deeper: Why Rust and why a separate program

The same driver logic is needed by five bindings. Writing it once as a separate program, compiled for each operating system, means Java, Python, JavaScript, C# and Ruby all behave the same way, and a fix lands in every language at once. Selenium Manager versions mirror Selenium: Selenium 4.51.0 ships Selenium Manager 0.4.51.

The eight steps of a first script

The documentation says that almost everything Selenium does is one of two things: send the browser a command, or ask it for information. A first script uses eight basic components, and you will recognise them in every test you ever read.

StepWhat it meansIn this example
1. Start the sessionCreate a driver. A browser opens.Chrome
2. Take action on the browserNavigate, go back, resize and so on.Open the web form
3. Request browser informationTitle, address, window handles, cookies.Read the title
4. Establish a waiting strategyMake sure an element is present before you look for it.Implicit wait of 500 ms
5. Find an elementMost commands are about elements.The text box and the button
6. Take action on an elementType, click, clear.Type Selenium, click Submit
7. Request element informationText, attributes, size, state.Read the message
8. End the sessionQuit the driver and close the browser.quit
The eight basic components of a Selenium script
FirstScript.java
import java.time.Duration;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class FirstScript {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/web-form.html");        String title = driver.getTitle();        System.out.println("Title: " + title);        driver.manage().timeouts().implicitlyWait(Duration.ofMillis(500));        WebElement textBox = driver.findElement(By.name("my-text"));        WebElement submitButton = driver.findElement(By.cssSelector("button"));        textBox.sendKeys("Selenium");        submitButton.click();        WebElement message = driver.findElement(By.id("message"));        String value = message.getText();        System.out.println("Message: " + value);        driver.quit();    }}
  1. Duration describes a length of time, used for the wait below.
  2. By holds the ways to locate an element: by name, by CSS selector and more.
  3. A WebElement is your handle on one element of the page.
  4. 1. Start the session. Chrome opens with a fresh profile.
  5. 2. Take action on the browser: go to the practice form.
  6. 3. Request browser information: the page title.
  7. 4. Establish a waiting strategy. Find calls will now retry for up to half a second.
  8. 5. Find an element: the text box whose name attribute is my-text.
  9. 5. Find another: the first button on the page.
  10. 6. Take action on an element: type into the box.
  11. 6. Click Submit. The browser loads the next page.
  12. Find the message on the new page. The implicit wait gives it time to appear.
  13. 7. Request element information: its visible text.
  14. 8. End the session. The browser and the driver both close.

Lesson 4 of 4

Always end the session

Step 8 is the one beginners forget. The documentation explains that quit ends the driver process, which by default closes the browser too, and that no more commands can be sent to that driver afterwards. If a test fails before it reaches quit, the browser and the driver keep running. Run a thousand failing tests and you have a thousand Chrome windows eating the memory of the build machine.

The fix is to put quit where it always runs: in a finally block, or in Python inside a with block, which quits for you.

Quit even when something fails
AlwaysQuit.java
import org.openqa.selenium.By;import org.openqa.selenium.NoSuchElementException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class AlwaysQuit {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        try {            driver.get("https://www.selenium.dev/selenium/web/web-form.html");            driver.findElement(By.id("no-such-id"));            System.out.println("never printed");        } catch (NoSuchElementException e) {            System.out.println("Failed: " + e.getMessage().split("\n")[0]);        } finally {            driver.quit();            System.out.println("Browser closed");        }    }}
  1. Start the session outside the try, so driver is known in finally.
  2. Everything that might fail goes inside try.
  3. This element does not exist, so this line throws.
  4. Java jumps straight to catch and never reaches this line.
  5. Catch the error so we can report it.
  6. Print only the first line of the message.
  7. finally runs whether the try worked or failed.
  8. So the browser always closes.
Real output from this run (Selenium 4.51.0 with Chrome 153)

main.py
from selenium import webdriverfrom selenium.common.exceptions import NoSuchElementExceptionfrom selenium.webdriver.common.by import By with webdriver.Chrome() as driver:    driver.get("https://www.selenium.dev/selenium/web/web-form.html")    try:        driver.find_element(By.ID, "no-such-id")        print("never printed")    except NoSuchElementException as e:        print("Failed:", e.msg.split("\n")[0])print("Browser closed")
  1. A with block calls driver.quit() for you when the block ends, even after an error.
  2. This element does not exist, so this line raises.
  3. Catch the error so we can report it.
  4. e.msg is the message from the driver. Keep its first line.
  5. We are outside the with block, so quit has already run.

main.js
const { Builder, Browser, By, error } = require('selenium-webdriver'); (async function alwaysQuit() {  const driver = await new Builder().forBrowser(Browser.CHROME).build();  try {    await driver.get('https://www.selenium.dev/selenium/web/web-form.html');    await driver.findElement(By.id('no-such-id'));    console.log('never printed');  } catch (e) {    if (!(e instanceof error.NoSuchElementError)) throw e;    console.log('Failed: ' + e.message.split('\n')[0]);  } finally {    await driver.quit();    console.log('Browser closed');  }})();
  1. error holds the exception classes.
  2. Everything that might fail goes inside try.
  3. This element does not exist, so the promise rejects.
  4. Only swallow the error we expected. Anything else is a real bug.
  5. finally runs whether the try worked or failed.
  6. So the browser always closes.

Remember
In a test framework the setup and teardown hooks do this job: start the driver before each test and quit it after each test, pass or fail. Chapter 5.1 shows the hooks in JUnit 5, pytest and Mocha.
One idea, four depths

Open the browser, do your steps, close the browser. Close it even if something goes wrong.

Wrap your steps in try and finally, or use Python with. quit sends Delete Session, the driver closes the browser, and the binding stops the driver process.

Driver processes and browser profiles are operating system resources. A suite that leaks them slows down and then fails with port or memory errors far from the real cause. One driver per test with guaranteed teardown keeps every test independent.

The binding owns the driver process through a Service object. quit both ends the W3C session and stops the service. A remote session on a Grid has no local service, so there quit only ends the session and the Grid frees the slot. Chapter 6.1 covers session timeouts that clean up after clients that never quit.
