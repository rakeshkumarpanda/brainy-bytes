Lesson 2 of 5

Predict the output

These questions show a few lines of code and ask what happens. Every answer below is what a real run printed in an earlier chapter, so you can trust it more than intuition.

Question 1. The pointer is moved to (8, 12) in the viewport, then moved by an offset of (13, 15). What does the page report?
  1. move to location sets an absolute point, so the pointer is at (8, 12).
  2. move by offset adds to where the pointer already is.
  3. 8 + 13 = 21 and 12 + 15 = 27, so the page printed 21, 27 (chapter 4.3).
Question 2
ActionChains(driver).key_down(Keys.SHIFT).send_keys("abc").key_up(Keys.SHIFT).send_keys("def").perform()
print(field.get_attribute("value"))
Question 2. What is printed?
  1. Shift is held while a, b and c are typed, so they arrive as capitals.
  2. Shift is released before d, e and f.
  3. The real run printed ABCdef (chapter 4.3).
Question 3
driver = webdriver.Chrome()
driver.add_cookie({"name": "k", "value": "v"})
Question 3. What happens?
  1. A new session sits on a blank page with no domain.
  2. A cookie belongs to a domain, so there is nothing to attach it to.
  3. The driver answers with the invalid cookie domain error. Navigate to the site first, then add the cookie (chapter 4.4).
Question 4. execute_script("return 7") is called in each language. What type comes back?
  1. The browser sends back a JSON number.
  2. Each binding maps it to its own type: Java gives a Long, Python an int and JavaScript a number.
  3. A decimal such as 7.5 comes back as a Double in Java and a float in Python (chapter 4.4).
Question 5
el = driver.find_element(By.ID, "my-text-id")
driver.refresh()
el.send_keys("hi")
Question 5. What happens on the last line?
  1. refresh builds a brand new document.
  2. The reference in el points to an element of the old document.
  3. The run raised StaleElementReferenceException. Find the element again after the refresh (chapter 5.4).
Question 6. A test switches into an iframe, then looks for a heading that is in the main page. What happens?
  1. After the switch, every find searches only inside the frame.
  2. The heading is not in the frame, so the search finds nothing.
  3. The real run raised NoSuchElementException. Switch back with default content first (chapters 4.2 and 5.4).
Question 7. A test asks for a cookie that does not exist. What comes back?
  1. Java returned null.
  2. Python returned None.
  3. JavaScript threw NoSuchCookieError. The same question has three answers, so know your binding (chapter 4.4).
Lesson 3 of 5

Find the bug

Each test below runs, but it is slow, flaky or wrong. Say the cause first, then the fix. The cause is what earns the marks.

Bug 1. A sleep before the click

driver.find_element(By.ID, "search").click()
time.sleep(5)
driver.find_element(By.CSS_SELECTOR, ".result").click()
Cause and fix
  1. Cause: the sleep always waits 5 seconds. When results come in 1 second it wastes 4. When they need 6 seconds the test still fails.
  2. Fix: wait for the condition you need, for example WebDriverWait(driver, 10).until(EC.element_to_be_clickable((By.CSS_SELECTOR, ".result"))).
  3. The explicit wait returns as soon as the condition holds, checking every 0.5 seconds in Python and Java (chapter 4.1).

Bug 2. Implicit and explicit waits together

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
new WebDriverWait(driver, Duration.ofSeconds(15)).until(ExpectedConditions.visibilityOfElementLocated(By.id("late")));
Cause and fix
  1. Cause: every check inside the explicit wait is a find that itself blocks for up to 10 seconds.
  2. With the numbers from the documentation the wait gave up after about 20.5 seconds, not 15.
  3. Fix: keep the implicit wait at 0 and use explicit waits only. The documentation says do not mix them (chapter 4.1).

Bug 3. A test that never closes its browser

driver = webdriver.Chrome()
driver.get(url)
assert driver.title == "Web form"
driver.quit()
Cause and fix
  1. Cause: when the assert fails, the line with quit never runs, so Chrome and the driver stay open.
  2. On a long run these leftovers fill the memory of the machine.
  3. Fix: quit in a finally block, or in the tear down of the test framework (chapters 1.3 and 5.1).

Bug 4. An absolute XPath

driver.find_element(By.XPATH, "/html/body/main/div[2]/form/div[1]/input")
Cause and fix
  1. Cause: the locator depends on six levels of page structure. Any change to any level breaks it.
  2. Fix: use the id or name if there is one, otherwise a short CSS selector tied to a stable attribute.
  3. Keep the locator in a page object so a change is fixed in one place (chapters 3.1 and 5.2).

Bug 5. Logging in through the form in every test

Cause and fix
  1. Cause: each test spends seconds typing a user name and password that are not what the test checks.
  2. Fix: get a session through an API or set the session cookie, then open the page under test.
  3. Keep one test that logs in through the form, because that form is a feature too (chapter 5.3).
Common mistake
A good bug answer has three parts: what the code really does, why that breaks, and a fix that removes the cause. A retry that hides the failure is not a fix.
Lesson 4 of 5

Design and sizing questions

Senior interviews and code reviews ask you to plan, not to recite. Answer with layers, numbers and reasons.

Question 1. Design a test framework for a shop

  1. TestsRead like a story: open the product, add to cart, check the total.
  2. Page objects and componentsOne class per page and per repeated part, holding the locators and the actions.
  3. Driver factoryBuilds a local or remote driver from configuration, with the options for each browser.
  4. SupportAPI helpers for set up, test data, a screenshot on failure, logs.

Say why each layer exists. Tests change when the behaviour changes. Page objects change when the page changes. The driver factory changes when the place you run changes, for example from a laptop to a Grid. Each change then touches one layer only.

Question 2. Size a Grid

Suite time on a GridExam favourite
total time = number of tests × average test timenumber of nodes
From the Grid documentation. Each node here runs one test at a time.
900 tests of 30 s must finish in 10 minutes. How many one slot nodes are needed?
  1. Rearrange the formula: nodes = tests × average time ÷ allowed time.
  2. The allowed time is 10 × 60 = 600 s.
  3. nodes = 900 × 30 ÷ 600 = 45
  4. The documentation suggests about one CPU and 1 GB of RAM per browser, so plan about 45 CPUs and 45 GB across the nodes (chapter 6.1).

Question 3. Triage a flaky suite

A suite fails a few different tests on each run. What do you do?
  1. Group the failures by error. no such element and stale element usually mean timing or a page that changed under the test.
  2. Read the screenshot and the logs of one failure from each group before changing code.
  3. Replace sleeps with explicit waits for the exact condition, and find elements again after the page changes.
  4. Make each test start from a fresh browser and its own data, so tests cannot affect each other.
  5. Track the failure rate after the fix. A retry may keep a release moving, but it does not count as the fix (chapters 5.3 and 5.4).
One idea, four depths

Selenium tests are small programs. Revise by predicting what they do, finding what is wrong, and planning how many machines they need.

Know the layers of a framework, the waits and the errors well enough to explain a failure from its message alone.

Size a Grid from the formula and the resources per browser, and read the queue size to scale it.

Compare WebDriver Classic, CDP and BiDi as protocols, and explain why events need a two way connection.
