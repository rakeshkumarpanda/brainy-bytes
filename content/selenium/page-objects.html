Page objects and page components

Keep locators, waits and page checks in one class per page, so tests read like user steps and a UI change is fixed in one place.

Lesson 1 of 3

Why page objects

A test that finds elements directly works fine on its own. The trouble starts at test number forty. The same By.cssSelector("button[type=submit]") is now copied into forty tests, and when the developers rename the button, forty tests break and forty places need the same fix.

The documentation describes a page object as an object oriented class that serves as an interface to a page of the application under test. Tests call its methods whenever they need the page. When the page changes, only the page object changes. The tests stay the same.

Without page objectsWith page objects
Locators are copied into every test that uses the pageEach locator is written once, inside the page object
A test reads as a list of clicks and CSS selectorsA test reads as what the user does: open the form, fill a field, submit
A UI change breaks many tests in many filesA UI change is fixed in one class
Waiting and page checks are repeatedThe page object waits for its page once, in its constructor
Real world scenario: the renamed button

A shop has 60 checkout tests. The design team changes the Pay button from an id to a data attribute. Without page objects the change touches 60 files and two of them are missed, so the nightly run is red for a day. With a CheckoutPage class, one line changes in one file and all 60 tests pass again on the next run.

Write page objects and components

Below are two page objects, WebFormPage and ReceivedPage, one page component, Field, and three tests. Open each file in the example and walk it line by line. The tests never mention a locator.

Two page objects, one component and three tests
pages/WebFormPage.java
package pages; import java.util.List;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver; public class WebFormPage {    static final String URL = "https://www.selenium.dev/selenium/web/web-form.html";    private final By fieldsBy = By.cssSelector("label.form-label");    private final By submitBy = By.cssSelector("button[type=submit]");    private final WebDriver driver;     public WebFormPage(WebDriver driver) {        this.driver = driver;        if (!"Web form".equals(driver.getTitle())) {            throw new IllegalStateException("This is not the web form, it is: " + driver.getTitle());        }    }     public static WebFormPage open(WebDriver driver) {        driver.get(URL);        return new WebFormPage(driver);    }     public List<Field> fields() {        return driver.findElements(fieldsBy).stream().map(Field::new).toList();    }     public Field field(String name) {        return fields().stream().filter(f -> f.name().equals(name)).findFirst()            .orElseThrow(() -> new IllegalArgumentException("No field called " + name));    }     public ReceivedPage submit() {        driver.findElement(submitBy).click();        return new ReceivedPage(driver);    }}
  1. Locators live here and nowhere else.
  2. The one check a page object should make: am I on the right page?
  3. Wrap every label element in a Field component.
pages/Field.java
package pages; import org.openqa.selenium.By;import org.openqa.selenium.WebElement; public class Field {    private final WebElement root;     public Field(WebElement root) { this.root = root; }     public String name() { return root.getText().split("\n")[0].trim(); }     private WebElement control() { return root.findElement(By.cssSelector("input, textarea, select")); }     public boolean isEnabled() { return control().isEnabled(); }     public Field fill(String text) {        control().clear();        control().sendKeys(text);        return this;    }}

pages/ReceivedPage.java

pages/web_form_page.py
from selenium.webdriver.common.by import By from pages.field import Fieldfrom pages.received_page import ReceivedPage  class WebFormPage:    URL = "https://www.selenium.dev/selenium/web/web-form.html"    FIELDS = (By.CSS_SELECTOR, "label.form-label")    SUBMIT = (By.CSS_SELECTOR, "button[type=submit]")     def __init__(self, driver):        self.driver = driver        if driver.title != "Web form":            raise ValueError("This is not the web form, it is: " + driver.title)     @classmethod    def open(cls, driver):        driver.get(cls.URL)        return cls(driver)     def fields(self):        return [Field(e) for e in self.driver.find_elements(*self.FIELDS)]     def field(self, name):        for f in self.fields():            if f.name() == name:                return f        raise LookupError("No field called " + name)     def submit(self):        self.driver.find_element(*self.SUBMIT).click()        return ReceivedPage(self.driver)

const { By } = require('selenium-webdriver');const { Field } = require('./field');const { ReceivedPage } = require('./received_page'); const URL = 'https://www.selenium.dev/selenium/web/web-form.html';const FIELDS = By.css('label.form-label');const SUBMIT = By.css('button[type=submit]'); class WebFormPage {  constructor(driver) { this.driver = driver; }   static async at(driver) {    const title = await driver.getTitle();    if (title !== 'Web form') throw new Error('This is not the web form, it is: ' + title);    return new WebFormPage(driver);  }   static async open(driver) {    await driver.get(URL);    return WebFormPage.at(driver);  }   async fields() {    return (await this.driver.findElements(FIELDS)).map(e => new Field(e));  }   async field(name) {    for (const f of await this.fields()) if ((await f.name()) === name) return f;    throw new Error('No field called ' + name);  }   async submit() {    await this.driver.findElement(SUBMIT).click();    return ReceivedPage.at(this.driver);  }} module.exports = { WebFormPage };

  2. A constructor cannot await, so an async factory does the page check.
  3. Wrap every label element in a Field component.
pages/field.js
const { By } = require('selenium-webdriver'); class Field {  constructor(root) { this.root = root; }   async name() { return (await this.root.getText()).split('\n')[0].trim(); }   control() { return this.root.findElement(By.css('input, textarea, select')); }   async isEnabled() { return (await this.control()).isEnabled(); }   async fill(text) {    const c = await this.control();    await c.clear();    await c.sendKeys(text);    return this;  }} module.exports = { Field };

Read the three tests against the rules from the documentation. The first test only calls methods that describe what a user does, and the assertion is in the test, not in the page object. The second test uses Field objects, each built around one label element, which is what the documentation calls a page component object. The third test opens the login page and asks for a web form page object, and the constructor refuses with an error.

Rule from the documentationWhere it shows in the example
The public methods represent the services the page offersfield, fields, submit, message
Try not to expose the internals of the pageLocators are private. Field.control() is private in Java
Generally do not make assertionsEvery assert is in the test file
The one allowed check: the right page is loadedThe constructors check the title, or wait for it after a navigation
Methods return other page objects, components or themselvessubmit() returns ReceivedPage, fill() returns the Field
A page object need not represent an entire pageField represents one labelled control
Remember
ReceivedPage waits for its title, while WebFormPage checks the title once. The web form is opened with get(), which returns after the page loads. The received page appears after a click, and chapter 3.3 showed that the next command can run before the new page is there.
Lesson 3 of 3

Design choices and the limits of page objects

Page objects are a pattern, not a library, so a team still makes choices. These are the ones that come up most often.

ChoiceWhat the documentation or practice suggests
Same action, different resultWrite two methods, for example loginAsValidUser and loginExpectingError, each returning the page that really follows
A part that appears on many pagesA component object such as a header, a menu or a product card, used inside page objects
Where waits goInside the page object, so tests do not repeat them
Base classShared code such as the driver field and a wait helper. Keep it small
PageFactory in JavaAn older helper that fills fields annotated with @FindBy. Plain By fields, as in the example, work in every language

A layer above page objects is a domain specific language: methods such as shop.buy("backpack") that hide whole user journeys. The documentation describes this as giving tests a language that business people can read. It sits on top of page objects and does not replace them.

One idea, four depths

A page object is a class for one page. Tests call its methods, so a change to the page is fixed in one place.

Locators and waits live in the page object, assertions live in the test. Methods that move to another page return that page object. Repeated parts become component objects.

The constructor checks that the right page is loaded, or waits for it after a navigation. Different results for the same action are modelled as different methods, as the documentation summary says.

On top of page objects, a domain layer gives business level steps. Components scope their searches to a root element, which also makes them reusable in lists, tables and repeated cards.
