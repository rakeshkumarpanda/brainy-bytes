Lesson 1 of 4

The pieces between your code and the browser

When you call click(), your code does not reach into Chrome and press the button. A message travels through three separate programs. Knowing them makes every error message later in this subject easy to read.

  1. Your testJava, Python or JavaScript code that calls the Selenium API.
  2. Language bindingThe Selenium library. The W3C spec calls it the local end.
  3. Driverchromedriver, geckodriver, msedgedriver or safaridriver. The remote end.
  4. BrowserDoes the real work and reports back.

The Selenium documentation describes the driver as the component responsible for delegating down to the browser, and handling communication to and from Selenium and the browser. That split is deliberate: browser vendors take responsibility for driving their own browser, and Selenium ties all the drivers together behind one interface.

Spec wordIn practiceExample
Local endThe client side, usually a language library on top of the protocolselenium for Python, selenium-java, selenium-webdriver for npm
Remote endThe server side that carries out the commandschromedriver, or Selenium Grid
Intermediary nodeA remote end that passes commands on to another remote endSelenium Grid, which forwards to a node
Endpoint nodeThe last remote end in the chain, built into or next to the browserchromedriver driving Chrome
Real world scenario: ordering in a restaurant

You tell the waiter "one masala dosa". The waiter writes it on a slip in a fixed format the kitchen understands, the kitchen cooks, and the waiter brings the plate back. You never enter the kitchen. Your code is the customer, the binding writes the slip, the driver is the kitchen pass that hands orders to the cook, and the browser is the cook. Whatever language you speak to the waiter, the slip looks the same.

Lesson 2 of 4

The W3C WebDriver protocol

The messages between the binding and the driver follow the W3C WebDriver specification. It is a plain HTTP protocol: each command is one HTTP request, and each answer is one HTTP response with a JSON body.

CommandMethodPathWhat you write in Python
New SessionPOST/sessionwebdriver.Chrome()
Delete SessionDELETE/session/{session id}driver.quit()
Navigate ToPOST/session/{id}/urldriver.get(url)
Get TitleGET/session/{id}/titledriver.title
Find ElementPOST/session/{id}/elementdriver.find_element(...)
Find ElementsPOST/session/{id}/elementsdriver.find_elements(...)
Element ClickPOST/session/{id}/element/{element id}/clickelement.click()
Element Send KeysPOST/session/{id}/element/{element id}/valueelement.send_keys(...)
Get Element TextGET/session/{id}/element/{element id}/textelement.text
Set TimeoutsPOST/session/{id}/timeoutsdriver.implicitly_wait(2)
Execute ScriptPOST/session/{id}/execute/syncdriver.execute_script(...)
Take ScreenshotGET/session/{id}/screenshotdriver.get_screenshot_as_png()

The shape of every answer

SuccessExam favourite
HTTP 200 and {"value": result}
The result is null for commands that only act, a string for text and titles, a list for Find Elements.
ErrorExam favourite
HTTP 4xx or 5xx and {"value": {"error", "message", "stacktrace"}}
error is a fixed code such as no such element. The binding turns it into an exception.
Element reference
{"element-6066-11e4-a52e-4f735466cecf": "f.C6…e.6"}
A web element travels as an object with this one fixed key. The value is an opaque id made by the driver.
Error codeHTTP statusPython exception you see
no such element404NoSuchElementException
stale element reference404StaleElementReferenceException
invalid session id404InvalidSessionIdException
element not interactable400ElementNotInteractableException
element click intercepted400ElementClickInterceptedException
invalid selector400InvalidSelectorException
timeout500TimeoutException
unexpected alert open500UnexpectedAlertPresentException
session not created500SessionNotCreatedException
Remember
The binding changes some locators before they leave your machine. The Python binding sends By.ID "x" as the CSS selector [id="x"], By.NAME as [name="x"] and By.CLASS_NAME as .x. Look for it in the log in the next lesson. That is why the W3C spec only needs five strategies: css selector, link text, partial link text, tag name and xpath.
Read one real request from the log
  1. The binding sent POST http://localhost:PORT/session/a443…/element.
  2. Its body was {"using": "css selector", "value": "[name="my-text"]"}, made from By.NAME, "my-text".
  3. chromedriver answered 200 with {"value": {"element-6066-11e4-a52e-4f735466cecf": "f.C6C4…e.6"}}.
  4. The binding wrapped that id in a WebElement object, so later calls such as send_keys know which element to name in their path.

See the wire for yourself

The best way to believe the protocol is simple is to drive Chrome without Selenium. The programs below start chromedriver, then send it the same requests a binding would, with nothing but the HTTP client of each language. They fill the web form and read the message on the next page. The output is what chromedriver really answered.

Remember
You will never write raw HTTP in real tests. The point is to see that nothing magic happens: Selenium is a polite HTTP client with good manners about waiting, errors and types. When a test fails with a strange message, picture the request that was sent and the error code that came back.
Going deeper: How chromedriver controls Chrome

The W3C spec only defines the HTTP side. How a driver controls its browser is up to the vendor. In the logged answer to New Session you can see goog:chromeOptions with a debuggerAddress: chromedriver connects to Chrome through its DevTools port. geckodriver uses the remote protocol built into Firefox, and safaridriver is built into macOS. This is why a driver version must match its browser: the inner protocol changes with each browser release.

Lesson 4 of 4

Local, remote and Grid, plus BiDi

The documentation shows three ways the pieces can be arranged. The protocol is the same in all of them, which is why moving a test from your laptop to a Grid changes one line.

LayoutWhere things runCode difference
DirectYour code, the driver and the browser on one machine.new ChromeDriver(), webdriver.Chrome()
RemoteYour code on one machine, driver and browser on another, reached through Selenium Server or RemoteWebDriver.new RemoteWebDriver(url, options), webdriver.Remote(url, options=...)
GridSelenium Grid receives the commands and relays them to the driver on a node machine.Same as remote, the URL points at the Grid

Why a second protocol, WebDriver BiDi?

Classic WebDriver is request and response: your code asks, the browser answers. The browser cannot start a conversation. That is fine for clicking and reading, but not for "tell me every time the page logs an error" or "tell me about every network request". WebDriver BiDi, a W3C standard made by the Selenium project and the browser vendors, adds a WebSocket connection so the browser can send events as they happen. Before BiDi, Selenium offered these features through the Chrome DevTools Protocol, which the docs call temporary until BiDi is implemented. Chapter 6.2 uses BiDi.

One idea, four depths

Your program sends small written orders to a helper program, and the helper makes the browser do them.

The binding sends HTTP requests with JSON bodies to a driver. Each command has a fixed method and path, and every answer has a value or an error code.

The W3C protocol is stateless HTTP with a session id in the path. Intermediary nodes such as Grid can route by that id without understanding the command. Capabilities in New Session negotiate the browser, version, platform and vendor extensions such as goog:chromeOptions.

BiDi moves automation to an event driven model over WebSocket, with modules such as browsingContext, script, network and log. It lets one client subscribe to browser events across tabs, which classic WebDriver could only approximate by polling.
