Lesson 1 of 3

The shape of a good browser test

The documentation starts its advice with a question: do you really need a browser for this? Browser tests are the most expensive tests you have. They need browsers, drivers and often a Grid, and they take seconds where a unit test takes milliseconds. Their strength is that they test the whole application, from the database to the screen, as a user sees it.

When a browser test is the right tool, the documentation says it should do three things, and keep each short: set up the data, perform a discrete set of actions, and evaluate the results. One or two operations are enough most of the time.

The documentation tells the story of Larry's unicorn shop: create an account, configure a unicorn, add it to the cart, check out and pay, give feedback. The temptation is one grand script for the whole journey. The documentation says to resist it, because such a test is slow, more exposed to timing problems, and when it fails it does not tell you at a glance what broke. Break it into small independent tests, each with one reason to exist.

Testing typeQuestion it answersSelenium fits?
AcceptanceAre we building the right product?Yes, by simulating what the user expects
FunctionalAre we building the product right?Yes
IntegrationDo the modules work together, for example order plus payment?Yes, for flows through the UI
SystemDoes the whole product work end to end, in an environment like production?Yes, a few journeys
Performance (load and stress)How fast is it, and does it survive a peak?Not as the measuring tool. The documentation points to tools such as JMeter
RegressionDid a change break what worked?Yes, by running the existing tests again
Lesson 2 of 3

Encouraged practices

These practices come from the encouraged behaviours section of the documentation. The first two are shown with real runs.

Fresh browser per test. Start each test from a clean, known state. The documentation notes that drivers such as ChromeDriver and GeckoDriver start with a new user profile by default. The run below proves it: the second browser sees none of the cookie or storage the first one left.

A new driver starts with a clean profile
FreshBrowser.java
import org.openqa.selenium.Cookie;import org.openqa.selenium.JavascriptExecutor;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class FreshBrowser {    static final String PAGE = "https://www.selenium.dev/selenium/web/blank.html";     public static void main(String[] args) {        WebDriver first = new ChromeDriver();        first.get(PAGE);        first.manage().addCookie(new Cookie("cart", "3 items"));        ((JavascriptExecutor) first).executeScript("localStorage.setItem('theme', 'dark')");        System.out.println("first browser: " + first.manage().getCookies().size() + " cookie, storage " + ((JavascriptExecutor) first).executeScript("return localStorage.length"));        first.quit();         WebDriver second = new ChromeDriver();        second.get(PAGE);        System.out.println("second browser: " + second.manage().getCookies().size() + " cookies, storage " + ((JavascriptExecutor) second).executeScript("return localStorage.length"));        second.quit();    }}
  1. State a first test leaves behind: a cookie
  2. and a value in local storage.
  3. A new driver gets a new, empty profile by default.
Real output from this run (Selenium 4.51.0 with Chrome 153)
first browser: 1 cookie, storage 1
second browser: 0 cookies, storage 0

Generate application state. Selenium should not be used to prepare a test case. Logging in through the form before every test is slow and adds a place to fail. The documentation suggests creating a method that logs in through an API and sets a cookie. Here the session cookie is set directly and the page under test reads it on load.

Prepare the state without clicking through the user interface
AppState.java
import org.openqa.selenium.By;import org.openqa.selenium.Cookie;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class AppState {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        String session = "abc123";        driver.get("https://www.selenium.dev/selenium/web/blank.html");        driver.manage().addCookie(new Cookie("session", session));        driver.get("https://www.selenium.dev/selenium/web/cookies.html");        System.out.println("page shows: " + driver.findElement(By.id("result")).getText());        driver.quit();    }}
  1. In a real suite this value comes from a login API call, not from the login form.
  2. A small page on the domain, only to be allowed to set the cookie.
  3. Now open the page under test. It reads its cookies on load.

PracticeWhat the documentation says
Avoid sharing stateDo not share test data, clean up stale data, and create a new WebDriver per test
Test independencyWrite each test as its own unit, not relying on another test to complete
Mock external servicesRemoving dependencies on external services improves speed and stability
Improved reportingSelenium does not report. Use the reports of your test framework, such as xUnit XML or HTML
LocatorsUnique ids first, then a well written CSS selector. XPath is flexible but harder to debug and often slower
Page objects and a fluent APIChapter 5.2. Methods can return the page for chained calls
Domain specific languageBusiness level methods on top of page objects
Real world scenario: one order, two tests

Two tests each query the database for a valid order and act on the first one they find. On a busy night both pick order 1042, one cancels it, and the other fails because the order is gone. The fix from the documentation: each test creates its own order through the API and cleans it up afterwards.

Things to avoid

The documentation also lists jobs that Selenium can technically do but should not, with what to do instead.

AvoidWhyDo instead
CAPTCHAsThey are built to stop automationDisable them in the test environment, or add a hook that lets tests bypass them
File downloadsThe API does not expose download progressFind the link with Selenium and fetch it with an HTTP library such as curl, using any cookies it needs
HTTP status codesWebDriver acts like a user, and a status code is rarely the useful detail of a failureCheck what the user sees, such as an error page. Chapter 6.2 shows BiDi network events if you really need codes
Logging in to Gmail or FacebookAgainst their terms, slow and unreliableUse the APIs or test account tools they provide
Test dependencyTests must run in any orderMake each test set up its own state
Performance testingBrowser start, servers and third parties add noise to every numberUse performance tools, and keep Selenium for function
Link spideringA browser takes seconds per pageUse curl or a library such as BeautifulSoup
Two factor authenticationAutomating it is hard and less secureA test only token, or 2FA turned off for test users, test IPs or the test environment
Remember
Every row has the same shape: Selenium is a tool for what a user does in a browser. When the job is not that, a lighter tool is faster and more reliable.
One idea, four depths

Use a browser test only when you need one, keep it short, start it clean, and do not make Selenium do jobs other tools do better.

Each test sets up its data, performs a few actions and checks the result. Fresh browser per test, no shared data, state prepared through APIs and cookies, reports from the framework.

The encouraged and discouraged lists in the documentation all serve two goals: tests that are independent, so they can run in any order and in parallel, and tests that fail for one clear reason.

Large suites add test data factories, service mocks at the network edge, contract tests for APIs and a small set of end to end browser journeys on top of many fast lower level tests.
