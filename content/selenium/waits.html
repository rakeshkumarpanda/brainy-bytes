The race between your code and the page

The documentation calls synchronisation perhaps the most common challenge in browser automation. Your code and the page run at the same time. Sometimes the page is ready first and the test passes. Sometimes Selenium is first and the test fails. A test that passes and fails on the same code is a flaky test, and this race is one of their main causes.

Navigation commands already wait for the page load strategy. But that only covers the HTML and its assets. Content that JavaScript adds or shows later, such as search results, a spinner that goes away or a dialog that slides in, is not covered. The documentation example is the dynamic.html page: Add a box! creates a red box and Reveal a new input shows a hidden input, each about a second after the click.

The race: look for the box straight after the click
Race.java
import org.openqa.selenium.By;import org.openqa.selenium.NoSuchElementException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.chrome.ChromeDriver; public class Race {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/dynamic.html");        driver.findElement(By.id("adder")).click();        try {            driver.findElement(By.id("box0"));            System.out.println("found the box");        } catch (NoSuchElementException e) {            System.out.println("too early: no such element");        }        driver.quit();    }}
  1. The page adds a red box, but only 1 second after the click.
  2. Our code asks at once. No wait is set, so the driver checks only once.
  3. Selenium was faster than the page.

The first idea most people have is to sleep for a few seconds. The documentation explains why that is poor: too short and it still fails on a slow day, too long and every test pays the full sleep every time. Selenium gives two better tools: implicit waits and explicit waits.

Lesson 2 of 4

Implicit waits

An implicit wait is a session setting. Once set, every find element call keeps looking for up to that long before it raises no such element. It is set with the timeouts capability or a driver method, and its default is 0.

Implicit wait: every find keeps looking
Implicit.java
import java.time.Duration;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver; public class Implicit {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(2));        driver.get("https://www.selenium.dev/selenium/web/dynamic.html");        driver.findElement(By.id("adder")).click();        long start = System.nanoTime();        WebElement box = driver.findElement(By.id("box0"));        double seconds = (System.nanoTime() - start) / 1e9;        System.out.println("found " + box.getAttribute("class") + " after about " + Math.round(seconds) + " s");        driver.quit();    }}
  1. For the whole session: a find may keep looking for up to 2 seconds.
  2. Not there yet, so the driver keeps checking until the box appears.
  3. Returns as soon as it is found, not after the full 2 seconds.

Explicit waits and expected conditions

An explicit wait is a loop in your code. It checks a condition, sleeps for a polling interval, and checks again, until the condition is true or the timeout passes. Because you choose the condition, you can wait for exactly what the next step needs. The documentation adds that the wait class handles no such element for you while it loops.

One explicit wait, step by step
  1. Create the wait with a timeout, for example 2 seconds.
  2. Call until with a condition: a lambda, a function, or a ready made expected condition.
  3. The wait calls the condition. If the result is true, or an element, it returns it to you.
  4. If the result is false, or an ignored error was raised, it looks at the clock. Past the timeout, it raises a timeout error with your message.
  5. Otherwise it sleeps for the polling interval and tries again.
Explicit wait: wait for exactly the condition you need
Explicit.java
import java.time.Duration;import org.openqa.selenium.By;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.support.ui.WebDriverWait; public class Explicit {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/dynamic.html");        WebElement revealed = driver.findElement(By.id("revealed"));        driver.findElement(By.id("reveal")).click();        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(2));        wait.until(d -> revealed.isDisplayed());        revealed.sendKeys("Displayed");        System.out.println("typed: " + revealed.getDomProperty("value"));        driver.quit();    }}
  1. The input is in the page already, just hidden.
  2. The page shows it 1 second later.
  3. Wait at most 2 seconds. Java checks every 500 ms.
  4. A lambda: keep calling it until it returns true.
  5. Safe now: the input is displayed, so it can take keys.

Expected conditions

Expected conditions are ready made conditions for the common cases: an element exists, is visible, is clickable or has gone stale, some text is present, or the title contains a value. Java has ExpectedConditions, Python has expected_conditions (usually imported as EC) and JavaScript has until.

Ready made conditions, and what a timeout looks like
Conditions.java
import java.time.Duration;import org.openqa.selenium.By;import org.openqa.selenium.TimeoutException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.support.ui.ExpectedConditions;import org.openqa.selenium.support.ui.WebDriverWait; public class Conditions {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/dynamic.html");        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(2));        driver.findElement(By.id("adder")).click();        WebElement box = wait.until(ExpectedConditions.presenceOfElementLocated(By.id("box0")));        System.out.println("present: " + box.getAttribute("id"));        driver.findElement(By.id("reveal")).click();        WebElement input = wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("revealed")));        System.out.println("visible: " + input.isDisplayed());        try {            new WebDriverWait(driver, Duration.ofSeconds(1)).withMessage("the second box never came")                .until(ExpectedConditions.presenceOfElementLocated(By.id("box1")));        } catch (TimeoutException e) {            System.out.println("TimeoutException: " + e.getMessage().split("\n")[0]);        }        driver.quit();    }}
  1. A ready made condition. It returns the element it waited for.
  2. Present is not enough for typing. Wait until it is visible.
  3. Our own message makes the failure readable.
  4. Nobody clicked again, so box1 never appears.

Customising waits, and never mixing them

The wait class takes extra settings: how often to poll, which errors mean "not yet", the total timeout and the message on failure. The documentation example retries an action that raises element not interactable until it works.

A customised wait: poll faster and retry on an error
Fluent.java
import java.time.Duration;import org.openqa.selenium.By;import org.openqa.selenium.ElementNotInteractableException;import org.openqa.selenium.WebDriver;import org.openqa.selenium.WebElement;import org.openqa.selenium.chrome.ChromeDriver;import org.openqa.selenium.support.ui.FluentWait;import org.openqa.selenium.support.ui.Wait; public class Fluent {    public static void main(String[] args) {        WebDriver driver = new ChromeDriver();        driver.get("https://www.selenium.dev/selenium/web/dynamic.html");        WebElement revealed = driver.findElement(By.id("revealed"));        driver.findElement(By.id("reveal")).click();        Wait<WebDriver> wait = new FluentWait<WebDriver>(driver)            .withTimeout(Duration.ofSeconds(2))            .pollingEvery(Duration.ofMillis(300))            .ignoring(ElementNotInteractableException.class);        wait.until(d -> {            revealed.sendKeys("Displayed");            return true;        });        System.out.println("typed: " + revealed.getDomProperty("value"));        driver.quit();    }}
  1. FluentWait lets you set every part of the loop.
  2. Give up after 2 seconds.
  3. Check every 300 ms instead of 500.
  4. Treat this error as not yet and try again.
  5. The condition does the action itself and returns true when it worked.

Do not mix implicit and explicit waits

The documentation is direct: do not mix them, because the wait times become unpredictable. Its example is an implicit wait of 10 seconds with an explicit wait of 15 seconds, which can time out after 20 seconds. The reason is that each check of the explicit wait calls find element, and find element now blocks for the implicit wait every time the element is missing.

Proof: mixing implicit and explicit waits stretches the timeout
Python only, because the timing rule is the same in every binding. The documentation warns that 10 s implicit plus 15 s explicit can time out after 20 s. Here smaller numbers make the run short.
main.py
import time from selenium import webdriverfrom selenium.common.exceptions import TimeoutExceptionfrom selenium.webdriver.common.by import Byfrom selenium.webdriver.support import expected_conditions as ECfrom selenium.webdriver.support.wait import WebDriverWait driver = webdriver.Chrome()driver.get("https://www.selenium.dev/selenium/web/dynamic.html")driver.implicitly_wait(2)start = time.monotonic()try:    WebDriverWait(driver, 3).until(EC.presence_of_element_located((By.ID, "box9")))except TimeoutException:    print(f"gave up after {time.monotonic() - start:.1f} s, not 3 s")driver.quit()
  1. Implicit wait: each find may block for 2 seconds.
  2. Explicit wait of 3 seconds for an element that never comes.
  3. Each check inside the explicit wait blocked 2 seconds on the implicit wait.
Real output from this run (Selenium 4.51.0 with Chrome 153)
gave up after 4.6 s, not 3 s

Three seconds were asked for, and the run gave up after more than four. With the documentation numbers the effect grows to many seconds per failing test. Pick one strategy for a project. Most teams keep the implicit wait at 0 and use explicit waits where they are needed.

Real world scenario: the suite that took an hour longer

A team set a 10 second implicit wait "to be safe", and their page objects also used 15 second explicit waits. Most tests passed, so nobody noticed. On a day when the login service was down, every one of 300 tests waited about 20 seconds per failed check instead of 15. The run that normally took 20 minutes ran past the CI limit. Removing the implicit wait made failures fast again.

One idea, four depths

Do not guess with sleep. Tell Selenium what you are waiting for and let it check again and again until it happens.

An implicit wait makes every find patient. An explicit wait loops over a condition you choose, with a timeout and a polling interval. Use one or the other, not both.

Explicit waits run in the client and send a command per poll. Implicit waits run in the driver inside one Find Element command. Combining them nests one loop inside the other, so the worst case is roughly the explicit timeout plus one whole implicit wait.

Polling trades speed of reaction against commands sent. WebDriver BiDi lets a client subscribe to DOM mutations and network events instead, so future waits can react to the page instead of asking it repeatedly.
