Lesson 1 of 13

Step 1: frame the problem before any code

Source: CRISP-DM 1.0 (2000), Geron, Hands-On Machine Learning chapter 2, Zinkevich, Rules of Machine Learning, and the scikit-learn 1.8 user guide.

What it is
Framing means writing down, in plain words, what decision the model will help with, what exactly it predicts, how we will measure success, and what simple rule it must beat.
Why we need it
The most common reason ML projects fail is not a weak model. It is solving the wrong problem, measuring the wrong thing, or building a model nobody can use. Ten minutes of framing saves months.
How it works
Answer six questions: What is the business goal? What is the output (number, category, ranking)? What data exists at the moment we must predict? Which metric shows success? What is the simplest baseline? How will the prediction be used?
Real world scenario: the delivery time on your food app

When you order food, the app says "arrives in 32 minutes". Before any model, the team agreed: the output is minutes, the data is past orders, the metric is the average error in minutes, and "3 minutes per km plus 10" is the baseline to beat. They also agreed the model may only use facts known when you press Order. The rider’s real route is not known yet, so it cannot be a feature.

Remember
Ask "do we even need ML?" first. If a simple rule or a lookup table is good enough, ship that. Google’s Rules of ML put it as rule number one: do not be afraid to launch a product without machine learning.

Step 4: train, validation and test sets

What it is
We cut the data into a training set (to learn parameters), a validation set (to compare models and settings) and a test set (one final honest score).
Why we need it
A model always looks good on the data it learned from. We need data it has never seen to know how it will do for real users. If we also chose settings using the test set, the test set would stop being "unseen".
How it works
Shuffle, then cut, for example 60 / 20 / 20 or 70 / 15 / 15. With a rare class, stratify so every part keeps the same class share. With time data, do not shuffle: train on the past and test on the most recent period.

Lesson 5 of 13

Step 5: always start with a baseline

What it is
A baseline is the score of a very simple method: always predict the average, always predict the most common class, or a one line rule from common sense.
Why we need it
Without a baseline a number like "error 6.2" means nothing. If the baseline gets 6.5, the fancy model barely helps. If it gets 15, the model is a big win.
How it works
scikit-learn has DummyRegressor and DummyClassifier for this. Train them like any model, then compare every real model against them on the same validation data.
Download this program (.py)Save it, open it in any editor and run it with python3 baseline_first.py.
Common mistake
A model that cannot beat the baseline usually means a bug, leakage the other way, or features that carry no signal. Check the data before trying a bigger model.
Lesson 6 of 13

Step 6 and 7: train, look at errors, improve

Training is a loop of its own: train a model, measure it on the validation set, study the mistakes, change one thing, and repeat. Looking at where the model fails tells you what to try next far better than guessing.

Download this program (.py)Save it, open it in any editor and run it with python3 error_analysis.py.
How an expert reads errors
  1. Sort validation examples by error, largest first, and read the worst 20.
  2. Group them: are they all at night, in rain, from one city, from one data source?
  3. Ask what information would have helped a person guess right in those cases.
  4. Add that information as a feature, collect more data of that kind, or fix wrong labels.
  5. Retrain and compare on the same validation set. Keep a written log of every try.
Remember
Change one thing at a time and keep notes. If you change the features, the model and the settings together, you never learn which change helped.
Lesson 7 of 13

The silent killer: data leakage

What it is
Data leakage happens when information that would not be available at prediction time sneaks into training. The model looks brilliant in testing and fails in real use.
Why we need it
Leakage produces false confidence. Teams ship a model with "99% accuracy" that falls to a coin flip on real users, which costs money and trust.
How it works
Ask for every feature: "Would I know this value at the exact moment I make the prediction?" Also fit every preprocessing step (scaling, filling missing values) on the training set only, then apply it to validation and test.

After launch, the world keeps changing. Prices rise, new cities open, user habits shift. When the data a model sees drifts away from the data it learned from, its accuracy drops quietly. The maths of splitting and testing

Split sizes
ntrain = n − nval − ntest, with ntest = round(n × test share)
For n = 1,000 with 20% test and 20% validation: 600, 200, 200.
Uncertainty of a test accuracyExam favourite
SE = √(p(1 − p) / n)
p is the measured accuracy, n the number of test examples. Smaller n means a shakier score.
Rough 95% rangeExam favourite
p ± 2 × SE
With p = 0.9 and n = 100: SE = 0.03, so the true accuracy is likely between 0.84 and 0.96.
Test size for a target precision
n ≈ 4 p(1 − p) / m2
m is the half width you want. For p = 0.9 and m = 0.02, n ≈ 900.
Mean absolute errorExam favourite
MAE = (1/n) Σ |yi − ŷi|
The average size of the mistakes, in the same unit as y.
Worked example: is model B really better?
  1. Model A: 85% accuracy on 200 test examples. Model B: 88% on the same 200.
  2. SE for A = √(0.85 × 0.15 / 200) = √0.0006375 ≈ 0.025.
  3. So A’s 95% range is about 0.80 to 0.90. B’s 0.88 is inside it.
  4. The 3 point gap is within the noise of 200 examples
  5. To be sure, use more test data or a paired test (McNemar) on the examples where A and B disagree. Cross validation (Supervised 4.2) also helps.
Going deeper: Why the test set must be used once

Every time you look at the test score and then change the model, you leak a little information from the test set into your choices. After many rounds you have "fit" the test set, and its score is too optimistic. This is called adaptive overfitting. Kaggle competitions show it clearly: the public leaderboard score is often higher than the hidden private score. Keep a validation set (or cross validation) for choices and touch the test set once.

From beginner to expert

One idea, four depths

An ML project starts with a clear question, gathers data, keeps some data aside for testing, tries a simple method first, then a real model, and keeps checking it after launch.

Frame the output and metric, explore and clean on training data, split into train, validation and test (stratified or by time when needed), beat a baseline, study errors, avoid leakage, deploy as batch or online, monitor for drift.

Choose the split to match how the model is used (random, grouped, time based). Quantify uncertainty of scores with standard errors or the bootstrap, compare models with paired tests, and build every preprocessing step into a pipeline fitted on training folds only.

Research on adaptive data analysis (Dwork and others, 2015) shows that reusing a holdout set for many decisions breaks its guarantees, and methods such as the reusable holdout limit what each query reveals. Production systems face distribution shift (covariate, label and concept shift), studied under domain adaptation, with tools such as importance weighting and drift detection tests.

Beginner
List the nine stages of a project and explain why we keep a test set.
Intermediate
Frame a real problem, build stratified and time based splits, beat a baseline, and spot leakage.
Expert
Put error bars on scores, choose splits that match deployment, and design monitoring for drift.

Chapter summary

  1. Frame first: goal, output, data available at prediction time, metric, success level and baseline.
  2. The project loop: frame, get data, explore and clean, split, baseline, train and tune, evaluate, deploy, monitor. CRISP-DM describes the same loop.
  3. Split into train (learn), validation (choose) and test (final score, used once). Stratify rare classes, split time data by time, keep groups together.
  4. Always compare against a baseline such as DummyRegressor or DummyClassifier.
  5. Study errors to decide what to try next, and change one thing at a time.
  6. Leakage means training on information not available at prediction time. Fit preprocessing on training data only.
  7. Deploy as batch, online API, on device or streaming, then monitor for drift and retrain.
  8. A test score is uncertain: SE = √(p(1 − p)/n).
