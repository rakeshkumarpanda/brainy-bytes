All or nothing: transactions and ACID

Moving 300 rupees from Asha to Ravi takes two UPDATEs. If the power fails between them, money vanishes. A transaction groups statements so they succeed together or not at all.

Remember
Without BEGIN, each statement is its own transaction (autocommit). Many small INSERTs inside one BEGIN ... COMMIT also run far faster, because the engine syncs to disk once instead of once per row.
Lesson 2 of 5

Errors, savepoints and failed transfers

When a statement inside a transaction fails, you decide: roll back everything, or go back to a savepoint and carry on.

What an app does around a transaction
  1. BEGIN.
  2. Run each statement and check for an error.
  3. On any error, ROLLBACK and report the problem.
  4. If every statement worked, COMMIT. Most database libraries wrap this in a "with transaction" block.
Common mistake
In SQLite a failed statement inside a transaction undoes only that statement by default. The transaction stays open, and it is the program’s job to ROLLBACK. PostgreSQL marks the whole transaction as failed until you ROLLBACK.

Isolation levels and anomalies

Many users run transactions at the same time. Full isolation is expensive, so the SQL standard defines four isolation levels, each preventing more anomalies.

Locks, MVCC, deadlocks and the journal

How do engines keep the promises? Two main tools: locks, which make others wait, and MVCC (multi version concurrency control), which lets readers see an older version while a writer works.

ToolHow it worksUsed by
Row locksa writer locks the rows it changes until commit, other writers waitPostgreSQL, MySQL InnoDB, SQL Server, Oracle
MVCCeach change creates a new row version, readers see the versions committed before they startedPostgreSQL, Oracle, InnoDB, SQL Server snapshot isolation
Database lockone writer for the whole database at a timeSQLite
Write ahead logchanges go to a log first, so a crash can replay or undo themalmost every engine, SQLite in WAL mode
A deadlock
  1. Transaction 1 locks Asha’s row, then asks for Ravi’s.
  2. Transaction 2 locked Ravi’s row first, and now asks for Asha’s.
  3. Each waits for the other forever.
  4. The engine detects the cycle and aborts one of them with a deadlock error. The app should retry it.
  5. Prevention: always lock rows in the same order, for example by account id.
Real world scenario: booking the last train seat

Two people press Book on the last seat at the same moment. With SELECT ... FOR UPDATE on the seat row (PostgreSQL, MySQL), the second request waits until the first commits, then sees the seat is taken and gets a polite "sold out". Without a lock, both could read "free" and both get tickets for the same seat, a classic race condition.

Lesson 5 of 5

From intuition to research

One idea, four depths

A transaction is all or nothing. COMMIT keeps the changes, ROLLBACK throws them away.

ACID, isolation levels and their anomalies, autocommit, savepoints. Use atomic UPDATEs or row locks to avoid lost updates, and retry on deadlock or serialization errors.

Serializability means the result equals some one at a time order. Two phase locking guarantees it with locks. Snapshot isolation, used by many MVCC engines, still allows write skew (Berenson et al., 1995), and PostgreSQL’s SERIALIZABLE adds Serializable Snapshot Isolation to catch it (Cahill et al., 2008).

Distributed transactions across machines use two phase commit, and consensus protocols such as Paxos and Raft replicate the log. Systems such as Google Spanner (2012) use synchronized clocks to give global ordering, and CockroachDB and TiDB follow similar ideas.

Going deeper: Where ACID came from

Jim Gray described the transaction concept in 1981, and Theo Haerder and Andreas Reuter named the four properties ACID in 1983. Gray received the Turing Award in 1998 largely for this work.
