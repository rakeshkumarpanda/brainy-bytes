Why queries slow down, and what an index is

With 10 products any query is instant. With 10 million, a query that reads every row, a full table scan, can take seconds. An index is a separate, sorted copy of one or more columns, each entry pointing at its row. It works like the index at the back of a textbook: look up a word, jump to the page.

RowsFull scan readsIndex search reads about
1,0001,000 rows10 comparisons
1,000,0001,000,000 rows20 comparisons
1,000,000,0001,000,000,000 rows30 comparisons
Remember
The numbers in the right column are log₂ of the row count, the steps of a binary search. Real B-tree indexes need even fewer disk reads, because each page holds hundreds of keys.
Lesson 2 of 5

Inside an index: the B-tree

Almost every relational engine stores indexes as B-trees (Rudolf Bayer and Edward McCreight, 1972), usually the B+tree variant. In SQLite, tables themselves are B-trees too, keyed by rowid.

How a B+tree finds price 850
  1. The root page holds a few separator keys, for example 200 and 700, splitting prices into three ranges.
  2. 850 is above 700, so follow the third pointer to an internal page for that range.
  3. Repeat until a leaf page, which holds the actual keys in order, each with the rowid of its row.
  4. Read the row by rowid. Leaves are linked in order, so a range such as price BETWEEN 800 AND 1500 walks along the leaves.
  5. depth ≈ log_fanout(rows): with 300 keys per page, 3 levels cover 27 million rows
PropertyWhy it matters
Always balancedevery leaf is at the same depth, so every lookup costs the same
Wide pages (thousands of bytes)few levels, so few disk reads
Sorted leaves linked togetherfast ranges, ORDER BY and MIN or MAX without sorting
Updated on every writeinserts may split pages, which costs time
Going deeper: Why not a binary tree

A binary tree node holds one key, so a million keys need about 20 levels, each possibly a separate disk read. A B-tree page holds hundreds of keys, so the same million fit in 3 levels. Disks and SSDs read whole pages at a time, so wide nodes waste nothing.

Unique, composite, covering, partial and expression indexes

One column is only the start. The shape of an index decides which queries it can help.

KindExampleHelps
UniqueCREATE UNIQUE INDEX ... ON customers(email)lookups, and refuses duplicates. UNIQUE and PRIMARY KEY create one for you
CompositeON orders(customer_id, order_date)filters on customer_id, or on customer_id and order_date, in that order
CoveringON products(category, price, name)queries that need only these columns never touch the table
PartialON products(name) WHERE stock = 0a small index for one common filter
ExpressionON customers(lower(email))WHERE lower(email) = ...
Remember
Think of a composite index like a phone book sorted by surname, then first name. You can find every Sharma, or Priya Sharma, but not every Priya.

When indexes do not help, and what they cost

An index is not free, and the planner does not always use it.

SituationWhy the index is skipped
A function on the column: WHERE upper(name) = ...the index is sorted by name, not upper(name). Use an expression index
Leading wildcard: LIKE '%box'sorted order cannot find words by their ending
Only a later column of a composite indexleftmost prefix rule
A tiny table, or a filter matching most rowsreading everything is cheaper than jumping around
Different types: comparing a TEXT column with a numberconversions can stop the index matching
CostDetails
Slower writesevery INSERT, UPDATE of an indexed column and DELETE must update every index too
Disk and memoryeach index is another B-tree, often a big share of the database size
Planner workmore choices to consider, and occasionally a wrong one
Maintenancestatistics go stale. ANALYZE refreshes them, PostgreSQL also needs VACUUM
A sensible indexing routine
  1. Find the slow or frequent queries from logs or monitoring.
  2. Read their plans with EXPLAIN QUERY PLAN or EXPLAIN ANALYZE.
  3. Index the columns in WHERE, JOIN ... ON and ORDER BY, equality columns first in a composite index.
  4. Check the plan again, then measure. Drop indexes that no query uses.
Lesson 5 of 5

From intuition to research

One idea, four depths

An index is a sorted list with page numbers, so the database can jump instead of reading everything.

B+tree indexes give O(log n) lookups and ordered ranges. Composite indexes follow the leftmost prefix rule, covering indexes avoid table reads, and every index slows writes.

Clustered storage keeps rows in key order: InnoDB and SQL Server clustered indexes, SQLite WITHOUT ROWID tables. Other structures suit other data: hash indexes for equality, GIN for arrays and JSON, GiST and R-trees for geometry, BRIN for huge naturally ordered tables.

Write heavy systems use log structured merge trees (O’Neil et al., 1996) in RocksDB and Cassandra, trading read cost for fast writes. Learned indexes (Kraska et al., SIGMOD 2018) replace B-tree search with a model that predicts a key’s position.

Going deeper: Clustered versus secondary

In MySQL InnoDB the table is stored inside its primary key B-tree, and every secondary index stores the primary key instead of a row address. A lookup through a secondary index therefore does two B-tree searches. That is one reason short primary keys are preferred there. SQLite ordinary tables are clustered by rowid in the same way.
