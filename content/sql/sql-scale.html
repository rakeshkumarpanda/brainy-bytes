Lesson 1 of 6

When one server is not enough

A database on one machine can serve a surprising amount: SQLite runs countless phone apps, and one well tuned PostgreSQL server can handle thousands of queries a second. When it is not enough, there are two directions.

DirectionWhat it meansLimits
Scale up (vertical)a bigger machine: more CPU, memory, faster disksone machine has a ceiling, and it is a single point of failure
Scale out (horizontal)more machines sharing the workharder: data must be copied or split, and kept consistent
The usual order of fixes
  1. Fix the queries and indexes first (chapters 7.1 and 7.2). It is the cheapest win.
  2. Add caching for repeated reads, for example Redis in front of the database.
  3. Add read replicas for read heavy traffic.
  4. Partition very large tables inside one server.
  5. Shard across servers only when one primary cannot take the writes.
Remember
Most apps never need sharding. Each step above adds moving parts, so take the next step only when measurements say the current one is not enough.
Lesson 2 of 6

Partitioning a big table

Partitioning splits one big table into smaller pieces on the same server, by a rule such as the year. Queries that name the year read only the matching piece, which is called partition pruning. Old pieces can be dropped in a moment instead of deleting millions of rows.

-- PostgreSQL declarative partitioning (version 10+)
CREATE TABLE sales (id bigint, sold_on date, amount int) PARTITION BY RANGE (sold_on);
CREATE TABLE sales_2024 PARTITION OF sales FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE sales_2025 PARTITION OF sales FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
Partition typeRuleExample
Rangea range of values per pieceone piece per month or year
Lista list of values per pieceone piece per country
Hashhash of the key mod Nspread customers evenly over 8 pieces
Lesson 3 of 6

Replication: copies of the whole database

Replication keeps copies of the database on other servers. The primary takes all writes and streams its change log to replicas, which serve reads and can take over if the primary fails.

ModeHow a write is confirmedTrade off
Asynchronousas soon as the primary has itfast, but a crash can lose the last few changes, and replicas lag behind
Synchronousonly when at least one replica also has itno loss on failover, but every write waits for the network
Semi synchronous (MySQL)when a replica has received ita middle ground
Real world scenario: the vanishing comment

You post a comment on a social site and the page reloads without it. The write went to the primary, but the reload read from a replica a second behind. That gap is replication lag. Apps fix it by reading your own recent writes from the primary for a short time, called read your writes consistency.

Failover
  1. The primary stops answering.
  2. Monitoring notices after a few missed heartbeats.
  3. The most up to date replica is promoted to primary.
  4. Apps reconnect to the new primary. With asynchronous replication, the newest changes may be lost.

Sharding and the CAP theorem

Sharding splits the rows of a table across several servers, each holding a shard. It spreads writes, which replication cannot do. The choice of shard key decides almost everything.

Good shard keyBad shard key
spreads data and traffic evenly (customer id)creates hot spots (today’s date sends all new writes to one server)
most queries include itmost queries must ask every shard
keeps related rows togethersplits rows that are always read together

The CAP theorem (Brewer 2000, proved by Gilbert and Lynch 2002) says that when the network between servers breaks (a partition), a distributed database must choose: stay consistent and refuse some requests, or stay available and risk returning old data.

Choice during a network splitBehaviourExamples
Consistency (CP)some requests fail until the split healsSpanner, CockroachDB, etcd
Availability (AP)every server answers, copies may disagree for a whileCassandra and DynamoDB in default modes

OLTP, OLAP and column stores

Not all databases do the same job. OLTP (online transaction processing) runs the app: many small reads and writes. OLAP (online analytical processing) answers big questions over history: few huge queries.

OLTPOLAP
Typical queryfetch order 105, insert one rowtotal sales by region by month for 5 years
Rows toucheda fewmillions or billions
Designnormalized (3NF)star schema, denormalized dimensions
Storagerow storecolumn store
ExamplesPostgreSQL, MySQL, SQL Server, SQLiteSnowflake, BigQuery, Redshift, ClickHouse, DuckDB

A column store keeps each column together on disk. A query that sums one column reads only that column, and similar values compress very well (C-Store, Stonebraker and others, 2005).

Remember
Many companies copy data from OLTP databases into a warehouse every night or continuously (ETL or ELT), so heavy reports never slow down the app.
Lesson 6 of 6

From intuition to research

One idea, four depths

When one server is too small, copy the data to more servers for reading, or split it so each server holds a part.

Partitioning splits a table on one server, replication copies the whole database, sharding splits rows across servers. OLTP and OLAP need different designs.

Consensus protocols (Paxos, Raft) keep replicas in agreement. Consistency models range from linearizable to eventual. Distributed SQL engines combine sharding, replication and transactions: Spanner, CockroachDB, YugabyteDB, TiDB.

Research explores disaggregated storage (Amazon Aurora, 2017, ships only the log to a shared storage layer), serverless databases that scale to zero, and lakehouse formats such as Apache Iceberg and Delta Lake that bring tables and transactions to files in object storage.

Going deeper: NoSQL and NewSQL

Around 2009 many systems dropped SQL and joins to scale out more easily: key value stores, document stores (MongoDB), wide column stores (Cassandra) and graph databases (Neo4j). Later, NewSQL and distributed SQL systems showed that SQL and transactions can also scale out, and many NoSQL systems added SQL like query languages. Choose by data shape and access pattern, not by fashion.
