Lesson 1 of 5

INSERT: adding rows

Tables start empty and grow one INSERT at a time. You name the columns you are filling, then give the values in the same order. Columns you leave out get their DEFAULT, or NULL.

One or more rowsExam favourite
INSERT INTO t (a, b) VALUES (1, 'x'), (2, 'y');
Always list the columns. The statement keeps working even if someone later adds a column.
Copy from a query
INSERT INTO t (a, b) SELECT ... ;
Every row the SELECT returns becomes a new row.
Common mistake
Writing INSERT INTO t VALUES (...) without a column list depends on the exact column order. It breaks quietly the day a column is added. List the columns.
Lesson 2 of 5

UPDATE and DELETE: changing and removing rows

UPDATE changes values in rows that already exist. DELETE removes rows. Both use WHERE to pick the rows, and both change every row when WHERE is missing.

The safe way to change data
  1. Write the WHERE as a SELECT first: SELECT * FROM products WHERE category = 'Kitchen';
  2. Check the rows. Are these exactly the rows you mean.
  3. Change SELECT * into UPDATE ... SET or DELETE, keeping the same WHERE.
  4. On a real server, do it inside a transaction (chapter 7.3), so a mistake can be rolled back.
Lesson 3 of 5

UPSERT and RETURNING

A common job: "add this row, but if it already exists, update it". That is an UPSERT (update or insert). It needs a UNIQUE or PRIMARY KEY column so the engine can detect the clash.

EngineHow to write an upsert
SQLite (3.24+) and PostgreSQL (9.5+)INSERT ... ON CONFLICT (key) DO UPDATE SET ... or DO NOTHING
MySQLINSERT ... ON DUPLICATE KEY UPDATE ...
SQL Server, Oracle, PostgreSQL 15+MERGE INTO target USING source ON ... WHEN MATCHED ... WHEN NOT MATCHED ...
SQLite shortcutsINSERT OR IGNORE skips a clashing row, INSERT OR REPLACE deletes the old row and inserts the new one

RETURNING hands back the rows a statement just changed, so the app gets new ids or new values without a second query. SQLite has it since 3.35, PostgreSQL for much longer. SQL Server uses OUTPUT instead.

Common mistake
INSERT OR REPLACE is not the same as an upsert. It deletes the old row, so columns you did not supply go back to their defaults, and ON DELETE actions on child rows can fire.
Lesson 4 of 5

Foreign key actions: what happens to the children

When a parent row is deleted or its key changes, the foreign key decides what happens to the child rows. You choose with ON DELETE and ON UPDATE.

ActionWhen the parent is deletedGood for
NO ACTION (default) or RESTRICTthe delete is refused while children existorders that must never lose their customer
CASCADEthe children are deleted tooorder lines that mean nothing without their order
SET NULLthe child column becomes NULLan employee whose department is closed
SET DEFAULTthe child column takes its defaultmoving items to a general bucket
Real world scenario: closing an account

When a user deletes their account in a photo app, the company must remove their photos, comments and likes too. Writing ON DELETE CASCADE on each child table makes the database do it in one step, and no orphan photo is left behind pointing at a user who no longer exists.

Remember
In SQLite, foreign keys and their actions only work when PRAGMA foreign_keys = ON. Every SQL block on this site turns it on for you.
Lesson 5 of 5

From intuition to research

One idea, four depths

INSERT adds rows, UPDATE changes them, DELETE removes them. WHERE says which rows, and forgetting it touches all of them.

These statements are DML, data manipulation language. Each statement is atomic: if one row breaks a constraint, the whole statement is undone, not just that row.

UPSERT and MERGE need a unique index to detect conflicts safely under concurrency. Foreign key actions are declarative triggers, and statement level RETURNING removes a round trip between app and database.

Inside the engine, an UPDATE is often a delete plus an insert. PostgreSQL keeps old row versions for MVCC (chapter 7.3), which VACUUM later cleans up, while InnoDB keeps undo logs. Bulk loading tools such as PostgreSQL COPY and SQLite’s .import skip much per statement work.

Going deeper: Soft delete

Many apps never really DELETE. They add a column such as deleted_at and set it instead, then filter WHERE deleted_at IS NULL everywhere. This allows undo and audits, at the cost of every query remembering the filter. Views (chapter 4.3) can hide that filter.
