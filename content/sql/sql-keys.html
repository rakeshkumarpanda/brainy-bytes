Lesson 1 of 5

Why one table is not enough

Imagine writing every order in one big table: order id, date, customer name, customer city, customer email, product name, product price. Asha orders three times, so her email is typed three times. If she changes her email, someone must find and fix all three rows. Miss one and the database now holds two different emails for the same person.

ProblemWhat goes wrong in one big table
Repeated dataAsha’s city and email are stored again in every order she makes
Update problemChange the email in one row but not the others, and the data disagrees with itself
Insert problemA new customer who has not ordered yet has nowhere to live
Delete problemDelete a customer’s only order and you lose the customer too

The fix is to give each kind of thing its own table, customers, products and orders, and link them with keys. Each fact is stored once. This idea is called normalization, and chapter 5.1 covers it formally.

Remember
A relational database is a set of small, focused tables plus the keys that connect them. Joins put the pieces back together when you ask a question.
Lesson 2 of 5

Primary keys, natural and surrogate

A primary key is the column, or set of columns, that picks out exactly one row. It must be unique and never NULL. A table has at most one primary key.

Kind of keyMeaningExample
Candidate keyany column set that could be the primary keycustomers.id, also customers.email if every customer had one
Primary keythe candidate chosen to identify rowscustomers.id
Natural keya real world valueAadhaar number, ISBN, vehicle number plate
Surrogate keya made up number with no outside meaningid 1, 2, 3 assigned by the database
Composite keytwo or more columns togetherorder_items (order_id, product_id)
Alternate keya candidate key not chosen, usually given a UNIQUE rulecustomers.email UNIQUE
In the exam
In SQLite, a column declared exactly INTEGER PRIMARY KEY becomes the rowid, the table’s hidden row number. Insert NULL into it and SQLite picks the next number for you. In PostgreSQL use GENERATED ALWAYS AS IDENTITY, in MySQL AUTO_INCREMENT, in SQL Server IDENTITY(1,1).
Real world scenario: why banks do not key on your name

A bank has thousands of customers called Rahul Sharma. Even phone numbers change and get reused. So the bank gives each customer a customer id that never changes, a surrogate key, and stores the PAN or phone number as ordinary columns with UNIQUE rules where needed.

Lesson 3 of 5

Foreign keys keep links honest

A foreign key is a column whose value must match a primary key in another table, the parent. orders.customer_id must be an existing customers.id. The database checks this on every insert, update and delete, so you can never have an order for a customer who does not exist.

ON DELETE actionWhen the parent row is deleted
NO ACTION (default)the delete fails if children exist (checked at the end of the statement)
RESTRICTthe delete fails at once if children exist
CASCADEthe children are deleted too
SET NULLthe children’s foreign key becomes NULL
SET DEFAULTthe children’s foreign key gets its default value
Common mistake
SQLite has foreign keys switched off by default for backwards compatibility. Each connection must run PRAGMA foreign_keys = ON. Every SQL block and the playground on these pages do that for you. PostgreSQL, SQL Server and MySQL (InnoDB) always enforce them.
Lesson 4 of 5

One to one, one to many, many to many

Tables relate in three shapes. Spotting the shape tells you where the foreign key goes.

ShapeReal lifeHow to build it
One to manyone customer, many ordersforeign key on the many side: orders.customer_id
Many to manyan order has many products, a product is in many ordersa junction table with two foreign keys: order_items(order_id, product_id)
One to oneone person, one passportforeign key that is also UNIQUE, or share the same primary key

Reading an ER diagram

An entity relationship (ER) diagram draws tables as boxes and relationships as lines. Peter Chen introduced the ER model in 1976. Most tools today draw crow’s foot notation: a three pronged foot means "many", a bar means "one", a circle means "zero allowed".

Line endMeans
|| (two bars)exactly one
o| (circle, bar)zero or one
|< (bar, crow’s foot)one or many
o< (circle, crow’s foot)zero or many
The shop as an ER diagram
  1. customers (|| to o<) orders: a customer has zero or many orders, each order belongs to exactly one customer.
  2. orders (|| to |<) order_items: an order has one or many lines.
  3. products (|| to o<) order_items: a product appears in zero or many lines.
  4. orders and products are many to many, through order_items
Lesson 5 of 5

From intuition to research

One idea, four depths

Each table is one kind of thing. Keys are the name tags and the arrows that point from one table to another.

Referential integrity means every foreign key value matches a parent key or is NULL. Actions such as CASCADE decide what happens to children when a parent changes.

Foreign keys can be deferred: DEFERRABLE INITIALLY DEFERRED checks them at COMMIT instead of after each statement, which lets you insert two rows that point at each other inside one transaction. Child key columns should be indexed, or every parent delete scans the whole child table.

Distributed and sharded databases often drop foreign key enforcement across machines because checking a parent on another server is slow. They move the check into application code or background jobs, trading safety for speed.

Going deeper: UUIDs as keys

Some systems use UUIDs (128 bit random identifiers) instead of 1, 2, 3, so that many servers can create ids without talking to each other. The cost is bigger keys and indexes. Time ordered UUIDs (version 7, RFC 9562, 2024) keep new ids near each other in the index.
