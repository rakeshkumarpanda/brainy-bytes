Triggers: code that runs on every change

A trigger is a small program stored in the database that runs by itself when rows are inserted, updated or deleted. Inside it, NEW is the row after the change and OLD is the row before.

TriggerExam favourite
CREATE TRIGGER name AFTER UPDATE OF col ON t WHEN condition BEGIN ... ; END;
BEFORE or AFTER, INSERT, UPDATE or DELETE. WHEN is optional.
Refuse a change
SELECT RAISE(ABORT, 'message');
Inside a trigger, stops the statement with an error (SQLite).

Keeping data in step, and writable views

Triggers can keep a stored total correct, or let people write through a view.

Good use of a triggerRisky use of a trigger
audit logs and history tablesbusiness rules that hide surprising side effects
keeping a denormalized total in steptriggers that fire other triggers several levels deep
refusing values a CHECK cannot expressslow work inside a trigger on a busy table
Common mistake
Triggers are invisible from the app code. Document them, keep them short, and remember that bulk loads fire them once per row.

Generated columns

A generated column is worked out from other columns of the same row. You never write it, and it can never be wrong. SQLite has them since 3.31 (2020), PostgreSQL since 12, MySQL since 5.7.

Stored procedures and functions

Server databases can store whole programs: stored procedures (run with CALL or EXEC) and user defined functions (used inside queries). SQLite has neither in SQL, because it runs inside your app, so the app registers functions in its own language instead.

-- PostgreSQL (PL/pgSQL)
CREATE PROCEDURE transfer(src TEXT, dst TEXT, amt INTEGER)
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE accounts SET balance = balance - amt WHERE name = src;
  UPDATE accounts SET balance = balance + amt WHERE name = dst;
END $$;
CALL transfer('Asha', 'Ravi', 300);

-- SQL Server (T-SQL)
CREATE PROCEDURE transfer @src NVARCHAR(50), @dst NVARCHAR(50), @amt INT AS
BEGIN
  UPDATE accounts SET balance = balance - @amt WHERE name = @src;
  UPDATE accounts SET balance = balance + @amt WHERE name = @dst;
END;
EXEC transfer 'Asha', 'Ravi', 300;

From intuition to research

One idea, four depths

Triggers are automatic reactions to changes. Generated columns are formulas. Procedures are saved programs.

BEFORE triggers check, AFTER triggers log or update totals, INSTEAD OF triggers make views writable. Generated columns are VIRTUAL or STORED. Procedures and functions live in server engines.

Triggers run inside the same transaction as the statement, so a failing trigger rolls the statement back. Statement level triggers (PostgreSQL, SQL Server) fire once per statement with transition tables, while SQLite only has row level triggers.

Active databases, which react to events with rules, were studied in the 1990s (the HiPAC and Starburst projects). Today change data capture streams every change from the log to other systems, using tools such as Debezium, instead of triggers.

Going deeper: Temporal tables

SQL:2011 added system versioned tables, which keep every past version of each row automatically, so you can query the data AS OF a past time. SQL Server and MariaDB support them. In SQLite and PostgreSQL the same effect is built with an AFTER UPDATE trigger that copies the old row to a history table.
