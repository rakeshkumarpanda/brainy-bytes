Lesson 1 of 5

Why repeated data hurts

Chapter 3.1 showed the problem: when one fact is written in many rows, the copies can drift apart. Normalization is the step by step method for splitting tables so that each fact is stored exactly once. It was set out by E. F. Codd between 1970 and 1974.

AnomalyIn the sheet
UpdateRao moves room, and every row with Rao must change, or the data contradicts itself
InsertA new course with no students yet cannot be recorded, because every row needs a student
DeleteIf Meera drops Security, the only row saying Security exists disappears too
Remember
Normalization is about the meaning of the data, not about saving disk space. The space saving is a side effect.
Lesson 2 of 5

Functional dependencies: what decides what

A functional dependency X → Y means: once you know X, there is only one possible Y. Knowing a roll number tells you the student’s name, so student_id → student_name. Knowing a teacher tells you their room, so teacher → room.

Dependency in the sheetRead it as
student_id → student_namea roll number decides the name
course → title, teachera course code decides its title and teacher
teacher → rooma teacher decides the room
(student_id, course) → gradea student and a course together decide the grade

The key of the sheet is (student_id, course), because together they decide every other column. The trouble comes from columns that depend on only part of the key, or on a column that is not a key.

How to spot a dependency
  1. Ask the business, not only the data: can one teacher ever have two rooms.
  2. Check the data: GROUP BY the left side and count distinct values of the right side.
  3. A count above 1 means the dependency does not hold, or the data is already broken.
  4. X → Y holds when COUNT(DISTINCT Y) = 1 for every X

1NF, 2NF, 3NF and BCNF

Each normal form removes one kind of bad dependency. Each one includes the rules of the forms before it.

FormRuleFix in the sheet
1NFevery cell holds one value, no lists or repeating groupsphones "98111, 98222" become one row per phone
2NFno column depends on only part of the keystudent_name moves to students, course details to courses
3NFno column depends on another non key columnroom moves to teachers, because teacher → room
BCNFevery determinant is a candidate keystricter 3NF, rarely different in practice
Remember
A memory line used by students: every non key column must depend on the key (1NF), the whole key (2NF), and nothing but the key (3NF).

Higher forms and denormalization

Most business databases stop at 3NF or BCNF. Two higher forms exist for rarer cases.

FormProblem it removesExample
4NF (Fagin 1977)two independent lists stored in one tablea teacher’s subjects and languages in one table make every combination appear
5NF (Fagin 1979)a table that can only be rebuilt from three or more piecessupplier, part and project rules that hold only in combination

Denormalization means deliberately storing a copy of data to make reading faster, accepting the work of keeping the copies in step. It is a decision you make after normalizing, not instead of it.

Normalize whenDenormalize when
data is written and changed often (OLTP apps)data is mostly read, such as reports (OLAP)
correctness matters mosta measured query is too slow even with good indexes
you are not sure yetyou can keep copies in step with triggers or batch jobs
Real world scenario: the star schema of a sales warehouse

A supermarket’s reporting database keeps one big fact table of sales and small dimension tables for date, store and product. The product table repeats the category and brand names in every row, which breaks 3NF on purpose. Reports become simple joins of one fact table to a few dimensions, and nobody updates these rows during the day, so the copies cannot drift.

Lesson 5 of 5

From intuition to research

One idea, four depths

Store each fact once. If you would have to fix the same thing in two places, split the table.

Find the key and the functional dependencies, then remove partial dependencies (2NF) and transitive dependencies (3NF). Check that a join rebuilds the original rows.

A decomposition is lossless when the common columns form a key of at least one part. Armstrong’s axioms (reflexivity, augmentation, transitivity) derive every dependency that follows from a given set. 3NF can always be reached while keeping all dependencies checkable, BCNF sometimes cannot.

Research looks at discovering dependencies automatically from data (algorithms such as TANE), at normal forms for nested and JSON data, and at schema design for distributed systems, where joins across machines are expensive and some redundancy is often the right trade.

Going deeper: Armstrong’s axioms

From a set of dependencies you can derive others: reflexivity (if Y is part of X, then X → Y), augmentation (if X → Y, then XZ → YZ) and transitivity (if X → Y and Y → Z, then X → Z). From course → teacher and teacher → room, transitivity gives course → room, the chain that 3NF removes.
