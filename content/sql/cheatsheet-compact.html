Step 1Start here

1.1Databases and SQL: where data lives

  • Database and DBMS A database is an organised collection of data. A DBMS is the program that stores it, checks rules, shares it safely and answers queries.
  • Tables Data lives in tables of rows (records) and columns (kinds of fact). A primary key is unique and never missing, so it names one row.
  • NULL NULL means missing or unknown. It is not zero and not an empty string.
  • SQL Structured Query Language, from IBM SEQUEL (1974), ANSI 1986, ISO 1987, current edition SQL:2023. Declarative: say what, not how.
  • First query SELECT columns FROM table. SELECT * means every column. Statements end with a semicolon.
  • Engines SQLite is embedded. PostgreSQL, MySQL, SQL Server and Oracle are servers. Each has its own dialect of SQL.
  • The smallest querySELECT column, column FROM table;
  • Trap A primary key must be unique and must never be missing. Names are bad keys because two customers can both be called Asha.

1.2SELECT in depth: columns, sums, aliases and paging

  • Expressions Every SELECT item is an expression worked out per row: columns, literals, arithmetic and || for text.
  • Integer division In SQLite and PostgreSQL 7 / 2 is 3. Use 7 / 2.0 for 3.5.
  • Aliases AS names a result column or a table. Single quotes mean text, double quotes mean a name.
  • DISTINCT Removes duplicate result rows, comparing the whole row. NULLs count as equal here.
  • LIMIT and OFFSET Sort first, then LIMIT n OFFSET k. Page p uses OFFSET (p − 1) × n. Standard form: FETCH FIRST n ROWS ONLY.
  • Remove repeatsSELECT DISTINCT col, col FROM t;
  • Page of results... ORDER BY col LIMIT n OFFSET k;
  • Trap In SQLite and PostgreSQL, dividing two whole numbers gives a whole number. 7 / 2 is 3. Write 7 / 2.0 or CAST(7 AS REAL) / 2 when you want 3.5. MySQL is different: its / always gives a decimal.
  • Trap LIMIT without ORDER BY gives "some" rows, not "the first" rows. Always sort before you limit.

1.3Filtering and sorting: WHERE and ORDER BY

  • WHERE Tests every row and keeps only rows where the condition is true. False and unknown rows are dropped.
  • Precedence NOT, then AND, then OR. Add brackets whenever AND and OR are mixed.
  • Ranges and lists BETWEEN a AND b includes both ends. IN (...) is a short form of several ORs.
  • Patterns LIKE: % any run, _ one character, case insensitive for ASCII in SQLite. GLOB is case sensitive.
  • NULL tests Use IS NULL and IS NOT NULL. = NULL never matches.
  • ORDER BY ASC default, DESC for big first, later columns break ties. NULLs sort first in SQLite, NULLS LAST moves them.
  • Trap When AND and OR appear together, add brackets even if you know the rule. The next reader may not.
  • Exam In SQLite, LIKE ignores the difference between capital and small letters for plain English letters. GLOB is the case sensitive cousin and uses * and ? instead of % and _. PostgreSQL LIKE is case sensitive, and it has ILIKE for case insensitive matching.

Step 2Shaping results

2.1Functions, CASE and dates

  • Text upper, lower, length, substr (positions start at 1), trim, replace, instr and || for joining.
  • CASE CASE WHEN ... THEN ... ELSE ... END. The first true WHEN wins, no ELSE gives NULL.
  • NULL helpers COALESCE returns the first non NULL value. NULLIF(a, b) gives NULL when a = b, handy for safe division.
  • Types SQLite storage classes: NULL, INTEGER, REAL, TEXT, BLOB. typeof shows them, CAST converts.
  • Dates SQLite stores dates as ISO text, Julian day or Unix time. date, datetime, strftime, julianday, unixepoch and modifiers such as +7 days.
  • Searched CASECASE WHEN cond THEN a WHEN cond2 THEN b ELSE c END
  • Exam SQLite is flexible about types: a column declared INTEGER can still hold text unless the table is STRICT. PostgreSQL, MySQL and SQL Server are strict and will reject or convert the value. Chapter 4.1 covers this in depth.

2.2NULL and three valued logic

  • NULL is unknown Not zero, not empty text. Arithmetic and comparisons with NULL give NULL. NULL = NULL is NULL.
  • Three values TRUE, FALSE, UNKNOWN. FALSE wins in AND, TRUE wins in OR.
  • Filters keep TRUE WHERE, HAVING and ON drop FALSE and UNKNOWN. CHECK rejects only FALSE, so NULL passes a CHECK.
  • Tests IS NULL, IS NOT NULL, a IS b (never NULL). COALESCE gives a fallback.
  • Traps NOT IN with a NULL returns nothing. COUNT(col), SUM, AVG skip NULLs. GROUP BY and DISTINCT treat NULLs as one value.
  • Safe NULL comparisona IS b, a IS NOT b
  • Exam Oracle treats an empty string '' as NULL. SQLite, PostgreSQL, MySQL and SQL Server keep them different. This is a common surprise when moving data between engines.

2.3Aggregates, GROUP BY and HAVING

  • Aggregates COUNT(*), COUNT(col), COUNT(DISTINCT col), SUM, AVG, MIN, MAX. All but COUNT(*) skip NULLs.
  • No GROUP BY An aggregate query without GROUP BY returns exactly one row. COUNT of nothing is 0, SUM of nothing is NULL.
  • GROUP BY One result row per group. Show only grouping columns or aggregates.
  • WHERE vs HAVING WHERE filters rows before grouping, HAVING filters groups after, and only HAVING can use aggregates.
  • Logical order FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT.
  • Grouped querySELECT g, agg(x) FROM t WHERE row_test GROUP BY g HAVING group_test ORDER BY ...;
  • Exam An aggregate query with no GROUP BY always returns exactly one row, even when the table is empty. COUNT then gives 0 and SUM gives NULL.

Step 3Many tables

3.1Keys and relationships between tables

  • Why many tables One big table repeats data and causes update, insert and delete anomalies. Store each fact once and link with keys.
  • Primary key Unique, never NULL, one per table. Surrogate (made up id) or natural (real world). Composite keys use several columns.
  • Foreign key Must match a parent key or be NULL. Actions: NO ACTION, RESTRICT, CASCADE, SET NULL, SET DEFAULT. SQLite needs PRAGMA foreign_keys = ON.
  • Relationship shapes One to many: FK on the many side. Many to many: junction table. One to one: FK plus UNIQUE.
  • ER diagrams Boxes for tables, lines for relationships. Crow’s foot means many, bar means one, circle means zero allowed.
  • Exam In SQLite, a column declared exactly INTEGER PRIMARY KEY becomes the rowid, the table’s hidden row number. Insert NULL into it and SQLite picks the next number for you. In PostgreSQL use GENERATED ALWAYS AS IDENTITY, in MySQL AUTO_INCREMENT, in SQL Server IDENTITY(1,1).
  • Trap SQLite has foreign keys switched off by default for backwards compatibility. Each connection must run PRAGMA foreign_keys = ON. Every SQL block and the playground on these pages do that for you. PostgreSQL, SQL Server and MySQL (InnoDB) always enforce them.

3.2Joins: putting tables back together

  • Inner join JOIN ... ON pairs rows where the condition is true. Unmatched rows are dropped.
  • Outer joins LEFT keeps all left rows, RIGHT all right rows, FULL both. Missing side becomes NULL. Count with COUNT(right.col).
  • Anti join LEFT JOIN ... WHERE right.key IS NULL finds rows with no partner.
  • Self and cross A self join uses two aliases of one table. CROSS JOIN makes every pair. A missing ON can cause a huge accidental cross join.
  • ON vs WHERE In outer joins, filters on the optional side belong in ON. In WHERE they remove the NULL rows.
  • Algorithms Nested loop, hash join, merge join. SQLite uses nested loops with indexes.
  • Inner joinSELECT ... FROM a JOIN b ON b.a_id = a.id;
  • Trap An inner join loses rows that have no partner. Kabir, Arjun and Vikram never ordered, so they do not appear in the result above.
  • Exam SQLite supports RIGHT JOIN and FULL OUTER JOIN since version 3.39.0 (July 2022). MySQL still has no FULL OUTER JOIN: people write a LEFT JOIN UNION a RIGHT JOIN instead.
  • Trap A join with a missing or wrong ON condition can turn into an accidental cross join: 10 000 rows times 10 000 rows is 100 million rows. If a result is suddenly huge, check the ON clauses first.

3.3Subqueries: questions inside questions

  • Subquery A query in brackets inside another. Scalar (one value), list (one column, used with IN), or table (in FROM, needs an alias).
  • IN and NOT IN IN tests membership. NOT IN returns nothing if the list holds a NULL.
  • EXISTS True when the subquery returns any row. NOT EXISTS is the NULL safe anti join.
  • Correlated Refers to the outer row, so it is evaluated per outer row. Great for per group comparisons.
  • Derived tables Aggregate first, then filter or join. AVG(SUM(x)) needs a derived table.
  • Trap If a scalar subquery returns more than one row, SQLite quietly uses the first row, while PostgreSQL and SQL Server raise an error. Make sure a scalar subquery can only return one row, for example with an aggregate or a key lookup.
  • Trap Remember the NULL trap from chapter 2.2: if the subquery list contains even one NULL, NOT IN returns no rows at all. NOT EXISTS, in the next lesson, does not have this problem.

3.4Set operations: UNION, INTERSECT and EXCEPT

  • Stacking UNION, UNION ALL, INTERSECT and EXCEPT stack results. Same number of columns, names from the first query, ORDER BY once at the end.
  • Duplicates UNION, INTERSECT and EXCEPT remove duplicates. UNION ALL keeps them and is faster.
  • EXCEPT Rows of the first query missing from the second. Order matters. MINUS in Oracle.
  • NULLs Set operations treat NULLs as equal, so EXCEPT compares tables safely.
  • Twins INTERSECT is like EXISTS, EXCEPT like NOT EXISTS or an anti join.

Step 4Building and changing data

4.1Building tables: CREATE, types and constraints

  • CREATE TABLE Names the table, its columns, their types and the rules. IF NOT EXISTS makes it safe to run twice.
  • Constraints NOT NULL, UNIQUE, PRIMARY KEY, CHECK, DEFAULT and REFERENCES are checked by the engine on every write.
  • CHECK and NULL CHECK refuses a row only when its test is false. NULL makes it unknown, which passes.
  • Types Use exact types for money. SQLite uses affinity, a preference, unless the table is STRICT.
  • ALTER and DROP ADD COLUMN, RENAME and DROP COLUMN change a live table. DROP TABLE deletes the table and its rows.
  • Create a tableCREATE TABLE name (column type constraints, ...);
  • Add a columnALTER TABLE t ADD COLUMN c type DEFAULT v;
  • Trap Never store money in a floating point column. 0.1 + 0.2 is not exactly 0.3 in binary. Use a DECIMAL type, or store whole paise or cents as an integer, as our products table does with prices in rupees.

4.2Changing data: INSERT, UPDATE, DELETE and UPSERT

  • INSERT List the columns, then the values in the same order. Several rows or a SELECT can supply them.
  • UPDATE and DELETE WHERE picks the rows. No WHERE means every row. Test the WHERE with a SELECT first.
  • UPSERT ON CONFLICT DO UPDATE or DO NOTHING in SQLite and PostgreSQL, ON DUPLICATE KEY UPDATE in MySQL, MERGE elsewhere. excluded is the attempted row.
  • RETURNING Gives back the changed rows, such as new ids, without a second query.
  • Foreign key actions NO ACTION refuses, CASCADE deletes children, SET NULL clears the link. Delete children before parents otherwise.
  • One or more rowsINSERT INTO t (a, b) VALUES (1, 'x'), (2, 'y');
  • Trap Writing INSERT INTO t VALUES (...) without a column list depends on the exact column order. It breaks quietly the day a column is added. List the columns.
  • Trap INSERT OR REPLACE is not the same as an upsert. It deletes the old row, so columns you did not supply go back to their defaults, and ON DELETE actions on child rows can fire.

4.3Views and CTEs: naming your queries

  • View CREATE VIEW stores a query under a name. It shows current data each time. Read only in SQLite.
  • CTE WITH name AS (query) names a step for one statement. Later steps and the main query can read it.
  • Temporary table CREATE TEMP TABLE stores rows until the connection closes, good for reuse.
  • Materialized view Stores the result, fast to read, as fresh as its last REFRESH. PostgreSQL, Oracle, SQL Server indexed views.
  • Choosing Subquery for once, CTE for readable steps, view for shared logic, temp table or materialized view for reused heavy results.
  • Make a viewCREATE VIEW name AS SELECT ... ;

Step 5Designing databases

5.1Normalization: storing each fact once

  • Anomalies Repeated facts cause update, insert and delete anomalies. Normalization stores each fact once.
  • Dependencies X → Y means X decides Y. The key decides every column.
  • 1NF, 2NF, 3NF One value per cell, no dependency on part of the key, no dependency on a non key column.
  • Lossless A good split can be joined back into exactly the original rows.
  • Denormalize on purpose Store copies only for measured read speed, and keep them in step.

5.2Database design in practice

  • Process Story first: nouns to tables, facts to columns, verbs to relationships, then keys and rules.
  • Relationships One to one: foreign key plus UNIQUE. One to many: foreign key on the many side. Many to many: junction table.
  • ER diagrams Boxes and lines. Crow’s foot: three prongs many, bar one, circle optional.
  • Conventions One naming style, surrogate ids with UNIQUE natural keys, foreign keys named after tables, exact money.
  • Rules in the schema Every business promise becomes NOT NULL, UNIQUE, CHECK or a foreign key.

Step 6Advanced queries

6.1Window functions: ranks, running totals and more

  • OVER function(...) OVER (PARTITION BY ... ORDER BY ...) gives a group answer on every row. Rows are not folded.
  • Ranking ROW_NUMBER never ties, RANK ties with gaps, DENSE_RANK ties without gaps. Add a tie breaker for stable results.
  • Running and neighbours An aggregate with ORDER BY is a running aggregate. LAG and LEAD read the previous and next rows.
  • Frames No ORDER BY means the whole partition. ORDER BY means start to current row with peers. ROWS BETWEEN sets your own.
  • Filtering Window functions run after WHERE, GROUP BY and HAVING. Filter on them in an outer query or CTE.
  • Window functionfunction(...) OVER (PARTITION BY a ORDER BY b)
  • Trap ROW_NUMBER breaks ties in no guaranteed order. Add a tie breaker such as id to the ORDER BY when the result must be the same every time.

6.2Recursive queries: trees, graphs and series

  • Shape WITH RECURSIVE name AS (anchor UNION ALL recursive part). The recursive part reads name and sees last round’s rows.
  • Stop rule Always stop: a WHERE condition, a depth limit, a cycle guard or an outer LIMIT.
  • Series Generate numbers and dates, then LEFT JOIN to show zero rows.
  • Trees Self referencing tables are walked one level per round. Carry level and path along.
  • Graphs Loops need a path check, UNION, or a depth limit. PostgreSQL has CYCLE.
  • Recursive CTEWITH RECURSIVE name(cols) AS ( anchor UNION ALL recursive_part ) SELECT ... FROM name;
  • Trap Always write a stop rule, such as WHERE x < 10, a depth limit, or a LIMIT on the outer query. SQL Server stops after 100 rounds by default (MAXRECURSION), SQLite has no such limit.

6.3Query patterns: top N, streaks, pivots and JSON

  • Top N per group ROW_NUMBER or RANK with PARTITION BY in a CTE, then WHERE rn <= N outside.
  • Gaps and islands value − ROW_NUMBER is constant within a run. LEAD finds the gaps.
  • Pivot SUM or COUNT around CASE, or FILTER, one column per value. Columns must be known in advance.
  • Duplicates Find with GROUP BY ... HAVING COUNT(*) > 1, remove with ROW_NUMBER > 1, prevent with UNIQUE.
  • JSON ->> and json_extract read fields, json_each makes rows, json_group_array and json_object build JSON.

Step 7Performance and transactions

7.1Indexes: making queries fast

  • Scan versus search Without an index a filter reads every row (SCAN). An index lets the engine jump (SEARCH). Check with EXPLAIN QUERY PLAN.
  • B-trees Balanced, wide, sorted. About log n steps, ranges and ORDER BY come almost free.
  • Index shapes Composite indexes follow the leftmost prefix rule. Covering indexes avoid the table. Partial and expression indexes exist.
  • When not used Functions on the column, leading wildcards, later composite columns only, tiny tables, filters matching most rows.
  • Costs Every index slows writes and takes space. Index what important queries filter, join and sort on, then measure.

7.2Query plans and tuning

  • Optimizer SQL says what, the optimizer decides how. EXPLAIN QUERY PLAN or EXPLAIN shows its choice.
  • Plan words SCAN reads all rows, SEARCH jumps by index, COVERING INDEX skips the table, TEMP B-TREE sorts.
  • Joins Nested loop wants an index on the inner column, hash join suits big equality joins, merge join suits sorted inputs.
  • Statistics Cost based optimizers need fresh statistics. Run ANALYZE after big changes.
  • Rewrites Sargable ranges instead of functions on columns, keyset instead of deep OFFSET, one join instead of N+1 queries.

7.3Transactions and concurrency

  • Transactions BEGIN ... COMMIT groups statements, ROLLBACK undoes them. Autocommit makes each statement its own transaction.
  • ACID Atomicity, consistency, isolation, durability.
  • Savepoints SAVEPOINT name, ROLLBACK TO name undoes part of a transaction.
  • Isolation READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE prevent more anomalies in turn. Know your engine’s default.
  • Concurrency Use balance = balance + x or SELECT ... FOR UPDATE against lost updates. Lock in a fixed order and retry on deadlock.
  • TransactionBEGIN; ... ; COMMIT;
  • Trap In SQLite a failed statement inside a transaction undoes only that statement by default. The transaction stays open, and it is the program’s job to ROLLBACK. PostgreSQL marks the whole transaction as failed until you ROLLBACK.

Step 8Professional SQL

8.1Triggers, generated columns and procedures

  • Triggers CREATE TRIGGER ... BEFORE or AFTER INSERT, UPDATE or DELETE. NEW is the new row, OLD the old one. Fires once per row in SQLite.
  • Uses Audit logs, history tables, stored totals, refusing bad values, INSTEAD OF to make views writable.
  • Generated columns GENERATED ALWAYS AS (expr) VIRTUAL or STORED. Computed, never written by hand.
  • Procedures Server engines store programs: PL/pgSQL, T-SQL, PL/SQL. SQLite uses functions from the host app.
  • Judgement Keep triggers short and documented. Choose database or app logic by who must be guarded and how it will be tested.
  • TriggerCREATE TRIGGER name AFTER UPDATE OF col ON t WHEN condition BEGIN ... ; END;
  • Trap Triggers are invisible from the app code. Document them, keep them short, and remember that bulk loads fire them once per row.

8.2Database security

  • Injection Gluing user text into SQL lets input become code. It bypasses logins and leaks data.
  • Parameters Use placeholders (?, $1, :name) for every value. Pick table and column names from an allow list.
  • Least privilege Accounts and roles get only the rights they need. GRANT gives, REVOKE takes away.
  • Rows and columns Views hide columns, row level security hides rows. SQLite relies on file permissions.
  • Personal data Hash passwords with Argon2id or bcrypt, mask on screen, encrypt at rest and in transit, test your backups.
  • Trap This page shows attacks only so you can recognise and prevent them, on a throwaway table in your own browser. Testing systems you do not own or have no permission to test is illegal in most countries.

8.3Databases at scale

  • Order of fixes Tune queries and indexes, cache, add read replicas, partition, and shard last.
  • Partitioning Range, list or hash pieces of one table on one server. Pruning reads only the pieces needed.
  • Replication Primary takes writes, replicas copy the log and serve reads. Async is fast but lags, sync waits but loses nothing.
  • Sharding and CAP Rows spread across servers by a shard key. During a network split, choose consistency or availability.
  • OLTP and OLAP Small transactions in normalized row stores, big analytics in star schemas and column stores.

8.4SQL standards and dialects

  • Standard ISO/IEC 9075. Key versions: SQL-92 joins and CASE, 1999 recursion and triggers, 2003 window functions, 2016 JSON, 2023 graphs.
  • Differences Quoting, LIMIT or TOP, text joining, booleans, dates, auto ids, upserts and LIKE case differ between engines.
  • Choosing SQLite for one device, PostgreSQL or MySQL for web apps, SQL Server and Oracle in enterprises, column stores for analytics.
  • Portable habits COALESCE, CASE, CAST, explicit JOIN, ISO dates, full GROUP BY lists, plain names.
  • Test where you deploy Run your SQL on the engine you will use. Dates, division and conversions differ most.
  • Trap Moving a database between engines usually breaks on dates, booleans, auto ids and string concatenation, not on SELECT or JOIN. Test those first.

Step 9Exam and interview revision

9.1Exam and interview revision

  • Logical order FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT explains aliases, HAVING and window function rules.
  • Interview patterns Second highest, self join, anti join, top N per group, duplicates, running totals, recursive chains.
  • Traps NULLs in NOT IN, ties in ranking, COUNT(column) skipping NULLs, missing WHERE in UPDATE and DELETE.
  • Design answers Entities, keys, relationships, constraints for rules, then argue 1NF, 2NF and 3NF.
  • Keep practising Use the playground daily and real datasets. Revise each chapter’s Summary tab before an exam.
