Lesson 1 of 4

Views: a saved query with a name

Some queries get written again and again, such as "money spent by each customer". A view stores that query under a name. After that you can SELECT from the view as if it were a table, and the engine runs the saved query each time, so the answer is always up to date.

Make a viewExam favourite
CREATE VIEW name AS SELECT ... ;
Only the query is stored, not the rows.
Remove a view
DROP VIEW IF EXISTS name;
The underlying tables are untouched.
Why people use viewsExample
Hide a long query behind a short nameSELECT * FROM customer_spend
Give each team only the columns it needsa view of employees without the salary column
Keep one definition of a business rulewhat counts as an active customer, written once
Keep old programs working after a table changesa view with the old table name and old column names
Remember
In SQLite a view is read only: you cannot INSERT, UPDATE or DELETE through it unless you add INSTEAD OF triggers (chapter 8.1). PostgreSQL and MySQL allow changes through simple views on one table.
Lesson 2 of 4

WITH: common table expressions

A CTE (common table expression) is a view that lives for one statement only. You write WITH name AS (query) before the main SELECT, and the main query, or later CTEs, can read it by name. Long queries become a list of small named steps you can read top to bottom.

Turning a nested subquery into a CTE
  1. Find the innermost subquery in FROM.
  2. Move it to the top: WITH step1 AS ( that subquery ).
  3. Replace it in the main query with the name step1.
  4. Repeat for the next level. The query now reads top to bottom instead of inside out.
Lesson 3 of 4

CTE, subquery, view or temporary table

All four give a name or a place to an intermediate result. They differ in how long they live and whether the rows are stored.

ToolLives forStores rowsUse it when
Subqueryone spot in one querynoa small inner step used once
CTE (WITH)one statementusually noa long query reads better as named steps
Viewuntil droppednomany queries or people need the same logic
Temporary tableuntil the connection closesyesa big result is reused by several statements
Materialized viewuntil dropped, refreshed on demandyesa slow report that may be a little out of date

A materialized view stores the result of its query like a table. Reading it is fast, but it is only as fresh as its last refresh. PostgreSQL writes CREATE MATERIALIZED VIEW and REFRESH MATERIALIZED VIEW, Oracle has them too, SQL Server uses indexed views. SQLite has none, a table filled by INSERT ... SELECT plays the same part.

Real world scenario: the morning sales dashboard

A retail chain shows managers yesterday’s sales by store on a dashboard. The query scans millions of rows and takes a minute. The team stores it as a materialized view and refreshes it at 6 every morning. Opening the dashboard now takes a fraction of a second, and nobody minds that it ignores sales from the last few hours.

Remember
SQLite and PostgreSQL 12+ accept WITH x AS MATERIALIZED (...) or NOT MATERIALIZED to ask the planner to compute a CTE once or to fold it into the main query. Without the hint the planner decides.
Lesson 4 of 4

From intuition to research

One idea, four depths

A view is a saved question with a name. A CTE is a named step inside one big question.

Views give logical data independence: programs read the view, and the tables behind it can change. CTEs make long queries readable and let one step be reused several times in the same statement.

The planner usually inlines views and CTEs into the main query, as if you had typed the subquery. Updatable views need a clear mapping from each view row to one base row. CTEs may be computed once and reused when that is cheaper.

Keeping materialized views fresh without recomputing them from scratch is incremental view maintenance, a long running research area. Systems such as Materialize and features like Oracle fast refresh update only the rows affected by each change.

Going deeper: Security through views

In server databases you can GRANT SELECT on a view without granting it on the table behind it. An analyst can then read employees_public, which leaves out salary and phone number, but cannot read the full employees table. Chapter 8.2 covers GRANT and row level security.
