Asking the optimizer: EXPLAIN QUERY PLAN

SQL says what you want, not how to get it. The query optimizer (also called the planner) picks the how: which index, which table first, whether to sort. EXPLAIN QUERY PLAN shows its choice without running the query.

Plan line in SQLiteMeaning
SCAN tread every row of t
SCAN t USING COVERING INDEX iread all of index i, which is smaller than the table
SEARCH t USING INDEX i (col=?)jump into index i, then fetch matching rows
SEARCH t USING INTEGER PRIMARY KEY (rowid=?)jump straight to rows by their key
USE TEMP B-TREE FOR ORDER BYsort the result in a temporary structure
AUTOMATIC COVERING INDEXbuild a throwaway index for this one query
SCALAR SUBQUERY, CORRELATED SCALAR SUBQUERYan inner query run once, or once per outer row
Remember
PostgreSQL and MySQL write EXPLAIN, and EXPLAIN ANALYZE also runs the query and reports real row counts and times. SQL Server shows graphical execution plans. The ideas are the same.
Lesson 2 of 5

How joins are executed

A join is a question, and engines have several algorithms to answer it. The optimizer also picks the join order: which table drives the loop.

AlgorithmHow it worksGood when
Nested loopfor each row of the outer table, look up matching rows in the inner tablethe inner table has an index on the join column
Hash joinbuild a hash table of the smaller input, then probe it with each row of the otherbig unsorted inputs, equality joins (PostgreSQL, MySQL 8, SQL Server)
Merge joinsort both inputs on the key, then walk them side by sideinputs already sorted, for example by an index
Cost of a nested loop join
  1. Outer table with N rows, inner table with M rows.
  2. Without an index: each outer row scans the inner table.
  3. With an index on the inner join column: each outer row does about log M steps.
  4. N × M without an index, about N × log M with one

Statistics and the cost based optimizer

Most optimizers are cost based: they estimate how many rows each step returns and pick the plan with the lowest estimated cost. The idea goes back to IBM’s System R (Selinger and colleagues, 1979). Estimates come from statistics about the data.

EngineGather statisticsSee estimates and reality
SQLiteANALYZE, or PRAGMA optimizeEXPLAIN QUERY PLAN
PostgreSQLANALYZE (autovacuum runs it automatically)EXPLAIN ANALYZE: estimated rows versus actual rows
MySQLANALYZE TABLEEXPLAIN ANALYZE (8.0.18+)
SQL ServerUPDATE STATISTICS, automatic by defaultactual execution plan
Real world scenario: the report that got slow overnight

A sales report ran in one second for months, then suddenly took two minutes. A bulk import had added millions of rows, but the statistics still described the old, small table. The optimizer kept choosing a nested loop that was perfect for a few rows. Running ANALYZE gave it fresh numbers, it switched to a hash join, and the report was fast again.

Remember
When estimated and actual row counts in EXPLAIN ANALYZE differ by a factor of 10 or more, look at statistics first. Bad estimates are the most common cause of bad plans.
Lesson 4 of 5

Writing queries the optimizer can help

Many slow queries are fixed by small rewrites. A condition the engine can answer with an index is called sargable (search argument able).

Slow patternFaster rewrite
WHERE substr(order_date, 1, 7) = '2025-06'WHERE order_date >= '2025-06-01' AND order_date < '2025-07-01'
WHERE price * 1.18 > 1000WHERE price > 1000 / 1.18
SELECT * when you need two columnsname the columns, which may allow a covering index
LIMIT 10 OFFSET 100000keyset paging: WHERE id > last_seen_id ORDER BY id LIMIT 10
one query per customer inside a loop in the appone query with a JOIN or IN for all customers
Real world scenario: the N+1 problem

A web page lists 50 customers with their order counts. The code runs one query for the customers, then one more query per customer: 51 queries, each with network delay. Rewriting it as one query with a JOIN and GROUP BY returns the same page in a single round trip. ORM tools make this mistake easy, and most offer eager loading to avoid it.

Lesson 5 of 5

From intuition to research

One idea, four depths

The database decides how to run your query. EXPLAIN shows its plan, and you can help with indexes and simple conditions.

Read plans for scans, searches and sorts. Know nested loop, hash and merge joins. Keep statistics fresh. Write sargable predicates and avoid N+1 query patterns.

Optimizers enumerate join orders with dynamic programming (System R) or rule based search spaces (Volcano and Cascades, Graefe 1993 to 1995). Cardinality estimation errors grow with each join and are the main source of bad plans (Leis et al., "How Good Are Query Optimizers, Really", VLDB 2015).

Research explores learned optimizers and learned cardinality estimators, adaptive query processing that changes plan mid flight, and worst case optimal join algorithms for many way joins.

Going deeper: Why join order matters so much

Joining 3 tables of 1,000, 1,000,000 and 10 rows: starting with the 10 row table and reaching the others by index touches a few thousand rows. Starting with the million row table and nesting the others without indexes can touch billions. For n tables there are n! orders, so optimizers prune the search with dynamic programming and heuristics.
