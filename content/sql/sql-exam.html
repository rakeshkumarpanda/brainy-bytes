Remember
In almost every written exam, first say the logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. It explains half of the tricky questions on aliases, WHERE versus HAVING and window functions.

School and first year questions

School boards and first year courses ask short, precise questions. Here are typical ones with model answers on the school database.

Short answer questionModel answer
Difference between WHERE and HAVINGWHERE filters rows before grouping, HAVING filters groups after grouping, and only HAVING can use aggregates
Difference between DELETE, DROP and TRUNCATEDELETE removes chosen rows, DROP removes the table itself, TRUNCATE removes all rows quickly (SQLite uses DELETE without WHERE)

What is a foreign keya column whose values must exist in the primary key of another table

Lesson 4 of 6

A design question, answered

University papers often ask you to design a schema from a story, then normalize it and write queries. Here is a full answer.

Real world scenario: the question

"A college runs clubs. Each club has a name and a faculty adviser. Students can join many clubs, and each membership records the joining date and the student’s role (member, secretary, president). Each club has at most one president. Design the tables, state the keys, show the schema is in 3NF, and write a query listing each club with its president."

Why the schema is in 3NF
  1. Every cell holds one value, so it is in 1NF.
  2. memberships has key (student_id, club_id), and joined_on and role depend on the whole pair, so it is in 2NF.
  3. The adviser’s name depends on the adviser, so it lives in advisers, not in clubs. No non key column depends on another non key column, so it is in 3NF.
  4. Business rules are constraints: role is checked, one president per club is a partial unique index.

Lesson 6 of 6

Where to go next

One idea, four depths

You can ask a database clear questions: filter, sort, group and join. Keep practising on real data you care about, such as your expenses or a sports table.

You can design schemas, write window functions and recursive queries, read plans and use transactions. Build a small app with PostgreSQL or SQLite and write its queries by hand.

Go deeper into internals: read the SQLite architecture pages, PostgreSQL’s planner and MVCC documentation, and Database System Concepts or the CMU database course lectures by Andy Pavlo.

Research directions: query optimization, transaction processing at scale, learned database components, and natural language to SQL. Read papers from SIGMOD, VLDB and CIDR, starting with the classics cited in each chapter here.

Going deeper: Practice sites and datasets

Practise with public datasets such as the Chinook music store or Northwind sample databases, government open data portals, and interview practice sites that offer SQL problems. Run everything in a local SQLite or PostgreSQL, so you also learn to load data and create indexes.
