NULL means unknown

A form asks for your phone number and you leave it blank. The database does not know your number. It is not zero, not an empty string, simply unknown. SQL writes that as NULL. Because NULL is unknown, almost every operation on it gives unknown too: unknown plus 5 is still unknown.

In the exam
Oracle treats an empty string '' as NULL. SQLite, PostgreSQL, MySQL and SQL Server keep them different. This is a common surprise when moving data between engines.

Three valued logic: TRUE, FALSE and UNKNOWN

Because of NULL, SQL logic has three answers: TRUE, FALSE and UNKNOWN (written as NULL). The rules follow common sense. If you know one side of an AND is false, the whole AND is false, whatever the unknown side is. If you know one side of an OR is true, the whole OR is true.

ABA AND BA OR B
TRUENULLNULLTRUE
FALSENULLFALSENULL
NULLNULLNULLNULL

The big rule for queries: WHERE keeps a row only when the condition is TRUE. FALSE and UNKNOWN rows are both dropped. This is why a test such as city <> 'Pune' silently leaves out customers whose city is NULL.

Why the count does not add up
  1. 8 customers in total.
  2. city = 'Pune' keeps 2 rows (Asha, Kabir).
  3. city <> 'Pune' keeps 5 rows.
  4. 2 + 5 = 7, not 8. Arjun, with a NULL city, is in neither answer

NULL traps: NOT IN, aggregates and DISTINCT

Three places where NULL changes answers in ways that surprise even experienced developers.

1. NOT IN with a NULL in the list

2. Aggregates skip NULLs

3. Grouping and DISTINCT treat NULLs as one group

For GROUP BY, DISTINCT and UNION, all NULLs are put together as if they were equal. But a UNIQUE column may hold many NULLs, because two unknowns are not known to be the same. The SQLite documentation lists exactly these rules.

Lesson 4 of 4

From intuition to research

One idea, four depths

NULL is a question mark. Sums with a question mark are question marks, and a question mark never passes a strict test.

SQL uses three valued logic. WHERE, HAVING and ON keep only TRUE. CHECK constraints are the opposite: they reject only FALSE, so a NULL passes a CHECK.

NULL breaks some algebra rules people rely on. x = x is not always TRUE, and NOT (a = b) is not the same as a <> b plus the NULL rows. Query rewrites in optimizers must respect this, which is why NOT IN and NOT EXISTS are not always interchangeable.

Codd later proposed two different kinds of missing value: applicable but unknown, and not applicable. Researchers such as Date and Darwen argued against NULL entirely and for designs that avoid it. Modern database theory studies certain answers: results that are true for every possible value the NULLs might take.

Going deeper: CHECK and NULL

The shop table has CHECK (price > 0). Inserting a price of NULL would pass that check, because NULL > 0 is UNKNOWN, not FALSE. That is why the column also says NOT NULL. Use both together when a value must exist and follow a rule.
