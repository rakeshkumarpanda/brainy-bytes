One language, one standard, many dialects

SQL is an international standard, ISO/IEC 9075. Every engine follows its core, then adds its own extras and spellings. Those local versions are called dialects. The SELECT, JOIN, GROUP BY and window functions you learned work almost everywhere.

VersionNotable additions
SQL-86 and SQL-89the first standard: SELECT, INSERT, UPDATE, DELETE, basic constraints
SQL-92explicit JOIN syntax, CASE, CAST, more data types, schema changes
SQL:1999recursive CTEs (WITH RECURSIVE), triggers, roles, boolean type
SQL:2003window functions, MERGE, sequences and identity columns
SQL:2008 and SQL:2011FETCH FIRST, TRUNCATE, temporal (system versioned) tables
SQL:2016JSON functions, row pattern recognition (MATCH_RECOGNIZE)
SQL:2023property graph queries (SQL/PGQ), a JSON data type
Remember
Each engine documents how closely it follows the standard. PostgreSQL publishes a feature by feature list, and SQLite lists its quirks on one page. When in doubt, read the engine’s own documentation.

Common mistake
Moving a database between engines usually breaks on dates, booleans, auto ids and string concatenation, not on SELECT or JOIN. Test those first.

Choosing an engine

There is no best database, only a best fit. These are the engines you are most likely to meet.

EngineStrengthsTypical home
SQLitea single file, no server, zero setup, extremely widely deployedphones, browsers, desktop apps, small sites, tests
PostgreSQLrich features, strict standards, extensions (PostGIS, pgvector), open sourceweb apps, analytics, geospatial
MySQL and MariaDBsimple to run, fast reads, huge hosting supportweb apps, content management systems
SQL Serverdeep Windows and .NET integration, strong toolsenterprise apps, reporting
Oraclevery large enterprise workloads, many advanced featuresbanks, telecom, large enterprises
DuckDBin process analytics on files such as CSV and Parquetdata science notebooks, local analytics
Questions that decide
  1. Is there one user on one device, or many users over a network. One device points to SQLite.
  2. How much data, and is it mostly small transactions or big reports. Reports point to a column store.
  3. Which features are needed: JSON, full text search, geospatial, vectors.
  4. What does the team already know, and what can it run and back up reliably.
Real world scenario: one app, three databases

A food delivery startup keeps orders and payments in PostgreSQL, caches menus in Redis, and copies everything nightly into BigQuery for reports. Each phone app also keeps a small SQLite database for offline use. Using the right engine for each job is normal in real systems.

Lesson 5 of 5

From intuition to research

One idea, four depths

SQL is one language with local accents. The core you learned works everywhere, and small things such as dates and quoting differ.

Know the standard versions and the common differences, prefer standard functions, and test on the engine you deploy to.

Dialect gaps are handled by ORMs, query builders and transpilers such as SQLGlot, which parse one dialect and print another. Conformance is measured feature by feature against ISO/IEC 9075 parts, such as Foundation (part 2) and SQL/JSON.

Research looks at automatically translating and verifying SQL across engines, at formal semantics of SQL (proving two queries always return the same rows), and at natural language to SQL with large language models, measured on benchmarks such as Spider and BIRD.

Going deeper: Why SQL has lasted

SQL started as SEQUEL at IBM in 1974 (Chamberlin and Boyce), built on Codd’s relational model. Many languages tried to replace it, yet it remains the common language of data, because it describes what to find and leaves the how to the engine, so each new engine can be faster without changing your queries.
