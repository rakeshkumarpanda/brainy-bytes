SQL injection: when input becomes code

SQL injection has been one of the most common and damaging web security flaws for over twenty years. It happens when a program builds SQL by gluing user input into the text, so specially crafted input changes what the SQL means.

Typed into the name boxEffect when glued into SQL
x' OR '1'='1' --every row matches, the login check is skipped
x' followed by a second statement such as DROP TABLE usersa second statement, on engines and drivers that allow several statements per call
x' UNION SELECT pin, role FROM users --other data is pulled into the page
Common mistake
This page shows attacks only so you can recognise and prevent them, on a throwaway table in your own browser. Testing systems you do not own or have no permission to test is illegal in most countries.
Lesson 2 of 5

The fix: parameterized queries

The reliable fix is a parameterized query (also called a prepared statement with bound parameters). The SQL text has placeholders, and the values travel separately. The database parses the SQL first, so a value can never become code.

# Python (sqlite3)
cur.execute("SELECT name, role FROM users WHERE name = ? AND pin = ?", (name, pin))

// JavaScript (node-postgres)
await client.query("SELECT name, role FROM users WHERE name = $1 AND pin = $2", [name, pin]);

// Java (JDBC)
PreparedStatement ps = conn.prepareStatement("SELECT name, role FROM users WHERE name = ? AND pin = ?");
ps.setString(1, name); ps.setString(2, pin);
DefenceNotes
Parameterized queriesthe main defence, use them for every value
ORMs and query buildersparameterize for you, but raw SQL inside them still needs care
Allow lists for namestable and column names cannot be parameters, so pick them from a fixed list in code
Least privilegethe app account cannot DROP tables, so a mistake does less damage
Escaping by handa last resort, easy to get wrong
Sorting by a column the user picks, safely
  1. The user picks "price" from a menu.
  2. The code checks it against a fixed list: name, price, stock.
  3. Only then is the column name written into the SQL text.
  4. Values, such as a search word, still go in as parameters.

Users, roles and GRANT

Server databases have accounts. Each account gets only the rights it needs, the principle of least privilege. SQLite has no accounts: whoever can open the file can read it, so it relies on the operating system’s file permissions.

-- PostgreSQL
CREATE ROLE reporting;
GRANT SELECT ON orders, customers TO reporting;
CREATE USER analyst WITH PASSWORD '...' IN ROLE reporting;
REVOKE SELECT ON customers FROM reporting;

-- MySQL
CREATE USER 'shop_app'@'%' IDENTIFIED BY '...';
GRANT SELECT, INSERT, UPDATE ON shop.* TO 'shop_app'@'%';
AccountNeedsShould not have
Web appSELECT, INSERT, UPDATE on its tablesDROP, ALTER, access to other databases
ReportingSELECT on a few tables or viewsany write
Migrations toolCREATE, ALTER, DROPto be used by the running app
Administratoreverythingto be used for daily work

Row level security and personal data

Sometimes users may see the same table but only their own rows: each customer sees only their orders. Row level security makes the database add that filter automatically.

-- PostgreSQL (9.5+)
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY own_orders ON orders
  USING (customer_id = current_setting('app.customer_id')::int);
ProtectHow
Passwordsnever store them. Store a slow salted hash (Argon2id or bcrypt) computed in the app
Personal data on screensmask it: a***@mail.in, last 4 digits of a card
Data on diskencryption at rest: TDE in SQL Server and Oracle, disk encryption, SQLCipher for SQLite
Data on the networkTLS between app and database
Mistakes and attacksbackups you have tested restoring, and audit logs of who changed what
Lesson 5 of 5

From intuition to research

One idea, four depths

Never glue typed text into SQL. Give every account only the rights it needs. Protect personal data.

Parameterized queries everywhere, allow lists for identifiers, roles with GRANT and REVOKE, views and row level security, hashing for passwords, TLS and backups.

Defence in depth: assume one layer fails. Second order injection stores harmful text that is later glued into SQL by another part of the system. Audit logging, separation of duties and key management complete the picture.

Research covers differential privacy (adding calibrated noise so aggregate queries reveal little about any one person), encrypted query processing such as CryptDB (2011), and automatic detection of injection with static analysis and taint tracking.

Going deeper: Differential privacy in one paragraph

A query is differentially private when its answer barely changes whether or not any single person is in the data. Systems add random noise sized to the query, for example to a COUNT. The US Census Bureau used differential privacy for its 2020 census results.
