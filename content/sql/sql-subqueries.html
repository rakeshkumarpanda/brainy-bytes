Lesson 1 of 5

A query inside a query

"Which products cost more than the average price?" has two steps: first work out the average, then compare each product with it. A subquery lets you write both steps in one statement. The inner query, in brackets, runs first and hands its answer to the outer query.

A subquery that returns exactly one value is called a scalar subquery. You can use it anywhere a single value fits: in WHERE, in the SELECT list, even inside a calculation.

Common mistake
If a scalar subquery returns more than one row, SQLite quietly uses the first row, while PostgreSQL and SQL Server raise an error. Make sure a scalar subquery can only return one row, for example with an aggregate or a key lookup.
Lesson 2 of 5

IN and NOT IN with a list from a query

A subquery can also return a whole column of values. IN then checks whether a value is in that list. "Customers who placed an order" is "customers whose id is in the list of customer ids in orders".

Common mistake
Remember the NULL trap from chapter 2.2: if the subquery list contains even one NULL, NOT IN returns no rows at all. NOT EXISTS, in the next lesson, does not have this problem.

EXISTS and correlated subqueries

A correlated subquery refers to a column of the outer query, so it runs again for every outer row, like a question asked about each person in turn. EXISTS is true when the subquery returns at least one row. It does not care what the row contains, which is why people write SELECT 1 inside it.

Lesson 4 of 5

Subqueries in FROM: derived tables

A subquery in the FROM clause builds a temporary table that the outer query reads like any other table. It is called a derived table and it must have an alias. It is perfect for "aggregate first, then filter or join the aggregate".

That query repeats the same inner query twice. Chapter 4.3 introduces WITH (common table expressions), which names a subquery once and reuses it, making such queries much easier to read.

Real world scenario: the loyalty programme

A shop wants to send a gift to customers who spend more than the average customer. The analyst first builds "spend per customer" as a derived table, then compares each row with the average of that table. Two clear steps, one query, and the marketing team gets the list in seconds.

Lesson 5 of 5

From intuition to research

One idea, four depths

A subquery is a small question you answer first, so the big question can use the answer.

Scalar subqueries return one value, IN subqueries one column, derived tables a whole table. Correlated subqueries are evaluated per outer row, at least logically.

Optimizers unnest subqueries: an IN or EXISTS subquery becomes a semi join, NOT EXISTS an anti join, and a correlated scalar subquery a join with a grouped derived table. After unnesting, the join algorithms from chapter 3.2 apply.

Decorrelation of arbitrary nested queries is an active research topic. A 2015 paper by Neumann and Kemper, Unnesting Arbitrary Queries, showed a general method that removes correlation from any subquery, and systems such as Umbra and DuckDB build on it.

Going deeper: Rewriting a correlated subquery as a join

The "most expensive product per category" query can be written as a join to a derived table: JOIN (SELECT category, MAX(price) AS top FROM products GROUP BY category) AS m ON m.category = p.category AND p.price = m.top. Window functions in chapter 6.1 give a third way.
