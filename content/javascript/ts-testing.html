Part 1

🛡️Why write tests in TypeScript

🧪 QA essentialTyped tests fail fast on mistakes in the test itself, so red builds point at real product bugs more often.

Test code is code. It has typos, wrong arguments and missing awaits, and in JavaScript you only find them when the test runs, often in CI, often after a slow browser start. TypeScript finds them while you type. Every Playwright, Vitest and Jest API ships its own types, so the editor knows every fixture, locator method and matcher.

Three test mistakes caught before the browser starts · 🔷 tsc finds 3 errors
📄 src/cart.spec.ts
import { test, expect } from "@playwright/test";

test("add a pen to the cart", async ({ page, shopp }) => {     // a typo in a fixture name
  await page.goto("/");
  await page.getByRol("button", { name: "Add to cart" }).click(); // a typo in a method name
  await expect(page.getByTestId("cart-count")).toHaveText(1);  // a number where text is expected
});

Part 2

🧪Unit tests in TypeScript

🧪 QA essentialKnowing which runners strip types and which check them avoids a green suite full of type errors.

Node.js 24 and later remove the types and run .ts files directly, so node --test needs no build step. Vitest reads TypeScript too, without any set up. In both cases the runner only strips the types and does not check them, so run tsc as its own step.

node:test runs .ts files directly · 🔷 tsc passes, then node:test runs
📄 src/cart.ts
export interface Line { sku: string; price: number; qty: number }
export type Coupon = "SAVE10" | "SAVE20";

const RATES: Record<Coupon, number> = { SAVE10: 0.1, SAVE20: 0.2 };

export function cartTotal(lines: Line[], coupon?: Coupon): number {
  const sum = lines.reduce((total, l) => total + l.price * l.qty, 0);
  return Math.round(sum * (1 - (coupon ? RATES[coupon] : 0)));
}
📄 src/cart.test.ts
import { test } from "node:test";

const lines: Line[] = [{ sku: "pen", price: 20, qty: 3 }, { sku: "mug", price: 199, qty: 1 }];

Vitest with TypeScript and no extra set up · 🔷 tsc passes, then Vitest runs
📄 src/cart.test.ts
import { describe, it, expect, expectTypeOf } from "vitest";
import { cartTotal, type Coupon, type Line } from "./cart.ts";

describe("cartTotal", () => {
  const pen: Line = { sku: "pen", price: 20, qty: 5 };

  it.each<[Coupon | undefined, number]>([
    [undefined, 100],
    ["SAVE10", 90],
    ["SAVE20", 80],
  ])("coupon %s gives %i", (coupon, want) => {
    expect(cartTotal([pen], coupon)).toBe(want);
  });

  it("has the types the rest of the suite relies on", () => {
    expectTypeOf(cartTotal).returns.toEqualTypeOf<number>();
    expectTypeOf(cartTotal).parameter(1).toEqualTypeOf<Coupon | undefined>();
  });
});

Jest with TypeScript · Set up only. The test code itself is the same as above.
// Jest does not read TypeScript by itself. Pick one transformer:
//   ts-jest      type checks while it runs (slower, catches more)
//   @swc/jest    or babel-jest: removes the types only (fast, run tsc separately)

// jest.config.ts
import type { Config } from "jest";

const config: Config = {
  preset: "ts-jest",                 // or: transform: { "^.+\\.tsx?$": "@swc/jest" }
  testEnvironment: "node",
  testMatch: ["**/*.test.ts"],
};
export default config;

// tsconfig.json for the tests: "types": ["jest", "node"] gives describe, it and expect their types
Removing types is not checking types. A test file full of type errors still runs green under node --test, Vitest or @swc/jest. Only tsc (or ts-jest) reports them. That is why every example on this page runs tsc first.
Part 3

🔬Type tests

🧪 QA essentialType tests stop a helper change from quietly breaking the types that the rest of the suite depends on.

Shared helpers, builders and API clients are used by hundreds of tests, so their types are part of their contract. expectTypeOf from Vitest (and the expect-type package it is built on) asserts on types instead of values. Nothing runs. The check happens when tsc reads the file.

Type tests: tests for the types themselves · 🔷 tsc finds 1 error
📄 src/user.test-d.ts
import { expectTypeOf } from "vitest";

type Role = "admin" | "customer";
interface User { id: number; email: string; role: Role }

// A helper the whole suite uses. Its type is part of its contract.
function makeUser(overrides: Partial<User> = {}): User {
  return { id: 1, email: "asha@shop.test", role: "customer", ...overrides };
}

expectTypeOf(makeUser).returns.toEqualTypeOf<User>();
expectTypeOf(makeUser).parameter(0).toEqualTypeOf<Partial<User> | undefined>();
expectTypeOf<User["role"]>().toEqualTypeOf<"admin" | "customer" | "guest">();   // somebody expects a guest role
Terminal
$ npx tsc
Terminal output
src/user.test-d.ts(13,44): error TS2344: Type '"admin" | "customer" | "guest"' does not satisfy the constraint '"Expected: literal string: admin, Actual: never" | "Expected: literal string: customer, Actual: never" | "Expected: literal string: guest, Actual: never"'.
  Type '"admin"' is not assignable to type '"Expected: literal string: admin, Actual: never" | "Expected: literal string: customer, Actual: never" | "Expected: literal string: guest, Actual: never"'.

Type test messages are long because the library builds them out of types. Read the line number first. It points at the assertion that no longer holds, here the role union that has no guest.

Vitest can also collect these files with vitest --typecheck, which runs tsc for you on every *.test-d.ts file and shows type failures next to normal test failures.

Part 4

🎭Playwright in TypeScript

🧪 QA essentialPlaywrightTyped page objects and typed fixtures are the standard way to write Playwright suites in teams.

Playwright runs TypeScript without any set up, and most Playwright documentation is written in it. Two things become much better with types. Page objects can limit their inputs, for example to real product names. Fixtures declared with test.extend<{ shop: ShopPage }> are typed in every test, so ({ shop }) auto completes and a typo does not compile.

Typed page objects and typed fixtures in Playwright · 🔷 tsc passes, then Playwright runs in Chromium
📄 pages/shop.page.ts
import { expect, type Locator, type Page } from "@playwright/test";

export type Product = "Gel pen" | "Coffee mug" | "Desk lamp";

export class ShopPage {
  readonly products: Locator;
  readonly cartCount: Locator;
  readonly total: Locator;

  constructor(readonly page: Page) {
    this.products = page.getByTestId("product");
    this.cartCount = page.getByTestId("cart-count");
    this.total = page.locator("#total");
  }
  async open(): Promise<this> {
    await this.page.goto("/");
    return this;
  }
  async logIn(email: string, password: string): Promise<void> {
    await this.page.getByLabel("Email").fill(email);
    await this.page.getByLabel("Password").fill(password);
    await this.page.getByRole("button", { name: "Sign in" }).click();
    await expect(this.products.first()).toBeVisible();
  }
  async add(name: Product): Promise<void> {     // only real product names compile
    await this.products.filter({ hasText: name }).getByRole("button", { name: "Add to cart" }).click();
  }
}
📄 fixtures.ts
import { test as base } from "@playwright/test";
import { ShopPage } from "./pages/shop.page.ts";

interface TestUser { email: string; password: string }

// The type argument tells every test which fixtures exist and what they hold
export const test = base.extend<{ user: TestUser; shop: ShopPage }>({
  user: [{ email: "asha@shop.example", password: "s3cret" }, { option: true }],
  shop: async ({ page, user }, use) => {
    const shop = await new ShopPage(page).open();
    await shop.logIn(user.email, user.password);
    await use(shop);
  },
});
export { expect } from "@playwright/test";

Part 5

🔌A typed API client with run time checks

🧪 QA essentialAPI tests that parse every response with a schema catch contract changes on the first call.

TypeScript types disappear at run time, so they cannot check JSON from a server. A schema library such as zod does both jobs at once. The schema checks the data at run time, and z.infer turns the same schema into a TypeScript type, so the two can never drift apart.

A typed API client that checks every response with zod · 🔷 tsc passes, then node:test runs
📄 src/client.ts
import { z } from "zod";

// One schema gives both the run time check and the TypeScript type
export const Product = z.object({ id: z.number().int(), name: z.string().min(1), price: z.number().nonnegative() });
export type Product = z.infer<typeof Product>;

export class ProductsClient {
  private readonly baseURL: string;
  constructor(baseURL: string) { this.baseURL = baseURL; }

  async list(query = ""): Promise<Product[]> {
    const res = await fetch(`${this.baseURL}/products${query}`);
    if (!res.ok) throw new Error(`GET /products answered ${res.status}`);
    return z.array(Product).parse(await res.json());   // unknown JSON in, typed data out
  }
}
📄 test/products.test.ts
import { test, after } from "node:test";
import assert from "node:assert/strict";
import type { AddressInfo } from "node:net";
import { z } from "zod";
import { startApi } from "../src/server.ts";
import { ProductsClient } from "../src/client.ts";

const server = await startApi();
const api = new ProductsClient(`http://localhost:${(server.address() as AddressInfo).port}`);
after(() => server.close());

test("products match the contract", async () => {
  const products = await api.list();
  assert.equal(products.length, 2);
  assert.equal(products[0].price + products[1].price, 219);   // price is a number here, the type says so
});

test("a changed field type is caught at the edge", async () => {
  await assert.rejects(api.list("?v=2"), (e: unknown) => {
    assert.ok(e instanceof z.ZodError);
    console.log(z.prettifyError(e));
    return true;
  });
});

Part 6

🚦TypeScript in CI

🧪 QA essentialA fast type gate keeps broken test code out of the expensive browser jobs.

Put the type check in front of everything slow. It needs no browser and no server, and it fails in seconds. Type aware lint rules from typescript-eslint add checks that tsc does not do, such as a missing await, which is one of the most common causes of flaky tests.

Type check first, browsers second · A CI pipeline, not run on this page
# .github/workflows/tests.yml
name: tests
on: [push, pull_request]

jobs:
  types:                                # fast gate: fails in about 30 seconds
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx tsc --noEmit           # type errors in tests or helpers stop here
      - run: npx eslint .               # with typescript-eslint: no floating promises, no any

  e2e:
    needs: types                        # browsers start only when the types are clean
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
typescript-eslint rules that catch flaky tests · Lint set up, not run on this page
// eslint.config.js: rules that only work with type information
import tseslint from "typescript-eslint";

export default tseslint.config(
  ...tseslint.configs.recommendedTypeChecked,
  {
    languageOptions: { parserOptions: { projectService: true } },
    rules: {
      "@typescript-eslint/no-floating-promises": "error",   // a missing await before expect or click
      "@typescript-eslint/no-explicit-any": "error",
      "@typescript-eslint/await-thenable": "error",          // await on something that is not a promise
    },
  },
);
Part 7

🎬Real world scenario: typed test data builders

🧪 QA essential
The situationTest data is copied between tests as large object literals. When the User type gained an address field, 140 tests broke at run time.
Typed test data builders · 🔷 tsc passes, then Node.js runs it
📄 src/main.ts
// Typed test data builders: sensible defaults, typed overrides, unique ids
type Role = "admin" | "customer";
interface Address { city: string; pin: string }
interface User { id: number; email: string; role: Role; address: Address }
interface Order { id: number; user: User; items: { sku: string; qty: number }[]; status: "new" | "paid" | "shipped" }

let next = 1000;
const id = () => ++next;

function builder<T>(defaults: () => T) {
  return (overrides: Partial<T> = {}): T => ({ ...defaults(), ...overrides });
}

const aUser = builder<User>(() => ({ id: id(), email: `user${next}@shop.test`, role: "customer", address: { city: "Pune", pin: "411001" } }));
const anOrder = builder<Order>(() => ({ id: id(), user: aUser(), items: [{ sku: "pen", qty: 1 }], status: "new" }));

const admin = aUser({ role: "admin" });
const paid = anOrder({ user: admin, status: "paid" });
const big = anOrder({ items: [{ sku: "lamp", qty: 2 }, { sku: "mug", qty: 4 }] });

console.log(admin.email, admin.role, paid.status, paid.user.id === admin.id);
console.log(big.items.length, big.user.role, big.id > paid.id);
Terminal
$ npx tsc && node src/main.ts
Terminal output
tsc: no type errors

$ node src/main.ts
user1001@shop.test admin paid true
2 customer true

Each builder holds the defaults in one place and gives every object a fresh id, so tests stay independent. Overrides are Partial<T>, so a test only writes the fields it cares about, and a misspelt field or a wrong role does not compile. When User gains a field, only the builder needs to change.
