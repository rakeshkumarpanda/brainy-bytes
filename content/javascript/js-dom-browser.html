🌳The DOM tree

🧪 QA essentialEvery locator in Selenium, Playwright and Cypress finds nodes in this tree.

When a browser loads HTML, it builds the DOM (Document Object Model): a tree of objects, one for each element, piece of text and comment. JavaScript reads and changes the page only through this tree, and so does every UI automation tool.

📄 script.js
function xpath(expr, context = document) {
  const r = document.evaluate(expr, context, null, XPathResult.ORDERED_NODE_SNAPSHOT_TYPE, null);
  return Array.from({ length: r.snapshotLength }, (_, i) => r.snapshotItem(i));
}

// Find by visible text, which CSS cannot do
console.log(xpath("//h2[text()='Coffee mug']").length);
// Go up to the card that contains that heading, then down to its button
console.log(xpath("//h2[text()='Coffee mug']/ancestor::article//button")[0].textContent);
// Contains, and an index
console.log(xpath("//button[contains(., 'Sold')]").map(b => b.disabled));
console.log(xpath("(//span[@class='price'])[last()]")[0].textContent);

✏️Changing the page

🖱️Events

🧪 QA essentialPlaywrightSeleniumCypressUnderstanding bubbling and trusted events explains "element click intercepted" errors and why forced clicks hide bugs.

Clicks, key presses, input changes and form submits are events. addEventListener(type, handler) runs your function each time one happens. An event travels down from the window to the target (capture), then back up (bubble), so a listener on a parent hears clicks on its children.

const count = document.querySelector("#cart-count");

document.querySelector("#products").addEventListener("click", event => {
  const button = event.target.closest("button.add");
  if (!button || button.disabled) return;
  const sku = button.closest("[data-sku]").dataset.sku;
  count.textContent = Number(count.textContent) + 1;
  console.log(`added ${sku}, target was <${event.target.tagName.toLowerCase()}>, listener on #${event.currentTarget.id}`);
});

document.querySelector('[data-sku="PEN-01"] button').click();
document.querySelector('[data-sku="MUG-03"] button').click();
document.querySelector('[data-sku="BOOK-07"] button').click();   // disabled: click() does nothing
console.log("cart count:", count.textContent);

// A link whose default action is stopped
const deals = document.querySelector("a.hot");
deals.addEventListener("click", e => { e.preventDefault(); console.log("navigation prevented"); });
deals.click();

// Custom events let parts of a page talk to each other
document.addEventListener("cart:changed", e => console.log("custom event:", e.detail));
document.dispatchEvent(new CustomEvent("cart:changed", { detail: { items: 2 } }));

Event delegation uses this: one listener on a list handles every item, including items added later. event.target is what was clicked and event.currentTarget is where the listener sits. preventDefault() stops the browser's own action, such as following a link.

Events created by scripts have isTrusted set to false, and element.click() skips the checks a real user goes through: it works on hidden or covered buttons. That is why Playwright and Selenium move a real mouse and check that the element is visible and not covered before clicking, and why { force: true } clicks can hide real bugs.

📝Forms and validation

🧪 QA essentialForms are the most tested part of any web app, and their validation rules are the source of many test cases.

Form fields hold their current value in value (or checked for checkboxes). HTML attributes such as required, type="email" and min give free validation, which JavaScript reads through checkValidity() and each field's validity. FormData collects every named field in one go.

🧱Shadow DOM, iframes and observers

🧪 QA essentialPlaywrightSeleniumCypressElements inside shadow roots and iframes are the most common reason a correct looking locator finds nothing.

Web components hide their inner elements inside a shadow root. A normal querySelector from the document cannot see inside it. An iframe holds a whole separate document, often for payment forms, maps or embedded editors.

📄 script.js
// Resolve when an element matching the selector exists, or reject after a timeout
function waitForElement(selector, timeout = 1000) {
  return new Promise((resolve, reject) => {
    const found = document.querySelector(selector);
    if (found) return resolve(found);
    const observer = new MutationObserver(() => {
      const el = document.querySelector(selector);
      if (el) { observer.disconnect(); clearTimeout(timer); resolve(el); }
    });
    observer.observe(document.body, { childList: true, subtree: true });
    const timer = setTimeout(() => { observer.disconnect(); reject(new Error(`${selector} not found in ${timeout} ms`)); }, timeout);
  });
}

// The "app" renders results after a fake network delay
setTimeout(() => {
  document.querySelector("#results").innerHTML = '<ul class="list"><li>Gel pen</li><li>Fountain pen</li></ul>';
}, 200);

const list = await waitForElement(".list");
console.log("appeared with", list.children.length, "items");
await waitForElement(".no-such-thing", 300).catch(e => console.log(e.message));

🎨How the browser draws the page

🧪 QA essentialPlaywrightCypressSeleniumClicks fail on elements that are still moving or covered, and visual tests compare painted pixels.

Changing the DOM does not change the screen straight away. The browser collects your changes and then runs its rendering pipeline, usually 60 times a second, between tasks of the event loop (chapter 2).

  1. Parse the HTML into the DOM and the CSS into the CSSOM.
  2. Style: work out which CSS rules apply to every element.
  3. Layout (also called reflow): work out the size and position of every box.
  4. Paint: fill in the pixels for text, colours, borders and images, in layers.
  5. Composite: put the layers together on the screen, often on the GPU.

Each step costs time, and changes restart the pipeline from different points. Changing width needs layout, paint and composite. Changing color skips layout. Changing transform or opacity can skip both layout and paint, which is why smooth animations use them.

Working with the rendering loop · Browser code, shown here
// 1. Animate with requestAnimationFrame: the browser calls you right before it paints
const box = document.querySelector(".progress");
let width = 0;
function frame() {
  width += 2;
  box.style.width = width + "%";
  if (width < 100) requestAnimationFrame(frame);   // once per screen refresh, paused in hidden tabs
}
requestAnimationFrame(frame);

// 2. Layout thrashing: reading a size right after a write forces a layout every time
for (const row of rows) {
  row.style.height = "40px";        // write
  total += row.offsetHeight;        // read, so the browser must lay out the page now
}
// Better: read everything first, then write everything
const heights = rows.map(r => r.offsetHeight);
rows.forEach(r => (r.style.height = "40px"));

// 3. IntersectionObserver: load images or more results only when they scroll into view
const io = new IntersectionObserver(entries => {
  for (const e of entries) if (e.isIntersecting) { e.target.src = e.target.dataset.src; io.unobserve(e.target); }
});
document.querySelectorAll("img[data-src]").forEach(img => io.observe(img));

// 4. A long task blocks all of this. Give the browser a turn in long loops.
let done = 0;
for (const item of hugeList) {
  process(item);
  if (++done % 50 === 0) await scheduler.yield();   // Chrome and Edge, or await new Promise(r => setTimeout(r))
}

Many "element not clickable" and "element is not stable" errors come from this pipeline: the element exists in the DOM but is still moving, hidden behind another layer or not laid out yet. Playwright waits for an element to be visible, stable and able to receive events before clicking. Visual regression tests compare the result of paint and composite, so they need fonts loaded and animations turned off.

const money = text => Number(text.replace(/[^\d.]/g, ""));
const headers = [...document.querySelectorAll("#orders thead th")].map(th => th.textContent);
const rows = [...document.querySelectorAll("#orders tbody tr")].map(tr =>
  Object.fromEntries([...tr.cells].map((td, i) => [headers[i], td.textContent])));

const problems = [];
for (const r of rows) {
  const expected = Number(r.Qty) * money(r.Price);
  if (expected !== money(r["Line total"])) {
    problems.push(`${r.Order}: ${r.Qty} x ${r.Price} should be ${expected}, page shows ${r["Line total"]}`);
  }
}
const sum = rows.reduce((s, r) => s + money(r["Line total"]), 0);
const shownTotal = money(document.querySelector("#orders tfoot td:last-child").textContent);
if (sum !== shownTotal) problems.push(`total: rows add up to ${sum}, footer shows ${shownTotal}`);

console.log(rows.length, "rows checked");
console.log(problems.length ? problems : "all good");
Output
4 rows checked
[ '#1045: 2 x ₹1,299.00 should be 2598, page shows ₹2,589.00' ]

Reading the header cells first turns each row into an object keyed by column name, so the check keeps working if a column is added or moved. The footer does match the rows as shown, so a check of the total alone would have missed this bug. Only the line by line check catches it.
