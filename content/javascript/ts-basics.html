Part 1

🔷What TypeScript is and how it runs

🧪 QA essentialPlaywrightCypressWebdriverIOMost modern automation frameworks are written and used in TypeScript.

TypeScript is JavaScript with type annotations. The compiler tsc reads the types and reports mistakes before the code runs. The types are then erased: at run time it is plain JavaScript. Node.js 23.6 and later can run .ts files directly by stripping the types, without checking them, so you use both: tsc to check, Node.js to run.

tsc finds the mistakes, Node.js runs the code anyway · 🔷 tsc finds 2 errors, then Node.js runs it
📄 src/main.ts
// TypeScript is JavaScript plus types. The types are checked by tsc and then removed.
function lineTotal(price: number, qty: number): number {
  return price * qty;
}

const total = lineTotal(40, 3);
const wrong = lineTotal("40", 3);          // a string where a number is expected
const name: string = total;                // a number where a string is expected

console.log(total, wrong, name);
Terminal
$ npx tsc
$ node src/main.ts
Terminal output
src/main.ts(7,25): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
src/main.ts(8,7): error TS2322: Type 'number' is not assignable to type 'string'.

$ node src/main.ts
120 120 120

Notice that Node.js ran the file even with two type errors. Types never change what code does. They are a safety net that only works if tsc runs in your editor and in CI.

A modern tsconfig.json · Explained below
{
  "compilerOptions": {
    "target": "es2024",            // which JavaScript features the output may use
    "module": "nodenext",          // how imports work: Node.js rules for ESM and CommonJS
    "strict": true,                // turn on every strict check, always do this
    "noUncheckedIndexedAccess": true,
    "noEmit": true,                // only type check, Node.js or a bundler runs the .ts files
    "allowImportingTsExtensions": true,
    "erasableSyntaxOnly": true,    // forbid syntax Node.js cannot simply strip, such as enum
    "types": ["node"]              // types for process, Buffer and friends from @types/node
  },
  "include": ["src", "tests"]
}
Playwright, Vitest, Jest (with a transform), Cypress and WebdriverIO all accept TypeScript tests. Most new automation projects are written in TypeScript because locators, fixtures and API responses become typed and the editor completes them.
Part 2

🧱Everyday types

🧪 QA essentialTyped test data and typed API responses catch typos in field names before a test even starts.

Most of the time TypeScript infers the type from the value, so you annotate function parameters, public APIs and empty containers, not every variable. Use readonly for data that must not change, ? for optional properties, and tuples for fixed length lists.

Everyday types, inference, readonly and unknown · 🔷 tsc finds 2 errors, then Node.js runs it
📄 src/main.ts
// Inference: no annotation needed when the value says it all
let retries = 3;                            // number
const browser = "chromium";                 // the literal type "chromium", because const never changes
const tags = ["smoke", "cart"];             // string[]

// Arrays, tuples, objects, optional and readonly
const timings: number[] = [840, 2310];
const pair: [string, number] = ["login", 840];
const user: { readonly id: number; name: string; email?: string } = { id: 7, name: "Asha" };

user.name = "Asha K";
user.id = 8;                                // readonly
retries = "three";                          // number only

// any switches checking off. unknown must be checked before use.
const fromApi: unknown = JSON.parse('{"status": 200}');
// fromApi.status;                          // error: 'fromApi' is of type 'unknown'
if (typeof fromApi === "object" && fromApi !== null && "status" in fromApi) console.log("status", fromApi.status);

console.log(browser, tags, timings, pair, user.email ?? "no email");

Part 3

🧩Functions

Annotate parameters, and let the return type be inferred or write it for public functions. Optional parameters use ?, defaults give both a type and a value, and rest parameters are typed as arrays. Function types describe callbacks, and overloads give one function several typed call shapes.

Typing functions, callbacks and overloads · 🔷 tsc finds 2 errors, then Node.js runs it
📄 src/main.ts
// Parameters and returns, optional and default values, rest parameters
function greet(name: string, greeting = "Hello", punctuation?: string): string {
  return `${greeting}, ${name}${punctuation ?? "!"}`;
}
const sum = (...values: number[]): number => values.reduce((a, b) => a + b, 0);

// A function type, used for callbacks
type Matcher = (actual: string) => boolean;
const startsWith = (prefix: string): Matcher => actual => actual.startsWith(prefix);

// Overloads: one implementation, several typed call shapes
function find(id: number): { id: number };
function find(email: string): { email: string };
function find(key: number | string) {
  return typeof key === "number" ? { id: key } : { email: key };
}

// void for "returns nothing", never for "never returns"
function fail(message: string): never { throw new Error(message); }

console.log(greet("Asha"), greet("Ravi", "Hi", "."), sum(1, 2, 3), startsWith("ORD-")("ORD-7"));
console.log(find(7), find("asha@shop.test"));
greet();                                    // missing argument
sum(1, "2");                                // wrong type in the rest list
try { fail("stop"); } catch (e) { console.log((e as Error).message); }

📐interface and type

🧪 QA essentialInterfaces describe API responses, test data and page object options in typed test projects.

Both interface and type name an object shape. Interfaces can be extended with extends and are merged when declared twice, which suits public object shapes. Type aliases can name anything: unions, tuples, functions and combinations with &. Teams usually pick one style for objects and use type for everything else.

interface and type, extends and intersections · 🔷 tsc finds 1 error, then Node.js runs it
📄 src/main.ts
// interface: a named object shape that can be extended and merged
interface TestResult {
  name: string;
  status: "passed" | "failed" | "skipped";
  durationMs: number;
}
interface RetriedResult extends TestResult {
  retries: number;
}

// type: a name for any type, including unions, tuples and intersections
type Browser = "chromium" | "firefox" | "webkit";
type WithBrowser = TestResult & { browser: Browser };
type ById = Record<string, TestResult>;            // an object with any string keys
type Timings = { [testName: string]: number };     // index signature, the same idea

const r: RetriedResult = { name: "checkout", status: "failed", durationMs: 2310, retries: 2 };
const w: WithBrowser = { name: "login", status: "passed", durationMs: 840, browser: "safari" };
const byId: ById = { t1: r };
const timings: Timings = { login: 840 };

console.log(r.retries, w.browser, Object.keys(byId), timings.login);

Part 5

🔍Unions and narrowing

🧪 QA essentialAPI responses are usually "success or error", which discriminated unions model exactly.

A union such as string | number means "one of these". Before you use a union, you narrow it with a check that TypeScript understands: typeof, instanceof, in, equality, or a shared literal field. Inside each branch, TypeScript knows the exact type.

Unions and narrowing · 🔷 tsc passes, then Node.js runs it
📄 src/main.ts
type ApiResult = { ok: true; data: string[] } | { ok: false; error: string; status: number };

function describe(r: ApiResult): string {
  if (r.ok) return `got ${r.data.length} items`;        // here TypeScript knows r has data
  return `failed with ${r.status}: ${r.error}`;          // and here that r has error and status
}

function formatId(id: string | number | null): string {
  if (id === null) return "none";                        // equality narrowing
  if (typeof id === "number") return `#${id.toFixed(0)}`; // typeof narrowing
  return id.toUpperCase();                               // only string is left
}

class TimeoutError extends Error {
  ms: number;
  constructor(ms: number) { super(`timeout after ${ms} ms`); this.ms = ms; }
}
function retryable(e: unknown): boolean {
  if (e instanceof TimeoutError) return e.ms < 30_000;  // instanceof narrowing
  if (e instanceof Error && "code" in e) return e.code === "ECONNRESET";   // in narrowing
  return false;
}

console.log(describe({ ok: true, data: ["a", "b"] }), "|", describe({ ok: false, error: "down", status: 503 }));
console.log(formatId(7), formatId("ord-7"), formatId(null), retryable(new TimeoutError(5000)));
Terminal
$ npx tsc && node src/main.ts
Terminal output
tsc: no type errors

$ node src/main.ts
got 2 items | failed with 503: down
#7 ORD-7 none true
A union of objects with a common literal field, such as ok: true or ok: false, is a discriminated union. It is the best way to type API results, test outcomes and state machines, and chapter 24 makes it exhaustive.
Part 6

🏷️Enums and their modern alternative

An enum creates a real object at run time, so it is not erasable and fails with erasableSyntaxOnly and with Node.js type stripping. The modern alternative is a plain object marked as const plus a union type made from its values. It works everywhere and accepts both Browser.Firefox and the string "firefox".

enum against as const objects · 🔷 tsc finds 2 errors
📄 src/main.ts
// enum creates real JavaScript, so Node.js cannot just strip it
enum Status { Passed = "passed", Failed = "failed" }

// The erasable alternative: a const object and a union type made from it
const Browser = { Chromium: "chromium", Firefox: "firefox", Webkit: "webkit" } as const;
type Browser = (typeof Browser)[keyof typeof Browser];   // "chromium" | "firefox" | "webkit"

function launch(b: Browser) { return `launching ${b}`; }
console.log(launch(Browser.Firefox), launch("webkit"), Status.Passed);
launch("edge");
Terminal
$ npx tsc
Terminal output
src/main.ts(2,6): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
src/main.ts(10,8): error TS2345: Argument of type '"edge"' is not assignable to parameter of type 'Browser'.

🛡️Strict options

🧪 QA essentialStrict null checks catch the "cannot read properties of undefined" errors that make tests crash.

"strict": true turns on a family of checks. The two that catch the most bugs are strictNullChecks, which makes you handle undefined and null, and noImplicitAny, which stops untyped parameters. noUncheckedIndexedAccess goes further: reading an array element or a record key may give undefined.

What strict mode catches · 🔷 tsc finds 3 errors
📄 src/main.ts
const users = ["asha", "ravi"];
const third = users[2];                   // with noUncheckedIndexedAccess this is string | undefined
console.log(third.toUpperCase());          // could crash at run time, so tsc complains

function len(s) { return s.length; }       // noImplicitAny: s has no type

const config: { timeout?: number } = {};
const ms: number = config.timeout;         // strictNullChecks: it may be undefined

$ npx tsc
Terminal output

Part 8

🎬Real world scenario: typed results from untyped JSON

🧪 QA essential
The situationA dashboard script reads test results from a JSON file written by another tool. Some rows have typos such as "pased" or a duration stored as a string.
Read untyped JSON safely · 🔷 tsc passes, then Node.js runs it
📄 src/main.ts
import { readFileSync } from "node:fs";

interface Result { name: string; status: "passed" | "failed"; ms: number }

// JSON from a file or an API is unknown until it is checked
function isResult(x: unknown): x is Result {
  if (typeof x !== "object" || x === null) return false;
  const r = x as Record<string, unknown>;
  return typeof r.name === "string" && (r.status === "passed" || r.status === "failed") && typeof r.ms === "number";
}

const raw: unknown = JSON.parse(readFileSync("src/results.json", "utf8"));
if (!Array.isArray(raw)) throw new Error("expected a list of results");

const valid = raw.filter(isResult);                 // Result[] from here on
const rejected = raw.length - valid.length;
const failed = valid.filter(r => r.status === "failed").map(r => r.name);
const slowest = valid.toSorted((a, b) => b.ms - a.ms)[0];

console.log({ valid: valid.length, rejected, failed, slowest: slowest?.name });

  { "name": "search", "status": "pased", "ms": 120 },
  { "name": "profile", "status": "passed", "ms": "45" }
]

JSON.parse really returns unknown data, whatever its declared type. A type predicate such as x is Result checks it at run time and tells TypeScript the result, so everything after the filter is fully typed and the bad rows are counted instead of breaking the report.
