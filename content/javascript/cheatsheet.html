1.1

Getting Started with JavaScript

Open chapter

What JavaScript is, where it runs, how to set up Node.js, how to print with the console, how a page loads scripts and how to read the errors you will meet every day.

Key ideas

  • What JavaScript is and where it runs JavaScript is the programming language of the web. Every modern browser has a JavaScript engine built in, so the same code runs on a phone, a laptop and a smart TV. Outside the browser, Node.js , Deno and Bun run JavaScript on servers, laptops and CI machines.
  • Setting up Node.js and an editor To follow along on your own machine you need two things: Node.js and a code editor. Every example on this page also runs inside your browser with the ✏️ Edit and run button, so you can start right now.
  • Your first program A JavaScript program is a list of statements that run from top to bottom. console.log prints whatever you give it. Several values are printed with a space between them.
  • The console toolbox The console is your first debugging tool and the place where test runners print what they find. It can do far more than log .
  • JavaScript in a web page In a browser, JavaScript can read and change the page. The page is a tree of objects called the DOM (Document Object Model). document.querySelector finds an element with a CSS selector, the same kind of selector a test tool uses to find a button.
  • How the engine runs your code Running a script happens in a few steps, and knowing them explains several surprises you will meet later.
  • Reading error messages Errors are not a failure on your part. They are the fastest way to learn what the program really did. Every error has a name , a message and a stack trace that lists where it happened.
  • Real world scenario: summarise a test run The script below does exactly that with only what this chapter covered: an array of objects, a loop, a template literal and the console.

1.2

How a JavaScript Program Runs Inside the Engine

Open chapter

Follow one program from a text file to the output: loading, the scanner and its tokens, the parser and its syntax tree, the creation phase and hoisting, Ignition bytecode, the call stack and the heap, the JIT compilers Sparkplug, Maglev and TurboFan, the event loop and how modules are linked. Type your own code into two step by step simulators.

Key ideas

  • The journey of a JavaScript program When you press Run, your .js file is only text. Two programs work together to turn that text into output. The engine understands the JavaScript language.
  • Step 1: loading the source text The engine cannot read files or download anything itself. The runtime fetches the text and hands it over.
  • Step 2: the scanner cuts text into tokens The first thing the engine does with the text is scanning (also called lexing or tokenising). It reads the characters from left to right and groups them into tokens , the smallest pieces that mean something.
  • Step 3: the parser builds a syntax tree The parser reads the tokens and checks them against the grammar of JavaScript. If they fit, it builds an abstract syntax tree (AST): a tree of nodes such as VariableDeclaration , BinaryExpression and CallExpression .
  • Step 4: scopes and the creation phase Before a script or a function runs, the engine sets up an execution context for it. This happens in two phases.
  • Step 5: Ignition turns the tree into bytecode V8 does not run the tree directly. Its interpreter, Ignition , first turns the tree into bytecode : a list of small, simple instructions. Bytecode is much smaller than machine code, so it starts fast and saves memory on phones.
  • Step 6: running: the call stack, the heap and garbage collection While the bytecode runs, the engine uses two areas of memory.
  • Step 7: hot code gets compiled: Sparkplug, Maglev and TurboFan Interpreting bytecode is quick to start but slower to run. So V8 watches which functions run often and compiles them to machine code while the program is running.
  • Step 8: the runtime, Web APIs and the event loop The engine runs one piece of code at a time on one thread. So how does a page wait for a server without freezing? It does not wait.
  • Modules: load, link, then evaluate An ES module is not run the moment it is read. The runtime and the engine go through three phases for the whole graph of files.
  • Real world scenario: a frozen page on sale day The cart runs a long synchronous calculation over every item. While it runs, the call stack is never empty, so the event loop cannot run click handlers, timers or painting. The code below measures this with a timer that should fire after 50 ms.

Variables, Types and Operators

Open chapter

let and const, the seven primitive types, why 0.1 + 0.2 is not 0.3, how JavaScript converts values by itself, the three kinds of equality and every operator, including ?. and ??.

Key ideas

  • Variables with let and const A variable is a name for a value. Modern JavaScript has two keywords for creating one.
  • The types of value Every value in JavaScript is one of eight types. Seven are primitives , simple values that cannot be changed. Everything else is an object .
  • Numbers, NaN and BigInt JavaScript has one number type for whole numbers and decimals. It stores them in binary, so some decimals cannot be stored exactly.
  • Type conversion and coercion Conversion is when you change a type on purpose. Coercion is when JavaScript does it for you behind the scenes. Both follow fixed rules.
  • Equality: ==, === and Object.is JavaScript has three ways to ask "are these the same".
  • Operators Operators combine values. Most of them you know from maths. A few are special to JavaScript and very handy.
  • Real world scenario: clean up data from an API Every tool from this chapter is here: ?? for missing values, ?. for the optional discount, explicit Number conversion, and a check with Number.isNaN for anything that went wrong.

Control Flow, Loops and Errors

Open chapter

if and switch, every kind of loop, the forEach and await trap, throwing and catching errors with causes and cleanup, and the polling and retry loops that power auto-waiting in every test tool.

Key ideas

  • Making decisions with if and else An if statement runs a block only when a condition is truthy. else if adds more conditions, checked from the top, and the first one that matches wins.
  • switch and lookup tables switch compares one value against many cases with === . Cases without a break or return fall through into the next one, which is useful for shared results and a classic bug otherwise.
  • Loops Loops repeat work. Pick the loop by what you are repeating over.
  • Loops with async steps Test code is full of steps that take time: open a page, click, wait for a response. These steps return promises and are written with await (chapter 11 explains how they work). Loops and await have one trap that breaks many first test suites.
  • Throwing and catching errors Code signals a problem by throwing an error. The error travels up through the functions that called it until a try block catches it. If nothing catches it, the program stops.
  • Polling and retry loops Two loops sit at the centre of every test framework. You will rarely write them yourself, but knowing how they work explains timeouts, flaky tests and the options every tool offers.
  • Real world scenario: data driven password checks This is data driven testing : the logic of the check is written once and the cases live in a table. Adding a case means adding one row.

Functions, Scope and Closures

Open chapter

Declarations and arrows, defaults, rest and options objects, scope and hoisting, closures, how this is decided, higher order functions such as memoize and debounce, and recursion on the call stack.

Key ideas

  • Declaring functions A function is a named, reusable piece of code. It takes parameters , does some work and returns a value. A function without a return returns undefined .
  • Function expressions and arrow functions A function can also be written as an expression and stored in a variable. The shorter arrow function syntax is the most common form in modern code and in test files.
  • Scope, hoisting and the temporal dead zone Scope decides where a name can be seen. JavaScript looks for a name in the current block, then in each enclosing block and function, out to the global scope. This chain is fixed by where the code is written , which is called lexical scope.
  • Closures A closure is a function together with the variables it could see when it was created. Those variables stay alive as long as the function does, even after the outer function has returned. Closures give you private state without classes.
  • this, call, apply and bind this is decided by how a function is called, not where it is written. Arrow functions are the exception: they never get their own this and use the one from the surrounding code.
  • Higher order functions A higher order function takes a function as an argument or returns one. You already used one: array.map(fn) . They let you write the shape of a task once and plug in the details.
  • Recursion and the call stack A recursive function calls itself on a smaller piece of the problem. It needs a base case that stops the calls. Every call waits on the call stack until the one it made returns.
  • Real world scenario: a test data factory

Objects and Arrays

Open chapter

Objects and their tools, destructuring, spread with shallow and deep copies, arrays, sorting without surprises, map, filter, reduce and friends, and grouping data for reports.

Key ideas

  • Objects An object groups related values under names called keys or properties . Almost everything you test is an object: a user, an API response, a configuration, a page element.
  • Destructuring Destructuring pulls values out of objects and arrays into variables in one line. It can rename, give defaults, skip items and collect the rest.
  • Spread, copies and immutability The spread syntax ... copies the items of an array or the keys of an object into a new one. When keys repeat, the later one wins, which makes it perfect for "defaults plus overrides".
  • Arrays An array is an ordered list. Indexes start at 0, length is the number of items and at(-1) reads from the end.
  • Array methods: map, filter, reduce and friends These methods replace most hand written loops. Each one takes a function and calls it for every item.
  • Grouping, counting and unique values Reports need data grouped and counted. ES2024 added Object.groupBy and Map.groupBy . reduce still handles any custom shape, and a Set removes duplicates.
  • Real world scenario: verify a sorted product listing The check found two real problems in this data: the second USB Hub at ₹1,299 comes after Keyboard at ₹2,499, so the order breaks at position 3, and USB Hub is listed twice.

Key ideas

  • Map A Map stores key and value pairs, like an object, with three differences that matter: keys can be any value (objects, numbers, functions), it remembers insertion order, and it has a size .
  • Set and set operations A Set holds unique values. Adding a value twice keeps one copy. ES2025 added the operations from school maths, so comparing two lists no longer needs nested loops.
  • WeakMap, WeakSet and WeakRef Weak collections hold objects without keeping them alive. When nothing else uses the object, the garbage collector may remove it and its entry disappears. They cannot be listed or counted, because their contents can change at any moment.
  • Iterators and iterator helpers An iterable is anything with a Symbol.iterator method: arrays, strings, Maps, Sets, NodeLists and arguments. That method returns an iterator , an object whose next() hands out { value, done } one at a time. for...of , spread and destructuring all use it.
  • Generators and async generators A generator function ( function* ) can pause at every yield and continue later from the same place. Calling it runs nothing. It returns an iterator, and each next() runs the body up to the next yield .
  • Binary data: ArrayBuffer, typed arrays and DataView Most JavaScript works with text and objects, but files, images, network packets, audio and cryptography work with bytes . An ArrayBuffer is a block of raw memory with a fixed size. You never read it directly.
  • Symbols A symbol is a unique value used as a hidden key. Two symbols with the same description are still different, unless they come from the shared registry with Symbol.for . Symbol keys are skipped by Object.keys and JSON.stringify .

Open chapter

Key ideas

  • Objects and prototypes Every object in JavaScript has a hidden link to another object called its prototype . When you read a property the object does not have, JavaScript follows that link and looks there, then on that object's prototype, and so on.
  • Classes A class is a template for objects that share the same shape and methods. It has a constructor that sets up each new object, methods shared through the prototype, fields that every object gets, getters and setters that look like properties, and static members ...
  • Private fields and encapsulation A field or method whose name starts with # is private . Only code inside the class body can read or change it. It does not show up in Object.keys , in JSON or in the console of other code, and any attempt to read it from outside is a syntax error.
  • Inheritance with extends and super class Dog extends Animal makes Animal.prototype the prototype of Dog.prototype . A Dog gets every Animal method and can override any of them. Inside the subclass, super(...) calls the parent constructor, and super.method() calls the parent version of a method.
  • Composition over inheritance Deep class trees get hard to change: a fix in a parent class affects every child. Many teams prefer composition , where an object is built from small parts it holds or mixes in.
  • The Page Object Model The Page Object Model (POM) is the most common design pattern in UI automation. Each page or component of the app gets a class. The class holds the locators and offers methods with business names such as loginAs or addToCart .
  • Real world scenario: test data and an API client A builder class starts from sensible defaults, and each test changes only what matters to it. Every built user gets a fresh email, so tests never clash.

Asynchronous JavaScript: Promises, async and await

Open chapter

How one thread handles slow work with the event loop, callbacks, promises, async and await, running promises together, cancelling with AbortController, and waiting with retries and polling instead of fixed sleeps.

Key ideas

  • One thread and the event loop JavaScript runs your code on one thread : one line at a time. Slow work such as a network request, a timer or reading a file is handed to the browser or Node.js, and your code keeps going. When the slow work finishes, a callback is queued.
  • Callbacks The first way to handle async work was to pass a function to call later. Node.js callbacks receive the error first and the result second.
  • Promises A promise is an object that stands for a result that is not ready yet. It starts pending , then becomes fulfilled with a value or rejected with an error, and never changes again. then runs when it fulfils, catch when it rejects and finally either way.
  • async and await async before a function makes it return a promise. Inside it, await pauses that function until a promise settles and gives you its value, while the rest of the program keeps running. Errors become normal exceptions you catch with try and catch .
  • Running many promises: all, allSettled, race, any Four helpers combine several promises into one. They differ in what counts as done and what happens on a failure.
  • Retries, polling and waiting the right way Tests and scripts often wait for something that happens at an unknown time: an element appears, a job finishes, a service recovers. A fixed sleep guesses the time. It wastes time when the guess is too long and fails when it is too short.
  • Real world scenario: a link checker mapLimit starts 3 workers that take the next URL as soon as they are free. AbortSignal.timeout stops slow requests, and catching each error turns it into a row in the report instead of stopping the run.

Key ideas

  • The DOM tree When a browser loads HTML, it builds the DOM (Document Object Model): a tree of objects, one for each element, piece of text and comment. JavaScript reads and changes the page only through this tree, and so does every UI automation tool.

Key ideas

  • Creation phase, hoisting and the scope chain Before a function runs, the engine scans it and sets up its bindings. var names start as undefined , function declarations are ready to call, and let , const and class exist but sit in the temporal dead zone until their line runs.
  • this in depth: five rules and a precedence The value of this is decided by how a function is called , not where it is written. Five rules cover every case, and when several apply, the one higher in this list wins.
  • The Node.js event loop, phase by phase Chapter 11 showed the browser view: microtasks first, then one task.   • Garbage collection JavaScript frees memory for you. V8 uses a generational collector because most objects die young. New objects go into the small young generation , which is cleaned often with a fast copying "scavenge".

Regular expressions in depth

Open chapter

Go beyond the basics of chapter 7: how the backtracking engine finds a match, greedy and lazy quantifiers, lookarounds and backreferences, every flag and the lastIndex trap, unicode letters in every language, replacing and masking, a sticky tokeniser, ReDoS, and testing patterns with tables.

Key ideas

  • How the regex engine matches JavaScript uses a backtracking engine. It tries the pattern at the first position of the text and, when a step fails, goes back to the last choice it made and tries another. If nothing works, it moves one character on and starts again.
  • Lookarounds and backreferences A lookaround checks what comes before or after a position without including it in the match. (?=x) and (?!x) look ahead, (?<=x) and (?<!x) look behind. A backreference such as \1 or \k<name> matches the same text a group already matched.
  • Flags in depth and the lastIndex trap Flags change how the whole pattern works. The g and y flags also make a regex stateful : it remembers lastIndex , the position after the last match.
  • Unicode and every language [a-z] only knows English. With the u or v flag, \p{L} matches a letter in any script, \p{Script=Devanagari} one script, and \p{Emoji} emoji. The u flag also treats an emoji as one character instead of two halves.
  • Replacing, masking and splitting replace and replaceAll can use $1 , $<name> and $& in the replacement text, or a function that receives every group and returns the new text.
  • ReDoS and safe patterns Some patterns make the engine try an exponential number of ways to split the input. ^(a+)+$ on a long run of "a" that ends with "!" never finishes in practice. An attacker who can send such input to a server can freeze it with one request.
  • Validation patterns and testing them A regex can check the shape of text, not its meaning. A date pattern accepts 31 February, and no practical email pattern follows the full standard. Use a regex for the shape, then real code for the rest, such as Temporal.PlainDate.from for dates.
  • Real world scenario: mine the access logs One pattern with named groups turns each line into an object. Lines that do not match are counted instead of silently dropped, which tells you when the log format changes. The same idea works for test runner output, browser console logs and CI logs.

7.1

TypeScript fundamentals

Open chapter

Start TypeScript the modern way: tsc to check and Node.js to run, a strict tsconfig, everyday types and inference, typed functions and overloads, interface and type, unions and narrowing, enums against as const objects, the strict options, and typed results from untyped JSON.

Key ideas

  • What TypeScript is and how it runs TypeScript is JavaScript with type annotations. The compiler tsc reads the types and reports mistakes before the code runs. The types are then erased : at run time it is plain JavaScript.
  • Everyday types Most of the time TypeScript infers the type from the value, so you annotate function parameters, public APIs and empty containers, not every variable. Use readonly for data that must not change, ? for optional properties, and tuples for fixed length lists.
  • Functions Annotate parameters, and let the return type be inferred or write it for public functions. Optional parameters use ? , defaults give both a type and a value, and rest parameters are typed as arrays.
  • interface and type Both interface and type name an object shape. Interfaces can be extended with extends and are merged when declared twice, which suits public object shapes. Type aliases can name anything: unions, tuples, functions and combinations with & .
  • Unions and narrowing A union such as string | number means "one of these". Before you use a union, you narrow it with a check that TypeScript understands: typeof , instanceof , in , equality, or a shared literal field. Inside each branch, TypeScript knows the exact type.
  • Enums and their modern alternative An enum creates a real object at run time, so it is not erasable and fails with erasableSyntaxOnly and with Node.js type stripping. The modern alternative is a plain object marked as const plus a union type made from its values.

Advanced TypeScript types

Open chapter

The type tools experts use: generics and constraints, typeof, keyof and indexed access, the utility types, mapped and conditional types with infer, template literal types, satisfies, exhaustive checks with never, assertion functions, branded types, and API routes whose types follow the path.

Key ideas

  • Generics A generic is a type parameter, written <T> , that is filled in when the function or type is used. It keeps the connection between inputs and outputs: first of a number list is a number. A constraint with extends says what T must at least have.
  • typeof, keyof and indexed access typeof value turns a value into a type, keyof T gives the union of its keys, and T[K] reads the type of one property. Together they let a function accept only real keys and return the right type for each one.
  • Utility types TypeScript ships with type helpers that change existing types instead of writing new ones by hand.
  • Mapped and conditional types A mapped type loops over keys: { [K in keyof T]: … } . It can rename keys with as and add or remove readonly and ? .
  • Template literal types Template literal types describe patterns of strings, built from other string types. They type routes, CSS values, event names and test ids, and the compiler checks every literal you write.
  • satisfies An annotation such as const x: Record<string, Project> replaces the type of the value with the wider annotation, so the exact keys are lost. satisfies checks the value against the type but keeps the precise type that was inferred.
  • Exhaustive checks with never With a discriminated union, a switch on the shared field narrows each case. Passing the leftover value to a function that takes never makes the check exhaustive : add a new kind to the union and every switch that forgot it becomes a compile error.
  • Assertion functions and branded types An assertion function with asserts value is T narrows the type after the call, or throws. Test helpers such as expect(x).toBeDefined() cannot narrow types, but your own assertion functions can.
  • Real world scenario: typed API routes A conditional type with infer pulls :id out of the route string, and the Routes map gives the response type. A missing parameter or a typo such as stok is now a compile error.

How the TypeScript type system decides

Open chapter

Why does one object fit and an almost identical one fail? This chapter explains the rules the checker follows: structural typing and the excess property check, literal types and widening, any, unknown and never, function compatibility and variance, index signatures with the strictest options, tuples, overloads and this, and recursive types.

Key ideas

  • Structural typing: shapes, not names In Java or C#, a class is a Reporter only if it says implements Reporter . TypeScript is structural : any value with the right members fits, whatever it is called. This matches how JavaScript code is really written, with plain objects passed around.
  • Literal types and widening A value can have a very exact type. const m = "GET" has the type "GET" , a literal type . A let may change later, so TypeScript widens it to string . Object properties are widened too. as const stops widening and makes everything readonly.
  • any, unknown and never any turns checking off for a value and everything you reach through it, so mistakes spread silently. unknown accepts any value too, but you must check it before use.
  • Function compatibility and variance When is one function type usable as another? Fewer parameters is fine, because JavaScript ignores extra arguments. A callback that returns a value is fine where void is expected. Parameter types are where it gets subtle.
  • Index signatures and the strictest options An index signature , { [key: string]: number } or Record<string, number> , describes objects used as dictionaries. By default TypeScript pretends every key exists. Two options, not included in strict , make it honest.
  • Tuples: fixed length arrays with names A tuple is an array with a fixed length and a type per position. Elements can have labels, be optional, or be a rest of many.
  • Overloads and this Overloads give one function several typed call signatures, so the return type follows the argument type.
  • Recursive types A type may refer to itself. That is how trees are described: JSON, file systems, menus, nested config. Recursive conditional types go further and compute types such as every dot path in an object.
