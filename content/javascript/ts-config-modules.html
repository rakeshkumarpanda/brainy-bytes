Part 1

⚙️tsconfig.json in depth

🧪 QA essentialTest projects often copy an old tsconfig. Knowing which options matter avoids hours of strange import errors.

Every TypeScript project is driven by tsconfig.json. It answers four questions: which files to check (include, exclude, files), how strict to be, what JavaScript to produce, and how imports are found. Since TypeScript 6.0 a fresh project already defaults to strict: true, module: "esnext", target: "es2025" and types: [].

GroupOptions you will meet
Filesinclude, exclude, rootDir, outDir
Checkingstrict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitOverride
Outputtarget, declaration, sourceMap, noEmit
Modulesmodule, moduleResolution, verbatimModuleSyntax, paths
Environmentlib, types, skipLibCheck
Sharingextends (a base config, or several since 5.0), references

Old options do not live forever. TypeScript 6.0 deprecated a long list and TypeScript 7.0 removed them, so an old config stops the build:

An old option that TypeScript 7.0 no longer accepts · 🔷 tsc finds 1 error
📄 src/main.ts
const ok = 1;
console.log(ok);
Terminal
$ npx tsc
Terminal output
tsconfig.json(15,5): error TS5102: Option 'baseUrl' has been removed. Please remove it from your configuration.
  Use '"paths": {"*": ["./*"]}' instead.
Part 2

📥ES modules and module resolution

🧪 QA essentialPlaywright and Vitest projects break most often on imports: missing extensions, CommonJS against ES modules, and types imported as values.

The module and moduleResolution options tell tsc which rules the real runtime will use to find files. With nodenext it copies Node exactly: ES module imports need the file extension, and packages are found through their exports field. With bundler it copies Vite, webpack and esbuild, which allow imports without extensions.

verbatimModuleSyntax keeps imports exactly as written, so anything that is only a type must say so with import type or an inline type marker. Tools that strip types one file at a time then know which imports to delete.

ES module imports under module nodenext · 🔷 tsc finds 2 errors
📄 src/main.ts
import { total, type Item } from "./price.ts";        // type is erased, total stays
import { total as sum } from "./price";               // no extension: Node cannot find this file
import { Item as Row } from "./price.ts";             // a type imported like a value

const cart: Item[] = [{ sku: "PEN-1", price: 49 }, { sku: "BAG-2", price: 899 }];
console.log("total", total(cart));
📄 src/price.ts
export interface Item { sku: string; price: number }

export function total(items: Item[]): number {
  return items.reduce((sum, i) => sum + i.price, 0);
}
Terminal
$ npx tsc
Terminal output
src/main.ts(2,30): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './price.js'?
src/main.ts(3,10): error TS1484: 'Item' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.

Part 3

#️⃣Subpath imports instead of ../../..

🧪 QA essential

Deep test folders end up with imports like ../../../lib/price. Node's subpath imports fix that with an imports field in package.json, and both Node and tsc understand it without extra tools. TypeScript 6.0 added support for the short #/ prefix that Node recently allowed.

Subpath imports that start with #/ (TypeScript 6.0) · 🧪 Tests run
📄 package.json
{
  "name": "shop-tests",
  "type": "module",
  "imports": {
    "#/*": "./src/*"
  }
}
📄 src/tests/cart.test.ts
// #/ points at the src folder, so deep files never need ../../..
import { total, type Item } from "#/lib/price.ts";

const items: Item[] = [{ sku: "PEN-1", price: 49 }, { sku: "PEN-2", price: 51 }];
console.log(total(items) === 100 ? "PASS total of two pens" : "FAIL");
Terminal
$ npx tsc && node src/tests/cart.test.ts
Terminal output
tsc: no type errors
PASS total of two pens
The older paths option in tsconfig only teaches tsc where files are. Node itself does not read it, so a separate plugin was needed at run time. Subpath imports work in both places with one setting.
Part 4

✂️Erasable syntax and running .ts files directly

🧪 QA essentialRunning test files with plain node, without ts-node or a bundler, is now common, and these three features are what breaks it.

Node.js 23.6 and later run .ts files directly by replacing types with spaces, without checking them. That only works for TypeScript features that leave no JavaScript behind. Enums, namespaces with values and constructor parameter properties produce real code, so Node refuses them. erasableSyntaxOnly (TypeScript 5.8) makes tsc flag them early.

erasableSyntaxOnly marks code that Node cannot strip · 🔷 tsc finds 3 errors
📄 src/main.ts
// Node.js runs .ts files by deleting the types. Code that needs real JavaScript output cannot be deleted.
enum Status { Pass, Fail }                         // generates an object at run time

class Client {
  constructor(private baseURL: string) {}          // parameter property: generates this.baseURL = baseURL
}

namespace Legacy { export const v = 1; }           // generates an object too

// The erasable alternatives
const Status2 = { Pass: 0, Fail: 1 } as const;
type Status2 = (typeof Status2)[keyof typeof Status2];
class Client2 {
  baseURL: string;
  constructor(baseURL: string) { this.baseURL = baseURL; }
}
const s: Status2 = Status2.Fail;
console.log(s, new Client2("http://localhost:3000").baseURL, Status, Client, Legacy);
Terminal
$ npx tsc
Terminal output
src/main.ts(2,6): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
src/main.ts(5,15): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
src/main.ts(8,11): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
This is also why the earlier chapters prefer as const objects over enums. They behave the same, work in Node, Deno and Bun without a build step, and the JavaScript output is exactly what you wrote.
Part 5

🧷Declaration merging and namespaces

TypeScript merges some declarations that share a name. Two interface blocks become one, which is how libraries let you add fields to their types. A function and a namespace can merge too, giving a function with extra properties. Namespaces come from before ES modules. In new code, use modules instead, and keep namespaces for reading older code and type declarations.

Declaration merging and namespaces · 🔷 tsc finds 1 error
📄 src/main.ts
// Two declarations of the same interface merge into one
interface TestInfo { title: string }
interface TestInfo { retries: number }
const info: TestInfo = { title: "checkout works", retries: 2 };

// Adding a field to a global type, as test libraries do
declare global {
  interface Window { __TEST_USER__?: string }
}

// A function and a namespace with the same name merge: callable, with extra members
function money(cents: number): string { return (cents / 100).toFixed(2); }
namespace money {
  export const currency = "INR";
}

console.log(info.title, info.retries, money(4950), money.currency);
const wrong: TestInfo = { title: "only a title" };
export {};
Terminal
$ npx tsc
Terminal output
src/main.ts(18,7): error TS2741: Property 'retries' is missing in type '{ title: string; }' but required in type 'TestInfo'.

This file is only checked here, not run. The namespace produces real JavaScript, so Node's type stripping refuses it, exactly as the erasable syntax part above explained.

Part 6

🏝️isolatedDeclarations and fast declaration files

A library publishes .d.ts files that describe its exports. Normally only tsc can write them, because it must infer return types. With isolatedDeclarations (TypeScript 5.5) every export states its type, so faster tools such as esbuild, oxc or swc can write the declarations one file at a time, in parallel.

isolatedDeclarations: every export states its type · 🔷 tsc finds 2 errors, then Node.js runs it
📄 src/main.ts
export interface Item { sku: string; price: number }

export function total(items: Item[]): number {        // explicit return type: fine
  return items.reduce((sum, i) => sum + i.price, 0);
}

export function withTax(amount: number) {             // return type must be inferred: not allowed
  return amount * 1.18;
}

export const VAT = 0.18;                              // a literal is easy to read: fine
export const defaults = { currency: "INR", vat: VAT };  // an object made of other values: not allowed

const local = (n: number) => n * 2;                   // not exported, so nothing to declare
console.log(total([{ sku: "A", price: 10 }]), withTax(100), local(2), defaults.currency);
Terminal
$ npx tsc
$ node src/main.ts
Terminal output
src/main.ts(8,10): error TS9013: Expression type can't be inferred with --isolatedDeclarations.
src/main.ts(12,49): error TS9013: Expression type can't be inferred with --isolatedDeclarations.

$ node src/main.ts
10 118 4 INR

🏗️Project references for big repositories

In a large repository with many packages, checking everything every time is slow. Project references split the code into projects that build separately and in order. tsc -b (build mode) checks only what changed since the last build.

Project references: build only what changed · 🧪 Tests run
📄 packages/core/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "target": "esnext",
    "module": "nodenext",
    "strict": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": [
    "src"
  ]
}
📄 packages/app/tsconfig.json
{
  "compilerOptions": {
    "target": "esnext",
    "module": "nodenext",
    "strict": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "references": [
    {
      "path": "../core"
    }
  ],
  "include": [
    "src"
  ]
}
📄 packages/app/src/main.ts
import { slug } from "../../core/dist/index.js";
console.log(slug("  Add To Cart "));
Terminal
$ npx tsc -b packages/app --verbose
node packages/app/dist/main.js
npx tsc -b packages/app --verbose
Terminal output
