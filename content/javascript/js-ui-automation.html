🧭The tools and how they drive a browser

🧪 QA essentialPlaywrightSeleniumCypressWebdriverIOPicking a tool and understanding how it reaches the browser is the first decision in every UI automation project.

A UI automation tool starts a real browser and acts like a user: it opens pages, types, clicks and reads what is shown. The four big JavaScript tools differ in how they talk to the browser, and that explains most of their strengths and limits.

🎭Playwright: locators and web first assertions

🧪 QA essentialPlaywrightLocators and auto-waiting assertions are the core of every Playwright test.

A Playwright test receives a page, finds elements with locators and checks them with web first assertions. A locator is a recipe, not an element: it is looked up again on every use, so it never goes stale. Every action waits until the element is visible, enabled and not moving, and every expect(locator) retries until it passes or times out.

A first Playwright suite · 🧪 Tests run

import { test, expect } from "@playwright/test";

test.beforeEach(async ({ page }) => {
  await page.goto("/");
});

test("wrong password shows an error", async ({ page }) => {
  await page.getByLabel("Email").fill("asha@shop.example");
  await page.getByLabel("Password").fill("wrong");
  await page.getByRole("button", { name: "Sign in" }).click();
  await expect(page.getByRole("alert")).toHaveText("Wrong email or password");
});

test("log in, add two products and place an order", async ({ page }) => {
  await page.getByLabel("Email").fill("asha@shop.example");
  await page.getByLabel("Password").fill("s3cret");
  await page.getByRole("button", { name: "Sign in" }).click();
  await expect(page.getByText("Hello, asha")).toBeVisible();

  // The list arrives 600 ms later. No sleep: the assertion keeps retrying.
  const products = page.getByTestId("product");
  await expect(products).toHaveCount(3);
  await products.filter({ hasText: "Coffee mug" }).getByRole("button", { name: "Add to cart" }).click();
  await products.filter({ hasText: "Gel pen" }).getByRole("button").click();

  await expect(page.getByTestId("cart-count")).toHaveText("2");
  await expect(page.locator("#total")).toHaveText("₹219");
  await page.getByRole("button", { name: "Place order" }).click();
  await expect(page.getByText(/^Order \d+ placed$/)).toBeVisible();
});

🛰️Controlling the network

🧪 QA essentialPlaywrightCypressNetwork mocking makes error states testable and UI tests independent of backend data.

Playwright sees every request the page makes. page.route can answer a request with fake data or an error, so you can test states that are hard to produce for real: a broken API, an empty list, a very long name. waitForRequest and waitForResponse check what the page sends.

Mock, break and spy on the network · 🧪 Tests run
📄 tests/network.spec.js
import { test, expect } from "@playwright/test";

async function logIn(page) {
  await page.goto("/");
  await page.getByLabel("Email").fill("asha@shop.example");
  await page.getByLabel("Password").fill("s3cret");
  await page.getByRole("button", { name: "Sign in" }).click();
}

test("shows a friendly message when the products API fails", async ({ page }) => {
  await page.route("**/api/products", route => route.fulfill({ status: 503, body: "down" }));
  await logIn(page);
  await expect(page.getByText("Could not load products. Try again later.")).toBeVisible();
});

test("renders whatever the API returns, even a huge price", async ({ page }) => {
  await page.route("**/api/products", route =>
    route.fulfill({ json: [{ id: 9, name: "Gold watch", price: 1234567 }] }));
  await logIn(page);
  await expect(page.getByTestId("product")).toHaveText(/Gold watch\s*₹12,34,567/);
});

test("sends the right order to the server", async ({ page }) => {
  await logIn(page);
  await page.getByTestId("product").filter({ hasText: "Desk lamp" }).getByRole("button").click();
  const [request] = await Promise.all([
    page.waitForRequest("**/api/orders"),
    page.getByRole("button", { name: "Place order" }).click(),
  ]);
  expect(request.postDataJSON()).toEqual({ items: [3] });
  await expect(page.getByText("Order 1042 placed")).toBeVisible();
});

🏗️Page objects, fixtures and retries

🧪 QA essentialPlaywrightFixtures, page objects and honest flaky reporting are what keep large UI suites maintainable.

As a suite grows, repeated steps move into page objects (chapter 9) and fixtures. A Playwright fixture prepares something a test needs, here a logged in shop, and passes it in as a parameter. Tests become short and read like a test case.

Page objects and fixtures · 🧪 Tests run
📄 pages/shop.page.js
import { expect } from "@playwright/test";

export class ShopPage {
  constructor(page) {
    this.page = page;
    this.products = page.getByTestId("product");
    this.cartCount = page.getByTestId("cart-count");
    this.total = page.locator("#total");
    this.placeOrder = page.getByRole("button", { name: "Place order" });
  }
  async open() {
    await this.page.goto("/");
  }
  async logIn(email, password) {
    await this.page.getByLabel("Email").fill(email);
    await this.page.getByLabel("Password").fill(password);
    await this.page.getByRole("button", { name: "Sign in" }).click();
    await expect(this.products.first()).toBeVisible();   // wait until the shop is ready
  }
  async add(name) {
    await this.products.filter({ hasText: name }).getByRole("button", { name: "Add to cart" }).click();
  }
}

Flaky tests and retries

A flaky test passes and fails without any code change. Playwright can retry a failed test, and a test that fails and then passes is reported as flaky, not hidden as passed.

Retries and flaky tests · 🧪 Tests run

test("fails on the first try, passes on the retry", async ({ page }, testInfo) => {

  const expected = testInfo.retry === 0 ? "Demo Shop!" : "Demo Shop";

Part 5

🚗Selenium WebDriver

🧪 QA essentialSeleniumMany enterprise suites are Selenium, and its explicit waits and locators are the base of every WebDriver tool.

Selenium WebDriver sends each command to a driver program (chromedriver, geckodriver, safaridriver), which controls the browser. Every call is a network round trip and returns a promise, so every line is awaited. Selenium does not wait for you: use explicit waits with driver.wait(until...) for anything that appears later.

Selenium WebDriver with Mocha, explicit waits and a page object · 🧪 Tests run
📄 selenium/driver.js
// One place that knows how to start Chrome for every Selenium test.
// Selenium Manager downloads a matching chromedriver by itself. CI machines
// can point CHROMEDRIVER and CHROME_BIN at fixed copies instead.
import { Builder } from "selenium-webdriver";
import chrome from "selenium-webdriver/chrome.js";

export async function buildDriver() {
  const options = new chrome.Options().addArguments("--headless=new", "--no-sandbox", "--window-size=1280,800");
  if (process.env.CHROME_BIN) options.setChromeBinaryPath(process.env.CHROME_BIN);
  const builder = new Builder().forBrowser("chrome").setChromeOptions(options);
  if (process.env.CHROMEDRIVER) builder.setChromeService(new chrome.ServiceBuilder(process.env.CHROMEDRIVER));
  return builder.build();
}
📄 selenium/pages/ShopPage.js
import { By, until } from "selenium-webdriver";

export class ShopPage {
  static EMAIL = By.name("email");
  static PASSWORD = By.name("password");
  static SIGN_IN = By.css("#login button");
  static ALERT = By.css("[role=alert]");
  static CART_COUNT = By.css("[data-testid=cart-count]");
  static TOTAL = By.id("total");
  static addButtonFor = name => By.xpath(`//li[h2='${name}']//button`);

  constructor(driver, baseUrl) {
    this.driver = driver;
    this.baseUrl = baseUrl;
  }
  async open() {
    await this.driver.get(this.baseUrl);
  }
  async logIn(email, password) {
    await this.driver.findElement(ShopPage.EMAIL).sendKeys(email);
    await this.driver.findElement(ShopPage.PASSWORD).sendKeys(password);
    await this.driver.findElement(ShopPage.SIGN_IN).click();
  }
  async add(name) {
    // Explicit wait: the products arrive after a delay
    const button = await this.driver.wait(until.elementLocated(ShopPage.addButtonFor(name)), 5000);
    await this.driver.wait(until.elementIsVisible(button), 5000);
    await button.click();
  }
  async cartCount(expected) {
    const el = await this.driver.findElement(ShopPage.CART_COUNT);
    await this.driver.wait(until.elementTextIs(el, expected), 5000);
    return el.getText();
  }
  async alertText() {
    const el = await this.driver.wait(until.elementLocated(ShopPage.ALERT), 5000);
    await this.driver.wait(until.elementIsVisible(el), 5000);
    return el.getText();
  }
}

🌲Cypress and WebdriverIO

🧪 QA essentialCypressWebdriverIOCypress is widely used by front end teams and its command queue works differently from every other tool.

Cypress runs inside the browser, in the same loop as your app. Commands such as cy.get are not promises: Cypress queues them and runs them in order, retrying each query and assertion until it passes. That is why you never write await in Cypress, and why plain variables do not hold element values (use .then or aliases).

The same tests in Cypress · Shown only: Cypress needs its own app download, which this page build cannot fetch
// cypress/e2e/shop.cy.js
describe("demo shop", () => {
  beforeEach(() => {
    cy.intercept("GET", "/api/products").as("products");   // watch the request
    cy.visit("/");
  });

  it("logs in and orders", () => {
    cy.get("input[name=email]").type("asha@shop.example");
    cy.get("input[name=password]").type("s3cret");
    cy.contains("button", "Sign in").click();
    cy.wait("@products").its("response.statusCode").should("eq", 200);

    cy.contains("[data-testid=product]", "Coffee mug").find("button").click();
    cy.get("[data-testid=cart-count]").should("have.text", "1");    // retries until true
    cy.contains("button", "Place order").click();
    cy.contains(/^Order \d+ placed$/).should("be.visible");
  });

  it("shows a message when the API fails", () => {
    cy.intercept("GET", "/api/products", { statusCode: 503 });
    cy.login("asha@shop.example", "s3cret");                       // a custom command, see below
    cy.contains("Could not load products").should("be.visible");
  });
});

// cypress/support/commands.js
Cypress.Commands.add("login", (email, password) => {
  cy.get("input[name=email]").type(email);
  cy.get("input[name=password]").type(password);
  cy.contains("button", "Sign in").click();
});

Run with npx cypress open (interactive) or npx cypress run (headless, for CI). Commands are queued and retried automatically, and are never awaited.

🎬Real world scenario: a UI suite in CI

🧪 QA essential
The situationThe team wants every pull request checked by the browser suite in under ten minutes, with a report anyone can open when something fails.
Browser tests in CI · Reference
# .github/workflows/e2e.yml
name: e2e
on: [pull_request]
jobs:
  playwright:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --shard=${{ matrix.shard }}/4
        env: { BASE_URL: "${{ vars.STAGING_URL }}" }
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with: { name: "report-${{ matrix.shard }}", path: playwright-report/ }
What happens

Four machines each run a quarter of the suite. The HTML report, with traces of failed tests, is kept for every run.

Sharding splits the tests across four machines. fail-fast: false lets every shard finish, so one failure does not hide others. The report is uploaded even when tests fail, and the traces inside it show exactly what the browser saw.

A healthy UI suite: tests independent of each other, data created through the API rather than the UI, stable locators, no fixed sleeps, network mocks only for edge cases, flaky tests tracked and fixed within days, and the slowest tests reviewed every sprint.
