Part 1

📚Execution contexts and the call stack

🧪 QA essentialReading stack traces quickly is the first step in debugging every failed automated test.

Every time a function is called, the engine creates an execution context: a record of its variables, its scope chain and its this. Contexts sit on the call stack. The one on top is running, and when it returns it is popped off. A stack trace in an error is simply a print of this stack.

The call stack and stack overflow · ▶ Runs
function placeOrder() { return chargeCard(); }
function chargeCard() { return callBank(); }
function callBank() {
  // Error().stack is a snapshot of the call stack at this moment
  return new Error("snapshot").stack.split("\n").slice(1, 4).map(l => l.trim().split(" (")[0]);
}
console.log(placeOrder());

// Each call adds a frame. Too many frames and the engine stops you.
function countDown(n) { return n === 0 ? "done" : countDown(n - 1); }
console.log(countDown(1000));
try { countDown(1e6); } catch (e) { console.log(e.name + ":", e.message); }
Output
[ 'at callBank', 'at chargeCard', 'at placeOrder' ]
done
RangeError: Maximum call stack size exceeded
Read a failing test's stack trace from the top: the first line that points into your code (a page object, a helper, a spec file) is usually where the fix belongs. Lines inside node_modules are the framework calling you.
Part 2

🏗️Creation phase, hoisting and the scope chain

Before a function runs, the engine scans it and sets up its bindings. var names start as undefined, function declarations are ready to call, and let, const and class exist but sit in the temporal dead zone until their line runs. This scan is what people call hoisting.

Execution contexts, the TDZ and the scope chain · ▶ Runs
// Creation phase: the engine scans the function before running a single line
function checkout() {
  console.log(typeof total, typeof applyCoupon);           // var is undefined, the function exists
  try { console.log(discount); } catch (e) { console.log(e.name + ":", e.message); }
  try { typeof Cart; } catch (e) { console.log("even typeof throws in the TDZ:", e.name); }

  var total = 100;
  let discount = 10;                                             // in the temporal dead zone until here
  function applyCoupon(t) { return t - discount; }
  class Cart {}
  return applyCoupon(total);
}
console.log(checkout());

// Each loop iteration with let gets a fresh binding. var shares one.
const withVar = [], withLet = [];
for (var i = 0; i < 3; i++) withVar.push(() => i);
for (let j = 0; j < 3; j++) withLet.push(() => j);
console.log(withVar.map(f => f()), withLet.map(f => f()));

// The scope chain is fixed where the function is written, not where it is called
const label = "global";
function show() { return label; }
function caller() { const label = "caller"; return show(); }
console.log(caller());
Output
undefined function
ReferenceError: Cannot access 'discount' before initialization
even typeof throws in the TDZ: ReferenceError
90
[ 3, 3, 3 ] [ 0, 1, 2 ]
global

Scope is lexical: a function looks up names in the place it was written, then outwards, never in the place it was called from. Closures (chapter 4) are this rule plus the fact that the outer variables stay alive as long as the inner function does.

Part 3

👉this in depth: five rules and a precedence

🧪 QA essentialPlaywrightSeleniumPage object methods passed to forEach, retry helpers or event handlers lose this, which crashes the test.

The value of this is decided by how a function is called, not where it is written. Five rules cover every case, and when several apply, the one higher in this list wins.

The five rules of this · ▶ Runs
"use strict";
function who() { return this?.name ?? String(this); }
const page = { name: "LoginPage", who };
const other = { name: "CartPage" };

console.log("1 default:", who());                       // plain call: undefined in strict mode
console.log("2 implicit:", page.who());                 // called on an object
console.log("3 explicit:", who.call(other));            // call, apply
const bound = who.bind(other);
console.log("4 bound:", bound(), bound.call(page));     // bind wins over call
function Page(name) { this.name = name; }
console.log("5 new:", new Page("Home").name);           // new creates a fresh this

// Arrow functions have no this of their own. They use the one around them.
const timer = {
  name: "Timer",
  regular() { return [1].map(function () { return this?.name; })[0]; },
  arrow() { return [1].map(() => this.name)[0]; },
};
console.log("arrow:", timer.arrow(), "regular:", timer.regular());
Output
1 default: undefined
2 implicit: LoginPage
3 explicit: CartPage
4 bound: CartPage CartPage
5 new: Home
arrow: Timer regular: undefined

The most common bug in test code is passing a method as a callback. The method is detached from its object, so the call becomes a plain call and this is undefined.

Losing this when you pass a method · ▶ Runs
class SearchPage {
  results = [];
  query = "pen";
  // A normal method: "this" depends on how it is called
  collect(item) { this.results.push(`${this.query}:${item}`); }
  // A class field arrow: "this" is fixed to the instance
  collectSafe = item => { this.results.push(`${this.query}:${item}`); };
}

const page = new SearchPage();
try { ["blue", "red"].forEach(page.collect); }
catch (e) { console.log("passing the method:", e.constructor.name, "-", e.message); }

["blue", "red"].forEach(page.collect.bind(page));
["green"].forEach(page.collectSafe);
["black"].forEach(item => page.collect(item));
console.log(page.results);
Output
passing the method: TypeError - Cannot read properties of undefined (reading 'results')
[ 'pen:blue', 'pen:red', 'pen:green', 'pen:black' ]
Part 4

🔄The Node.js event loop, phase by phase

🧪 QA essentialKnowing which callback runs first explains log orders, race conditions and why a missing await lets a test finish too early.

Chapter 10 showed the browser view: microtasks first, then one task. Node.js splits the task side into phases that run in a fixed order on every turn: timers (setTimeout and setInterval), poll (finished I/O such as files and sockets) and check (setImmediate). Between every callback, Node.js empties the process.nextTick queue and then the promise microtask queue.

Node.js event loop phases in order · ▶ Runs
const fs = require("node:fs");

console.log("1 sync start");
setTimeout(() => console.log("6 timers phase: setTimeout 0"), 0);
Promise.resolve().then(() => console.log("4 microtask: promise then"));
queueMicrotask(() => console.log("5 microtask: queueMicrotask"));
process.nextTick(() => console.log("3 nextTick queue"));

fs.readFile(__filename, () => {
  console.log("7 poll phase: I/O callback");
  setTimeout(() => console.log("9 timers phase, next loop"), 0);
  setImmediate(() => console.log("8 check phase: setImmediate"));
  process.nextTick(() => console.log("7b nextTick after the callback"));
});
console.log("2 sync end");
Output
1 sync start
2 sync end
3 nextTick queue
4 microtask: promise then
5 microtask: queueMicrotask
6 timers phase: setTimeout 0
7 poll phase: I/O callback
7b nextTick after the callback
8 check phase: setImmediate
9 timers phase, next loop
Every await gives other code a turn · ▶ Runs
const log = [];
async function step(name) {
  log.push(`${name} start`);
  await null;                        // one microtask hop, even for a value that is not a promise
  log.push(`${name} after await`);
}
step("A");
step("B");
Promise.resolve().then(() => log.push("then C"));
log.push("sync done");
await new Promise(r => setTimeout(r, 0));
console.log(log);
Output
[
  'A start',
  'B start',
  'sync done',
  'A after await',
  'B after await',
  'then C'
]
Inside an I/O callback, setImmediate always runs before setTimeout(fn, 0), because the check phase comes straight after poll. At the top level of a script, the order of those two depends on how fast the process starts, so never write a test that relies on it.
Part 5

⚙️Inside V8: JIT, hidden classes and inline caches

V8, the engine in Chrome and Node.js, first turns your code into bytecode and runs it with the Ignition interpreter. Functions that run often are compiled to machine code by the optimising compilers (Sparkplug, Maglev and TurboFan). The optimised code makes guesses, such as "this object always has x then y". If a guess turns out wrong, V8 deoptimises and falls back to slower code.

Hidden classes: objects with the same shape · ▶ Runs
// V8 gives objects with the same properties added in the same order the same hidden class ("map").
// Code that always sees one shape stays fast. %HaveSameMap is a V8 debugging helper.
function Point(x, y) { this.x = x; this.y = y; }
const a = new Point(1, 2), b = new Point(3, 4);
console.log("same constructor:", %HaveSameMap(a, b));

const c = new Point(5, 6);
c.label = "extra";                                   // a new property moves c to a new shape
console.log("extra property:", %HaveSameMap(a, c));

console.log("different order:", %HaveSameMap({ x: 1, y: 2 }, { y: 2, x: 1 }));

const d = new Point(7, 8);
delete d.x;                                          // delete makes V8 fall back to a slow dictionary
console.log("after delete:", %HaveSameMap(a, d), "| dictionary mode:", !%HasFastProperties(d));
Terminal
$ node --allow-natives-syntax main.mjs
Output
same constructor: true
extra property: false
different order: false
after delete: false | dictionary mode: true

Each property access remembers the shapes it has seen in an inline cache. One shape is monomorphic and fastest, a few is polymorphic, and many is megamorphic and slow. In practice: create objects with all their properties in the constructor, in the same order, and avoid delete on hot objects.

Do not tune for the engine before you measure (chapter 27). Shapes matter in tight loops over millions of objects, such as parsing a large log file, and almost never in test code.
Part 6

🧹Garbage collection

🧪 QA essentialSoak tests and long UI sessions expose memory leaks, and heap snapshots are how testers report them precisely.

JavaScript frees memory for you. V8 uses a generational collector because most objects die young. New objects go into the small young generation, which is cleaned often with a fast copying "scavenge". Objects that survive twice move to the old generation, which is cleaned less often with mark and sweep: mark everything reachable from the roots (globals and the stack), then free the rest. Most of the work happens in parallel and in small steps, so pauses stay short.

Generations in the V8 heap · ▶ Runs
import v8 from "node:v8";

// The heap is split into a young generation (new objects) and an old generation (survivors)
const spaces = v8.getHeapSpaceStatistics().map(s => s.space_name);
console.log("young:", spaces.includes("new_space"), "| old:", spaces.includes("old_space"), "| big objects:", spaces.includes("large_object_space"));

// Short lived objects are cheap: most die young and are collected in a quick "scavenge"
let kept = [];
for (let i = 0; i < 100_000; i++) {
  const temp = { id: i, tags: ["a", "b"] };          // garbage right after this iteration
  if (i % 10_000 === 0) kept.push(temp);              // only these survive
}
console.log("kept", kept.length, "objects out of 100000");
console.log("heap limit is a few GB:", v8.getHeapStatistics().heap_size_limit > 1e9);
Output
young: true | old: true | big objects: true
kept 10 objects out of 100000
heap limit is a few GB: true
If memory keeps rising in a long test run, take two heap snapshots in Chrome DevTools (Memory tab) or with v8.writeHeapSnapshot() and compare them. The objects that grow between the snapshots, and the "retainers" that hold them, point to the leak (chapter 27).
Part 7

🎬Real world scenario: a crash only in the retry helper

🧪 QA essential
The situationA test fails with "Cannot read properties of undefined (reading 'attempts')". The page object works when called directly, and fails only when it is passed to the shared retry helper.
Fix "Cannot read properties of undefined" in a page object · ▶ Runs
// A retry helper used by many page objects
async function retry(action, times = 3) {
  for (let i = 1; i <= times; i++) {
    try { return await action(); }
    catch (e) { if (i === times) throw e; }
  }
}

class CheckoutPage {
  attempts = 0;
  constructor(api) { this.api = api; }
  async submit() { this.attempts++; return this.api.post("/orders"); }
}

const flakyApi = { calls: 0, async post() { if (++this.calls < 2) throw new Error("503"); return { id: 1042 }; } };
const page = new CheckoutPage(flakyApi);

// The bug from the ticket: "Cannot read properties of undefined (reading 'attempts')"
await retry(page.submit).catch(e => console.log("bug:", e.message));

// Three fixes, each keeps "this" pointing at the page
console.log(await retry(() => page.submit()), "attempts:", page.attempts);
console.log(await retry(page.submit.bind(page)), "attempts:", page.attempts);
Output
bug: Cannot read properties of undefined (reading 'attempts')
{ id: 1042 } attempts: 2
{ id: 1042 } attempts: 3

The helper calls action() as a plain function, so this is undefined inside submit. Wrapping it in an arrow or binding it keeps the page object as this. The team also added a lint rule, @typescript-eslint/unbound-method, which flags this mistake in review.
