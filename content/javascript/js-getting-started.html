Part 1

🌍What JavaScript is and where it runs

🧪 QA essentialPlaywrightCypressSeleniumWebdriverIOMost modern UI and API automation tools are written in JavaScript or TypeScript, and their tests are too.

JavaScript is the programming language of the web. Every modern browser has a JavaScript engine built in, so the same code runs on a phone, a laptop and a smart TV. Outside the browser, Node.js, Deno and Bun run JavaScript on servers, laptops and CI machines.

NameWhat it is
ECMAScriptThe official standard. JavaScript is the language that follows it. A new edition comes out every June: ES2015 (also called ES6), ES2016 and so on up to ES2026.
TC39The committee that decides new features. A proposal moves through stages 0 to 4 and joins the standard at stage 4.
EngineThe program that runs the code: V8 (Chrome, Edge, Node.js, Deno), SpiderMonkey (Firefox) and JavaScriptCore (Safari, Bun).
RuntimeAn engine plus extra tools. A browser adds the page (DOM), fetch and storage. Node.js adds files, network servers and processes.
🛠️ Developers use it forweb pages, React or Angular apps, servers and APIs with Node.js, mobile apps with React Native and desktop apps with Electron.
🧪 QA engineers use it forUI automation with Playwright, Cypress, WebdriverIO and Selenium WebDriver, API tests, unit tests with Jest or Vitest, and small scripts that create test data or read reports.
JavaScript has nothing to do with Java. The name was picked in 1995 for marketing, and the language was written in about ten days by Brendan Eich.
Part 2

🧰Setting up Node.js and an editor

🧪 QA essential

To follow along on your own machine you need two things: Node.js and a code editor. Every example on this page also runs inside your browser with the ✏️ Edit and run button, so you can start right now.

  1. Install Node.js from nodejs.org. Pick the LTS (long term support) release for work projects. The Current release has the newest features.
  2. Install Visual Studio Code, the editor most JavaScript teams use. Its built in terminal opens with Ctrl + `.
  3. Open a terminal and check that both node and npm answer.
Check your setup in a terminal · Terminal commands
node -v          # which Node.js is installed
npm -v           # npm comes with Node.js
node             # opens the REPL, type .exit to leave
node hello.js    # runs a file
What happens

node -v prints a version such as v26.12.0. Every example on this page was run with that version.

Teams that work on several projects often need several Node.js versions. A version manager such as nvm switches between them.

Several Node.js versions side by side · Terminal commands
# macOS and Linux: install nvm once, then any Node.js version you need
nvm install --lts       # the long term support release, the safe choice for projects
nvm install 26          # the newest release line, used on this page
nvm use 26
node -v

# Windows: use the installer from nodejs.org or "nvm-windows"
A project can pin its Node.js version in a file called .nvmrc or in the engines field of package.json, so every developer and every CI machine uses the same one.
Playwright, Cypress and WebdriverIO all need Node.js. Before you install any of them, check node -v against the version the tool supports. A test that passes on your laptop and fails in CI is often just a different Node.js version.
Part 3

👋Your first program

A JavaScript program is a list of statements that run from top to bottom. console.log prints whatever you give it. Several values are printed with a space between them.

Your first program · ▶ Runs
console.log("Hello, Brainy Bytes!");
console.log("2 + 3 =", 2 + 3);
console.log(`Today we learn ${"JavaScript"}`);
Output
Hello, Brainy Bytes!
2 + 3 = 5
Today we learn JavaScript

The text inside backticks is a template literal. Anything inside ${ } is worked out and placed into the text. You will use it constantly for messages and test names.

Comments and semicolons

Statements, comments and semicolons · ▶ Runs
// A single line comment explains the next line
let price = 250; // a comment can also sit at the end of a line

/* A block comment
   can span many lines */
let qty = 3;

console.log(price * qty)   // no semicolon here, JavaScript adds one for us
console.log("done");
Output
750
done

Semicolons end statements. JavaScript has automatic semicolon insertion (ASI), so leaving them out usually works. Most teams pick one style and let a formatter such as Prettier enforce it.

The one place automatic semicolons bite · ▶ Runs
function getUser() {
  return
  {
    name: "Asha"
  };
}
console.log(getUser());
Output
undefined
A line break right after return makes JavaScript insert a semicolon there. The function returns undefined and the object below is never reached. Always start the returned value on the same line as return.

🖨️The console toolbox

🧪 QA essentialPlaywrightCypressJest

The console is your first debugging tool and the place where test runners print what they find. It can do far more than log.

The console toolbox · ▶ Runs
console.log("log is for normal messages");
console.info("info looks the same in Node");
console.warn("warn goes to the error stream");
console.error("error also goes to the error stream");

console.table([

console.group("Suite: cart");
console.log("adds an item");
console.log("removes an item");
console.groupEnd();

console.count("retry");
console.count("retry");

Measuring how long something takes · ▶ Runs
console.time("build list");
const items = [];
for (let i = 0; i < 100000; i++) items.push(i * 2);
console.timeEnd("build list");
console.log("items:", items.length);
Output
build list: 2.481ms
items: 100000
When a Playwright or Cypress test fails, add a console.log of the value you expected and the value you got. Playwright shows test output in its report, and in Cypress the browser console shows it. For timings, prefer the runner's own reports over console.time.
Part 5

🌐JavaScript in a web page

🧪 QA essentialSeleniumPlaywrightCypressLocators are CSS or XPath selectors, and executeScript or evaluate send JavaScript into the page.

In a browser, JavaScript can read and change the page. The page is a tree of objects called the DOM (Document Object Model). document.querySelector finds an element with a CSS selector, the same kind of selector a test tool uses to find a button.

JavaScript changes the page · ▶ Runs in the browser
📄 page.html
<!doctype html>
<html>
<head><title>Shop</title></head>
<body>
  <h1 id="title">Welcome</h1>
  <button id="buy">Buy now</button>
  <p id="msg"></p>
</body>
</html>
📄 script.js
const title = document.querySelector("#title");
console.log("Before:", title.textContent);
title.textContent = "Welcome back, Asha";
console.log("After:", title.textContent);

document.querySelector("#buy").addEventListener("click", () => {
  document.querySelector("#msg").textContent = "Added to cart";
  console.log("Clicked!");
});
document.querySelector("#buy").click();
console.log("Message:", document.querySelector("#msg").textContent);
Output
Before: Welcome
After: Welcome back, Asha
Clicked!
Message: Added to cart

A page loads JavaScript with a <script> tag. Where and how the tag is written decides when the code runs.

Four ways to load a script · HTML
<!-- Classic script: blocks the HTML parser while it downloads and runs -->
<script src="app.js"></script>

<!-- defer: downloads in parallel, runs in order after the HTML is parsed -->
<script defer src="app.js"></script>

<!-- async: downloads in parallel, runs as soon as it arrives, in any order -->
<script async src="analytics.js"></script>

<!-- module: deferred by default, strict mode, can use import and export -->
<script type="module" src="main.js"></script>

Every browser has DevTools (F12). Its Console tab runs any JavaScript you type against the open page. Testers use it to try a selector before putting it in a test: document.querySelectorAll("button.buy").length tells you at once whether the selector is unique.

Test tools send JavaScript into the page · Snippets, full runs come in chapter 15
// Selenium WebDriver for JavaScript
const title = await driver.executeScript("return document.title");

// Playwright
const count = await page.evaluate(() => document.querySelectorAll(".product").length);

// Cypress
cy.window().then(win => win.localStorage.setItem("token", "abc"));
All three tools let you run your own JavaScript inside the page under test. That is how you read values the UI does not show, set up storage or check something a locator cannot reach. The code you send runs in the browser, so it can use document and window, but it cannot see the variables in your test file.
Part 6

⚙️How the engine runs your code

Running a script happens in a few steps, and knowing them explains several surprises you will meet later.

  • Parse: the engine reads the whole file first. A typo anywhere is a SyntaxError and nothing runs at all.
  • Compile: V8 turns the code into bytecode, then a JIT (just in time) compiler turns busy functions into fast machine code while the program runs.
  • Execute: one line at a time on a single thread. JavaScript does one thing at a time. Waiting for a server or a timer is handed to the runtime, which is how one thread stays responsive. Chapter 10 explains this event loop.

Strict mode

Strict mode turns silent mistakes into errors. Modules (type="module" or .mjs files) and classes are always strict. Older scripts opt in with "use strict" on the first line.

The same typo without strict mode · ▶ Runs
let total = 0;
totl = 10;          // sloppy mode silently creates a global variable
console.log(total, totl);
Output
0 10
Strict mode catches a typo · 💥 Throws
"use strict";
let total = 0;
totl = 10;          // a typo creates a new global in sloppy mode, strict mode stops it
console.log(total);
Output
strict.cjs:3
totl = 10;          // a typo creates a new global in sloppy mode, strict mode stops it
     ^

ReferenceError: totl is not defined
    at Object.<anonymous> (strict.cjs:3:6)

Node.js v26.12.0
Write new code as modules and you get strict mode for free. Every .mjs example on this page is strict.
Part 7

🚨Reading error messages

🧪 QA essentialJestPlaywrightCypressEvery failed test hands you an error message and a stack trace to read.

Errors are not a failure on your part. They are the fastest way to learn what the program really did. Every error has a name, a message and a stack trace that lists where it happened.

Reading an error message · 💥 Throws
const user = { name: "Asha" };
console.log(user.name.toUpperCase());
console.log(user.address.city);
Output
ASHA
main.mjs:3
console.log(user.address.city);
                         ^

TypeError: Cannot read properties of undefined (reading 'city')
    at main.mjs:3:26

Node.js v26.12.0
  1. Read the name: TypeError means a value was the wrong type for what you did with it. Here user.address is undefined, and you cannot read city from it.
  2. Read the first stack line that points into your own file. main.mjs:3 is file, line and column.
  3. Look at that line and ask which value was missing. Then print it.
ErrorUsual cause
SyntaxErrorThe code is not valid JavaScript: a missing bracket or quote. Nothing in the file runs.
ReferenceErrorA name that does not exist, often a typo, or a variable used before let declared it.
TypeErrorReading a property of undefined or null, or calling something that is not a function.
RangeErrorA number out of range, such as new Array(-1), or endless recursion.

A try and catch block lets the program handle the error and carry on. Chapter 3 goes much deeper.

Catching the error instead of crashing · ▶ Runs
const cart = [];
try {
  cart.push({ id: 1, price: 99 });
  console.log(cart[0].price.toFixed(2));
  console.log(cart[1].price);
} catch (err) {
  console.log("Caught:", err.name);
  console.log("Message:", err.message);
}
console.log("The program keeps going");
Output
99.00
Caught: TypeError
Message: Cannot read properties of undefined (reading 'price')
The program keeps going
A failing test prints exactly this kind of stack. "Cannot read properties of undefined" inside a test usually means a locator found nothing or an API response did not have the field you expected. Read the line number, then log the value.
Part 8

🎬Real world scenario: summarise a test run

🧪 QA essentialnode:testReading results and reporting them is daily QA work, and node:test is the simplest way to start testing.
The situationYour team's nightly run produces a list of results. The lead wants a short summary in the chat every morning: how many passed, how many failed, the total time and the names of the failures.

The script below does exactly that with only what this chapter covered: an array of objects, a loop, a template literal and the console.

Summarise a test run · ▶ Runs
const results = [
  { name: "login works", status: "passed", ms: 812 },
  { name: "wrong password shows error", status: "passed", ms: 640 },
  { name: "checkout total", status: "failed", ms: 2310 },
  { name: "coupon applies", status: "skipped", ms: 0 },
  { name: "logout", status: "passed", ms: 301 },
];

const summary = { passed: 0, failed: 0, skipped: 0 };
let totalMs = 0;
for (const r of results) {
  summary[r.status]++;
  totalMs += r.ms;
}

console.table(summary);
console.log(`Total time: ${(totalMs / 1000).toFixed(2)} s`);
const failed = results.filter(r => r.status === "failed").map(r => r.name);
console.log("Failed:", failed);
Output
┌─────────┬────────┐
│ (index) │ Values │
├─────────┼────────┤
│ passed  │ 3      │
│ failed  │ 1      │
│ skipped │ 1      │
└─────────┴────────┘
Total time: 4.06 s
Failed: [ 'checkout total' ]

Real teams turn helpers like this into tested code. Node.js ships with a test runner, so a first automated check needs no extra installs. Run it with npm test.

A first automated check with the built in test runner · 🧪 Tests run
📄 summary.js
export function summarize(results) {
  const summary = { passed: 0, failed: 0, skipped: 0 };
  for (const r of results) summary[r.status]++;
  return summary;
}
📄 summary.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { summarize } from "./summary.js";

test("counts each status", () => {
  const got = summarize([{ status: "passed" }, { status: "failed" }, { status: "passed" }]);
  assert.deepEqual(got, { passed: 2, failed: 1, skipped: 0 });
});

test("an empty run has zero of everything", () => {
  assert.deepEqual(summarize([]), { passed: 0, failed: 0, skipped: 0 });
});
Terminal
$ npm test
Terminal output

Splitting the logic (summarize) from the printing makes it easy to test. The same idea, pure functions with the input and output kept separate, comes back in every chapter.
