Part 1

🧯The error types and building your own

🧪 QA essentialTest frameworks, HTTP clients and drivers all throw typed errors, and good helpers in a test framework do the same.

Every error has a name, a message and a stack. The built in types tell you what kind of mistake happened, which narrows the search before you read a single line of code.

The built in error types · ▶ Runs
const cases = [
  () => null.length,                         // TypeError: wrong kind of value
  () => notDefinedAnywhere,                  // ReferenceError: unknown name
  () => new Array(-1),                       // RangeError: value out of range
  () => JSON.parse("{bad json}"),            // SyntaxError: at run time, from a parser
  () => decodeURIComponent("%"),             // URIError
  () => { throw new AggregateError([new Error("a"), new Error("b")], "2 checks failed"); },
];
for (const fn of cases) {
  try { fn(); }
  catch (e) { console.log(e.constructor.name.padEnd(15), e.message, e.errors ? `(${e.errors.length} inside)` : ""); }
}
Output
TypeError       Cannot read properties of null (reading 'length') 
ReferenceError  notDefinedAnywhere is not defined 
RangeError      Invalid array length 
SyntaxError     Expected property name or '}' in JSON at position 1 (line 1 column 2) 
URIError        URI malformed 
AggregateError  2 checks failed (2 inside)

For your own code, a small hierarchy of error classes lets callers catch a whole family or one exact kind. Give each error a stable code for programs to check, a human message, and a cause when you wrap a lower level error.

Custom errors with code and cause · ▶ Runs
// A small hierarchy: catch the family, or one exact kind
class AppError extends Error {
  constructor(message, { code, cause, details } = {}) {
    super(message, { cause });
    this.name = new.target.name;             // "ValidationError", not "Error"
    this.code = code;
    this.details = details;
  }
}
class ValidationError extends AppError {}
class HttpError extends AppError {
  constructor(status, url) { super(`HTTP ${status} from ${url}`, { code: `HTTP_${status}` }); this.status = status; }
  get retryable() { return this.status >= 500 || this.status === 429; }
}

function placeOrder(qty) {
  if (!Number.isInteger(qty) || qty < 1) throw new ValidationError("qty must be a whole number from 1", { code: "BAD_QTY", details: { qty } });
  throw new HttpError(503, "/api/orders");
}

for (const qty of [0, 2]) {
  try { placeOrder(qty); }
  catch (e) {
    if (e instanceof ValidationError) console.log("fix the input:", e.code, e.details);
    else if (e instanceof HttpError) console.log(e.name, e.message, "| retry?", e.retryable);
    console.log("  still an Error:", e instanceof Error, "| an AppError:", e instanceof AppError);
  }
}

// Wrap low level errors with cause so no detail is lost
try {
  try { JSON.parse("<html>502 Bad Gateway</html>"); }
  catch (e) { throw new AppError("Could not read the orders response", { code: "BAD_BODY", cause: e }); }
} catch (e) {
  console.log(`${e.name}: ${e.message}\n  caused by ${e.cause.name}: ${e.cause.message.split(",")[0]}`);
}
Output
fix the input: BAD_QTY { qty: 0 }
  still an Error: true | an AppError: true
HttpError HTTP 503 from /api/orders | retry? true
  still an Error: true | an AppError: true
AppError: Could not read the orders response
  caused by SyntaxError: Unexpected token '<'
Check the code or the class, never the message text. Messages change with translations and wording fixes, codes do not.
Part 2

⏳Errors in async code

🧪 QA essentialPlaywrightNode.jsMissing awaits and unhandled rejections cause failures that appear in the wrong test, the hardest kind to debug.

A try block only sees errors thrown while it is on the call stack. A callback that runs later has left it already. With await, a rejected promise turns into an ordinary throw at that line, which is the main reason async and await made error handling simple.

Errors in async code · ▶ Runs
// 1. try and catch does not reach a callback that runs later
try {
  setTimeout(() => { try { throw new Error("inside the timer"); } catch (e) { console.log("caught inside the callback:", e.message); } }, 0);
} catch { console.log("this outer catch never runs"); }

// 2. With await, a rejected promise becomes a normal throw
async function loadUser() { throw new Error("401 Unauthorized"); }
try { await loadUser(); } catch (e) { console.log("await turns rejection into throw:", e.message); }

// 3. Without await, the rejection escapes the try block
try { loadUser().catch(e => console.log("only .catch sees it:", e.message)); }
catch { console.log("never reached"); }

// 4. finally runs whatever happens, which is where clean up belongs
async function withBrowser() {
  try { throw new Error("assertion failed"); }
  finally { console.log("finally: browser closed"); }
}
await withBrowser().catch(e => console.log("test failed:", e.message));
await new Promise(r => setTimeout(r, 5));
Output
await turns rejection into throw: 401 Unauthorized
finally: browser closed
only .catch sees it: 401 Unauthorized
test failed: assertion failed
caught inside the callback: inside the timer

A rejected promise that nobody handles is an unhandled rejection. Since Node.js 15 it stops the process with exit code 1, which is good: the bug cannot hide.

An unhandled rejection stops Node.js · 💥 Throws
async function save() { throw new Error("DB down"); }
save();                                      // nobody awaits or catches this promise
setTimeout(() => console.log("this line never prints"), 10);
Output
main.mjs:1
async function save() { throw new Error("DB down"); }
                              ^

Error: DB down
    at save (main.mjs:1:31)
    at main.mjs:2:1

Node.js v26.12.0
Global handlers for the errors nobody caught · 💥 Throws
// Last line of defence: log, then exit with a failure code so CI notices
process.on("unhandledRejection", (reason) => {
  console.log("unhandledRejection:", reason.message);
  process.exitCode = 1;
});
process.on("uncaughtException", (err, origin) => {
  console.log(`${origin}:`, err.message);
  process.exitCode = 1;
});
process.on("exit", code => console.log("exit code", code));

Promise.reject(new Error("forgot to await the cleanup"));
setTimeout(() => { throw new Error("bug in a timer"); }, 0);
Output
unhandledRejection: forgot to await the cleanup
uncaughtException: bug in a timer
exit code 1
The most common cause of an unhandled rejection in tests is a missing await before a Playwright action or an API call. The test may even pass, then a later test fails with a strange error. Turn on the no-floating-promises lint rule.
Part 3

📬Throw or return: errors as values

Throwing is right for things that should never happen. For failures you expect, such as a user typing a bad coupon, returning a result object keeps the flow simple and forces the caller to look at both cases.

Errors as values for expected failures · ▶ Runs
// Expected failures as values, unexpected ones as exceptions
const ok = value => ({ ok: true, value });
const fail = (code, message) => ({ ok: false, code, message });

function parseCoupon(text) {
  const m = /^([A-Z]+)(\d{1,2})$/.exec(text.trim());
  if (!m) return fail("FORMAT", `"${text}" is not like SAVE10`);
  const percent = Number(m[2]);
  if (percent > 50) return fail("TOO_BIG", `${percent}% is over the 50% limit`);
  return ok({ name: m[1], percent });
}

for (const input of ["SAVE10", "save10", "MEGA90"]) {
  const r = parseCoupon(input);
  console.log(input.padEnd(7), r.ok ? `valid ${r.value.percent}%` : `${r.code}: ${r.message}`);
}
Output
SAVE10  valid 10%
save10  FORMAT: "save10" is not like SAVE10
MEGA90  TOO_BIG: 90% is over the 50% limit
A good rule: validation and parsing of outside input return results, while broken assumptions inside your own code throw. Never use an empty catch {}, which hides the very information you will need later.

🔎Debugging tools

🧪 QA essentialPlaywrightVitestThe Inspector and trace viewer turn a red CI run into a step by step replay of what the browser saw.

console.log is fine for a quick look, but it hides deep objects and its output is easy to misread. Node.js gives you precise tools for inspecting values.

Inspect what you log · ▶ Runs
import util from "node:util";

const response = { status: 200, body: { order: { id: 7, items: [{ sku: "PEN", price: { amount: 10, currency: "INR" } }] } } };
console.log(response);                                          // nested objects are cut at depth 2
console.log(util.inspect(response, { depth: null, compact: true, breakLength: 120 }));
console.dir(response.body.order.items, { depth: 0 });

console.table([{ test: "login", ms: 840, ok: true }, { test: "checkout", ms: 2310, ok: false }]);
console.group("checkout");
console.count("retry");
console.count("retry");
console.assert(1 + 1 === 3, "maths is broken");               // prints only when false
console.groupEnd();
console.log(util.format("%s took %d ms (%o)", "login", 840, { slow: false }));

For anything harder, use a real debugger. You can pause on any line, look at every variable, step into functions and set conditional breakpoints that stop only when, for example, order.total < 0. Logpoints print a message without changing the code.

Starting the debuggers · Interactive tools
# Pause on the first line, then open chrome://inspect in Chrome or press F5 in VS Code
node --inspect-brk src/checkout.js

# Debug a single test file
node --inspect-brk --test test/cart.test.js
npx vitest --inspect-brk --no-file-parallelism cart.test.js

# Playwright: step through actions in the Inspector, or record a trace to replay later
PWDEBUG=1 npx playwright test checkout.spec.ts
npx playwright test --trace on && npx playwright show-trace test-results/**/trace.zip

# A debugger; statement in code pauses there when DevTools or the debugger is attached
The Playwright trace viewer is the best debugger for a failed UI test: it shows every action, a DOM snapshot before and after, the network calls and the console, all from a CI run you cannot reproduce on your laptop.
Part 5

🪵Structured logging

🧪 QA essentialAttaching a test id or request id to every log line is how you find the server logs that match one failed test.

Plain text logs are hard to search across many servers or parallel tests. Structured logs write one JSON object per line with a level, a message and fields. Tools such as pino in Node.js, and log platforms such as Grafana Loki, Datadog or ELK, filter them by any field.

Structured logs with a request id across awaits · ▶ Runs
import { AsyncLocalStorage } from "node:async_hooks";

// Structured JSON logs with a request id that follows the work through every await
const context = new AsyncLocalStorage();
const log = (level, msg, extra = {}) =>
  console.log(JSON.stringify({ level, msg, requestId: context.getStore()?.requestId, ...extra }));

async function fetchStock(sku) { await new Promise(r => setTimeout(r, sku === "PEN" ? 20 : 5)); log("debug", "stock checked", { sku }); return 3; }
async function handleOrder(requestId, sku) {
  return context.run({ requestId }, async () => {
    log("info", "order received", { sku });
    await fetchStock(sku);
    log("info", "order placed");
  });
}

// Two requests run at the same time, yet every line carries the right id
await Promise.all([handleOrder("req-1", "PEN"), handleOrder("req-2", "BOOK")]);
Output
{"level":"info","msg":"order received","requestId":"req-1","sku":"PEN"}
{"level":"info","msg":"order received","requestId":"req-2","sku":"BOOK"}
{"level":"debug","msg":"stock checked","requestId":"req-2","sku":"BOOK"}
{"level":"info","msg":"order placed","requestId":"req-2"}
{"level":"debug","msg":"stock checked","requestId":"req-1","sku":"PEN"}
{"level":"info","msg":"order placed","requestId":"req-1"}

AsyncLocalStorage keeps a value, such as a request id or the current test name, attached to all async work started inside context.run. That is how a log line deep in a helper still knows which request or test it belongs to.

🗺️Source maps

TypeScript, bundlers and minifiers change your code before it runs, so stack traces point at generated files. A source map is a file that maps each generated position back to the original line. Browsers use them automatically in DevTools. Node.js uses them with --enable-source-maps.

Source maps point the trace at the TypeScript line · 🧪 Tests run
📄 src/price.ts
export function lineTotal(price: number, qty: number): number {
  if (qty > 10) {
    throw new RangeError(`qty ${qty} is over the limit of 10`);
  }
  return price * qty;
}

lineTotal(99, 12);
📄 run.sh
npx tsc || exit 1
echo "$ node dist/price.js"
node dist/price.js 2>&1 | grep -E "RangeError|at lineTotal"
echo
echo "$ node --enable-source-maps dist/price.js"
node --enable-source-maps dist/price.js 2>&1 | grep -E "RangeError|at lineTotal"
true
Terminal
$ sh run.sh
Terminal output
$ node dist/price.js
        throw new RangeError(`qty ${qty} is over the limit of 10`);
RangeError: qty 12 is over the limit of 10
    at lineTotal (dist/price.js:3:15)

$ node --enable-source-maps dist/price.js
    throw new RangeError(`qty ${qty} is over the limit of 10`);
RangeError: qty 12 is over the limit of 10
    at lineTotal (src/price.ts:3:11)
Upload source maps to your error tracker, such as Sentry, so production errors show the real file and line. Keep them off the public web server if your source code is private.
Part 7

🎬Real world scenario: triage a red pipeline

🧪 QA essential
The situationThe nightly run has five failures. Before anyone opens a debugger, the team wants to know which failures are the product, which are the tests and which are the environment.
Triage failures by error type · ▶ Runs
// Sort failed tests into buckets before anyone starts debugging
const failures = [
  { test: "checkout total", error: { name: "AssertionError", message: "expected 450 to equal 405" } },
  { test: "login", error: { name: "TimeoutError", message: "locator.click: Timeout 5000ms exceeded" } },
  { test: "search", error: { name: "Error", message: "connect ECONNREFUSED 127.0.0.1:3000" } },
  { test: "profile", error: { name: "TypeError", message: "Cannot read properties of undefined (reading 'name')" } },
  { test: "orders", error: { name: "Error", message: "HTTP 503 from /api/orders" } },
];

const rules = [
  [e => /ECONNREFUSED|ENOTFOUND|HTTP 50[234]/.test(e.message), "environment"],
  [e => e.name === "TimeoutError", "timing or locator"],
  [e => e.name === "AssertionError" || /expect/.test(e.message), "possible product bug"],
  [e => ["TypeError", "ReferenceError"].includes(e.name), "test code bug"],
];
const bucket = e => rules.find(([match]) => match(e))?.[1] ?? "unknown";

const report = Object.groupBy(failures, f => bucket(f.error));
for (const [kind, list] of Object.entries(report)) console.log(kind.padEnd(21), list.map(f => f.test).join(", "));
Output
possible product bug  checkout total
timing or locator     login
environment           search, orders
test code bug         profile

Error names and messages carry enough signal to sort most failures automatically. Connection errors and 5xx responses point at the environment, timeouts at timing or locators, assertion errors at the product, and TypeErrors in test code at the tests themselves. Posting this summary to the team chat saves the first half hour of every morning.
