Part 1

📦Variables with let and const

🧪 QA essential

A variable is a name for a value. Modern JavaScript has two keywords for creating one.

constThe name always points at the same value. Use it by default, for URLs, selectors, test data and almost everything else.
letThe name can be pointed at a new value later. Use it for counters, totals and values that really change.
let, const and what const really protects · 💥 Throws
const baseUrl = "https://shop.example";   // never reassigned, so const
let attempts = 0;                          // changes, so let
attempts = attempts + 1;
attempts++;
console.log(baseUrl, attempts);

const user = { name: "Asha" };
user.name = "Ravi";        // allowed: the object changes, the binding does not
console.log(user);
user = {};                 // not allowed: const means this name always points at the same thing
Output
https://shop.example 2
{ name: 'Ravi' }
main.mjs:10
user = {};                 // not allowed: const means this name always points at the same thing
     ^

TypeError: Assignment to constant variable.
    at main.mjs:10:6

Node.js v26.12.0
const does not freeze an object. It only stops the name from being reassigned. Use Object.freeze(obj) when the contents must not change either.

And var

var is the original keyword from 1995. It ignores blocks and can be used before its line runs, which causes bugs. You will still see it in old code and old tutorials. Do not use it in new code.

var leaks out of blocks, let does not · ▶ Runs
for (var i = 0; i < 3; i++) {}
console.log("var i after the loop:", i);    // var leaks out of the block

for (let j = 0; j < 3; j++) {}
console.log(typeof j);                        // let stays inside the block
Output
var i after the loop: 3
undefined
Names are case sensitive and use camelCase: totalPrice, isLoggedIn, maxRetries. Constants that never change across the whole project are often written as MAX_RETRIES.
Keep test configuration in const values at the top of a file or in a config module: const BASE_URL = process.env.BASE_URL ?? "http://localhost:3000". Changing environments then means changing one line.

Copied or shared

Primitives are copied, objects are shared · ▶ Runs
let a = 5;
let b = a;       // the number is copied
b = 10;
console.log(a, b);

const cart1 = { items: 1 };
const cart2 = cart1;   // both names point at ONE object
cart2.items = 99;
console.log(cart1.items, cart2.items);

const cart3 = { ...cart1 };  // a shallow copy is a second object
cart3.items = 0;
console.log(cart1.items, cart3.items);
Output
5 10
99 99
99 0
This explains a common test bug. A shared object used as test data is changed by one test and the next test sees the change. Build fresh data in a beforeEach hook or copy it with structuredClone(data).

🔢Numbers, NaN and BigInt

🧪 QA essentialJestVitestPlaywright

JavaScript has one number type for whole numbers and decimals. It stores them in binary, so some decimals cannot be stored exactly.

Numbers, NaN, Infinity and BigInt · ▶ Runs
console.log(0.1 + 0.2);
console.log(0.1 + 0.2 === 0.3);
console.log(Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON);
console.log((0.1 + 0.2).toFixed(2));

console.log(7 / 2, Math.floor(7 / 2), 7 % 2, 2 ** 10);
console.log(1 / 0, -1 / 0, 0 / 0);
console.log(Number.isNaN(NaN), NaN === NaN);
console.log(Number.MAX_SAFE_INTEGER);
console.log(9007199254740993);             // too big, silently rounded
console.log(9007199254740993n + 1n);       // BigInt keeps every digit
Output
0.30000000000000004
false
true
0.30
3.5 3 1 1024
Infinity -Infinity NaN
true false
9007199254740991
9007199254740992
9007199254740994n
  • 0.1 + 0.2 is not exactly 0.3. Compare decimals with a small tolerance, or round them first.
  • NaN means "not a number", the result of a failed calculation. It is the only value not equal to itself, so test it with Number.isNaN.
  • Whole numbers are exact up to Number.MAX_SAFE_INTEGER (about 9 quadrillion). Larger IDs, such as some database keys, need BigInt or must stay strings.
Money without rounding errors · ▶ Runs
// Work with money in the smallest unit (paise or cents) to avoid floating point errors
const pricePaise = 129950;      // ₹1299.50
const qty = 3;
const totalPaise = pricePaise * qty;
console.log(totalPaise / 100);

const fmt = new Intl.NumberFormat("en-IN", { style: "currency", currency: "INR" });
console.log(fmt.format(totalPaise / 100));
Output
3898.5
₹3,898.50
Store money in the smallest unit as a whole number and format it only for display. Never add up prices as decimals.
Checking a cart total such as expect(total).toBe(0.3) can fail for the wrong reason. Use toBeCloseTo in Jest or Vitest, or compare the formatted text the user sees, such as "₹3,898.50".

🔄Type conversion and coercion

🧪 QA essentialEvery value read from the page with textContent, inputValue or getAttribute is a string.

Conversion is when you change a type on purpose. Coercion is when JavaScript does it for you behind the scenes. Both follow fixed rules.

Converting on purpose · ▶ Runs
console.log(Number("42"), Number(""), Number("42px"), Number(" 7 "));
console.log(parseInt("42px"), parseFloat("3.5kg"), parseInt("0x1F"), parseInt("101", 2));
console.log(String(42), (42).toString(2), `${42}`);
console.log(Boolean(""), Boolean("0"), Boolean(0), Boolean([]));
Output
42 0 NaN 7
42 3.5 31 5
42 101010 42
false true false true

When an operator gets the "wrong" type, JavaScript converts the value. The + operator prefers text: if either side is a string, it joins. The other maths operators convert to numbers.

Conversions JavaScript does by itself · ▶ Runs
console.log("5" + 3);        // + with a string joins text
console.log("5" - 3);        // - only works on numbers, so "5" becomes 5
console.log("5" * "2");
console.log(true + 1);
console.log([] + []);
console.log([] + {});
console.log(null + 1, undefined + 1);
console.log("10" > "9", 10 > "9");
Output

Truthy and falsy

In an if or with &&, || and !, every value counts as true or false. Only eight values are falsy. Everything else, including "0", "false", [] and {}, is truthy.

The eight falsy values · ▶ Runs
const values = [false, 0, -0, 0n, "", null, undefined, NaN, "0", "false", [], {}];
const labels = ["false", "0", "-0", "0n", '""', "null", "undefined", "NaN", '"0"', '"false"', "[]", "{}"];
values.forEach((v, i) => {
  console.log(labels[i].padEnd(10), v ? "truthy" : "falsy");
});
Output

Values read from an input field, a URL or an environment variable are always strings. process.env.HEADLESS set to "false" is truthy. Compare it with the text: process.env.HEADLESS === "true".

⚖️Equality: ==, === and Object.is

🧪 QA essentialJestVitestChaiPlaywrightPicking the wrong equality is the most common reason a correct assertion fails.

JavaScript has three ways to ask "are these the same".

==, === and Object.is · ▶ Runs
console.log(5 == "5", 5 === "5");
console.log(0 == false, 0 === false);
console.log(null == undefined, null === undefined);
console.log(NaN === NaN, Object.is(NaN, NaN));
console.log(0 === -0, Object.is(0, -0));

const a = { id: 1 }, b = { id: 1 }, c = a;
console.log(a === b, a === c);
console.log(JSON.stringify(a) === JSON.stringify(b));
Output
true false
true false
true false
false true
true false
false true
true
  • === (strict equality) compares without converting. Use it everywhere.
  • == (loose equality) converts first, which gives surprises such as 0 == "". The one useful case is x == null, which is true for both null and undefined.
  • Object.is is like === except that NaN equals NaN and 0 differs from -0.
  • Objects and arrays are equal only when they are the same object. Two objects with the same contents are not ===.

Test runners have the same split. In Jest and Vitest, toBe uses Object.is and toEqual compares contents. The first test below fails on purpose so you can read the message.

➕Operators

🧪 QA essentialPlaywrightCypressJest

Operators combine values. Most of them you know from maths. A few are special to JavaScript and very handy.

Arithmetic, comparison, logic and ?? · ▶ Runs
let score = 10;
score += 5;      // 15
score *= 2;      // 30
score -= 4;      // 26
score %= 7;      // 5
console.log(score);

const age = 20;
console.log(age >= 18 ? "adult" : "minor");
console.log(age > 18 && age < 60, age < 18 || age > 60, !true);

console.log("" || "default", 0 || 10, "set" && "both true");
console.log(JSON.stringify("" ?? "default"), 0 ?? 10, null ?? "fallback");
Output
5
adult
true false false
default 10 both true
"" 0 fallback
GroupOperators
Arithmetic+ - * / % **, and ++ and -- to add or take away one
Assignment= += -= *= /= %= **=
Comparison=== !== < > <= >=
Logical&& (and), || (or), ! (not). They return one of their values, not just true or false.
Nullish?? uses the right side only when the left is null or undefined
Optional chaining?. stops and gives undefined instead of crashing on a missing value
Logical assignment||= &&= ??= assign only when needed
Conditionalcondition ? a : b

?? against ||

|| replaces every falsy value, so a real 0 or an empty string is lost. ?? replaces only null and undefined. For defaults such as a timeout or a retry count, ?? is almost always what you want.

Optional chaining and logical assignment · ▶ Runs
const response = {
  user: { name: "Asha", address: null, orders: [{ id: 7, total: 1299 }] },
};

console.log(response.user?.address?.city);           // undefined, no crash
console.log(response.user?.address?.city ?? "Unknown");
console.log(response.user.orders?.[0]?.total);
console.log(response.user.orders?.[5]?.total ?? 0);
console.log(response.user.greet?.());                // call it only if it exists

const settings = { retries: 0, timeout: null };
settings.retries ||= 3;     // 0 is falsy, so it becomes 3
settings.timeout ??= 5000;  // only null or undefined is replaced
console.log(settings);
Output
undefined
Unknown
1299
0
undefined
{ retries: 3, timeout: 5000 }
API responses are full of optional fields. body.data?.items?.[0]?.id reads deep values without a crash, so the assertion that follows fails with a clear message instead of a TypeError.
Part 7

🎬Real world scenario: clean up data from an API

🧪 QA essential
The situationA product API returns prices as text with a currency sign, stock as text and a discount that is sometimes missing. Before you can check the numbers, you must turn them into real numbers without crashing on the gaps.
Normalise messy test data · ▶ Runs
// An API returned product data in an awkward shape. Normalise it before checking it.
const apiProducts = [
  { sku: "A1", price: "₹1,299.50", stock: "12", discount: null },
  { sku: "B2", price: "₹499", stock: "0", discount: { percent: 10 } },
  { sku: "C3", price: "", stock: undefined },
];

function toNumber(text) {
  const clean = String(text ?? "").replace(/[^0-9.]/g, "");
  return clean === "" ? null : Number(clean);
}

const products = apiProducts.map(p => ({
  sku: p.sku,
  price: toNumber(p.price),
  inStock: Number(p.stock ?? 0) > 0,
  discount: p.discount?.percent ?? 0,
}));
console.table(products);

const problems = products.filter(p => p.price === null || Number.isNaN(p.price));
console.log("Products with a missing price:", problems.map(p => p.sku));
Output
┌─────────┬──────┬────────┬─────────┬──────────┐
│ (index) │ sku  │ price  │ inStock │ discount │
├─────────┼──────┼────────┼─────────┼──────────┤
│ 0       │ 'A1' │ 1299.5 │ true    │ 0        │
│ 1       │ 'B2' │ 499    │ false   │ 10       │
│ 2       │ 'C3' │ null   │ false   │ 0        │
└─────────┴──────┴────────┴─────────┴──────────┘
Products with a missing price: [ 'C3' ]

Every tool from this chapter is here: ?? for missing values, ?. for the optional discount, explicit Number conversion, and a check with Number.isNaN for anything that went wrong.

The same toNumber helper is useful in the app itself. Parsing input once, at the edge, keeps the rest of the code working with clean types.
