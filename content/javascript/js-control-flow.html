Part 1

🔀Making decisions with if and else

🧪 QA essentialEach branch is a test case, and coverage tools measure how many branches your tests reach.

An if statement runs a block only when a condition is truthy. else if adds more conditions, checked from the top, and the first one that matches wins.

if, else if and else · ▶ Runs
function shippingFee(total, isMember) {
  if (total <= 0) {
    return "invalid";
  } else if (isMember || total >= 999) {
    return 0;
  } else if (total >= 500) {
    return 40;
  } else {
    return 80;
  }
}

console.log(shippingFee(1200, false));
console.log(shippingFee(600, false));
console.log(shippingFee(300, true));
console.log(shippingFee(300, false));
console.log(shippingFee(-5, false));
Output
0
40
0
80
invalid
Order matters. Put the most specific condition first. If total >= 500 came before total >= 999, a ₹1200 order would wrongly pay ₹40.

Guard clauses

Deep nesting is hard to read. Handle the bad cases first and return early, so the main logic stays at the left edge.

Guard clauses keep code flat · ▶ Runs
function applyCoupon(cart, code) {
  if (!cart) return "no cart";
  if (cart.items.length === 0) return "cart is empty";
  if (code !== "SAVE10") return "unknown coupon";

  // the happy path, no nesting needed
  return `saved ${cart.total * 0.1}`;
}

console.log(applyCoupon(null, "SAVE10"));
console.log(applyCoupon({ items: [], total: 0 }, "SAVE10"));
console.log(applyCoupon({ items: [1], total: 500 }, "OOPS"));
console.log(applyCoupon({ items: [1], total: 500 }, "SAVE10"));
Output
no cart
cart is empty
unknown coupon
saved 50
Every if and else is a path that needs a test. The shipping fee above has five paths, so it needs at least five test cases, plus the boundary values 499, 500, 998 and 999. Branch coverage reports count exactly these paths.
Part 2

🎛️switch and lookup tables

switch compares one value against many cases with ===. Cases without a break or return fall through into the next one, which is useful for shared results and a classic bug otherwise.

switch, shared cases and fall through · ▶ Runs
function statusIcon(status) {
  switch (status) {
    case "passed":
      return "✅";
    case "failed":
    case "broken":           // two cases share one result
      return "❌";
    case "skipped":
      return "⏭️";
    default:
      return "❓";
  }
}
["passed", "broken", "skipped", "flaky"].forEach(s => console.log(s, statusIcon(s)));

// forgetting break makes execution "fall through" into the next case
const level = 2;
switch (level) {
  case 1: console.log("one");
  case 2: console.log("two");
  case 3: console.log("three");
  default: console.log("default");
}
Output
passed ✅
broken ❌
skipped ⏭️
flaky ❓
two
three
default

When each case only picks a value, an object used as a lookup table is shorter and easier to extend.

An object lookup instead of a switch · ▶ Runs
const ICONS = { passed: "✅", failed: "❌", broken: "❌", skipped: "⏭️" };
const icon = status => ICONS[status] ?? "❓";
console.log(icon("passed"), icon("broken"), icon("flaky"));
Output
✅ ❌ ❓

🔁Loops

Loops repeat work. Pick the loop by what you are repeating over.

Every kind of loop · ▶ Runs
for (let i = 1; i <= 3; i++) {
  console.log("for", i);
}

let tries = 0;
while (tries < 2) {
  tries++;
  console.log("while try", tries);
}

let n = 10;
do {
  console.log("do runs at least once, n =", n);
} while (n < 5);

for (const browser of ["chromium", "firefox", "webkit"]) {
  console.log("for...of", browser);
}

const user = { name: "Asha", role: "admin" };
for (const key in user) {
  console.log("for...in", key, "=", user[key]);
}
Output
for 1
for 2
for 3
while try 1
while try 2
do runs at least once, n = 10
for...of chromium
for...of firefox
for...of webkit
for...in name = Asha
for...in role = admin
LoopUse it when
for (let i = 0; i < n; i++)you need the counter, or a fixed number of repeats
for (const x of list)you want each value of an array, string, Map or Set. The usual choice.
for (const key in obj)you want the keys of a plain object. Avoid it on arrays.
while (condition)you do not know how many times, such as polling until something is ready
do { } while (condition)the body must run at least once

break, continue and labels

break, continue and labels · ▶ Runs
const results = ["pass", "pass", "skip", "fail", "pass"];
for (const r of results) {
  if (r === "skip") continue;      // jump to the next item
  if (r === "fail") {
    console.log("stopping at the first failure");
    break;                         // leave the loop
  }
  console.log("checked", r);
}

outer: for (const row of [[1, 2], [3, 4], [5, 6]]) {
  for (const cell of row) {
    if (cell === 4) break outer;   // a label breaks out of both loops
    console.log(cell);
  }
}

checked pass
stopping at the first failure

2

const scores = { asha: 82, ravi: 67, mei: 91 };
for (const [name, score] of Object.entries(scores)) {
  console.log(`${name}: ${score >= 70 ? "pass" : "fail"}`);

const tests = ["login", "search", "checkout"];

A while loop whose condition never becomes false runs forever and freezes the page or the test. Every polling loop needs a timeout, as shown later in this chapter.
Part 4

⏱️Loops with async steps

🧪 QA essentialPlaywrightWebdriverIOSeleniumCypressAwaiting inside forEach is one of the most common causes of flaky UI tests.

Test code is full of steps that take time: open a page, click, wait for a response. These steps return promises and are written with await (chapter 11 explains how they work). Loops and await have one trap that breaks many first test suites.

forEach does not wait for async steps · ▶ Runs
const sleep = ms => new Promise(r => setTimeout(r, ms));
const steps = ["open page", "fill form", "submit"];

console.log("forEach does not wait:");
steps.forEach(async step => {
  await sleep(10);
  console.log("  done:", step);
});
console.log("  forEach returned already");
await sleep(50);

console.log("for...of waits for each step:");
for (const step of steps) {
  await sleep(10);
  console.log("  done:", step);
}
console.log("  every step finished");
Output
forEach does not wait:
  forEach returned already
  done: open page
  done: fill form
  done: submit
for...of waits for each step:
  done: open page
  done: fill form
  done: submit
  every step finished
  • array.forEach calls the function for every item and does not wait for any of them. The loop is "finished" while the steps are still running.
  • for...of with await inside runs the steps one after another, in order. Use it for UI steps.
  • To start many independent requests at once and wait for all of them, use await Promise.all(list.map(async x => ...)).
In Playwright and WebdriverIO, items.forEach(async item => await page.click(item)) makes clicks race each other and the test may end before they finish. Write for (const item of items) await page.click(item). Cypress queues its commands, so a plain forEach with cy commands inside works there, which is one of the main differences between the tools.
Part 5

🧯Throwing and catching errors

🧪 QA essentialJestPlaywrightMochaAn assertion failure is a thrown error. Knowing how errors travel explains how runners report and clean up.

Code signals a problem by throwing an error. The error travels up through the functions that called it until a try block catches it. If nothing catches it, the program stops.

throw, try, catch and finally · ▶ Runs
function withdraw(balance, amount) {
  if (typeof amount !== "number" || Number.isNaN(amount)) {
    throw new TypeError("amount must be a number");
  }
  if (amount > balance) {
    throw new RangeError(`cannot withdraw ${amount}, balance is ${balance}`);
  }
  return balance - amount;
}

for (const amount of [30, "ten", 500]) {
  try {
    console.log("new balance:", withdraw(100, amount));
  } catch (err) {
    console.log(`${err.name}: ${err.message}`);
  } finally {
    console.log("finally always runs");
  }
}
Output
new balance: 70
finally always runs
TypeError: amount must be a number
finally always runs
RangeError: cannot withdraw 500, balance is 100
finally always runs
  • Throw Error objects (or subclasses such as TypeError), never plain strings. Only Error objects carry a stack trace.
  • finally runs whether the block passed, threw or returned. It is the place for cleanup.
  • Catch only what you can handle. Rethrow everything else with throw err.

Custom errors and causes

A subclass of Error lets callers tell your error apart from others with instanceof. The cause option (ES2022) wraps a low level error in a clearer one without losing it.

A custom error with a cause · ▶ Runs
class ValidationError extends Error {
  constructor(field, message, options) {
    super(message, options);
    this.name = "ValidationError";
    this.field = field;
  }
}

function parseAge(text) {
  const age = Number(text);
  if (!Number.isInteger(age)) {
    throw new ValidationError("age", `"${text}" is not a whole number`);
  }
  return age;
}

function signUp(form) {
  try {
    return { ok: true, age: parseAge(form.age) };
  } catch (err) {
    if (err instanceof ValidationError) {
      // wrap it with more context and keep the original as the cause
      throw new Error(`sign up failed for ${form.email}`, { cause: err });
    }
    throw err;   // anything else is unexpected, pass it on
  }
}

try {
  signUp({ email: "asha@example.com", age: "twenty" });
} catch (err) {
  console.log(err.message);
  console.log("cause:", err.cause.name, "on", err.cause.field, "-", err.cause.message);
}
Output
sign up failed for asha@example.com
cause: ValidationError on age - "twenty" is not a whole number

finally for cleanup

finally for cleanup · ▶ Runs
async function runTest(name, body) {
  const browser = { open: true };          // pretend we launched a browser
  console.log(`[${name}] browser launched`);
  try {
    await body();
    console.log(`[${name}] passed`);
  } catch (err) {
    console.log(`[${name}] failed: ${err.message}`);
  } finally {
    browser.open = false;                    // cleanup runs on pass and on fail
    console.log(`[${name}] browser closed`);
  }
}

await runTest("login", async () => {});
await runTest("checkout", async () => { throw new Error("button not found"); });
Output
[login] browser launched
[login] passed
[login] browser closed
[checkout] browser launched
[checkout] failed: button not found
[checkout] browser closed
A test runner is a giant try, catch and finally. Each test body runs inside try, a failed assertion is a thrown error, and afterEach hooks run like finally. That is why a failed assertion stops the rest of that test but not the suite.
Part 6

⏳Polling and retry loops

🧪 QA essentialPlaywrightCypressSeleniumWebdriverIOAuto-waiting and retries are loops like these, and their timeout options are the loop limits.

Two loops sit at the centre of every test framework. You will rarely write them yourself, but knowing how they work explains timeouts, flaky tests and the options every tool offers.

Wait until something is true

A polling loop with a timeout · ▶ Runs
const sleep = ms => new Promise(r => setTimeout(r, ms));

// The heart of every "wait until" helper: check, wait a little, check again, give up after a timeout.
async function waitFor(check, { timeout = 1000, interval = 100 } = {}) {
  const start = Date.now();
  let attempt = 0;
  while (true) {
    attempt++;
    const value = await check();
    if (value) return { value, attempt };
    if (Date.now() - start >= timeout) {
      throw new Error(`condition not met after ${attempt} attempts`);
    }
    await sleep(interval);
  }
}

// A fake "order status" that becomes ready on the 4th check
let calls = 0;
const orderStatus = async () => (++calls >= 4 ? "SHIPPED" : null);

const result = await waitFor(orderStatus, { timeout: 2000, interval: 50 });
console.log(result);

try {
  await waitFor(async () => false, { timeout: 200, interval: 50 });
} catch (err) {
  console.log(err.message);
}
Output
{ value: 'SHIPPED', attempt: 4 }
condition not met after 5 attempts

Playwright's auto-waiting, expect.poll, Cypress retry-ability, WebdriverIO's waitUntil and Selenium's driver.wait are all versions of this loop: check, wait a short interval, check again, fail with a clear message after the timeout.

Retry an action that sometimes fails

Retry with exponential backoff · ▶ Runs
async function retry(action, { attempts = 3, delay = 50 } = {}) {
  let lastError;
  for (let i = 1; i <= attempts; i++) {
    try {
      return await action(i);
    } catch (err) {
      lastError = err;
      console.log(`attempt ${i} failed: ${err.message}`);
      if (i < attempts) await new Promise(r => setTimeout(r, delay * 2 ** (i - 1)));  // 50, 100, 200 ms
    }
  }
  throw new Error(`gave up after ${attempts} attempts`, { cause: lastError });
}

const flaky = async attempt => {
  if (attempt < 3) throw new Error("503 Service Unavailable");
  return "200 OK";
};
console.log(await retry(flaky));
Output
attempt 1 failed: 503 Service Unavailable
attempt 2 failed: 503 Service Unavailable
200 OK
Retry infrastructure problems (a 503 from a test server, a slow container). Never retry to hide a real bug. A test that only passes on the third try is reporting something.
Part 7

🎬Real world scenario: data driven password checks

🧪 QA essentialJestVitestPlaywright
The situationA sign up form has a password rule: 8 to 64 characters, at least one capital letter and one digit. You need to check the rule on all the important inputs, including the boundaries, and show a readable report.
A table of test cases · ▶ Runs
// Data driven checks: one validation rule, a table of inputs and the result each should give.
function isValidPassword(pw) {
  if (typeof pw !== "string") return false;
  if (pw.length < 8 || pw.length > 64) return false;
  if (!/[A-Z]/.test(pw)) return false;
  if (!/[0-9]/.test(pw)) return false;
  return true;
}

const cases = [
  { input: "Secret12", expected: true, why: "8 chars, upper, digit" },
  { input: "Secret1", expected: false, why: "7 chars, one too short" },
  { input: "secret12", expected: false, why: "no upper case" },
  { input: "SecretOK", expected: false, why: "no digit" },
  { input: "A1" + "x".repeat(62), expected: true, why: "64 chars, the maximum" },
  { input: "A1" + "x".repeat(63), expected: false, why: "65 chars, one too long" },
  { input: null, expected: false, why: "not a string" },
];

let failures = 0;
for (const c of cases) {
  const actual = isValidPassword(c.input);
  const ok = actual === c.expected;
  if (!ok) failures++;
  console.log(`${ok ? "PASS" : "FAIL"}  ${c.why.padEnd(24)} expected ${c.expected}, got ${actual}`);
}
console.log(failures === 0 ? "All cases pass" : `${failures} case(s) failed`);
Output
PASS  8 chars, upper, digit    expected true, got true
PASS  7 chars, one too short   expected false, got false
PASS  no upper case            expected false, got false
PASS  no digit                 expected false, got false
PASS  64 chars, the maximum    expected true, got true
PASS  65 chars, one too long   expected false, got false
PASS  not a string             expected false, got false
All cases pass

This is data driven testing: the logic of the check is written once and the cases live in a table. Adding a case means adding one row. Every test runner has a built in version: test.each in Jest and Vitest, a loop over test() in Playwright, and data providers in TestNG.

The rows were chosen with boundary value analysis: 7, 8, 64 and 65 characters, plus one row for each rule broken on its own. Each row has a short "why", which becomes the test name and tells the reader what failed.
