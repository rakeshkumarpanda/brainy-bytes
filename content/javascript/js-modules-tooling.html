Part 1

📦ES modules: import and export

🧪 QA essentialEvery test file imports a runner, page objects and helpers. Playwright, Vitest and WebdriverIO projects are ES modules by default.

A module is a file with its own scope. Nothing inside it is visible to other files unless it is exported, and nothing from outside is available unless it is imported. This keeps large codebases and test suites tidy: page objects, helpers and test data each live in their own file.

Named and default exports · ▶ Runs
📄 money.mjs
export const TAX_RATE = 0.18;

export function addTax(amount) {
  return Math.round(amount * (1 + TAX_RATE));
}

export class Cart {
  total = 0;
  add(price) { this.total += price; return this; }
}

export default function formatPrice(amount) {
  return `₹${amount.toLocaleString("en-IN")}`;
}
📄 main.mjs
import formatPrice, { TAX_RATE, addTax, Cart as ShoppingCart } from "./money.mjs";
import * as money from "./money.mjs";       // everything, as one object

console.log(TAX_RATE, addTax(100));
console.log(formatPrice(2695));
const cart = new ShoppingCart();
console.log(cart.add(500).add(250).total);
console.log(Object.keys(money));

Modules are always strict, run once however many files import them, and may use await at the top level.

🧱CommonJS and how the two mix

🧪 QA essentialJestMochaSeleniumJest, Mocha and many Selenium projects are CommonJS, and mixing the two styles causes the most common set up errors.

Before ES modules, Node.js used CommonJS: require() to load and module.exports to share. Older packages, Jest setups, Mocha and many Selenium projects still use it, so you will read both styles.

CommonJS: require and module.exports · ▶ Runs
📄 text.cjs
function slugify(text) {
  return text.toLowerCase().trim().replace(/[^a-z0-9]+/g, "-");
}
module.exports = { slugify };
📄 money.mjs
export const addTax = amount => Math.round(amount * 1.18);
📄 main.cjs
const { slugify } = require("./text.cjs");     // CommonJS: require and module.exports
const path = require("node:path");

console.log(slugify("Add to Cart Button"));
console.log(path.join("tests", "e2e", "login.spec.js"));
console.log(typeof module.exports, typeof __dirname);

// Since Node 22, require() can also load an ES module that has no top level await
const { addTax } = require("./money.mjs");
console.log(addTax(100));

Part 3

📥npm and package.json

🧪 QA essentialInstalling, pinning and updating test tools, and running them through npm scripts, is part of every automation project.

npm installs packages from the npm registry into node_modules and records them in package.json. The lock file (package-lock.json) pins the exact version of every package, so every laptop and CI machine installs the same thing.

A package.json for a test project · Reference
{
  "name": "shop-tests",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=22" },
  "scripts": {
    "test": "npm run test:unit && npm run test:api",
    "test:unit": "vitest run",
    "test:api": "node --test tests/api/",
    "test:e2e": "playwright test",
    "lint": "eslint .",
    "format": "prettier --write ."
  },
  "dependencies": {
    "ajv": "^8.17.1"
  },
  "devDependencies": {
    "@playwright/test": "~1.56.0",
    "vitest": "^5.0.0",
    "eslint": "10.13.0"
  }
}
What happens

"type": "module" makes .js files ES modules. Scripts run with npm run test:unit. devDependencies are tools only needed to build and test.

Version ranges

Versions follow semantic versioning: MAJOR.MINOR.PATCH. A major bump may break your code. A caret ^ allows new minor and patch versions. A tilde ~ allows only new patches. No symbol means that exact version. Below 1.0.0 the caret is stricter: ^0.4.2 allows only 0.4.x, because in a 0.x package every minor release may break things.

What ^ and ~ allow · ▶ Runs
import semver from "semver";            // a package from node_modules

const checks = [
  ["^1.56.0", "1.58.2"], ["^1.56.0", "2.0.0"],
  ["~1.56.0", "1.56.9"], ["~1.56.0", "1.57.0"],
  ["1.56.1", "1.56.2"], ["^0.4.2", "0.5.0"],
];
for (const [range, version] of checks) {
  console.log(range.padEnd(8), version.padEnd(7), semver.satisfies(version, range) ? "allowed" : "not allowed");
}
console.log(semver.maxSatisfying(["1.55.0", "1.56.4", "1.60.1", "2.1.0"], "^1.56.0"));

The npm commands you use every week · Reference
npm init -y                      # create package.json
npm install ajv                  # add a dependency (writes package.json and package-lock.json)
npm install -D @playwright/test  # add a dev dependency
npm ci                           # clean install exactly what the lock file says (use this in CI)
npm run test:unit                # run a script from package.json
npm test -- --reporter=verbose   # pass extra options to the script after --
npx playwright test --headed     # run a tool from node_modules/.bin
npm outdated                     # what has newer versions
npm audit                        # known security problems in dependencies
Use npm ci in pipelines, not npm install. It fails if package.json and the lock file disagree, and it never changes the lock file. Pin browser automation tools such as Playwright exactly or with ~, because a new version also brings new browser builds.

🔷TypeScript

🧪 QA essentialPlaywrightCypressWebdriverIOPlaywright and most modern frameworks generate TypeScript projects, and typed page objects catch broken locators and data at edit time.

TypeScript is JavaScript with types added. You describe the shape of your data once, and the type checker warns you about wrong property names, missing fields and wrong value types while you type, long before a test runs. Playwright, Angular and most new projects use it, and its tests are usually written in it too.

TypeScript runs directly in Node.js · ▶ Runs
type Status = "passed" | "failed" | "skipped";

interface TestResult {
  name: string;
  status: Status;
  durationMs: number;
  retries?: number;              // optional
}

function slowest<T extends { durationMs: number }>(items: T[], count = 1): T[] {
  return items.toSorted((a, b) => b.durationMs - a.durationMs).slice(0, count);
}

const results: TestResult[] = [
  { name: "login", status: "passed", durationMs: 840 },
  { name: "checkout", status: "failed", durationMs: 2310, retries: 2 },
  { name: "search", status: "passed", durationMs: 120 },
];

const failed = results.filter(r => r.status === "failed").map(r => r.name);
console.log(failed, slowest(results)[0].name);
Output
[ 'checkout' ] checkout

Node.js 23.6 and later run .ts files directly by removing the type annotations. It does not check them. Checking is the job of tsc, the TypeScript compiler, usually run as its own step in CI.

🧹ESLint and Prettier

🧪 QA essentialPlaywrightJestCypressA missing await or a forgotten test.only is caught by the linter before it reaches CI.

ESLint reads your code without running it and reports likely bugs and risky habits: unused variables, typos in names, == where === was meant, an async function that never awaits. Rules live in eslint.config.js.

🔐Environment variables and config

🧪 QA essentialChoosing the target environment, test users and secrets through variables is how one suite runs against every environment.

The same tests must run against a laptop, a staging server and sometimes production. The parts that change, such as the base URL, user names and secrets, come from environment variables in process.env. Node.js can load them from a .env file with --env-file, with no extra package.

Configuration from environment variables · ▶ Runs
📄 .env
# Never commit real secrets. Keep .env in .gitignore and use CI secrets instead.
TEST_ENV=staging
BASE_URL=https://staging.shop.example
TEST_USER=qa.bot@shop.example
TEST_PASSWORD=not-a-real-password
HEADLESS=true
📄 main.mjs
// Values come from .env, which Node.js loads with --env-file
const config = {
  env: process.env.TEST_ENV,
  baseURL: process.env.BASE_URL,
  user: process.env.TEST_USER,
  headless: process.env.HEADLESS !== "false",
  workers: Number(process.env.WORKERS ?? 2),
};
console.log(config);
console.log("password loaded:", Boolean(process.env.TEST_PASSWORD), "| length:", process.env.TEST_PASSWORD.length);
Terminal
$ node --env-file=.env main.mjs
Output
{
  env: 'staging',
  baseURL: 'https://staging.shop.example',
  user: 'qa.bot@shop.example',
  headless: true,
  workers: 2
}
password loaded: true | length: 19
Everything in process.env is a string. "false" is truthy, so compare with === "true" or !== "false", and turn numbers into numbers. Never commit passwords or tokens: add .env to .gitignore and use your CI tool's secret store.

🎬Real world scenario: lay out a test project

🧪 QA essential
The situationYou are starting the automation project for a shop. Unit tests, API tests and end to end tests must be runnable on their own, and CI must be able to run each of them as a separate job.

Source code lives in src. Tests are split by kind under tests. Each kind gets its own npm script, so a developer runs npm run test:unit in seconds while CI runs every script.

Separate scripts for each kind of test · 🧪 Tests run
📄 package.json
{
  "name": "shop-tests",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "test:unit": "node --test --test-reporter=spec tests/unit/",
    "test:api": "node --test --test-reporter=spec tests/api/"
  }
}
📄 src/price.js
export function addTax(amount, rate = 0.18) {
  return Math.round(amount * (1 + rate) * 100) / 100;
}
📄 src/api.js
export function buildQuery(params) {
  return new URLSearchParams(Object.entries(params).filter(([, v]) => v != null)).toString();
}
📄 tests/unit/price.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { addTax } from "../../src/price.js";

test("adds 18% by default", () => assert.equal(addTax(100), 118));
test("rounds to paise", () => assert.equal(addTax(9.99), 11.79));
📄 tests/api/query.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { buildQuery } from "../../src/api.js";

test("drops empty filters", () => {
  assert.equal(buildQuery({ q: "pen", page: 2, sort: null }), "q=pen&page=2");
});
