Part 1

🗺️The journey of a JavaScript program

When you press Run, your .js file is only text. Two programs work together to turn that text into output. The engine understands the JavaScript language. The runtime (also called the host) is the program the engine lives inside, such as Chrome or Node.js, and it adds everything the language itself does not have: timers, the network, files and the web page.

PieceWhat it doesReal examples
EngineScans, parses, compiles and runs the code, and cleans up memoryV8 (Chrome, Edge, Node.js, Deno), SpiderMonkey (Firefox), JavaScriptCore (Safari, Bun)
RuntimeLoads files, provides the event loop and the extra APIsA browser tab, Node.js, Deno, Bun, Electron apps, Cloudflare Workers
Extras from a browserdocument, fetch, setTimeout, localStorage, eventsThe Web APIs

Think about what happens when you open a shopping site on your phone. Chrome downloads the page and its scripts, V8 turns those scripts into running code in a few milliseconds, and the same V8 keeps optimising the code that runs most, such as the function that recalculates your cart. When you tap "Add to cart", the browser notices the tap, and the event loop hands your click handler to V8 to run. Every part of this chapter is one step of that story.

StepJavaJavaScript
Who compiles firstYou run javac, which writes a .class file of bytecodeNobody. You ship the source text and the engine compiles it when it loads
What runs itThe JVM: class loader, bytecode verifier, interpreter, JIT, garbage collectorThe engine: parser, Ignition interpreter, Sparkplug, Maglev and TurboFan, garbage collector

You never call the compiler in JavaScript, but it is still there. V8 compiles in the background while your page runs. That is why the same code can get faster after it has run a few thousand times.
Part 2

📥Step 1: loading the source text

The engine cannot read files or download anything itself. The runtime fetches the text and hands it over.

  • In a browser, the HTML parser meets a <script> tag and downloads the file. A classic script blocks the page while it downloads and runs, defer and type="module" scripts wait until the HTML is parsed (chapter 1 shows the timeline).
  • In Node.js, node app.js reads the file from disk. The file extension and the "type" field in package.json decide whether it is an ES module or a CommonJS file.
  • For an ES module, the runtime also finds and loads every file it imports before running any of them. That is covered in the modules part below.

A CommonJS file gets a small surprise first: Node.js wraps your whole file in a function. That is why require, module and __dirname exist without being declared, and why a top level return works in a .cjs file but not in a .mjs one.

The invisible wrapper around a CommonJS file · ▶ Runs
// Node.js wraps every CommonJS file in a function before the engine sees it.
// That is where require, module, exports, __filename and __dirname come from.
const { wrapper } = require("node:module");
console.log(wrapper[0] + "...your file..." + wrapper[1]);

console.log(typeof require, typeof module, typeof exports);
console.log(__filename.endsWith("main.cjs"));
console.log("arguments of the wrapper:", arguments.length);
Output

});

Big websites ship one or a few bundled files instead of hundreds of small ones. Bundlers such as Vite, esbuild and webpack join and shrink the files so the loading step takes fewer network trips.

🔤Step 2: the scanner cuts text into tokens

The first thing the engine does with the text is scanning (also called lexing or tokenising). It reads the characters from left to right and groups them into tokens, the smallest pieces that mean something.

Token kindExamples from let total = price * 2; // tax
Keywordlet
Identifier (name)total, price
Punctuator (operator)=, *, ;
Literal2, and strings such as "pen"
Thrown awayspaces, line breaks (it remembers where they were) and the comment // tax

Try it yourself below. Type a few lines and press the button. The animation walks your own code through scanning, parsing, the creation phase, bytecode and running, the same five steps this chapter explains one by one.

The scanner always takes the longest token it can. That rule explains some puzzles you may meet in quizzes and code reviews.

What the scanner accepts and rejects · ▶ Runs
import vm from "node:vm";

// vm.Script only scans and parses. Nothing runs unless we ask.
const samples = [
  "1.toString()",        // the scanner reads "1." as one number token, then sees a name
  "1..toString()",       // "1." is the number, ".toString" is the property
  "1 .toString()",       // the space ends the number token
  "let total = 1_000_000",
  "let 2fast = 1",       // a name may not start with a digit
  "let price = 10 // a comment is thrown away",
];
for (const src of samples) {
  try {
    new vm.Script(src);
    console.log("ok       ", src.padEnd(24), "->", vm.runInNewContext(src));
  } catch (e) {
    console.log("rejected ", src.padEnd(24), "->", e.name + ":", e.message);
  }
}
Output
rejected  1.toString()             -> SyntaxError: Invalid or unexpected token
ok        1..toString()            -> 1
ok        1 .toString()            -> 1
ok        let total = 1_000_000    -> undefined
rejected  let 2fast = 1            -> SyntaxError: Invalid or unexpected token
ok        let price = 10 // a comment is thrown away -> undefined
Line breaks matter to the scanner because of automatic semicolon insertion. If a line ends where a statement could end, a semicolon is added. That is why return on its own line followed by an object returns undefined (chapter 1 shows it).
Part 4

🌳Step 3: the parser builds a syntax tree

🧪 QA essentialA single syntax error makes a whole spec file report zero tests, and knowing early errors helps you read the message fast.

The parser reads the tokens and checks them against the grammar of JavaScript. If they fit, it builds an abstract syntax tree (AST): a tree of nodes such as VariableDeclaration, BinaryExpression and CallExpression. The tree keeps the meaning and drops the noise. In price * qty + 40 the multiply sits lower in the tree than the add, so it is worked out first.

If the tokens do not fit the grammar, the parser throws a SyntaxError and the whole file is rejected. Not even line 1 runs.

One typo on line 4 stops line 1 too · 💥 Throws
console.log("line 1: this never prints");
const user = { name: "Asha" };
console.log("line 3: neither does this");
if (user.name === "Asha" {
  console.log("hello");
}
Output
main.mjs:4

Node.js v26.12.1

Some mistakes are grammatically fine but forbidden anyway. The specification calls them early errors, and the parser reports them before anything runs too: declaring the same let twice, a const with no value, or a return outside a function. Other problems, such as calling a function that does not exist, can only be found when the line actually runs.

Early errors against runtime errors · ▶ Runs
import vm from "node:vm";

// Early errors: the parser finds these before running anything
const early = [
  "let a = 1; let a = 2;",
  "const limit;",
  "return 5",
  "function f() { 'use strict'; with (Math) {} }",
];
for (const src of early) {
  try { new vm.Script(src); console.log("parsed  ", src); }
  catch (e) { console.log("early   ", src.padEnd(42), e.message); }
}

// Errors that only appear when the line runs
const late = new vm.Script("console.log('before'); missingFn(); console.log('after');");
try { late.runInNewContext({ console }); }
catch (e) { console.log("runtime ", e.name + ":", e.message); }
Output

Lazy parsing

Parsing a big web app fully at start up would be slow, so V8 pre-parses functions it has not needed yet. It only checks their grammar and remembers where they are. The full parse happens the first time the function is called. Functions wrapped in brackets, such as (function () { ... })(), are parsed fully at once because V8 guesses they run immediately.

A spec file with one missing bracket fails with a SyntaxError and zero tests run, so the report may show "0 tests" instead of a red test. Run node --check file.js or your linter in CI to catch it before the test run starts.
Part 5

🏗️Step 4: scopes and the creation phase

Before a script or a function runs, the engine sets up an execution context for it. This happens in two phases.

  1. Creation phase. The engine creates the scope and a slot for every name declared in it. Function declarations are created whole. var names start as undefined. let, const and class names exist but are uninitialised: reading them throws, which is called the temporal dead zone (TDZ). The value of this is decided here too.
  2. Execution phase. The code runs line by line, giving variables their values and calling functions. Each function call repeats both phases for that function.
The creation phase, then the execution phase · ▶ Runs
console.log(total, typeof applyTax);            // the names already exist
var total = 100;
let rate = 0.18;
function applyTax(t) { return t + t * rate; }
console.log(applyTax(total));

try {
  console.log(gst);                            // let is in the temporal dead zone here
  let gst = 5;
} catch (e) {
  console.log(e.name + ":", e.message);
}

// Every call makes a new execution context with its own variables
function greet(name) { const msg = `Hello ${name}`; return msg; }
console.log(greet("Ravi"), greet("Meena"), typeof msg);
Output

118
ReferenceError: Cannot access 'gst' before initialization
Hello Ravi Hello Meena undefined

Nothing is physically moved to the top of your file. "Hoisting" is simply the result of the creation phase: the names exist before their line runs. Chapter 14 goes further into scope chains, closures and the rules of this.

⚙️Step 5: Ignition turns the tree into bytecode

V8 does not run the tree directly. Its interpreter, Ignition, first turns the tree into bytecode: a list of small, simple instructions. Bytecode is much smaller than machine code, so it starts fast and saves memory on phones.

Ignition is a register machine with one special register, the accumulator. Most instructions read or write it. You can ask Node.js to print the real bytecode of a function with a V8 flag:

The real bytecode V8 makes for one function · ▶ Runs
function addTax(price, rate) {
  const tax = price * rate;
  return price + tax;
}
console.log(addTax(100, 0.18));

The feedback slots are the important part. Every time the line runs, Ignition notes what it saw: "always small whole numbers" or "a number and a string". The optimising compilers in step 7 read these notes. The engine animation above uses the same instruction names, so you can watch the accumulator change for your own code.

The exact bytecode changes between V8 versions, and the flag is a debugging tool, not something to use in production. The numbers on the left are positions in the source text, which is how a stack trace knows your line and column.
Part 7

📚Step 6: running: the call stack, the heap and garbage collection

🧪 QA essentialReference copies explain test data that changes between tests, and reachability explains memory leaks in long test runs.

While the bytecode runs, the engine uses two areas of memory.

  • The call stack holds one frame for every function that has started and not yet returned: its arguments, its local variables and where to go back to. It is small and very fast. Too many nested calls give RangeError: Maximum call stack size exceeded.
  • The heap holds objects, arrays, functions and long strings. Variables keep a reference (an address) to them. Copying the variable copies the reference, so two names can share one object.
Values on the stack, objects on the heap · ▶ Runs
function makeOrder(id) {
  const items = ["pen"];
  return { id, items };
}
let qty = 2;
let copyQty = qty;           // a number is copied
copyQty = 5;

const order = makeOrder(7);
const copy = order;          // an object is shared: both names point at one heap object
copy.id = 8;
console.log(order.id, qty, copyQty, order === copy);

// The call stack has a limit. The heap is much larger.
function depth(n) { try { return depth(n + 1); } catch { return n; } }
console.log("stack frames before overflow > 5000:", depth(0) > 5000);
Output
8 2 5 true
stack frames before overflow > 5000: true

Garbage collection

You never free memory yourself. The garbage collector keeps every object that can be reached from the roots (global variables and the variables on the stack) and frees the rest. V8's collector is called Orinoco. New objects start in a small young area that is cleaned very often, because most objects are thrown away quickly, like the temporary arrays a map creates. Objects that survive move to the old area, which is cleaned less often with mark and sweep. Most of the work happens on helper threads, so pauses stay short.

Unreachable objects are collected · ▶ Runs
// Run with --expose-gc so the example can ask V8 to collect garbage now.
let cart = { items: new Array(100_000).fill("item") };
const watch = new WeakRef(cart);            // a weak reference does not keep the object alive

await new Promise(r => setTimeout(r, 0));  // let the current job finish first
console.log("still reachable:", watch.deref() !== undefined);

cart = null;                               // the last strong reference is gone
await new Promise(r => setTimeout(r, 0));
gc();
console.log("after gc:", watch.deref());
Terminal
$ node --expose-gc main.mjs
Output
still reachable: true
after gc: undefined
A memory leak in JavaScript means something still reaches an object you no longer need: a global array that keeps growing, a listener that was never removed, or a cache with no limit. In long UI test runs, watch the memory graph in Chrome DevTools or compare two heap snapshots (chapter 31).

🚀Step 7: hot code gets compiled: Sparkplug, Maglev and TurboFan

Interpreting bytecode is quick to start but slower to run. So V8 watches which functions run often and compiles them to machine code while the program is running. This is just in time (JIT) compilation, and V8 has three compilers for it, each one slower to compile but producing faster code.

TierUsed forHow it works
IgnitionEverything, at firstInterprets bytecode and collects type feedback
SparkplugFunctions that are warmTurns bytecode into machine code almost one to one, no optimisation
MaglevFunctions that are hotUses the feedback to make good machine code quickly
TurboFanThe hottest code, such as tight loopsUses the feedback to make the fastest code, and takes the longest to compile

Optimised code is built on guesses. If lineTotal has only ever seen small whole numbers, the fast code handles only small whole numbers. When a string arrives, the guess is wrong, so V8 deoptimises: it throws the fast code away, continues in the bytecode and may optimise again later with the new knowledge. This run is real. Watch the V8 messages between the program's own lines:

Watch V8 optimise and deoptimise a hot function (trace lines shortened) · ▶ Runs
// A function the checkout page calls for every cart line
function lineTotal(price, qty) {
  return price * qty;
}

let sum = 0;
for (let i = 0; i < 100_000; i++) sum += lineTotal(i % 50, 2);   // always numbers: the function gets hot
console.log("sum of numbers:", sum);

console.log("a string sneaks in:", lineTotal("12", 2));        // the guess "price is a small integer" breaks
for (let i = 0; i < 100_000; i++) sum += lineTotal(i % 50, 2);
console.log("done");

How to read the trace: "hot and stable" means the function ran often and its type feedback stopped changing. Notice that the program still printed the right answers. Deoptimisation only costs speed, never correctness. In daily work this matters for code that runs millions of times, such as parsing a large log file or drawing a chart, and it is the reason for a simple habit: keep the types going into a hot function the same.

Firefox and Safari use the same idea with different names. SpiderMonkey has a baseline interpreter, a baseline compiler and the Warp optimiser. JavaScriptCore has LLInt, Baseline, DFG and FTL.
Part 9

🔄Step 8: the runtime, Web APIs and the event loop

🧪 QA essentialThe event loop explains missing await bugs, log orders and why fixed sleeps make tests slow and flaky.

The engine runs one piece of code at a time on one thread. So how does a page wait for a server without freezing? It does not wait. A call such as setTimeout or fetch hands the waiting to the runtime, which does it outside JavaScript (the browser's timers and network code, or libuv in Node.js). When the waiting is over, the runtime puts a callback into a queue.

  1. The call stack runs the current job until it is empty.
  2. Then the microtask queue is emptied completely: promise callbacks, await continuations and queueMicrotask.
  3. Then the event loop takes one task from the task queue: a timer, a click, a network response. Then back to step 2.
  4. Between tasks, the browser may repaint the screen, roughly every 16 ms on a 60 Hz display.

Write your own lines in the simulator and predict the console before you press Play.

Node.js follows the same idea and splits the task side into phases (timers, poll for I/O, check for setImmediate), which chapter 14 shows. Promises and async code get a full chapter in chapter 11.

This order is why a test that forgets an await can finish and report "passed" before the check inside a .then has even run. It is also why Playwright's auto waiting works: it keeps giving the page turns of the event loop until the element is ready.
Part 10

📦Modules: load, link, then evaluate

An ES module is not run the moment it is read. The runtime and the engine go through three phases for the whole graph of files.

  1. Construction: find, download and parse the entry file, read its import lines, then do the same for every imported file. No code runs yet.
  2. Linking: connect every import to the matching export. A misspelled export name fails here, before any code runs.
  3. Evaluation: run each module body once, dependencies first. A module imported by many files still runs only once.
Modules: linked first, then evaluated in order · ▶ Runs
📄 logger.mjs
console.log("logger.mjs runs first, it is a dependency");
📄 price.mjs
import "./logger.mjs";                 // already loaded, so it does not run twice
console.log("price.mjs runs second");
export let price = 100;
export function bump() { price += 10; }
📄 main.mjs
console.log("main.mjs body runs last");
import { price, bump } from "./price.mjs";
import "./logger.mjs";

console.log("price is", price);
bump();
console.log("price after bump is", price);   // a live binding, not a copy
Terminal
$ node main.mjs
Output
logger.mjs runs first, it is a dependency
price.mjs runs second
main.mjs body runs last
price is 100
price after bump is 110

Two things in that output surprise people. The console.log at the top of main.mjs ran last, because imports are processed before the body. And price changed after bump(), because an import is a live binding to the exporting module's variable, not a copy of its value. CommonJS require works differently: it runs the file when the line is reached and returns a copy of module.exports.

Top level await fits into the evaluation phase: a module that awaits pauses its own evaluation and the modules that depend on it, while other branches of the graph carry on.
Part 11

🎬Real world scenario: a frozen page on sale day

🧪 QA essentialLong tasks are a common cause of slow, flaky UI tests and of performance bugs that testers report.
The situationDuring a big sale, users report that the "Apply coupon" button does nothing for half a second after the cart loads. The code has no errors. A tester records the problem and a developer measures it.

The cart runs a long synchronous calculation over every item. While it runs, the call stack is never empty, so the event loop cannot run click handlers, timers or painting. The code below measures this with a timer that should fire after 50 ms.

A frozen page on sale day, and the fix · ▶ Runs
// Sale day: the "Apply coupon" button stops responding for a moment.
// A ticker that should fire every 50 ms shows how long the thread was busy.
function heavyWork(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {}             // one long synchronous job
}

function measure(label, work) {
  return new Promise(resolve => {
    const start = Date.now();
    setTimeout(() => {
      const late = Date.now() - start - 50;
      console.log(label.padEnd(24), "timer was late by more than 200 ms:", late > 200);
      resolve();
    }, 50);
    work();
  });
}

await measure("blocking 400 ms", () => heavyWork(400));

// The fix: split the work into small chunks and give the event loop a turn between them
async function chunked(total, chunk) {
  for (let done = 0; done < total; done += chunk) {
    heavyWork(chunk);
    await new Promise(r => setTimeout(r, 0));   // let timers, clicks and painting run
  }
}
await measure("chunked 20 x 20 ms", () => { chunked(400, 20); });
Output
blocking 400 ms          timer was late by more than 200 ms: true
chunked 20 x 20 ms       timer was late by more than 200 ms: false

The fix does the same total work in small chunks and gives the event loop a turn between them. Clicks and paints now get in between the chunks, so the page feels responsive. In a browser, the newer scheduler.yield() does the same job in Chrome and Edge, and very heavy work can move to a Web Worker on another thread (chapter 31).

Lighthouse and the Performance panel in DevTools mark any task over 50 ms as a long task, and the Interaction to Next Paint (INP) metric shows how long users waited after a tap. Both are good evidence to attach to a bug report about a slow page.
