Part 1

🔄One thread and the event loop

JavaScript runs your code on one thread: one line at a time. Slow work such as a network request, a timer or reading a file is handed to the browser or Node.js, and your code keeps going. When the slow work finishes, a callback is queued. The event loop runs queued callbacks only when the call stack is empty.

Which line prints first · ▶ Runs
console.log("1 start");
setTimeout(() => console.log("5 timeout"), 0);
Promise.resolve().then(() => console.log("3 promise"));
queueMicrotask(() => console.log("4 microtask"));
console.log("2 end");
Output
1 start
2 end
3 promise
4 microtask
5 timeout

Now try your own code. The simulator below accepts console.log, setTimeout, queueMicrotask and Promise.resolve().then, including callbacks inside callbacks. Predict the console first, then press Play.

QueueWhat goes thereWhen it runs

Tasks (macrotasks)setTimeout, setInterval, clicks, network and file eventsone per turn of the loop, after the microtasks are empty

Because there is only one thread, a long loop blocks everything: timers, clicks and screen updates all wait.

One thread: a busy loop delays everything · ▶ Runs
const started = Date.now();
setTimeout(() => console.log(`timer fired after ${Math.round((Date.now() - started) / 100) * 100} ms`), 100);

// A long loop keeps the only thread busy. Nothing else can run meanwhile.
const until = Date.now() + 500;
while (Date.now() < until) {}
console.log("busy loop done");
Output

Part 2

📞Callbacks

The first way to handle async work was to pass a function to call later. Node.js callbacks receive the error first and the result second. It works, but each step that depends on the previous one adds a level of nesting, known as callback hell, and error handling must be repeated at every level.

Callbacks and the pyramid they build · ▶ Runs
import { readFile } from "node:fs";

// Node.js style: the callback receives (error, result)
readFile("missing.json", "utf8", (err, text) => {
  if (err) return console.log("callback got an error:", err.code);
  console.log(text);
});

// Callbacks inside callbacks get deep quickly
function step(name, done) { setTimeout(() => done(null, name), 10); }
step("login", (e1, a) => {
  step("search", (e2, b) => {
    step("checkout", (e3, c) => {
      console.log("finished:", a, b, c);
    });
  });
});
Output
callback got an error: ENOENT
finished: login search checkout
Most Node.js APIs now have promise versions: import { readFile } from "node:fs/promises". For an old callback API, util.promisify(fn) creates one.
Part 3

🤝Promises

🧪 QA essentialEvery Playwright, WebdriverIO and Selenium call returns a promise, so you need to know what one is.

A promise is an object that stands for a result that is not ready yet. It starts pending, then becomes fulfilled with a value or rejected with an error, and never changes again. then runs when it fulfils, catch when it rejects and finally either way. Returning a value or a promise from then passes it to the next step, so the steps form a flat chain.

Creating and chaining promises · ▶ Runs
function wait(ms, value, fail = false) {
  return new Promise((resolve, reject) => {
    setTimeout(() => (fail ? reject(new Error(`${value} failed`)) : resolve(value)), ms);
  });
}

const p = wait(20, "token-123");
console.log(p);                              // still pending

p.then(token => {
  console.log("got", token);
  return wait(10, `profile for ${token}`);    // returning a promise chains it
})
  .then(profile => console.log(profile))
  .then(() => wait(10, "orders", true))
  .catch(err => console.log("caught:", err.message))   // one catch for the whole chain
  .finally(() => console.log("cleanup runs either way"));
Output
Promise { <pending> }
got token-123
profile for token-123
caught: orders failed
cleanup runs either way

Follow one real chain below. Each then creates a new promise, which is why returning a value passes it on, returning a promise makes the chain wait for it, and one catch at the end handles a failure in any earlier step.

Promise.withResolvers for event driven code · ▶ Runs
// ES2024: create a promise and get its resolve and reject functions outside it
const { promise, resolve } = Promise.withResolvers();

const events = [];
function onMessage(msg) {
  events.push(msg);
  if (msg === "order-confirmed") resolve(events.length);
}

setTimeout(() => onMessage("cart-updated"), 5);
setTimeout(() => onMessage("payment-ok"), 10);
setTimeout(() => onMessage("order-confirmed"), 15);

console.log("confirmed after", await promise, "events");
Output
confirmed after 3 events
A rejected promise that nobody catches is an unhandled rejection. In Node.js it crashes the process, and in test runners it often shows up as a confusing failure in a different test.
Part 4

⏸️async and await

🧪 QA essentialPlaywrightSeleniumWebdriverIOJestCypressA missing await is the number one cause of flaky and falsely passing automated tests.

async before a function makes it return a promise. Inside it, await pauses that function until a promise settles and gives you its value, while the rest of the program keeps running. Errors become normal exceptions you catch with try and catch.

async and await · ▶ Runs
const wait = (ms, v) => new Promise(r => setTimeout(() => r(v), ms));

async function login(user) {
  await wait(10);
  if (user === "blocked") throw new Error("account locked");
  return { user, token: "t-" + user };
}

async function main() {
  const session = await login("asha");      // reads like normal code
  console.log(session);
  try {
    await login("blocked");
  } catch (e) {
    console.log("caught:", e.message);
  }
  return "done";
}

const result = main();
console.log(result instanceof Promise);     // an async function always returns a promise
console.log(await result);
Output
true
{ user: 'asha', token: 't-asha' }
caught: account locked
done

Sequential or parallel

Two await lines one after another run one after another. When the steps do not depend on each other, start both and wait for both with Promise.all.

Sequential or parallel · ▶ Runs
const wait = (ms, v) => new Promise(r => setTimeout(() => r(v), ms));
const t = () => Math.round((performance.now() - start) / 100) * 100;
let start = performance.now();

const a = await wait(300, "users");
const b = await wait(300, "orders");
console.log("one after another:", t(), "ms", a, b);

start = performance.now();
const [c, d] = await Promise.all([wait(300, "users"), wait(300, "orders")]);
console.log("at the same time:", t(), "ms", c, d);
Output
one after another: 600 ms users orders
at the same time: 300 ms users orders

The most common bug in test code

Forgetting await lets the test finish before the check runs. The test is reported as passed even though the server returned an error. The Node.js runner at least prints a warning about activity after the test ended. Many other runners print nothing at all.

🧮Running many promises: all, allSettled, race, any

🧪 QA essentialPlaywrightJestClicking and waiting for a response together, checking many endpoints, and timeouts all use these helpers.

Four helpers combine several promises into one. They differ in what counts as done and what happens on a failure.

all, allSettled, race and any · ▶ Runs
const ok = (ms, v) => new Promise(r => setTimeout(() => r(v), ms));
const bad = (ms, msg) => new Promise((_, j) => setTimeout(() => j(new Error(msg)), ms));

try {
  await Promise.all([ok(10, "a"), bad(20, "b broke"), ok(30, "c")]);
} catch (e) {
  console.log("all: rejects on the first failure ->", e.message);
}

const settled = await Promise.allSettled([ok(10, "a"), bad(20, "b broke")]);
console.log("allSettled:", settled.map(r => r.status === "fulfilled" ? r.value : r.reason.message));

console.log("race:", await Promise.race([ok(30, "slow"), ok(10, "fast")]));

console.log("any:", await Promise.any([bad(5, "mirror 1 down"), ok(20, "mirror 2"), ok(30, "mirror 3")]));
try {
  await Promise.any([bad(5, "x"), bad(10, "y")]);
} catch (e) {
  console.log("any, all failed:", e.constructor.name, e.errors.map(x => x.message));
}
Output
all: rejects on the first failure -> b broke
allSettled: [ 'a', 'b broke' ]
race: fast
any: mirror 2
any, all failed: AggregateError [ 'x', 'y' ]

The timeline below runs the four helpers on the same three promises, so you can see the exact moment each one decides. Notice that the requests themselves keep running: Promise.all stops waiting, it does not cancel anything. Use an AbortController to really cancel requests.

Cancelling

An AbortController gives you a signal to pass to fetch and other APIs, and an abort() method to stop them. AbortSignal.timeout(ms) aborts by itself, and AbortSignal.any combines signals.

Cancelling with AbortController · ▶ Runs
async function slowRequest(signal) {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => resolve("response"), 500);
    signal.addEventListener("abort", () => {
      clearTimeout(timer);
      reject(signal.reason);
    }, { once: true });
  });
}

// Cancel by hand
const controller = new AbortController();
setTimeout(() => controller.abort(new Error("user left the page")), 50);
await slowRequest(controller.signal).catch(e => console.log("aborted:", e.message));

// Cancel on a timeout
await slowRequest(AbortSignal.timeout(100)).catch(e => console.log("timed out:", e.name));

// Whichever comes first
const either = AbortSignal.any([AbortSignal.timeout(80), new AbortController().signal]);
await slowRequest(either).catch(e => console.log("any:", e.name));
Output
aborted: user left the page
timed out: TimeoutError
any: TimeoutError

⏱️Retries, polling and waiting the right way

🧪 QA essentialPlaywrightCypressSeleniumWebdriverIOWaiting correctly is the difference between a stable suite and a flaky one.

Tests and scripts often wait for something that happens at an unknown time: an element appears, a job finishes, a service recovers. A fixed sleep guesses the time. It wastes time when the guess is too long and fails when it is too short. Polling checks again and again until the condition is true or a timeout is reached.

Poll until a condition is true · ▶ Runs
const sleep = ms => new Promise(r => setTimeout(r, ms));

// Keep checking until the condition is true, or give up after timeout
async function waitFor(check, { timeout = 1000, interval = 50, message = "condition" } = {}) {
  const deadline = Date.now() + timeout;
  let lastError;
  while (Date.now() < deadline) {
    try {
      const value = await check();
      if (value) return value;
    } catch (e) {
      lastError = e;
    }
    await sleep(interval);
  }
  throw new Error(`Timed out after ${timeout} ms waiting for ${message}` + (lastError ? `: ${lastError.message}` : ""));
}

// A report that becomes ready after about 200 ms
const readyAt = Date.now() + 200;
const getReport = async () => (Date.now() >= readyAt ? { status: "ready", rows: 42 } : { status: "processing" });

const report = await waitFor(async () => {
  const r = await getReport();
  return r.status === "ready" && r;
}, { message: "the report" });
console.log(report);

await waitFor(() => false, { timeout: 150, message: "a button that never appears" }).catch(e => console.log(e.message));
Output
{ status: 'ready', rows: 42 }
Timed out after 150 ms waiting for a button that never appears

A retry with exponential backoff repeats a failing call with longer and longer pauses, which gives a struggling server room to recover.

Retry with exponential backoff · ▶ Runs
const sleep = ms => new Promise(r => setTimeout(r, ms));

async function retry(fn, { attempts = 4, baseMs = 20 } = {}) {
  for (let i = 1; ; i++) {
    try {
      return await fn(i);
    } catch (e) {
      if (i === attempts) throw e;
      const delay = baseMs * 2 ** (i - 1);            // 20, 40, 80 ...
      console.log(`attempt ${i} failed (${e.message}), waiting ${delay} ms`);
      await sleep(delay);
    }
  }
}

let calls = 0;
const flakyService = async () => {
  calls++;
  if (calls < 3) throw new Error("503 Service Unavailable");
  return { status: 200 };
};
console.log(await retry(flakyService));
Output
attempt 1 failed (503 Service Unavailable), waiting 20 ms
attempt 2 failed (503 Service Unavailable), waiting 40 ms
{ status: 200 }

Modern tools build this in, so you rarely write the loop yourself.

Waiting the right way in Playwright · Runs for real in chapter 22
// Playwright waits for you: actions wait for the element to be visible, enabled and stable
await page.getByRole("button", { name: "Pay" }).click();

// Web first assertions keep retrying until they pass or time out
await expect(page.getByText("Payment received")).toBeVisible({ timeout: 10_000 });

// Poll anything, such as an API, with expect.poll
await expect.poll(async () => {
  const res = await request.get("/api/orders/42");
  return (await res.json()).status;
}, { timeout: 30_000 }).toBe("shipped");

// Wait for a response the page makes
const [response] = await Promise.all([
  page.waitForResponse(r => r.url().includes("/api/cart") && r.ok()),
  page.getByRole("button", { name: "Add to cart" }).click(),
]);

// Avoid: a fixed sleep is either too long or too short
await page.waitForTimeout(3000);
Retrying a whole test hides flakiness. Use retries for setup calls to unstable services and report retried tests as flaky, but fix the cause: a missing wait for a response, a fixed sleep, or shared test data.
Part 7

🎬Real world scenario: a link checker

🧪 QA essential
The situationBefore a release you must check that 8 product pages respond. The server must not get more than 3 requests at once, a page that takes longer than 200 ms counts as broken, and the report must list every page, not stop at the first problem.
A link checker with a concurrency limit and timeouts · ▶ Runs
// Check 8 product URLs, at most 3 requests at a time, with a timeout on each.
const sleep = ms => new Promise(r => setTimeout(r, ms));
const latency = { "/p/1": 30, "/p/2": 50, "/p/3": 400, "/p/4": 20, "/p/5": 40, "/p/6": 30, "/p/7": 25, "/p/8": 35 };
let active = 0, peak = 0;

async function fakeFetch(url, { signal }) {
  active++; peak = Math.max(peak, active);
  try {
    await new Promise((resolve, reject) => {
      const t = setTimeout(resolve, latency[url]);
      signal.addEventListener("abort", () => { clearTimeout(t); reject(signal.reason); });
    });
    return { url, status: url === "/p/5" ? 404 : 200 };
  } finally {
    active--;
  }
}

async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i]);
    }
  }
  await Promise.all(Array.from({ length: limit }, worker));
  return results;
}

const urls = Object.keys(latency);
const results = await mapLimit(urls, 3, url =>
  fakeFetch(url, { signal: AbortSignal.timeout(200) })
    .then(r => ({ url, ok: r.status === 200, status: r.status }))
    .catch(e => ({ url, ok: false, status: e.name })));

console.table(results);
console.log("peak parallel requests:", peak);
console.log("broken:", results.filter(r => !r.ok).map(r => `${r.url} (${r.status})`).join(", "));
Output
┌─────────┬────────┬───────┬────────────────┐
│ (index) │ url    │ ok    │ status         │
├─────────┼────────┼───────┼────────────────┤
│ 0       │ '/p/1' │ true  │ 200            │
│ 1       │ '/p/2' │ true  │ 200            │

mapLimit starts 3 workers that take the next URL as soon as they are free. AbortSignal.timeout stops slow requests, and catching each error turns it into a row in the report instead of stopping the run.
