Part 1

⚙️How the regex engine matches

JavaScript uses a backtracking engine. It tries the pattern at the first position of the text and, when a step fails, goes back to the last choice it made and tries another. If nothing works, it moves one character on and starts again. Quantifiers are greedy by default: they take as much as they can, then give back. Add ? to make them lazy.

Greedy, lazy and how the engine searches · ▶ Runs
const html = '<b>Sale</b> and <b>New</b>';

console.log(html.match(/<b>.*<\/b>/)[0]);       // greedy: as much as possible
console.log(html.match(/<b>.*?<\/b>/)[0]);      // lazy: as little as possible
console.log(html.match(/<b>[^<]*<\/b>/g));      // a negated class is often clearer and faster

// The engine tries every start position, and backtracks inside each one
const re = /a.*c/;
console.log(re.exec("xxabcbc"), "| found at index", re.exec("xxabcbc").index);
Output
<b>Sale</b> and <b>New</b>
<b>Sale</b>
[ '<b>Sale</b>', '<b>New</b>' ]
[ 'abcbc', index: 2, input: 'xxabcbc', groups: undefined ] | found at index 2

The animation shows the same text matched twice. Each "give back one character" is a backtracking step. On a short string that costs nothing, but nested quantifiers on a long string can need millions of them, which is the ReDoS problem later in this chapter.

When you can say exactly what is allowed, a negated class such as [^<]* or [^"]* is clearer and much faster than .*?, because the engine never needs to backtrack.
Part 2

👀Lookarounds and backreferences

🧪 QA essentialPassword rules, price extraction and duplicate word checks in content are everyday test tasks.

A lookaround checks what comes before or after a position without including it in the match. (?=x) and (?!x) look ahead, (?<=x) and (?<!x) look behind. A backreference such as \1 or \k<name> matches the same text a group already matched.

Lookahead, lookbehind and backreferences · ▶ Runs
const prices = "Pen ₹40, Book ₹250, Bag $30, Mug ₹120";

console.log(prices.match(/(?<=₹)\d+/g));             // lookbehind: digits after ₹, without the ₹
console.log(prices.match(/\b\w+(?= ₹)/g));          // lookahead: words followed by " ₹"
console.log(prices.match(/(?<!₹)\b\d+/g));          // negative lookbehind: numbers not in rupees

// Password rules as lookaheads: each (?=...) checks a rule without moving forward
const strong = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^\w\s]).{8,}$/;
for (const pw of ["Secret1!", "secret1!", "Sec1!", "Secret12"]) console.log(pw.padEnd(9), strong.test(pw));

// Backreferences: \1 matches the same text the first group matched
console.log("the the test passed passed".match(/\b(\w+) \1\b/g));
console.log('<a href="x">'.match(/(["']).*?\1/)[0]);
Output
[ '40', '250', '120' ]
[ 'Pen', 'Book', 'Mug' ]
[ '30' ]
Secret1!  true
secret1!  false
Sec1!     false
Secret12  false
[ 'the the', 'passed passed' ]
"x"
Several lookaheads in a row are the standard way to express "must contain a lower case letter, a capital, a digit and a symbol". Each rule becomes a separate test case in your password suite.
Part 3

🚩Flags in depth and the lastIndex trap

🧪 QA essentialA shared /g regex in a test helper makes checks pass and fail in turn, a confusing source of flaky tests.

Flags change how the whole pattern works. The g and y flags also make a regex stateful: it remembers lastIndex, the position after the last match.

Flags in depth: g, m, s, y and the lastIndex trap · ▶ Runs
const log = `INFO  start
ERROR db timeout
info  retry
ERROR card declined`;

console.log(log.match(/^ERROR.*$/gm));                // m: ^ and $ work per line
console.log(log.match(/^info.*$/gim).length);          // i: ignore case
console.log(/start.ERROR/.test(log), /start.ERROR/s.test(log));   // s: dot matches a new line

// g with test() remembers lastIndex between calls, a classic bug
const hasError = /ERROR/g;
console.log(hasError.test(log), hasError.test(log), hasError.test(log), "| lastIndex", hasError.lastIndex);

// y (sticky) only matches exactly at lastIndex, which is how tokenisers work
const word = /\w+/y;
word.lastIndex = 6;
console.log(word.exec(log)?.[0], (word.lastIndex = 5, word.exec(log)));
Output
[ 'ERROR db timeout', 'ERROR card declined' ]
2
false true
true true false | lastIndex 0
start null
Never reuse a regex with the g flag for test() across different strings or calls. The second call starts at the old lastIndex and can fail on text that clearly matches. Drop the g flag for yes or no checks.

🌍Unicode and every language

🧪 QA essentialInternationalisation testing catches validation that only works for English input.

[a-z] only knows English. With the u or v flag, \p{L} matches a letter in any script, \p{Script=Devanagari} one script, and \p{Emoji} emoji. The u flag also treats an emoji as one character instead of two halves.

Unicode: letters in every language · ▶ Runs
const names = ["Zoë", "Ravi", "José", "Łukasz", "東京", "😀 smile"];

console.log(names.filter(n => /^[a-z]+$/i.test(n)));          // ASCII only: drops real names
console.log(names.filter(n => /^\p{L}+$/u.test(n)));         // any letter in any script
console.log("😀".length, [..."😀"].length, /^.$/.test("😀"), /^.$/u.test("😀"));
console.log("Grüße, Привет, नमस्ते".match(/\p{Script=Devanagari}+/u)[0]);
console.log("café".normalize("NFD").replace(/\p{M}/gu, ""));  // strip accents
Output
[ 'Ravi' ]
[ 'Zoë', 'Ravi', 'José', 'Łukasz', '東京' ]
2 1 false true
नमस्ते
cafe
Test name and address fields with names such as Zoë, José, Łukasz, 東京 and right to left Arabic. A form that rejects real names is a bug that hits real customers.

✂️Replacing, masking and splitting

🧪 QA essentialMasking passwords, card numbers and tokens before logs and reports are saved is a security requirement in test frameworks.

replace and replaceAll can use $1, $<name> and $& in the replacement text, or a function that receives every group and returns the new text.

Replacing with groups and functions, masking secrets · ▶ Runs
// Replace with named groups and with a function
const iso = "Shipped 2026-10-18, due 2026-10-25";
console.log(iso.replace(/(?<y>\d{4})-(?<m>\d\d)-(?<d>\d\d)/g, "$<d>/$<m>/$<y>"));

const cart = "PEN x2 @40, BOOK x1 @250";
console.log(cart.replace(/(\w+) x(\d+) @(\d+)/g, (all, sku, qty, price) => `${sku}=${qty * price}`));

// Mask secrets in logs before they are saved
const line = 'POST /login {"user":"asha","password":"s3cret","card":"4111111111111111"} token=eyJhbGciOi.abc.def';
const masked = line
  .replace(/("password":")[^"]*/, "$1***")
  .replace(/\b(\d{4})\d{8}(\d{4})\b/, "$1********$2")
  .replace(/token=[\w.-]+/, "token=[hidden]");
console.log(masked);

// split keeps captured separators
console.log("a1b22c333".split(/(\d+)/));
Output
Shipped 18/10/2026, due 25/10/2026
PEN=80, BOOK=250
POST /login {"user":"asha","password":"***","card":"4111********1111"} token=[hidden]
[
  'a',  '1', 'b',
  '22', 'c', '333',
  ''

For anything with structure, such as a whole language of filters, use the sticky flag to read one token at a time from an exact position.

Sticky regexes as a tokeniser · ▶ Runs
// A tiny tokeniser for filter expressions such as: status == "failed" && ms > 1000
const rules = [
  ["space", /\s+/y], ["string", /"(?:[^"\\]|\\.)*"/y], ["number", /\d+(?:\.\d+)?/y],
  ["op", /==|!=|>=|<=|&&|\|\||[<>!]/y], ["name", /[A-Za-z_]\w*/y], ["paren", /[()]/y],
];

function tokenize(src) {
  const out = [];
  let pos = 0;
  outer: while (pos < src.length) {
    for (const [type, re] of rules) {
      re.lastIndex = pos;
      const m = re.exec(src);
      if (m) {
        if (type !== "space") out.push(`${type}:${m[0]}`);
        pos = re.lastIndex;
        continue outer;
      }
    }
    throw new SyntaxError(`Unexpected "${src[pos]}" at ${pos}`);
  }
  return out;
}
console.log(tokenize('status == "failed" && ms > 1000'));
try { tokenize("ms # 2"); } catch (e) { console.log(e.message); }
Output
[
  'name:status',
  'op:==',
  'string:"failed"',
  'op:&&',
  'name:ms',
  'op:>',
  'number:1000'
]
Unexpected "#" at 3

💣ReDoS and safe patterns

🧪 QA essentialSending long crafted strings to search and validation fields is a standard security and performance test.

Some patterns make the engine try an exponential number of ways to split the input. ^(a+)+$ on a long run of "a" that ends with "!" never finishes in practice. An attacker who can send such input to a server can freeze it with one request. This is called regular expression denial of service.

ReDoS: a pattern that takes forever · ▶ Runs
// Catastrophic backtracking: nested quantifiers try every way to split the input
const evil = /^(a+)+$/;
const safe = /^a+$/;

function time(re, n) {
  const input = "a".repeat(n) + "!";                  // the ! forces a failure at the end
  const start = performance.now();
  re.test(input);
  return performance.now() - start;
}

time(evil, 5);                                        // warm up, so compiling the regex is not measured
const t22 = time(evil, 22), t26 = time(evil, 26);
console.log("4 more characters made it more than 5 times slower:", t26 / t22 > 5);
console.log("the safe pattern on 100000 characters is instant:", time(safe, 100_000) < 50);
Output
4 more characters made it more than 5 times slower: true
the safe pattern on 100000 characters is instant: true
Danger signs: a quantifier inside a quantified group, such as (a+)+, (\w*)* or (a|aa)+. Safe habits: limit input length first, prefer specific classes, and run the linter rule regexp/no-super-linear-backtracking from eslint-plugin-regexp.

✅Validation patterns and testing them

🧪 QA essentialRegex validation rules are a frequent source of bugs, and table driven tests show exactly which inputs they accept.

A regex can check the shape of text, not its meaning. A date pattern accepts 31 February, and no practical email pattern follows the full standard. Use a regex for the shape, then real code for the rest, such as Temporal.PlainDate.from for dates.

Validation patterns and their limits · ▶ Runs
// Practical patterns. Each one is a trade off, write tests that show the choice.
const patterns = {
  email: /^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/,             // pragmatic, not the full RFC 5322
  isoDate: /^\d{4}-(0[1-9]|1[0-2])-(0[1-9]|[12]\d|3[01])$/, // shape only: 2026-02-31 passes
  uuid: /^[0-9a-f]{8}-[0-9a-f]{4}-[1-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i,
  indianPin: /^[1-9]\d{5}$/,
  semver: /^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)(?:-[\w.-]+)?$/,
};
const samples = {
  email: ["asha@example.com", "a@b", "no spaces@x.io"],
  isoDate: ["2026-10-20", "2026-13-01", "2026-02-31"],
  uuid: [crypto.randomUUID(), "1234"],
  indianPin: ["560001", "056001"],
  semver: ["1.56.1", "1.02.0", "2.0.0-rc.1"],
};
for (const [name, list] of Object.entries(samples))
  console.log(name.padEnd(9), list.map(s => patterns[name].test(s)).join(" "));
Output

uuid      true false

Treat a regex like any other code: keep it in one module and test it with a table of strings that must match and strings that must not.

Test a regex with a table of cases · 🧪 Tests run
📄 src/patterns.js
export const orderId = /^ORD-\d{6}$/;
export const price = /^₹(?:0|[1-9]\d{0,2}(?:,\d{3})*|[1-9]\d*)(?:\.\d{2})?$/;
📄 test/patterns.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { orderId, price } from "../src/patterns.js";

// A table of examples that must match and examples that must not
const cases = {
  orderId: { yes: ["ORD-000001", "ORD-104233"], no: ["ord-104233", "ORD-10423", "ORD-1042333", " ORD-104233"] },
  price: { yes: ["₹0", "₹40", "₹1,250", "₹12,500", "₹99.50"], no: ["₹040", "₹1,25", "₹9.5", "40", "₹-5"] },
};

for (const [name, { yes, no }] of Object.entries(cases)) {
  const re = { orderId, price }[name];
  for (const s of yes) test(`${name} accepts ${JSON.stringify(s)}`, () => assert.match(s, re));
  for (const s of no) test(`${name} rejects ${JSON.stringify(s)}`, () => assert.doesNotMatch(s, re));
}

🎬Real world scenario: mine the access logs

🧪 QA essential
The situationAfter a load test, the team wants every failed request and every slow one from the server access log, with the time of each.
Parse access logs and find the failures · ▶ Runs
// Turn raw access log lines into rows you can check
const logs = `203.0.113.9 - - [20/Oct/2026:09:14:03 +0000] "GET /api/products?page=2 HTTP/1.1" 200 5123 412ms
203.0.113.9 - - [20/Oct/2026:09:14:04 +0000] "POST /api/orders HTTP/1.1" 503 87 2210ms
198.51.100.4 - - [20/Oct/2026:09:14:05 +0000] "GET /health HTTP/1.1" 200 2 3ms
198.51.100.4 - - [20/Oct/2026:09:14:07 +0000] "POST /api/orders HTTP/1.1" 201 312 640ms
garbage line`;

const LINE = /^(?<ip>\S+) \S+ \S+ \[(?<time>[^\]]+)\] "(?<method>[A-Z]+) (?<path>[^ ?"]+)(?:\?[^ "]*)? HTTP\/[\d.]+" (?<status>\d{3}) (?<bytes>\d+) (?<ms>\d+)ms$/;

const rows = [], bad = [];
for (const line of logs.split("\n")) {
  const m = LINE.exec(line);
  if (m) rows.push({ ...m.groups, status: +m.groups.status, ms: +m.groups.ms });
  else bad.push(line);
}
const errors = rows.filter(r => r.status >= 500);
const slow = rows.filter(r => r.ms > 1000 && r.path !== "/health");
console.log(rows.length, "parsed,", bad.length, "rejected:", bad);
console.log("5xx:", errors.map(r => `${r.method} ${r.path} at ${r.time.split(":").slice(1, 4).join(":")}`));
console.log("slow:", slow.map(r => `${r.path} ${r.ms}ms`), "| p50 of orders:", rows.filter(r => r.path === "/api/orders").map(r => r.ms).toSorted((a, b) => a - b)[0], "ms");
Output
4 parsed, 1 rejected: [ 'garbage line' ]
5xx: [ 'POST /api/orders at 09:14:04 +0000' ]
slow: [ '/api/orders 2210ms' ] | p50 of orders: 640 ms

One pattern with named groups turns each line into an object. Lines that do not match are counted instead of silently dropped, which tells you when the log format changes. The same idea works for test runner output, browser console logs and CI logs.
