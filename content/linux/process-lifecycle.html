fork, exec, exit and wait

Every process except the very first is made by another process. Unix splits this into two steps that you can combine freely: fork copies the running process, and execve replaces the program inside a process with a new one.

The life of one command
  1. fork(): the kernel makes a child that is a copy of the parent, with a new PID. fork returns twice: 0 in the child and the child’s PID in the parent. On Linux the system call behind it is clone.
  2. execve(path, argv, envp): the child loads a new program. The PID, the parent, the open file descriptors and the current folder stay. Memory, code and signal handlers are replaced.
  3. exit(status): the program ends. The kernel frees almost everything but keeps the exit status for the parent.
  4. wait() or waitpid(): the parent collects the status, and only then does the process disappear completely. In bash the status ends up in $?.
fork, exec and wait in a small C programRun for real on Linux while this page was built
cat > forkdemo.c <<'EOF'
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    printf("parent %d starts\n", getpid());
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) {
        printf("child %d, my parent is %d\n", getpid(), getppid());
        fflush(stdout);
        execlp("ls", "ls", "/nope", (char *)NULL);
        _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);
    printf("child %d exited with status %d\n", pid, WEXITSTATUS(status));
    return 0;
}
EOF
gcc -Wall -o forkdemo forkdemo.c
./forkdemo
parent 24721 starts
child 24722, my parent is 24721
ls: cannot access '/nope': No such file or directory
child 24722 exited with status 2
fork returns 0 in the child, which prints its own PID and its parent and then runs execlp, a libc helper for execve that searches PATH. ls fails because /nope does not exist and exits with 2. The line after execlp only runs if exec itself fails (127 is what shells use for “command not found”). The parent waits for exactly this child and reads its status with WEXITSTATUS. fflush matters: without it, text still sitting in the output buffer would be copied by fork and could be printed twice.
Remember
This split is why redirections and pipes are easy in Unix. Between fork and exec, the child can close and reopen file descriptors (dup2, as in chapter 1.1), change folder, drop privileges or set limits, and the new program simply starts with that setup.
Every process on Linux is made by another one, in two steps. Fork makes a copy of the running process with a new process id. Fork returns twice: zero in the child, and the child’s process id in the parent. Then the child calls exec, which loads a new program into the same process. The process id, the parent and the open files stay. When the program ends, it calls exit with a status, and the parent collects that status with wait. Bash does exactly this for every external command you type, and puts the status in dollar question mark. In the C demo you can see all four steps, and ls failing with status two.

pstree draws the inner bash with its children: the two sleeps and the two sides of the pipe, pstree and sed (which hides the process ids, as they change every run). When its output is not a terminal, pstree draws with plain ASCII characters instead of lines. A process killed by a signal has no exit code of its own, so the shell reports 128 plus the signal number: 143 for SIGTERM and 137 for SIGKILL. A status is only 8 bits, so exit 300 becomes 300 − 256 = 44.
Common mistake
PID 1 is special. On Ubuntu it is systemd, which starts every service. The kernel never lets PID 1 die (if it exits, the kernel panics), it does not get signals it has no handler for, and it becomes the parent of every orphaned process. In a container, your own program may be PID 1, which is why containers use a small init such as tini or docker run --init.
All processes form one tree. At the top is process one, systemd on Ubuntu, which the kernel starts at boot. Every other process has a parent, shown as P P I D, and pstree draws the whole family. When a process ends, it leaves an exit status for its parent. Zero means success and anything else is an error. Some numbers have fixed meanings: one hundred twenty seven means command not found, and one hundred twenty eight plus a signal number means the process was killed by that signal. So one hundred thirty seven means it got SIGKILL, number nine, which is what you see when the kernel kills a program that uses too much memory.

unshare gives the demo its own PID namespace, so the outer bash is PID 1 here and ps sees only the demo. The inner bash starts sleep 1 in the background and then replaces itself with sleep 4 (exec), a program that never calls wait. When sleep 1 exits, it stays behind as a zombie, Z and <defunct>, with its parent still alive. In the second part, bash -c starts sleep 3 and exits at once. The orphaned sleep gets PID 1 as its new parent (PPID 1), and PID 1 will reap it.
Remember
Many processes in state D at once, a high load average with idle CPUs, and commands that hang on ls often mean a disk or an NFS server that does not answer. kill -9 cannot help with D, because the signal is only handled when the I/O returns. Look at dmesg for I/O errors and at the storage itself.
Every process is in a state, shown in the stat column of p s. R means running or ready to run, and S means sleeping while it waits for something, which is the normal state of most processes. D is a deep sleep inside the kernel while it waits for a disk, and such a process cannot be killed until the disk answers. T means stopped, for example by control Z. Z means zombie: the process has exited, but its parent has not collected the exit status yet. A zombie uses no memory, but a parent that never waits can leak thousands of them. If a parent dies first, the child becomes an orphan and gets process one as its new parent, which cleans up after it. The demo makes both, for real, in a private process namespace.

Threads of a Python program, nice and the scheduling policyRun for real on Linux while this page was built
cat > threads.py <<'EOF'
import os, subprocess, threading, time
for i in range(3):
    threading.Thread(target=time.sleep, args=(3,)).start()
subprocess.run(["ps", "-L", "-o", "pid,lwp,nlwp,stat,comm", "-p", str(os.getpid())])
print("tasks:", len(os.listdir(f"/proc/{os.getpid()}/task")))

Remember
Since Linux 6.6 the normal scheduler is EEVDF (earliest eligible virtual deadline first), which replaced CFS. Both give each runnable task a fair share of CPU time weighted by its nice value: each nice step changes the weight by about 25 percent, so a nice 0 task gets about 1.25 times the CPU of a nice 1 task when they compete.
A process can contain several threads. Threads share the memory and the open files of their process, so they can work on the same data, but a crash in one thread ends the whole process. On Linux every thread is a task of its own with a thread id, shown as L W P in p s dash capital L, and a folder in slash proc slash P I D slash task. The scheduler decides which task runs on which C P U and for how long. Nice values from minus twenty to nineteen change a task’s share: nicer tasks get less. Chrt sets special policies such as real time, and taskset pins a process to certain C P Us. Since kernel six point six, the scheduler is called E E V D F.

Practice: follow processes through their life

Start, inspect, pause and end processes on the practice server, and read their state in /proc.

Now follow processes yourself. Draw the process tree with pstree, once with process ids. Start sleep in the background and look at its parent and state with p s dash o. Read its state in slash proc, stop it with SIGSTOP and read the state again, which turns into T for stopped. Let it continue. Then run a shell that exits with status three and print the status. Finally start a nicer sleep with niceness ten and check the N I column.
Lesson 6 of 6

Processes from school to research

One idea, four depths

A process is a program that is running. Each one has a number, a parent that started it, and a state such as running or sleeping. When it ends, it leaves a result code: 0 means everything went well.

Read the tree with pstree and ps, understand fork, exec, exit and wait, exit statuses including 128+N, process states (D, Z, T), zombies and orphans, threads in ps -L, and priorities with nice, chrt and taskset.

Engineers write services that handle SIGTERM and SIGCHLD correctly, use process supervisors (systemd units with Restart=, or a small init in containers), choose between processes and threads (or event loops) for concurrency, pin latency critical work to CPUs, isolate CPUs with isolcpus or cgroup cpusets, and debug with /proc/PID/stack, gdb and perf.

Research studies schedulers (EEVDF, sched_ext in Linux 6.12, which lets schedulers be written as BPF programs), the cost of fork for large processes and alternatives such as posix_spawn and vfork, process creation in microservices and serverless systems that start thousands of short tasks per second, and lightweight virtual machines such as Firecracker.

Real world scenario: the server that ran out of process ids

A monitoring agent on a build server started a small check script every second, but never called wait for it. After two days, ps showed over 30000 <defunct> entries, and new logins failed with “fork: retry: Resource temporarily unavailable”. Killing the agent made systemd the parent of all zombies, which reaped them in a second. The vendor fixed the agent, and the team added a check that alerts when the number of Z processes grows.

Here is how understanding processes grows. At school you learn that a process is a running program with a number, a parent and a result code. Professionals read the process tree, understand fork, exec and wait, know what states like D and Z mean, and use nice and chrt to share the C P U. Engineers build services that handle signals and child processes correctly, pick between processes and threads, and pin critical work to C P Us. Researchers design new schedulers, including ones written as B P F programs, and find faster ways to start thousands of tiny tasks per second.
