Stop on the first error: set -e, -u and pipefail

By default bash runs every line of a script, even after a command fails. Three options make a script stop instead of carrying on with bad data. Many scripts start with all three on one line.

OptionEffectWatch out for
set -e (errexit)exit as soon as a simple command failsignored inside if, while and until tests, in && and || lists except the last command, and after !
set -u (nounset)using a variable that was never set is an error, and the script exitsuse ${VAR:-} for variables that may be missing, such as optional settings
set -o pipefaila pipeline fails when any part fails, not only the lastgrep finding nothing in the middle of a pipe now counts as a failure
set -euo pipefailall three at once, usually the second line of a scriptit is a safety net, not a replacement for checking errors yourself
What set -e and friends really doRun for real on Linux while this page was built
cat > strict.sh <<'EOF'
#!/bin/bash
set -euo pipefail
echo "start"
if grep -q pizza fruits.txt; then echo "pizza"; else echo "no pizza, still running"; fi
grep -q pizza fruits.txt || echo "handled with ||"
count=$(grep -c apple fruits.txt)
echo "apples: $count"
grep pizza fruits.txt | sort
echo "never printed"
EOF
bash strict.sh; echo "exit status $?"
start
no pizza, still running
handled with ||
apples: 3
exit status 1
printf 'set -u\necho "name is ${NAME:-unknown}"\necho "home is $HOEM"\necho "never"\n' > typo.sh
bash typo.sh; echo "exit status $?"
name is unknown
typo.sh: line 3: HOEM: unbound variable
exit status 1
printf 'set -e\nn=0\n(( n++ ))\necho "n=$n"\n' > gotcha.sh
bash gotcha.sh; echo "exit status $?"
exit status 1
printf 'set -e\nn=0\n(( ++n ))\necho "n=$n"\n' > fixed.sh
bash fixed.sh
n=1
The failing test inside if and the failure before || did not stop the script. With pipefail the grep that found nothing made the pipeline fail, so set -e stopped it. set -u caught the typo HOEM, while ${NAME:-unknown} supplied a default. (( n++ )) returns the old value 0, which counts as a failure, but (( ++n )) returns 1 and passes.
Common mistake
set -e is ignored in a function called from a condition such as if myfunc or myfunc || ..., for the whole function body. Check important steps explicitly with || die "...".
A plain bash script keeps going after a failure, which can be dangerous. Imagine a cleanup script whose cd command fails, followed by a delete that now runs in the wrong folder. Three options give you a safety net. Set dash e stops the script when a command fails. Set dash u stops it when you use a variable that was never set, which catches typos in variable names. And set dash o pipefail makes a pipeline fail if any part of it fails, not only the last command. Most careful scripts start with set dash e u o pipefail. But set dash e has exceptions, and they matter. A failure inside an if test, a while test, or before a double ampersand or double bar is treated as a decision, not an error. And arithmetic that evaluates to zero, such as n plus plus when n starts at zero, counts as a failure and stops the script. Try the animation to see every rule in action.

Cleaning up with trap and temporary files

trap 'commands' SIGNALS runs commands when the script receives a signal or reaches a special moment. The most useful is EXIT, which runs whenever the script ends, normally, after an error, or after Ctrl+C or a kill.

CommandWhat it doesExample
trap 'cmds' EXITRun cmds when the script ends, however it endstrap 'rm -rf "$tmpdir"' EXIT
trap 'cmds' ERRRun cmds after any failing command (same rules as set -e)trap 'echo "failed at line $LINENO"' ERR
trap 'cmds' INT TERMCatch Ctrl+C (INT) and kill (TERM)trap 'echo stopping; exit 130' INT
trap '' INTIgnore a signaltrap '' HUP
trap - INTBack to the default actiontrap - INT
mktemp, mktemp -dCreate a unique temporary file or folder that only you can readtmp=$(mktemp) && trap 'rm -f "$tmp"' EXIT
A script that always cleans upRun for real on Linux while this page was built
cat > tidy.sh <<'EOF'
#!/bin/bash
set -euo pipefail
workdir=$(mktemp -d)
cleanup() { rm -rf -- "$workdir"; echo "cleanup: removed the temp folder" >&2; }
trap cleanup EXIT
trap 'echo "error on line $LINENO: $BASH_COMMAND" >&2' ERR
echo "working in a private folder: $(stat -c %A "$workdir")"
sort fruits.txt > "$workdir/sorted"
uniq -c "$workdir/sorted" | sort -rn | head -2
cp "$workdir/sorted" /root/sorted.txt
echo "not reached"
EOF
bash tidy.sh; echo "exit status $?"
working in a private folder: drwx------
      3 apple
      2 mango
cp: cannot stat '/root/sorted.txt': Permission denied
error on line 10: cp "$workdir/sorted" /root/sorted.txt
cleanup: removed the temp folder
exit status 1
cat > stop.sh <<'EOF'
#!/bin/bash
trap 'echo "caught Ctrl+C (INT), saving state"; exit 130' INT
trap 'echo "goodbye from EXIT"' EXIT
echo "working"
kill -INT $$
echo "never printed"
EOF
bash stop.sh; echo "exit status $?"
working
caught Ctrl+C (INT), saving state
goodbye from EXIT
exit status 130
mktemp -d made a folder only the owner can open (drwx------). The cp to /root failed, so the ERR trap printed the line number and the failing command, set -e stopped the script, and the EXIT trap still removed the temporary folder. The second script sent itself SIGINT, as Ctrl+C would, and the INT trap ran before EXIT. 130 is 128 plus 2, the number of SIGINT.
Common mistake
Never use a fixed name such as /tmp/myscript.tmp. Another user can create it first, as a symbolic link to one of your files, and your script would overwrite that file. mktemp picks a new random name every time.
Scripts often create temporary files, take locks, or start helper processes, and these must be cleaned up even when something goes wrong. The trap command is the tool for this. Trap followed by a command and the word EXIT runs that command whenever the script ends, whether it finished normally, failed under set dash e, or was stopped with Control C. The usual pattern is to create a private temporary folder with mktemp dash d, write a small cleanup function, and register it with trap cleanup EXIT straight away. A trap on ERR runs after any failing command, and the variables LINENO and BASH COMMAND tell you exactly where it happened, which makes error messages much more helpful. Traps on INT and TERM let a script react to Control C and to kill, for example to save its state. Always let mktemp choose the name, because fixed names in slash tmp can be abused by other users.

Each finding has a code you can look up on the ShellCheck wiki. Fixing both gives cd -- "$dir" || exit 1 and rm -rf -- "$dir/cache". With an empty $1, the original would have run rm -rf /cache.
Three tools find most bugs in shell scripts. Bash dash n reads the whole script and checks the syntax without running anything, which is a quick safety step before you deploy a script. Bash dash x runs the script and prints every command after all expansions, with a plus sign in front, so you see the real values of variables at each step. You can switch tracing on and off inside a script with set dash x and set plus x, and the variable PS4 changes the prefix, for example to show line numbers. The third tool is ShellCheck, a free program that reads a script and warns about common mistakes, such as missing quotes around variables or a cd whose failure is ignored. Each warning has a code like S C two zero eight six, which you can look up on the ShellCheck wiki for an explanation and a fix. Many teams run ShellCheck automatically on every change.

command -v answered without running anything. The readonly variable refused the change. With -- the file named -rf was treated as a name, not as options. umask 077 in a child bash made a file only the owner can read, without changing the umask of this shell. The dry run printed the dangerous command instead of running it. The grep or echo line added the setting once, even though it ran twice.
Scripts that run unattended, from cron or a deployment pipeline, need extra care, because nobody is watching when something odd happens. A few habits prevent most disasters. Quote every variable, and put a double dash before file names, so a file called dash r f can never be read as options. Check at the start that every tool the script needs is installed, using command dash v, and stop with a clear message if not. Make constants readonly, and set umask zero seven seven when the script writes private data. Use flock so that two copies of the same job cannot run at once. Offer a dry run mode that prints what would happen. And write steps that are idempotent, which means running them twice gives the same result as running them once, such as mkdir dash p, or adding a line to a file only when it is not already there.
Lesson 5 of 5

Robust scripts from school to research

One idea, four depths

A good script stops when something goes wrong, tells you where, and tidies up after itself. set -euo pipefail stops it, trap cleans up, and bash -x and ShellCheck help you find mistakes.

errexit is skipped in conditions, in && and || lists except the last command, after !, and in all commands of a function called from a condition. A command substitution inside a local declaration hides its status, since local itself succeeds, so write local x and then x=$(cmd). The EXIT trap runs once when the shell ends, and ERR follows the same rules as errexit.

Subshells and command substitutions do not inherit the ERR trap unless set -E (errtrace) is on, and set -T does the same for DEBUG and RETURN. inherit_errexit (shopt, bash 4.4) makes $( ) inherit set -e. Signals interrupt a foreground external command only after it exits, so long-running tools should be started in the background and waited for if a script must react quickly. PIPESTATUS gives the status of every part of the last pipeline.

Many experts argue that set -e is unreliable because of its many exceptions (see the BashFAQ entry 105 on Greg’s Wiki), and prefer explicit checks with || die. Static analysis research on shell scripts, including work behind ShellCheck and the NL2Bash and Smoosh projects, shows that error handling and quoting dominate real bugs. Configuration management tools such as Ansible encode the idea of idempotent steps directly, so that running a task twice is always safe.

Real world scenario: the backup that deleted itself

A nightly job ran cd $BACKUP_DIR; rm -rf * to empty a staging folder. One night BACKUP_DIR was empty after a config change, cd went to the home folder, and the job deleted it. The rewrite starts with set -euo pipefail, reads : "${BACKUP_DIR:?is not set}", runs cd -- "$BACKUP_DIR" || exit 1, uses flock so two runs never overlap, and logs every step through an ERR trap. ShellCheck now runs in CI and flagged three other scripts with the same pattern.

Here is the expert view on robust scripts. Set dash e has many exceptions: it is ignored inside conditions, in all but the last command of double ampersand and double bar lists, after an exclamation mark, and in every command of a function that was called from a condition. A command substitution inside a local declaration also hides its failure, because local itself succeeds, so declare the variable first and assign it on the next line. Subshells do not inherit the ERR trap unless you set dash capital E. Because of these traps, many experienced writers prefer explicit checks with double bar die after each important step, and treat set dash e only as a backup. Researchers who study real shell scripts find that error handling and quoting cause most bugs, which is exactly what ShellCheck focuses on. And tools such as Ansible build the idea of idempotent steps into their design.
