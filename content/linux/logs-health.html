Where Linux keeps its logs

Programs report what they do in logs. Modern systems keep two kinds side by side: the systemd journal, a structured store read with journalctl, and plain text files in /var/log, written by rsyslog and by programs themselves.

Not every program writes here: this container has no rsyslog, so there is no syslog or auth.log file, and the journal holds those messages instead. term.log belongs to the group adm, the usual group for reading logs. dpkg.log and history.log show exactly what changed and when, which is the first place to look after an update breaks something.
When something goes wrong on a Linux machine, the logs tell you what happened. Today most systems keep two kinds. The systemd journal collects messages from every service, the kernel and many programs, and stores them with extra facts such as the unit name and the priority. You read it with journalctl. Many systems also run rsyslog, which copies messages into plain text files in slash var slash log, such as syslog for general messages and auth dot log for logins, ssh and sudo. Package tools keep their own history in dpkg dot log and apt slash history dot log. Every message has a priority from zero, emergency, to seven, debug, and errors are priority three. Many log files can only be read by root or by members of the group adm. Try the animation to see how a few filters turn a wall of log lines into the handful that explain a problem.

A normal user sees only their own messages. One filter on priority found a failed backup, a user who typed the sudo password wrong three times, and a program killed because memory ran out. Every line of the journal has a time, the host, the program with its process ID, and the message.
Remember
On some systems the journal lives only in memory (/run/log/journal) and is lost at reboot. Create /var/log/journal, or set Storage=persistent in /etc/systemd/journald.conf, to keep it, so that journalctl -b -1 can show why the last boot crashed.
Journalctl is a search tool for the journal. Without options it prints everything, which is far too much, so you add filters. Dash u picks one unit, such as nginx. Dash p err keeps errors and anything worse. Dash b limits it to the current boot, and dash b minus one to the boot before, which helps after a crash. Since and until set a time window, and they understand words like today and phrases like two hours ago. Dash g searches the text with a regular expression, and dash k shows only kernel messages. Dash f keeps the output open and prints new lines as they arrive, which is perfect while you restart a service in another window. Remember that normal users only see their own messages, so use sudo or join the adm group. And if the journal is kept only in memory, make it persistent, so you can read what happened before the last reboot.

The address is always the fourth field from the end of a Failed password line, so awk can pick it with $(NF-3) however long the line is. Comparing the time field as text works because the format has a fixed width. One address made most of the attempts, a typical sign of a password guessing robot.

Text logs are just lines of text, so everything you learned about grep, awk, sort and uniq works on them. A classic job is to find who is trying to guess passwords over ssh. Grep finds the failed password lines, grep dash o pulls out the addresses, and sort, uniq dash c and sort dash r n count them and put the busiest first. Awk can pick fields by number, and dollar N F minus three counts from the end of the line, which works even when lines have different lengths. Tail dash f keeps a log open while it grows. Rotated logs are often compressed, and zgrep searches inside them without unpacking. And when you write your own scripts, the logger command puts your messages into the same system log, with a tag and a priority, so they appear next to everything else.
Lesson 4 of 7

Keeping logs small with logrotate

Logs grow forever unless something trims them. logrotate, run once a day by a systemd timer or cron, renames the current file, starts a fresh one, compresses old ones and deletes the oldest.

A logrotate rule in /etc/logrotate.d/myappThe general form
/var/log/myapp/*.log {
    daily               # or weekly, monthly, or size 100M
    rotate 7            # keep 7 old files
    compress            # gzip old files
    delaycompress       # but leave the newest old file uncompressed
    missingok           # no error if the log is missing
    notifempty          # skip empty logs
    create 0640 myapp adm
    postrotate          # tell the program to reopen its log
        systemctl reload myapp
    endscript
}
Many programs keep writing to the old file after a rename. postrotate makes them reopen the log, and copytruncate is the fallback for programs that cannot.
logrotate at work, run as rootRun for real on Linux while this page was built

logrotate -d -f -s state app.conf 2>&1 | grep -E '^(rotating log|  log needs)'

-d is a dry run that only explains what would happen, and -f forces a rotation now. The create line made a fresh, empty app.log with mode 640 for root and adm. After two rotations there is the fresh app.log, the newest old file app.log.1 kept plain because of delaycompress, and app.log.2.gz. The state file remembers when each log was last rotated.
Log files grow every day, and a full disk can stop a whole server. Logrotate prevents this. Once a day it checks each log against its rules in slash etc slash logrotate dot d. When a log is due, it renames app dot log to app dot log dot one, shifts older files up by one number, compresses them, deletes the oldest beyond the count you chose, and creates a fresh empty file. A rule says how often to rotate, by time or by size, how many old files to keep, and whether to compress them. Because many programs keep writing into the old renamed file, a postrotate script usually tells the program to reopen its log. Test a new rule with logrotate dash d, which only describes what it would do, and dash f to force a rotation now.

A load average below the number of CPUs means the CPUs keep up. In free, buff/cache is memory the kernel lends to the file cache and gives back when programs need it, so available is the number that matters. df -i counts inodes, since a disk can be full of tiny files while it still has free bytes. In vmstat the first line is an average since boot, the next ones are live, and wa is time spent waiting for disks.
Common mistake
When memory runs out, the kernel’s OOM killer stops a process to save the system. The journal then has a line like “Out of memory: Killed process 2261 (java)”. Find it with sudo journalctl -k -g "out of memory" or sudo dmesg -T | grep -i oom.
Before you dig into logs, a quick health check often points to the problem. Uptime shows the load average, the number of processes that want a CPU, averaged over one, five and fifteen minutes. Compare it with nproc, the number of CPUs. A load of four on a four CPU machine means fully busy. Free dash h shows memory, and the available column is what counts, because Linux uses spare memory as a file cache and gives it back when needed. Df dash h shows free disk space, and df dash i shows free inodes, which can run out when there are millions of tiny files. Vmstat prints a line every second with processes, memory, input and output, and CPU use. And dmesg shows kernel messages, such as disk errors or the out of memory killer, which stops a program when memory runs out.

Practice: investigate an incident in the practice shell

The practice server had a busy night: password guessing over ssh, a failed backup and a program killed for using too much memory. Use the logs to find out what happened.

Now you are the admin on call. The practice server had a busy night. Start by trying to read the auth log without sudo, to see that it is protected. Then count the failed password lines, and list the attacking addresses with a count for each, busiest first. Next ask the journal for every error since today, and narrow the kernel messages down to the one about memory. Find out who used sudo and whether anyone typed the password wrong. Finally, write a note into the system log with logger and a tag, and find it again with journalctl dash t.
Lesson 7 of 7

Logs and monitoring from school to research

One idea, four depths

Logs are the diary of a computer. When something breaks, look at the newest errors first: sudo journalctl -p err -b and the log of the program that failed.

Make the journal persistent, set size limits in journald.conf, and rotate text logs. Ship logs off the machine (rsyslog forwarding, systemd-journal-upload), so an attacker who becomes root cannot erase the trail. Watch disk, memory, load and failed units, and alert before users notice.

Central stacks collect logs and metrics from many machines: the ELK stack (Elasticsearch, Logstash, Kibana) or Grafana Loki for logs, Prometheus with node_exporter and Grafana for metrics, and alerting rules on top. Structured logs (key=value or JSON) are much easier to search than free text. auditd records security events such as file access and commands for compliance.

Observability research and practice join logs, metrics and traces (OpenTelemetry) to follow one request across many services. Studies of large outages, such as the published post-mortems of cloud providers, show that missing or misleading monitoring often delays recovery more than the fault itself. Log parsing research (for example the Drain algorithm and the LogHub data sets) turns free-text lines into templates so machine learning can spot unusual patterns.

Real world scenario: the disk that filled up at 3 a.m.

A web server stopped answering at night. df -h showed / at 100 percent, and du -h --max-depth=1 /var | sort -h pointed at /var/log/myapp, where a debug log had grown to 40 GB because it had no rotation rule. The fix added a logrotate rule with size 500M and rotate 5, set SystemMaxUse=1G for the journal, and added a disk alert at 80 percent so the next problem pages someone hours earlier.

Here is how log work grows with experience. Beginners learn to look at the newest errors first. Professionals make sure logs survive reboots, rotate them so disks never fill up, and send copies to another machine, because an attacker with root could delete local logs. They also watch a few key numbers, such as disk space, memory, load and failed services, and get an alert before users notice a problem. Larger teams collect logs and metrics from all machines in central systems such as the E L K stack, Grafana Loki and Prometheus, and prefer structured logs that are easy to search. At the research level, observability joins logs, metrics and traces to follow a single request through many services, and log parsing algorithms turn millions of free text lines into patterns that machine learning can check for anything unusual.
