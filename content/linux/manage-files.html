Linux file names may contain any character except / and the invisible null byte, and they are case sensitive. Good habits: use lower case, letters, digits, dots, dashes and underscores. Avoid spaces and characters like *, ?, $, & and the semicolon, which the shell treats specially. A file extension such as .txt is only part of the name. Linux does not need it, programs look at the content.

Common mistake
mkdir a/b fails with "No such file or directory" when a does not exist yet. Add -p to create every missing parent.
mkdir is short for make directory and touch is a funny name with a real meaning. Its first job was to touch a file, updating its time stamp without changing the content. Programmers used it with a build tool called make, which decides what to rebuild by comparing file times. Making an empty file was a side effect that turned out to be handy. Here is a rule many people learn the hard way. Linux treats Report.txt and report.txt as two different files, while Windows and macOS usually treat them as the same. In 2014 Git had a serious security bug on Windows and macOS caused by exactly this difference in how case is handled. Pick a simple naming style early: lower case letters, digits and dashes, no spaces. Your future self, and every script you write, will thank you.

Copying, moving and renaming: cp and mv

CopyExam favourite
cp SOURCE DEST
Copies a file. If DEST is a folder, the copy goes inside it with the same name. Several sources need a folder as DEST.
Copy a folderExam favourite
cp -r FOLDER DEST
-r (recursive) copies the folder and everything inside. -a also keeps times, owners and links, best for backups.
Move or renameExam favourite
mv OLD NEW
Inside one disk, mv only changes the name, so even a huge folder moves instantly. mv to another disk copies, then deletes.
CommandWhat it doesExample
cp -iAsk before overwriting an existing filecp -i a.txt b.txt
cp -vPrint each copycp -v *.txt backup/
cp -pKeep mode, owner and timescp -p notes.txt old/
mv -iAsk before overwritingmv -i draft.txt final.txt
mv -nNever overwritemv -n new.txt old.txt

Common mistake
cp and mv overwrite an existing destination file without asking. Use -i while you learn, or -n when you never want to overwrite.
Remember
There is no rename command needed: renaming is moving a file to a new name in the same folder.
Copying a huge folder can take minutes, but moving it to another place on the same disk takes a fraction of a second. Why? Because a move does not touch the data at all. A folder is really just a list of names, each pointing to the place where the file lives. mv only takes the name out of one list and writes it into another. The bytes stay exactly where they were. Only when you move to a different disk does mv have to copy every byte and then delete the original. Another thing that surprises beginners is that cp and mv will silently replace a file that already has the destination name. There is no undo. That is why many Linux distributions set up cp and mv with the dash i option for the root user, so they ask first, and why careful people check with ls before pressing Enter.

Deleting safely: rm and rmdir

rm deletes for good. There is no recycle bin on the command line, and no undo. Read every rm command twice before pressing Enter.

CommandWhat it doesExample
rm FILEDelete filesrm old.txt
rm -i FILEAsk about each file firstrm -i *.log
rm -r FOLDERDelete a folder and everything inside itrm -r build
rm -f FILEForce: never ask, no error if missing. Dangerous with -rrm -f tmp.txt
rmdir FOLDERDelete a folder only if it is empty, a safe choicermdir empty-folder
rm -- -nameDelete a file whose name starts with a dashrm -- -weird.txt
Delete, and see the safety netsRun for real on Linux while this page was built
mkdir -p trash/inner
touch trash/a.txt
rmdir trash
rmdir: failed to remove 'trash': Directory not empty
rm trash
rm: cannot remove 'trash': Is a directory
rm -r trash
ls trash
ls: cannot access 'trash': No such file or directory
rmdir refuses because the folder is not empty, rm refuses a folder without -r, and after rm -r it is gone.
A safe deleting routine
  1. Run ls with exactly the same pattern first, for example ls *.log, and read the list.
  2. Press Up, change ls to rm, and check that nothing else changed.
  3. Prefer a specific path to a wildcard, and never type a lonely * or / with -r.
  4. Use rm -i or move things to a trash folder while you learn.
  5. Keep backups. They are the only real undo.
Common mistake
GNU rm refuses rm -r / and needs --no-preserve-root to do it (protection added in coreutils 6.4, 2006). But it will happily delete everything with rm -rf ~/* or with a typo such as a space in rm -rf ./ folder. There is no protection for those.
Here is a true kind of story that happens every year. In 2017 an engineer at the code hosting company GitLab was fixing a database problem late at night, tired, logged into two servers. He meant to delete a folder on the broken server, but ran the command on the healthy one. About three hundred gigabytes of live data disappeared in seconds. GitLab recovered most of it from a copy that happened to be six hours old, and they wrote openly about it so others could learn. The lesson is simple. rm does not ask, does not use a recycle bin, and does not forgive. Check the prompt to see which machine you are on, list the files before deleting them, and keep backups that you have actually tested. Professionals are not people who never make mistakes. They are people who build habits that make mistakes rare and recoverable.

Wildcards and braces: many files at once

Instead of typing every name, you can give the shell a pattern. The shell turns the pattern into the list of matching names before the command starts. This is called globbing.

*Exam favourite
any text, even none
*.txt matches notes.txt and a.txt. * alone matches every name that does not start with a dot.
?
exactly one character
photo?.jpg matches photo1.jpg but not photo10.jpg.
[abc] [a-z] [!a]
one character from a set
[nf]* matches names starting with n or f. [!0-9]* names not starting with a digit.
{a,b} {1..5}Exam favourite
brace expansion, not a match
Makes words even if no file exists: mkdir day{1..3} makes day1 day2 day3.

Remember
If nothing matches, bash passes the pattern itself unchanged. rm *.bak in a folder with no .bak files gives "rm: cannot remove ’*.bak’: No such file or directory".
Wildcards save enormous amounts of typing. A photographer with three thousand pictures can copy every JPEG file with one short pattern. The important detail is who does the matching. It is the shell, not the command. Before cp even starts, the shell looks in the folder, finds every name that fits the pattern, and hands that list to cp. That is why patterns work the same way with every command. The idea goes back to the first Unix, where a separate tiny program called glob did the expanding, short for global, and the name stuck. Braces are different. They do not look at files at all. They simply make words, so mkdir with day one to three in braces creates three folders that did not exist before. One warning: a star does not match hidden names that start with a dot, which is usually what you want.
Lesson 5 of 5

File operations from school to research

One idea, four depths

mkdir makes a folder, touch makes an empty file, cp copies, mv moves or renames, and rm deletes for ever. A star in a name means "anything here", so *.jpg means every picture ending in .jpg.

File management commands operate on paths. Globbing (*, ?, [...]) is performed by the shell, brace expansion generates words before globbing, and the command receives the resulting argument list. cp -a preserves metadata, mv within a filesystem is a rename, and rm unlinks names.

rm calls unlink() or unlinkat(), which removes a directory entry. The data blocks are freed only when the inode link count reaches zero and no process holds the file open, which is why deleting a log that a program still writes does not free disk space. mv on one filesystem calls rename(), which is atomic: other processes see the old name or the new one, never a half state. Across filesystems mv falls back to copy plus unlink.

Topics include atomic file replacement patterns (write a temp file, fsync, rename) used by databases and editors, crash consistency studies that showed many applications lose data on power failure (Pillai and others, OSDI 2014), copy on write filesystems (Btrfs, ZFS) with instant reflink copies via cp --reflink, and secure deletion, which is hard on SSDs because of wear levelling.

Real world scenario: a disk that stays full

An engineer deletes a 20 GB log file to free space, but df still shows the disk full. The web server still has the file open, so the kernel keeps the data until the server closes it. Restarting the service, or emptying the file with : > file instead of deleting it, frees the space. You will meet this again in the inodes chapter.

Inside the computer, deleting a file is not what most people imagine. rm does not wipe the data. It removes the name from the folder list, and the space is only marked as free when no name points to it and no program has the file open. This explains a famous puzzle on servers. An engineer deletes a huge log file, but the disk stays full, because the web server is still writing to it. Researchers have also studied what happens to files when the power fails. A well known study presented at the OSDI conference in 2014 found that many popular programs could lose or corrupt data in a crash, because they replaced files in an unsafe order. The safe pattern is to write a new file, flush it to disk, and then rename it over the old one, because rename on one disk is atomic. Databases and good editors all use this trick.
