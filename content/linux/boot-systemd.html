How Linux starts: firmware to login

Starting a computer is a relay race. Each stage loads the next one and hands over control, and knowing the order tells you where to look when a machine does not come up.

StageWhat it doesWhere it is configured
Firmware (UEFI or BIOS)tests the hardware and starts a boot loader from the diskfirmware setup screen, the EFI System Partition at /boot/efi
Boot loader (GRUB)shows the menu, loads the kernel and initramfs, passes the kernel command line/etc/default/grub, then sudo update-grub writes /boot/grub/grub.cfg
Kerneldetects the hardware, starts memory management and drivers/boot/vmlinuz-VERSION, the command line in /proc/cmdline
initramfsa small file system in memory that loads the drivers for the real root disk and mounts itbuilt by update-initramfs (Debian) or dracut (Fedora, RHEL)
systemd (PID 1)mounts file systems from /etc/fstab and starts services until the default target is reachedunit files in /usr/lib/systemd/system and /etc/systemd/system
Logingetty on text consoles, a display manager on desktops, sshd for remote loginsthe units getty@.service, gdm.service, ssh.service
TargetOld runlevelMeaning

The runlevel names still exist as links to targets, so old scripts keep working. This system boots into graphical.target by default. A server would usually use multi-user.target, set with sudo systemctl set-default multi-user.target.
Remember
To reach a rescue shell on a machine that does not boot, press e in the GRUB menu, add systemd.unit=rescue.target (or emergency.target) to the line that starts with linux, and boot with Ctrl+X. The change lasts for one boot only.
When you press the power button, several programs take turns. First the firmware, called U E F I on modern computers or BIOS on old ones, checks the hardware and starts a boot loader from the disk. On Linux the boot loader is usually GRUB, which shows a menu and loads two files into memory: the kernel and the initramfs. The kernel detects the hardware, and the initramfs, a tiny temporary file system, loads the drivers needed to reach the real root disk, for example for encryption, where it asks for your passphrase. Then the kernel starts systemd as process number one. Systemd mounts the file systems listed in slash etc slash fstab and starts all services, many of them in parallel, until it reaches the default target, such as multi user for servers or graphical for desktops. Targets replaced the old numbered runlevels. In the animation, choose a fault to see exactly where a broken boot stops and how to fix it.

Units and unit files

Everything systemd manages is a unit, described by a small text file in INI style. The file name ends with the unit type.

TypeManagesExample
.servicea program, often a background daemonssh.service, nginx.service
.timerstarts a service on a scheduleapt-daily.timer
.socketa network or local socket, which starts its service on the first connectionssh.socket
.targeta group of units, a synchronisation pointmulti-user.target
.mount, .automounta mounted file system (made from /etc/fstab lines too)home.mount
.pathstarts a service when a file or folder changescups.path

Real unit files: a service and the timer that starts itRun for real on Linux while this page was built
cat /lib/systemd/system/apt-daily.service
[Unit]
Description=Daily apt download activities
Documentation=man:apt(8)
ConditionACPower=true
After=network.target network-online.target systemd-networkd.service NetworkManager.service connman.service

[Service]
Type=oneshot
ExecStartPre=-/usr/lib/apt/apt-helper wait-online
ExecStart=/usr/lib/apt/apt.systemd.daily update
cat /lib/systemd/system/apt-daily.timer
[Unit]
Description=Daily apt download activities

[Timer]
OnCalendar=*-*-* 6,18:00
RandomizedDelaySec=12h
Persistent=true

[Install]
WantedBy=timers.target
systemctl --root=/ list-unit-files --type=timer --no-pager | head -5
UNIT FILE                      STATE    PRESET
apt-daily-upgrade.timer        enabled  enabled
apt-daily.timer                enabled  enabled
dpkg-db-backup.timer           enabled  enabled
e2scrub_all.timer              enabled  enabled
The service is Type=oneshot, a job that runs and ends. Its timer fires at 06:00 and 18:00 with a random delay of up to 12 hours, and Persistent=true catches up after downtime. The [Install] section says which target pulls the unit in when it is enabled.
Check a unit file before you use itRun for real on Linux while this page was built
printf '[Unit]\nDescription=Hello web demo\nAfter=network.target\n\n[Service]\nExecStart=/usr/bin/python3 -m http.server 8080\nRestart=on-failure\n\n[Install]\nWantedBy=multi-user.target\n' > hello.service
systemd-analyze verify ./hello.service && echo "hello.service looks fine"
hello.service looks fine
printf '[Service]\nExecStart=/usr/bin/python3 -m http.server 8080\nRestrat=always\n' > typo.service
systemd-analyze verify ./typo.service
/home/learner/typo.service:3: Unknown key name 'Restrat' in section 'Service', ignoring.
systemd-analyze verify found the misspelled key Restrat. systemd itself only logs such a line and ignores it, so the service would quietly run without the restart rule.
CommandWhat it doesExample
sudo systemctl edit NAMECreate a drop-in override in /etc/systemd/system/NAME.service.d/override.conf, without touching the package filesudo systemctl edit nginx
systemctl cat NAMEShow the unit file and all its drop-inssystemctl cat nginx
sudo systemctl daemon-reloadMake systemd read changed unit filessudo systemctl daemon-reload
systemctl list-dependencies TARGETShow what a target pulls insystemctl list-dependencies multi-user.target
Systemd manages things called units, and each unit is a short text file. The ending of the file name tells the type. A dot service unit runs a program, a dot timer starts a service on a schedule, a dot socket waits for connections, and a dot target groups other units, like a milestone during boot. Package units live in slash usr slash lib slash systemd slash system, and you should never edit them, because an upgrade overwrites them. Your own units and changes go in slash etc slash systemd slash system, which wins over the package folder. The safest way to change a package’s unit is systemctl edit, which writes a small override file. Every unit file has sections in square brackets. Unit holds the description and the order, Service says what to run, and Install says which target pulls it in when it is enabled. Before you trust a new file, run systemd analyze verify, which catches typos that systemd would otherwise silently ignore.

The Loaded line says where the unit file is, whether it starts at boot (enabled) and what the vendor preset is. Active says the state and since when. Changing a service needs root, so the first stop was refused. systemctl --failed found a backup job that failed during the night.
Common mistake
enable and start are different. enable only creates a link so the unit starts at the next boot. start runs it now. A new service usually needs both, which is what enable --now does.
Systemctl is the remote control for services. Systemctl status shows whether a service runs, its main process, how much memory it uses, and its last log lines, which is often enough to see what went wrong. Start, stop and restart act right now, and reload asks the service to read its configuration again without dropping connections, if it supports that. Enable and disable are about the next boot: enable creates a link so the service starts automatically, and dash dash now also starts it at once. Mask is stronger than disable, because it forbids any start at all. For scripts, is active and is enabled print one word and set the exit status. And after every boot or change, systemctl dash dash failed quickly lists anything that broke.

Writing your own service

/etc/systemd/system/myapp.serviceThe general form
[Unit]
Description=My web app
After=network-online.target
Wants=network-online.target

[Service]
User=myapp                       # never run an app as root
WorkingDirectory=/srv/myapp
Environment=PORT=8080
ExecStart=/srv/myapp/venv/bin/python app.py
Restart=on-failure               # start it again if it crashes
RestartSec=5
NoNewPrivileges=yes              # sandboxing, see systemd.exec(5)
ProtectSystem=full
PrivateTmp=yes

[Install]
WantedBy=multi-user.target
ExecStart needs a full path. The program must stay in the foreground, because systemd watches that process. Do not use & or nohup here.
SettingEffect
Type=simple (default)the program in ExecStart is the service itself
Type=oneshota job that runs and ends, such as a backup started by a timer
Type=forkingold style daemons that fork into the background, such as nginx
Restart=on-failure, alwaysrestart after a crash or a non-zero exit, or after any exit
EnvironmentFile=/etc/myapp.envread KEY=value lines, keeps secrets out of the unit file
ProtectHome=yes, ProtectSystem=stricthide /home, make the whole file system read-only for the service
DynamicUser=yesrun as a temporary user that exists only while the service runs
From unit file to running service
  1. Write the unit. Create the file in /etc/systemd/system with sudo, for example with sudo systemctl edit --force --full myapp.service.
  2. Reload. sudo systemctl daemon-reload makes systemd read it.
  3. Enable and start. sudo systemctl enable --now myapp.
  4. Check. systemctl status myapp and journalctl -u myapp -f to watch the log.
  5. Change later. Edit, then daemon-reload and restart. systemctl status warns when the file changed on disk without a reload.
Turning your own program into a service is easy and gives you a lot for free: start at boot, automatic restarts after crashes, logging, and security limits. Create a file in slash etc slash systemd slash system ending in dot service. In the Unit section give a description and say that it should start after the network is online. In the Service section, name the user it runs as, because an app should never run as root, and give the full path of the program in ExecStart. The program must stay in the foreground, since systemd watches that process. Restart equals on failure brings it back after a crash. Options such as ProtectSystem and PrivateTmp put the service in a small sandbox. In the Install section, WantedBy multi user target makes it start at boot. Then run daemon reload, enable dash dash now, and check it with systemctl status and journalctl dash u.

Lesson 6 of 6

Boot and services from school to research

One idea, four depths

A computer starts in stages: firmware, boot loader, kernel, then systemd, which starts the services. systemctl status, start, stop and enable control services.

Order and requirement are different things: After= only orders, Wants= and Requires= pull units in. Use network-online.target only when a service really needs a working network at start. systemd-analyze blame and systemd-analyze critical-chain show what slows the boot. Socket activation starts a service on its first connection.

systemd puts each service in its own cgroup, so it can limit memory and CPU (MemoryMax=, CPUQuota=) and always kill every process of a service. systemd-analyze security NAME scores a unit’s sandbox. Secure Boot checks signatures from the firmware through the boot loader to the kernel, and measured boot records hashes in the TPM so disk keys unlock only on an untouched system.

Init systems are a long-running debate: SysV init scripts ran one after another, Upstart reacted to events, and systemd uses dependencies and parallel start-up. Research and industry work on unified kernel images, which bundle kernel, initramfs and command line into one signed UEFI file, and on fast boot for containers and micro-VMs such as Firecracker, which start a kernel in about a hundred milliseconds.

Real world scenario: the server that waited 90 seconds

After a reboot a web server took two minutes to come up. systemd-analyze critical-chain showed a mount of a network share waiting 90 seconds for a server that had been retired. The fix added nofail and x-systemd.mount-timeout=10 to the fstab line, and the boot went back to 14 seconds. The team now checks systemctl --failed and the boot time after every kernel update.

Here is the bigger picture on boot and services. In unit files, After only sets the order, while Wants and Requires actually pull another unit in, and mixing these up is a common mistake. Systemd analyze blame and critical chain show which units slow down the boot. Each service lives in its own control group, so systemd can limit its memory and CPU, and when you stop a service every one of its processes is stopped. Systemd analyze security gives each service a score for how well it is sandboxed. Secure Boot checks digital signatures at each stage, and a T P M chip can keep disk keys locked unless the boot was untouched. Historically, Linux moved from simple numbered init scripts to systemd’s dependency based, parallel start, and today researchers work on single signed boot images and on virtual machines that boot in a fraction of a second.
