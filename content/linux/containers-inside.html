Common mistake
Containers share the host’s kernel. A container cannot run a different kernel, a kernel bug can be a way out of every container, and a container built for x86-64 does not run on ARM. Virtual machines each run their own kernel, which is stronger isolation at a higher cost.
A container is not a small virtual machine. It is an ordinary Linux process that the kernel shows a different view of the system. Namespaces give it its own process ids, its own network, its own host name and its own list of mounts. A root file system from an image gives it its own programs and libraries. Cgroups limit how much C P U and memory it may use, capabilities take away most of root’s powers, and seccomp blocks dangerous system calls. Choose namespaces in the animation and see what the process inside sees. Remember that all containers on a machine share one kernel.

busybox is one static program that acts as sh, ps, ls, ip and hundreds more, so one file makes a working root file system. Inside, the namespace links show different inode numbers than outside, which proves they are new namespaces. The shell is PID 1, ps lists only the two processes of the container, ip link shows only lo, switched off, and ls / shows only bin, proc and the script. The host name box exists only inside: the last line counts 0 matches outside. Real runtimes do the same steps, use pivot_root instead of chroot so the old root cannot be reached, and add cgroups, capabilities and seccomp.
You can build a container with two commands. Unshare starts a program in new namespaces, and chroot gives it a new root folder. In the demo, busybox, a single program that acts as hundreds of commands, fills a tiny root file system. Inside the container the shell is process one, ps sees only two processes, the network has only an unused loopback, and the root folder has only bin and proc. The host name box exists only inside. The links in slash proc slash P I D slash n s identify each namespace by an inode number, so you can compare them inside and outside. Nsenter does the opposite of unshare: it joins the namespaces of a running process, which is how you debug a container with the host’s tools.

Images and overlayfs

A container image is a stack of read-only layers, each a set of file changes, for example the base system, then the installed packages, then your app. When a container starts, overlayfs joins the layers into one tree and puts a thin writable layer on top.

Join two folders with overlayfs, change, delete and add filesRun for real on Linux while this page was built
cd "$(mktemp -d)"
mkdir lower upper work merged
echo base > lower/a.txt
echo keep > lower/b.txt
mount -t overlay overlay -o lowerdir=lower,upperdir=upper,workdir=work merged
echo changed > merged/a.txt
rm merged/b.txt
echo new > merged/c.txt
ls merged
a.txt
c.txt
cat lower/a.txt
base
ls -l upper
total 8
-rw-r--r-- 1 root root    8 Nov 24 05:03 a.txt
c--------- 2 root root 0, 0 Nov 24 05:03 b.txt
-rw-r--r-- 1 root root    4 Nov 24 05:03 c.txt
umount merged
merged shows the joined view. Changing a.txt copies it up into upper first (copy up), so the lower layer still says base. Deleting b.txt cannot touch the read-only lower layer, so overlayfs puts a whiteout in upper: a character device with the numbers 0, 0, which hides the lower file. The new c.txt exists only in upper. Docker’s overlay2 driver keeps image layers as lower folders and each container’s changes as its upper folder, which is why docker diff can list them.
Image practiceWhy
put rarely changing steps first in the Dockerfilelayers are cached and shared, so a change rebuilds only the layers after it
delete temporary files in the same RUN stepa file deleted in a later layer still takes space in the earlier one, hidden by a whiteout
use small base images (alpine, distroless, ubuntu minimal)fewer files to download and fewer packages with security holes
keep data in volumes, not in the writable layerthe writable layer disappears with the container
A container image is a stack of read only layers, each holding the files that one build step added or changed. Overlay f s joins them into one tree and adds a writable layer on top for the running container. In the demo, changing a file copies it up into the upper layer first, so the lower layer stays untouched. Deleting a file that lives in a lower layer leaves a whiteout, a special device file that hides it. That is why a file deleted in a later build step still makes the image bigger. Put steps that rarely change first, and clean up in the same step that made the mess.

cgroups: limits for CPU, memory and processes

cgroup v2 on Ubuntu 24.04The general form
/sys/fs/cgroup/                    one tree, all controllers
├── system.slice/                  services
│   ├── ssh.service/
│   └── docker-4f2c….scope/        a container
│       ├── cgroup.procs           PIDs in this group
│       ├── memory.max             hard memory limit
│       ├── memory.current         memory in use now
│       ├── cpu.max                "50000 100000" = half a CPU
│       ├── pids.max               the most processes
│       └── memory.events          oom_kill counter
└── user.slice/                    login sessions
Every process belongs to exactly one cgroup, shown in /proc/PID/cgroup as 0::/path. systemd makes a cgroup per service, per login session and per container scope. cgroup v1, still found on older systems and in some containers, has one tree per controller (/sys/fs/cgroup/memory, /sys/fs/cgroup/pids) with other file names.
Stop a runaway with a pids limit of 5Run for real on Linux while this page was built
mkdir /sys/fs/cgroup/pids/demo
echo 5 > /sys/fs/cgroup/pids/demo/pids.max
bash -c 'echo $$ > /sys/fs/cgroup/pids/demo/cgroup.procs
for i in 1 2 3 4 5 6; do sleep 2 & done
wait' 2>&1 | sort | uniq -c
      2 bash: fork: retry: Resource temporarily unavailable
cat /sys/fs/cgroup/pids/demo/pids.max
5
sleep 2
rmdir /sys/fs/cgroup/pids/demo
The bash and its first four sleeps fill the limit of 5. Every further fork fails with “Resource temporarily unavailable” (EAGAIN), bash retries, and the last sleeps start only when earlier ones end. A fork bomb inside such a group cannot take the machine down. This build container has the older v1 layout, so the folder is /sys/fs/cgroup/pids. On Ubuntu 24.04 the same file pids.max sits in the group’s folder in the one v2 tree.

Cgroups, short for control groups, put processes into groups and limit what each group may use: C P U time, memory, the number of processes and disk I O. On Ubuntu twenty four point zero four there is one tree under slash sys slash f s slash cgroup, and systemd makes a group for every service, every login and every container. Files such as memory dot max, c p u dot max and p i d s dot max hold the limits. In the demo, a group with a limit of five processes stops a burst of forks with resource temporarily unavailable. That is how one container cannot eat all the memory or start a fork bomb that freezes the host.

Capabilities, seccomp and rootless containers

Linux splits root’s power into about 40 capabilities, such as CAP_NET_BIND_SERVICE (use ports below 1024), CAP_NET_RAW (raw sockets, ping), CAP_CHOWN or CAP_SYS_ADMIN (mounts and many other things). A process has sets of them, shown in /proc/PID/status as hex masks, and a program file can carry some (file capabilities).

Give one program one capability instead of rootRun for real on Linux while this page was built
getcap /usr/bin/ping
/usr/bin/ping cap_net_raw=ep
capsh --decode=0000000000000400
0x0000000000000400=cap_net_bind_service
ip netns add lab
ip -n lab link set lo up
cp /usr/bin/python3.12 /usr/local/bin/pyweb
ip netns exec lab sudo -u learner python3 -c 'import socket; socket.socket().bind(("127.0.0.1", 80))' 2>&1 | tail -n 1
PermissionError: [Errno 13] Permission denied
setcap cap_net_bind_service=+ep /usr/local/bin/pyweb
getcap /usr/local/bin/pyweb
/usr/local/bin/pyweb cap_net_bind_service=ep
ip netns exec lab sudo -u learner /usr/local/bin/pyweb -c 'import socket; socket.socket().bind(("127.0.0.1", 80)); print("bound to port 80")'
bound to port 80
sudo -u learner grep CapEff /proc/self/status
CapEff:	0000000000000000
rm /usr/local/bin/pyweb
ip netns delete lab
ping on Ubuntu 24.04 carries cap_net_raw instead of being SUID root. capsh --decode turns a hex mask into names. As learner, Python may not bind port 80 (PermissionError), but a copy of the Python program with the file capability cap_net_bind_service may, with no other root power. (The test runs in a network namespace so it touches no real port 80.) A normal user’s effective set is all zeros. A root shell on a normal host shows 000001ffffffffff, all 41 bits set, while a container usually gets a much smaller set because the runtime drops the dangerous ones.
OptionEffect

rootless Podman or Dockera user namespace maps root inside to your own user outside, using /etc/subuid and /etc/subgid
Who does what when you type docker run nginx
  1. The docker client sends the request to the dockerd daemon over /run/docker.sock (anyone who can write that socket is effectively root).
  2. dockerd asks containerd to pull the image layers and prepare an overlayfs snapshot.
  3. containerd starts a shim, which calls runc with an OCI bundle: a config.json with namespaces, cgroups, capabilities, seccomp, mounts, plus the root file system.
  4. runc makes the namespaces and cgroup, switches root with pivot_root, drops capabilities, loads seccomp and finally runs execve on nginx, which becomes PID 1 of the container. runc then exits.
  5. Podman does the same without a daemon, and Kubernetes talks to containerd or CRI-O through the CRI interface.
Root on Linux is really a bundle of about forty capabilities, such as binding to ports below one thousand twenty four, or using raw sockets. A program can get just one of them instead of full root. On Ubuntu, ping carries the raw socket capability instead of running as root. In the demo, a copy of Python gets the capability to bind low ports, and then the normal user learner can listen on port eighty, with no other powers. Containers use this to drop most of root’s powers even for root inside, add a seccomp filter on system calls, and with user namespaces, root inside a rootless container is just your own user outside. Avoid the privileged flag, which switches all of this off.

Lesson 7 of 7

Containers from school to research

One idea, four depths

A container is a program packed with everything it needs, which runs in its own little room on the computer: it sees only its own files, its own network and its own processes, while sharing the computer’s kernel.

Explain namespaces, cgroups, capabilities, seccomp and overlayfs, read /proc/PID/ns and cgroup, use unshare and nsenter to debug, set limits for containers and services, drop capabilities, run as a normal user, and avoid --privileged and a writable docker.sock.

Platform teams run Kubernetes with resource requests and limits, Pod Security Standards, network policies, rootless and read-only containers, image scanning and signing (Trivy, cosign, SBOMs), and stronger isolation where needed with gVisor (a user space kernel), Kata Containers or Firecracker micro VMs.

Research studies container escapes and kernel attack surface, eBPF based security and observability (Cilium, Falco, Tetragon), WebAssembly as a lighter sandbox, confidential containers in encrypted VMs (AMD SEV, Intel TDX), and the cost of isolation for serverless platforms that start thousands of sandboxes per second.

Real world scenario: the container that could read the host

A team ran a monitoring container with --privileged and the host’s / mounted inside, because “it needed access”. A bug in the tool let an attacker run commands, and with all capabilities and the host files they read SSH keys from the host. In the clean-up, the team listed what the tool really needed: read access to /proc and one capability (CAP_SYS_PTRACE). They ran it with --cap-drop ALL --cap-add SYS_PTRACE, a read-only root file system and no host mounts, and added a policy that rejects privileged containers.

Here is how understanding containers grows. At school you learn that a container is a packed program in its own little room, sharing the computer’s kernel. Professionals know the building blocks, namespaces, cgroups, capabilities, seccomp and overlay layers, and use them to debug and to lock containers down. Platform teams run Kubernetes with limits, security policies, signed images and, where needed, stronger sandboxes such as g Visor or micro virtual machines. Researchers look for container escapes, build security tools with e B P F, and explore WebAssembly and confidential computing as new kinds of sandboxes.
