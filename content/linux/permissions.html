Users, groups and the ls -l mode string

Linux was built for many people sharing one computer, so every file has an owner (a user) and a group. Every person who is not the owner and not in the group counts as others. For each of these three classes the file stores three switches: r read, w write, x execute.

-rw-r--r--Exam favourite
the mode string
First character is the type (- file, d folder, l link). Then three groups of three: owner, group, others.
r = 4, w = 2, x = 1
the numbers
Add the switches of one class to get one digit. rw- is 4 + 2 = 6.
644Exam favourite
the same mode in numbers
Owner rw (6), group r (4), others r (4). The usual mode of a text file.

Remember
Deleting a file is a change to the folder, not to the file. So whether you may delete notes.txt depends on the w and x of its folder, not on the mode of notes.txt.
Linux comes from Unix, and Unix was designed in the nineteen seventies for many people sharing one big computer at a university or company. So from day one, every file needed an answer to the question who may do what with this. The answer is small and clever. Each file has one owner and one group, and everybody else is called others. For each of those three, there are three switches: read, write and execute. When you run ls dash l, you see them as letters, for example r w dash, r dash dash, r dash dash. People also write the same thing as numbers, where read counts four, write counts two and execute counts one. Add them up and you get one digit per class, so the common text file mode is six four four. Once you can read these nine letters, a large part of Linux administration stops being mysterious.
Lesson 2 of 5

How the kernel decides

When a program tries to open a file, the kernel checks only one class, chosen in this order:

The permission check
  1. If you are root, reading and writing are allowed. Executing a file still needs at least one x bit somewhere in its mode.
  2. If you are the owner of the file, only the owner bits count, even if the group or others bits would give you more.
  3. Otherwise, if you are a member of the file’s group, only the group bits count.
  4. Otherwise the others bits count.
  5. To reach the file at all, you also need x on every folder in its path, from / down.
Remember
Because only one class is checked, a file with mode 604 (rw- --- r--) can be read by strangers but not by members of its group. Unusual, but legal.
Folders need x to enterRun for real on Linux while this page was built
mkdir vault
echo secret > vault/key.txt
chmod 600 vault
ls vault
key.txt
cat vault/key.txt
cat: vault/key.txt: Permission denied
cd vault
bash: cd: vault: Permission denied
chmod 700 vault
cat vault/key.txt
secret
With r but no x, ls can read the names in the folder, but nothing inside can be opened and cd is refused. Putting x back fixes both.
Here is the rule the kernel follows every time a program opens a file. First, is this the root user. Root may read and write anything. Second, is this person the owner of the file. If yes, the kernel looks at the owner switches and stops there. Third, is this person a member of the file group. If yes, it looks at the group switches and stops. Otherwise it uses the switches for others. Only one class is ever checked, so the owner cannot borrow rights from the group. There is one more condition that surprises people. To open a file, you need the execute switch on every folder on the way to it. On a folder, execute really means may pass through. That is how a home folder with mode seven five zero keeps other people out, even if a file inside is readable by everyone.

Common mistake
chmod 777 to make an error go away is a classic mistake. It lets every user and every hacked service on the machine change the file. Find which user needs access and give only that.
The command that changes permissions is chmod, short for change mode. You can use it in two ways. With numbers, you give the whole mode at once, such as seven five five for a script. With letters, you describe a change. u plus x means give the owner execute. g o minus w means take write away from group and others. The letter form is safer when you only want to change one thing, because it leaves the other bits alone. Ownership is changed with chown, and only root may give a file to someone else. Otherwise anybody could hand a huge file to a colleague and fill up their disk quota. A useful habit for secrets: SSH refuses to use a private key that other people can read, so key files should be six hundred. When something says permission denied, resist the temptation to type chmod seven seven seven. Work out which user needs which right, and give exactly that.
Lesson 4 of 5

umask and the special bits

New files do not start with random permissions. The program asks for 666 for a file (rw for everyone) or 777 for a folder, and the kernel switches off every bit that is set in your umask. The common umask 022 switches off w for group and others, so files come out as 644 and folders as 755. Some distributions use 002 for normal users, which keeps group write.

mode = request AND NOT umaskExam favourite
umask removes bits
666 with umask 022 gives 644. 777 with umask 077 gives 700.
4000 setuid
run as the file owner
/usr/bin/passwd is rwsr-xr-x and owned by root, so it can write /etc/shadow for you.
2000 setgid
group of the file or folder
On a folder, new files inherit the folder’s group. Perfect for team folders.
1000 sticky
only owners delete
/tmp is drwxrwxrwt: everyone may create files, but only the owner of a file may delete or rename it.

In ls -l the special bits replace the x position: s for setuid or setgid, t for sticky. A capital S or T means the special bit is set but the x under it is not.
Remember
Linux ignores setuid and setgid on scripts that start with #!. Only compiled programs can use them, because a script could be swapped or tricked between the moment the kernel reads it and the moment the interpreter does.
Two last pieces complete the picture. The first is umask. When a program creates a file, it usually asks for read and write for everyone, and the umask removes some of those bits. With the common umask of zero two two, write is removed for group and others, so new files come out as six four four. The second piece is three special bits. Setuid makes a program run with the rights of its owner. That is how the passwd program, owned by root, can update the protected password file for an ordinary user. Dennis Ritchie invented this idea, and Bell Labs received a patent for it in 1979, then placed it in the public domain. Setgid on a folder makes new files inherit the folder group, which keeps team folders tidy. The sticky bit on a shared folder like slash tmp lets everyone create files, but only the owner may delete them.
Lesson 5 of 5

Permissions from school to research

One idea, four depths

Every file has an owner, a group and others, and for each of them read, write and execute switches. chmod changes the switches, chown changes the owner, and root can do almost anything. Keep secrets at 600 and never use 777.

Unix discretionary access control stores 12 mode bits in the inode: 9 rwx bits plus setuid, setgid and sticky. Access is checked against the effective user and group IDs of the process, using exactly one class. umask filters the mode requested in open() and mkdir(). Directory x is search permission.

Modern Linux splits root into about 40 capabilities (capabilities(7)), so a web server can get only CAP_NET_BIND_SERVICE to use port 80. POSIX ACLs (getfacl, setfacl, shown as a + after the mode) give rights to extra users and groups. Mandatory access control in SELinux and AppArmor adds rules that even the owner cannot override, and setuid binaries are a classic source of privilege escalation bugs, so distributions keep their number small.

Research compares discretionary, mandatory and role based models (Bell and LaPadula 1973 for secrecy, Biba 1977 for integrity), studies capability systems such as Capsicum in FreeBSD, and measures how often real systems are misconfigured. Container isolation builds on these ideas with user namespaces, where uid 0 inside a container maps to an unprivileged user outside, a topic in the advanced section.

Real world scenario: the leaked key

A developer copies a cloud SSH key to a shared server and gets WARNING: UNPROTECTED PRIVATE KEY FILE! followed by a refusal to use the key. ssh is right: the file was 644, readable by every user on the machine. chmod 600 ~/.ssh/id_ed25519 fixes it, and chmod 700 ~/.ssh protects the folder.

The nine switches you learned are the base of a much bigger security story. The full mode has twelve bits, including the three special ones, and they live inside the file inode. On modern Linux, the all powerful root user is actually split into about forty separate capabilities, so a web server can be given only the right to open port eighty and nothing else. When nine switches are not enough, access control lists let you give rights to extra people, and you can spot them by a plus sign after the mode in ls dash l. On top of that, security modules like SELinux on Red Hat systems and AppArmor on Ubuntu add rules that even a file owner cannot break. Researchers have studied these models since the nineteen seventies, and the same ideas now protect every container running in the cloud.
