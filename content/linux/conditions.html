Lesson 1 of 5

if, elif and else: decisions by exit status

if runs a command and looks only at its exit status. Status 0 means true and runs the then part. Anything else tries the next elif, then else. The block ends with fi, which is if backwards.

if, elif and elseThe general form
if COMMAND; then
  ...            # runs when COMMAND exits with 0
elif OTHER; then
  ...            # runs when COMMAND failed and OTHER succeeded
else
  ...            # runs when everything above failed
fi
Any command can be the conditionRun for real on Linux while this page was built
if grep -q apple fruits.txt; then
  echo "we have apples"
fi
we have apples
if ! grep -q pear fruits.txt; then
  echo "no pears today"
fi
no pears today
if mkdir reports 2>/dev/null; then
  echo "made reports"
else
  echo "reports already exists"
fi
made reports
mkdir reports 2>/dev/null && echo "made it" || echo "could not make it"
could not make it
count=$(grep -c apple fruits.txt)
if [ "$count" -ge 3 ]; then
  echo "plenty: $count"
elif [ "$count" -ge 1 ]; then
  echo "a few: $count"
else
  echo "none"
fi
plenty: 3
grep -q gives only a status, which is perfect for if. ! turns success into failure and back. The second mkdir failed because the folder now exists. The fruit list has the word apple on 3 lines, so the first branch ran.
Common mistake
a && b || c is not a full if. If b itself fails, c runs too. Use a real if when the middle command can fail.
The if statement in bash works differently from most languages. It does not test a true or false value. It runs a command and looks at the exit status. Zero means success, so the then part runs. Any other status moves on to the next elif, and finally to else. The block always ends with the word fi, which is if spelled backwards. Because any command can be the condition, you can write if grep dash q apple fruits dot t x t, and the block runs only when the word is found. An exclamation mark in front reverses the result. You will often see the short form with double ampersand and double bar. It reads well, but it has a trap: if the middle command fails, the last one runs as well. So use a proper if whenever the middle command might fail.

test and [ ]: files, strings and numbers

= compares text, so 10 and 10.0 differ, while -eq compares numbers. The unquoted empty variable vanished, so test saw only = yes and complained. With quotes it worked and simply returned 1. Status 2 means test itself could not understand the question.
Common mistake
Write [ "$x" = y ], always with quotes. Use = and != for text, -eq and -lt for whole numbers. [ 9 > 10 ] is not a comparison at all: it redirects output into a file called 10.
The test command checks a single condition. You can write it as the word test, but almost everyone uses the square bracket form. The opening bracket is actually the name of a command, so the spaces around it are required, just like spaces between any command and its arguments. There are three families of checks. File checks such as dash f for a regular file, dash d for a folder and dash x for executable. String checks: dash z for empty, dash n for not empty, and equals and not equals. Number checks use letters: dash e q for equal, dash l t for less than and dash g t for greater than. Mixing them up is a classic bug, because equals compares text, so ten and ten point zero are different. Because the bracket is a normal command, its arguments go through word splitting first. An empty variable without quotes simply disappears, and test then sees the wrong number of arguments. The animation shows exactly how that happens. The cure is always the same: put double quotes around every variable inside single brackets.

The bash way: [[ ]] and (( ))

bash adds two safer forms. [[ ... ]] is a keyword, not a command, so there is no word splitting and no globbing inside it. It also understands patterns, regular expressions and && and ||. (( ... )) evaluates whole number arithmetic with C-like operators and is true when the result is not 0.

count=34

Inside [[ ]] the empty variable caused no error. Patterns after == are case sensitive, so the lower-cased copy ${file,,} matched. Quoting the right side turns the pattern into plain text. BASH_REMATCH holds the whole match at index 0 and each bracket group after it. (( )) can also assign, and a result of 0 means false.
Remember
Use [[ ]] and (( )) in bash scripts. Use [ ] only when the script must run under plain sh (#!/bin/sh), because dash has no [[ ]].
Bash gives you two better tools for conditions. Double square brackets are a keyword that the shell understands directly, so it does not split variables or expand stars inside. That makes empty and spaced values safe, even without quotes. Inside double brackets, double equals compares with a pattern, so star dot j p g matches any file ending in dot j p g. Equals tilde matches a regular expression, and every bracket group you capture lands in an array called BASH REMATCH. You can also join tests with double ampersand and double bar inside the brackets. For numbers, double parentheses let you write maths the way you learned it at school, with greater than, less than, and the percent sign for the remainder. The result counts as true when it is not zero. One caution: these are bash features, so a script that starts with hash bang slash bin slash s h cannot use them.
Lesson 4 of 5

case: choose by pattern

When one value can take many forms, case is clearer than a long elif chain. bash tries the patterns from top to bottom and runs the first arm that matches.

caseThe general form
case "$answer" in
  y|yes|Y)  echo "go on" ;;
  n*|N*)    echo "stop" ;;
  "")       echo "no answer" ;;
  *)        echo "please answer y or n" ;;
esac
Arm endingEffect
;;stop after this arm (the normal case)
;&also run the next arm without testing its pattern (bash 4 and later)
;;&keep testing the following patterns and run any that match (bash 4 and later)
case in a small service scriptRun for real on Linux while this page was built
cat > svc.sh <<'EOF'
#!/bin/bash
case "$1" in
  start)        echo "starting the service" ;;
  stop)         echo "stopping the service" ;;
  restart)      echo "stopping"; echo "starting" ;;
  status|st)    echo "running" ;;
  *)            echo "usage: $0 {start|stop|restart|status}" >&2; exit 2 ;;
esac
EOF
bash svc.sh start
starting the service
bash svc.sh st
running
bash svc.sh reload; echo "status $?"
usage: svc.sh {start|stop|restart|status}
status 2
for f in a.jpg b.TXT c.tar.gz notes; do
  case $f in
    *.jpg|*.png)   echo "$f: image" ;;
    *.[tT][xX][tT]) echo "$f: text" ;;
    *.tar.*)       echo "$f: archive" ;;
    *)             echo "$f: unknown" ;;
  esac
done
a.jpg: image
b.TXT: text
c.tar.gz: archive
notes: unknown
case abc in a*) echo "starts with a" ;;& *c) echo "ends with c" ;; esac
starts with a
ends with c
The script picks one arm by its first argument, and the catch-all *) prints a usage message to stderr with status 2. With ;;& the second pattern was tested too, so both lines printed.
The case statement chooses between many possibilities by pattern. You give it one value, then a list of arms. Each arm starts with a pattern and a closing parenthesis, followed by the commands, and ends with two semicolons. Bash tests the patterns from the top and runs only the first arm that matches, so put specific patterns first and the catch all star last. A vertical bar lets one arm accept several patterns, such as y or yes. The patterns are the same wildcards you use for file names, so star dot j p g matches every JPEG name. That makes case the natural choice for service scripts that accept start, stop and restart, and for sorting files by type. Two less common endings exist: semicolon ampersand runs the next arm as well, and two semicolons with an ampersand keeps testing the remaining patterns.
Lesson 5 of 5

Decisions from school to research

One idea, four depths

if runs a command and checks whether it worked. [ ] asks a question about a file, some text or a number. case picks one action from a list of patterns. fi and esac close the blocks.

The condition of if, while and until is a list of commands, and only the status of the last one counts. test decides by the number of arguments it receives, which is why unquoted empty variables break it. [[ ]] and (( )) are parsed by bash itself, so their contents are not split or globbed.

Inside [[ ]], quoting the right side of == or =~ makes it literal text, so keep a regular expression in a variable, re="^[0-9]+$", and write [[ $x =~ $re ]]. The bash option nocasematch makes [[ ]] and case ignore letter case. A number in (( )) with a leading 0 is octal, so (( 08 )) is an error, while 10#08 forces base 10. errexit (set -e) ignores failures inside if conditions and in all but the last command of && and || lists.

The POSIX test rules by argument count were written to make test predictable, but parsing operators and operands from the same words stays ambiguous, for example in [ "$a" = -n ]. Research on shell semantics such as Smoosh and studies of real-world scripts report condition errors and quoting mistakes among the most common bugs, and linters such as ShellCheck include dedicated checks (SC2070, SC2071, SC2086) for them.

Real world scenario: the deployment gate

A release script must stop when the disk is nearly full or when the branch is not main. It uses [[ $(git branch --show-current) == main ]] || { echo "deploy only from main" >&2; exit 1; } and (( usage < 90 )) on the percentage that df reports. A case statement maps the first argument to staging or production, with a usage message in the *) arm. Every rule is a single readable line, and a wrong value stops the deploy before anything changes.

Here is the expert view of decisions. The condition of if is really a list of commands, and only the status of the last one matters. The test command decides what to do by counting its arguments, which explains every unary operator expected message you will ever see. Double brackets and double parentheses are read by bash itself, so their contents are never split or globbed. A few traps remain. If you quote the right side of a regular expression match, it becomes plain text, so store the expression in a variable instead. Numbers with a leading zero are octal inside double parentheses, so eight with a leading zero is an error unless you write ten hash before it. And the set dash e option ignores failures inside conditions, which surprises many people. Linters such as ShellCheck carry dedicated warnings for these mistakes, because studies of real scripts find them again and again.
