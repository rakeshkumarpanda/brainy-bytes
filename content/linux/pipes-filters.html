The pipe: one command feeds the next

The pipe | connects the stdout of one command to the stdin of the next. No temporary file is needed: data flows straight from one program into the other while both run.

A | BExam favourite
pipe
The output of A becomes the input of B. Errors (stream 2) still go to the terminal.
A | B | C | D
pipeline
Any number of commands. Each one does a small job.
A 2>&1 | B
errors too
Send stderr into the pipe as well. Bash also accepts A |& B.

Remember
A command that reads a file name never needs cat in front of it: sort fruits.txt does the same as cat fruits.txt | sort with one process less. cat is still handy to start a long pipeline in a readable way.
The pipe is the single most famous idea in Unix. The vertical bar takes the output of one command and feeds it directly into the next one, with no file in between. Doug McIlroy at Bell Labs pushed for this for years, and Ken Thompson added pipes to Unix in 1973, reportedly in a single night. Overnight, the small tools that already existed could be combined into new ones. McIlroy later summed up the Unix way of thinking: write programs that do one thing and do it well, and write programs that work together. A pipeline is exactly that. ls lists, head keeps the first lines, sort sorts, wc counts. None of them knows about the others, yet together they answer questions nobody planned for. Notice that error messages are not sent down the pipe. They still go to your screen, so you see problems while the data keeps flowing.

Remember
sort uses the rules of your language setting (locale), which can put capitals and small letters together. Scripts that need the same order everywhere run LC_ALL=C sort, which compares plain byte values.
sort and uniq are a famous pair. sort puts lines in order. By default it compares text from the left, letter by letter, which surprises people with numbers: one hundred comes before twenty five, because the character one comes before two. Add dash n to sort by numeric value, dash r to reverse, and dash k to pick a column. uniq removes repeated lines, but only when the repeats are next to each other. That is why you almost always see sort followed by uniq. With dash c, uniq counts how many times each line appeared. Then a final sort dash r n puts the most common at the top. This short recipe, sort, uniq dash c, sort dash r n, head, is used every day to find the most frequent visitors in a web log, the commonest errors, or the most popular products.

Common mistake
cut uses exactly one character as the separator. Columns separated by several spaces, as in ps or ls -l output, need squeezing with tr -s first, or awk, which is covered two chapters later.
cut and tr are small tools that do one job each. cut picks columns. Tell it the separator with dash d and the field numbers with dash f, and it pulls out, for example, just the names from a spreadsheet file, or the user names from the system password file. tr translates characters one for one. tr with a to z and capital A to Z shouts everything in capitals. With dash d it deletes characters, and with dash s it squeezes repeated characters into one. Put them together with sort and uniq and you can count word frequencies in a whole book with one line. In 1986 the computer scientist Donald Knuth wrote a long, carefully crafted program for exactly that task, for a magazine column. Doug McIlroy reviewed it and showed that a six command Unix pipeline gave the same answer. Both approaches have their place, but the story shows how much power small tools have when combined.

Did the pipeline work: exit status and pipefail

Every command ends with an exit status, a number from 0 to 255. 0 means success, anything else means a problem. The shell keeps the last one in $?. A pipeline reports the status of its last command only, which can hide an early failure.

CommandWhat it doesExample
echo $?Status of the last command or pipelinels nothere; echo $?
echo ${PIPESTATUS[@]}Bash: the status of every command in the last pipelinefalse | true; echo ${PIPESTATUS[@]}
set -o pipefailThe pipeline fails if any command in it failsset -o pipefail

Without pipefail the pipeline reports 0 because sort succeeded, even though cat failed with status 1. yes prints y for ever, but stops quietly once head has its three lines, because writing to a closed pipe ends it with the signal SIGPIPE.
How do you know whether a command worked. Every command finishes with a number called its exit status. Zero means success, and any other number means something went wrong. The shell stores it in dollar question mark. Pipelines have a trap. Their status is the status of the last command only. If cat fails because a file is missing, but sort after it runs happily on empty input, the whole pipeline reports success. In a backup script that can mean a failure nobody notices for months. Bash offers two fixes. The PIPESTATUS array holds the status of every command in the last pipeline, and set dash o pipefail makes the pipeline fail when any part fails. Careful scripts turn pipefail on at the top, as you will see in the scripting section.
Lesson 5 of 5

Pipes from school to research

One idea, four depths

The | symbol sends the output of one command into the next. sort orders lines, uniq -c counts repeats, cut picks columns, tr changes letters and wc -l counts lines. Joined together they answer questions in one line.

A pipeline connects stdout of each command to stdin of the next and runs all of them at the same time. Filters read stdin and write stdout. The pipeline status is that of the last command unless pipefail is set, and PIPESTATUS holds every status.

The shell calls pipe() to get a pair of descriptors, forks one child per command and uses dup2() to wire them. The kernel buffers data in the pipe, 65,536 bytes by default on Linux, and blocks a fast writer until the reader catches up, which gives natural flow control. When the reader exits, the next write sends SIGPIPE to the writer. Bash runs each part of a multi command pipeline in a subshell, so echo hi | read x sets x only in a child, unless shopt -s lastpipe is used.

The pipe and filter style influenced software architecture (Shaw and Garlan), stream processing systems such as Apache Kafka and Apache Flink, and dataflow languages. Research on shell performance, such as the PaSh project (EuroSys 2021), automatically turns ordinary pipelines into parallel ones that use many CPU cores while giving the same output.

Real world scenario: the slow website

A site slows down and the engineer suspects a single visitor. One line answers it: cut -d" " -f1 access.log | sort | uniq -c | sort -rn | head -n 5. It prints the five IP addresses with the most requests. One address with 400,000 requests in an hour stands out, and a firewall rule blocks it.

Inside the computer, a pipe is a small buffer in the kernel with two ends, one for writing and one for reading. The shell creates the pipe, starts both programs at the same time, and connects the writer to one end and the reader to the other. On Linux the buffer holds sixty four kilobytes. If the writer is faster, the kernel pauses it until the reader catches up, so memory never fills up. When the reader stops early, as head does, the writer receives a signal called SIGPIPE and ends quietly. The pipe and filter idea spread far beyond the shell. Large data systems such as Apache Kafka are built on the same thinking: small steps connected by streams. Researchers have even built tools, such as the PaSh project presented in 2021, that take an ordinary shell pipeline and run it in parallel on many processor cores automatically.
