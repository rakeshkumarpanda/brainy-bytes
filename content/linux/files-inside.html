Names, inodes and data

A file on Linux has three parts. Its name is an entry in a folder. The entry points to an inode, a numbered record with everything else about the file. The inode points to the data blocks with the content.

An inode holdsAn inode does not hold
the type and the permission bitsthe name, which lives in the folder
the owner and group (as numbers)the path, a file can have several
the size and the block or extent list
the times: access, modify, change, birth
the link count: how many names point to it

The first column of ls -i is the inode number, and the first letter of the mode is the type: - regular file, d directory, l symbolic link, p named pipe (FIFO), c character device such as /dev/null, b block device such as /dev/sda, s socket. A new folder starts with 2 links, its name in the parent and its own . entry, and every subfolder adds one more for its .. entry. The root folder of an ext4 file system is always inode 2, which is what / shows. Inode numbers are only unique inside one file system, and /home shows a low number too because it is a separate file system in the build container.

mkfs.ext4 -N 64 makes a file system with only 64 inodes. The first 11 are reserved (2 is the root folder, 11 is lost+found), so touch fails at the 54th file with “No space left on device”, although df -h shows 56M free. df -i shows 100 % of inodes used. A file on Linux is more than its name. The name is only an entry in a folder, and it points to an inode, a numbered record that holds everything else: the type, the owner, the permissions, the size, the times, and where the data is stored. The inode also counts how many names point to it. You can see inode numbers with ls dash i and stat. Every file system has a fixed number of inodes, set when it is made. In the demo, a tiny file system runs out of inodes after fifty three files, while the disk is still almost empty, and touch reports no space left on device. Df dash i shows the inode usage, and it is the first thing to check when that error appears on a disk with free space.

notes.txt and copy share one inode with link count 2, so text added through copy appears in notes.txt. After rm notes.txt the data is still there under the name copy. The symbolic link stores only the path notes.txt, so it now dangles and cat fails. find -xtype l finds such broken links. A hard link to /dev/shm fails, because it is another file system (tmpfs). The last line fails for a different reason: Ubuntu sets fs.protected_hardlinks = 1, so you may only hard link files you own or can read and write, which stops tricks with links to root’s files in shared folders.

Common mistake
A relative symbolic link is resolved from the folder the link is in, not from your current folder. ln -s ../shared/config.yml app/config.yml works, ln -s shared/config.yml app/config.yml from the parent folder makes a link that points to app/shared/config.yml.
There are two kinds of links. A hard link is a second name for the same inode. Both names are equal, a change through one is visible through the other, and the data stays until the last name is gone. Hard links only work inside one file system and not for folders. A symbolic link is a tiny file of its own that stores a path. The kernel follows that path whenever a program opens the link, so symbolic links can point to folders and to other disks. But if the target is deleted or moved, the link dangles. In the demo you see the shared inode number, the link count of two, a dangling link, and two refused hard links: one to another file system, and one to a file that belongs to root.
Lesson 3 of 6

Open files: descriptors and deleted files

Three tables behind every open file
  1. Each process has a file descriptor table: small numbers 0, 1, 2, 3 and so on. You see it in /proc/PID/fd.
  2. Each descriptor points to an open file description in the kernel, which holds the current offset and the open flags (read, write, append). After fork, or after dup2, two descriptors share one description, and therefore one offset. That is why the lines of a parent and a child do not overwrite each other in a shared log.
  3. The description points to the inode. The kernel counts open descriptions as well as names, and frees the data only when both reach zero.
A file deleted while a program still writes itRun for real on Linux while this page was built
python3 -c 'import time; f = open("big.log", "w"); f.write("x" * 5000000); f.flush(); time.sleep(20)' &
sleep 1
ls -l big.log
-rw-r--r-- 1 learner learner 5000000 Nov 24 04:48 big.log
rm big.log
ls -l /proc/$!/fd | grep big
l-wx------ 1 learner learner 64 Nov 24 04:48 3 -> /home/learner/big.log (deleted)
lsof -p $! 2> /dev/null | grep deleted
python3 3086 learner    3w   REG  254,0  5000000 640934 /home/learner/big.log (deleted)
cp /proc/$!/fd/3 rescued.log
ls -l rescued.log
-rw-r--r-- 1 learner learner 5000000 Nov 24 04:48 rescued.log
kill $!
After rm the name is gone, but the Python process still has the file open on descriptor 3, so the 5 MB stay on the disk and df does not go down. /proc/PID/fd shows the link with “(deleted)”, and lsof shows the same with the size and the inode number. Copying from /proc/PID/fd/3 rescues the content, which has saved many deleted databases and logs. On a server, sudo lsof +L1 lists every open file whose link count is 0.

Remember
“Too many open files” (EMFILE) means a process hit its descriptor limit, often 1024. Check ls /proc/PID/fd | wc -l to see whether it leaks descriptors, and raise the limit in the service with LimitNOFILE= only if the program really needs that many.
When a program opens a file, the kernel gives it a small number called a file descriptor. Zero, one and two are standard input, output and error, and new files get three, four and so on. Slash proc slash P I D slash f d shows every descriptor of a process. The kernel keeps a file’s data as long as any name points to it or any process has it open. That is why deleting a huge log that a service still writes does not free any space. In the demo, the deleted file still shows up in slash proc with the word deleted, lsof finds it, and copying from slash proc rescues the content. To free the space safely, empty the file in place instead of deleting it, or restart the service.

The VFS, the page cache and fsync

What happens to a write()
  1. The VFS (virtual file system) is the common layer that turns open, read and write into calls of the right file system driver: ext4, xfs, vfat, tmpfs, NFS, procfs and so on.
  2. write() copies your data into the page cache in RAM and returns at once. The pages are now dirty: newer in memory than on disk.
  3. Kernel flusher threads write dirty pages to the disk later, after about 30 seconds (vm.dirty_expire_centisecs = 3000) or sooner when too much memory is dirty (vm.dirty_background_ratio and vm.dirty_ratio).
  4. fsync(fd) makes the kernel write a file’s dirty data and metadata to the disk now and waits until the disk confirms it. sync does that for everything. Databases call fsync before they tell you a transaction is saved.
  5. Reads go through the same cache. A file read twice comes from RAM the second time, which is why the buff/cache column of free is large on a healthy server. That memory is given back as soon as programs need it.
SituationWhat it means for you
power loss right after cpthe copy may be incomplete unless you ran sync. Pull a USB stick only after umount or eject
a program says “saved”only true after fsync. Editors and databases do it, simple scripts usually do not

benchmarking a diskthe cache makes reads look too fast. Use fio with --direct=1, or drop the cache first with echo 3 | sudo tee /proc/sys/vm/drop_caches on a test machine only

Writing a file safelyThe general form
write new content to  config.yml.tmp
fsync(config.yml.tmp)          the data is on the disk
rename(config.yml.tmp, config.yml)   atomic switch
fsync(the folder)              the new name is on the disk
This is how editors, package managers and databases avoid half written files after a crash. In shell scripts, mv on one file system is the rename step, and the sync command can do the fsync steps.
Under every file system sits the V F S, the virtual file system, which gives all of them the same open, read and write calls. When a program writes, the data first lands in the page cache in memory, and write returns at once. The kernel writes these dirty pages to the disk a little later, usually within thirty seconds. This makes Linux fast, but it means a power cut can lose the last seconds of writes. Fsync tells the kernel to write one file to the disk now and to wait until it is safe, and sync does it for everything. Reads use the same cache, which is why Linux seems to use a lot of memory for buff slash cache. That memory is handed back the moment programs need it.

Lesson 6 of 6

Files from school to research

One idea, four depths

A file’s name is like a label on a box. The box (the inode) holds the details and points to the contents. You can stick several labels on one box (hard links) or write down where another box is (symbolic links).

Read inode numbers and link counts, use hard and symbolic links on purpose, check df -i when “No space left” appears on a disk with space, find deleted but open files with lsof +L1, empty logs with : > instead of rm, and write files safely with a temp file, fsync and rename.

Storage engineers plan inode counts (mkfs -N or -i) for millions of small files, use reflinks on XFS and Btrfs (cp --reflink) that share data blocks until one copy changes, deduplicate backups with hard links (rsync --link-dest), tune the dirty page settings for write heavy servers, and debug with debugfs, xfs_db and filefrag.

Research covers crash consistency (studies such as “All File Systems Are Not Created Equal”, OSDI 2014, found many applications that lose data because they rename without fsync), copy on write file systems (Btrfs, ZFS, bcachefs), file systems for persistent memory, and user space file systems with FUSE and io_uring.

Real world scenario: the disk that was full with space left

A PHP web shop suddenly showed errors, and logs said “No space left on device”. df -h showed 40 % free. A colleague ran df -i: 100 % of inodes were used. A broken cleanup job had left 6 million session files in /var/lib/php/sessions. Deleting the old files with find /var/lib/php/sessions -type f -mmin +1440 -delete freed the inodes, and the team fixed the cleanup timer and added an inode alert to the monitoring.

Here is how understanding files grows. At school you learn that a name is a label on a box, and that one box can have several labels. Professionals read inode numbers and link counts, check d f dash i when a disk with free space says it is full, find deleted files that are still open, and write important files safely with fsync and rename. Storage engineers plan inode counts, share data between copies with reflinks, and build backups from hard links. Researchers study how programs lose data after crashes and design new copy on write file systems.
