enp0s3 is the network card. Modern names describe where the card sits (en for Ethernet, p0s3 for PCI bus 0, slot 3), so they stay the same across reboots. The route for 192.168.1.0/24 is added by the kernel when the address is set. The default route sends everything else to the router. The addresses 198.51.100.0/24 and 203.0.113.0/24 used for shop.lab in this course are reserved for documentation (RFC 5737), so they never clash with real servers.
To talk on a network, a machine needs an address, a subnet, a gateway and a name server. The address, such as one nine two dot one six eight dot one dot fifty, is its number. The slash twenty four after it says that the first three numbers name the network, so every address that starts with one nine two dot one six eight dot one is a neighbour that can be reached directly. Everything else goes to the default gateway, the router. A D N S server turns names into addresses, and on Ubuntu a local helper called systemd resolved answers at one two seven dot zero dot zero dot five three. Finally, a port number picks the program on the other machine: twenty two for s s h, eighty for web pages, four four three for secure web pages. A network namespace is a separate network stack inside one Linux kernel, the same feature that gives every container its own network. A veth pair is a virtual cable. ip netns exec runs a command inside a namespace, and the little function pc saves typing. Before ip link set up the interface is DOWN and has no address, and eth0@if2 means the other end of the cable is interface number 2 in the other namespace. Setting the address also adds the route for 192.168.50.0/24, so the other side can be reached directly, and ARP fills the neighbour table with its MAC address. There is no default route, so 10.9.9.9 is unreachable.
Common mistake
Changes made with ip addr, ip link and ip route are lost at the next reboot. That is useful for tests, and the permanent settings go into netplan or NetworkManager (lesson 7). On a remote server, never take down the interface you are connected through.
The ip command shows and changes the network settings of a Linux machine. Ip dash b r addr gives a short list of interfaces and their addresses, and ip route shows the routing table, which decides where each packet goes. Ip route get and an address tells you exactly which route that address would use. Ip neigh shows the neighbour table, the M A C addresses that A R P has found on the local network. With sudo you can add addresses and routes and switch interfaces on and off, but these changes only last until the next reboot. Ping sends small echo requests and shows how long each answer takes, the first test for any connection. In the demo, two network namespaces act as two machines joined by a virtual cable, which is exactly how containers get their own networks.

Routing between networks

A machine sends a packet straight to a neighbour in its own subnet. For any other address it uses the most specific matching route, and the default route (0.0.0.0/0) matches everything. A router is a machine with interfaces in two networks that forwards packets between them.

Names: /etc/hosts, DNS and systemd-resolved

Programs ask the C library to resolve a name. The order is set by the hosts: line of /etc/nsswitch.conf, on Ubuntu Server hosts: files dns: first /etc/hosts, then DNS. Desktops add mdns4_minimal for .local names. On Ubuntu, DNS questions go to systemd-resolved at 127.0.0.53, which asks the real DNS servers given by DHCP or netplan and caches the answers.

dnsmasq is a small DNS server, here answering for the made-up zone shop.lab only. ip netns exec mounts /etc/netns/pc/resolv.conf and /etc/netns/pc/hosts over the real files for the commands it runs, which lets the pc have its own name settings. A misspelt name gets NXDOMAIN, which means the name does not exist. getent finds files through /etc/hosts, while dig asks DNS only and gets no answer for it. That difference explains many puzzles of the kind “ping works but dig says nothing”.
People use names, computers use numbers, and name resolution joins the two. When a program needs an address, Linux first checks slash etc slash hosts, a simple list of addresses and names for this machine only, and then asks D N S. On Ubuntu, D N S questions go to systemd resolved, a local helper at one two seven dot zero dot zero dot five three, which forwards them to the real D N S servers and remembers the answers. D N S stores records: A records hold addresses, M X records name mail servers, C NAME records point to another name. Dig asks D N S directly and shows the full answer, and getent hosts resolves a name exactly as programs do, including the hosts file. In the demo, a tiny D N S server answers for the made up zone shop dot lab, and you can see that a name in the hosts file works for getent but not for dig.

A server program listens on a port and waits. Ss shows these listening sockets: ss dash t l n p lists T C P sockets that listen, with numeric ports and the program that owns each one. Curl talks to web servers, and curl dash capital I shows just the status line and headers. Lesson 6 of 9

Troubleshooting step by step, and tcpdump

When “the network does not work”, test from the bottom up
  1. Is the interface up with an address? ip -br addr
  2. Can you reach the gateway? ip route, then ping -c 3 192.168.1.1
  3. Can you reach an outside address without DNS? ping -c 3 1.1.1.1
  4. Does DNS work? dig +short example.org and resolvectl status
  5. Is the port open on the server? nc -zv HOST PORT, and on the server sudo ss -tlnp
  6. Does the application answer? curl -v http://HOST/, then the service’s logs with journalctl -u NAME
  7. Still unclear: watch the packets with sudo tcpdump -n -i DEV port PORT
Watching a TCP handshake with tcpdumpRun for real on Linux while this page was built
cd "$(mktemp -d)"
ip netns add srv
ip netns add pc
ip link add eth0 netns pc type veth peer name eth0 netns srv
ip -n srv addr add 10.0.0.80/24 dev eth0
ip -n pc addr add 10.0.0.50/24 dev eth0
ip -n srv link set eth0 up
ip -n pc link set eth0 up
ip netns exec srv python3 -m http.server 80 --bind 10.0.0.80 > /dev/null 2>&1 &
sleep 1
ip netns exec srv timeout 3 tcpdump -n -i eth0 -c 4 'tcp port 80' 2>/dev/null | awk '{print $3, $4, $5, $6, $7}' > dump.txt &
sleep 1
ip netns exec pc curl -s -o /dev/null -w '%{http_code}\n' http://10.0.0.80/
200
wait %2
cat dump.txt | sed -E 's/\.[0-9]{4,5} /.CLIENT /; s/\.[0-9]{4,5}:/.CLIENT:/'
10.0.0.50.CLIENT > 10.0.0.80.80: Flags [S],
10.0.0.80.80 > 10.0.0.50.CLIENT: Flags [S.],
10.0.0.50.CLIENT > 10.0.0.80.80: Flags [.],
10.0.0.50.CLIENT > 10.0.0.80.80: Flags [P.],
kill %1
ip -all netns delete
The first three packets are the handshake: Flags [S] is SYN, [S.] is SYN-ACK and [.] is ACK. The fourth, [P.], pushes the HTTP request. The client port is random, so it is replaced by CLIENT here. tcpdump needs root, and -n keeps it from looking up names. Save a capture with -w file.pcap to open it later in Wireshark.
When someone says the network does not work, test from the bottom up, one layer at a time. First check that the interface is up and has an address. Then ping the gateway, then an outside address without using names, then test D N S with dig. If all that works, check whether the port is open with n c, and on the server whether the program listens, with ss. Then ask the application itself with curl dash v and read its logs. Each step that works rules out a whole group of causes. When nothing explains the problem, tcpdump shows the actual packets. In the demo it catches the three way handshake of a web request: S Y N, S Y N A C K and A C K, followed by the request itself.

Permanent settings: netplan and NetworkManager

Settings made with ip vanish at reboot. Ubuntu Server keeps them in YAML files under /etc/netplan/, which netplan turns into configuration for systemd-networkd (servers) or NetworkManager (desktops). Fedora, RHEL and most desktops use NetworkManager directly, with nmcli.

The netplan file of the practice serverTypical output, yours will differ
sudo cat /etc/netplan/01-netcfg.yaml
network:
  version: 2
  ethernets:
    enp0s3:
      addresses:
        - 192.168.1.50/24
      routes:
        - to: default
          via: 192.168.1.1
      nameservers:
        addresses: [192.168.1.1]
A static address, a default route and a DNS server. For DHCP, replace the three settings with dhcp4: true. YAML needs spaces, never tabs, and the indentation is part of the meaning. The file should be readable by root only, mode 600, because it can hold Wi-Fi passwords.

Remember
On a server you reach over ssh, always use netplan try instead of apply. If the new settings cut you off, you cannot press Enter, and netplan puts the old settings back after two minutes.
Settings made with the ip command are gone after a reboot, so the permanent settings live in configuration files. On Ubuntu servers these are Y A M L files in slash etc slash netplan. Each file describes interfaces, with addresses, routes and name servers, or simply says D H C P four true. Indentation matters in Y A M L, and tabs are not allowed. Netplan try applies the change and rolls it back after two minutes unless you confirm, which protects you from locking yourself out of a remote server. Netplan apply makes it permanent. Desktops and Red Hat style systems use NetworkManager instead, controlled with n m c l i, where you modify a stored connection and bring it up. Hostnamectl sets the name of the machine.

Practice: diagnose the network of the practice server

Users say the web site on the practice server is down, and some names do not resolve. Work through the layers.

Now be the admin who gets the call. Start at the bottom: show the interfaces and addresses, and the routing table, and ping the gateway. Look up the web shop’s address with dig, and ask the kernel which route it would take. Then list the listening sockets and see nginx on port eighty. Lesson 9 of 9

Networking from school to research

One idea, four depths

Every device has an address, a router connects your home to the internet, and DNS turns names into addresses. ping tells you whether another machine answers.

Read and set addresses, routes and DNS with ip, netplan and resolvectl, find listening services with ss, test ports with nc and curl, and troubleshoot from the bottom up. Bind private services to 127.0.0.1, and know the common ports.

Network namespaces, veth pairs and bridges are how Docker and Kubernetes give each container its own network, with NAT through nftables. VLANs, bonding, WireGuard tunnels, IPv6 with SLAAC, load balancers and reverse proxies such as nginx or HAProxy build real data centre and cloud networks (VPCs, subnets, security groups, route tables).

Research and large operators work on software-defined networking (OpenFlow, P4), fast packet processing with eBPF and XDP inside the kernel, new congestion control (BBR), QUIC and HTTP/3 over UDP, and measuring the internet at scale. Studies of big outages often trace them to BGP route leaks or DNS failures, which is why both are watched so closely.

Real world scenario: the site that worked by address but not by name

After a move to a new office network, a team could reach their test server with curl http://10.20.0.15 but not with its name. getent hosts test.internal returned nothing while ping by address worked, so routing and the server were fine. resolvectl status showed the laptops still used the old office DNS server, which the new network blocked. Updating the DNS server in netplan, and running netplan try, fixed it in a minute because the layers were checked in order.

Here is how networking knowledge grows. At school you learn that every device has an address, that the router connects your home to the internet, and that D N S turns names into addresses. Professionals read and change addresses, routes and D N S with ip and netplan, find services with ss, test ports with n c and curl, and always troubleshoot from the bottom up. Containers and clouds build on the same ideas: network namespaces and virtual cables give each container its own network, and cloud networks use subnets, route tables and security groups. Researchers and large operators push packets faster with e B P F, design new protocols like QUIC, and study how routing and D N S failures take down large parts of the internet.
