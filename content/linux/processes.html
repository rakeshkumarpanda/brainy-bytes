Lesson 1 of 5

What a process is

A program is a file on disk, such as /usr/bin/sleep. A process is a program while it runs: it has memory, open files, an owner and a number called the process ID (PID). Every process except the first one was started by another process, its parent, whose number is the PPID.

How the shell starts a command
  1. You type sleep 5 and press Enter.
  2. bash calls fork(), which makes a copy of itself. The copy is the child, with a new PID.
  3. The child calls execve() to replace itself with the program /usr/bin/sleep. The PID stays the same.
  4. The parent bash waits. When the child exits, bash collects its exit status into $? and shows the prompt.
State letterMeaning
Rrunning, or ready to run on a CPU
Ssleeping, waiting for something (input, a timer, the network)
Duninterruptible sleep, usually waiting for a disk
Tstopped, for example by Ctrl+Z
Zzombie: finished, but the parent has not collected its exit status yet

$$ is the PID of the current shell and $! the PID of the last background job. Every running process has a folder /proc/PID full of live information from the kernel. The numbers change on every run.
Remember
The first process, PID 1, is started by the kernel at boot. On most current distributions it is systemd. It adopts orphans: when a parent dies first, its children get PID 1 as their new parent.
A program is just a file sitting on the disk. When you run it, the kernel creates a process: a running copy with its own memory, its own open files and a unique number called the process ID. Processes form a family tree. The shell you type in is a process, and every command you start from it becomes its child. Under the hood, bash first makes a copy of itself with the fork system call, and the copy then replaces itself with the new program using exec. At any moment a process is in a state: running, sleeping while it waits for something, stopped, or a zombie, which has finished but whose parent has not yet read its exit status. Linux shows all of this live in the folder slash proc, where every process has a sub folder named after its number.

Remember
ps aux | grep nginx also finds the grep command itself. pgrep nginx avoids that, and pgrep -a shows the full command lines.
ps takes a snapshot of the processes. On its own it shows only the processes of your terminal. ps aux, written without a dash, is the classic way to see everything, with the owner, the share of CPU and memory, the state letter and the full command. ps dash e f shows the same processes with the number of each parent, which helps you follow the family tree. For a live view, top refreshes every few seconds and sorts the busiest processes to the top. Its first lines are worth learning. The load average shows how many processes wanted the CPU over the last one, five and fifteen minutes, and the CPU line shows how much time goes to programs, to the kernel, and to waiting for disks. When you only need a process number, pgrep finds it by name.

Signals: asking and forcing processes to stop

A signal is a small numbered message the kernel delivers to a process. Most signals can be caught by the program, which then runs its own handler, for example to save work before exiting. Two cannot be caught, blocked or ignored: SIGKILL and SIGSTOP.

NumberNameSent byDefault action
1SIGHUPthe terminal closing, or kill -HUPend. Many services reload their config on it
2SIGINTCtrl+Cend
3SIGQUITCtrl and the backslash keyend and write a core dump
9SIGKILLkill -9end at once, cannot be caught
15SIGTERMkill (the default)end, the polite request
18SIGCONTfg, bg, kill -CONTcontinue a stopped process

A process killed by signal N ends with exit status 128 + N: 143 for SIGTERM (15) and 137 for SIGKILL (9). kill -l turns such a status back into a name.
Stopping a stuck program the right way
  1. Try Ctrl+C in its terminal first (SIGINT).
  2. From another terminal, find the PID with pgrep -a NAME, then send kill PID (SIGTERM) and give it a few seconds.
  3. Only if it is still there, use kill -9 PID. It cannot save files or remove lock files, so expect some cleanup.
  4. A process in state D (waiting for a disk) ignores even SIGKILL until the disk answers. Look at the storage, not the process.
Signals are how processes are told to stop, pause or reload. Pressing control C sends SIGINT to the program in the foreground. The kill command, despite its name, simply sends a signal, and by default it sends SIGTERM, number fifteen, which politely asks the program to finish. A good program catches it, saves its work and exits. Number nine, SIGKILL, is different: the program never sees it, and the kernel removes the process at once. That makes it the last resort, because files may be left half written. SIGHUP, number one, was sent when a modem line hung up, and today many services such as nginx treat it as a request to reload their configuration. When a process is killed by a signal, its exit status is one hundred and twenty eight plus the signal number, so one hundred and forty three means it got SIGTERM.

Job control: &, Ctrl+Z, fg, bg and nohup

bash can run several commands from one terminal. A job is a command started from this shell. Only one job is in the foreground, reading your keyboard. The others run, or wait stopped, in the background.

CommandWhat it doesExample
CMD &Start in the background, the prompt returns at oncesleep 300 &
Ctrl+ZStop the foreground job (SIGTSTP)press it while vim or a long copy runs
jobsList this shell’s jobs (+ current, - previous)jobs -l
fg %NBring job N to the foregroundfg %1
bg %NContinue a stopped job in the backgroundbg %1
kill %NSignal a job by number instead of PIDkill %2
waitWait for background jobs to finishwait
nohup CMD &Keep running after you log out, output goes to nohup.outnohup ./backup.sh &
disown %NRemove a running job from the shell, so logging out does not send it SIGHUPdisown %1
An interactive sessionTypical output, yours will differ
sleep 300 &
[1] 2400
sleep 600
^Z
[2]+  Stopped                 sleep 600
jobs
[1]-  Running                 sleep 300 &
[2]+  Stopped                 sleep 600
bg %2
[2]+ sleep 600 &
fg %1
sleep 300
The second sleep ran in the foreground until Ctrl+Z (shown as ^Z) stopped it. bg let it continue in the background, and fg %1 brought the first job forward, so the shell waits for it.
Common mistake
Closing a terminal sends SIGHUP to its shell, which passes it on to its jobs. Use nohup, disown, or better a terminal multiplexer such as tmux or screen for long work over ssh, so a dropped connection does not kill it.
Job control lets one terminal juggle several tasks. Put an ampersand at the end of a command and it starts in the background, so the prompt comes back at once. If a command is already running in the foreground, control Z stops it, and then you choose: bg lets it continue in the background, fg brings it back to the foreground. The jobs command lists everything this shell started, with a plus sign on the current job and a minus on the previous one, and you can refer to jobs as percent one, percent two and so on, even with kill. One danger remains. When you close the terminal or your ssh connection drops, the shell sends the hang up signal to its jobs and they die. nohup makes a command ignore that signal and saves its output in nohup dot out. For long work on a server, most people use tmux or screen, which keep whole sessions alive and let you reconnect later.
Lesson 5 of 5

Processes from school to research

One idea, four depths

Every running program is a process with a number. ps and top show them, kill asks one to stop, and & runs a command in the background so you can keep typing.

Processes are created by fork() and execve(), reaped by the parent with wait(), and controlled with signals. nice values from -20 (most favoured) to 19 (least) change the share of CPU time: nice -n 10 CMD starts a command politely, renice -n 5 -p PID changes a running one, and only root may lower the value.

Linux schedules threads, not processes: each is a task_struct, and threads are tasks that share memory, made with clone(). Since kernel 6.6 the default scheduler is EEVDF (Earliest Eligible Virtual Deadline First), which replaced CFS and still turns nice values into weights. Process groups and sessions let the terminal driver send Ctrl+C and Ctrl+Z to the whole foreground pipeline. Control groups (cgroups v2) limit CPU, memory and I/O for groups of processes, which is the base of containers and systemd services.

Research on scheduling now targets huge core counts and mixed workloads: sched_ext (merged in Linux 6.12) lets schedulers be written as eBPF programs and loaded at runtime, so new policies can be tested without rebuilding the kernel. Work on memory pressure (PSI, pressure stall information) and on user space OOM killers such as systemd-oomd aims to keep phones and servers responsive under load instead of freezing.

Real world scenario: the runaway report

Users say the server is slow. The engineer runs top, presses P and sees a reporting script at 100% CPU for two hours. pgrep -a report gives PID 7310. kill 7310 sends SIGTERM, the script logs "shutting down" and exits after closing its database connection. The fix for tomorrow: run it with nice -n 15 so it never slows down the web shop again.

Underneath, Linux schedules tasks. A process is a task with its own memory, and threads are tasks that share memory with each other. The scheduler decides which task runs on which core and for how long. Nice values from minus twenty to plus nineteen act as weights: a nicer process gets a smaller share when the CPU is busy, but still runs when the CPU is free. Since version six point six, Linux uses a scheduler called EEVDF, and since version six point twelve, sched ext even lets engineers write scheduling policies as eBPF programs and load them while the system runs. Control groups put limits on whole groups of processes, and they are the foundation of containers such as Docker. So the simple ps and kill commands you learned sit on top of some of the most studied code in the kernel.
