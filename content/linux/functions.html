Defining and calling a function

A function gives a name to a group of commands. You call it like any other command, with arguments. Inside the function, $1, $2, $# and "$@" are the function’s own arguments, not the script’s.

Two ways to write a functionThe general form
name() {
  commands           # $1 $2 ... "$@" are the function's arguments
}

function name {      # the bash keyword form, same result
  commands
}
Functions, run for realRun for real on Linux while this page was built
greet() {
  echo "Hello, $1! You gave $# argument(s)."
}
greet Asha
Hello, Asha! You gave 1 argument(s).
greet "Ravi Kumar" extra
Hello, Ravi Kumar! You gave 2 argument(s).
type greet
greet is a function
greet () 
{ 
    echo "Hello, $1! You gave $# argument(s)."
}
backup() {
  local src=$1 dest=${2:-backup}
  mkdir -p "$dest" && cp -- "$src" "$dest/" && echo "copied $src to $dest/"
}
backup notes.txt
copied notes.txt to backup/
backup poem.txt archive
copied poem.txt to archive/
declare -F
declare -f backup
declare -f greet
unset -f greet
greet Meera
bash: greet: command not found
Each call gets its own $1 and $#. type shows the stored body. backup used ${2:-backup} as a default folder. declare -F lists the names of all functions. After unset -f, greet is gone and bash reports command not found.
Remember
A function must be defined before the line that calls it runs. In a script, put all functions at the top and the main commands at the bottom.
A function is a small named piece of a script. You write the name, a pair of round brackets, and then the commands between curly braces. After that, the name works like a new command. When you call it, any words after the name become its arguments, and inside the function dollar one, dollar two and dollar at sign refer to those arguments, not to the arguments of the whole script. Bash also accepts the keyword function in front of the name, which does the same thing. Functions must be defined before they are used, because bash reads and runs the script from top to bottom. The type command shows the body of a function, declare dash capital F lists all function names, and unset dash f removes one. Functions keep scripts short and readable: write a task once, give it a clear name, and call it wherever you need it.

Getting results out: status, output and variables

A bash function has three ways to hand back a result. Pick the one that fits.

WayHowUse it for
Exit statusreturn N (0 to 255). Without return, the status of the last commandyes or no answers, used with if, && and ||
Outputecho or printf the result, catch it with v=$(fn ...)text and numbers
A variableset a global, or write into a name given by the caller with printf -v "$1"avoiding the subshell of $( ), several results
Three ways to returnRun for real on Linux while this page was built
is_even() { (( $1 % 2 == 0 )); }
for n in 3 8; do
  if is_even "$n"; then echo "$n is even"; else echo "$n is odd"; fi
done
3 is odd
8 is even
check_file() {
  [ -f "$1" ] || { echo "missing: $1" >&2; return 2; }
  return 0
}
check_file nothere.txt; echo "status $?"
missing: nothere.txt
status 2
square() { echo $(( $1 * $1 )); }
area=$(square 12)
echo "area is $area"
area is 144
to_upper() { printf -v "$1" '%s' "${2^^}"; }
to_upper shout "quiet please"
echo "$shout"
QUIET PLEASE
fact() {
  (( $1 <= 1 )) && { echo 1; return; }
  echo $(( $1 * $(fact $(( $1 - 1 ))) ))
}
echo "5! = $(fact 5)"
5! = 120
r() { return 300; }; r; echo "return 300 gives $?"
return 300 gives 44
is_even returns the status of (( )), so it works directly in if. check_file sends its message to stderr and returns 2. square prints its answer and $( ) catches it. printf -v wrote into the variable named by the first argument. fact calls itself, a recursive function. Statuses are 8 bits, so 300 became 44.
Common mistake
return is for statuses, not data. return 1000 or return "text" cannot carry a result. Print the value and capture it with $( ) instead.
Functions return results in three ways. The first is the exit status, set with the word return and a number from zero to two hundred and fifty five. Zero means yes or success, anything else means no or failure. That makes a function perfect as an if condition, as in if is even. If you leave out return, the function gives the status of its last command. The second way is output. Print the answer with echo or printf, and the caller catches it with dollar and round brackets, like area equals dollar square twelve. This is the usual way to return text or numbers. The third way is a variable. A function can set a global variable, or use printf dash v to write into a variable whose name the caller passes in. That avoids starting a subshell and can hand back more than one value. A common mistake is to return a big number or a word with return, which cannot work, because a status is only eight bits.
Lesson 3 of 5

local variables and dynamic scope

Variables in bash are global unless you declare them with local inside a function. A local variable exists only while that function runs. bash uses dynamic scope: a function that reads a variable sees the value of the nearest caller that has one.

local and global, run for realRun for real on Linux while this page was built
total=0
add_bad()  { total=$(( total + $1 )); tmp=$1; }
add_good() { local tmp=$1; total=$(( total + tmp )); }
add_bad 5; add_good 7
echo "total=$total tmp=$tmp"
total=12 tmp=5
x=main
show() { echo "show sees x=$x"; }
caller_fn() { local x=caller; show; }
caller_fn
show sees x=caller
show
show sees x=main
where() { echo "I am ${FUNCNAME[0]}, called by ${FUNCNAME[1]:-the script}"; }
outer() { where; }
outer
I am where, called by outer
counter=0
bump() { (( counter++ )); }
bump; bump; echo "counter=$counter"
counter=2
v=$(bump; echo "$counter"); echo "inside \$( ): $v, outside: $counter"
inside $( ): 3, outside: 2
in_sub() ( cd /tmp; pwd )
in_sub; pwd
/tmp
/home/learner
add_bad leaked tmp into the script, add_good kept it local. show saw the caller’s local x, which is dynamic scope. FUNCNAME lists the function names on the call stack. A function called inside $( ) runs in a subshell, so its change to counter was lost. A body in round brackets always runs in a subshell, so its cd did not move the script.
Remember
Start every function by copying its arguments into local variables with clear names: local file=$1 count=${2:-10}. It documents the function and protects the rest of the script.
By default, every variable in bash is global, even one you set inside a function. That is a common source of bugs, because a helper function can quietly overwrite a variable the main script needs. The fix is the local keyword. A local variable lives only while its function runs, and it hides any global with the same name. Bash also has dynamic scope, which surprises people who know other languages. When a function reads a variable it does not own, bash looks at the function that called it, then that function’s caller, and so on up to the script. So a helper can see the local variables of whoever called it. The animation shows the call stack and which value each line reads. The array FUNCNAME holds the names on the stack, which is handy for log messages. Finally, remember that a function run inside dollar and round brackets runs in a subshell, so changes to variables there never come back.
Lesson 4 of 5

Function libraries and the main layout

Useful functions can live in their own file, a library, that several scripts load with source. A well-organised script then has three parts: settings, functions, and a short main function that is called with "$@".

A small library and a script that uses itRun for real on Linux while this page was built
mkdir -p lib
cat > lib/log.sh <<'EOF'
# lib/log.sh: logging helpers, load with source
[[ -n ${LOG_SH_LOADED:-} ]] && return 0
LOG_SH_LOADED=1
_say() { printf '%s [%s] %s\n' "$(date +%H:%M)" "${FUNCNAME[2]:-main}" "$*" >&2; }
log()  { _say "$*"; }
die()  { _say "ERROR: $*"; exit 1; }
EOF
cat > report.sh <<'EOF'
#!/bin/bash
source "$(dirname "$0")/lib/log.sh"
source "$(dirname "$0")/lib/log.sh"
count_lines() { wc -l < "$1"; }
main() {
  [ $# -ge 1 ] || die "usage: report.sh FILE..."
  local f
  for f in "$@"; do
    [ -r "$f" ] || die "cannot read $f"
    echo "$f: $(count_lines "$f") lines"
  done
  log "done with $# file(s)"
}
main "$@"
EOF
bash report.sh fruits.txt poem.txt 2>&1 | sed 's/^[0-9][0-9]:[0-9][0-9]/HH:MM/'
fruits.txt: 8 lines
poem.txt: 4 lines
HH:MM [main] done with 2 file(s)
bash report.sh 2>&1 | sed 's/^[0-9][0-9]:[0-9][0-9]/HH:MM/'; echo "status ${PIPESTATUS[0]}"
HH:MM [main] ERROR: usage: report.sh FILE...
status 1
bash report.sh nothere.txt 2>&1 | sed 's/^[0-9][0-9]:[0-9][0-9]/HH:MM/'
HH:MM [main] ERROR: cannot read nothere.txt
The library guards itself with LOG_SH_LOADED, so loading it twice is harmless. log and die write to stderr through _say, which prints the time and the name of the function that called log or die, FUNCNAME[2]. die then exits with status 1, which PIPESTATUS[0] shows even through the pipe. main "$@" passes every script argument to main unchanged. The sed only replaces the clock time so this page does not change on every build.
As scripts grow, organise them the way professionals do. Put reusable functions, such as logging and error handling, into a library file, and load it with source at the top of each script. A small guard variable at the top of the library makes it safe to load twice. A helper called die prints an error message to standard error and exits with a failure status, so every check in the script becomes one short line. Then write the main logic inside a function called main, and make the very last line main followed by dollar at sign in double quotes. That passes all the script arguments to main unchanged, keeps the top level of the file clean, and makes sure every function is defined before any of them runs. The example shows a report script built this way, with clear usage and error messages.
Lesson 5 of 5

Functions from school to research

One idea, four depths

A function is a named list of commands. You define it once and call it by name with arguments. It answers with a status, or prints a result that you can catch with $( ).

Functions run in the current shell, so they can change variables and the current folder, unless they run inside $( ), a pipeline or a ( ) body. Variables are global unless declared local, and scope is dynamic. return sets an 8-bit status, and the positional parameters are saved and restored around each call.

local -n declares a nameref, a variable that refers to another variable by name, so a function can fill an array the caller chose. export -f makes a function visible to child bash processes through the environment, a feature that was involved in the Shellshock bug (CVE-2014-6271) when old bash versions ran code found after a function definition in an environment variable. Redirections written after a function body apply to every call, and declare -f prints the body.

Dynamic scoping, used by bash and early Lisp, contrasts with the lexical scoping of most modern languages. Programming language research treats it as harder to reason about, because a function’s meaning depends on its callers. Tools such as bats-core (Bash Automated Testing System) and shUnit2 test shell functions one by one, and sourcing a script whose last line is guarded with [[ ${BASH_SOURCE[0]} == "$0" ]] && main "$@" lets tests load its functions without running it.

Real world scenario: the shared deploy helpers

A team had the same twenty lines of logging, retry and lock code copied into nine deploy scripts. They moved it into lib/common.sh with log, die, retry and with_lock functions, all using local variables. Each script became a short main function. When the retry logic needed a fix, one change in the library fixed all nine scripts, and bats tests now check every helper.

Let us look at functions from an expert point of view. Functions run inside the current shell, so they can change variables and even the current folder, unless they run in a subshell such as a pipeline or command substitution. Bash saves and restores the positional parameters around every call. A nameref, made with local dash n, lets a function write into a variable or array the caller names. Export dash f passes a function to child bash processes through the environment. That exact feature was the doorway for the famous Shellshock security bug in 2014, when old versions of bash ran extra commands hidden after a function definition. In language research, bash uses dynamic scope like early Lisp, while most modern languages use lexical scope, which is easier to reason about. For quality, teams test shell functions with tools such as bats, and guard the last line of a script so that tests can load its functions without running main.
