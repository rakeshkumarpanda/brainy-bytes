Measure first: the USE method and the 60 second checklist

“The server is slow” is a feeling, not a measurement. Performance work starts by turning it into numbers: latency (how long one request takes, best as percentiles such as p99), throughput (requests or bytes per second), utilization (how busy a resource is) and saturation (how much work waits in a queue).

Remember
This list of ten commands is Brendan Gregg’s 60 second checklist from Netflix. All of them come with Ubuntu or with the sysstat package (sudo apt install sysstat), so they are ready before an incident starts.
When someone says the server is slow, first turn the feeling into numbers. Latency is how long one request takes, throughput is how many requests per second get done, utilization is how busy a part is, and saturation is how much work is waiting for it. The USE method checks every resource, C P U, memory, disk and network, for utilization, saturation and errors, in a fixed order, so you do not guess. In the animation, pick a symptom and follow the check. The ten commands of the sixty second checklist give a first picture of any Linux server in about a minute.
Lesson 2 of 7

CPU: load average, vmstat, mpstat and pidstat

The load average in uptime and /proc/loadavg is the average number of tasks that are running, waiting for a CPU, or in uninterruptible sleep (state D, usually waiting for disk), over 1, 5 and 15 minutes. Compare it with the number of CPUs: a load of 4 is full use on 4 CPUs but a long queue on 1.

Common mistake
A load of 8 on a 2 CPU machine with id near 0 means CPU saturation. A load of 8 with id high and wa high means tasks in state D, waiting for disk or a hung NFS server, so adding CPUs would not help.
The load average is the number of tasks that run, wait for a C P U, or wait in uninterruptible sleep, usually for the disk, averaged over one, five and fifteen minutes. Always compare it with the number of C P Us. In the demo, two workers of stress n g keep two of four C P Us busy, so vmstat shows about fifty percent user time and pidstat shows each worker near one hundred percent. Read vmstat from left to right: r for the run queue, b for tasks blocked on I O, s i and s o for swapping, then the C P U split into user, system, idle, wait and steal. Remember that the first line of vmstat is the average since boot.

Disks: iostat, await, queue size and %util

Disk trouble shows as slow saves, high wa in vmstat, and tasks in state D. iostat -x shows each device: requests per second, kilobytes per second, the average time a request takes including the wait in the queue (r_await and w_await, in milliseconds), the average queue length (aqu-sz) and %util, the share of time the device had at least one request.

The hdd worker writes and rereads a 64 MiB file as fast as it can. vmstat shows bo (blocks written per second) jump, and wa rises while id falls. On a slower disk b also shows the tasks blocked waiting for I/O. pidstat -d names the process and its write rate in kB/s. The exact numbers differ on every run and every disk.

Common mistake
On devices that serve many requests in parallel, such as RAID arrays and NVMe or SATA SSDs, %util at 100 does not mean the device is at its limit, as iostat(1) itself warns. Watch await and aqu-sz instead: if the wait times grow while throughput stays flat, the device is saturated.

On the practice server the disk sda is quiet: a few requests per second, 1 to 2 ms per request and under 1 % util. The first report is the average since boot, the second covers the last second. -z hides devices with no activity, which keeps the output short on machines with many loop devices.
Disk problems show as slow saves, a high wait value in vmstat and tasks in state D. In the demo, a worker writes a sixty four megabyte file again and again: vmstat shows the written blocks jump and the wait time rise, and pidstat names the writer. iostat with minus x gives each disk: requests per second, kilobytes per second, the average time per request in milliseconds, the queue size, and percent util. On S S Ds and RAID arrays, percent util can be one hundred while the device still has room, so watch the wait times and the queue size.
Lesson 4 of 7

Where the time goes: time, strace -c, perf and eBPF

Once you know which process is slow, ask where its time goes: in its own code (user time), in the kernel (system time, for example many small system calls), or waiting (real time much longer than user plus sys).

About 200 kB copied with 1 byte and with 64 KiB per callRun for real on Linux while this page was built
dd if=/dev/zero of=/dev/null bs=1 count=200000 2>&1 | tail -n 1
200000 bytes (200 kB, 195 KiB) copied, 0.0452395 s, 4.4 MB/s
dd if=/dev/zero of=/dev/null bs=64k count=4 2>&1 | tail -n 1
262144 bytes (262 kB, 256 KiB) copied, 5.2869e-05 s, 5.0 GB/s
strace -c -o /tmp/one.txt dd if=/dev/zero of=/dev/null bs=1 count=200000 status=none

------ ----------- ----------- --------- --------- ----------------

  0.00    0.000000           0         7           read

The first copies 200 kB and the second 256 KiB, nearly the same amount. With bs=1 dd makes 200 000 read and 200 000 write calls, and each call crosses into the kernel and back. The rate line shows how much slower that is. strace -c counts the calls: about 200 000 reads and writes against a handful with 64 KiB blocks. strace itself makes every call much slower, so its times are only good for comparing, and it is not for busy production servers.

Profile a slow program with perf
  1. Install perf on Ubuntu with sudo apt install linux-tools-common linux-tools-$(uname -r), because perf must match the running kernel.
  2. Record the slow program under real load: sudo perf record -F 99 -g -p PID -- sleep 30.
  3. Look at the hottest functions with sudo perf report, or draw a flame graph: perf script piped into stackcollapse-perf.pl and flamegraph.pl from Brendan Gregg’s FlameGraph project. The widest boxes are where the CPU time goes.
  4. For questions perf cannot answer cheaply, such as the latency of each disk request or how long tasks wait for a CPU, use the eBPF tools of bcc (package bpfcc-tools, commands ending in -bpfcc) or a one line bpftrace program.
Remember
Unlike strace, perf and eBPF tools sample or count inside the kernel with little overhead, which is why they are the tools for production. Normal users may be limited by kernel.perf_event_paranoid, so run them with sudo.
After you know which process is slow, find out where its time goes. The time command splits it into real time, user time in the program and system time in the kernel. In the demo, dd copies the same two hundred kilobytes once with one byte per call and once with sixty four kilobytes per call. strace minus c counts two hundred thousand reads and writes against a handful, and the rate shows the cost of so many trips into the kernel. strace slows a program down a lot, so on production servers use perf, which samples the C P U with little cost, flame graphs to see the hottest code, and e B P F tools such as biolatency and runqlat.
Lesson 5 of 7

History with sar, and fixing what you found

The tools so far show now. To answer “what happened at 3 a.m.?” you need history. The sysstat package collects it: on Ubuntu 24.04 the timer sysstat-collect.timer runs every 10 minutes and saves a file per day in /var/log/sysstat, which sar reads.

Keep a performance history with sysstat
  1. Install and switch it on: sudo apt install sysstat, set ENABLED="true" in /etc/default/sysstat (it is "false" after install), then sudo systemctl enable --now sysstat.
  2. Read today: sar -u (CPU), sar -r (memory), sar -q (run queue and load), sar -d (disks), sar -n DEV (network).
  3. Read an earlier day with sar -u -f /var/log/sysstat/sa23 for the 23rd, and a time window with -s 02:50:00 -e 03:20:00.
  4. For many servers, ship the same numbers to a monitoring system such as Prometheus with node_exporter, and graph them in Grafana.
What you foundTypical fixes
one process uses all of one CPUprofile it with perf, fix the hot loop, or run more workers on the other CPUs
every CPU busy, run queue longfewer jobs at once, nice or CPUQuota= for batch jobs, more CPUs
swapping (si, so) and OOM killsfind the leak, MemoryMax= per service, more RAM

many system calls, high sybigger buffers, batching, fewer small reads and writes
high st on a cloud VMa bigger or dedicated instance type
Common mistake
Change one thing at a time and measure again with the same tool. A fix that is not measured is a guess, and a tuning value copied from the internet without a measurement often makes things worse.
The tools so far show what is happening now, but often the question is what happened last night. The sysstat package saves numbers every ten minutes on Ubuntu, after you set enabled to true in slash etc slash default slash sysstat and enable the service. sar reads them back: minus u for C P U, minus r for memory, minus q for the run queue, minus d for disks and minus n DEV for the network, with minus f for an earlier day. Then fix what the numbers show, one change at a time, and measure again with the same tool.
Lesson 6 of 7

Practice: find the busy process

Start a CPU hog on the practice server, then find it with the performance tools, and stop it.

Now practise on the server. Count the C P Us with n proc and read the load averages with uptime and from slash proc slash load avg. Start a C P U hog with yes sent to slash dev slash null in the background. Run vmstat, then mpstat for each C P U, and see one C P U at almost one hundred percent. pidstat and ps sorted by C P U both name yes as the culprit. Stop it with pkill, and finish with a look at the disks with iostat and at memory in megabytes with vmstat.
Lesson 7 of 7

Performance from school to research

One idea, four depths

A computer has parts that can get too busy: the processor, the memory, the disk and the network. When one of them has more work than it can do, things wait in a line and the computer feels slow. Good tools show which part is busy.

Use the USE method and the 60 second checklist, read load average, vmstat, mpstat, pidstat, iostat -x and sar, know what %util means on SSDs, compare real, user and sys time, count system calls with strace -c on a test system, and change one thing at a time.

Site reliability engineers set latency objectives in percentiles, profile production with perf and continuous profilers (Parca, Pyroscope), draw flame graphs and off-CPU graphs, trace with eBPF (bcc, bpftrace), size systems with queueing theory and load tests, and tune CPU frequency, NUMA placement, interrupts and I/O schedulers with measurements.

Research works on tail latency at scale, scheduler designs (the EEVDF scheduler since Linux 6.6, sched_ext with BPF schedulers), low overhead always on tracing, performance models of cloud machines with noisy neighbours, and automatic tuning with machine learning.

Real world scenario: the slow website at 9 a.m.

Every morning at 9 the shop’s pages took 6 seconds. The CPUs were at 40 %, so the team first blamed the database. Following the USE method, vmstat showed wa at 35 % and b at 6, and iostat showed w_await of 200 ms on the data disk with small 4 kB writes. pidstat -d named a log shipper that started at 9, read every log file again and called fsync after each line. Batching the writes and moving the logs to their own disk brought the pages back under 300 ms, and sar the next morning showed the disk queue gone.

Here is how performance skills grow. At school you learn that a computer has parts that can be too busy, and then work waits in a line. Professionals use the U S E method and the sixty second checklist, read vmstat, mpstat, pidstat, iostat and sar, and change one thing at a time. Reliability engineers set targets for slow requests, profile production with perf and flame graphs, and trace with e B P F. Researchers work on tail latency, new schedulers such as E E V D F and s c h e d e x t, and tracing that is cheap enough to leave on all the time.
