Lesson 1 of 5

A script is a file of commands

A shell script is a text file that holds commands you could type yourself. bash reads it from top to bottom and runs each line. Anything you repeat more than twice, such as a backup, a report or a setup, is a good first script.

Write and run a script
  1. Create the file with an editor, for example nano greet.sh.
  2. Make the first line the shebang: #!/bin/bash. It tells the kernel which program should read the file.
  3. Write the commands, one per line. Lines that start with # are comments and are ignored.
  4. Make it executable once: chmod +x greet.sh.
  5. Run it with its path: ./greet.sh. The ./ is needed because the current folder is not in PATH.
Your first scriptRun for real on Linux while this page was built
cat > greet.sh <<'EOF'
#!/bin/bash
# greet.sh: say hello to everyone named on the command line
echo "Script: $0, number of names: $#"
for name in "$@"; do
  echo "Hello, $name!"
done
EOF
chmod +x greet.sh
ls -l greet.sh
-rwxr-xr-x 1 learner learner 160 Nov 23 18:26 greet.sh
./greet.sh Asha "Ravi Kumar"
Script: ./greet.sh, number of names: 2
Hello, Asha!
Hello, Ravi Kumar!
bash greet.sh Meera
Script: greet.sh, number of names: 1
Hello, Meera!
greet.sh
bash: greet.sh: command not found
The here document (cat with EOF) writes the script in one go. chmod +x added the x bits. Typing greet.sh alone fails with status 127, because bash looks for commands only in the PATH folders.

Common mistake
Use #!/bin/bash when the script uses bash features such as [[ ]] or arrays. #!/bin/sh asks for a plain POSIX shell, which on Debian and Ubuntu is dash, and many bash features fail there.
A shell script is simply a text file full of commands. Instead of typing the same ten lines every morning, you write them once and run the file. The first line, called the shebang, starts with a hash and an exclamation mark followed by the path of the interpreter, for example slash bin slash bash. When you run the file, the kernel reads those two characters and starts that program to read the rest. Lines starting with a hash are comments for humans. Before you can run the script by name, give it permission to execute with chmod plus x, and then start it with dot slash and its name. The dot slash matters: for safety, the current folder is not in PATH, so bash would not find the script otherwise. You can also run any script with bash followed by the file name, or load it into your current shell with source.

Arguments: $1, $2, $# and "$@"

Words typed after the script name are its arguments. Inside the script they are the positional parameters $1, $2 and so on. From the tenth on you need braces: ${10}.

ParameterHolds
$0the name the script was started with
$1 ... $9, ${10}the arguments, one each
$#how many arguments there are
"$@"all arguments, each kept as its own word (almost always what you want)
"$*"all arguments joined into one word with spaces
shiftdrops $1 and moves the others down by one
${1:-default}$1, or the default when it is empty or missing
Arguments in actionRun for real on Linux while this page was built
cat > args.sh <<'EOF'
#!/bin/bash
echo "name: $0  count: $#"
echo "first: $1  second: $2"
echo "all, one per line:"
printf '  [%s]\n' "$@"
shift
echo "after shift: $# left, first is now $1"
EOF
bash args.sh Asha "New Delhi" 42
name: args.sh  count: 3
first: Asha  second: New Delhi
all, one per line:
  [Asha]
  [New Delhi]
  [42]
after shift: 2 left, first is now New Delhi
bash args.sh
name: args.sh  count: 0
first:   second: 
all, one per line:
  []
after shift: 0 left, first is now 
cat > hello.sh <<'EOF'
#!/bin/bash
name=${1:-friend}
echo "Hello, $name!"
EOF
bash hello.sh
Hello, friend!
bash hello.sh Ravi
Hello, Ravi!
printf repeats its format for every argument, so it prints each one in brackets. The quotes kept "New Delhi" as one argument. With no arguments, $1 is empty and ${1:-friend} falls back to friend.
Common mistake
Always quote "$1" and "$@". Without quotes a file name like My Report.pdf becomes two words, and an empty argument disappears completely.
Scripts become useful when they take input from the command line. Every word after the script name is an argument, and inside the script you read them as dollar one, dollar two and so on, while dollar zero holds the name of the script itself. Dollar hash tells you how many arguments were given, which is how a script checks that it was used correctly. To pass all the arguments on, write dollar at sign inside double quotes. That keeps every argument as its own word, even if it contains spaces. The shift command throws away the first argument and moves the rest down, which is handy when you process them one by one in a loop. And a default value such as dollar brace one colon dash friend gives a friendly fallback when the user types nothing.

Exit status: how scripts say yes or no

Every command ends with an exit status, a number from 0 to 255. 0 means success and anything else means some kind of failure. The status of the last command is in $?. A script sets its own status with exit N, and without it the script returns the status of its last command.

StatusUsual meaning
0success
1general failure (grep: no line matched)
2wrong usage, for example a bad option
126found but not executable (no x bit)
127command not found
128 + Nkilled by signal N, for example 130 after Ctrl+C
Reading and setting exit statusesRun for real on Linux while this page was built
ls notes.txt; echo "status $?"
notes.txt
status 0
ls nothere; echo "status $?"
ls: cannot access 'nothere': No such file or directory
status 2
grep -q milk notes.txt; echo "grep found it: status $?"
grep found it: status 0
grep -q pizza notes.txt; echo "grep found nothing: status $?"
grep found nothing: status 1
nosuchcmd; echo "status $?"
bash: nosuchcmd: command not found
status 127
cat > check.sh <<'EOF'
#!/bin/bash
if [ $# -eq 0 ]; then
  echo "usage: $0 FILE" >&2
  exit 2
fi
echo "checking $1"
EOF
bash check.sh; echo "status $?"
usage: check.sh FILE
status 2
bash check.sh notes.txt; echo "status $?"
checking notes.txt
status 0
mkdir -p backup && cp notes.txt backup/ && echo "copied"
copied
cd nowhere || echo "could not enter nowhere"
bash: cd: nowhere: No such file or directory
could not enter nowhere
ls notes.txt prints the file name and succeeds. grep -q prints nothing and only sets the status. check.sh writes its usage message to stderr with >&2 and exits with 2. && runs the next command only after a success, || only after a failure.
Remember
Test a status right after the command. Even echo changes $?, so save it first if you need it twice: rc=$?.
In the shell, success and failure are numbers. Every command finishes with an exit status, and zero means everything went well, while any other number means something went wrong. That is the opposite of many programming languages, where zero means false, so it is worth remembering. The special variable dollar question mark holds the status of the last command, so you can print it or test it. Some numbers have fixed meanings: one hundred and twenty seven means the command was not found, and one hundred and twenty six means it could not be executed. Your own scripts should follow the same rule: exit zero when they succeed, and exit with a small non zero number, often one or two, when they fail. That lets other scripts and tools such as cron, make and CI pipelines know whether your script worked. The operators double ampersand and double bar build on exit statuses: run the next command only if the last one succeeded, or only if it failed.

printf reused its format for the second pair of values. read takes its input from a here string here, and with no terminal attached the -p prompt is not shown. The first here document expanded the variable and the command, the quoted EOF kept the text exactly.
Scripts talk to people through standard output and standard error. echo is quick for simple lines, while printf gives exact control with a format string, much like in C: percent s for text, percent d for whole numbers and percent point one f for one decimal place. Send error messages and progress notes to standard error with greater than ampersand two, so they still reach the screen when the normal output goes into a file or a pipe. To ask a question, use read dash r with a variable name, and dash p to show a prompt. Here documents let you write many lines of text at once, such as a report or a config file. Without quotes around the end word, variables and commands inside are expanded. With quotes, the text is written exactly as it is, which is perfect for creating another script.
Lesson 5 of 5

First scripts from school to research

One idea, four depths

A script is a list of commands saved in a file. The first line says which program runs it. Arguments come in as $1, $2, and the script answers with an exit status, where 0 means it worked.

When you run ./greet.sh, the kernel’s execve() sees the two bytes #! at the start, reads the interpreter path and runs it with the script path as an argument, as if you typed /bin/bash ./greet.sh. The shell then parses the file line by line, so a syntax error late in the file appears only when that line is reached. Exit statuses are 8 bits, so exit 256 becomes 0.

The #! line allows one optional argument and is limited in length (256 bytes on current Linux). #!/usr/bin/env bash finds bash through PATH, which helps on systems where bash lives elsewhere, at the cost of trusting PATH. POSIX sh scripts run on any Unix (dash, busybox ash, ksh), while bash scripts may use arrays, [[ ]] and other extensions. Tools such as ShellCheck read scripts statically and warn about unquoted variables, missing exit checks and portability problems.

Studies of real shell scripts (for example the Smoosh formal semantics of POSIX shell, POPL 2020, and work on static analysis of Dockerfiles and CI scripts) show how hard the shell language is to analyse: word splitting and expansion depend on runtime values. Projects such as Oil and NGS design new shells that keep compatibility while removing these traps.

Real world scenario: the morning report

An analyst runs the same five commands every morning to count yesterday’s orders from a log. She writes them into orders.sh, takes the date as $1 with today as the default, prints a usage line to stderr and exits with 2 when the log is missing. Now ./orders.sh 2026-11-22 gives the answer in a second, and the team’s dashboard calls the same script.

Here is what really happens when you run a script by name. The kernel opens the file, sees the two characters hash and exclamation mark at the very start, reads the interpreter path that follows, and runs that interpreter with your script as its argument. bash then reads the file and executes it line by line, which is why a typo near the end only shows up when that line is reached. Exit statuses are stored in eight bits, so the largest is two hundred and fifty five. Experienced writers often start scripts with hash bang slash usr slash bin slash env bash, which finds bash wherever it is installed. They also run ShellCheck, a free tool that reads a script and warns about common mistakes, especially missing quotes. Researchers have even written exact mathematical descriptions of how the shell expands words, because the rules are so easy to get wrong, and some new shells try to keep the convenience while removing the traps.
