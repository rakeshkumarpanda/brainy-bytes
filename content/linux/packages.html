Packages, repositories and dependencies

On Linux you rarely download programs from websites. A package is an archive with a program’s files plus facts about it: its name, version, the other packages it needs (its dependencies), and scripts to run when it is installed. Packages come from repositories, servers run by the distribution, and a package manager fetches, checks, installs, upgrades and removes them.

Common mistake
The Signed-By key in the sources file is how apt knows that the package lists are genuine. Only add a third-party repository when you trust its owner, because its packages run their scripts as root.
On Linux you seldom download programs from websites. Instead, the distribution keeps huge collections of ready made software, called repositories, and a package manager installs it for you. A package is an archive that holds the program’s files together with facts about it, such as its version and the other packages it depends on. Debian and Ubuntu use dot deb packages with the tools dpkg and apt. Fedora and Red Hat use dot r p m packages with rpm and dnf. Arch uses pacman. The ideas are the same everywhere. The list of repositories is in slash etc slash apt on Ubuntu, and each one is signed with a key, so apt can detect a fake. Every installed file belongs to exactly one package, and dpkg dash capital S tells you which. Common mistake
Read the plan before you answer Y. Upgrades and removals can list far more packages than you expect, for example when a library change removes a desktop or a database server.
Apt is the everyday tool on Debian and Ubuntu. Start with sudo apt update, which downloads the latest lists of packages from the repositories. It does not install anything. Then sudo apt upgrade installs newer versions of what you already have, and this is how a server gets its security fixes. Sudo apt install followed by a name installs a program together with everything it needs, and apt marks those extra packages as automatic. Remove takes a program away but keeps its settings, purge also deletes the settings, and autoremove cleans up automatic packages that nothing needs any more. Apt search and apt show help you find the right package. When you write scripts, use apt get instead of apt, because apt’s screen output may change between versions. And always read the summary before you say yes, especially before removals.

Inside a .deb file, and dpkg

apt finds and downloads packages, then calls dpkg to do the actual installing. A .deb file is an archive with two parts: control (the facts and the maintainer scripts) and data (the files that go into the file tree).

figlet only needs libc6, which every system has, so dpkg could install it alone. With a missing dependency dpkg would stop and leave the package half configured, and sudo apt install -f would then fetch what is missing. The postinst script registered /usr/bin/figlet through update-alternatives.
Under apt sits dpkg, the tool that really unpacks packages and keeps the database of every installed file in slash var slash lib slash dpkg. A dot deb file has two parts. The control part holds the facts, such as the name, version and dependencies, plus small maintainer scripts that run before and after installing or removing, for example to create a service user. The data part holds the files that go into the file tree. You can look inside without installing, using dpkg deb dash capital I for the facts and dash c for the file list. Dpkg dash i installs a downloaded dot deb file, but it does not fetch dependencies, so the better way is sudo apt install with a dot slash in front of the file name, which lets apt fetch whatever is missing. Dpkg dash capital L lists a package’s files, and dpkg dash capital S finds which package owns a file.

Building from source (the GNU convention)The general form
tar xf tool-2.1.tar.gz && cd tool-2.1
./configure --prefix=/usr/local     # check the system, write the Makefile
make                                # compile
sudo make install                   # copy into /usr/local/bin, /usr/local/lib ...
/usr/local is kept for software that the package manager does not manage, so the two never overwrite each other. /usr/local/bin comes before /usr/bin in PATH.
Other distributions use other tools, but they do the same jobs. On Fedora and Red Hat you type dnf install, on Arch pacman dash capital S, and on openSUSE zypper install. The table lets you translate between them. There are also universal formats that work across distributions. Snap and Flatpak bundle an application with its libraries and keep it updated, and Flatpak runs desktop apps in a sandbox. An AppImage is a single file you make executable and run. Programming languages have their own managers, such as pip and npm, which are for project libraries and should not be run with sudo. And when you need a version that no package offers, you can build from source with configure, make and make install, which by convention goes into slash usr slash local so it never collides with packaged files.

Lesson 6 of 6

Software management from school to research

One idea, four depths

Install software from the distribution’s repositories with the package manager. Run sudo apt update and sudo apt upgrade often, because most updates are security fixes.

Servers install security updates automatically with unattended-upgrades on Debian and Ubuntu, or dnf-automatic on Fedora and RHEL, and reboot in a planned window when the kernel changes (needrestart and /var/run/reboot-required tell you). Pin important versions with apt-mark hold, and read /var/log/apt/history.log to see what changed and when.

Companies mirror repositories (aptly, Pulp, Artifactory) so every server installs exactly the same tested versions. Configuration management (Ansible, Puppet, Salt) states which packages must be present. Container images and image-based systems such as Fedora Silverblue or Ubuntu Core replace package by package upgrades with whole images that are swapped and can be rolled back.

Reproducible builds aim for identical binary packages from identical source, so anyone can check that a package matches its code. Debian, Arch and others track this at reproducible-builds.org. Nix and Guix install every package under a path made from a hash of all its inputs, which allows many versions side by side and atomic rollbacks. The 2024 xz-utils backdoor showed why supply chain checks matter.

Real world scenario: the upgrade that broke production

An admin ran sudo apt full-upgrade -y on a database server on a Friday evening. A new major version of the database package was pulled in, and the service did not start because its data needed a migration. Since then, the team holds the database package with apt-mark hold, lets unattended-upgrades install only security updates, tests every upgrade on a staging copy first, and reads /var/log/apt/history.log after each change.

Here is how software management grows up. At home, keeping a system updated is the single most important security habit. On servers, security updates are usually installed automatically with unattended upgrades, while bigger changes go through a test server first, and important packages are held at a fixed version. Larger companies keep their own copies of the repositories so that every machine gets exactly the same tested packages, and tools such as Ansible describe which packages each server must have. Newer systems go further and update the whole system as one image that can be rolled back. Researchers work on reproducible builds, which let anyone check that a binary package really comes from its published source code. And systems such as Nix give every package a unique path from a hash of its inputs, so many versions can live side by side.
