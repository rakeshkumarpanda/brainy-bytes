Shell variables and environment variables

A shell variable is a name with a text value, kept inside one running bash. Write it with no spaces around the equals sign and read it with a dollar sign. An environment variable is a variable that is exported: bash copies it into every program it starts. Children get a copy, so they can never change the parent's value.

Common mistake
city = Pune with spaces is not an assignment. bash runs a command called city with the arguments = and Pune, and prints city: command not found.
Variables let the shell remember a value by name. You set one with a name, an equals sign and a value, with no spaces, and you read it back with a dollar sign in front of the name. Such a variable lives only inside the current shell. To pass it on to programs you start, you export it, which turns it into an environment variable. Every process has its own environment, and a child receives a copy of its parent’s exported variables when it starts. Because it is a copy, a child can never change a variable in its parent, which surprises many beginners who run a script to set something and find it gone afterwards. You can also put a variable in front of a single command, like LANG equals C sort, to change it just for that one run. Some variables are set for you at login: HOME, USER, PATH, SHELL and LANG are the most important.
Lesson 2 of 5

PATH: how bash finds commands

When you type a command name with no slash in it, bash looks for it in this order: an alias, a function, a builtin command, and then each folder listed in PATH, from left to right. The first executable file with that name wins. A name with a slash, such as ./run.sh, is used as a path and PATH is not searched.

Adding your own folder of toolsRun for real on Linux while this page was built
echo "$PATH"
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
mkdir -p ~/bin
printf '#!/bin/bash\necho "hello from my tool"\n' > ~/bin/tool
chmod +x ~/bin/tool
tool
bash: tool: command not found
PATH="$HOME/bin:$PATH"
tool
hello from my tool
type tool cd ls
tool is hashed (/home/learner/bin/tool)
cd is a shell builtin
ls is /usr/bin/ls
command -v tool
/home/learner/bin/tool
The first tool fails with status 127 because ~/bin is not in PATH yet. Putting the new folder first means your tools win over system ones with the same name. Write PATH="$PATH:$HOME/bin" to put it last instead.
Make a PATH change permanent
  1. Open ~/.bashrc in an editor (or ~/.profile for every login).
  2. Add the line export PATH="$HOME/bin:$PATH" at the end.
  3. Run source ~/.bashrc, or open a new terminal, to load it.
  4. Check with echo "$PATH" and type yourcommand.
Common mistake
Never put . (the current folder) in PATH, and never write PATH=~/bin without $PATH. The first lets a file called ls in a shared folder run instead of the real ls. The second leaves you with no commands at all until you open a new terminal.
PATH is a list of folders separated by colons. When you type a name like ls, bash first checks whether it is an alias, a function or a builtin, such as cd or echo. If not, it looks in the first folder of PATH, then the second, and so on, and runs the first executable file it finds. If none has it, you get command not found and exit status one hundred and twenty seven. That is why your own scripts need either a path, like dot slash run dot s h, or a folder that is listed in PATH. A common habit is a bin folder in your home, added to the front of PATH in your startup file. bash also remembers where it found each command, in a table you can see with the hash command, so it does not search every time.

Startup files, aliases and functions

bash reads a few files when it starts, so your settings come back in every new terminal. Which files depend on the kind of shell. A login shell is the first shell after you log in, for example over ssh. An interactive non-login shell is a new terminal window or tab on a desktop.

FileRead byPut here
/etc/profilelogin shells, for every usersystem wide settings (the administrator edits it)
~/.bash_profile, ~/.bash_login, ~/.profilelogin shells, only the first of them that existsenvironment variables such as PATH and EDITOR
~/.bashrcinteractive non-login shellsaliases, functions, prompt, history settings
~/.bash_logoutlogin shells when they exitcleanup
Remember
On Ubuntu and Debian, ~/.profile itself runs ~/.bashrc, so putting your settings in ~/.bashrc covers both kinds of shell. Scripts run non-interactively and read none of these files.

Scripts do not expand aliases unless they run shopt -s expand_aliases, interactive shells have it on already. A function runs inside the current shell, so its cd changes this shell’s folder. A script could not do that, because it runs as a child.
Every time bash starts, it reads startup files, so your aliases and settings come back. A login shell, the first one after you log in, reads slash etc slash profile and then the first of dot bash profile, dot bash login and dot profile that exists in your home. A new terminal window is usually an interactive non login shell, which reads dot bash r c. On Ubuntu, dot profile runs dot bash r c too, so dot bash r c is the place for most personal settings. After editing it, run source dot bash r c to load the changes into the shell you are using. An alias gives a short name to a longer command, such as l l for ls dash a l capital F. When you need arguments in the middle, write a small function instead. Functions run inside your current shell, so a function can even change folder, something a separate script can never do for you.

History and the prompt

bash keeps a list of the commands you typed, saves it to ~/.bash_history when the shell exits, and lets you search and reuse it. The prompt is drawn from the variable PS1.

bash prints the expanded command before running it, so you always see what !! turned into. The new prompt shows the time, the user and the last part of the folder.
bash remembers what you type. The history command lists it with numbers, and a few short forms save a lot of typing. Two exclamation marks repeat the last command, which is handy as sudo bang bang when you forgot sudo. Bang and a number repeats that line from history, and bang dollar is the last word of the previous command. The most useful trick of all is control R: start typing any part of an old command and bash finds it, and pressing control R again goes further back. The history is saved to dot bash history when the shell exits, and HISTSIZE sets how many lines are kept. Finally, the prompt itself is just a variable, PS1. Special codes such as backslash u for the user, backslash w for the folder and backslash t for the time let you design it, and many people add the git branch or colours.
Lesson 5 of 5

The environment from school to research

One idea, four depths

Variables store values by name. export passes them to programs you start. PATH lists the folders where commands live, and ~/.bashrc keeps your settings for every new terminal.

The environment is an array of NAME=value strings handed to a program by execve() and read with getenv(). Child processes get a copy, which is why scripts cannot change the caller and why source exists. Command lookup order is alias, function, builtin, then PATH, and the result is cached in a hash table that hash -r clears.

Environment variables are a security boundary: sudo resets most of them (env_reset in sudoers) and setuid programs ignore LD_PRELOAD and LD_LIBRARY_PATH, which would otherwise let a user inject code. Services under systemd do not read shell startup files at all and get their environment from Environment= lines. The twelve factor app method stores configuration in environment variables so the same container image runs in testing and production.

Shells keep evolving: zsh and fish add richer completion and history search, and tools such as direnv load project specific variables when you enter a folder. Shellshock (CVE-2014-6271) showed the danger of parsing environment values: bash ran code hidden after function definitions in variables, which web servers passed in from HTTP headers. Research on secret management (Vault, SOPS) moves passwords out of plain environment variables, which leak through /proc/PID/environ, crash reports and child processes.

Real world scenario: the missing tool after reboot

A developer installs a tool into ~/.local/bin and it works, but after logging in again the shell says command not found. echo "$PATH" shows the folder is missing. The developer had typed export PATH=... only in the terminal. Adding the same line to ~/.bashrc and running source ~/.bashrc makes it permanent, and type tool now prints the full path.

Under the hood, the environment is a plain list of name equals value strings. When bash starts a program, it passes that list to the kernel along with the program and its arguments, and the program reads it with the getenv function. That is the whole mechanism, and it explains the rules: children get a copy, and nothing flows back. Because variables can change how programs behave, they also matter for security. sudo throws most of them away, and programs that run with extra privileges ignore variables that would let a user load their own code. In twenty fourteen a bug called Shellshock let attackers run commands on web servers simply by sending a crafted header that became an environment variable for bash. Today, cloud apps store their configuration in environment variables, while real secrets move into dedicated tools, because the environment of a process can leak in more places than people expect.
