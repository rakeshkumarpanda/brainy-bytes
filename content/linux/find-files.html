find: search the tree by name, type, size and age

find WHERE TESTS walks through a folder and everything below it, checks each entry against your tests and prints the ones that pass. Unlike ls, it looks inside every sub folder, and unlike grep it searches names and details, not content.

find visits entries in the order the file system stores them, which is not alphabetical, so these lines pipe the result through sort. -empty finds the empty projects folder.
Common mistake
Always quote the pattern: find . -name "*.txt". Without quotes the shell expands *.txt in the current folder first, and find then searches for those exact names only.
find is the tool for questions like where did I save that file, which logs are older than a month, or what is eating my disk. You tell it where to start and what to look for, and it walks through every folder underneath, checking each entry. Tests can look at the name with dash name, at the kind of entry with dash type, at the size with dash size and at the age with dash m time. Units matter: dash size plus one hundred M means bigger than one hundred mebibytes, and dash m time plus thirty means changed more than thirty days ago. Always put the name pattern in quotes. Otherwise the shell expands the star before find even starts, and you get confusing results. find has been part of Unix since the nineteen seventies, and the GNU version on Linux adds many extra tests.

Combining tests: and, or, not, prune

Tests written one after another must all be true (an implied -a, "and"). -o means "or", ! means "not", and parentheses group tests. In the shell the parentheses must be escaped or quoted: \( ... \).

ExpressionMeaning
-type f -name '*.log'files AND named *.log
-name '*.jpg' -o -name '*.png'named *.jpg OR *.png
! -name '*.txt' or -not -name '*.txt'NOT named *.txt
-type f \( -name '*.jpg' -o -name '*.png' \)files that are jpg or png (the brackets group the or)
-path ./node_modules -prune -o -type f -printskip a whole folder, list the files everywhere else

-prune stops find from going into ./logs, and -print is then needed so that only the -o part prints. -size -1k means "rounded up to whole KiB, less than 1", which only empty files pass, so the last command prints nothing even though app.log is tiny.
Remember
The and binds tighter than the or. find . -name "*.jpg" -o -name "*.png" -type f means jpg files of any type, or png files that are regular files. Use parentheses whenever you mix -o with other tests.
Once you need more than one condition, find becomes a small logic language. Tests next to each other must all pass, so dash type f dash name star dot log means files and also named dot log. Dash o means or, and an exclamation mark means not. Because and is stronger than or, mixing them without brackets gives surprising results, so put round brackets around the or part. In the shell the brackets must be escaped with a backslash. One more useful word is dash prune, which tells find not to enter a folder. Developers use it all the time to skip huge folders such as node underscore modules or dot git, which can contain hundreds of thousands of files they never want to search.

Doing something with the results: -exec, -delete and xargs

CommandWhat it doesExample
find ... -exec CMD {} \;Run CMD once for each file, {} is the file namefind . -name '*.sh' -exec chmod +x {} \;

A safe routine for -delete and -exec rm
  1. Run the find command with no action and read the list.
  2. Add the action only when the list is exactly what you want to remove.
  3. Keep -delete at the end: placed first, find -delete -name x deletes everything it visits.
  4. For names that may contain spaces, use -print0 with xargs -0, or -exec ... + instead of a plain pipe.
Finding files is often only the first step. With dash exec, find runs a command for each match, and the curly braces stand for the file name. End it with a backslash semicolon to run the command once per file, or with a plus sign to pass many files to one run, which is much faster when there are thousands. Dash delete removes every match, so always run the same find without it first and read the list. The xargs command does a similar job in a pipeline. It reads words from its input and adds them as arguments to another command. File names with spaces can confuse it, so the safe pair is find dash print zero with xargs dash zero, which separates names with an invisible null character that can never appear in a file name. xargs dash P even runs several commands in parallel to use all your processor cores.

Faster lookups: locate, which and type

find reads the disk every time, which can take minutes on a big system. locate searches a database of file names instead, built by updatedb, usually once a day by a timer. It answers in a fraction of a second, but it does not know about files created since the last update. On current Debian and Ubuntu it is provided by the plocate package.

cd is built into bash, so there is no file for it. type ls may show an alias on systems that set one in ~/.bashrc, this build shell has none.
Searching the whole disk with find can take a long time on a big server. locate takes a different approach. Once a day, a program called updatedb walks the file system and stores every path in a compact database. locate then searches only that database, so it answers almost instantly. The price is freshness: a file created five minutes ago is not in the database until the next update, unless you run sudo updatedb yourself. Two other small commands answer a related question: which program will run when I type this name. which follows the PATH variable and prints the file. type is built into bash and also knows about aliases, functions and built in commands such as cd. In scripts, command dash v is the portable way to check whether a tool is installed before using it.
Lesson 5 of 5

Finding files from school to research

One idea, four depths

find searches folders for files by name, type, size or age, and can run a command on each one. locate is faster because it searches a list made earlier. which shows where a command lives.

find evaluates a boolean expression of tests, operators and actions for each directory entry in a depth first walk. -exec {{}} + batches arguments like xargs, -print0 and xargs -0 use NUL separators. locate trades freshness for speed with a periodically built index.

GNU find walks the tree with the fts library, reading directory entries with getdents64() and calling stat (or using the d_type field to skip stat) only when a test needs metadata, which makes -name searches fast. xargs keeps each command line below the limit given by sysconf(_SC_ARG_MAX), minus the size of the environment, which is why it splits huge lists into several runs. plocate uses a posting list index with compression and io_uring to answer queries in milliseconds.

File search at scale moves to indexes: desktop search engines (Spotlight, Tracker, Windows Search) watch the file system with inotify or similar events and update a full text index. Research on file system metadata search (for example Spyglass, FAST 2009, and GUFI from Los Alamos) builds indexes that answer find style questions over billions of files on supercomputer storage in seconds.

Real world scenario: the full disk at night

A database server runs out of space. The engineer runs sudo find / -xdev -type f -size +1G -exec ls -lh {{}} + 2>/dev/null and spots a 40 GB core dump in /var/crash from a crashed program. After checking it is not needed, sudo find /var/crash -name "*.crash" -mtime +7 -delete frees the space, and a ticket is opened to fix the crash.

Under the hood, find walks the directory tree depth first, reading the list of names in each folder. A clever detail is that it avoids asking for full file details unless a test needs them, because the folder listing already tells it whether an entry is a file or a folder. That is why searching by name is fast. xargs hides another detail: the kernel limits how long a command line can be, so when you pipe a million names into xargs, it quietly splits them into several runs that each fit the limit. At larger scale, searching the disk every time becomes too slow, so desktop search tools keep an index that is updated whenever a file changes. Supercomputer centres face file systems with billions of files, and research projects such as GUFI at Los Alamos National Laboratory build special indexes so that administrators can answer find style questions in seconds instead of days.
