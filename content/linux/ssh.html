Lesson 1 of 8

How an ssh login works

SSH (secure shell) gives you a shell, a command or a file copy on another machine over an encrypted connection. The client ssh connects to the server sshd on TCP port 22.

One login, in order
  1. TCP connection to port 22, then both sides agree on algorithms and run a key exchange. On OpenSSH 9.x the default is a hybrid of sntrup761 and x25519, meant to resist future quantum computers. Everything after this is encrypted.
  2. The server proves its identity with its host key. The client compares it with ~/.ssh/known_hosts. On the first visit it shows the fingerprint and asks.
  3. The user proves their identity, best with a key pair: the client signs a challenge with the private key, and the server checks it against the public keys in ~/.ssh/authorized_keys of the account. A password is the fallback.
  4. sshd starts a shell or the command you gave, as that user, and pipes its input and output through the encrypted channel.

S S H gives you a secure shell on another machine. The client, called s s h, connects to the server program, s s h d, on port twenty two. First the two sides run a key exchange, so everything that follows is encrypted, even your password. Then the server proves who it is with its host key. Your client keeps the host keys of servers you have visited in known hosts, and on the very first visit it shows the fingerprint and asks whether to trust it. If a known server suddenly shows a different key, ssh stops with a loud warning, because someone could be pretending to be that server. Next you prove who you are, best with a key pair. Your private key signs a challenge, and the server checks the signature with your public key in authorized keys. The private key never leaves your computer. -N "" sets an empty passphrase so this page can be built without a keyboard. For your own keys, leave -N out and type a passphrase: then a stolen key file is useless without it, and ssh-agent asks for it only once per session. ssh-keygen created ~/.ssh with mode 700 and the private key with mode 600 by itself. The randomart picture is a drawing of the fingerprint, easier for people to compare than a long string.
Common mistake
Never copy your private key to a server or into a chat. Give out only the .pub file. Use one key per device, so you can remove a lost laptop’s key from authorized_keys without touching the others.
A key pair has two halves. The private key stays on your computer, readable only by you. The public key, the file ending in dot pub, can be copied anywhere. Ssh keygen dash t ed25519 makes a modern key pair, short and fast. Add a comment with dash capital C so you can recognise it later. Protect the private key with a passphrase, so a stolen file is useless. To avoid typing the passphrase for every login, start ssh agent once per session and unlock the key with ssh add. The fingerprint, shown with ssh keygen dash l f, is a short summary of a key that is easy to compare. Use a separate key for each device, so you can remove one without affecting the others.

The first try fails with Host key verification failed, because BatchMode cannot ask the question and the host is unknown. accept-new stores an unknown host key without asking but still refuses a changed one. That login has no key on the server yet and BatchMode forbids passwords, so it ends with Permission denied. ssh-copy-id logs in once with the password and appends your public key to ~/.ssh/authorized_keys on the server. sshpass types the password here only because this page is built without a keyboard. Remember
If key login fails, check modes first: on the server, the home folder must not be writable by others, ~/.ssh must be 700 and authorized_keys 600, or sshd logs “Authentication refused: bad ownership or modes”. On the client, a private key readable by others is ignored with “UNPROTECTED PRIVATE KEY FILE”. Then try ssh -v, which prints every step.
Before you can log in with a key, your public key must be on the server, in the file authorized keys inside the dot s s h folder of the account. Ssh copy id does this for you: it logs in once with the password and appends your key. From then on, s s h logs in with the key, and you can switch password logins off. In the demo, a real s s h server runs in its own network namespace with the host name web one. The very first connection fails because the host is unknown and batch mode cannot ask. Accept new stores the host key, then ssh copy id installs the key, and the next login runs commands as the user deploy without any password. If key login ever fails, check the file modes on both sides first, and use s s h dash v to watch every step.

Aliases, file copies and rsync over ssh

A host entry in ~/.ssh/configThe general form
Host web1
    HostName 10.0.0.80
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519
After this, ssh web1 is enough. For each setting, the first value found wins, so put specific Host blocks before a general Host * block at the end.

The alias saves typing the address and user every time. scp copies whole files (-q hides its progress bar). rsync compares both sides and sends only files that changed, here just style.css on the second run, which makes it the better tool for repeated copies and big folders. Both use the same ssh login, key and known_hosts. Since OpenSSH 9.0, scp uses the SFTP protocol underneath, so the server needs the Subsystem sftp line that Ubuntu’s sshd_config has. (This box runs in learner’s home folder as root, so chown hands the new files to learner.)
Typing user names and addresses gets old quickly, so put them in the file dot s s h slash config. A Host block gives an alias, and below it HostName, User, Port and IdentityFile say how to reach it. Then s s h web one is all you type, and every tool that uses s s h understands the alias too. To copy files, s c p works like c p with a host name and a colon in front of the remote path. Rsync over s s h is smarter: it compares both sides and sends only what changed, so the second run in the demo sends just the one changed file. Sftp gives an interactive file transfer session. All of them use the same keys and known hosts as s s h itself.

Reach a service that listens only on the server’s localhostRun for real on Linux while this page was built
mkdir -p /srv/sshlab/admin
echo 'admin page, local only' > /srv/sshlab/admin/index.html
ip netns exec web python3 -m http.server 8080 --bind 127.0.0.1 --directory /srv/sshlab/admin > /dev/null 2>&1 &

pc curl -s --max-time 2 http://10.0.0.80:8080/ || echo "direct: no connection"
direct: no connection
pc ssh -f -N -o ExitOnForwardFailure=yes -L 9000:127.0.0.1:8080 web1

pkill -u learner -f 'ssh -f -N'

The admin page listens on 127.0.0.1 of the server only, so a direct connection from outside fails. The tunnel carries connections to port 9000 on the client through ssh, and on the server they are made to 127.0.0.1:8080. ExitOnForwardFailure makes ssh give up if the tunnel cannot be set up, instead of running without it.
A jump host in ~/.ssh/configThe general form
Host bastion
    HostName bastion.example.com
    User asha

Host db1
    HostName 10.0.5.20
    User asha
    ProxyJump bastion
ssh db1 first logs in to bastion and from there opens the connection to 10.0.5.20. Your private key stays on your laptop the whole time, which is safer than copying keys to the bastion or using agent forwarding (-A).
S S H can carry other connections inside its encrypted channel. With dash capital L, a port on your own machine leads to a port as seen from the server, which is how admins reach a database or an admin page that listens only on the server’s localhost. In the demo, the admin page cannot be reached directly, but through the tunnel on port nine thousand it answers. Dash capital R works the other way round, and dash capital D makes a S O C K S proxy. Big networks hide their servers behind one public jump host, also called a bastion. With ProxyJump in the config file, s s h hops through it automatically, and your private key never leaves your laptop.

Securing sshd

KbdInteractiveAuthenticationno unless you use one-time codesanother password path
X11Forwardingno on serversnot needed without a desktop
Change sshd settings without locking yourself out
  1. Make sure key login works and keep one ssh session open the whole time.
  2. Put your changes in a file in /etc/ssh/sshd_config.d/, for example 50-hardening.conf. The main file includes that folder near the top, and the first value found for a setting wins.
  3. Test the syntax with sudo sshd -t, and the effective values with sudo sshd -T | grep -i password.
  4. Reload with sudo systemctl reload ssh. Existing sessions stay open.
  5. Open a new session from a second terminal before you close the old one.

One letter missing in PasswordAuthentication makes sshd refuse the whole file, which is why you test before you reload. sshd -T prints the settings sshd would really use, in lower case. A HUP signal makes sshd reread its file, which is what systemctl reload ssh does. With passwords off, the server offers only publickey, so a client without a key is turned away at once.
Remember
Password guessing robots try every server on the internet within hours of it going online, as the auth.log in chapter 2.2 showed. Keys only, no root login, a short AllowUsers list and a firewall (chapter 4.3) stop nearly all of it. fail2ban can block addresses that keep failing.
On the server side, a few settings in s s h d config make a big difference. Once your key works, set PasswordAuthentication to no, so password guessing robots have nothing to guess. Set PermitRootLogin to no, so people log in as themselves and use sudo. AllowUsers limits s s h to the accounts that really need it. Put your changes in a small file in the s s h d config dot d folder, test them with s s h d dash t, which catches typos, and look at the effective values with s s h d dash capital T. Then reload the service, which keeps existing sessions open. Always keep one session open and test a new login before you log out, so a mistake never locks you out of a remote server.

Practice: key login to the file server

Set up key login from the practice server to the file server files.shop.lab (192.168.1.20), copy a file there, and switch off password logins on the practice server itself.

Now set up key login yourself. Make an ed25519 key pair with a comment, and look at its fingerprint. Write a small config file with the alias f s for the file server. Lesson 8 of 8

Remote access from school to research

One idea, four depths

ssh lets you use another computer’s command line safely over the network. A key pair is like a lock and a key: the public half goes on the server, the private half stays with you.

Use Ed25519 keys with passphrases and ssh-agent, one key per device, aliases in ~/.ssh/config, rsync over ssh for copies, tunnels for private services, and sshd with keys only, no root login and an AllowUsers list. Check host key fingerprints on the first visit.

Teams use SSH certificates (ssh-keygen -s with a certificate authority) so servers trust one CA instead of many authorized_keys files, short-lived certificates from tools such as HashiCorp Vault or step-ca, hardware keys (FIDO2, ed25519-sk), bastion hosts with session recording, and configuration management (Ansible works over ssh) to keep hundreds of servers in step.

Research looks at post-quantum key exchange (OpenSSH made sntrup761x25519 the default in 9.0 and added ML-KEM later), formal analysis of the SSH protocol, and attacks such as Terrapin (2023), which tampered with the handshake sequence numbers and led to the strict key exchange extension. Internet-wide scans study weak and shared host keys.

Real world scenario: the laptop that was stolen

A developer’s laptop was stolen from a car. Because the team used one key per device with a passphrase, the admin removed just that public key from authorized_keys on all servers with a short Ansible run, and nobody else had to change anything. A team that had copied one shared private key to everyone would have had to replace it everywhere at once. The team later moved to short-lived SSH certificates, which expire by themselves after a day.

Here is how remote access grows with experience. At school you learn that s s h opens a safe command line on another computer, and that a key pair works like a lock and key. Professionals use modern keys with passphrases, one per device, aliases, rsync and tunnels, and servers that accept keys only. Teams with many servers use S S H certificates signed by their own authority, short lived certificates, hardware security keys and bastion hosts. Researchers make the protocol ready for quantum computers and analyse it for flaws, such as the Terrapin attack, which led to a stricter handshake.
