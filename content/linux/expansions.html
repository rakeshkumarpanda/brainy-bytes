Four ways to quote

Many characters mean something special to bash: a space separates words, $ starts a variable, * matches file names, | starts a pipe. Quoting switches that meaning off, so the character is just text.

Unquoted, the runs of spaces collapse because each space just separates words. Double quotes kept the spaces and expanded $name, single quotes kept $name as text. A single quote cannot appear inside single quotes, so the fourth line closes them, adds a double quoted one and opens them again. Without quotes, the file name became two arguments, My and Report.txt.
Remember
Rule of thumb: put double quotes around every $variable and $(command), unless you really want the result split into words. Use single quotes for text that must stay exactly as typed, such as awk and sed programs.
Bash gives many characters a special job. A space separates words, a dollar sign starts a variable, and a star matches file names. Quoting turns those jobs off. A backslash protects just the next character. Single quotes protect everything between them, so nothing inside changes at all. Double quotes are the everyday choice: they keep spaces and stars as plain text, but they still let dollar signs work, so variables and command substitutions are filled in. The fourth kind, dollar followed by single quotes, works like single quotes but understands codes such as backslash n for a new line and backslash t for a tab. The most common bug in shell scripts is a missing pair of double quotes around a variable. A file name with a space then becomes two separate arguments, as the last line of the example shows. So the safe habit is simple: always write double quotes around dollar variables.
Lesson 2 of 5

The order of expansions

After splitting a line into words, bash expands them before running the command. The manual fixes the order. Knowing it explains many surprises.

What bash does to every command line
  1. Brace expansion: {a,b} and {1..3} make several words. Pure text, nothing is looked up yet.
  2. Tilde expansion: ~ at the start of a word becomes a home folder.
  3. Parameter, arithmetic and command substitution (and process substitution), from left to right: $name, ${...}, $((...)), $(...), <(...).
  4. Word splitting: unquoted results of the previous step are split at the characters in $IFS (space, tab and newline by default).
  5. Pathname expansion: unquoted words with * ? or [ ] become the matching file names.
  6. Quote removal: the quote characters that are left are removed. The command starts with what remains.
The order explains these resultsRun for real on Linux while this page was built
n=3
echo {1..$n}
{1..3}
seq -s ' ' 1 $n
1 2 3
echo ~ "~" ~root
/home/learner ~ /root
pattern='*.txt'
echo $pattern
fruits.txt notes.txt poem.txt
echo "$pattern"
*.txt
empty=''
printf '[%s]' $empty x "$empty"; echo
[x][]
Braces run before variables, so {1..$n} saw the text $n and was left alone. seq does the counting instead. Quoted, ~ stays a plain tilde. The pattern stored in a variable is globbed only when unquoted. The unquoted empty variable vanished completely, the quoted one stayed as an empty argument.
Common mistake
Globbing happens after variables are expanded, so a file name inside a variable can turn into a list of other files. That is why rm $f is dangerous and rm -- "$f" is safe.
Every command line goes through a fixed series of expansions before the command starts, and the bash manual gives the exact order. First comes brace expansion, which is pure text work: a comma list or a range inside braces becomes several words. Second is tilde expansion, where a tilde at the start of a word becomes your home folder. Third, from left to right, bash fills in variables, arithmetic, and the output of commands. Fourth, the results of step three that were not inside double quotes are split into separate words at spaces, tabs and new lines. Fifth, any unquoted word that still has a star, a question mark or square brackets is replaced by matching file names. Last of all, the quote characters themselves are removed. The order explains real puzzles. For example, brace ranges cannot use a variable, because the braces are handled before the variable has a value. Parameter expansion: editing a value without sed

Inside ${...} bash can do much more than read a variable. It can give a default, cut a prefix or suffix, replace text, take a slice or change case. It is fast because no extra program starts.

CommandWhat it doesExample
${#v}Length of the value in charactersecho ${#name}
${v:-word}v, or word when v is unset or emptyport=${PORT:-8080}
${v:=word}Like :- and also assigns word to v: ${LOG:=/tmp/app.log}
${v:?message}Stop with an error when v is unset or emptycd "${DIR:?DIR is not set}"
${v:+word}word only when v is set and not emptyecho ${debug:+-v}
${v#pat} ${v##pat}Remove the shortest or longest match from the startecho ${path##*/}
${v%pat} ${v%%pat}Remove the shortest or longest match from the endecho ${file%.*}
${v/old/new} ${v//old/new}Replace the first match, or every matchecho ${s// /_}
${v:start:len}A slice, counting from 0. A negative start counts from the endecho ${d:0:4}
${v^^} ${v,,} ${v^}Upper case, lower case, capital first letterecho ${name^^}

One # or % removes the shortest match, two remove the longest. ${path%%.*} stopped at the first dot. PORT and DEBUG are not set, so :- gave the default and :+ gave nothing. The loop only prints the mv commands, a safe way to preview a bulk rename.
Parameter expansion lets you edit the value of a variable right inside the dollar and braces, without starting sed or cut. Dollar brace hash name gives the length. A colon and a dash gives a default when the variable is empty, which is the standard way to read optional settings such as a port number. A colon and a question mark stops the script with a clear message when a required variable is missing. The hash and percent forms cut a pattern from the start or the end of the value. One hash or one percent removes the shortest possible match, and two remove the longest. That gives you the file name, the folder or the extension of a path in a single step. A slash replaces text, and two slashes replace every match. Finally, two carets make the value upper case and two commas make it lower case. Because no new program starts, these are much faster than sed inside a loop that runs thousands of times.

$( ) nests without escaping. Arithmetic is whole numbers only, so 7 / 2 is 3. diff read two command outputs as if they were files, and echo shows the name bash gave such a file. With IFS set to a comma, splitting kept the empty field between the two commas. Command substitution removed all three trailing newlines.
Remember
$((...)) has no fractions. For decimals use awk, for example awk "BEGIN { print 7 / 2 }", or bc.
Command substitution, written as a dollar and parentheses around a command, runs that command and puts its output into the line. It is how a script stores the date, the number of files, or any result, in a variable. The old form with backquotes does the same thing, but it is awkward to nest, so modern scripts use the dollar and parentheses form. Trailing new lines are removed from the output. Arithmetic expansion, with a dollar and double parentheses, does whole number maths: plus, minus, times, divide, the remainder with percent, and powers with two stars. There are no fractions, so seven divided by two gives three. Process substitution, a less than sign and parentheses, runs a command and hands its output to another command as if it were a file. That is perfect for comparing two command outputs with diff. Finally, IFS, the internal field separator, decides where word splitting and read cut a line. Set it to a colon to read a line of the password file, and unset it again afterwards to return to the normal spaces, tabs and new lines.
Lesson 5 of 5

Expansions from school to research

One idea, four depths

Before a command runs, bash replaces parts of the line: braces, ~, $variables, $(commands) and wildcards. Quotes decide what may be replaced. Double quotes around variables keep values with spaces in one piece.

The order is fixed: brace, tilde, then parameter, arithmetic and command substitution from left to right, then word splitting with IFS, pathname expansion and quote removal. Only results that were not in double quotes are split and globbed, which is why "$var" is safe and $var is not.

Word splitting treats IFS white space and other IFS characters differently: runs of white space count as one separator and are trimmed at the ends, while each other character such as a colon ends a field, so a::b gives an empty field. Command substitution runs in a subshell, so variables set inside it are lost. set -f turns pathname expansion off, and shopt -s nullglob makes a pattern with no match disappear instead of staying as text.

The POSIX standard defines these steps in its Shell Command Language chapter, and the Smoosh project (Greenberg and Blatt, POPL 2020) turned them into an executable formal model that was tested against real shells. It found places where shells disagree with the standard and with each other. Static analysers such as ShellCheck flag unquoted expansions (warning SC2086) because word splitting and globbing of data is a frequent source of bugs and security holes.

Real world scenario: the file with a space

A nightly cleanup script ran rm $old on a file called backup 2026.tar. Word splitting turned it into two arguments, backup and 2026.tar, and the script deleted an unrelated file called backup. The fix was one pair of quotes: rm -- "$old". The team added ShellCheck to their CI so the same mistake is caught before a merge.

Here is the deeper picture. The bash manual and the POSIX standard both describe the same pipeline of expansions, and the only words that are split and globbed are the ones produced by unquoted expansions. Splitting follows IFS. Spaces, tabs and new lines in IFS are grouped and trimmed, while any other character, such as a colon, ends a field each time it appears, so two colons in a row give an empty field. Command substitution runs in a subshell, so it cannot change variables in your script. Two options change globbing: set dash f turns it off, and the nullglob option makes a pattern with no match vanish. Researchers built a formal model of all these rules, called Smoosh, and tested it against real shells, finding cases where the shells disagree. In practice, the lesson from all this work is the same as on day one: quote your variables, and let ShellCheck remind you when you forget.
