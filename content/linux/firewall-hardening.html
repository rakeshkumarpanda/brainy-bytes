Lesson 1 of 7

What a firewall does

A firewall decides, packet by packet, which network traffic may reach a machine, leave it or pass through it. On Linux the filtering itself happens inside the kernel, in a framework called netfilter. Tools such as nft, iptables, ufw and firewalld only write the rules.

How a new incoming connection is judged
  1. The packet arrives on a network card. The kernel sees that it is for this machine and passes it to the input hook. Packets the machine sends go through output, and packets it routes for others through forward.
  2. Connection tracking (conntrack) checks whether the packet belongs to a connection that is already allowed. Replies and the rest of an allowed connection are accepted at once. This is what makes the firewall stateful.
  3. A new connection is compared with the rules from the top. The first rule that matches decides: accept, drop (silently) or reject (with an error back).
  4. If no rule matches, the chain’s policy decides. A safe server uses default deny for incoming traffic and opens only the ports it needs.

Remember
Drop or reject. A dropped packet gets no answer, so the client waits until it gives up. A rejected one gets an error back at once (“Connection refused”). Drop is the usual choice for traffic from the internet, reject is friendlier inside your own network.

The box runs ufw inside the namespace web, a small server with something listening on ports 22, 80 and 5432, and tests it from the namespace pc with nc. Before ufw is on, all three ports answer. After default deny with ssh and web allowed, 5432 is blocked. The deny rule for the client 10.0.0.50 is inserted at position 1, above the allow rules, so it wins for port 80. No (v6) rows appear in this lab namespace. On a normal Ubuntu server, where IPV6=yes in /etc/default/ufw, every rule without an address shows up twice, once for IPv4 and once as (v6).
Common mistake
Always allow ssh before you run ufw enable on a remote server. ufw warns “Command may disrupt existing ssh connections” for this reason. Keep your session open and test a new login, as in chapter 4.2. Cloud consoles have a serial console for the day it still goes wrong.
U f w, the uncomplicated firewall, comes with Ubuntu but starts switched off. A good start is ufw default deny incoming, then allow only what the server offers, for example OpenSSH and port eighty. Allow s s h before you enable the firewall, or you lock yourself out of a remote server. A rule can name an app profile, a port with its protocol, or a source address, such as allowing the database port only from the office network. Rules are checked from the top, so a block rule for one bad address must be inserted at position one with ufw insert. Ufw status numbered shows the order, and ufw delete with a number removes a rule. In the demo, nc from a second machine shows each port opening and closing for real.

nftables: the rules underneath

A small server ruleset, /etc/nftables.confThe general form
table inet filter {
	chain input {
		type filter hook input priority filter; policy drop;
		iif "lo" accept
		ct state established,related accept
		ct state invalid drop
		icmp type echo-request accept
		tcp dport { 22, 80 } counter accept
		counter comment "dropped by policy"
	}
}
A table holds chains, and the family inet covers IPv4 and IPv6 together. A base chain is attached to a hook (input) with a priority and a policy. Each rule is a list of matches and a verdict, read from left to right. { 22, 80 } is an anonymous set. counter counts packets and bytes, so you can see which rules are used.
CommandWhat it doesExample
nft list rulesetShow every table, chain and rulesudo nft list ruleset

nft -f FILELoad a file in one atomic stepsudo nft -f /etc/nftables.conf
nft -a list chain inet filter inputShow rules with their handle numberssudo nft -a list chain inet filter input
nft insert rule ...Add a rule at the top of a chain (add puts it at the end)sudo nft insert rule inet filter input tcp dport 443 accept
nft delete rule inet filter input handle NDelete one rule by handlesudo nft delete rule inet filter input handle 7
systemctl enable --now nftablesLoad /etc/nftables.conf at every bootsudo systemctl enable --now nftables

nft -c only checks the file, which catches typos before anything changes. Loading with -f replaces the rules in one step, so there is never a moment with half a firewall. Ports 22 and 80 are accepted and counted, 5432 falls through to the last counter and then to policy drop, and ping passes because echo requests are allowed. The counters show 2 packets accepted (one SYN for each open port) and 1 packet dropped. insert puts the new database rule at the top of the chain, so it is checked before everything else, and -a shows the handle numbers you need to delete a rule later.
Remember
Use one tool per machine. ufw, firewalld and Docker all write nftables or iptables rules, and mixing them by hand makes the order hard to follow. On Ubuntu with ufw, look with sudo nft list ruleset but change things with ufw.
Underneath u f w and firewalld, modern Linux uses n f tables. A ruleset has tables, a table has chains, and a base chain hangs on a hook such as input with a default policy. On a server the policy is drop, and the rules then accept traffic on loopback, packets of connections that are already established, ping, and the ports the server offers. Curly braces make a set, so one rule can cover several ports. Counters show how many packets each rule matched, which is the fastest way to see whether a rule is used at all. Check a file with n f t dash c before you load it, load it with n f t dash f, and enable the n f tables service so the rules come back after a reboot.

Hardening a server step by step

A short hardening checklist for a new server
  1. Install security updates automatically. On Ubuntu, unattended-upgrades installs updates from the security pocket every day.
  2. Log in with ssh keys only, no root login (chapter 4.2), and give each admin their own account with sudo (chapter 1.1).
  3. List what listens on the network with sudo ss -tulpn. Stop and disable every service you do not need with sudo systemctl disable --now NAME, and bind internal ones to 127.0.0.1.
  4. Turn on the firewall with default deny incoming and only the needed ports open.
  5. Check files with the SUID bit, which run as their owner (often root). Only well known programs such as passwd and sudo should have it.
  6. Set safe kernel network settings with sysctl, and keep logs, an audit trail and backups so you notice and recover from a break-in.
/etc/apt/apt.conf.d/20auto-upgradesThe general form
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
"1" means every day. Which updates are installed is set in /etc/apt/apt.conf.d/50unattended-upgrades, where Ubuntu allows the release’s security pocket by default. Run sudo dpkg-reconfigure -plow unattended-upgrades to write this file, and sudo unattended-upgrade --dry-run --debug to see what it would do. A reboot is still needed for a new kernel, and /var/run/reboot-required says so.

ss -tlnp lists TCP sockets in LISTEN state with the program that owns them (process ids are cut out here). 0.0.0.0:8000 is reachable from every network, 127.0.0.1:6379 only from the machine itself, which is how a cache or database should listen. -perm -4000 finds files with the SUID bit, shown as the s in -rwsr-xr-x. This list is the normal one for Ubuntu 24.04. A new or unknown SUID file is a classic sign of a break-in. In the sysctl output, ip_forward 0 means the machine does not route for others, syncookies 1 protects against SYN floods, randomize_va_space 2 is full address space randomisation, and accept_redirects 1 is worth turning off on a server.
/etc/sysctl.d/99-hardening.confThe general form
net.ipv4.conf.all.accept_redirects = 0
net.ipv6.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.rp_filter = 1
net.ipv4.tcp_syncookies = 1
kernel.kptr_restrict = 1
Files in /etc/sysctl.d are read at boot. Apply them now with sudo sysctl --system. ICMP redirects let another machine change your routes, rp_filter drops packets whose source address could not come from that interface, and kptr_restrict hides kernel addresses from normal users.
Hardening means making a server a smaller target. First, let unattended upgrades install security updates every day, so known holes get fixed without you. Second, use ssh keys only and personal accounts with sudo. Third, look at what listens on the network with s s tulpn. Every listening program is a door, so stop the ones you do not need, and bind internal ones such as a cache or database to one twenty seven dot zero dot zero dot one. Fourth, switch on the firewall. Fifth, check for files with the S U I D bit, because they run as root, and an unknown one is a warning sign. Finally, set a few kernel network settings with sysctl, such as refusing I C M P redirects, and keep logs and backups so you can notice a problem and recover.

fail2ban, auditd and AppArmor

/etc/fail2ban/jail.localThe general form
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
fail2ban reads logs, counts failures per address with a filter, and bans an address that fails maxretry times within findtime, for bantime. On Ubuntu 24.04 the file jail.d/defaults-debian.conf already enables the sshd jail, reads the systemd journal (backend = systemd) and bans with nftables. Put your own values in jail.local, because package updates replace jail.conf.

Remember
Rules added with auditctl are lost at reboot. Make them permanent in a file in /etc/audit/rules.d/ and load them with sudo augenrules --load. AppArmor is on by default in Ubuntu and limits what a program may open even when it runs as root. Its denials appear in the kernel log as apparmor="DENIED".
Three more tools watch and limit a server. Fail2ban reads the logs, counts failed logins per address, and bans an address that fails too often, here five times in ten minutes. In the demo it really bans the address with an n f tables rule. Ubuntu enables its s s h jail as soon as you install it. Auditd records security events. A watch rule on slash etc slash passwd, made with auditctl dash w, logs every change to that file with a key you can search for with ausearch. App armor gives a program a profile that lists the files and abilities it may use, so even a broken program running as root cannot read everything. Aa status shows which profiles are loaded and whether they block or only log.

Practice: lock down the practice server

The practice server runs ssh on port 22 and nginx on port 80. A database on port 5432 should be reachable from the office network 192.168.1.0/24 only, and the address 203.0.113.7 keeps guessing passwords.

Now lock down the practice server yourself. Check that the firewall is off, set the default for incoming traffic to deny, and look at the app profiles. Allow OpenSSH first, so you never lock yourself out, then the web port, and the database port only for the office network. Switch the firewall on, then block the password guesser with a rule at position one, above the allow rules. Look at the numbered and the verbose status to check the order and the defaults. Finally, list the listening ports with s s, and search for files with the S U I D bit.
Lesson 7 of 7

Firewalls from school to research

One idea, four depths

A firewall is a set of rules that decides which network traffic may come in or go out. A server should allow only the few services it offers, such as ssh and a web site, and block everything else.

Use default deny, allow ssh first, open ports per service and per network, insert block rules above allow rules, test from another machine with nc, and read counters in nft. Keep the server updated with unattended-upgrades, remove services you do not need, check SUID files, use fail2ban against guessing, auditd for a trail and AppArmor to contain programs.

Teams keep firewall rules in configuration management (Ansible, Terraform for cloud security groups), use network segmentation with separate zones for web, application and database servers, filter outgoing traffic too (egress filtering), and follow benchmarks such as the CIS Benchmarks and DISA STIGs, checked with tools like Lynis or OpenSCAP. Kubernetes uses NetworkPolicies, often enforced with eBPF tools such as Cilium.

Research covers fast packet filtering with eBPF and XDP, which drops unwanted packets in the network driver before the normal kernel path, verification of firewall rule sets for conflicts and shadowed rules, zero trust networks where every connection is authenticated instead of trusting the local network, and intrusion detection with machine learning.

Real world scenario: the database that was open to the world

A start-up moved its database to a cloud server and left it listening on 0.0.0.0:5432 with no firewall, “just for the move”. Within days, automated scanners found it and tried thousands of logins. An engineer noticed the noise in the logs, bound the database to the private network, added a ufw rule that allowed 5432 only from the application servers, and set up fail2ban for ssh. The team then added a check that runs ss -tlnp on every server each night and reports any new listening port.

Here is how firewall skills grow. At school you learn that a firewall is a set of rules that lets only wanted traffic in. Professionals use default deny, open each port only for the networks that need it, test from another machine, and harden the server with updates, fewer services, fail2ban, audit rules and app armor. Teams manage rules as code, split networks into zones, filter outgoing traffic too, and check servers against security benchmarks. Researchers build very fast filters with e B P F and X D P, check large rule sets for mistakes automatically, and work on zero trust networks, where no connection is trusted just because it comes from inside.
