cron: a schedule in five fields

cron is a background service (a daemon) that starts commands at fixed times. Each user has a list of jobs called a crontab. Every line of it holds five time fields and then the command to run.

One crontab lineThe general form
minute  hour  day-of-month  month  day-of-week  command
  30     2         *          *         *      /home/learner/backup.sh
The job starts whenever the clock matches all five fields. A star means any value.
FieldAllowed valuesExampleMeaning of the example
minute0 to 5930at minute 30
hour0 to 239-17every hour from 9 to 17
day of month1 to 311,15on the 1st and the 15th
month1 to 12, or jan to dec*/3every third month: 1, 4, 7, 10
day of week0 to 7 (0 and 7 are both Sunday), or sun to sat1-5Monday to Friday
SymbolMeaningExample
*every value* * * * * runs every minute
,a list0 8,20 * * * runs at 08:00 and 20:00
-a range0 9-17 * * * runs on the hour from 09:00 to 17:00
/a step inside a range or **/15 * * * * runs at minutes 0, 15, 30 and 45
@daily and friendsshortcuts: @yearly, @monthly, @weekly, @daily, @hourly@daily is 0 0 * * *
@rebootonce, when the cron daemon startsstart a helper after every boot
Common mistake
When both day of month and day of week are restricted, cron runs the job when either one matches. 0 0 13 * 5 runs on every 13th and on every Friday, not only on Friday the 13th.
Remember
Names work for months and days, such as mon or jan, in any case. Debian cron says in crontab(5) that ranges and lists of names are not allowed, while cronie on Fedora and RHEL accepts them. Numbers such as 1-5 work everywhere.
Many jobs on a server must happen on their own at fixed times, such as a nightly backup, a weekly report, or cleaning old log files every hour. The cron service handles this. It wakes up every minute and checks a list of jobs called a crontab. Each line has five time fields and then a command. The fields are the minute, the hour, the day of the month, the month, and the day of the week. A star means any value. So thirty, two, star, star, star means at two thirty every night. You can list values with commas, give ranges with a dash, and use a slash for steps, so star slash fifteen in the minute field means every fifteen minutes. There are shortcuts too, such as at daily and at hourly. One rule surprises many people. When you set both the day of the month and the day of the week, cron runs the job when either one matches. Type your own schedules into the animation and Pip will list the next times the job would run.

Common mistake
Always redirect output in a cron line, for example >> /var/log/myjob.log 2>&1. Without it the output is mailed, and on a server without mail it is lost, so you never see the error.
You manage your own crontab with the crontab command. Crontab dash e opens it in your editor, and cron checks every line when you save. Crontab dash l lists it, and crontab followed by a file name replaces it with the lines in that file. Be careful with crontab dash r, which deletes the whole crontab at once without asking, so keep a copy with crontab dash l first. The biggest surprise for beginners is the environment. A cron job does not run in your login shell. It runs with slash bin slash sh, a short PATH of only slash usr slash bin and slash bin, and none of your aliases or settings from dot bash r c. So use full paths, start scripts with a bash shebang, and always send the output to a log file with two greater than signs and two greater than ampersand one. One more trap: a percent sign in a crontab line means a new line, so write it with a backslash in front, or move the command into a script.

The package file in /etc/cron.d names root as the user before the command. run-parts runs the scripts of a folder in name order. Debian run-parts only accepts names made of letters, digits, dashes and underscores, so backup.sh and 30-old~ were skipped. A dot in the name is the classic reason a script in /etc/cron.daily never runs.

On Debian and Ubuntu, /etc/crontab starts the cron.hourly folder at minute 17 of every hour and the daily, weekly and monthly folders at 06:25, 06:47 and 06:52, unless anacron is installed, which then takes over the last three.

An anacron line in /etc/anacrontabThe general form
period-in-days  delay-in-minutes  job-name      command
      1               5           cron.daily    run-parts --report /etc/cron.daily
      7              10           cron.weekly   run-parts --report /etc/cron.weekly
anacron remembers the last run of each job in /var/spool/anacron. If the computer was off at the planned time, the job runs soon after the next start, after the delay.
Besides each user’s own crontab, Linux has system wide schedules. The file slash etc slash crontab and the files in slash etc slash cron dot d look like normal crontab lines with one extra field after the five time fields, the name of the user who runs the command. Packages drop their jobs into cron dot d, as you saw with a real file from this computer. Simpler still are the folders cron dot hourly, cron dot daily, cron dot weekly and cron dot monthly. You put an executable script there and a tool called run parts runs every script in the folder in name order. Watch out for file names, because on Debian run parts skips names with a dot, so a script called backup dot s h is silently ignored. Cron assumes the computer is always on. Anacron is for laptops and desktops that are often switched off. It remembers when each daily, weekly or monthly job last ran, and runs it soon after the next start if a run was missed.

at always runs the job with /bin/sh. Each job gets a number, and the letter a in atq is the queue. batch jobs go to queue b.
Remember
Unlike cron, at keeps the working folder, the umask and almost all environment variables from the moment you queued the job. Output is mailed to you, so redirect it to a file when the system has no mail.
Cron is for jobs that repeat. For a job that should run only once, later, use at. You type at and a time, such as at now plus ten minutes, at four thirty p m, or at nine a m tomorrow, and give it the commands on standard input, for example with echo and a pipe, or from a file with dash f. At answers with a job number. A t q lists the waiting jobs and a t r m with a number removes one. The command batch is similar, but instead of a time it waits until the system is not busy, which suits heavy work such as a big compile. A nice detail is that at remembers your current folder and your environment variables from the moment you queued the job, so it behaves much more like your terminal than cron does.

systemd timers: the modern scheduler

On systems that use systemd, a timer unit can start a service unit on a schedule. It takes two small files instead of one line, but gives you logs, missed-run catch up, random delays and dependencies.

backup.service and backup.timer in /etc/systemd/systemThe general form
# backup.service: what to run
[Unit]
Description=Nightly backup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh

# backup.timer: when to run it
[Unit]
Description=Run the nightly backup

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=10min

[Install]
WantedBy=timers.target
The timer starts the service with the same name. Persistent=true runs a missed job at the next boot, as anacron does. RandomizedDelaySec spreads the start over up to 10 minutes, so many servers do not all start at once.
Timer settingMeaning
OnCalendar=Mon..Fri 09:00calendar times, written as weekday year-month-day hour:minute:second
OnCalendar=dailyshortcuts: minutely, hourly, daily, weekly, monthly, yearly, quarterly
OnBootSec=5min5 minutes after the computer starts
OnUnitActiveSec=1h1 hour after the service last started, so it repeats
Persistent=truecatch up a run that was missed while the computer was off
AccuracySec=1show exact the start time must be. The default is 1 minute

Most modern Linux systems use systemd, and systemd has its own scheduler called timers. Instead of one crontab line you write two small files. A service file says what to run, and a timer file with the same name says when. The when is written with OnCalendar, for example Monday to Friday at nine o’clock, or simply daily. Timers have useful extras. Persistent equals true runs a job that was missed while the computer was off. RandomizedDelaySec adds a small random wait so a thousand servers do not all hit the backup server at the same second. Every run is logged, so journalctl dash u with the service name shows exactly what happened. Before you trust a schedule, test it with systemd analyze calendar, which prints the next times it would fire. Then reload systemd, enable the timer, and check it with systemctl list timers.
Lesson 6 of 7

Scheduled jobs from school to research

One idea, four depths

cron runs jobs again and again at fixed times, written as five fields: minute, hour, day of month, month and day of week. at runs a job once, later. Always use full paths and send the output to a log file.

Prefer one script per job, with set -euo pipefail, a lock with flock -n so runs never overlap, and output redirected with >> log 2>&1. Remember the small environment, the % rule, the either rule for day fields, and that crontab -r removes everything. anacron or Persistent=true catches runs missed while the machine was off.

cron uses the local time zone of the system, so a job set inside the hour that summer time skips or repeats needs care. cron(8) explains how your cron handles such clock changes, and many teams keep servers on UTC to avoid the question. systemd timers add RandomizedDelaySec against the thundering herd, where many machines start the same job at the same moment, and AccuracySec lets systemd group wake ups to save power. Monitoring a job means checking that it ran, not only that it did not fail, for example with a heartbeat that the last step sends.

Distributed schedulers such as Kubernetes CronJobs keep the cron syntax but add a concurrency policy (Allow, Forbid or Replace) and a deadline for late starts. Workflow engines such as Apache Airflow describe jobs as graphs with dependencies, retries and backfills of missed intervals. Research on large clusters, such as Google’s Borg papers, studies how batch jobs with flexible start times fill the gaps left by services that must answer at once.

Real world scenario: the report that ran at the wrong time

A team scheduled 0 0 1-7 * 1, hoping for a report on the first Monday of each month. It ran on the 1st to the 7th of every month and on every Monday, because cron runs the job when either day field matches. The fix keeps 0 0 * * 1 and adds [ "$(date +\%d)" -le 07 ] || exit 0 at the start, or moves the job to a timer with OnCalendar=Mon *-*-1..7 00:00, which systemd-analyze confirms before it goes live.

Here is the bigger picture on scheduled jobs. A good scheduled job is a small script that stops on errors, takes a lock with flock so two copies never overlap, and writes everything to a log. Cron works in the local time zone, so a job planned inside the hour that changes for summer time needs care, which is one reason many teams run servers on U T C. When thousands of machines run the same job, a random delay spreads the load, and systemd timers have this built in. Checking that a job succeeded is not enough. You also need an alert when it did not run at all, which is often done with a heartbeat message from the last step. At large scale, Kubernetes CronJobs keep the familiar cron syntax and add rules for overlapping runs, and workflow tools such as Apache Airflow handle dependencies between jobs, retries and catching up on missed runs.

Practice: schedule jobs in the practice shell

The practice shell below has its own crontab and at commands. They check your lines the way Debian cron does and keep the jobs, but nothing really runs at the chosen time.

Now it is your turn. The practice shell has its own crontab and at commands that check your lines exactly like Debian cron, although nothing really runs later. First write a crontab line into a file with echo, install it with crontab and the file name, and list it with crontab dash l. Then try a broken line on purpose and read the error, so you know what it looks like. After that, queue a one off job with at, list the queue with a t q, and remove the job with a t r m. Finally, remove the whole crontab with crontab dash r.
