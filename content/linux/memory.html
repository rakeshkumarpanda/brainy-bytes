Virtual memory, pages and page faults

Every process sees its own virtual address space, as if it had the whole memory to itself. The kernel and the CPU’s memory management unit (MMU) translate each virtual address to a real place in RAM, one page (4 KiB on x86-64) at a time, using the process’s page table.

TermMeaning
page and framea 4 KiB piece of virtual memory, and the 4 KiB piece of RAM that holds it
VSZ (VmSize)all virtual memory the process has mapped, used or not
RSS (VmRSS)the part that is in RAM right now, shared pages included
minor page faultthe page gets a frame without disk I/O (a fresh zero page, or a page already in the cache)
major page faultthe page must be read from disk (swap or a file), which takes milliseconds
ASLRaddress space layout randomisation: the kernel puts stack, heap and libraries at random addresses each run (kernel.randomize_va_space = 2)
Map 1 GiB, use 200 MiB, and count the page faultsRun for real on Linux while this page was built
cat > lazy.py <<'EOF'
import mmap, resource

def show(label):
    with open("/proc/self/status") as f:
        v = {k: x.split()[0] for k, x in (l.split(":", 1) for l in f) if k in ("VmSize", "VmRSS")}
    faults = resource.getrusage(resource.RUSAGE_SELF).ru_minflt
    print(f"{label:<17} VmSize {int(v['VmSize']) // 1024:>5} MiB  VmRSS {int(v['VmRSS']) // 1024:>4} MiB  faults {faults}")

show("start")
m = mmap.mmap(-1, 1024 * 2**20)
show("1 GiB mapped")
for i in range(0, 200 * 2**20, 4096):
    m[i] = 1
show("200 MiB touched")
m.close()
show("unmapped")
EOF
python3 lazy.py
start             VmSize    34 MiB  VmRSS   10 MiB  faults 957
1 GiB mapped      VmSize  1058 MiB  VmRSS   10 MiB  faults 961
200 MiB touched   VmSize  1058 MiB  VmRSS  210 MiB  faults 52161
unmapped          VmSize    34 MiB  VmRSS   10 MiB  faults 52161
Mapping 1 GiB raises VmSize by 1024 MiB at once, but RSS stays the same, because no page has a frame yet. Writing one byte in every 4 KiB page of the first 200 MiB causes one minor page fault per page: 200 × 256 = 51200 more faults, and RSS grows by 200 MiB. Unmapping gives everything back. This demand paging is why VSZ alone says little about how much RAM a program really needs.

Each line of /proc/PID/maps is one mapping: an address range, the permissions (r read, w write, x execute, p private copy on write), and what is behind it. The program file appears several times, once per part: code is r-xp, data rw-p. [heap] grows with brk and [stack] with function calls, and [vdso] is a small piece of kernel code mapped into every process so that calls such as clock_gettime need no system call. The addresses change on every run because of ASLR.
Every process lives in its own virtual address space, as if it owned all the memory. The kernel and the C P U translate virtual addresses into real memory, one four kilobyte page at a time. Memory is handed out lazily: when a program asks for a gigabyte, the kernel only notes the range. Real memory is attached the first time each page is touched, through a page fault. That is why the virtual size of a program, V S Z, is often much bigger than its resident size, R S S. The demo maps one gigabyte, touches two hundred megabytes, and you can count exactly one fault per page. The memory map in slash proc shows each mapping: the program, its libraries, the heap and the stack.

Copy on write and shared memory

fork shares pages until someone writesRun for real on Linux while this page was built
cat > cow.py <<'EOF'
import os, resource

def faults():
    return resource.getrusage(resource.RUSAGE_SELF).ru_minflt

data = bytearray(100 * 2**20)
pid = os.fork()
if pid == 0:
    before = faults()
    total = sum(data[::4096])
    after_read = faults()
    for i in range(0, 40 * 2**20, 4096):
        data[i] = 1
    print(f"child: reading 100 MiB caused {after_read - before} faults")
    print(f"child: writing 40 MiB caused {faults() - after_read} faults", flush=True)
    os._exit(0)
os.waitpid(pid, 0)
EOF
python3 cow.py
child: reading 100 MiB caused 31 faults
child: writing 40 MiB caused 10258 faults
After fork the child shares all 100 MiB with its parent. Reading every page costs almost nothing (the few faults come from Python’s own work). Writing 40 MiB causes about 40 × 256 = 10240 faults, one per page, because each written page must first be copied into a frame of the child’s own. The other 60 MiB stay shared. (flush=True matters here: os._exit skips the normal clean-up that would empty Python’s output buffer.)

Remember
Adding up the RSS of every process counts shared pages many times, so the sum can be bigger than the RAM in the machine. Use PSS when you need a fair total per program, or look at the cgroup’s memory.current for a whole service.
When a process forks, the kernel does not copy its memory. Parent and child share the same pages, marked read only. Only when one of them writes to a page does the kernel copy that page, which is called copy on write. That keeps fork fast, even for big programs. In the demo, the child reads one hundred megabytes for free, and writing forty megabytes causes one fault per copied page. Programs also share their code and libraries, and files in the page cache are in memory only once. That is why adding up the R S S of all processes gives too much. P S S divides each shared page fairly between the processes that use it.

Reading free, meminfo and swap

free -h on the practice serverThe general form
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       2.1Gi       3.0Gi       120Mi       2.6Gi       5.3Gi
Swap:          2.0Gi          0B       2.0Gi
This is what free -h prints in the practice shell. used is memory programs hold, buff/cache is the page cache and kernel buffers, and available estimates how much new programs can get without swapping, cache that can be dropped included. A server with little free but plenty available is healthy.

Is the machine short of memory
  1. Look at available in free -h, not at free. Under about 10 % of total means pressure.
  2. Run vmstat 1 5. Non-zero si and so (swap in and out) in every line means the machine swaps all the time.
  3. Read /proc/pressure/memory. The some avg10 value is the share of the last 10 seconds in which at least one task waited for memory.
  4. Search the kernel log: journalctl -k | grep -i "out of memory".
  5. Find the biggest users with ps aux --sort=-rss | head or systemd-cgtop -m per service.
Free shows the memory of the whole machine. Do not worry when free is small: Linux uses spare memory as page cache, shown as buff slash cache, and gives it back the moment programs need it. The column to watch is available. Slash proc slash meminfo has the details, such as how much memory is dirty and waiting to be written, and how much swap is used. Swappiness, sixty by default, sets how much the kernel prefers swapping out idle program memory over dropping file cache. To check for a real memory shortage, look at available, at the s i and s o columns of vmstat, which show swapping, at the memory pressure file, and at the kernel log for out of memory kills.

The OOM killer and memory limits

What happens when memory runs out
  1. The kernel first reclaims: it drops clean page cache, writes dirty pages back, and swaps anonymous pages out if there is swap.
  2. If that is not enough, the OOM killer (out of memory) gives every process a badness score, mainly from how much memory it uses, adjusted by /proc/PID/oom_score_adj from −1000 (never kill) to 1000 (kill first). /proc/PID/oom_score shows the result.
  3. It sends SIGKILL to the process with the highest score. The shell shows “Killed” and status 137, and the kernel log has a line “Out of memory: Killed process PID (name)”.
  4. With a cgroup memory limit, the same happens inside the group only: the service that hit its own limit is killed, and the rest of the machine is fine.

The bash moves itself into the cgroup and then becomes Python (exec). The first 50 MiB fit inside the 100 MiB limit. The next 200 MiB do not, so the kernel kills Python with SIGKILL, and the shell reports status 137. The cgroup counts the kill (oom_kill 1), while the rest of the machine never noticed. The build container uses the older cgroup v1 files. On Ubuntu 24.04, which uses cgroup v2, the limit is the file memory.max and the kill count is in memory.events.
Limits for a service on Ubuntu 24.04 (systemctl edit shop.service)The general form
[Service]
MemoryHigh=800M
MemoryMax=1G
MemorySwapMax=0
OOMScoreAdjust=500
MemoryHigh slows the service down and reclaims its memory hard when it goes above 800M. MemoryMax is the hard limit where the OOM killer acts inside the service. OOMScoreAdjust makes it the preferred victim if the whole machine runs out. systemctl status shows the memory in use and the peak, and systemd-cgtop shows all services.
Common mistake
Java, Node.js and databases manage their own heaps. Set their limits (for example -Xmx for Java, --max-old-space-size for Node.js, shared_buffers for PostgreSQL) below the cgroup limit, or the kernel will kill them before they get a chance to clean up.
When memory really runs out, the kernel first drops cache and swaps. If that is not enough, the out of memory killer picks a victim, usually the process that uses the most memory, and kills it with SIGKILL. The program just dies with status one hundred thirty seven, and the kernel log names it. Oom score adj lets you protect important processes or offer others as victims. The best protection is a memory limit per service, using cgroups. In the demo, a real cgroup with a one hundred megabyte limit kills a Python program that asks for two hundred fifty megabytes, and nothing else on the machine is touched. On Ubuntu you set such limits with MemoryMax in a systemd unit.

Practice: check memory on the practice server

Find out how the practice server uses its memory and change one memory setting.

Now look at memory on the practice server. Show free in human units, and find MemAvailable in meminfo. Read the virtual size and the resident size of your shell in its status file, and list the V S Z and R S S of your processes with p s. Then look at swappiness and the overcommit mode with sysctl. Lesson 6 of 6

Memory from school to research

One idea, four depths

RAM is the computer’s fast working memory. Each program thinks it has its own memory, and the operating system quietly hands out real memory only for the parts it uses. When memory is full, the system can park unused parts on the disk (swap).

Read free (watch available), meminfo, VSZ and RSS, maps and smaps_rollup, understand page faults and copy on write, set swappiness and overcommit with sysctl, recognise OOM kills (status 137, kernel log) and set MemoryMax for services.

Performance engineers use huge pages (2 MiB and 1 GiB, transparent huge pages) for databases and virtual machines, NUMA placement with numactl on servers with several CPU sockets, zram and zswap for compressed swap, systemd-oomd with PSI to act before the kernel OOM killer does, and tools such as perf, bpftrace and valgrind to find leaks and faults.

Research looks at memory tiering with CXL attached memory and persistent memory, multi-generational LRU (MGLRU, in Linux 6.1) for better reclaim decisions, memory safety (Rust, hardware tagging such as ARM MTE), and attacks on memory hardware such as Rowhammer, which flips bits in neighbouring rows of DRAM.

Real world scenario: the nightly report that killed the database

Every night at 02:00 the PostgreSQL server of a shop restarted. The kernel log showed “Out of memory: Killed process (postgres)”. A new reporting job ran on the same machine and loaded a whole table into memory, but the OOM killer chose postgres because it used the most RAM. The team put the job in its own systemd service with MemoryMax=2G, set OOMScoreAdjust=-900 on PostgreSQL, and the next night only the report hit its limit, while the database stayed up.

Here is how understanding memory grows. At school you learn that each program believes it has its own memory, and that the system hands out real memory only for the parts in use. Professionals read free, meminfo and the memory map, know what page faults and copy on write mean, and set limits for services so one program cannot take the whole machine down. Performance engineers use huge pages, place memory close to the right C P U, compress swap with zram, and react to memory pressure before the kernel has to kill. Researchers build new kinds of memory tiers, better reclaim algorithms, and defences against attacks on the memory chips themselves.
