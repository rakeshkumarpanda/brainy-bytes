Lesson 1 of 5

Three streams for every command

Every program on Linux starts with three open channels, called standard streams. Each has a number, its file descriptor.

NumberNameNormally connected toUsed for
0stdin (standard input)the keyboardData the program reads
1stdout (standard output)the terminalNormal results
2stderr (standard error)the terminalError messages and warnings

Results and errors both appear on your screen, so they look the same. But they travel on separate streams, and the shell can send each one somewhere else. This is called redirection, and the shell sets it up before the command starts. The command itself does not know where its output goes.

One command, two streamsRun for real on Linux while this page was built
ls notes.txt nothere
ls: cannot access 'nothere': No such file or directory
notes.txt
ls notes.txt nothere > /dev/null
ls: cannot access 'nothere': No such file or directory
ls notes.txt nothere 2> /dev/null
notes.txt
The first line shows both streams. In the second, stdout goes to /dev/null, a special file that swallows everything, so only the error is left. In the third, the error is thrown away and only the result is left.
Remember
/dev/null is a real file in the tree, a character device. Writing to it always succeeds and the data disappears. Reading from it gives end of file at once.
Every program on Linux is born with three open channels. Channel zero is standard input, where it reads data, normally from your keyboard. Channel one is standard output, for normal results, and channel two is standard error, for complaints and warnings. Both of those go to your terminal, which is why they look the same on screen. Keeping errors on a separate channel was a clever early Unix decision. It means you can save the useful results of a command in a file while the error messages still appear in front of you, or the other way round. The numbers zero, one and two are called file descriptors. You will see them again and again in shell commands, in programming and in system internals, so it is worth remembering them now.

Sending output to files: > and >>

The order of 2>&1 mattersRun for real on Linux while this page was built
ls notes.txt nothere > out1.txt 2>&1
cat out1.txt
ls: cannot access 'nothere': No such file or directory
notes.txt
ls notes.txt nothere 2>&1 > out2.txt
ls: cannot access 'nothere': No such file or directory
cat out2.txt
notes.txt
Redirections are read from left to right. 2>&1 means: make stream 2 go where stream 1 goes right now. In the first command, stream 1 already points at out1.txt, so both end up there. In the second, stream 1 still points at the terminal when 2>&1 is read, so the error stays on screen.
A safety catchRun for real on Linux while this page was built
set -o noclobber
echo "new" > notes.txt
bash: notes.txt: cannot overwrite existing file
echo "forced" >| diary.txt
cat diary.txt
forced
With noclobber on, > refuses to replace an existing file. >| overrides the catch on purpose.
Common mistake
A classic accident: sort data.txt > data.txt leaves an empty file. The shell empties data.txt before sort starts reading it. Write to a new name and rename it afterwards.
The arrow is one of the most useful symbols in the shell. A single arrow pointing right sends the output of a command into a file. Two arrows add the output to the end of a file instead, which is how log files grow line by line. Be careful with the single arrow. The shell empties the file before the command even starts, so a command that reads and writes the same file destroys it. To catch error messages, put the number two in front of the arrow. The trickiest pattern is two arrow ampersand one, which means send errors to the same place as normal output. Order matters here. The shell reads redirections from left to right, and two arrow ampersand one copies wherever output points at that moment. So write the file redirection first, and two arrow ampersand one after it. Engineers write this in cron jobs every day.

Feeding input: <, here documents and here strings

CommandWhat it doesExample
cmd < FILEstdin reads from FILE instead of the keyboardwc -l < fruits.txt

wc prints the file name only when it opened the file itself. With < the shell opens the file, and wc only sees a stream. With a quoted end word the here document is taken literally.
Remember
A here document is the usual way for a script to write a whole configuration file in one go. Use <<- (with a dash) to let the closing word and the lines be indented with tab characters.
Input can be redirected too. An arrow pointing left makes a command read from a file instead of the keyboard. Many commands can open files themselves, so the difference seems small, but it teaches an important idea: with the arrow, the shell opens the file and the command only sees a stream of data. A here document goes one step further. You write two left arrows and an end word, then several lines of text, then the end word again on its own line. Everything in between becomes the input. Scripts use this constantly to write configuration files or long messages. If you put the end word in quotes, the text is taken exactly as written. Without quotes, the shell fills in variables such as dollar USER. Bash also has a short form with three arrows, called a here string, for a single line of input.

Seeing and saving at the same time: tee

tee reads stdin and writes it both to the screen and to one or more files, like a T shaped pipe fitting that splits water two ways. It is the tool to use when you want to watch output and keep a copy.

CommandWhat it doesExample
cmd | tee FILEShow the output and save it to FILEls -l | tee listing.txt
cmd | tee -a FILEShow it and add it to the end of FILEdate | tee -a runs.log
cmd | sudo tee FILEWrite a root owned file, because sudo echo x > file does not workecho 1 | sudo tee /proc/sys/net/ipv4/ip_forward
tee in actionRun for real on Linux while this page was built
ls logs | tee folder.txt

old.log
cat folder.txt
app.log
old.log
date -u -d '2026-11-23 10:00' | tee -a runs.log

date -u -d '2026-11-23 11:00' | tee -a runs.log
Mon Nov 23 11:00:00 UTC 2026
wc -l runs.log

The | symbol connects commands, the subject of the next chapter. tee prints what it receives and also writes it to the file.
Common mistake
sudo echo hi > /etc/motd fails with Permission denied, because the redirection is done by your own shell before sudo runs. echo hi | sudo tee /etc/motd works, because tee runs as root and opens the file itself.
Sometimes you want to see output and save it at the same time. That is the job of tee, named after the T shaped fitting plumbers use to split a pipe in two directions. Whatever flows into tee comes out on the screen and also lands in a file. With dash a, it adds to the file instead of replacing it. tee also solves a puzzle that confuses many beginners. Typing sudo echo something into a protected file fails with permission denied, even though sudo is there. The reason is that the arrow is handled by your own shell, before sudo starts, and your shell is not root. Piping into sudo tee works, because then tee runs as root and opens the file itself. You will see this pattern in many official installation guides.
Lesson 5 of 5

Redirection from school to research

One idea, four depths

Commands read from stdin and write results to stdout and errors to stderr. > saves output in a file, >> adds to it, 2> catches errors, < reads from a file and tee shows and saves at the same time.

The shell performs redirections before executing the command, processing them left to right. n>&m duplicates descriptor m onto n. Here documents and here strings supply stdin from the script itself. /dev/null discards writes.

Inside, the shell forks, then in the child calls open() for each file and dup2() to place it on descriptor 0, 1 or 2, and finally execve() the program, which inherits the descriptor table. That is why programs need no code for redirection. 2>&1 is literally dup2(1, 2). Bash creates here documents as temporary files or pipes. stdout to a terminal is line buffered by the C library, but block buffered to a file or pipe, which explains why output order can change when redirected.

The idea that every resource looks like a file descriptor ("everything is a file") was pushed further by Plan 9 from Bell Labs, and today appears in Linux as /proc and /sys, eventfd, timerfd and signalfd. Research on capability systems such as Capsicum treats file descriptors as unforgeable access tokens, so a sandboxed program can use only the descriptors it was given.

Real world scenario: the nightly backup

A cron job runs /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1 at 02:00. Normal progress and errors both land in one growing log. With 2>&1 >> file in the wrong order, errors would go to the cron daemon instead, which mails them to root, and nobody reads that mail box.

Inside the computer, redirection is beautifully simple. When you run a command, the shell first makes a copy of itself. In that copy it opens the file you named and moves it into slot one, or slot two, of the file descriptor table, using a system call named dup two. Then it replaces itself with the program you asked for. The program inherits the table and simply writes to slot one, never knowing that slot one is now a file. That is why every program supports redirection for free. The same thinking, that everything should look like a file, was taken further by the Plan 9 system at Bell Labs, and Linux borrowed parts of it in slash proc and slash sys. Researchers working on sandboxes even treat file descriptors as keys: a program can only touch what it has been handed.
