Accounts: users, groups and the files behind them

Linux knows people and services as numbers. A UID names a user and a GID names a group, and three plain text files map the numbers to names and settings.

FileHoldsWho can read it
/etc/passwdone line per account: name, UID, primary GID, comment, home folder, shelleveryone (mode 644)
/etc/shadowthe password hashes and the password ageing datesroot and the shadow group only (mode 640)
/etc/groupone line per group: name, GID, extra memberseveryone (mode 644)
/etc/login.defsdefaults for new accounts, such as UID_MIN and PASS_MAX_DAYSeveryone

getent reads the account databases, which are the files here but can also come from a network directory such as LDAP. id -nG lists the group names, and learner is in the sudo group, so learner may use sudo. /etc/shadow refused to open for a normal user, which protects the password hashes from guessing attacks.
Linux does not really think in names. Every user has a number called a U I D, and every group has a number called a G I D. Three text files connect the numbers to names. Slash etc slash passwd has one line per account with seven fields separated by colons: the name, an x, the U I D, the main group, a comment with the full name, the home folder and the login shell. Despite its name it holds no passwords any more. The password hashes moved to slash etc slash shadow, which only root can read. Slash etc slash group lists groups and their extra members. U I D zero is root. Numbers below one thousand belong to services, and people start at one thousand. Use the animation to read each field of real lines, and notice that the getent command reads these databases for you.

Creating, changing and removing accounts

CommandWhat it doesExample
useradd -m -s /bin/bash -c "Full Name" NAMECreate a user with a home folder (-m), a shell and a comment. Without -s, Debian and Ubuntu give /bin/shsudo useradd -m -s /bin/bash dev1
adduser NAMEDebian and Ubuntu: a friendly script that asks questions, creates the home folder and sets a passwordsudo adduser dev1
passwd NAMESet or change a password. Without a name it changes your ownsudo passwd dev1
usermod -aG GROUP NAMEAdd the user to an extra group. The change applies from the next loginsudo usermod -aG docker dev1
usermod -L NAME, usermod -U NAMELock and unlock the passwordsudo usermod -L dev1
chage -M DAYS NAME, chage -l NAMESet the maximum password age, list the ageing settingssudo chage -M 90 dev1
groupadd NAME, groupdel NAMECreate or delete a groupsudo groupadd web
userdel -r NAMEDelete the user, with -r also the home folder and mailsudo userdel -r dev1
Common mistake
usermod -G web dev1 without -a replaces the whole list of extra groups, so dev1 silently leaves sudo, docker and every other group. Always write -aG.

useradd -m copied the files of /etc/skel into the new home folder. passwd -S printed L (locked) until chpasswd set a password, then P, then L again after usermod -L. The fifth field of passwd -S is the maximum age, now 90 days. userdel -r removed the home folder and warned that dev1 had no mail spool.
Remember
chpasswd reads name:password lines from standard input, which suits scripts. Never put a real password in a command line on a shared machine, because other users can see running commands with ps.
Creating an account is a job for root, so these commands run with sudo. Useradd dash m creates a user and a home folder, which is filled with starter files copied from slash etc slash skel. On Debian and Ubuntu, adduser is a friendlier helper that asks for the full name and a password. A new account from useradd starts with a locked password, shown as L by passwd dash capital S, until you set one with passwd or chpasswd. To add someone to an extra group, use usermod dash a capital G. Never forget the a, which means append. Without it the user is removed from every group that is not in your list. Chage controls password ageing, for example a maximum age of ninety days. And userdel dash r deletes the account together with its home folder, so copy any data you need first.

sudo, su and the sudoers file

CommandWhat happensPassword asked
sudo CMDrun one command as root, and log ityour own password, then remembered for 15 minutes by default
sudo -u NAME CMDrun one command as another useryour own
sudo -ia full root login shell, until you type exityour own
sudo -llist what you are allowed to runyour own
su - NAMEbecome another user with a login shellthe password of that user
sudo visudoedit /etc/sudoers safely, with a syntax checkyour own
A sudoers ruleThe general form
who      hosts = (run as users:groups)  tags       commands
%sudo    ALL   = (ALL:ALL)                         ALL
dev1     ALL   = (root)               NOPASSWD:    /usr/bin/systemctl restart nginx
A % in front of the name means a group. Put your own rules in a small file in /etc/sudoers.d and create it with sudo visudo -f /etc/sudoers.d/NAME.

The %sudo rule is why members of the sudo group may run any command. secure_path is the PATH sudo uses, which includes the sbin folders where admin tools live. visudo -c checked one good file and found the missing colon after NOPASSWD in the other, pointing at the column.
Common mistake
A sudoers file with a syntax error can stop sudo from working for everyone. Never edit it with a plain editor. visudo refuses to save a broken file.

Logging in as root for daily work is risky, because one typo can damage the whole system. Instead, normal users run single commands as root with sudo. Sudo asks for your own password, not root’s, remembers it for a few minutes, and writes every use to the log, so you always know who did what. Sudo dash i gives a root shell when you need several commands, and sudo dash u runs a command as another user, such as a database account. Who may do what is written in slash etc slash sudoers. A rule says who, on which hosts, as which user, and which commands. A percent sign means a group, which is why everyone in the sudo group may run anything. Never edit this file with a normal editor. Use visudo, which checks the syntax first, and keep your own rules in small files inside slash etc slash sudoers dot d. You can give a narrow right, such as restarting one service, without handing out full root power.
Lesson 4 of 5

Practice: manage an account in the practice shell

The practice shell keeps its own /etc/passwd, /etc/group and /etc/shadow, and its useradd, usermod and userdel change them the way the real tools do. Commands in /usr/sbin are found only through sudo, as on Debian.

Time to practise. The practice shell has its own account files, and its useradd, usermod and userdel change them just like the real tools. Create a user called dev one with a home folder, look at its line with getent, make a group called web and add dev one to it with usermod dash a capital G. Then give it a password with chpasswd, check the status, lock it, and finally remove the account and its home folder with userdel dash r. Look at slash etc slash group between the steps to see the files change.
Lesson 5 of 5

Accounts and privilege from school to research

One idea, four depths

Each person has their own account and password. Only administrators may use sudo, and they use it for one command at a time. Accounts for people who left are locked or deleted.

Give rights through groups, not through individual sudo rules, and keep each sudoers.d rule as narrow as possible, with full paths. Avoid NOPASSWD for broad commands. A rule such as (root) /usr/bin/vim gives full root, because vim can start a shell. Service accounts use /usr/sbin/nologin and no password. Expire contractor accounts with chage -E.

The Name Service Switch (/etc/nsswitch.conf) lets getent and every program read accounts from files, LDAP or SSSD, so large sites manage users centrally. PAM (Pluggable Authentication Modules, /etc/pam.d) decides how a login is checked, with password rules, lockouts after failed tries, and two-factor modules. sudo can log full session input and output, and its rules can live in LDAP.

Password hashing has moved from MD5 crypt to SHA-512 crypt to yescrypt, a memory-hard function, because GPUs made fast hashes cheap to attack. Research on privilege separation, such as the OpenSSH design that splits a small privileged monitor from an unprivileged worker, and on Linux capabilities, which divide root’s power into pieces like CAP_NET_BIND_SERVICE, aims to make UID 0 matter less.

Real world scenario: the intern with root

A startup gave every developer ALL=(ALL) NOPASSWD: ALL for convenience. A leaked laptop key let an attacker log in as one developer and become root at once. The fix moved rights into groups, replaced the blanket rule with narrow files such as %deploy ALL=(root) /usr/bin/systemctl restart app, turned on passwords for sudo, and sent auth.log to a central log server, where a failed sudo now raises an alert.

Here is the bigger picture. Good practice is to give rights to groups rather than to single people, and to keep every sudo rule as narrow as possible. Be careful, because some programs can escape to a shell, so allowing an editor or a pager through sudo can hand out full root power. Service accounts get the nologin shell and no password. In larger organisations accounts come from a central directory such as LDAP, which the name service switch makes look just like the local files, and PAM modules decide how logins are checked, including lockouts and two factor codes. Password hashes have moved to slow, memory hard functions such as yescrypt, because graphics cards can test billions of fast hashes per second. And the long term research goal is to make root less special, by splitting its power into smaller capabilities and by separating programs into privileged and unprivileged parts.
