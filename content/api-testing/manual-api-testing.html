Part 1

🔌What an API is and why we test it

An API (Application Programming Interface) is a set of rules that lets one program ask another program for data or for an action. When a food delivery app shows restaurants near you, the app sends a request such as GET /restaurants?lat=12.97&lng=77.59 to a server, and the server replies with a list in JSON. The screen you see is only the presentation. The API is where the business logic, the data and the security live.

The parts of an API call

  • Client: the app, browser, another service, or you with Postman.
  • Server: the program that receives the request and does the work.
  • Endpoint: an address such as https://api.shop.com/v1/orders.
  • Contract: the agreed shape of requests and responses, usually written as an OpenAPI document.

What API testing means

You send requests directly to endpoints, without the user interface, and check the status code, headers, body, data in the database, speed and security. Manual API testing is the exploratory, thinking part of this work. You read the contract, design cases, send requests by hand with a tool, and report what does not match.

Why test at the API layer

ReasonWhat it means in practice
Earlier feedbackAPIs are often ready before the screens. You can test the logic weeks before the UI exists.
Faster and more stableA request takes milliseconds. No browser, no waiting for pages, no flaky locators.
Deeper coverageThe UI may block a negative quantity, but a direct API call can still send one. Attackers do not use your UI.
Many clients share one APIThe web app, the Android app, the iOS app and partner systems all call the same API. One bug reaches every client.
Clear root causeWhen a UI test fails you ask whether the page or the server broke. An API test points straight at the server.
In the test pyramid, API tests sit in the middle layer, also called the service or integration layer. Teams usually want many unit tests, a solid set of API tests and only a few end to end UI tests, because the cost and the run time grow as you go up.

Types of API testing

TypeWhat it confirms
FunctionalEach endpoint does what the contract says for valid and invalid input
IntegrationSeveral APIs and the database work together in a full flow
ContractThe provider and its consumers still agree on the request and response shape
SecurityNobody can read or change data they should not
PerformanceResponse times stay within targets, also under load
ReliabilityTimeouts, retries, duplicates and partial failures are handled safely
Usability of the APINames, errors and documentation are clear for the developers who use it
Part 2

🌐What a web service is

A web service is an API that one program calls over a network using web standards such as HTTP, XML or JSON. Two systems use it to exchange data no matter which language or operating system each one runs on. A Java banking system and a Python mobile backend can talk to each other because both understand HTTP and JSON.

Key properties of a web service

  • Available over a network, usually the internet or a company intranet.
  • Uses open, standard protocols (HTTP, HTTPS, SOAP).
  • Language and platform independent.
  • Machine to machine. There is no screen, only requests and responses.
  • Described by a contract such as a WSDL file (SOAP) or an OpenAPI file (REST).

Where you meet them

  • A travel site asks airline systems for seat prices.
  • A shopping app asks a payment gateway to charge a card.
  • A weather widget reads forecasts from a weather service.
  • A bank checks an account number through a central banking service.

API versus web service

People often use the two words as if they meant the same thing. They overlap, but they are not equal.

PointAPIWeb service
MeaningAny defined way for software to talk to other softwareAn API that is reached over a network with web protocols
NetworkNot required. A Java library or an operating system call is also an APIAlways needed
ProtocolsAny: HTTP, gRPC, WebSocket, in process function callsHTTP based: SOAP, REST, XML-RPC
FormatsAny: JSON, XML, binary Protocol Buffers, objects in memoryMostly XML (SOAP) and JSON (REST)
Rule of thumbEvery web service is an API, but not every API is a web service.

The two big families: SOAP and REST

SOAP (Simple Object Access Protocol) is a strict protocol from around 2000. Every message is an XML envelope, and the service is described by a WSDL (Web Services Description Language) file. REST (Representational State Transfer) is an architectural style, a set of design rules for using HTTP the way it was meant to be used. Switch between them below to see the same operation, "get order 5", done both ways.

PointSOAPREST
What it isA protocol with a fixed message formatAn architectural style with guidelines
Message formatXML only, inside an Envelope with Header and BodyAny, usually JSON, also XML, plain text, files
TransportUsually HTTP POST, can also use SMTP or JMSHTTP, using GET, POST, PUT, PATCH and DELETE
ContractWSDL, with XSD schemas for every messageOpenAPI (optional but common)
ErrorsA <soap:Fault> element, usually with HTTP 500HTTP status codes with an error body
SecurityWS-Security standard (signatures, encryption inside the message)HTTPS plus OAuth 2.0, JWT or API keys
State and transactionsSupports WS-AtomicTransaction and WS-ReliableMessagingStateless by design
CachingNot cacheable, since everything is POSTGET responses can be cached
Typical usersBanks, insurance, telecom, government, older enterprise systemsWeb and mobile apps, public APIs, microservices
Testing toolsSoapUI, ReadyAPI, PostmanPostman, curl, Bruno, Insomnia

Inside a WSDL file

ElementWhat it describesTest idea
typesXSD schemas for the dataSend values that break the schema (wrong type, missing required element)
messageThe input and output messagesCheck each output element is present and correctly typed
portType (interface in WSDL 2.0)The operations, such as GetOrderCall every operation, including ones the UI never uses
bindingProtocol and style (SOAP 1.1 or 1.2, document or rpc)Use the right SOAPAction header and Content-Type

In SoapUI or Postman, import the WSDL and the tool creates a sample request for every operation. SOAP 1.1 uses Content-Type: text/xml plus a SOAPAction header. SOAP 1.2 uses application/soap+xml.
"Is REST a protocol?" is a favourite interview trap. No. REST is an architectural style. HTTP is the protocol most REST APIs use. SOAP is a protocol.
Part 3

🏛️REST in depth

REST was defined by Roy Fielding in his doctoral dissertation in 2000. He was also one of the authors of the HTTP specification. An API that follows the REST constraints is called RESTful.

Resources, representations and URIs

Resource

Any thing the API exposes: a customer, an order, a list of orders, even a search result. Resources are nouns.

URI

The unique address of a resource, such as /v1/orders/1042. A URL is a URI that also says how to reach it (https://…). A URN names something without a location (urn:isbn:9780134685991).

Representation

The form a resource takes in a message, such as JSON or XML. The same order can be sent as JSON to a mobile app and as XML to a legacy system.

State transfer

The client changes a resource by sending a new representation of it (PUT or PATCH). The server sends back the current representation. That is the "representational state transfer" in the name.

The six REST constraints and how to test them

ConstraintMeaningWhat a tester checks
Client and serverThe UI and the data storage are separate and evolve independentlyThe API works the same when called from Postman, the app or another service
StatelessEach request carries all the context, such as the token. The server keeps no session between callsSend requests in a random order or from two tools at once. Results must not depend on a previous call
CacheableResponses state whether and how long they can be cachedCache-Control, ETag, 304 responses, and no caching of private data
Uniform interfaceStandard methods, URIs for resources, self descriptive messages, hypermediaCorrect methods and status codes, consistent naming, correct Content-Type
Layered systemGateways, load balancers and caches can sit between client and serverBehaviour is the same through the gateway and directly. Headers are not lost on the way
Code on demand (optional)The server may send executable code, such as JavaScriptRare in APIs. If present, check it is served safely

The Richardson Maturity Model

Leonard Richardson described four levels of REST maturity. Most real APIs sit at Level 2. Pick a level to see what requests look like and what to test.

REST design rules worth checking

Good practice

  • Plural nouns for collections: /orders, /orders/42.
  • Nesting for clear ownership: /customers/7/orders, at most two levels deep.
  • Lowercase with hyphens: /order-items.
  • Filtering, sorting and paging in the query string.
  • Versioning such as /v1 or a version header.
  • Consistent error format across all endpoints.

Common violations to report

  • Verbs in paths: /createOrder, /getUser.
  • Every call is POST, even reads.
  • 200 for every response, with errors hidden in the body.
  • GET requests that change data.
  • Server side sessions that break when a load balancer switches servers.
  • Different names for the same thing, such as userId and user_id.

HATEOAS in one example

HATEOAS means Hypermedia As The Engine Of Application State. The response tells the client what it can do next, through links, so the client does not hard code URLs.

{
  "id": 1042,
  "status": "PLACED",
  "_links": {
    "self":   { "href": "/v1/orders/1042" },
    "pay":    { "href": "/v1/orders/1042/payment", "method": "POST" },
    "cancel": { "href": "/v1/orders/1042", "method": "DELETE" }
  }
}

After payment, the pay link should disappear and a track link may appear. A tester checks that the links match the state. A cancel link on a delivered order is a bug.

Part 5

📨How HTTP carries a request

Most APIs you will test use HTTP (Hypertext Transfer Protocol), and almost always HTTPS, which is HTTP inside an encrypted TLS connection. HTTP is a request and response protocol. The client sends one request, the server sends back one response. HTTP is stateless, so every request must carry everything the server needs, such as the token that says who you are.

Anatomy of a URL

Type any URL below and watch it split into its parts. Path parameters identify a resource. Query parameters filter, sort or page through it.

Anatomy of a request and a response

POST /v1/orders HTTP/1.1          ← request line
Host: api.shop.com                ← headers
Authorization: Bearer eyJhbGci...
Content-Type: application/json
Accept: application/json
                                  ← blank line
{ "productId": 7, "quantity": 2 } ← body
HTTP/1.1 201 Created          ← status line
Content-Type: application/json
Location: /v1/orders/1042
X-Request-Id: 7f3c9a10

{
  "id": 1042,
  "status": "PLACED",
  "total": 1998
}

The journey of one request

Press Play to follow a request from the app to the database and back. Each stop is a place where things can go wrong and where testers look for evidence.

HTTP versions you will meet

VersionWhat changedWhy a tester cares
HTTP/1.1Text based, one request at a time per connection, keep aliveStill the format you read in tools and logs
HTTP/2Binary frames, many requests at once over one connection, header compressionHeader names are always lowercase on the wire. gRPC runs on it
HTTP/3Runs on QUIC over UDP, faster connection setup, better on weak mobile networksMostly invisible to API tests, but matters for performance on mobile
The meaning of methods, status codes and headers is the same in all three versions. It is defined in one document, RFC 9110 (HTTP Semantics), published in 2022.
Part 6

🛠️HTTP methods, safety and idempotency

The method tells the server what you want to do with the resource. Two properties matter a lot for testing. A safe method only reads and never changes data. An idempotent method gives the same server state whether you send it once or ten times. Idempotency matters because networks fail and clients retry.

MethodPurposeBodySafeIdempotentTypical success
GETRead a resource or a listNoYesYes200 OK
POSTCreate a resource or trigger an actionYesNoNo201 Created, 200 or 202
PUTReplace the whole resourceYesNoYes200 or 204
PATCHChange some fieldsYesNoNot guaranteed200 or 204
DELETERemove a resourceRarelyNoYes204 or 200
HEADSame as GET but headers onlyNoYesYes200
OPTIONSAsk which methods are allowed, used by CORS preflightNoYesYes204 or 200

Try it: send the same request three times

Pick a method and press Send repeatedly. Watch the server state. POST creates a new order each time. PUT and DELETE leave the same final state no matter how many times you send them.

Idempotent does not mean the same response. The first DELETE /orders/5 returns 204 and the second returns 404. The server state is the same after both (order 5 is gone), so DELETE is still idempotent.
A GET that changes data, such as GET /orders/5/cancel, is a design bug. Browsers, crawlers and caches may call GET links on their own and cancel real orders. Report it.

🚦Status codes

The three digit status code is the first thing you check. The first digit gives the family.

1xxInformation100 Continue, 101 Switching Protocols (WebSocket upgrade)
2xxSuccessThe request worked
3xxRedirectionLook elsewhere or use your cached copy
4xxClient errorThe request is wrong. Fix the request
5xxServer errorThe server failed. Always a bug or an outage
CodeNameWhen you should see it
200OKA successful GET, or an update that returns the resource
201CreatedA POST created something. A Location header should point to it
202AcceptedWork was queued and will finish later, for example a report export
204No ContentSuccess with an empty body, common for DELETE
301 / 308Moved Permanently / Permanent RedirectThe resource has a new URL. 308 keeps the method and body
304Not ModifiedYour cached copy is still valid (after If-None-Match)
400Bad RequestMalformed JSON, wrong type, missing required field
401UnauthorizedNo credentials, or invalid or expired credentials. It really means unauthenticated
403ForbiddenYou are known, but not allowed to do this
404Not FoundThe resource does not exist, or the API hides that it exists
405Method Not AllowedFor example DELETE on a read only endpoint. An Allow header should list valid methods
409ConflictThe request clashes with current state, such as a duplicate email
412Precondition FailedAn If-Match check failed because someone else changed the resource
415Unsupported Media TypeYou sent XML to an endpoint that only accepts JSON
422Unprocessable ContentValid JSON, but the values break a business rule
429Too Many RequestsYou hit a rate limit. Look for Retry-After
500Internal Server ErrorUnhandled exception. Never acceptable as a response to bad input
502 / 503 / 504Bad Gateway / Service Unavailable / Gateway TimeoutA proxy or gateway could not get a good answer from the service behind it

Game: pick the right status

A 5xx caused by your input is always a bug. Bad input should give a 4xx with a helpful message. When you see a 500 with a stack trace in the body, report two bugs: the missing validation and the information leak.
Part 8

🏷️Headers, cookies and content negotiation

Headers carry metadata about the request or the response. Header names are case insensitive, so content-type and Content-Type are the same header.

HeaderDirectionWhat to test
Content-TypeBothThe format of the body. Send a wrong one and expect 415 or 400, not 500
AcceptRequestThe format you want back. Ask for XML from a JSON only API and expect 406
AuthorizationRequestCredentials such as Bearer <token>. Missing, malformed, expired and wrong user
Cache-Control, ETagResponsePrivate data must not be cached by shared caches. ETag changes when the resource changes
LocationResponsePresent on 201 and redirects, and the URL works
X-Request-Id or traceparentBothA correlation id you can give developers to find the exact log line
Set-CookieResponseSession cookies should have HttpOnly, Secure and a SameSite value
Access-Control-Allow-OriginResponseCORS. A wildcard together with credentials is a security bug
Strict-Transport-SecurityResponseTells browsers to use HTTPS only
Retry-AfterResponseWith 429 or 503, how long to wait before retrying

Content negotiation

The client says what it can read with Accept, and what it is sending with Content-Type. The server picks a format and says what it chose in the response Content-Type. A good API test suite includes at least one case per supported format and one unsupported format.

Request

GET /v1/products/7
Accept: application/xml

Possible responses

200 OK  Content-Type: application/xml
406 Not Acceptable  if XML is not offered
In browser DevTools, open the Network tab, click any request and look at the Headers panel. Right click the request and choose Copy as cURL to replay it in a terminal or import it into Postman. This is the fastest way to start testing an API behind a web page.
Part 9

🧾JSON, XML and other payloads

JSON (JavaScript Object Notation) is the default format for modern APIs. It has six value types: string, number, boolean, null, object and array. Keys must be in double quotes, and trailing commas are not allowed.

{
  "id": 1042,
  "customer": { "name": "Asha", "vip": true },
  "items": [
    { "sku": "PEN-01", "qty": 2, "price": 15.5 }
  ],
  "coupon": null
}
<order id="1042">
  <customer vip="true">
    <name>Asha</name>
  </customer>
  <items>
    <item sku="PEN-01" qty="2" price="15.5"/>
  </items>
</order>

XML is still common in SOAP services, banking and older enterprise systems. Other bodies you will meet are application/x-www-form-urlencoded (classic HTML forms and OAuth token requests), multipart/form-data (file uploads), plain text, and binary files such as PDFs.

Try it: JSON explorer

Edit the JSON, then type a path such as $.items[0].price or $.items[*].sku. The explorer validates the JSON and shows the value and its type. Break the JSON on purpose, for example add a trailing comma, to see the error a server parser would raise.

Data checks testers forget

  • Types: "42" (string) is not 42 (number). A client in a strictly typed language may crash on the wrong one.
  • Null versus missing: "coupon": null and no coupon key at all can mean different things. The contract should say which.
  • Numbers: money as a float such as 0.1 + 0.2 gives 0.30000000000000004. Prefer integers in the smallest unit (paise or cents) or decimal strings. Very large ids above 253 lose precision in JavaScript.
  • Dates: expect ISO 8601 with a time zone, such as 2026-10-20T17:06:25Z.
  • Unicode: send names like Zoë, राकेश and emoji, and check they come back unchanged.
  • Empty values: empty string, empty array, empty object, only spaces.

Postman building blocks

Workspaces and collections

A collection is a folder of saved requests, often one folder per resource. Share it so the whole team tests the same requests.

Environments and variables

{{baseUrl}} and {{token}} switch between dev, QA and staging. Scopes from widest to narrowest: global, collection, environment, data, local. The narrowest wins.

Pre-request scripts

JavaScript that runs before the request, for example to create a timestamp, a random email or a signature.

Post-response scripts (Tests tab)

JavaScript that runs after the response with pm.test and pm.expect. This is where manual testing turns into repeatable checks.

pm.test("status is 201", () => pm.response.to.have.status(201))
pm.test("returns the new order id", () => {
  const body = pm.response.json()
  pm.expect(body.id).to.be.a("number")
  pm.collectionVariables.set("orderId", body.id)
})
pm.test("answers in under 800 ms", () => pm.expect(pm.response.responseTime).to.be.below(800))
Never save real passwords or production tokens in a shared collection. Use the environment's secret variable type or a vault, and keep the current value local so it is not synced.
Part 12

📘Reading API docs and OpenAPI

Your test oracle is the contract. For REST APIs this is usually an OpenAPI document (formerly called Swagger) in YAML or JSON. It lists every path, method, parameter, request body, response, status code and security scheme. Learning to read it is the most valuable skill for a manual API tester, because every line is a test idea.

openapi: 3.1.0
info: { title: ShopLite API, version: 1.4.0 }
paths:
  /orders:
    post:
      summary: Place an order
      security: [ { bearerAuth: [] } ]
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [productId, quantity]
              properties:
                productId: { type: integer, minimum: 1 }
                quantity:  { type: integer, minimum: 1, maximum: 10 }
                note:      { type: string, maxLength: 200 }
      responses:
        "201": { description: Order created }
        "401": { description: Missing or invalid token }
        "422": { description: A rule was broken }

Turn the contract into test ideas

Line in the specTest ideas
security: bearerAuthNo token gives 401. Expired token gives 401. Another user's token cannot see this user's data
required: [productId, quantity]Omit each one in turn. Send null. Send an empty body. Send {}
type: integerSend "2", 2.5, true, [], a very large number
minimum: 1, maximum: 10Boundary values 0, 1, 2, 9, 10, 11 and a negative number
maxLength: 200199, 200 and 201 characters, plus Unicode and HTML
responsesCan you trigger every documented status. Does the API ever return a status that is not documented
Also test what the spec does not say. Send unknown extra fields and see whether they are ignored, rejected with 400, or saved. If they are saved, you may have found the mass assignment bug covered in the security part.
OpenAPI 3.1 (2021) aligned its schemas with JSON Schema. OpenAPI 3.2, released in September 2025, adds support for the QUERY method, streaming responses such as Server-Sent Events, and nested tags. Expect to see 3.0 and 3.1 in most projects today.
Part 13

🔐Authentication and authorization

Authentication answers who you are. Authorization answers what you are allowed to do. A missing or bad identity should give 401. A known identity without permission should give 403 (or 404 if the API hides that the resource exists).

SchemeHow it is sentTester checklist
Basic authAuthorization: Basic base64(user:password)Only over HTTPS. Base64 is encoding, not encryption
API keyA header such as x-api-key, sometimes a query parameterKeys in URLs leak into logs. Revoked keys must stop working
Bearer tokenAuthorization: Bearer <token>Expiry, revocation on logout, token from another environment
JWTA bearer token with three base64url parts: header, payload, signatureChange the payload and the signature must fail. alg: none must be rejected
OAuth 2.0An authorization server issues access tokens with scopesScopes enforced, refresh flow, redirect URI exact match
OpenID ConnectOAuth 2.0 plus an ID token that says who the user isID token audience and expiry
Session cookieCookie: session=...HttpOnly, Secure, SameSite, invalid after logout
mTLSBoth sides present certificatesRequests without the client certificate are refused

Try it: decode a JWT

A JWT is only signed, not encrypted. Anyone can read the payload, so it must never contain secrets. Paste a token or use the sample. The decoder shows the claims and flags common problems.

OAuth 2.0 authorization code flow with PKCE

This is the flow used by web, mobile and single page apps to log a user in with an identity provider. PKCE (Proof Key for Code Exchange) stops a stolen authorization code from being used by another app. Step through it.

Other OAuth flows

  • Client credentials: service to service, no user involved.
  • Device code: smart TVs and command line tools.
  • Refresh token: gets a new access token without logging in again.
  • The implicit and password flows are deprecated and removed in OAuth 2.1.

Authorization tests to always run

  • User A reads user B's resource by changing the id in the URL.
  • A normal user calls an admin endpoint.
  • A token with a read scope tries to write.
  • A token still works after logout or password change.
  • A token from staging is used on production.

✍️Designing API test cases

The test design techniques from manual testing all apply to APIs. The difference is that you control every byte of the request, so you can reach cases the UI never allows.

Positive

Valid input, valid token, expected status and body. Include optional fields both present and absent.

Negative

Missing fields, wrong types, invalid formats, unknown fields, wrong method, wrong content type, malformed JSON.

Boundary value analysis

Test at, just below and just above every limit: lengths, numeric ranges, page sizes, dates.

Equivalence partitioning

Group inputs that should behave the same and test one value from each group.

Decision tables

For rules that combine conditions, such as coupon valid and cart above 500 and user is VIP.

State transitions

An order goes PLACED to PAID to SHIPPED to DELIVERED. Try illegal jumps such as cancelling a delivered order.

Part 15

✅What to check in every response

A 200 status alone proves very little. A response can be 200 and still wrong. Check these layers every time.

1. Status codeExactly the documented one. 201 for create, not 200.
2. HeadersContent-Type, Location, caching, security headers, correlation id.
3. SchemaEvery required field present with the right type. No unexpected fields.
4. Data valuesValues match the request and the database. Totals add up. Dates in the right zone.
5. Business rulesDiscounts applied, stock reduced, status moved to the right state.
6. Side effectsDatabase row, email or event sent, audit log written, and nothing extra.
7. Non functionalResponse time, payload size, no sensitive data, no stack traces.

Verifying in the database

Many API testers have read access to a test database. After POST /orders returns 201 with id 1042, confirm the data really landed.

SELECT id, customer_id, product_id, quantity, total, status
FROM orders WHERE id = 1042

Check that the customer id is the logged in user and not a value from the request body, that the total was calculated by the server and not trusted from the client, and that only one row exists after a retry.

Schema validation in Postman

const schema = {
  type: "object",

Part 17

📄Pagination, filtering and sorting

No API returns a million rows at once. Lists come in pages. There are three common styles.

StyleRequestStrengthWeakness
Offset and limit?offset=40&limit=20 or ?page=3&size=20Jump to any pageRows can repeat or be skipped when data changes between calls. Slow on large offsets
Cursor?after=eyJpZCI6NDB9&limit=20Stable and fast on large dataNo jumping to page 7
Keyset?createdAfter=2026-10-01T00:00:00Z&limit=20Fast with an indexNeeds a unique sort key

Pagination test checklist

  • First page, middle page, last page, and one page past the end (expect an empty list, not an error or the last page again).
  • limit of 0, 1, the maximum, maximum plus one, negative, and not a number. Check that the maximum is enforced.
  • The total count and the number of pages are correct: pages = ceil(total / limit).
  • No duplicates and no missing items when you walk every page and join the results.
  • Insert a record while paging and see whether items shift between pages.
  • Sort by every allowed field in both directions, with ties. Sort by a field that is not allowed.
  • Filters combined with paging, and filters that match nothing.
  • The next link or cursor works and keeps the same filters.
Offset pagination with a changing data set is a classic interview question. If a new item is inserted at the top while you read page 1, the last item of page 1 moves to page 2 and you see it twice. Cursor pagination avoids this.
Part 18

⏱️Rate limits, caching and idempotency keys

Rate limiting

APIs limit how many requests a client can make, to protect the service and to stop brute force attacks. When you exceed the limit you should get 429 Too Many Requests with a Retry-After header. Many APIs also return headers such as X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset.

A common algorithm is the token bucket. The bucket holds up to N tokens and refills at a fixed rate. Each request takes one token. With no tokens left, the request is refused. Click Send quickly to drain it, then wait and watch it refill.

  • Find out whether the limit applies per user, per API key, per IP address, or globally, and whether rotating IPs or keys gets around it.
  • Login, OTP and password reset endpoints should have much stricter limits than others.
  • The counter should reset at the time the headers say.

Caching with ETags

Check that private responses carry Cache-Control: private or no-store, that the ETag changes after an update, and that If-Match with an old ETag returns 412, which protects against lost updates when two people edit the same record.

Idempotency keys

POST is not idempotent, so a retried payment could charge twice. Payment APIs such as Stripe accept an Idempotency-Key header. The server stores the first result for that key and returns it again for any retry.

Test the same key with a different body. A well designed API returns an error such as 422 or 409, because reusing a key for a different payment is a client bug, not a retry.
Part 19

🧯Error handling and Problem Details

Good errors tell the client what went wrong and how to fix it, without leaking internals. The standard format is Problem Details for HTTP APIs, RFC 9457 (2023), which replaced RFC 7807. It uses the media type application/problem+json.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.shop.test/problems/validation",
  "title": "Your request has invalid fields",
  "status": 422,
  "detail": "quantity must be between 1 and 10",
  "instance": "/v1/orders",
  "errors": [ { "field": "quantity", "message": "must be at most 10" } ]
}

Good error response

  • Correct 4xx or 5xx status
  • Same structure for every error
  • Names the field and the rule
  • Has a correlation id for support
  • Same language as the API docs

Bugs to report

  • Stack traces, SQL or file paths in the body
  • 500 for bad input
  • Different error shapes on different endpoints
  • "Something went wrong" with no detail
  • Login errors that reveal whether an email exists

Resilience checks

Ask developers or use a mock to make a dependency slow or broken, then check the API's behaviour. A payment provider timeout should give a clear 502 or 504 and leave the order in a known state, not a half saved one. Retries should use backoff, and a circuit breaker should stop hammering a service that is down.

Generate response times and compare the average with the percentiles. A few slow requests barely move the average but ruin p99, and p99 is what your unluckiest users feel.

Part 22

📬Async APIs: webhooks, polling and queues

Some work takes too long for one request, such as generating a report or processing a video. The API answers 202 Accepted with a job id, and the client either polls a status endpoint or waits for a webhook.

Testing webhooks

  • Point the webhook URL at a request catcher such as webhook.site, or a local server exposed with ngrok, and inspect what arrives.
  • Check the signature header (for example an HMAC of the body) and that a tampered body is rejected by your receiver.
  • Make your endpoint return 500 or time out and confirm the provider retries with backoff.
  • Confirm the receiver handles the same event delivered twice. Most providers guarantee at least once delivery, not exactly once.
  • Events can arrive out of order. "paid" may arrive before "created".

Eventual consistency

In systems built from many services and message queues (Kafka, RabbitMQ, SQS), a write may take a moment to appear in another service. A test that reads immediately after a write may fail by chance. Poll with a timeout instead of a fixed sleep, and report when the delay exceeds what the business accepts.

🤝Contract testing and versioning

When ten teams depend on one API, a small change such as renaming a field can break apps that nobody on the provider team knows about. Contract testing catches this before release.

Consumer driven contracts

Each consumer writes down exactly what it uses (requests and the fields it reads). The provider runs these contracts in its own pipeline. The best known tool is Pact, with a Pact Broker to share contracts and a can-i-deploy check before release.

Provider or schema driven

The OpenAPI document is the contract. Tools compare the running API with the spec, or compare two versions of the spec to flag breaking changes (for example oasdiff).

Try it: is this change breaking

Edit the new version of the response. The checker compares it with the old one and labels each difference as safe or breaking for existing clients.

Versioning and deprecation

StrategyExample
URL path/v1/orders and /v2/orders
HeaderApi-Version: 2026-10-01 (date based, used by Stripe and others)
Media typeAccept: application/vnd.shop.v2+json

When an endpoint is retired, the Deprecation header (RFC 9745, 2025) says it is deprecated and the Sunset header (RFC 8594) gives the date it will stop working. Test that both old and new versions behave as documented until the sunset date, and that the old one really stops afterwards.

🎭Mocks, service virtualization and test data

You often need to test an API whose dependencies are not ready, are expensive (a real payment provider), or cannot be made to fail on demand. A mock server pretends to be that dependency.

ToolUse

What a mock lets you test

  • A dependency that times out after 30 seconds.
  • A dependency that returns 503, then 200 on the retry.
  • Malformed or unexpected data from a partner (OWASP API10).
  • Rare states, such as a card that is declined for insufficient funds.

Test data management

  • Create data through the API in setup, and delete it in teardown.
  • Use unique values (timestamps, UUIDs) so parallel runs do not collide.
  • Never copy real customer data into test environments. Use synthetic or masked data, which privacy laws such as GDPR and India's DPDP Act expect.
  • Keep a small set of known seed records for read only tests.

📡Testing GraphQL, gRPC, WebSocket and SSE

GraphQL

POST /graphql
{
  "query": "query($id: ID!) { order(id: $id) { id total items { sku } } }",
  "variables": { "id": "1042" }

200 OK

  "errors": [ { "message": "Not authorized",

}
  • Errors usually come back with status 200 and an errors array. Always check the body, not only the status.
  • Test field level authorization. A customer must not be able to query order { customer { email } } for another user's order.
  • Deeply nested queries and huge lists can overload the server. Check depth limits, complexity limits and query timeouts.
  • Introspection (__schema) is often turned off in production. Check it is.
  • Batching many operations in one request can bypass rate limits on login mutations.

gRPC

grpcurl -plaintext localhost:50051 list

gRPC has its own status codes such as OK, INVALID_ARGUMENT, NOT_FOUND, PERMISSION_DENIED, UNAUTHENTICATED, RESOURCE_EXHAUSTED and DEADLINE_EXCEEDED. Test deadlines (timeouts set by the client), and for streaming calls test early cancel and a stream that ends with an error.

WebSocket and Server-Sent Events

  • Connect without a token, with an expired token, and with a token that expires during the session.
  • Send malformed messages and very large messages.
  • Drop the network and reconnect. Check whether missed messages are replayed, and in the right order.
  • For SSE, check the text/event-stream content type, the data: lines, and resume with Last-Event-ID.

🤖Testing AI and LLM APIs and MCP servers

More and more products call large language model (LLM) APIs, or expose their own AI endpoints. These APIs behave differently from classic ones, and testers need new techniques.

DifferenceHow to test it
Non deterministic outputThe same prompt can give different words. Assert on structure, required facts and rules, not on exact text. Run the same case several times
Streaming responsesAnswers arrive as Server-Sent Events. Check the event order, the final event, and what happens if the stream is cut

Evaluations

Teams build an eval set: a list of inputs with the facts or rules each answer must satisfy. Each release is scored against it. Checks can be exact (the JSON parses, the order id is present), rule based (no phone numbers in the output), or graded by another model against a rubric. A manual tester's job is to design the cases, especially the tricky and adversarial ones.

MCP servers

The Model Context Protocol (MCP), introduced by Anthropic in late 2024, is an open standard that lets AI apps connect to tools and data through MCP servers. A server exposes tools, resources and prompts over JSON-RPC 2.0, using a local stdio connection or the Streamable HTTP transport.

{ "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": { "name": "get_order", "arguments": { "orderId": 1042 } } }
  • Call tools/list and check every tool has a clear description and an input schema.
  • Send arguments that break the schema. Expect a JSON-RPC error or a tool error result, not a crash.
  • Authorization: a remote MCP server must check that the user behind the AI is allowed to see order 1042, exactly like a normal API (BOLA again).
  • Tool results that contain instructions are a prompt injection risk for the AI that reads them.
  • The MCP Inspector tool lets you connect to a server and call its tools by hand.

🗺️An API test strategy and great bug reports

A strategy that scales

  1. Understand: read the spec, the user stories and the architecture diagram. List every endpoint, consumer and dependency.
  2. Prioritize by risk: money, personal data, authentication and the busiest endpoints first.
  3. Design: positive, negative, boundary, authorization, state and flow cases for each endpoint.
  4. Explore: timebox sessions with a charter, for example "Explore order cancellation with two users and stale data to find authorization and state bugs".
  5. Automate what is stable: move repeatable checks into a collection or code, and run them in CI.
  6. Measure: endpoint coverage, status code coverage, defects found by layer, escaped defects.
  7. Monitor: synthetic checks and alerts in production.

An API bug report that gets fixed fast
