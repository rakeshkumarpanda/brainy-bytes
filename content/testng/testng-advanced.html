Listeners, Retries, Factories and Framework Design

A suite that runs every night needs more than assertions. It needs a screenshot when something fails, a second chance for a timeout on a slow server, the same checks for every language or role, and a clean structure so that one change in the login page touches one file. This page builds those pieces on real TestNG.

Part 1

👂Listeners

A listener is a class TestNG calls on every test event: start, success, failure, skip, and the start and end of each <test>. Frameworks use it to take a screenshot when a test fails, write logs, or feed a report, without adding a single line to the tests themselves.

Way to registerCode
On a class@Listeners(ScreenshotListener.class)
For the whole suite<listeners><listener class-name="com.shop.ScreenshotListener"/></listeners> in testng.xml
AutomaticallyA META-INF/services/org.testng.ITestNGListener file listing the class
In a real suite, onTestFailure gets the driver from the test instance (result.getInstance()) and calls ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE). In pytest the same job is done by the pytest_runtest_makereport hook in conftest.py, and in Mocha by an afterEach that checks this.currentTest.state.
Part 2

🔁Retrying flaky tests

An IRetryAnalyzer decides whether a failed test gets another attempt. It suits failures caused by the environment, such as a slow test server or a network blip. It never fixes a real bug: a wrong total fails on every attempt.

Retries hide problems if nobody looks at them. Count and report retried tests, keep the limit low (one or two), and treat a test that needs retries every night as a defect in the test or the environment.
Part 3

🏭@Factory: one class, many instances

A data provider repeats one method with different arguments. A factory repeats a whole class: it returns several instances, each built with different constructor data, and every @Test of the class runs on every instance. That fits "run this whole checklist for each language" or "for each user role".

@Factory(dataProvider = "roles") on a constructor combines both ideas: the provider supplies the rows and the factory builds one instance per row.
Part 4

⏭️Conditional skips

Sometimes a test cannot run meaningfully: the payment sandbox is down, or a destructive test must never run outside the QA environment. Throwing SkipException marks the test as skipped with a reason, which is honest: it did not pass and it did not find a product bug.

Part 5

🏗️A framework: Page Objects and a BaseTest

In the Page Object Model, each page of the application gets a class that holds its locators and actions, such as loginAs(user, pass). Tests talk to pages, never to locators. When a button's id changes, one page class changes and every test keeps working. A BaseTest class creates and quits the driver, so test classes only extend it.

src/test/java/com/shop/
  base/BaseTest.java            driver setup and teardown, ThreadLocal<WebDriver>
  pages/LoginPage.java          locators and actions, no assertions
  pages/CartPage.java
  tests/LoginTests.java         assertions only, extends BaseTest
  listeners/ScreenshotListener.java
  utils/ConfigReader.java       reads config.properties
src/test/resources/
  config.properties  testdata/login.csv  testng.xml
Keep assertions in tests and out of page objects. A page method returns what it sees, and the test decides whether that is right, so the same page can serve positive and negative tests.
Part 6

📊Reports, reruns and CI

File after a runUse
emailable-report.htmlA single page summary to attach or email
index.htmlThe full browsable report
testng-results.xmlMachine readable results that CI servers and report tools import
testng-failed.xmlA ready suite with only the failed and skipped tests: run it to rerun the failures
<!-- pom.xml, inside <build><plugins> -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <version>3.2.5</version>
  <configuration>
    <suiteXmlFiles><suiteXmlFile>testng.xml</suiteXmlFile></suiteXmlFiles>
  </configuration>
</plugin>

mvn test                          runs the suite
mvn test -Dbrowser=firefox        passes a system property the ConfigReader can read

A CI server such as Jenkins or GitHub Actions runs mvn test on every change or every night, publishes testng-results.xml as test results, and keeps the screenshots and HTML reports as build artifacts. Many teams add Extent Reports or Allure on top, both of which plug in as TestNG listeners.
