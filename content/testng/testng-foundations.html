TestNG Foundations: Annotations, Assertions and Test Control

A main method can run checks, but it cannot report which ones passed, skip the rest when setup fails, or rerun only the failures. TestNG does all of that through annotations. Every example on this page runs on real TestNG, and the same idea is shown in pytest and Mocha, so you can compare the three most common test runners for testers.

Test classes go in src/test/java. Run them from the IDE (right click, Run), from a testng.xml file, or with mvn test, where the Maven Surefire plugin finds the tests. After a run, TestNG writes its reports to test-output (or target/surefire-reports with Maven), including emailable-report.html and testng-failed.xml.

The examples here run on TestNG 6.9, which is what this site's code runner has. Everything shown works the same in TestNG 7, the version to use in new projects. In pytest the same roles are played by test functions and fixtures, in Mocha by describe, it and hooks.
Part 2

✅A first test class

A test method is a public void method marked @Test. It calls the code under test and checks the result with an assertion. If every assertion holds, the test passes. The first assertion that fails throws an AssertionError, and TestNG records the test as failed and moves on to the next one.

TestNG's Assert.assertEquals(actual, expected) takes the actual value first. JUnit uses the opposite order. Swapping them still passes and fails correctly, but the failure message then says "expected 3 but found 4", which sends you looking in the wrong place.

🔄The annotation lifecycle

AnnotationRunsTypical use in UI automation
@BeforeSuite / @AfterSuiteOnce for the whole runStart and close the report, load configuration
@BeforeTest / @AfterTestOnce per <test> tag in testng.xmlSet the browser for that block of tests
@BeforeClass / @AfterClassOnce per test classLaunch and quit the browser
@BeforeMethod / @AfterMethodBefore and after every @TestOpen the start page, clear cookies, take a screenshot on failure
pytest builds the same layers with fixture scopes: session, module, class and function. The code before yield is the setup, the code after it the teardown. Mocha has before, beforeEach, afterEach and after.
Part 4

⚖️Hard and soft assertions

Hard assert (Assert)

Stops the test at the first failure. Use it when the remaining steps make no sense after a failure, for example when login itself failed.

Soft assert (SoftAssert)

Records each failure and keeps going. assertAll() at the end fails the test with every problem listed. Use it to check many fields on one page.

Forgetting soft.assertAll() is a classic bug: every check fails silently and the test still passes. Create a new SoftAssert inside each test, never share one between tests.
Part 5

🏷️Test attributes

AttributeEffect
priority = 1Lower numbers run first. The default is 0, and negative values are allowed
enabled = falseThe test is not run at all and not counted
description = "…"Text shown in the reports
timeOut = 200Fails the test if it takes longer than 200 milliseconds
invocationCount = 3Runs the same test 3 times (add threadPoolSize to run them in parallel)
expectedExceptions = X.classThe test passes only if X is thrown. With expectedExceptionsMessageRegExp, the message must match too

Without priorities, TestNG runs test methods of a class in alphabetical order, not in the order they are written. Tests should not depend on that order. When order matters, say so with priority or dependsOnMethods.

Part 6

🔗Dependencies between tests

dependsOnMethods makes a test wait for others and run only if they passed. If a dependency fails, the dependent test is skipped, not failed, so the report shows one real failure instead of a cascade of misleading ones. alwaysRun = true turns it into a soft dependency: run after, but run anyway.

Prefer independent tests. Each one should prepare its own state, for example by logging in through an API in @BeforeMethod. Dependencies make sense for real end to end flows, where a later step truly cannot start without the earlier one.
