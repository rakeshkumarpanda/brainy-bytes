Part 1

🔎First, the name: there is no rules.md

🧒 Beginner friendly📄 .claude/rules/📄 ~/.claude/rules/

Many guides and videos talk about a "rules.md" file. Claude Code does not read a file with that name. What it does have is a folder of rule files:

❌ Not a Claude Code filerules.md at the project root does nothing on its own.
✅ What really exists.claude/rules/*.md in the project and ~/.claude/rules/*.md for you. Any number of Markdown files, one topic each.
Other tools have their own rule files, such as a .cursorrules file. Those are not read by Claude Code either. To reuse one, copy its contents into a file in .claude/rules/ or import it from CLAUDE.md with @.
Part 2

🧱Create your first rules, step by step

🧒 Beginner friendly📄 .claude/rules/code-style.md📄 .claude/rules/security.md
  1. In your project, create the folder .claude/rules/.
  2. Add one Markdown file per topic, with a clear name like testing.md or security.md.
  3. Write short, checkable bullet points, just like in CLAUDE.md.
  4. Optional: add a paths list at the top so the rule loads only for matching files.
  5. Start a new session and run /context to see which rules loaded.
A project with rules · 📂 Folder layout
your-project/
├── CLAUDE.md                    <- short: commands and the big picture
└── .claude/
    └── rules/
        ├── code-style.md        <- no paths: loads every session
        ├── security.md          <- no paths: loads every session
        ├── testing.md           <- paths: tests only
        ├── backend/
        │   └── api.md           <- paths: src/api only
        └── content/
            └── blog.md          <- paths: blog posts only

Claude Code finds every .md file in .claude/rules/, including subfolders like backend/. A rule without paths loads at launch with the same priority as .claude/CLAUDE.md.

.claude/rules/code-style.md (no paths, always loaded) · 📄 Ready to copy
# Code style
- TypeScript strict mode. No `any`.
- Name files in kebab-case: `order-summary.ts`.
- Prefer small pure functions. Keep side effects at the edges.
Part 3

🎯Path rules: load only for matching files

📄 .claude/rules/backend/api.md

Add YAML front matter with a paths list. The rule then loads only when Claude reads, writes or edits a file that matches one of the patterns. paths is the only field rules use. Any other field is ignored.

.claude/rules/backend/api.md (loaded for API files) · 📄 Ready to copy
---
paths:
  - "src/api/**/*.ts"
---

# API rules
- Validate every request body with the schemas in `src/api/schemas/`.
- Errors use the shape `{ error: { code, message } }` with a 4xx or 5xx status.
- Every new endpoint gets an entry in `docs/openapi.yaml`.
PatternMatches
**/*.tsevery TypeScript file, in any folder
src/**/*everything under src/
*.mdMarkdown files in the project root only
src/**/*.{ts,tsx}both .ts and .tsx under src/

You can write paths as a list, or as one comma separated string.

Which rules load for which file · ▶ Runs a model of rule loading on the five rule files above
📄 which-rules.mjs
// A model of how Claude Code picks rules: a rule with no paths loads at launch,
// a rule with paths loads when Claude reads, writes or edits a matching file.
import { readFileSync, readdirSync } from "node:fs";
import { join, matchesGlob } from "node:path";

function rules(dir) {
  return readdirSync(dir, { recursive: true }).filter(f => f.endsWith(".md")).map(f => {
    const text = readFileSync(join(dir, f), "utf8");
    const front = text.match(/^---\n([\s\S]*?)\n---/);
    const paths = front ? [...front[1].matchAll(/^\s*-\s*"(.+)"/gm)].map(m => m[1]) : [];
    return { file: f, paths };
  });
}

const all = rules(".claude/rules");
console.log("At launch:", all.filter(r => !r.paths.length).map(r => r.file).join(", "));
for (const touched of ["src/api/orders.ts", "tests/cart.test.ts", "README.md", "content/blog/diwali-sale.md"]) {
  const extra = all.filter(r => r.paths.some(p => matchesGlob(touched, p))).map(r => r.file);
  console.log(`Claude edits ${touched.padEnd(28)} -> also loads: ${extra.join(", ") || "(nothing new)"}`);
}

🧾Ready to copy rule files

🧒 Beginner friendly📄 .claude/rules/testing.md📄 .claude/rules/content/blog.md📄 .claude/rules/contracts.md

Rules are not only for code. Any team that keeps files in a folder can use them.

.claude/rules/testing.md (loaded for test files) · 📄 Ready to copy
---
paths:
  - "tests/**/*.test.ts"
  - "src/**/*.test.ts"
---

# Testing rules
- Use Vitest. One `describe` per function, plain English test names.
- No real network calls. Use the fakes in `tests/fakes/`.
- Run only the changed file: `npx vitest run <file>`.
.claude/rules/content/blog.md (for a content team) · 📄 Ready to copy
---
paths:
  - "content/**/*.md"
---

# Blog writing rules
- Title under 60 characters. One H1 only.
- Every post ends with a call to action linking to /shop.
- Prices in rupees as "Rs 499", never "INR 499".
.claude/rules/contracts.md (comma separated paths, for a legal team) · 📄 Ready to copy
---
paths: "contracts/**/*.docx, contracts/**/*.pdf"
---

# Contract review rules
- Flag any clause with unlimited liability or auto renewal longer than 12 months.
- Quote the exact clause number for every point you raise.
- Our standard payment term is 30 days. Flag anything longer.
  • One topic per file, with a name that says what it covers.
  • Rules that apply everywhere: no paths.
  • Rules for one area: paths that match that area.
  • Short, concrete bullets that can be checked.
Part 5

🙋Personal rules in ~/.claude/rules/

🧒 Beginner friendly📄 ~/.claude/rules/

Rules in your home folder apply to every project on your machine. They load before project rules. Neither overrides the other, so if they disagree Claude may follow either. Keep them consistent.

Personal rules for every project · 📂 Your home folder
~/.claude/rules/
├── preferences.md     # "Answer with the command first, then one line of explanation"
└── git.md             # "Never force push. Explain any rebase before running it."
Part 6

🔗Share one set of rules across many projects

📄 .claude/rules/

The rules folder follows symlinks, so a company can keep its standards in one place and link them into every repository.

Share rules between projects with symlinks · ⌨️ Type this in your terminal
# keep company rules in one folder and link them into each project
ln -s ~/company-standards/security.md .claude/rules/security.md
ln -s ~/shared-claude-rules .claude/rules/shared
What happens

The first session asks you once to approve rules linked from outside the project. After approval, linked rules without paths load. Rules in ~/.claude/rules/ need no approval.

A path rule joins the conversation when its file is touched, so /compact summarises it away with everything else. It loads again the next time Claude touches a matching file. If a rule must survive compaction, remove its paths or move it to the root CLAUDE.md.
Part 8

🩺When a rule does not seem to work

📄 .claude/rules/
Check that your rules load · ⌨️ Type this in your terminal
/context          # rules that loaded appear in the memory files list
/memory           # open and edit rule files
claude --debug    # shows a YAML parse error if a rule's frontmatter is broken
What happens

A rule whose frontmatter does not parse is loaded as if it had no paths, so it loads every session. --debug shows why.

  • Never loads? Check the path pattern. *.md matches only the root folder. Use **/*.md for every folder.
  • Always loads? The front matter may not parse, for example a missing closing ---. Then the rule loads as if it had no paths.
  • Loads but is ignored? Look for a rule elsewhere that says the opposite. Run /doctor prompt-audit.
