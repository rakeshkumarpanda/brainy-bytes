Part 1

🤖What a subagent is

🧒 Beginner friendly📄 .claude/agents/

A subagent is a helper that Claude can hand a task to. It has its own context window, its own instructions and its own allowed tools. It does the work, then sends back only a short result. Your main conversation stays small and focused.

Use a subagent when...Stay in the main chat when...
a task reads many files or long logsyou need quick back and forth
you want a specialist with fixed rules, like a reviewerseveral steps share a lot of context
several independent searches can run in parallelthe change is small and quick

Part 3

🛠️Create your first subagent, step by step

🧒 Beginner friendly📄 .claude/agents/code-reviewer.md📄 ~/.claude/agents/
  1. Decide the scope: ~/.claude/agents/ for you in every project, or .claude/agents/ for the team.
  2. Ask Claude to write it, or create a Markdown file yourself.
  3. Check the front matter: name and description are required.
  4. Write the body. It becomes the agent's system prompt.
  5. Try it: "Use the code-reviewer agent to check my changes".
Ask Claude to write the agent file for you · 💬 Prompt to try
Create a personal code-improver subagent in ~/.claude/agents/ that scans
files and suggests improvements for readability, performance, and best
practices. It should explain each issue, show the current code, and
provide an improved version. Make it read-only and have it use Sonnet.
What happens

Claude writes ~/.claude/agents/code-improver.md with a name, description, a read-only tools list, model: sonnet and a system prompt. You review it and keep or edit it.

.claude/agents/code-reviewer.md · 📄 Ready to copy
---
name: code-reviewer
description: Expert code reviewer. Use right after writing or changing code, and before any commit.
tools: Read, Grep, Glob, Bash
model: sonnet
---

You are a senior code reviewer for this repository.

When invoked:
1. Run `git diff` to see recent changes and focus on the changed files.
2. Check for: unclear names, duplicated code, missing error handling,
   secrets in code, missing input validation and missing tests.
3. Report findings in three groups: Must fix, Should fix, Nice to have.
   For each, give the file, the line and a concrete fix.

Be specific and brief. Do not rewrite files yourself.
This is the real "agents.md" people talk about: not one file, but one Markdown file per agent inside .claude/agents/. A root level AGENTS.md is something else: shared project instructions (chapter 5).

Part 5

🗂️Ready to copy agents

🧒 Beginner friendly📄 .claude/agents/test-runner.md📄 .claude/agents/doc-researcher.md
.claude/agents/test-runner.md · 📄 Ready to copy
---
name: test-runner
description: Runs the test suite and fixes failing tests. Use proactively after code changes or when the user mentions failing tests.
tools: Read, Edit, Bash, Grep, Glob
model: inherit
maxTurns: 25
---

You run tests and fix failures.

1. Run the smallest test command that covers the change (see CLAUDE.md).
2. For each failure, find the cause in the code under test, not in the test.
3. Fix it, rerun, and repeat until green.
4. Reply with: what failed, the cause, the fix, and the final test summary.

Never delete or skip a test to make it pass.
.claude/agents/doc-researcher.md · 📄 Ready to copy
---
name: doc-researcher
description: Reads long documents, policies or reports and returns a short cited summary. Use when a question needs many files read.
tools: Read, Grep, Glob, WebFetch
model: haiku
color: cyan
---

You research questions in documents and return only what matters.

- Search first, then read only the relevant sections.
- Return at most 10 bullet points.
- Cite the file and heading for every point.
  • Description: when to use it, in the words people use.
  • Tools: only what the job needs. A reviewer does not need Edit.
  • Model: haiku for quick reading jobs, sonnet or inherit for real work.
  • Body: numbered steps, what to return and in what shape, and the one or two things it must never do.
Part 6

📣Calling a subagent

🧒 Beginner friendly
Three ways to call a subagent · 💬 Prompt to try
Use the test-runner subagent to fix the failing checkout tests
@"code-reviewer (agent)" look at my changes to src/payments
Use 3 doc-researcher subagents in parallel: one on the leave policy, one on travel, one on expenses
What happens

The first lets Claude decide to delegate. The @-mention makes sure that exact agent runs. The third runs three helpers at once, each returning a short summary.

Run a whole session as one agent · ⌨️ Type this in your terminal
claude --agent code-reviewer        # the whole session runs as that agent
/agents                             # prints a reminder of where agent files live
What happens

With --agent, the agent's system prompt, tools and model apply to the main conversation. Setting "agent": "code-reviewer" in .claude/settings.json makes it the project default.

🧑‍⚖️ Real scenario: a policy questionAn HR manager asks "can a new joiner take leave in their first month and get travel paid for a training?". Claude starts two doc-researcher agents in parallel on the leave and travel policies. Each returns five cited bullets. The answer arrives with exact clause references and the main chat stays short.
Part 7

🧠Agents that remember

📄 .claude/agents/support-triage.md

With memory set, the agent keeps its own notes folder and gets better over time, for example learning which support issues keep coming back.

An agent that remembers between sessions · 📄 Ready to copy
---
name: support-triage
description: Triages new support tickets by product area and urgency. Use for any batch of tickets.
tools: Read, Grep
memory: project
---

Sort each ticket into: billing, delivery, product, account.
Mark urgency as P1 (money or data at risk), P2 (blocked) or P3 (other).
Check your memory for recurring issues and update it with new patterns you see.
  • user: notes shared across all your projects.
  • project: notes for this project, can be shared with the team.
  • local: notes for this project on your machine only.
Part 8

🎨Output styles: change how Claude talks for a whole session

🧒 Beginner friendly📄 ~/.claude/output-styles/📄 .claude/output-styles/

An output style changes Claude's role, tone and answer format for the session. Four built-in styles sit on top of the Default:

StyleWhat changes
Proactivestarts work right away and makes reasonable assumptions
Conciseleads with the result, no preamble or recap
Explanatoryadds short "Insight" notes explaining the choices
Learningexplains and leaves small pieces of code for you to write

Make your own in ~/.claude/output-styles/ or .claude/output-styles/. Set keep-coding-instructions: true if Claude will still write code.

~/.claude/output-styles/teach-me.md · 📄 Ready to copy
---
name: Teach me
description: Explains every step in plain words for a beginner and checks understanding
keep-coding-instructions: true
---

You are working with a beginner who is learning while you work.

- Before each change, say in one sentence what you are about to do and why.
- After each change, explain any new word or command in plain English.
- Every few steps, ask one short question to check understanding.
- Keep the actual work the same quality as usual.
Switch output styles · ⌨️ Type this in your terminal
/output-style                 # list styles and see the current one
/output-style concise         # switch to a built-in style
/output-style "Teach me"      # switch to your own style
What happens

The choice is saved to .claude/settings.local.json as "outputStyle". Set it in ~/.claude/settings.json to make it your default everywhere.
