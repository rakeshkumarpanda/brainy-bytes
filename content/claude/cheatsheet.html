Meet Claude: Models, Tokens, Projects and Skills

Open chapter

What Claude is, where you can use it, the four current models and what they cost, tokens and the context window, how a chat really works, and how claude.ai Projects and Skills save you from repeating yourself.

Key ideas

  • What Claude is, in plain words Claude is an AI model made by Anthropic. You write to it in normal language and it writes back. It can read and write text, look at images and PDFs, write and run code, and use tools you connect to it.
  • The Claude models and when to pick each Claude comes in a family of models. Bigger models think more deeply. Smaller ones are faster and cheaper. All four current models read up to 1 million tokens at once and can write up to 128 thousand tokens in one answer.
  • Tokens and the context window Claude does not read letters or whole words. It reads tokens , which are small pieces of text. A short word is usually one token. A long word may be two or three.
  • How a conversation really works Claude has no hidden memory between messages. Each time you press send, the app sends the whole conversation so far , and Claude reads all of it again before replying.
  • Your first useful prompt A good prompt says who you are , what you have , what you want and what shape the answer should take . Here is one a home baker could send on any Sunday.
  • claude.ai Projects: instructions plus knowledge A Project in claude.ai is a folder for chats about one topic. It has two places to put information:
  • Skills: teach Claude a task once A Skill is a folder with a file called SKILL.md . The file has a short name and description at the top and the steps for one task below. Claude reads only the name and description at first. When a request matches, it opens the full file.

Prompt Engineering That Works

Open chapter

The techniques from Anthropic's own prompting guide, each with a real daily task: clear instructions, reasons, examples, XML tags, roles, output format, thinking, templates and prompt chains.

Key ideas

  • Be clear and direct Anthropic's own advice is to treat Claude like a brilliant but new employee . It is very capable, but it does not know your customers, your style or what "good" means to you.
  • Say why, not only what Claude follows a rule better when it knows the reason. A bare rule covers one case. A reason lets Claude handle cases you did not think of.
  • Show examples Examples are one of the most reliable ways to control format and tone. This is called few shot or multishot prompting.
  • Use XML tags to separate the pieces A prompt often mixes instructions, background, examples and data. Put each kind in its own tag, such as <instructions> , <context> or <notes> . There are no magic tag names. Pick clear ones and use them the same way every time.
  • Give Claude a role One sentence about who Claude is for this task changes tone and focus. In the API this goes in the system prompt . In claude.ai it goes in project instructions. In Claude Code the closest place is CLAUDE.md or an output style.
  • Control the format of the answer Tell Claude the exact shape: a numbered list, a table, JSON, a word limit, a closing line. Showing the shape works even better.
  • Let Claude think before answering For sums, comparisons and decisions, ask Claude to work through the problem first. Tags make it easy to keep the working separate from the final answer, so a script can read just the answer.
  • Prompt templates for daily work When you send the same kind of prompt every day, turn it into a template with blanks in double braces. Fill the blanks each time. Later, the same template becomes a skill (chapter 7) or a line in a script (chapter 11).
  • Chain prompts: draft, review, refine Big jobs go better in steps. The most useful chain is self correction : one prompt drafts, one checks the draft against a list, one rewrites. You can read each step and stop if something is off.
  • A recipe card for any prompt

Context Engineering: The Right Information at the Right Time

Open chapter

Why a focused context beats a full one, how to write instructions at the right altitude, just in time retrieval, compaction, progress notes and subagents, and the context commands in Claude Code.

Key ideas

  • Context engineering in one sentence Prompt engineering is about how you ask . Context engineering is about everything Claude can see when it answers: instructions, files, tools, past messages and notes.
  • Why more is not always better Claude's attention is a limited budget . Every extra token takes a little of it. As the window fills, the model gets slightly worse at recalling any one fact. Anthropic calls this context rot .
  • Write instructions at the right altitude A system prompt, CLAUDE.md or SKILL.md can be too low (a long list of brittle if this then that rules) or too high (vague advice that assumes Claude knows your business).
  • Tools and examples are context too Every tool Claude has comes with a name and description that sit in the context. Good tool sets are small , do not overlap and have clear names . If a human could not say which of two tools fits a job, Claude cannot either.
  • Just in time retrieval Do not paste everything up front. Give Claude light pointers such as file paths, a list of document titles or a search tool, and let it load details only when a question needs them.
  • Long tasks: compaction, notes and subagents Some jobs run for hours and outgrow any window. Three techniques keep them on track.
  • Context tools in Claude Code Claude Code gives you direct control over the window.
  • A context checklist for any task

Claude Code: First Steps

Open chapter

Install Claude Code, run your first session, see how the agent loop works, choose permission modes, follow the explore, plan, code, commit workflow, undo safely, and learn where every Claude Code file lives.

Key ideas

  • What Claude Code is Claude Code is Claude working as an agent inside a folder on your computer. It can read your files, search them, edit them, run commands such as tests, and use git. You describe the goal in plain words.
  • Install and start, step by step
  • How it works: the agent loop For each request, Claude repeats a simple loop: gather context (search and read), take action (edit, run a command), check the result , then decide the next step. It stops when the task is done or it needs you.
  • Permission modes: how much Claude may do alone The permission mode decides which actions Claude can take without asking. Press Shift+Tab to switch during a session, or set defaultMode in settings.json (chapter 8).
  • Explore, plan, code, commit Anthropic's recommended workflow for anything bigger than a one line fix has four steps. The first two happen in plan mode , so nothing changes until you agree.
  • Stop, undo and come back later
  • The commands you will use most Two more shortcuts: type @ and a file name to point Claude at a file, and press the up arrow for your earlier requests.
  • The .claude folder: where everything lives Claude Code reads settings and instructions from two places: your project (shared with your team through git) and your home folder (just for you, in every project). The rest of this module fills in each file.

CLAUDE.md and Memory: What Goes Where

Open chapter

Exactly what to put in CLAUDE.md and what to leave out, the four places it can live and the order they load in, @ imports, CLAUDE.local.md, AGENTS.md, auto memory, and how to create and maintain it with /init, /memory and a prompt audit.

Key ideas

  • What CLAUDE.md is for CLAUDE.md is a plain Markdown file of instructions Claude Code reads at the start of every session . Write down what you would otherwise explain again and again: how to run the project, the house rules, the traps.
  • Where CLAUDE.md files live Claude Code loads these from the folder you start in and every folder above it , joined from the top down. A CLAUDE.md inside a subfolder loads later, when Claude reads or edits a file in that subfolder.
  • What to put in, and what to leave out This table comes from Anthropic's best practices guide. For every line, ask: would removing this cause Claude to make mistakes? If not, cut it.
  • Three real CLAUDE.md files Each file is short, specific and written for its own audience. Copy the one closest to your work and change the details.
  • Your personal files: ~/.claude/CLAUDE.md and CLAUDE.local.md Some instructions are about you , not the project. Keep them out of the team file.
  • Split a long file with @ imports Write @path/to/file anywhere in a CLAUDE.md to pull another file in. Paths are relative to the file that contains the import. Imported files may import others, up to four hops deep. A path inside backticks is not imported.
  • AGENTS.md and other tools Some teams already have an AGENTS.md file for other coding tools. Claude Code reads it as project instructions only when there is no CLAUDE.md , .claude/CLAUDE.md or CLAUDE.local.md in your folder or above it. If you have both, only the CLAUDE.md files load.
  • Auto memory: notes Claude writes for itself Besides your CLAUDE.md , Claude Code keeps its own notes per project. When you correct it ("use PowerShell, not bash"), it may save that so you do not have to repeat it next week.
  • Create, check and improve it

Rules: The .claude/rules Folder and Path Rules

Open chapter

Why there is no rules.md, how to build a .claude/rules/ folder step by step, path rules that load only for matching files, ready to copy rules for code, content and contracts, a screenshot guide, rule files for a QA engineer and for a developer, personal and shared rules, and how to choose between rules, CLAUDE.md, skills and hooks.

Key ideas

  • First, the name: there is no rules.md Many guides and videos talk about a "rules.md" file. Claude Code does not read a file with that name. What it does have is a folder of rule files:
  • Create your first rules, step by step Claude Code finds every .md file in .claude/rules/ , including subfolders like backend/ . A rule without paths loads at launch with the same priority as .claude/CLAUDE.md .
  • Path rules: load only for matching files Add YAML front matter with a paths list. The rule then loads only when Claude reads, writes or edits a file that matches one of the patterns. paths is the only field rules use. Any other field is ignored.
  • Ready to copy rule files Rules are not only for code. Any team that keeps files in a folder can use them.
  • Set up QA and developer rules, with screenshots This is the real setup of the rule files from the next two parts, in a small Python shop app. Both pictures are real terminal output.
  • Rule files for a QA engineer Testers repeat the same team standards in every chat: our ID format, no time.sleep , check the status code first. Put each standard in a rule with paths , and it appears exactly when Claude works on that kind of file.
  • Rule files for a developer Developers need two kinds of rules: a few that apply to all code, and some that matter only in risky places such as database migrations.
  • Personal rules in ~/.claude/rules/ Rules in your home folder apply to every project on your machine. They load before project rules. Neither overrides the other, so if they disagree Claude may follow either. Keep them consistent.
  • Share one set of rules across many projects The rules folder follows symlinks, so a company can keep its standards in one place and link them into every repository.
  • Rules, CLAUDE.md, skills or hooks?
  • When a rule does not seem to work

Skills: Build SKILL.md Step by Step

Open chapter

Build a skill from an empty folder with a screenshot for every step, learn where skills live and how they are named, every front matter field, arguments and live command output, supporting files and scripts, who can start a skill, ready to copy skills for a QA engineer's day and a developer's day, and how to upload a skill to claude.ai.

Key ideas

  • What a skill is A skill is a folder with a file called SKILL.md . The top of the file has a short description of when to use it. The rest has the steps . Claude Code, claude.ai and the API all use this format.
  • Build your first skill in three steps The line !`git diff HEAD` is dynamic context : Claude Code runs the command first and pastes the output into the skill, so Claude reads your real changes.
  • Set up a skill in Claude Code, with screenshots Here is the whole setup for a real QA skill, pick-regression , one screen at a time. The terminal pictures are real output from a real run. Use the numbers or the Back and Next buttons to move between steps.
  • Where skills live and how they get their name
  • The front matter: what goes at the top Every field is optional, but description matters most: Claude reads it to decide when to use the skill. Put the main use first and include the words people actually type.
  • Arguments and live data Text typed after the skill name becomes its arguments. Use $ARGUMENTS for all of it, $0 , $1 for each word (counting from zero), or names listed in arguments . Lines with !`command` are replaced by the command's output before Claude sees the skill.

Open chapter

The five settings levels and which one wins, allow, ask and deny rules and how they are matched, ready to copy settings files for the team, for you and for your machine, and four real hooks that block commands, protect files, add live facts and log edits, each run with the JSON Claude Code sends.

Key ideas

  • The settings files and which one wins Settings are plain JSON files. Each one has a different reach. When two files set the same key, the higher one in this list wins. Lists such as permission rules are combined from all files.
  • Permission rules: allow, ask and deny A rule names a tool, and optionally what it may touch: Bash(pytest *) , Read(./.env) , Edit(app/**) , WebFetch(domain:example.com) . A * matches anything.
  • Ready to copy settings files A safety detail: defaultMode values auto and bypassPermissions are ignored in project files, so a repository cannot switch your safety checks off. Allow rules in a project file apply only after you trust the folder. Deny and ask rules apply straight away.
  • Hooks: code that runs on events A hook is a command Claude Code runs at a fixed moment, such as just before a tool runs or when Claude is waiting for you. Unlike CLAUDE.md , a hook always runs.
  • Hook 1: block dangerous commands Claude sees the "Blocked" message and tries a safer way, or asks you.
  • Hook 2: protect secret files, with a JSON answer Instead of an exit code, a PreToolUse hook can print JSON with permissionDecision set to deny , ask or allow , plus a reason Claude will read.
  • Hook 3: add live facts to prompts A UserPromptSubmit hook can add text to Claude's context with additionalContext , nested inside hookSpecificOutput . Here it tells Claude about a release freeze, but only when the prompt is about deploying.
