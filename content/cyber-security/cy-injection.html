Lesson 1 of 9

Injection: when data is read as code

Injection is one idea behind many attacks. A program builds a command in some language, SQL for a database, shell for the operating system, a file path, a URL, an LDAP query or a template, and it pastes user input into that command. If the input contains characters that mean something in that language, such as a quote, a semicolon or two dots, the input stops being data and becomes part of the command. The first public write up of SQL injection was by Jeff Forristal, writing as rain.forest.puppy, in the hacker magazine Phrack in December 1998. Since then injection has caused some of the largest breaches on record. Albert Gonzalez and his group used SQL injection to get into Heartland Payment Systems and steal about 130 million card numbers in 2008, and he was sentenced to 20 years in prison. In 2015 teenagers used SQL injection on the UK telecom TalkTalk and took data on about 157000 customers, and the regulator fined the company 400000 pounds. In 2023 the Cl0p group used a SQL injection in the MOVEit file transfer product to steal data from thousands of organisations. Injection was number one in the OWASP Top 10 from 2010 to 2017, third in 2021 and fifth in 2025, so it is falling as frameworks make the safe way the default. The cure is always the same principle: keep code and data apart, using an interface that cannot confuse them, such as a parameterised query or an argument list.

Source: rain.forest.puppy (Jeff Forristal), NT Web Technology Vulnerabilities, Phrack 54 (1998), OWASP SQL Injection Prevention, Query Parameterization, OS Command Injection Defense, SSRF Prevention and Path Traversal pages, MITRE CWE-89, CWE-78, CWE-918, CWE-22, CWE-502, US DOJ press releases on Albert Gonzalez (2009 and 2010) and Paige Thompson (2019 and 2022), UK ICO penalty notice to TalkTalk (2016), NVD CVE-2014-6271 (Shellshock), CVE-2021-41773 (Apache path traversal), CVE-2023-34362 (MOVEit), AWS documentation on IMDSv2 (2019), Python documentation for sqlite3, subprocess, shlex and ipaddress.

Practise safely and legally
All databases, shells and networks on this page are simulations inside Python: an in memory SQLite database, a text splitter that shows what a shell would do, and a dictionary instead of DNS. Practise on DVWA, OWASP Juice Shop or PortSwigger Web Security Academy labs, never on real sites.
What it is
Injection happens when untrusted input is put into a command, query or path in a way that lets the input change the command’s structure instead of only filling in a value.
Why we need it
An injection often gives the attacker the full power of the interpreter behind the app: every row of the database, any shell command, any file, or any address the server can reach.
How it works
Never build commands by string concatenation. Use parameterised queries, argument lists without a shell, allow lists of expected values, path checks after normalising, and address checks after resolving. Run with least privilege so a mistake is contained.

Lesson 2 of 9

SQL injection and parameterised queries

Most web apps store their data in a relational database and talk to it in SQL. A login form might check a user like this: select the row where name equals what was typed and password hash equals what was computed. If the code builds that query by pasting the typed name between quotes, a name containing a quote ends the string early. The attacker can then add SQL of their own. Typing alice followed by a quote and two dashes logs in as alice, because the two dashes start a comment and the password check disappears. Typing a quote, OR, and a condition that is always true returns every row. With UNION, the attacker can bolt the results of a second query onto the first and read other tables, such as card numbers. On some databases stacked queries even allow deleting tables or running operating system commands. The well known xkcd comic from 2007 about a boy whose name ends with a DROP TABLE Students command made this famous outside security. The fix is the parameterised query, also called a prepared statement. The query text with placeholders is sent first and parsed, and the values are sent separately. The database already knows the shape of the query, so a quote in a value is just a character. Escaping input by hand is fragile and has been bypassed many times through character set tricks. Object relational mappers such as Django’s ORM and SQLAlchemy parameterise for you, but raw query features inside them can bring the bug back.

Lesson 3 of 9

Blind SQL injection: leaking data one bit at a time

Sometimes an injectable page shows no data and no errors. It might only say found or not found, or show the same page either way. That is still enough. In boolean based blind injection, the attacker injects a condition and watches which of the two answers comes back, which is one bit of information per request. Asking whether the first character of the admin’s token has a code above 79, then above 103, and so on, is a binary search, and it finds any printable character in at most seven requests. In time based blind injection, the attacker makes the database pause, for example with SLEEP(5), only when a condition is true, and measures how long the reply takes, so even an identical page leaks information. Tools such as sqlmap, first released in 2006, automate all of this and can dump a whole database through a single vulnerable parameter. Defenders sometimes think that hiding error messages makes injection harmless. Blind injection shows it does not: the only real fix is to remove the injection itself with parameterised queries. Rate limits and web application firewalls slow the attack and raise alerts, which is useful as a second layer.

Questions for a secretExam favourite

A 32 character token: about 32 × 7 = 224 requests.
Time based cost
T ≈ Q × (delay × P(true) + normal time)
224 questions, half of them true with a 5 s delay: about 560 s plus normal time.
Going deeper: Information theory view

Each yes or no answer gives at most one bit. A secret with H bits of entropy needs at least H answers on average, whatever the method. A random 32 character token over 95 symbols holds 32 × log2 95 ≈ 210 bits, so binary search, at 224 questions, is close to the best possible. Out of band techniques, such as making the database send a DNS lookup that carries data, can leak many bits per request.

Lesson 4 of 9

OS command injection

Some features call operating system commands: a network tool that pings an address, an image converter, a backup script. If the code builds a command line by pasting user input into it and runs it through a shell, the shell’s special characters become weapons. A semicolon ends one command and starts another, two ampersands run a second command if the first succeeds, a pipe sends output into another program, and backticks or dollar brackets run a command and paste its output. So an address field holding 8.8.8.8 followed by a semicolon and cat /etc/passwd runs two commands. Command injection usually gives the attacker the full rights of the web server process, which is why it is rated among the most severe flaws. It also appears in surprising places. Shellshock, disclosed in September 2014 and found by Stéphane Chazelas, was a flaw in the bash shell itself: text in an environment variable that looked like a function definition could carry extra commands, and web servers passed request headers to scripts as environment variables, so a single crafted header could run commands on millions of servers. Home routers and other devices with web admin pages are full of command injection bugs, and botnets such as Mirai variants use them to spread. The defences are simple. Prefer a library function over a command. If a command is needed, pass an argument list with no shell, which in Python means subprocess.run with a list and shell=False, so no character is special. Validate input against a strict allow list, such as a real IP address.

Lesson 5 of 9

Server side request forgery and the cloud metadata service

Many apps fetch URLs on a user’s behalf: link previews, webhooks, importing a file from a URL, or rendering a PDF from a web page. In server side request forgery the attacker gives the server a URL that points somewhere the attacker could never reach directly, because the request now comes from inside the network. Targets include internal admin panels, databases with web interfaces, and above all the cloud metadata service. Every virtual machine in AWS, Azure and Google Cloud can ask a special address, 169.254.169.254, for information about itself, including temporary credentials for the role it runs as. In 2019 an attacker used an SSRF through a misconfigured web application firewall at Capital One to read those credentials, then used them to copy data on about 106 million people in the United States and Canada from cloud storage. She was convicted in 2022. AWS responded by releasing IMDSv2 in November 2019, which requires a PUT request to get a session token first, something a simple SSRF usually cannot send. SSRF filters are hard to get right because addresses can be written in many ways: 127.0.0.1 can also be written as 2130706433, as 0x7f000001, or as the IPv6 address ::ffff:127.0.0.1, and a public domain name can point to a private address. Some attackers use DNS rebinding, where a name resolves to a public address when checked and a private one when fetched, or redirects from an allowed site to an internal one. The robust approach is to resolve the name once, check the resulting address against blocked ranges, connect to exactly that address, refuse redirects, and where possible only allow a short list of known destinations.

Lesson 6 of 9

Path traversal, deserialisation and template injection

Path traversal is injection into file names. An app that serves files from an uploads folder by gluing the requested name onto the folder path can be asked for dot dot slash dot dot slash etc slash passwd, and the operating system follows the dots up out of the folder. In October 2021 Apache HTTP Server 2.4.49 shipped with a path normalisation bug, CVE-2021-41773, that allowed exactly this with URL encoded dots, and attackers were exploiting it within days. The fix in code is to normalise the full path first and then check that it still lies inside the intended folder, or better, never use user input as a path at all and look files up by an id. Two related bugs belong in the same family. Insecure deserialisation happens when an app turns attacker supplied bytes back into objects with a format that can run code while loading, such as Python’s pickle or Java’s native serialisation. Loading a pickle from an untrusted source is the same as running the attacker’s program, so use JSON for untrusted data. Server side template injection happens when user input is placed into a template, for example a Jinja2 or Twig template, instead of being passed as a value to it. Template languages can call functions, so an attacker who types template syntax can often reach code execution. The lesson is the same as for SQL: user input must only ever fill a slot, never become part of the program.

Safe file serving
  1. Prefer an id: store files under random names and map ids to them in a database.
  2. If a name is needed, allow only a strict pattern, for example letters, digits, dash and one dot.
  3. Join with the base folder and normalise the result (resolve .. and symlinks).
  4. Check that the result is still inside the base folder.
  5. Run the app with a user that can read only that folder.
Remember
Python’s pickle documentation carries a warning: never unpickle data received from an untrusted or unauthenticated source. The same applies to yaml.load without SafeLoader, and to Java ObjectInputStream.

Injection defences compared

Students often list input validation as the fix for injection. It helps, but it is not the main defence, because what counts as dangerous depends on where the data goes. The main defence is to use an interface that keeps data apart from code for that particular interpreter. Validation and least privilege come next, and a web application firewall is a safety net, not a cure.

Lesson 8 of 9

From beginner to expert

A beginner understands that a website must never trust what people type. A college student can exploit SQL injection in a lab, write the parameterised fix, and explain blind injection with binary search. A professional finds injection in code reviews and tests, builds safe database layers and SSRF protected fetchers, and tunes WAF rules. Researchers build static analysis that tracks tainted data from input to dangerous functions, and study new injection surfaces such as prompts to large language models.
One idea, four depths

Know that typed input can attack a program, and that a site leaking passwords or card numbers often had an injection bug.

SQL injection with comments, tautologies and UNION, parameterised queries, blind injection by binary search, command injection and argument lists, SSRF and address checks, path traversal.

Test with Burp Suite and sqlmap in authorised engagements, review code for sinks such as raw queries and shell=True, defend cloud apps with IMDSv2 and egress rules, and write SAST rules.

Taint analysis and program analysis for injection, grammar based fuzzing of parsers, SSRF in complex cloud graphs, and prompt injection against LLM applications, where the same code versus data confusion appears in natural language.

Beginner
Explain why a website must not trust typed input.
Intermediate

Expert
Find injection at scale with tools and analysis.

Chapter summary

  1. Injection: input pasted into a command becomes code. First described for SQL in Phrack in 1998. Heartland, TalkTalk and MOVEit show the cost.
  2. SQL injection: quote plus comment, OR always true, UNION to read other tables. Fix: parameterised queries, allow lists for names, least privilege.
  3. Blind injection: one bit per request, binary search needs ⌈log2 95⌉ = 7 questions per character. Hiding errors is not a fix.
  4. Command injection: ; && | $( ) in a shell. Fix: subprocess with a list and no shell, strict validation. Shellshock hid it inside bash.
  5. SSRF: the server fetches internal URLs, such as 169.254.169.254. Resolve, block internal ranges, pin the address, no redirects, IMDSv2. Capital One 2019.
  6. Paths and objects: normalise then check the base folder. Never unpickle untrusted data. Never let users write templates.
