Lesson 1 of 9

Hash functions: a fingerprint for any data

A cryptographic hash function is one of the most used tools in all of computing, even though most people never see one. It takes any amount of data, a word or a whole film, and produces a short fixed size value, such as 256 bits for SHA-256. The same input always gives the same output, and the smallest change gives a completely different one. But the real power comes from three hardness properties. Given a hash, you cannot find any input that produces it. Given one input, you cannot find a second input with the same hash. And you cannot find any two inputs with the same hash at all. Ron Rivest’s MD5, from 1991, was the workhorse of the 1990s until Wang Xiaoyun’s team broke its collision resistance in 2004. In 2012 the Flame spy malware used an MD5 collision to forge a Microsoft code signing certificate, so infected computers trusted it as a Windows update. SHA-1 fell in 2017. Today we use SHA-256 and SHA-3. Hashes protect software downloads, Git commits, digital signatures, blockchains and passwords.

Source: FIPS 180-4, FIPS 202, RFC 2104, RFC 4231, RFC 6962, RFC 8018, RFC 9106, the OWASP Password Storage Cheat Sheet, Wang et al. (2005), Stevens et al. (2017), Leurent and Peyrin (2020).

What it is
A cryptographic hash function H maps any input to a fixed length output (the digest) and is easy to compute but hard to reverse or to collide.
Why we need it
Hashes let you check that data is unchanged, identify files, sign large documents by signing only their hash, and store passwords without storing the passwords.
How it works
Compute hashlib.sha256(data).hexdigest(). Security rests on three properties, each with its own brute force cost for an n bit hash: preimage 2n, second preimage 2n, collision 2n/2.

Lesson 2 of 9

The birthday paradox and collision maths

Here is a puzzle that surprises almost everyone. How many people do you need in a room for a better than even chance that two share a birthday? Most people guess around 180, half of 365. The real answer is 23. The trick is that we are not asking whether someone shares your birthday. We are asking whether any pair shares a birthday, and 23 people form 253 pairs. Each new person has to avoid every birthday already taken, and the chance of avoiding them all shrinks quickly. The same maths applies to hash values. If a hash has n bits, there are 2 to the n possible outputs, but an attacker who hashes many random messages will find two with the same output after only about 2 to the n over 2 tries. That is why a 128 bit hash like MD5 only ever offered 64 bits of collision security, and why we now use 256 bit hashes, which give 128 bits. The same bound limits block ciphers, random IDs and nonces: anything chosen at random from N values starts repeating after about the square root of N.
What it is
The birthday paradox: among n random values from N possibilities, a repeat becomes likely once n is around √N.
Why we need it
It sets the real collision security of a hash (half its length in bits) and how many random nonces, IDs or blocks you can use before repeats appear.
How it works
P(no repeat) = (1 − 1/N)(1 − 2/N)...(1 − (n−1)/N) ≈ e−n(n−1)/2N. Set it to 1/2 and solve: n ≈ √(2 N ln 2) ≈ 1.18 √N.
ExactExam favourite
P(collision) = 1 − ∏i=1n−1 (1 − i/N)
For N = 365 and n = 23 this is 0.507.
ApproximationExam favourite
P(collision) ≈ 1 − e−n2/2N ≈ n2/2N when small
Uses 1 − x ≈ e−x for small x.
50% point
n1/2 ≈ √(2 ln 2 · N) ≈ 1.1774 √N
N = 365: 22.5, so 23 people. N = 2128: about 2.2 × 1019 hashes.
Hash collision security
n bit hash → about 2n/2 work
MD5: 264 at best (and broken far below). SHA-256: 2128.
Going deeper: Deriving the approximation

Take logs: ln P(no repeat) = Σi<n ln(1 − i/N) ≈ −Σ i/N = −n(n − 1)/2N, using ln(1 − x) ≈ −x when x is small. So P(no repeat) ≈ e−n(n−1)/2N. Setting this to 1/2 gives n(n − 1) = 2N ln 2, so n ≈ √(2N ln 2). Pollard’s rho method finds hash collisions in about the same number of steps while using almost no memory, by walking x → H(x) until the path loops.

Lesson 3 of 9

Inside SHA-256: the Merkle-Damgård chain and length extension

How can a function take input of any length? In 1989, Ralph Merkle and Ivan Damgård independently showed a neat answer. Build a compression function that takes a fixed size state and one fixed size block of message and outputs a new state. Pad the message to a whole number of blocks, including its length at the end, then feed the blocks in one by one. The final state is the hash. They proved that if the compression function is collision resistant, so is the whole hash. MD5, SHA-1 and SHA-256 are all built this way. SHA-256 uses 64 byte blocks, a 32 byte state made of eight 32 bit words, and 64 rounds of additions, rotations and bit mixing, with constants taken from the cube roots of the first 64 prime numbers, so nobody can claim the designers hid a trapdoor in them. But the design has one surprising weakness. The hash output is the full internal state. So anyone who knows the hash of some unknown data can keep hashing more blocks, as if they had the data. If a website signs requests as SHA-256 of a secret key followed by the request, an attacker can add new parameters and compute a valid signature without the key. Exactly this broke the Flickr API in 2009.
What it is
Merkle-Damgård builds a hash from a compression function f: H0 = IV, Hi = f(Hi−1, Mi), and the hash is the last H. Length extension: from H(m) alone, anyone can compute H(m ‖ pad ‖ x).
Why we need it
It explains why SHA(key ‖ message) is not a safe MAC and why HMAC exists. SHA-3 uses a different design, the sponge, which is not vulnerable.
How it works
SHA-256 pads with the bit 1, then zeros, then the 64 bit message length, to a multiple of 512 bits. It then runs the compression function on each 512 bit block. The attacker uses the published hash as the state and continues.

Message authentication codes and HMAC

Encryption keeps a message secret, but it does not prove who sent it or that it was not changed. For that we need a message authentication code, a MAC. Both sides share a secret key. The sender computes a short tag from the key and the message, and the receiver recomputes it. If an attacker changes the message, they cannot compute the matching tag without the key. The obvious design, hashing the key followed by the message, falls to the length extension attack you just saw. In 1996 Mihir Bellare, Ran Canetti and Hugo Krawczyk designed HMAC, which hashes twice with two different versions of the key, and they proved it secure under mild assumptions about the hash. HMAC became RFC 2104 in 1997 and is now everywhere: in TLS, in JSON Web Tokens, in AWS request signatures, in TOTP codes on your phone, and in the password function PBKDF2. A MAC is not a signature, though. Because both sides share the key, either side could have made the tag, so a MAC cannot prove to a third person who wrote the message. That needs public key signatures, coming later in this section.
What it is
A MAC is a short tag computed from a secret key and a message. HMAC is the standard way to build a MAC from a hash: HMAC(K, m) = H((K0 ⊕ opad) ‖ H((K0 ⊕ ipad) ‖ m)).
Why we need it
Without a MAC, an attacker can change encrypted or plain messages unnoticed. HMAC is simple, fast, proven, and available in every language.
How it works
Pad the key to the block size (64 bytes for SHA-256). XOR with ipad (0x36 bytes), hash with the message. XOR the key with opad (0x5c bytes), hash with the inner result. Compare tags with a constant time function.

Storing passwords: salts and slow hashes

Websites must check your password without storing it, because databases get stolen. The first idea was to store a hash of each password. But a fast hash is a gift to attackers. A single modern graphics card can compute many billions of MD5 hashes per second, so after a breach attackers simply hash every word in a huge list of real leaked passwords and look for matches. In 2012, LinkedIn lost millions of unsalted SHA-1 password hashes, and most were cracked within days. Two defences fix this. A salt is a random value stored next to each hash and mixed into it. Two users with the same password then get different hashes, and attackers cannot reuse precomputed tables, called rainbow tables, across users. A slow hash is deliberately expensive. bcrypt, from 1999, has a cost setting. scrypt, from 2009, also needs lots of memory, which graphics cards have little of per core. Argon2 won the Password Hashing Competition in 2015 and is now the first choice. If checking a guess takes a server a tenth of a second, that is nothing for one login but a disaster for an attacker trying billions of guesses.
What it is
Store passwords with a password hashing function: a random salt per user and a deliberately slow, ideally memory hard function such as Argon2id, scrypt, bcrypt or PBKDF2.
Why we need it
Password databases leak. Salting stops one table cracking everyone, and slowness makes each guess cost the attacker real time and money.
How it works
On sign up: make a random 16 byte salt, compute the slow hash, store salt and hash. On login: recompute with the stored salt and compare in constant time. Raise the cost settings as computers get faster.

Merkle trees: hashing many things at once

Ralph Merkle had another lasting idea, from 1979: the hash tree. Hash every item in a list, then hash the hashes in pairs, then hash those in pairs, until one hash is left at the top, called the root. The root commits to the whole list: change any item and the root changes. The clever part is the proof. To show that one item is in a list of a million, you only need about twenty hashes, the siblings on the path from the item up to the root, because two to the twenty is about a million. Merkle trees are everywhere. Git stores your project as a tree of hashes, so a commit hash pins every file. Bitcoin puts a Merkle root of all transactions in each block header, so a phone can check that a payment is in a block without downloading the block. Certificate Transparency, which keeps public logs of every web certificate, uses Merkle trees so that browsers can check that a certificate was logged and that logs never quietly rewrite history. And file sharing systems like BitTorrent and IPFS use them to check each downloaded piece.
What it is
A Merkle tree hashes items in pairs, level by level, to a single root. An inclusion proof for one item is the list of sibling hashes on its path to the root.
Why we need it
One short root commits to millions of items, and anyone can check one item with about log2(n) hashes instead of all n.
How it works
Leaves are H(item). Each parent is H(left ‖ right). To verify, start from H(item) and combine with each sibling in the right order. If you reach the root, the item is in the tree.

Proof sizeExam favourite
hashes in a proof = log2 n
n = 4: 2 hashes. n = 1,048,576: 20 hashes, 640 bytes with SHA-256.
Domain separation
leaf = H(0x00 ‖ item), node = H(0x01 ‖ left ‖ right)
RFC 6962 uses different prefixes so that an inner node can never be passed off as a leaf.
Common mistake
The program uses plain H(item) and H(left ‖ right) to stay short. Real systems add the 0x00 and 0x01 prefixes. Bitcoin’s simpler rule of copying the last hash when a level is odd allowed a real bug in 2012 (CVE-2012-2459), where two different transaction lists had the same root.
Lesson 7 of 9

Hash functions compared

With so many hash functions around, the choice can look confusing, but the rules are short. For general integrity and signatures, use SHA-256, or SHA-512 on 64 bit machines where it can be faster. If length extension could matter, use HMAC, SHA-512/256 or SHA-3. BLAKE2 and BLAKE3 are very fast modern designs, popular in tools and file systems. For passwords, never use any of these directly. Use Argon2id, scrypt or bcrypt. For non security jobs such as hash tables, checksums for accidental errors, or deduplication where nobody is attacking, fast non cryptographic hashes like xxHash or CRC32 are fine, but never let them near a security decision.

Lesson 8 of 9

From beginner to expert

Hash functions reach from everyday use to the deepest theory. A beginner learns that a hash is a fingerprint and that passwords must be stored as slow, salted hashes. A college student can explain the three security properties, the birthday bound, HMAC and Merkle trees, and write code for each. A masters student studies the random oracle model, where a hash is treated as a perfectly random function in proofs, and its known limits. They study how differential attacks broke MD5 and SHA-1, and how the sponge construction gets its security from the hidden capacity. At the research level, cryptographers build chosen prefix collisions, where two different chosen starting documents are completed so they hash the same. That attack on SHA-1 in 2020 cost about 45 thousand dollars of rented graphics cards and showed that PGP keys signed with SHA-1 could be impersonated. Others design hashes that are cheap inside zero knowledge proofs, such as Poseidon, which matter for the advanced crypto chapter later.
One idea, four depths

A hash is a short fingerprint of data. The same data always gives the same hash, and a tiny change gives a different one. Websites should store passwords as salted, slow hashes, never as plain text.

State preimage, second preimage and collision resistance with costs 2n, 2n, 2n/2. Derive the birthday bound. Explain Merkle-Damgård, padding and length extension. Build HMAC and Merkle proofs, and choose Argon2id with a salt for passwords.

The random oracle model and its limits (Canetti, Goldreich and Halevi, 1998). Differential cryptanalysis of MD5 and SHA-1, multicollisions (Joux, 2004) showing that joining two Merkle-Damgård hashes adds little security, indifferentiability and the sponge’s 2c/2 security from capacity c.

Chosen prefix collisions (MD5 in 2007, used by Flame in 2012, SHA-1 in 2020 by Leurent and Peyrin), quantum collision search (Brassard, Høyer and Tapp: about 2n/3 in theory), and arithmetization oriented hashes such as Poseidon for zero knowledge proof systems.

Beginner
Explain hashes as fingerprints and why passwords need salted slow hashes.
Intermediate
Use the three properties, the birthday bound, HMAC, Merkle trees and password hashing correctly.
Expert
Reason in the random oracle model, analyse MD and sponge designs, and follow chosen prefix collision research.

Chapter summary

  1. A hash maps any input to a fixed size digest. Security: preimage (2n), second preimage (2n), collision (2n/2).
  2. Birthday paradox: P ≈ 1 − e−n2/2N, 50% at n ≈ 1.18 √N. 23 people for 365 days. SHA-256 gives 128 bit collision security.
  3. MD5 (2004) and SHA-1 (2017) have broken collision resistance. Use SHA-256, SHA-512 or SHA-3.
  4. Merkle-Damgård: Hi = f(Hi−1, Mi). Padding: 0x80, zeros, 64 bit length. The output is the full state, so length extension breaks SHA(key ‖ msg).
  5. HMAC(K, m) = H((K0 ⊕ opad) ‖ H((K0 ⊕ ipad) ‖ m)), ipad 0x36, opad 0x5c. Check tags with compare_digest. A MAC does not prove who sent it to a third party.
  6. Passwords: random salt per user plus a slow, memory hard function. Argon2id first, then scrypt, bcrypt, PBKDF2 (600,000 iterations). Never plain fast hashes.
  7. Merkle trees: one root commits to n items, inclusion proofs need log2 n hashes. Used in Git, Bitcoin and Certificate Transparency.
