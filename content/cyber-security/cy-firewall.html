Defence in depth: layers between attacker and data

No single control stops every attack, so defenders stack several, each catching what the others miss. This idea is called defence in depth, borrowed from military thinking. For networks the first layers are firewalls, which decide which traffic may pass, intrusion detection systems, which watch traffic for signs of attack, and virtual private networks, which carry traffic safely across networks you do not trust. Firewalls grew out of packet filtering routers in the late 1980s, and William Cheswick and Steven Bellovin’s 1994 book Firewalls and Internet Security made the idea mainstream. Dorothy Denning described intrusion detection in 1987. For years the model was a castle with a moat: a hard perimeter around a trusted inside. That model failed when attackers got inside through phishing or a supplier, then moved freely. In the 2013 Target breach, attackers entered with stolen credentials from a heating and ventilation contractor and reached the payment systems. Google, after the Operation Aurora attacks of 2009, rebuilt its access model so that no network is trusted, which became zero trust. This chapter covers each layer, how it works inside, and how to measure whether it works.

Source: Cheswick and Bellovin, Firewalls and Internet Security (1994), Denning (IEEE TSE 1987), Axelsson (ACM TISSEC 2000), Snort 3 and Suricata documentation, RFC 4301 (IPsec architecture), RFC 7296 (IKEv2), Donenfeld, WireGuard: Next Generation Kernel Network Tunnel (NDSS 2017), Ward and Beyer, BeyondCorp (login 2014), NIST SP 800-207 Zero Trust Architecture (2020), NIST SP 800-41 r1 (firewall policy).

What it is
Network defences: a firewall enforces a traffic policy, an IDS or IPS detects (and an IPS also blocks) attacks in traffic, a VPN gives an encrypted tunnel, and zero trust checks every request on identity and device instead of location.
Why we need it
Each layer lowers risk in a different way: firewalls shrink what is reachable, IDS shortens the time attackers stay unnoticed, VPNs protect data in transit, and zero trust limits how far a stolen account can go.
How it works
Firewalls match packet fields against ordered rules and track connection state. IDS match signatures or score anomalies. VPNs encapsulate and encrypt packets. Zero trust puts a policy decision point in front of every resource.

Firewalls: rules, state and order

A firewall compares each packet with an ordered list of rules. A rule names fields such as protocol, source address, destination address and port, and an action, allow or deny. The first rule that matches decides, so order matters. If a broad allow rule sits above a narrow deny rule, the deny is never reached, a mistake called shadowing. Good policy ends with a default deny, so anything not clearly allowed is blocked. The earliest firewalls were stateless packet filters: they judged each packet alone, which made return traffic awkward, because replies had to be allowed by separate rules. Stateful firewalls, popularised by Check Point FireWall-1 in 1994, keep a table of connections that were started from inside, and let only matching replies back in. Application layer firewalls and proxies understand protocols such as HTTP, and next generation firewalls add user identity, application recognition and intrusion prevention. A web application firewall sits in front of a website and blocks attacks like SQL injection. On Linux, nftables replaced iptables from 2014, and every cloud offers security groups that are stateful firewalls attached to each server. A common design puts public servers in a demilitarised zone, a separate network between the internet and the internal network, so a hacked web server cannot reach internal systems directly.

What it is
A firewall enforces a policy on traffic between networks or hosts, using ordered rules over packet fields and, when stateful, a connection table.
Why we need it
It reduces the attack surface: services that are not reachable cannot be attacked from outside, and outbound rules make it harder for malware to call home.
How it works
Check rules top down, first match wins, default deny. A stateful firewall adds each outbound connection to a table and allows inbound packets only if they match an entry with addresses and ports swapped.

Lesson 3 of 8

Intrusion detection and prevention

An intrusion detection system watches network traffic or host activity and raises alerts when something looks like an attack. An intrusion prevention system sits in the path of traffic and can also drop it. There are two main ways to decide. Signature based detection matches known patterns, such as a path traversal string in a web request or the bytes of a known exploit. Snort, written by Martin Roesch in 1998, and Suricata, released in 2010, are the best known open source engines, and their rules combine ports, protocol details and content patterns. Signatures are precise but blind to new attacks. Anomaly based detection, proposed by Dorothy Denning in 1987, learns what normal looks like and flags large deviations, for example a sudden burst of failed logins. It can catch new attacks but raises more false alarms. Zeek, started by Vern Paxson as Bro in the mid 1990s, takes a third approach: it turns traffic into rich logs of connections, DNS queries and certificates that analysts and scripts can search. The hardest problem is the base rate. Attacks are rare among billions of events, so even a detector with a tiny false alarm rate produces mostly false alarms, a point Stefan Axelsson made in 2000. That is why tuning, context and good metrics such as precision and recall matter as much as detection itself.

What it is
IDS (detect and alert) and IPS (detect and block) inspect network traffic (NIDS) or host activity (HIDS) for attacks, using signatures, anomaly scores or both.
Why we need it
Firewalls allow some traffic by design, and attacks hide inside allowed traffic. Detection shortens the time an attacker stays unnoticed, which reports put at days to months.
How it works
Signatures: match fields and content patterns. Anomalies: model normal (mean and standard deviation, or machine learning) and alert beyond a threshold. Measure with a labelled test set: precision, recall, F1.
z scoreExam favourite
z = (x − μ) / σ, alert if z > k
Normal failures: μ = 4.17, σ = 1.21. 41 failures gives z ≈ 30.4, an alert. With k = 3, about 0.27% of normal minutes still cross the line (two sided, for a normal distribution).
Precision and recallExam favourite
P = TP / (TP + FP), R = TP / (TP + FN), F1 = 2PR / (P + R)
TP = 90, FP = 10, FN = 30: P = 0.90, R = 0.75, F1 = 0.82.
Base rate (Bayes)Exam favourite
P(attack | alert) = P(alert | attack) P(attack) / P(alert)
Detection 99.9%, false alarms 0.1%, attacks 1 in 100000 events: only about 1% of alerts are real.
EWMA baseline
St = αxt + (1 − α)St−1
α = 0.2, S = 100, x = 150: S = 110. The baseline follows slow change but not sudden bursts.

VPNs: IPsec, TLS VPNs and WireGuard

A virtual private network builds an encrypted tunnel across a network you do not trust, such as the internet or café Wi-Fi. Each original packet is encrypted and wrapped inside a new packet addressed to the other end of the tunnel, which unwraps it and forwards it. Site to site VPNs join office networks. Remote access VPNs connect a laptop to the company network. Consumer VPNs send all of a user’s traffic through a provider, which hides it from the local network but makes the provider the party you must trust. The oldest standard is IPsec, designed in the 1990s, whose Encapsulating Security Payload protects packets and whose IKE protocol, now IKEv2, agrees keys. It is powerful but complex. TLS based VPNs such as OpenVPN, from 2001, run over ordinary TLS and pass easily through firewalls. WireGuard, designed by Jason Donenfeld and published in 2017, uses a small fixed set of modern algorithms, Curve25519, ChaCha20-Poly1305 and BLAKE2s, in about 4000 lines of code, and became part of the Linux kernel in 2020. VPN appliances themselves are prime targets: several serious vulnerabilities in commercial VPN gateways have been exploited at scale, so patching them quickly is essential.
Download this program (.py)Save it, open it in any editor and run it with python3 tunnel.py.
What it is
A VPN encapsulates packets inside encrypted, authenticated packets between two tunnel endpoints, giving confidentiality and integrity across an untrusted network.
Why we need it
It protects traffic from local eavesdroppers, joins networks securely and gives remote staff access to internal services.
How it works
A handshake authenticates both ends and agrees keys (IKEv2, TLS, or the Noise framework in WireGuard). Each packet is then sealed with an AEAD cipher and a counter that stops replay.

Lesson 5 of 8

Zero trust and segmentation

Zero trust is the idea that no request should be trusted just because it comes from inside the network. The term was popularised by John Kindervag at Forrester in 2010. Google’s BeyondCorp, described in 2014, was the first large implementation: employees reach internal applications through an access proxy from any network, and each request is checked against who the user is, whether their device is managed and healthy, and what they are allowed to do. NIST published Special Publication 800-207 on zero trust architecture in 2020. The core parts are a policy engine that decides, a policy enforcement point in front of each resource, strong identity with multi factor authentication or passkeys, device health checks, least privilege, and continuous monitoring. Segmentation is the network side of the same idea. Instead of one flat network, systems are divided into zones, and with microsegmentation each workload talks only to what it needs. This limits lateral movement, where an attacker who takes one machine hops to the next. Zero trust is not a product you buy but a direction, usually reached step by step, starting with identity and the most valuable data.

What it is
Zero trust: never trust, always verify. Every access is decided on identity, device health and context, with least privilege, no matter where the request comes from.
Why we need it
Perimeters fail through phishing, stolen VPN credentials and suppliers. Zero trust limits what a stolen account or a hacked laptop can reach.
How it works
A policy decision point evaluates each request using identity, device posture, resource sensitivity and signals such as location. A policy enforcement point allows, denies or asks for step up authentication.
Moving towards zero trust
  1. List your users, devices, applications and data, and mark the most valuable.
  2. Make identity strong: single sign on, MFA or passkeys for everyone.
  3. Check device health: managed, patched, disk encrypted, endpoint protection running.
  4. Put applications behind an identity aware proxy instead of a flat VPN.
  5. Segment the network so each workload reaches only what it needs.
  6. Log every decision and watch for unusual access.
Microsegmentation pairsExam favourite
possible directed flows = n(n − 1)
50 workloads: 2450 possible flows. Allowing only the few dozen that are needed removes most paths for lateral movement.

Network defences compared

Students often mix up firewalls, intrusion detection and VPNs, because all three sit on the network. A firewall decides what is allowed, an IDS notices what is bad among the allowed traffic, an IPS does both in line, a VPN protects traffic while it crosses an untrusted network, and zero trust moves the decision from the network to each application request. They work together. A firewall without monitoring leaves you blind to attacks through open ports, and a VPN without zero trust can give a stolen account access to everything inside.

Lesson 7 of 8

From beginner to expert

A beginner knows that a firewall blocks unwanted traffic, that a VPN encrypts traffic on public Wi-Fi, and that companies watch for attacks. A college student writes firewall rules with default deny, explains stateful inspection, reads a Snort or Suricata rule, computes precision, recall and the base rate effect, and configures WireGuard between two virtual machines. A masters student designs segmented networks and zero trust access, tunes detection with statistics and machine learning, studies IPsec and IKEv2 in detail, and understands evasion, where attackers split or encode traffic so the IDS sees something different from the target. Researchers work on encrypted traffic analysis, provable properties of firewall rule sets, high speed pattern matching in hardware, adversarial attacks on machine learning detectors and formal verification of VPN protocols.
One idea, four depths

Firewalls block, IDS watch, VPNs encrypt, and zero trust checks every request. No single tool is enough.

First match rules with default deny, stateful tables, DMZ design, signature and anomaly detection, precision, recall and the base rate, and VPN encapsulation with MTU maths.

Rule set analysis (shadowing and redundancy), IDS evasion (fragmentation, Ptacek and Newsham 1998), Zeek scripting, IKEv2 and the Noise framework, zero trust architecture per SP 800-207, microsegmentation.

Encrypted traffic classification, adversarial ML against detectors, hardware pattern matching (Aho-Corasick at line rate), verified implementations of WireGuard and TLS, and formal models of policy.

Beginner
Say what each defence does and where it sits.
Intermediate
Write rules, read alerts with precision and recall, and set up a tunnel in a lab.
Expert
Design layered architectures and measure their effect.

Chapter summary

  1. Defence in depth: firewalls, IDS and IPS, VPNs and zero trust, each covering others’ gaps. Perimeters alone failed (Target 2013).
  2. Firewall: ordered rules, first match wins, default deny. Stateful tables let replies in. Watch for shadowed rules.
  3. Types: stateless filter, stateful, application proxy and WAF, NGFW, host firewall. DMZ for public servers.
  4. IDS and IPS: signatures (Snort 1998, Suricata 2010) versus anomalies (Denning 1987). Zeek logs everything for analysis.
  5. Maths: z = (x − μ)/σ, P = TP/(TP + FP), R = TP/(TP + FN), F1 = 2PR/(P + R). Base rate: most alerts can be false.
  6. VPN: encrypted encapsulation. IPsec with IKEv2, OpenVPN, WireGuard (Curve25519, ChaCha20-Poly1305, 1420 byte MTU).
  7. Zero trust: BeyondCorp 2014, NIST SP 800-207. Identity, device health, least privilege, per request decisions, microsegmentation.
