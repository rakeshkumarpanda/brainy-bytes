Lesson 1 of 11

Why we log, and what a SIEM does

Think of logs as the diary of every computer. Each time someone logs in, opens a file, starts a program or sends data out, the system can write one line about it. On a single laptop that is a few thousand lines a day. In a company with thousands of machines it is billions. Nobody can read that by hand. A SIEM, which stands for Security Information and Event Management, is the tool that collects all these lines in one place, puts them into the same shape, keeps them safe, and runs rules on them all day and all night to spot trouble. The name was coined by two Gartner analysts, Mark Nicolett and Amrit Williams, in 2005, when they joined two older ideas: keeping logs for reports, and watching events live. Today the best known SIEMs are Splunk, Microsoft Sentinel, IBM QRadar, Elastic Security and Google Security Operations, and Wazuh is a popular free one. Logs matter because most attacks leave traces long before damage is done. In the Target breach of 2013, security tools raised alerts when the attackers installed their malware, but the alerts were not acted on, and data on about 40 million payment cards was stolen. At Equifax in 2017, a device that inspected outgoing traffic had an expired certificate, so for about 76 days nobody saw the data leaving. Both stories teach the same lesson. Collecting logs is not enough. Someone, or some rule, has to look at them, and the tools have to be kept working. In India, the CERT-In rules of April 2022 ask companies to keep their logs for 180 days and to report serious incidents within 6 hours, so logging is also the law.

Source: NIST SP 800-92 Guide to Computer Security Log Management (2006), Gartner (Nicolett and Williams, 2005), RFC 3164 and RFC 5424 (syslog), Microsoft Windows security auditing reference, US Senate Commerce Committee report on the Target breach (2014), US GAO report on the Equifax breach (GAO-18-559, 2018), PCI DSS v4.0 requirement 10, CERT-In Directions under section 70B of the IT Act (28 April 2022).

Practise safely and legally
Every program in this chapter reads made up log lines written inside the program. To practise on real logs, use your own laptop, for example the Linux journal with journalctl or the Windows Event Viewer, or free practice data sets such as the Splunk Boss of the SOC data.
What it is
A log is a line a system writes when something happens. A SIEM collects logs from every system, puts them into one shape, keeps them safe and runs detection rules on them.
Why we need it
Attacks leave traces. Without logs you cannot spot an attack while it happens, find out what happened afterwards, or prove it to a court or a regulator.
How it works
Agents and collectors send logs to the SIEM. It parses each line into fields, adds context such as who owns an IP, stores everything with the right time, and checks rules. Matches become alerts for analysts.
The journey of one log line
  1. A user types a wrong password on a server. The SSH service writes a line to the system log.
  2. A small agent on the server, such as a forwarder, reads the new line and sends it over an encrypted link to the SIEM.
  3. The SIEM parses the line into fields: time, host, user, source IP, action and outcome.
  4. It adds context: the IP belongs to a foreign hosting company, and the user is an administrator.
  5. Detection rules check the event together with recent events. Five failures in five minutes from one IP fire an alert.
  6. An analyst sees the alert, looks at the related events and decides what to do. The raw line is stored for months in case it is needed later.
Lesson 2 of 11

What to log: the sources and the events that matter

You cannot log everything forever, because storage costs money and noise hides the signal. So teams pick the sources and events that tell the most. The first group is identity: logins that work and logins that fail, password resets, new accounts, and accounts that get admin rights. The second group is endpoints, meaning laptops and servers: which programs start, which services are installed, and when the audit log itself is cleared, because attackers love to wipe their tracks. The third group is the network: firewall allow and deny records, DNS lookups, web proxy logs and VPN connections. The fourth is the cloud: who changed what in the cloud console. The fifth is the applications themselves. On Windows each kind of event has a number. 4624 means a successful logon, 4625 a failed logon, 4672 means special admin rights were given at logon, 4688 means a new process started, 4720 means a user account was created, and 1102 means the security log was cleared. Many analysts know these numbers by heart. On Linux and network devices the common format is syslog, which Eric Allman wrote for the Sendmail program in the 1980s and which was later written down as RFC 3164 and then RFC 5424 in 2009. Two practical rules matter as much as the list. First, every machine must have the right time, set by NTP, or you cannot put events from different machines in order. Second, logs must leave the machine quickly, because an attacker with admin rights on a machine can delete its local logs.

Never log secrets. Passwords, full card numbers, session tokens and private keys must not appear in logs, because logs are read by many people and kept for a long time.
Lesson 3 of 11

Parsing and normalising: one shape for every log

Every product writes its logs in its own way. The SSH service on Linux writes a sentence. Windows writes an event with numbered fields. A modern web app writes JSON. A firewall writes its own short codes. If you want to ask a simple question like show me everything from this IP address, the SIEM first has to turn all of these into the same set of fields. This step is called parsing, and the shared set of fields is called a schema. Common schemas are the Elastic Common Schema, Splunk’s Common Information Model, and OCSF, the Open Cybersecurity Schema Framework, started in 2022 by AWS, Splunk and others. Parsing often uses regular expressions, which are small patterns that match text, as in the program below. After parsing comes enrichment, which means adding facts the log line did not carry: which country an IP is in, whether it is on a list of known bad addresses, which department a user works in, and how important a server is. Good parsing is boring but vital. If a parser breaks after a software update, the rules that depend on it go silent, and nobody notices until an attack is missed. That is why teams watch for sources that suddenly stop sending logs.

Going deeper: Regular expressions in one minute

A regular expression is a pattern. \d+ means one or more digits, \S+ means one or more characters that are not spaces, and brackets ( ) capture the part we want to keep. The pattern in the program, Failed password for (\S+) from (\S+), captures the user and the IP from an SSH log line. Write patterns that are strict enough not to grab the wrong text, and test them on real samples.

Remember
Keep the raw line as well as the parsed fields. If the parser was wrong, you can parse the raw line again later, and courts often want the original record.
Lesson 4 of 11

Detection rules: thresholds, correlation and Sigma

A detection rule is a small question the SIEM asks again and again. The simplest kind is a match: tell me whenever the security log is cleared. The next kind is a threshold over a time window: tell me when one IP fails to log in five times within five minutes. That catches password guessing, which MITRE ATT&CK calls technique T1110, Brute Force. A sliding window means the SIEM always looks back the same number of minutes from now, so old failures drop out as time moves on. The third kind is correlation, which links different events into a story. Many failures followed by one success from the same IP is far more worrying than either alone, because it suggests the attacker guessed the password and is now inside, which ATT&CK calls T1078, Valid Accounts. Choosing the numbers is a balance. If the threshold is too low, ordinary people who mistype raise alerts all day. If it is too high or the window too short, a patient attacker who tries one password every few minutes slips through. This is called low and slow. In 2017 Florian Roth and Thomas Patzke started Sigma, a way to write rules as plain data files that can be converted into the search language of any SIEM. Sigma rules are shared freely, so a rule written by one defender can protect thousands of companies. Each good rule also names the ATT&CK technique it detects, so a team can see which techniques it covers and which it does not.

Lesson 5 of 11

Impossible travel and behaviour baselines

Some rules do not look for a bad event at all. They look for something that is unusual for this person. The best known is impossible travel. If Meena logs in from Mumbai at nine in the morning and from London half an hour later, she cannot have flown that far. Either someone else has her password, or something is hiding her real location. To check, the SIEM looks up where each IP address is, works out the distance on the curved surface of the Earth with the haversine formula, and divides by the time between the two logins. If the speed is faster than a passenger jet, about 900 kilometres an hour, it raises an alert. There are honest reasons for false alarms. Company VPNs, mobile networks and cloud proxies can make a user seem to be in another city, so good rules know the company’s own VPN addresses and ignore them. The wider idea is called user and entity behaviour analytics, UEBA. The system learns what is normal for each user and each machine, such as the hours they work, the servers they use, and how much data they usually download, and it flags big changes. A clerk who suddenly downloads ten thousand customer records at two in the morning is worth a look, even if each action alone is allowed.

Haversine distanceExam favourite
d = 2R · arcsin √( sin2(Δφ/2) + cos φ1 cos φ2 sin2(Δλ/2) )
φ is latitude and λ is longitude, in radians. R = 6371 km. Mumbai to London is about 7192 km.
Travel speedExam favourite
v = d / Δt
7192 km in 0.5 hours is about 14383 km per hour, far above 900.
Remember
Location from an IP address is a guess, not a fact. Treat impossible travel as a reason to check, then confirm with the user through a trusted channel such as a known phone number.
Lesson 6 of 11

The base rate problem: why most alerts are false

Here is a surprise that every security analyst must understand. Imagine a detector that catches 99 out of every 100 attacks, and wrongly flags only 1 out of every 100 normal events. It sounds excellent. Now feed it one million events, of which only 100 are attacks. It catches 99 attacks. But it also flags 1 percent of the 999900 normal events, which is 9999 false alarms. So an analyst sees about 10098 alerts and only 99 of them are real, less than 1 in 100. This is called the base rate fallacy, and Stefan Axelsson explained it for intrusion detection at the ACM CCS conference in 1999. The cause is simple: real attacks are rare, so even a tiny false alarm rate on a huge number of normal events makes a mountain of noise. The maths is Bayes’ rule, which you met in the foundations section. The lesson for defenders is practical. Making the detector catch a few more attacks hardly helps. Cutting false alarms helps a lot. Teams do that by adding context, by requiring two different signals before alerting, by allowing known good activity, and by ranking alerts by risk. When analysts are flooded with false alarms they get tired and start to ignore alerts, which is called alert fatigue, and that is how real attacks such as the one at Target slip through.

Bayes’ rule for alertsExam favourite
P(attack | alert) = P(alert | attack) P(attack) / P(alert)
P(alert) = TPR · P(attack) + FPR · (1 − P(attack)).
PrecisionExam favourite
precision = TP / (TP + FP)
99 / (99 + 9999) ≈ 0.0098.
Two independent signals must agree
TPR = TPR1 TPR2, FPR = FPR1 FPR2
0.9 × 0.9 = 0.81 detection, but 0.01 × 0.01 = 0.0001 false alarms. Precision jumps.
Lesson 7 of 11

Keeping logs trustworthy: time, retention and tamper evidence

A log is only useful if you can trust it. That needs three things. The first is correct time. If one server’s clock is five minutes slow, its events land in the wrong place in the story, so every machine syncs its clock with NTP, and logs should record time in UTC with the time zone shown. The second is retention, which means keeping logs long enough. Many breaches are found months after they start, so a log kept for only a week is often useless. PCI DSS, the card industry standard, asks for at least one year of audit logs with the last three months ready to search, and CERT-In in India asks for 180 days. The third is integrity, meaning that nobody can quietly change or delete old lines. Attackers with admin rights often clear logs, so logs should be copied off the machine at once to a store that only accepts new lines, often called write once storage. On top of that, the log can be made tamper evident with a hash chain. Bruce Schneier and John Kelsey described secure audit logs in 1998. Each record carries a hash, or better a keyed hash called an HMAC, of the previous record’s tag plus its own text. If anyone edits or deletes a record, the chain stops matching at that point, and the checker can show exactly where. The same idea is used in systemd journal sealing on Linux and, in a bigger form, in blockchains and in Certificate Transparency logs.

Lesson 8 of 11

The security operations centre: people, triage and automation

The SIEM is a tool. The people who use it work in a security operations centre, or SOC. Many SOCs have tiers. Tier 1 analysts look at new alerts, check the facts and close the false ones or pass the real ones up. Tier 2 analysts dig deeper into real incidents and decide how to contain them. Tier 3 analysts and threat hunters look for attackers that no rule has found yet, and they write new rules. A SOC lead watches the numbers. Two of the most important are mean time to detect, MTTD, which is how long attackers are inside before anyone notices, and mean time to respond, MTTR, which is how long it then takes to stop them. Lower is better for both. Triage means sorting alerts by how urgent they are, using the importance of the machine, the rights of the user, and how sure the rule is. Repetitive work is handed to SOAR tools, which stands for security orchestration, automation and response. A SOAR playbook can, for example, look up an IP in threat intelligence, check whether the user is travelling, and lock the account, all within seconds, and then ask a human to confirm. Detection engineering is the name for treating rules like software: write them, test them on real and simulated data, keep them in version control, measure their false alarms, and retire the ones that never help.
Triage of one alert, the way a tier 1 analyst does it
  1. Read the alert: which rule fired, on which host and user, and when.
  2. Check the context: is the host important, does the user have admin rights, is the IP known good or known bad.
  3. Look at nearby events from the same user, host and IP in the minutes before and after.
  4. Decide: false alarm (close it with a reason), or real or unsure (raise to tier 2 with notes).
  5. If it was a false alarm, suggest a rule change so it does not happen again.
Mean time to detectExam favourite
MTTD = (Σ detection time − start time) / number of incidents
Incidents found after 2, 5, 11 and 30 days give MTTD = 12 days.
Analysts needed
analysts = alerts per day × minutes per alert / minutes per shift
3000 alerts of 10 minutes over 480 minute shifts need 62.5 analysts. Cutting false alarms is cheaper.

SIEM compared with other monitoring tools

People often mix up the names of monitoring tools, so here they are side by side. Log management simply collects and stores logs for search and reports. A SIEM adds normalising, correlation rules and alerts across every source. EDR, endpoint detection and response, is an agent on each laptop and server that watches processes in great detail and can stop or isolate a machine. NDR watches network traffic. XDR joins endpoint, network, email and cloud data from one vendor into one view. SOAR automates the response steps. They work together: EDR and NDR see deeply in their own area, the SIEM sees across everything, and SOAR acts fast.

Lesson 10 of 11

From beginner to expert

At the start, you only need to know that computers keep a diary and that someone should read it. A college student can parse logs, write threshold and correlation rules, and explain the base rate problem with numbers. A working analyst triages alerts, writes Sigma rules mapped to ATT&CK and tunes them. Experts design whole detection programmes and research better ways to find rare attacks in huge data.
One idea, four depths

Every computer keeps a diary called a log. If a stranger tries many wrong passwords, the diary shows it, and a guard program can raise an alarm.

Log sources and Windows event IDs, syslog, parsing with regular expressions, sliding window and correlation rules, impossible travel with haversine, Bayes and the base rate problem, hash chained logs.

Run a SIEM, write and test Sigma rules mapped to MITRE ATT&CK, measure precision and coverage, build SOAR playbooks, and size storage and retention for laws such as PCI DSS and CERT-In.

Streaming detection at scale, graph based correlation of attack stories, learning baselines that stay robust when attackers poison them, provable log integrity with forward secure keys, and cost aware alert ranking.

Chapter summary

  1. Logs and SIEM: logs are each system’s diary. A SIEM collects, normalises, stores and checks them with rules (term from Gartner, 2005). Target 2013 and Equifax 2017 show logs must be watched and tools kept working.
  2. Sources: identity, endpoint, network, cloud and apps. Windows 4624, 4625, 4672, 4688, 4720, 1102. Syslog RFC 5424. NTP time, never log secrets.
  3. Parsing: regular expressions turn text into fields in one schema (ECS, CIM, OCSF). Enrich with geo, threat intel and asset value. Keep the raw line.
  4. Rules: match, threshold in a sliding window, correlation (failures then success). Sigma rules as data, mapped to ATT&CK T1110, T1078, T1070.
  5. Baselines: impossible travel with haversine and v = d / t, UEBA. Check VPNs before alerting.
  6. Base rate: precision = TP / (TP + FP). Rare attacks make most alerts false (Axelsson 1999). Cut false alarms, combine signals.
  7. Trust: UTC and NTP, retention (PCI 1 year, CERT-In 180 days), ship logs off the host, HMAC hash chains (Schneier and Kelsey 1998).
