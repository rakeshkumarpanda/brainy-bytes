Lesson 1 of 8

How the web works, and why it is attacked so often

Tim Berners-Lee built the World Wide Web at CERN between 1989 and 1991 to share documents. A browser sends an HTTP request, such as GET /cart, and the server sends back a response with a status code, headers and a body. HTTP is stateless: each request stands alone, and the server does not remember the last one. Shopping carts and logins need memory, so in 1994 Lou Montulli at Netscape invented cookies, small values the server asks the browser to store and send back. A year later Netscape added JavaScript, and with it the same origin policy, so that a script from one site could not read pages from another. These three ideas, stateless requests, cookies and origins, explain most web attacks. Today the web is the main way people use software, so it is also the largest attack surface. Web applications take input from anyone on the internet, often talk to databases and other services, and hold valuable data. Verizon’s Data Breach Investigations Reports have found basic web application attacks behind a large share of breaches year after year. The Open Worldwide Application Security Project, OWASP, a non profit founded in 2001, publishes free guides, tools and the famous OWASP Top 10 list of the most critical web risks, first released in 2003. HTTPS, which wraps HTTP in TLS as you saw in the cryptography section, protects the traffic in transit. It does nothing about bugs in the application itself, and that is what this section is about.

Source: RFC 9110 HTTP Semantics (2022), RFC 6265 HTTP State Management (2011) and the RFC 6265bis draft, RFC 6454 The Web Origin Concept (2011), WHATWG Fetch Standard (CORS), RFC 6797 HSTS (2012), RFC 7519 JSON Web Token and RFC 7518 JSON Web Algorithms (2015), RFC 8725 JWT Best Current Practices (2020), OWASP Top 10 2021 and 2025, OWASP Session Management, HTTP Headers and Authorization cheat sheets, MDN Web Docs, Tim McLean, Critical vulnerabilities in JSON Web Token libraries (2015).

Practise safely and legally
Test only your own applications or deliberately vulnerable practice apps such as OWASP Juice Shop or DVWA running on your own machine. Probing a real website without written permission is illegal even if you mean no harm.
What it is
A web application is a program that answers HTTP requests from browsers and other clients. Web security keeps its data and users safe from requests that are crafted to abuse it.
Why we need it
Web apps face everyone on the internet, handle money and personal data, and are built quickly from many parts. Most breaches of organisations touch a web app or API somewhere.
How it works
Protect the session (cookies with the right flags, short lived tokens), rely on the browser’s same origin policy, check authorisation on the server for every request, validate and encode all input and output, send security headers, and keep components updated.

Lesson 2 of 8

Sessions and cookies: staying logged in safely

After you log in, the server creates a session: a record of who you are, stored on the server and found by a long random session id. The id goes to the browser in a Set-Cookie header and comes back in every request. Anyone who learns the id is you, for as long as the session lasts, so protecting it is the core of web session security. In 2010 Eric Butler released Firesheep, a Firefox add on that let anyone on a café Wi-Fi click to take over other people’s Facebook and Twitter sessions, because those sites used HTTPS only for the login page and sent the session cookie in the clear afterwards. Within a few years the big sites moved to HTTPS everywhere. Three cookie flags block three different attacks. Secure tells the browser never to send the cookie over plain HTTP. HttpOnly hides the cookie from JavaScript, so a cross site scripting bug cannot simply read it. SameSite controls whether the cookie is sent on requests that start from another site: Strict never, Lax only on top level link clicks, and None always, which then requires Secure. Chrome made Lax the default in 2020. The cookie prefix __Host- adds a further guarantee that the cookie was set by this exact host over HTTPS. Good session handling also means making a new session id at login, to stop session fixation, expiring idle sessions, and deleting the session on the server at logout, not just in the browser.

Real world scenario: Firesheep, October 2010

At the ToorCon conference in San Diego, Eric Butler showed a browser add on with a sidebar listing the people around him on the same open Wi-Fi, with their names and profile photos. Double click one, and you were logged in as them. Nothing about it was new to security experts, but it made the risk obvious to everyone. It spread quickly, and within a few years Facebook, Twitter and Google had moved to full time HTTPS.

The same origin policy and CORS

Your browser is logged in to many sites at once: email, bank, work tools. Without a rule, any web page you visit could send a request to your bank, with your cookies, and read the answer. The same origin policy, introduced with JavaScript in Netscape Navigator 2.0 in 1995, is that rule. A script may only read responses from its own origin, where the origin is the scheme, host and port together. https://shop.example.com and http://shop.example.com are different origins, and so are shop.example.com and api.example.com. The policy restricts reading, not sending: a page can still submit a form or load an image from another site, which is why cross site request forgery is possible and why SameSite cookies were added. When a site really does want to share, for example a front end on one origin calling its own API on another, the server uses Cross Origin Resource Sharing, CORS. It replies with an Access-Control-Allow-Origin header naming the origins it trusts, and for unusual requests the browser first sends a preflight OPTIONS request to ask permission. CORS mistakes are common. Reflecting whatever Origin header arrives while also allowing credentials is the worst: it switches the protection off for every site on the internet.

Lesson 4 of 8

Tokens: JWTs, OAuth 2.0 and OpenID Connect

Many modern apps, especially APIs and mobile apps, use tokens instead of server side sessions. The most common format is the JSON Web Token, standardised in RFC 7519 in 2015. A JWT has three parts, each base64url encoded and joined by dots: a header naming the signing algorithm, a payload of claims such as the user id, role and expiry time, and a signature. With HS256 the server signs with HMAC-SHA-256 and a secret key, the same HMAC you met in the hashing chapter. With RS256 or ES256 it signs with an RSA or elliptic curve private key, so other services can verify with only the public key. The payload is encoded, not encrypted, so anyone holding the token can read it. Never put secrets in it. The signature only stops changes. In 2015 Tim McLean showed that several JWT libraries trusted the header’s alg field: an attacker could set it to none and drop the signature, or switch RS256 to HS256 and sign with the public key as if it were an HMAC secret. The fix, now written into RFC 8725, is that the server decides which algorithm it accepts. Tokens cannot easily be revoked before they expire, so access tokens are kept short, often 5 to 15 minutes, with a refresh token to get new ones. OAuth 2.0, from 2012, is the framework behind "Sign in with Google": it lets one service get limited access to your account at another without your password. OpenID Connect, from 2014, adds a signed ID token on top of OAuth so the app learns who you are.

Lesson 5 of 8

The OWASP Top 10

The OWASP Top 10 is the best known list in application security. OWASP builds it from data contributed by testing companies and from a survey of practitioners, and it is used as a training syllabus, a checklist and a requirement in standards such as PCI DSS for card payments. The 2021 edition put broken access control at number one: in tested apps, some form of it showed up more than any other weakness. Broken access control means a logged in user can do or see things they should not, such as changing the invoice number in a URL to read someone else’s invoice. This kind is called an insecure direct object reference, or IDOR. In 2019 First American Financial exposed about 885 million mortgage documents this way, and in 2022 the Australian telecom Optus lost data on about 9.8 million customers through an exposed API that took sequential ids. The fix is simple to state and easy to forget: check, on the server, for every request, that this user may access this object. The 2025 edition keeps broken access control at the top, moves security misconfiguration to second, and adds two new categories: software supply chain failures, which grew out of vulnerable and outdated components, and mishandling of exceptional conditions, such as code that fails open when an error occurs. Server side request forgery, which had its own place in 2021, is now part of broken access control. Many items on the list get their own lessons in the next two chapters: injection, cross site scripting and request forgery.

Web defences compared

Web defences are often confused because they sit close together. The same origin policy stops reading across sites, CORS relaxes it on purpose, SameSite stops cookies travelling with cross site requests, and a content security policy limits what scripts may run. Each answers a different question, and a secure site uses them together.

Lesson 7 of 8

From beginner to expert

A beginner looks for the padlock, logs out on shared computers and uses a password manager. A college student can read raw HTTP, explain the same origin policy, audit cookies and headers, and find an IDOR in a practice app. A professional tests web apps and APIs with tools such as Burp Suite and OWASP ZAP and writes secure code reviews. Researchers find new browser level attack classes, such as cross site leaks and request smuggling, and design new browser defences.
One idea, four depths

Check the address and the padlock, log out on shared devices, keep the browser updated, and use a password manager so that look alike sites get nothing.

HTTP requests and responses, cookies and their flags, the same origin policy and CORS, JWT structure and verification, the OWASP Top 10, and IDOR.

Test apps with Burp Suite or OWASP ZAP, review code for access control, design token lifetimes and refresh, set CSP and HSTS, and follow the OWASP ASVS checklist.

HTTP request smuggling, cross site leaks (XS-Leaks), browser isolation models such as Site Isolation, formal models of web protocols such as OAuth, and automated access control testing.

Chapter summary

  1. The web: stateless HTTP, cookies (1994) for memory, the same origin policy (1995) for isolation. HTTPS protects transport, not app logic.
  2. Sessions: a 128 bit random id in a cookie with Secure, HttpOnly and SameSite. New id at login, server side logout, idle expiry. Firesheep showed why.
  3. Origins: scheme + host + port must all match. SOP blocks reading, not sending. CORS lets a server share on purpose, with exact origins.
  4. Tokens: JWT = header.payload.signature, signed not encrypted. Fix the algorithm on the server, use strong keys, short lifetimes. OAuth 2.0 and OIDC.
  5. OWASP Top 10: broken access control is first in 2021 and 2025. Check ownership on every request. 2025 adds supply chain failures and exceptional conditions.
  6. Headers: HSTS, CSP, X-Content-Type-Options, Referrer-Policy, Permissions-Policy. Remove version banners.
