Lesson 1 of 9

Subjects, objects and the reference monitor

Once a system knows who you are, it must decide what you may do. This is access control, also called authorisation. The vocabulary comes from the early 1970s. Subjects are the active parties, users and the processes acting for them. Objects are the things they act on: files, records, devices, API endpoints. Rights or permissions are the operations allowed, such as read, write or execute. Butler Lampson described in 1971 the access matrix, a table with a row for each subject, a column for each object, and the rights in each cell. In 1972 James Anderson’s report for the US Air Force introduced the reference monitor: a component that checks every access, cannot be tampered with, and is small enough to verify. Every operating system kernel, database and web framework contains some version of it. In 1975 Jerome Saltzer and Michael Schroeder wrote down design principles that are still taught, among them least privilege, fail safe defaults and complete mediation. Access control is still where many breaches happen: broken access control is number one in the 2021 OWASP Top 10, and the 2019 Capital One breach combined a server side request forgery with an overly powerful cloud role. This chapter covers the classic models and how they appear in real systems today.

Source: Lampson, Protection (1971), Anderson, Computer Security Technology Planning Study (1972), Saltzer and Schroeder, The Protection of Information in Computer Systems (1975), Harrison, Ruzzo and Ullman (1976), Bell and LaPadula (MITRE 1973 to 1976), Biba (1977), Clark and Wilson (IEEE S&P 1987), Brewer and Nash (1989), Ferraiolo and Kuhn (1992), ANSI INCITS 359-2004, NIST SP 800-162 (2014), Hardy (1988), Pang et al., Zanzibar (USENIX ATC 2019), OWASP Top 10 (2021).

What it is
Access control decides whether a subject may perform an operation on an object, according to a policy, and enforces that decision on every access.
Why we need it
Authentication only says who you are. Without correct authorisation, any logged in user, or any process an attacker hijacks, could do anything.
How it works
A reference monitor intercepts each request and checks it against stored policy: an access matrix kept as ACLs or capabilities, security labels, roles or attributes.

ACLs and capabilities

No system stores the whole access matrix, because it is huge and mostly empty. There are two natural ways to store only its useful parts. An access control list stores one column with each object: for this file, asha may read and write, ravi may read. Unix permission bits are a compressed ACL with three entries, owner, group and others, and Windows, macOS, cloud storage buckets and databases all use richer ACLs. A capability list stores one row with each subject: this process holds a right to read this file and write that socket. An open file descriptor in Unix is a capability: once you have it, the kernel does not check the file’s permissions again. ACLs make it easy to answer who can access an object and to revoke one person, but hard to list everything a subject can reach. Capabilities make delegation and checking easy, because holding the capability is the proof, but revocation is hard, since copies may be anywhere. Capabilities also avoid the confused deputy problem, described by Norm Hardy in 1988, where a privileged program is tricked into using its own authority on behalf of a caller who should not have it. Server side request forgery and many cloud breaches are confused deputy attacks.

Common mistake
A confused deputy is a program with authority that acts on a request without checking the requester’s authority. A web server that fetches any URL a user gives it, including the cloud metadata service, is a confused deputy. Fix it by checking on behalf of whom an action is done, or by passing capabilities instead of names.
Lesson 3 of 9

DAC and MAC: Bell-LaPadula and Biba

In discretionary access control, DAC, the owner of an object decides who may use it. Most desktop systems work this way. Its weakness is that any program you run acts with your rights, so a Trojan horse can copy your secret file anywhere you can write. Mandatory access control, MAC, takes the decision away from users: the system enforces a policy based on security labels that users cannot change. The classic secrecy model is Bell-LaPadula, developed at MITRE from 1973 for the US military. Each subject has a clearance and each object a classification, such as Confidential, Secret or Top Secret, plus categories called compartments, such as Nuclear or Crypto. Labels form a lattice. A subject may read an object only if its label dominates the object’s label: no read up. It may write only if the object’s label dominates its own: no write down. Together these stop information from flowing to a lower level, even through a Trojan horse. In 1977 Kenneth Biba turned the model around for integrity: no read down, so trusted processes are not polluted by untrusted data, and no write up, so untrusted processes cannot corrupt trusted data. Today SELinux, released by the NSA in 2000 and part of Android since 2014, and AppArmor provide MAC in Linux, and Windows Mandatory Integrity Control follows Biba’s idea.

What it is
Bell-LaPadula (secrecy): read if L(s) ≥ L(o), write if L(o) ≥ L(s). Biba (integrity): read if I(o) ≥ I(s), write if I(s) ≥ I(o).
Why we need it
They give guarantees that hold even when users make mistakes or run malicious code, which DAC cannot.
How it works
Give every subject and object a label (level plus a set of categories). The reference monitor compares labels with the dominance relation on every read and write.
DominanceExam favourite
(l1, C1) ≥ (l2, C2) iff l1 ≥ l2 and C2 ⊆ C1
SECRET {NUCLEAR} dominates UNCLASSIFIED {}, but not SECRET {CRYPTO}: the categories do not nest.
Number of labelsExam favourite
|levels| × 2|categories|
4 levels and 3 categories: 4 × 8 = 32 labels.
Lattice operations
join = (max level, union of categories), meet = (min level, intersection)
Data combined from two labels must carry their join.
Going deeper: Why the star property is needed

With only no read up, a Secret user could run a program that reads a Secret file and writes its contents into an Unclassified file, which Unclassified users can read. The leak needs no read up at all, just a write down. The star property forbids that write. It does make life awkward: a Secret user cannot even send an email to an Unclassified colleague. Real systems add trusted subjects that may downgrade after review. Even then, covert channels, such as a high process varying CPU load or file locks that a low process can observe, can leak bits, which is why high assurance systems also measure and limit covert channel bandwidth.

Lesson 4 of 9

Commercial models: Clark-Wilson and the Chinese Wall

Businesses care less about classified levels and more about honest records and conflicts of interest. In 1987 David Clark and David Wilson described a model based on how accountants keep books. Data that matters, such as account balances, may only be changed by well formed transactions, programs certified to keep the data consistent, and duties are separated so no single person can both create and approve a change. Every change is logged so it can be audited. In 1989 David Brewer and Michael Nash formalised the Chinese Wall policy used by consultancies and banks. Companies are grouped into conflict of interest classes, such as all banks or all oil firms. A consultant may at first read any company’s data, but once they have read one bank’s files, they may no longer read another bank’s, although an oil company is still fine. What you may access depends on what you have already accessed, which makes this model dynamic, unlike Bell-LaPadula.

Lesson 5 of 9

Role based access control

In a company of thousands, giving permissions to each person directly becomes unmanageable: people join, move and leave every week. Role based access control, proposed by David Ferraiolo and Richard Kuhn at NIST in 1992 and standardised in 2004, adds a layer in between. Permissions are assigned to roles, such as accountant or nurse, and users are assigned to roles. When someone changes job, an administrator changes their roles, not hundreds of permissions. Roles can form a hierarchy, where a senior role inherits the permissions of junior ones. Constraints add safety: static separation of duties forbids one person from holding two conflicting roles, such as the person who approves payments and the person who makes them, and dynamic separation forbids activating both in the same session. RBAC is everywhere: databases, Kubernetes, cloud platforms and business applications. Its typical problem is role explosion, where organisations create thousands of narrow roles, and permission creep, where people collect roles as they move and never lose them, which regular access reviews must catch.

What it is
RBAC: users → roles → permissions, with role hierarchies and separation of duty constraints (ANSI INCITS 359-2004).
Why we need it
It matches how organisations think about jobs, cuts administration, and makes reviews and audits practical.
How it works
Store user assignment (UA) and permission assignment (PA) relations. A user has permission p if some role they hold, or a role that role inherits, has p. Refuse assignments that break conflict rules.
Administration savingExam favourite
direct: |users| × perms per user, RBAC: |UA| + |PA|
1000 users with 80 permissions each: 80000 direct entries. With 20 roles: 2000 user role links + 800 role permission links = 2800.
Possible conflicting pairs
C(r, 2) = r(r − 1)/2
6 roles give 15 pairs to consider for separation of duties.

Attribute based and relationship based access control

Roles are sometimes too coarse. A hospital may want to say that a doctor may read a patient’s record only while assigned to that patient’s ward, during a shift, from a managed device. Attribute based access control, ABAC, described in NIST SP 800-162 in 2014, writes policies over attributes of the subject (department, clearance, role), the resource (owner, classification), the action, and the environment (time, location, device health). A policy engine evaluates each request against the rules. Cloud identity policies, such as those in AWS IAM with their conditions, and policy engines such as Open Policy Agent work this way, and XACML is an older standard language for it. When rules conflict, a combining rule decides, commonly deny overrides: any matching deny wins. A related idea, relationship based access control, decides from a graph of relationships: you may edit this document because you are a member of a group that owns its folder. Google described its global system for this, Zanzibar, in 2019, and it inspired open source systems such as SpiceDB and OpenFGA. The trade off is power against understandability: the more expressive the policy, the harder it is to know who can actually do what.

What it is
ABAC: allow or deny from rules over subject, resource, action and environment attributes. ReBAC: decide from relationships in a graph.
Why we need it
It expresses context such as time, location, device health and ownership that roles alone cannot, which zero trust needs.
How it works
A policy decision point evaluates rules, combines results (often deny overrides with default deny), and a policy enforcement point applies the result.
Attribute combinationsExam favourite
cases = product of the number of values of each attribute
5 departments × 3 clearances × 2 device states = 30 cases a policy must handle correctly.
Remember
More expressive policies are harder to audit. Test policies like code: write cases that must be allowed and must be denied, and run them on every change.
Lesson 7 of 9

Access control models compared

Most real systems mix models. A Linux server uses DAC permission bits, SELinux MAC labels and sudo roles. A cloud account uses RBAC for broad roles and ABAC conditions for context. The useful exam habit is to match the model to the goal: secrecy with labels calls for Bell-LaPadula, integrity for Biba or Clark-Wilson, conflicts of interest for the Chinese Wall, organisational jobs for RBAC, and context dependent rules for ABAC.

Lesson 8 of 9

From beginner to expert

A beginner understands that logging in is not the same as being allowed, and that everyone should have only the access they need. A college student can explain the access matrix, ACLs and capabilities, Bell-LaPadula and Biba rules, RBAC with separation of duties, and write a policy check in code. A masters student studies lattice based information flow, the Harrison, Ruzzo and Ullman result that deciding whether a right can ever leak is undecidable in general, Clark-Wilson certification, SELinux type enforcement, cloud IAM policy analysis and the confused deputy. Researchers verify kernels such as seL4, analyse policies with SMT solvers, as cloud providers now do to find public buckets, design language based information flow control, and build relationship based systems at global scale.
One idea, four depths

Logging in is not permission. Give people only the access they need, and remove it when they change jobs.
