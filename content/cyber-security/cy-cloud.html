What cloud security is, and the shared responsibility model

Cloud computing means renting computers, storage and software from a provider such as Amazon Web Services, Microsoft Azure or Google Cloud, instead of buying and running your own. NIST describes three main service models. In infrastructure as a service, IaaS, you rent virtual machines and manage everything on them. In platform as a service, PaaS, the provider also runs the operating system and the platform, such as a managed database, and you bring your code and data. In software as a service, SaaS, you just use finished software such as Microsoft 365 or Gmail. Security in the cloud is shared. The provider secures the buildings, the hardware and the virtualisation layer, often called security of the cloud. You secure what you put in it, called security in the cloud: your data, your user accounts, your settings and, in IaaS, your operating systems. The line moves with the service model, as the animation shows, but your data and your accounts are always yours. Most cloud breaches come from the customer side. In 2019 Gartner predicted that through 2025, 99 percent of cloud security failures would be the customer’s fault. Real cases agree. At Capital One in 2019, a firewall setting and a server side request forgery bug exposed data on about 100 million people. In 2024, attackers logged into about 165 companies’ Snowflake data warehouse accounts with passwords stolen by malware, because those accounts had no MFA. And sometimes the provider slips: in 2023 a group Microsoft calls Storm-0558 used a stolen signing key to forge logins to government email accounts, which a US review board later called a cascade of avoidable errors.

Source: NIST SP 800-145 (2011), AWS, Azure and Google Cloud shared responsibility pages, AWS IAM policy evaluation logic, AWS IMDSv2 and KMS documentation, NIST SP 800-38D, CIS cloud benchmarks, CSA Cloud Controls Matrix, US court and Senate records on Capital One (2019), US Cyber Safety Review Board report on Storm-0558 (April 2024), Mandiant report on UNC5537 and Snowflake customers (June 2024), Gartner (2019).

Identity is the new perimeter: IAM and least privilege

In the cloud, almost everything is controlled through an API, so whoever holds the right identity can change anything from anywhere. That is why people say identity is the new perimeter. Identity and access management, IAM, decides who can do what to which resource. A policy is a list of statements, each saying allow or deny, which actions, and on which resources, often with wildcards like s3:* for every storage action. When a request comes in, AWS checks in a fixed order: if any statement explicitly denies it, the answer is no, whatever else is allowed. Otherwise, if any statement allows it, the answer is yes. Otherwise the default is no. Azure and Google Cloud use similar ideas with their own words. Two habits keep IAM safe. The first is least privilege: give each person and each program only the actions it needs. Over time roles collect permissions nobody uses. The program below compares what a role is granted with what the audit log shows it actually used, the same idea as AWS IAM Access Analyzer, and finds that most permissions can go. The second is to avoid long lived secret keys. People should log in through single sign on with MFA, and programs running in the cloud should use roles that give short lived keys automatically. Long lived access keys in code are one of the most common causes of cloud breaches, because they leak through public repositories, laptops and logs.

Misconfiguration: buckets, firewall rules and the metadata service

The second big cause of cloud breaches is a wrong setting. Storage buckets set to public, databases reachable from the internet, firewall rules that let anyone in the world reach port 22 for SSH or 3389 for Remote Desktop, and audit logging switched off. These mistakes are easy to make, because a single tick box changes them, and easy for attackers to find, because they scan the whole internet for open services and guess bucket names all day. A cloud security posture management tool, CSPM, reads all your settings through the provider’s API and checks them against rules such as the CIS Benchmarks, as the program below does in miniature. One special setting deserves its own story. Every cloud server can ask a local address, 169.254.169.254, called the instance metadata service, for the short lived keys of its role. At Capital One in 2019, an attacker found a web app with a server side request forgery bug, made it fetch the metadata address, received the role’s keys, and used them to download data from storage buckets that the role could read. The fixes are layered: fix the bug, require IMDSv2, which needs a session token that a simple forged request cannot get, and give each role access only to its own data, as the animation shows. Address ranges are written as CIDR blocks, such as 10.0.0.0/24, and a little maths tells you how many addresses a rule really opens.

Protecting data: encryption, keys and secrets

Cloud providers encrypt data at rest by default today, but who controls the keys matters. Behind the scenes they use envelope encryption. Each file or disk gets its own data key. The data key is then locked with a master key, called a key encryption key, that lives inside the key management service, KMS, in tamper resistant hardware and never leaves it. To read the file, a program sends the locked data key to KMS, which checks the program’s permission, writes a log entry, and returns the unlocked data key. This design has three benefits, shown in the animation. A thief who copies the stored files gets only locked data and a locked key. Every unlock leaves an audit record. And rotating the master key means re locking only the small data keys, not re encrypting terabytes of data. A data key per file also keeps each key well within safe limits, because AES-GCM with random 96 bit nonces should not be used for more than about four billion messages under one key. Customers can choose provider managed keys, customer managed keys in KMS, or keys they bring from their own hardware, trading convenience for control. Passwords, API keys and database credentials, called secrets, belong in a secrets manager such as AWS Secrets Manager, Azure Key Vault or HashiCorp Vault, never in code or configuration files, and they should be rotated regularly.

Infrastructure as code, containers and monitoring

Modern teams create cloud resources with code, called infrastructure as code, using tools such as Terraform, AWS CloudFormation or Bicep. That is good news for security, because settings can be reviewed and scanned before they ever reach the cloud. Scanners such as Checkov, tfsec and KICS read the code and flag public buckets, open ports and missing encryption in the pull request, as the program below shows. Containers and Kubernetes add their own checks: scan images for known vulnerabilities, run containers as a non root user with a read only file system, never run privileged containers, limit what each workload can reach with network policies, and use Kubernetes role based access control. Finally, the cloud must be watched like any network. Turn on audit logs such as AWS CloudTrail, Azure activity logs and Google Cloud audit logs in every account and region, send them to a separate, locked logging account, and alert on dangerous events: root logins, logging turned off, new admin users, keys created, and policies made public. Many tools now bundle these jobs. CSPM checks settings, CWPP protects workloads such as servers and containers, CIEM manages cloud identities and permissions, and a CNAPP, cloud native application protection platform, joins them together.

A secure cloud landing zone, step by step
  1. Separate accounts or subscriptions for production, development, security tooling and logging.
  2. Single sign on with MFA for all people, no long lived access keys, and a locked root account.
  3. Guard rails at the top level: block public storage, deny turning off logging, allow only approved regions.
  4. Audit logs from every account sent to the logging account that nobody else can change.
  5. Infrastructure as code with scanning in every pull request, and CSPM checks on what is running.
  6. Alerts on root logins, new admin users, public resources and keys used from unusual places.

Cloud security tools compared

The cloud security market has many short names. They overlap, and many products now combine several. What matters is which question each one answers: are my settings right, are my workloads safe, are my identities too powerful, is my code safe before deployment, and what is happening right now.

From beginner to expert

A beginner knows that the cloud is someone else’s computer and that you still look after your own data and passwords. A student can explain shared responsibility, evaluate IAM policies, count CIDR addresses and describe envelope encryption. A professional builds secure landing zones and runs CSPM and incident response in the cloud. Experts design multi cloud security at scale and research isolation and confidential computing.
One idea, four depths

The cloud is someone else’s computer. They lock the building, but you still choose who gets your password and which files are shared.

IaaS, PaaS and SaaS responsibility, IAM evaluation order and least privilege, CIDR counting, public bucket and open port checks, IMDSv2, envelope encryption with KMS, IaC scanning.

Landing zones with guard rails, single sign on and roles everywhere, CSPM and CIEM programmes, cloud incident response with audit logs, Kubernetes hardening, and certifications such as CCSP or AWS Security Specialty.

Formal reasoning about IAM policies (AWS Zelkova uses SMT solvers), confidential computing with hardware enclaves, side channels between tenants, and multi cloud identity federation at scale.
