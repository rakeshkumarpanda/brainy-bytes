Lesson 1 of 9

Building security in: the secure development life cycle

For a long time security was something tested at the end, if at all. On 15 January 2002, after worms such as Code Red and Nimda had hit Windows servers, Bill Gates sent every Microsoft employee a memo titled Trustworthy Computing, saying that security must come before new features. Microsoft stopped much of its Windows development for security training and code review, and in 2004 made the Security Development Lifecycle, SDL, mandatory for its products. The idea spread: build security into every phase, from requirements and design through coding, testing, release and response, instead of bolting it on afterwards. This is often called shifting left, because security work moves earlier on the project timeline, where flaws are cheaper to fix. Today the main frameworks are the NIST Secure Software Development Framework, SP 800-218 from 2022, which US government suppliers must attest to, OWASP SAMM for measuring a programme’s maturity, OWASP ASVS as a checklist of verifiable requirements, and SLSA for the integrity of the build and supply chain. DevSecOps means doing all of this inside fast automated pipelines, so that every commit is scanned and tested without slowing developers down. This chapter covers the core practices: threat modelling at design time, attack trees to decide where to spend, static analysis and secret scanning on code, fuzzing during testing, and protecting the build pipeline itself, which attackers targeted in the SolarWinds compromise of 2020.

Threat modelling with STRIDE

Threat modelling means thinking like an attacker about a design before it is built. Adam Shostack, who led threat modelling at Microsoft, sums it up in four questions: what are we working on, what can go wrong, what are we going to do about it, and did we do a good job. The usual first step is a data flow diagram that shows external entities such as users and other systems, the processes that handle data, the data stores, the flows between them, and the trust boundaries where data crosses from a less trusted zone to a more trusted one, such as from the internet into your network. Most attacks happen at those boundaries. The second step is to ask what can go wrong, and STRIDE, created by Loren Kohnfelder and Praerit Garg at Microsoft in 1999, gives a checklist of six threat types, each the opposite of a security property. Spoofing breaks authentication, Tampering breaks integrity, Repudiation breaks non repudiation, Information disclosure breaks confidentiality, Denial of service breaks availability, and Elevation of privilege breaks authorisation. Microsoft’s STRIDE per element table says which letters apply to which kind of element: processes can suffer all six, data flows can be tampered with, read or blocked, and so on. Each threat found becomes a work item with an owner: mitigate it, transfer it, avoid it by changing the design, or accept it with a recorded reason. Other methods exist, such as PASTA, which is risk centred, LINDDUN for privacy threats, and simple attack trees, but STRIDE remains the most taught. An older scoring scheme, DREAD, was dropped by Microsoft because scores varied too much between people.

Attack trees: quantifying where to defend

Bruce Schneier popularised attack trees in Dr. Dobb’s Journal in December 1999. The attacker’s goal sits at the root, such as read the customer database. Below it are the ways to achieve it, and below those the steps each way needs. A node is either an OR node, where any one child is enough, or an AND node, where all children are needed. Once leaves carry numbers, such as the attacker’s cost, the skill needed or the chance of success, the tree can be evaluated from the bottom up. For cost, an OR node takes the cheapest child and an AND node adds its children. For probability, assuming independence, an AND node multiplies its children’s chances, and an OR node gives one minus the product of the chances of failing. The root then shows the attacker’s cheapest route, and trying a defence means setting a leaf to impossible and evaluating again. This makes the main lesson of security economics visible: a rational attacker takes the weakest path, so strengthening anything other than the weakest path changes little. Fixing an injection bug while a backup bucket sits open to the internet leaves the cheapest attack exactly where it was. Attack trees connect naturally to the MITRE ATT&CK framework, whose techniques make good leaves, and to the risk calculations in the foundations section.

Static analysis and secret scanning

Static application security testing, SAST, reads source code without running it and looks for dangerous patterns. Simple tools work like the program below: they parse the code into a syntax tree and flag calls such as eval, pickle.loads or subprocess with shell set to true. Bandit does this for Python, and Semgrep lets teams write such rules in a few lines for many languages. Deeper tools such as GitHub CodeQL track data flow, following untrusted input from where it enters, called a source, to dangerous functions, called sinks, so they can tell a SQL query built from user input from one built from constants. No static analyser can be perfect. Rice’s theorem, from 1953, says that no program can decide any interesting property of all programs, so every tool either misses some bugs or raises some false alarms, and good tools let teams tune that balance. Secret scanning is a special, very valuable case. Developers often commit passwords, API keys and private keys by accident. In 2016 attackers found AWS credentials in a private GitHub repository used by Uber engineers, used them to download data on 57 million riders and drivers from cloud storage, and Uber then paid the attackers to stay quiet, which led to criminal charges against its security chief. Scanners such as gitleaks and GitHub’s secret scanning match known key formats, such as AWS keys beginning with AKIA, and also flag strings with high entropy that look random. When a real secret leaks, deleting the commit is not enough, because copies exist in clones and caches. The secret must be revoked and replaced.

Going deeper: Sources, sinks and taint

Taint analysis marks values from untrusted sources, such as request parameters, files and environment variables, as tainted. Taint flows through assignments and function calls. Passing a value through a sanitiser, such as an escaping function or a strict parser, removes the taint. A finding is reported when tainted data reaches a sink, such as a SQL execute call, a shell command, eval or an HTML template marked safe. This is how CodeQL and commercial tools find injection paths that cross many files.

Fuzzing: millions of strange inputs

Fuzzing means feeding a program huge numbers of malformed or random inputs and watching for crashes, hangs or sanitiser reports. Barton Miller at the University of Wisconsin coined the term in 1988, after a stormy night when line noise on his dial up connection crashed Unix tools, and his class found that random input crashed about a quarter to a third of standard Unix utilities. Pure random fuzzing is weak against programs that check their input step by step, because random bytes almost never pass several checks in a row. The breakthrough was coverage guidance. Michal Zalewski’s American Fuzzy Lop, AFL, released in 2013, instruments the program so that each run reports which branches it took, keeps any input that reaches new branches, and mutates those inputs further. The fuzzer climbs through the program check by check, as in the animation, where a crash that random inputs would need tens of millions of tries to hit appears after about twenty thousand. AFL found hundreds of bugs in widely used software, and libFuzzer and AFL++ continue the line. Google’s OSS-Fuzz, launched in 2016, runs these fuzzers continuously for over a thousand open source projects and has found tens of thousands of bugs, many of them security issues. Fuzzing works best together with sanitisers, which turn silent memory corruption into crashes, and with grammar based or structure aware fuzzers for formats such as PDF, fonts, protocols and JavaScript.

The build pipeline and software supply chain

Modern software is mostly other people’s code: a typical application pulls in hundreds of open source packages, and it is built and shipped by automated pipelines. Attackers have learned that compromising the pipeline or a popular dependency reaches thousands of victims at once. In the SolarWinds attack, discovered in December 2020, intruders, attributed by the US government to Russia’s foreign intelligence service, planted code in the build system of the Orion network management product, so the company itself signed and shipped a backdoored update to about 18000 customers, including US government agencies. In the same years attackers published malicious packages with names close to popular ones, called typosquatting, took over abandoned packages, and in the xz utils case spent two years earning a maintainer’s trust. Defences focus on knowing and controlling what goes into a build. A software bill of materials lists every component. Dependencies are pinned to exact versions and verified with hashes. Software composition analysis tools match components against vulnerability databases. Builds run in isolated, short lived environments from version controlled definitions, and their outputs are signed, for example with Sigstore, so users can check where an artefact came from. The SLSA framework, started by Google in 2021, defines levels of build integrity, up to builds whose provenance can be verified end to end. Pipelines themselves need protection: secrets kept in a vault, branch protection and required reviews, and least privilege tokens for every automated step.
A DevSecOps pipeline for every commit
  1. Pre commit: secret scanning and formatting hooks on the developer’s machine.
  2. Pull request: peer review, SAST (Semgrep, CodeQL), dependency scan, licence check.
  3. Build: pinned dependencies with hashes, isolated runner, SBOM generated, artefact signed.
  4. Test: unit and integration tests, fuzzing for parsers, dynamic scan of a test deployment.
  5. Deploy: verify signatures and provenance, infrastructure as code checks, least privilege credentials.
  6. Run: monitoring, alerts, and a path for vulnerability reports back into the backlog.

Security testing methods compared

Testing methods are complementary, because each sees the software from a different angle. Static analysis sees all the code but not how it behaves at runtime. Dynamic scanning sees the running app from outside but not the code. Fuzzing goes deep into parsers. Software composition analysis covers the code you did not write. Penetration testers find the logic flaws that tools miss. A mature programme uses all of them at the stage where each is cheapest.

From beginner to expert

A beginner understands that security is part of building software, not an afterthought. A college student can draw a data flow diagram, apply STRIDE, evaluate an attack tree, and write simple scanners and fuzzers. A professional runs threat modelling sessions, maintains a DevSecOps pipeline and tunes tools so developers trust them. Researchers work on precise static analysis, smarter fuzzers that use symbolic execution or machine learning, and verifiable build provenance.
One idea, four depths

Know that good software teams plan for attacks, review each other’s code, and keep their tools and libraries up to date.

The SDL phases, data flow diagrams and STRIDE, attack tree maths, SAST with syntax trees, secret scanning with entropy, coverage guided fuzzing, SBOMs and signed builds.

Run threat modelling workshops, write Semgrep and CodeQL rules, build fuzzing harnesses, set up SLSA provenance and Sigstore signing, and measure the programme with OWASP SAMM.

Sound and precise static analysis, symbolic and concolic execution (KLEE, angr), hybrid and ML guided fuzzing, reproducible builds, and formal verification of critical components.
