Lesson 1 of 9

Cross site scripting: three kinds, one cause

Cross site scripting, or XSS, lets an attacker run their own JavaScript inside someone else’s website, in the victim’s browser. Engineers at Microsoft gave it its name around the turn of the year 2000, and CERT warned about it in advisory CA-2000-02 in February 2000. It happens when a page includes text from an untrusted source in its HTML without encoding it, so that the browser reads the text as markup and code. Because the script arrives from the real site, the same origin policy treats it as the site’s own. It can read everything on the page, make requests as the logged in user, change what the user sees, and record keystrokes. There are three kinds. In stored XSS the payload is saved on the server, for example in a comment or profile, and runs for everyone who views it. In reflected XSS the payload travels in a link and is echoed back once, so the attacker must get each victim to click. In DOM based XSS the server never sees the payload: the site’s own JavaScript takes something like the part of the URL after the hash sign and writes it into the page with innerHTML. The most famous XSS is the Samy worm. On 4 October 2005 Samy Kamkar put a script in his MySpace profile that added him as a friend of anyone who viewed it and copied itself into their profile. Over a million users were infected in about 20 hours, MySpace had to shut down, and Samy was later sentenced to probation and community service. A related attack is changing a script the site loads from elsewhere. In 2018 attackers altered a script on the British Airways site to copy card details as customers typed them, affecting around 400000 people, and the UK regulator fined the airline 20 million pounds.

Why we need it
The script runs with the site’s origin, so it can do anything the user can: read private data, post, buy, change settings, or show a fake login. XSS is one of the most often reported web bugs in bug bounty programmes.

Output encoding: the right escape for each context

The main defence against XSS is output encoding, and the key idea is that the right encoding depends on where the text lands. Inside normal HTML text, the characters less than, greater than and ampersand must become entities such as &lt;, so the browser shows them instead of opening a tag. Inside an HTML attribute the value must also be quoted and its quote characters encoded, or the attacker can close the attribute and add an event handler such as onmouseover. Inside a JavaScript string, HTML entities do not help, because the JavaScript parser does not decode them. Here the safe way is to produce a proper JavaScript string, for example with json.dumps, and also make the less than sign harmless so that a closing script tag inside the string cannot end the script block early. Inside a URL attribute such as href, encoding is not enough: a link to javascript:steal() is perfectly well encoded and still runs when clicked, so the scheme must be checked against an allow list of http and https. Getting all of this right by hand is hard, which is why modern template engines and frameworks encode automatically. Jinja2 with autoescape, Django templates, React and Angular all escape by default. XSS creeps back in through escape hatches with names that warn you, such as the safe filter, mark_safe, or dangerouslySetInnerHTML.

Lesson 3 of 9

Allowing some HTML, and DOM based XSS

Some sites must accept a little HTML, such as bold and italic in comments or formatted text from a rich editor. Encoding everything would break that, so the HTML has to be sanitised. Blocklists, which try to remove dangerous things such as the word script, fail again and again. Removing script once from scr-script-ipt leaves script behind. Payloads need no script tag at all: an image with a broken source and an onerror handler, an SVG with onload, or a link with a javascript URL all run code. Browsers also repair broken HTML in surprising ways, which has defeated many clever filters. The reliable approach is an allow list parser: parse the HTML properly, keep only known safe tags and attributes, encode all text, and drop everything else. Use a maintained library, such as DOMPurify in the browser or nh3 in Python, because the edge cases are endless. DOM based XSS needs its own attention because the server may never see the payload. The page’s own JavaScript reads from a source an attacker controls, such as location.hash, document.referrer or a message from another window, and writes it to a sink that parses HTML or runs code, such as innerHTML, document.write, eval or setTimeout with a string. The safe versions are textContent instead of innerHTML and real functions instead of strings. Browsers based on Chromium also support Trusted Types since 2020, which, when turned on by a CSP directive, makes the dangerous sinks refuse plain strings, so every write must go through a reviewed policy.

Lesson 4 of 9

Content Security Policy and Subresource Integrity

Content Security Policy is a response header that tells the browser which scripts, styles, images and frames a page may load and run. It was proposed at Mozilla in 2009 and first shipped in Firefox 4 in 2011, and CSP Level 3 is the current version. Its main job in security is to be a second line of defence against XSS: even if an attacker manages to inject a script tag, the browser will not run it unless the policy allows it. Early policies listed allowed hosts, but in 2016 a Google team led by Lukas Weichselbaum studied about 26000 real policies and found that almost 95 percent could be bypassed, mostly because they allowed unsafe-inline, which permits every inline script, or listed large hosts such as public CDNs that also serve scripts an attacker can abuse. They recommended strict CSP instead. The server generates a fresh random value, a nonce, for every response, puts it in the header and on each of its own script tags, and the browser runs only scripts with that nonce. The strict-dynamic keyword lets those trusted scripts load others, which keeps real sites working. Policies should be rolled out first with the Report-Only header, which logs violations without blocking. Subresource Integrity handles a different risk: a library loaded from another server being changed, as in the British Airways case. The script tag carries a hash of the expected file, such as integrity="sha384-…", and the browser refuses the file if its hash differs.

Cross site request forgery

Cross site request forgery, CSRF, abuses the fact that a browser attaches a site’s cookies to every request it sends to that site, no matter which page started the request. If you are logged in to your bank and visit an evil page, that page can contain a hidden form that posts a transfer to the bank, submitted automatically by a line of script. Your browser adds your bank cookie, and a bank that checks only the cookie performs the transfer. The attacker never sees your cookie or the bank’s reply, and does not need to, because the damage is the action itself. In 2008 William Zeller and Edward Felten at Princeton showed working CSRF attacks against ING Direct, where they could open accounts and move money, and against YouTube, The New York Times and MetaFilter. The classic defence is a CSRF token: a secret value the server puts in each of its forms and checks on submission. The evil page cannot read the bank’s pages, thanks to the same origin policy, so it cannot know the token. Tokens can be random values stored in the session, or HMAC values computed from the session id with a server key, so nothing extra has to be stored. The modern layer is the SameSite cookie attribute. With Lax, which Chrome made the default in 2020, cookies are not sent on cross site POST requests or background requests, which stops the classic attack. Checking the Origin header on state changing requests is a third, simple layer. All of them assume one rule: requests that change something must never use GET.

Lesson 6 of 9

Clickjacking and framing

Clickjacking was named in 2008 by Robert Hansen and Jeremiah Grossman. The attacker loads the victim site in an invisible frame on top of an innocent looking page, and lines up a button on the real site, such as Delete account or Allow camera, under something the user wants to click, such as Play video. The user thinks they clicked the game, but the click lands on the real site, where they are logged in. Variants have tricked people into liking pages, changing privacy settings and approving payments. The fix is to tell the browser who may frame your pages. The old header X-Frame-Options, with values DENY or SAMEORIGIN, still works in all browsers. The modern way is the CSP directive frame-ancestors, which can list exact allowed parent origins. Sensitive actions should also ask for confirmation, such as typing a password or a code, which a single hidden click cannot provide.

Lesson 7 of 9

XSS and CSRF compared

XSS and CSRF are often confused because both involve another site and a logged in user. The difference is where the attacker’s code runs. In XSS the attacker’s script runs inside the victim site, so it can read and do everything. In CSRF the attacker’s page stays on its own site and can only send blind requests that ride on the victim’s cookies. That is why XSS is more serious, and why an XSS bug defeats CSRF tokens: a script inside the site can simply read the token.

From beginner to expert

A beginner knows not to click strange links while logged in to important sites. A college student can find and fix stored, reflected and DOM XSS in lab code, write a strict CSP and explain CSRF tokens. A professional reviews templates for escape hatches, deploys CSP with reporting, and tests with Burp Suite. Researchers study mutation XSS caused by browser parsing quirks, script gadgets in frameworks that bypass CSP, and new browser defences such as Trusted Types and sanitiser APIs.
One idea, four depths

Be careful with links and pop ups while logged in, keep the browser updated, and log out of banking sites when done.

Three kinds of XSS, context aware encoding, allow list sanitising, DOM sources and sinks, strict CSP with nonces, SRI, CSRF tokens and SameSite, framing headers.

Review code for innerHTML, eval and template escape hatches, roll out CSP with Report-Only, enforce Trusted Types, and test with Burp Suite and DOM Invader.

Mutation XSS from parser differences, script gadgets in JavaScript frameworks, formal models of browser security, the HTML Sanitizer API, and automatic detection of DOM XSS with taint tracking.

Lesson 9 of 9

Chapter summary

  1. XSS: untrusted text read as code in other users’ browsers, with the site’s origin. Stored, reflected, DOM based. Samy worm 2005, British Airways 2018.
  2. Encoding: depends on context. HTML text, attribute (quoted), JavaScript string (json.dumps), URL (scheme allow list). Frameworks escape by default.
  3. Sanitising: allow list parsers such as DOMPurify or nh3, never blocklists. DOM sinks: use textContent, not innerHTML. Trusted Types.
  4. CSP: strict policy with a fresh nonce and strict-dynamic, not unsafe-inline or broad host lists. Report-Only first. SRI hashes for third party files.
  5. CSRF: the browser sends cookies on cross site requests. Defend with tokens (random or HMAC of the session), SameSite=Lax, Origin checks, and no state change on GET.
  6. Clickjacking: hidden frames steal clicks. frame-ancestors or X-Frame-Options.
