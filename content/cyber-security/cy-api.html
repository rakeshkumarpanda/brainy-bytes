Lesson 1 of 10

APIs: the doors behind every app

When you open a shopping app, the screen you see is only the front. Every tap sends a request to an API, an application programming interface, which is a set of web addresses that accept data and send data back, usually as JSON over HTTPS. Phone apps, web pages, smart devices and other companies’ servers all talk to the same APIs. That makes APIs the place where attackers look first. They do not need the app at all. They can send requests straight to the API with a script, change any field, and try any ID. In this chapter you will see the bugs that keep appearing in APIs, from changing one number in a URL to sneaking an extra field into a request, and the simple rules that stop them.
What it is
APIs are web endpoints that programs call to read and change data. Most modern apps are a thin screen on top of them.
Why we need it
Every check that lives only in the app’s screen can be skipped, because attackers talk to the API directly. API flaws have exposed millions of records at Optus, T-Mobile, USPS and Peloton.
How it works
Check who the caller is and what they may touch on every request, accept only the fields you expect, return only the fields they may see, limit how fast and how much they can ask for, and keep a list of every API you run.

Real world scenario: Around you

Open your browser’s developer tools (F12), choose the Network tab, and reload a site you use. Every row marked fetch or XHR is an API call. Click one and look at the Response tab. That raw JSON is exactly what an attacker sees, including any field the page chooses not to show you.

Lesson 2 of 10

Broken object level authorisation: change one number

The most common serious API bug is also the simplest. An API takes an ID in the URL, such as orders slash 1001, checks that the caller is logged in, and returns the order. It never checks whether that order belongs to the caller. So a logged in customer changes 1001 to 1002 and reads a stranger’s order. OWASP calls this broken object level authorisation, BOLA, and older guides call it an insecure direct object reference, IDOR. It is number one on the API list because it is everywhere and needs no skill to exploit. A close cousin is broken function level authorisation, where a normal user calls an admin function, for example by changing GET to DELETE, or by guessing a path like slash admin slash users. Stopping BOLA and BFLA
  1. On every endpoint that takes an ID, load the object, then check that its owner (or the caller’s role) allows this action.
  2. Put the check in one shared place, such as a policy function or middleware, so new endpoints cannot forget it.
  3. Deny by default: admin functions need an explicit role check, not a hidden URL.
  4. Return 404 rather than 403 if you do not want to confirm that an ID exists.
  5. Write tests with two users: user A must never read, change or delete user B’s objects.
Remember
Random IDs (UUIDs) are good practice because they stop counting through records, but they are not access control. IDs leak in shared links, logs, emails and other API responses.
Lesson 3 of 10

Broken authentication: keys, tokens and logins

Before an API can decide what you may do, it has to know who you are. Most APIs use one of three things. An API key is a long secret string that identifies a program, not a person, and it is often leaked by being pasted into a mobile app or pushed to a public code repository. A session cookie works for browsers. A bearer token, often a JSON web token, is sent in the Authorization header and proves who the user is until it expires. The Authentication chapter (Network and Systems 2.1) shows how JWTs are built and the classic mistakes, such as accepting alg none. For APIs the common failures are simpler: endpoints that forget to require a token at all, tokens that never expire, tokens that are not checked for audience, and login or password reset endpoints with no rate limit, which invite password guessing. In 2018 a bug in Facebook’s View As feature let attackers steal access tokens for about 30 million accounts, which shows that a token is as good as a password.

An authentication checklist for an API
  1. Require authentication on every endpoint by default, and mark the few public ones explicitly.
  2. Verify tokens fully: signature, expiry, issuer and audience.
  3. Keep tokens short lived and support revoking them.
  4. Rate limit login, password reset and one time code endpoints per account, not only per IP.
  5. Never put long lived secrets in mobile apps or front end code.
Lesson 4 of 10

Rate limits and resource consumption

An API that answers as fast as anyone can ask will be abused. A bot with a leaked list of passwords can test thousands of logins, a scraper can copy your whole catalogue, and a single huge request can tie up a database. OWASP calls this unrestricted resource consumption. The usual fix is a rate limit, and a common way to build one is a token bucket. Each client has a bucket that holds a few tokens and refills slowly. Each request spends a token, and an empty bucket means the API answers 429 Too Many Requests, often with a Retry-After header. The key question is what you count. In the animation, a bot spreads its guesses over ten IP addresses. A per IP limit gives it ten buckets and it still gets in. A per account limit puts every guess into one small bucket, and the attack crawls. Limits are not only about speed. Cap page sizes, upload sizes and the cost of each query, especially for GraphQL, where one request can ask for deeply nested data or bundle hundreds of login attempts using aliases.

Lesson 5 of 10

Mass assignment and excessive data exposure

Two more bugs come from trusting the shape of the data. The first is mass assignment. Frameworks make it easy to write user dot update with the whole request body, which copies every field the client sends into the database record. If the record has fields like role, is admin or credits, an attacker just adds them to the request. In March 2012 a developer used exactly this bug on GitHub, which is built with Ruby on Rails, to add a key to the Rails project there, to prove the point. The second is excessive data exposure. The API returns the whole database record and leaves it to the app to show only some fields on screen. Anyone who reads the raw response sees everything, such as password hashes, home addresses or internal flags. In 2022 Twitter confirmed that an API bug had let attackers match email addresses and phone numbers to about 5.4 million accounts. OWASP now groups both as broken object property level authorisation. Lesson 6 of 10

Webhooks, SSRF and trusting other APIs

Many APIs also call out to the world. A payment service sends webhooks to a URL the customer types in. A document tool fetches a picture from a link. If the API fetches whatever URL it is given, an attacker can point it at addresses that only the server can reach, such as an admin page on localhost or the cloud metadata service at 169 dot 254 dot 169 dot 254, which hands out temporary cloud keys. This is server side request forgery, SSRF. In 2019 an attacker used SSRF through a misconfigured firewall to take cloud keys from Capital One and copy data on about 106 million people. Application Security 1.2 covers SSRF in depth. The other half of this lesson is the reverse problem: your API consuming someone else’s. Data from a partner API is still untrusted input. Validate it, set timeouts, do not follow redirects blindly, and do not let a partner’s outage or a poisoned response break your own service.
Download this program (.py)Save it, open it in any editor and run it with python3 ssrf_guard.py.
Safe outbound calls
  1. Allow only https and, where possible, a fixed list of destination hosts.
  2. Resolve the host name and check every address it returns against private, loopback and link local ranges.
  3. Connect to the address you checked, so a second DNS answer cannot switch it (DNS rebinding).
  4. Turn off automatic redirects, or check each new location again.
  5. Use IMDSv2 in the cloud, and run the fetcher with no access to internal networks.
  6. Treat partner API responses as untrusted: validate their schema, set timeouts and size limits.
Lesson 7 of 10

Misconfiguration, forgotten APIs and business flows

Some API failures are not bugs in one endpoint but in how the whole set is run. Improper inventory management means nobody has a full list of the APIs in use. Old versions, like v1 left running after v2 launched, keep answering without the newer checks. Teams publish internal or test endpoints that no one documented. These are called zombie and shadow APIs, and attackers find them by guessing paths and reading mobile apps. Security misconfiguration covers things like a CORS policy that lets any website call the API with the user’s cookies, error messages that print stack traces and database names, and debug endpoints left switched on. Finally, unrestricted access to sensitive business flows is when every request is valid on its own but the pattern is harmful, such as bots buying every concert ticket in seconds or creating thousands of fake accounts to claim sign up bonuses. In early 2023 T-Mobile reported that an attacker had pulled data on about 37 million accounts through one API over about six weeks before it was noticed.

Lesson 8 of 10

Building and testing secure APIs

Putting it together, a secure API is designed, not patched. Start with a written contract, usually an OpenAPI file, that lists every endpoint, who may call it, and the exact shape of each request and response. An API gateway in front of the services can then do the common jobs in one place: check tokens, apply rate limits, reject requests that do not match the schema, and log every call. Inside each service, authorisation still has to be checked against the actual object, because only the service knows who owns it. Test with two or more users in your automated tests, so that user A trying to read user B’s data fails every build that breaks it. Run API scanners and fuzzers against a test copy, and watch the production logs for unusual patterns per token. Bug bounty programmes pay outside researchers to find what you missed, and many of the cases in this chapter were reported that way.
A secure API life cycle
  1. Design: write the OpenAPI contract with authentication, roles and schemas for each endpoint.
  2. Build: one shared authorisation layer, allow lists for input, response schemas for output.
  3. Protect: gateway with token checks, rate limits per account and per key, size limits.
  4. Test: two user authorisation tests, schema tests and fuzzing in CI.
  5. Run: inventory from logs, alerts on unusual volume, switch off old versions on schedule.
  6. Learn: bug bounty or disclosure programme, and fix every class of bug, not just the one report.
Practise safely and legally
Only test APIs you own or are explicitly allowed to test, for example through a bug bounty programme’s published scope. Changing IDs to read other people’s data on a live service is unauthorised access even when the API makes it easy. Practise on deliberately vulnerable labs such as OWASP crAPI or OWASP Juice Shop running on your own computer.

From beginner to expert

A beginner understands that every app talks to an API and that the app’s screen is not a security boundary. A student can explain the OWASP API Top 10 and fix BOLA and mass assignment in code. A professional designs gateways, rate limits and authorisation layers and tests them in CI. Experts find new classes of API flaws, build policy engines and run API security for large companies.
One idea, four depths

Apps are screens on top of APIs. Anyone can call an API directly, so the server must check who you are and what you may see on every request.

OWASP API Top 10, BOLA and BFLA with owner checks, token buckets and 429, mass assignment and response schemas, SSRF guards for webhooks, zombie and shadow APIs.

Design OpenAPI contracts with security, run gateways and per account limits, write two user authorisation tests, monitor per token behaviour and run disclosure programmes.

Build policy engines for fine grained authorisation, research GraphQL and gRPC attack classes, detect business flow abuse with behaviour models, and lead API security programmes.
