Memory safety: why C and C++ bugs become exploits

A running program keeps its data in memory. Local variables and the bookkeeping for function calls live on the stack, which grows and shrinks as functions are called and return. Objects that must live longer are allocated on the heap and, in C and C++, freed by hand. These languages give the programmer raw pointers and trust them completely: reading or writing past the end of a buffer, using memory after freeing it, or freeing it twice is not an error the language catches. The behaviour is undefined, and often the program just carries on with corrupted memory. Attackers turn that corruption into control. The Morris worm of 1988 overflowed a buffer in the fingerd service. In 1996 Aleph One’s article Smashing the Stack for Fun and Profit, in Phrack, explained the technique step by step and started decades of exploits. Code Red in 2001, Slammer in 2003, and EternalBlue in 2017 were all memory corruption bugs, as was Heartbleed. In 2019 Matt Miller of Microsoft reported that about 70 percent of the security bugs Microsoft fixed each year were memory safety issues, and the Chromium project reported the same 70 percent in 2020. That number changed the debate. Governments, including the US Cybersecurity and Infrastructure Security Agency, the NSA and the White House Office of the National Cyber Director in 2024, now urge vendors to write new code in memory safe languages such as Rust, Go, Java, C sharp, Swift and Python. This chapter shows the main bug classes, the defences added to operating systems and compilers over 25 years, and why a memory safe language removes whole classes at once.

Source: Aleph One, Smashing the Stack for Fun and Profit, Phrack 49 (1996), Cowan et al., StackGuard: Automatic Adaptive Detection and Prevention of Buffer-Overflow Attacks (USENIX Security 1998), Shacham, Page, Pfaff, Goh, Modadugu and Boneh, On the Effectiveness of Address-Space Randomization (ACM CCS 2004), Shacham, The Geometry of Innocent Flesh on the Bone: Return-into-libc without Function Calls (ACM CCS 2007), Matt Miller, Trends, Challenges and Strategic Shifts in the Software Vulnerability Mitigation Landscape (BlueHat IL 2019), Chromium Project, Memory Safety (2020), Google Security Blog, Eliminating Memory Safety Vulnerabilities at the Source (2024), US ONCD, Back to the Building Blocks (2024), Linux kernel documentation on randomize_va_space and mmap_rnd_bits, The Rust Programming Language book.

Practise safely and legally
Every program here models memory with Python lists and bytearrays, so nothing real is overflowed. To study real exploitation, use deliberately vulnerable binaries in a virtual machine, such as the exercises in pwn.college or picoCTF.
What it is
Memory safety means a program can only access memory it is allowed to: within the bounds of each object, only while the object is alive, and only as the right type.
Why we need it
Most severe vulnerabilities in operating systems, browsers and network services are memory safety bugs, and they often give the attacker full control of the process.
How it works
Avoid the bugs by checking bounds and lifetimes (or by using a language that enforces them), and make the remaining bugs hard to exploit with canaries, non executable memory, ASLR, control flow integrity and hardware tagging.

Stack overflows, canaries, NX and return oriented programming

When a function is called, the CPU pushes the return address, the place to continue when the function ends, onto the stack. The function’s local arrays sit just below it. If the function copies input into a local array with something like strcpy or gets, which never check the size, a long input runs past the end of the array and overwrites the saved return address. When the function returns, the CPU jumps wherever the attacker wrote. In the 1990s attackers put machine code, called shellcode, in the same input and jumped straight to it. Defenders answered in layers. Stack canaries, introduced by StackGuard in 1998 and now turned on by compiler flags such as -fstack-protector, place a random value between the buffers and the return address and check it before returning: an overflow that reaches the return address must destroy the canary first. Non executable memory, the NX bit in AMD processors from 2003 and Data Execution Prevention in Windows XP Service Pack 2 in 2004, marks the stack as data only, so injected shellcode cannot run. Attackers answered with code reuse. Instead of injecting code, they chain together short pieces of the program’s own code that end in a return instruction, called gadgets. Hovav Shacham showed in 2007 that such return oriented programming can compute anything. That is why ASLR, in the next lesson, matters: gadgets are useless if you do not know where they are. Newer processors add shadow stacks, such as Intel CET since 2020, which keep a protected second copy of return addresses and stop the process if the two differ.

ASLR: randomness against exploits

Address space layout randomisation loads the program, its libraries, the stack and the heap at random addresses each time the program starts. An exploit that needs to jump to a gadget, or to the system function in the C library, must first guess where it is, and a wrong guess usually crashes the process. The PaX project introduced ASLR for Linux in 2001, mainline Linux followed in 2005 and Windows Vista in 2007. How much it helps depends on two things. The first is entropy, the number of random bits. On 32 bit Linux the default randomisation of shared libraries is only 8 bits, 256 possibilities, which can be brute forced in seconds. In 2004 Hovav Shacham and colleagues at Stanford showed that even 16 bits on 32 bit systems fell to a brute force attack on a web server in about 216 seconds on average. On 64 bit systems Linux uses 28 bits or more by default, which makes blind guessing hopeless. The second is what happens after a crash. Servers that fork a new child for each connection give every child the same layout, so each wrong guess rules out one possibility and the attacker can simply sweep through them. A process that re-randomises after each crash makes every guess a fresh lottery. The most important caveat is that ASLR is defeated completely by an information leak. If any bug reveals one pointer into a library, the attacker learns the random offset and can compute every other address. Modern exploits therefore usually chain two bugs: one to leak an address, one to take control.

Going deeper: Where the bits go on 64 bit Linux

The kernel setting /proc/sys/kernel/randomize_va_space = 2 turns on full randomisation. The mmap base, where shared libraries go, gets mmap_rnd_bits of randomness, 28 by default on x86-64, and the stack and heap have their own random offsets. A position independent executable (PIE), the default in most distributions since around 2017, lets the main program move too. Kernel ASLR (KASLR) randomises the kernel itself, though side channels such as timing attacks on the CPU’s caches have repeatedly leaked its offset.

Heap bugs: use after free, integer overflow and friends

The heap is where long lived objects go. In C a program calls malloc to get a block and free to give it back, and the allocator keeps lists of free blocks to reuse. Three bug classes dominate here. Use after free happens when code frees an object but some pointer still refers to it. If the attacker can make the program allocate a new object of the same size, often just by sending a message or loading a web page element, the allocator hands out the same block, now filled with attacker data. The old pointer then reads the attacker’s values, which can include fake function pointers that redirect execution. Browsers, with their complex object lifetimes driven by JavaScript, have suffered from this more than any other bug class. A double free gives the same block back twice and corrupts the allocator’s own lists. Integer overflow causes heap overflows indirectly. In C a 32 bit unsigned multiplication such as count times 4 silently wraps around, so a huge count can produce a tiny allocation, and the loop that fills it then writes far past the end. In 2015 Joshua Drake showed a set of such bugs in Android’s Stagefright media library that could be triggered by a single multimedia message, affecting around 950 million devices. Signed and unsigned mix ups are similar: a length of minus 16 passes a check for being too large and then becomes four billion when passed to memcpy. The defences are checks before arithmetic, using size types correctly, allocators that delay reuse and add checks, and memory tagging in hardware such as Arm MTE, which gives each allocation a small tag that pointers must match.

Lesson 5 of 8

Finding and stopping memory bugs

Defence against memory bugs works on three fronts. The first is finding bugs before attackers do. Sanitisers are compiler options that add checks to a test build: AddressSanitizer, from Google in 2011, puts poisoned zones around every allocation and stops at the first out of bounds or use after free access, at about twice the normal running cost. Fuzzers such as AFL, released by Michal Zalewski in 2013, and libFuzzer feed millions of mutated inputs to a program while watching which code paths each one reaches, and keep the inputs that find new paths. Google’s OSS-Fuzz project has used this to find tens of thousands of bugs in open source software. The second front is making bugs hard to exploit, the layers of canaries, NX, ASLR and control flow integrity covered earlier, plus hardware features such as memory tagging and pointer authentication on Arm. CHERI, a research architecture from the University of Cambridge and SRI International, goes further by replacing plain pointers with capabilities that carry their own bounds and permissions, and Arm built a prototype chip called Morello in 2022. The third front, and the only one that removes the bug classes, is memory safe languages. Rust, first stable in 2015, enforces bounds checks and tracks who owns each value and how long each reference lives, at compile time, so use after free and data races simply do not compile, while still giving C like speed without a garbage collector. Rust is now accepted in the Linux kernel and used in Android, Windows and Chromium.

A modern plan for an old C or C++ code base
  1. Turn on every compiler hardening flag: -fstack-protector-strong, -D_FORTIFY_SOURCE=3, PIE, RELRO, CET where available.
  2. Run tests and fuzzers under AddressSanitizer and UndefinedBehaviorSanitizer in continuous integration.
  3. Replace unsafe functions (gets, strcpy, sprintf) and raw arrays with bounded alternatives.
  4. Write new components in a memory safe language and connect them through narrow interfaces.
  5. Rewrite the riskiest parts first: parsers of untrusted input such as image, font and network code.

Languages and memory safety compared

People sometimes say that safe languages are slow or that careful C programmers do not make these mistakes. Decades of data from Microsoft, Google and Apple say otherwise: even the best teams ship memory bugs in large C and C++ code bases. Lesson 7 of 8

From beginner to expert

A beginner knows that updates often fix memory bugs and installs them. A college student can explain stack frames, overflows, canaries, NX and ASLR, and compute brute force odds. A professional hardens builds, runs sanitisers and fuzzers, and reviews C code for risky patterns. Experts write exploits in capture the flag contests and research new mitigations and the formal semantics of safe languages.
One idea, four depths

Install updates promptly, because many of them fix memory bugs that could let a web page or file take over your device.

Stack and heap layout, buffer overflows, canaries, NX, ASLR maths, use after free, integer overflow, and why Rust removes these classes.

Compiler hardening flags, ASan and UBSan in CI, coverage guided fuzzing with AFL++ or libFuzzer, binary analysis with Ghidra, and migration plans to memory safe languages.

Exploit development against modern mitigations in CTFs, heap exploitation techniques, control flow integrity design, CHERI and MTE, and formal proofs of safety such as RustBelt.

Chapter summary

  1. Why: C and C++ trust pointers, so bounds and lifetime mistakes become exploits. About 70% of serious bugs at Microsoft and in Chromium are memory safety bugs.
  2. Stack overflow: a long copy overwrites the return address. Canaries (1998), NX (2003 to 2004), then ROP (2007), then shadow stacks (2020).
  3. ASLR: random addresses. Same layout: (2n + 1)/2 guesses, fresh layout: 2n. 8 bits is weak, 28 bits strong. One pointer leak defeats it.
  4. Heap bugs: use after free, double free, integer overflow (mod 232 wrap), signedness. Check before arithmetic. MTE, hardened allocators.
  5. Finding bugs: AddressSanitizer, fuzzers such as AFL and OSS-Fuzz. Hardening flags. CHERI and Morello.
  6. Safe languages: Rust, Go, Java, Swift, Python remove the classes. Android memory bugs fell from 76% (2019) to 24% (2024).
