Lesson 1 of 10

Ethereum: a world computer whose programs hold money

Bitcoin made a shared notebook for payments. In 2013 a nineteen year old programmer, Vitalik Buterin, asked a bigger question: what if the notebook could also store small programs that anyone can call, and that move money by themselves according to their code? He described it in the Ethereum white paper, and the network went live on 30 July 2015. Those programs are called smart contracts. Think of a vending machine. You put in a coin, press a button, and the machine gives you a drink without a shopkeeper. A smart contract is a vending machine for money and digital things: a loan, an exchange, a game, a vote. Every node runs the same code on a virtual machine, the EVM, and gets the same result. Ethereum has two kinds of accounts. Externally owned accounts belong to people and are controlled by a private key. Contract accounts hold code and their own balance. Every step of a program costs gas, paid in ether, which stops endless loops and pays the validators. Two properties make contracts very different from normal software. First, the code is public, so attackers can study it for weeks. Second, once deployed it usually cannot be changed, and any money it loses is gone, because there is no bank to reverse a payment. People said code is law, but history shows that code is also bugs, and a bug in a contract holding hundreds of millions is an open safe on a busy street. This chapter walks through the main kinds of bugs, each with a real incident.

Source: Buterin (2013), Wood (yellow paper), EIP-1559, Solidity documentation, SWC registry, OWASP Smart Contract Top 10, Daian et al. (2020), public post mortems of The DAO, Parity, BeautyChain, bZx, Harvest, Poly Network, Wormhole, Ronin, Nomad, Mango Markets and Euler.

What it is
A smart contract is a program stored on a blockchain such as Ethereum. Anyone can call it, every node runs it the same way, and it can hold and move cryptocurrency by itself.
Why we need it
It replaces a trusted middleman (a bank, an exchange, an escrow agent) with public code. That removes one kind of trust but adds a new risk: a bug cannot be patched quietly, and stolen money cannot be recalled.
How it works
Write small, well tested contracts in Solidity or Vyper, follow known safe patterns, use audited libraries, test with fuzzers and formal tools, get independent audits, and keep emergency controls such as a pause switch behind a time delay.

A metro token gate is a simple smart machine: insert a valid token and the gate opens, with nobody checking. If its software had a bug that opened the gate for a bent coin, everyone would soon know. A smart contract is like that gate, except it guards money and the whole world can study its wiring.

Lesson 2 of 10

Reentrancy: The DAO and calling back in

The most famous smart contract bug has a strange name: reentrancy. When a contract sends ether to another contract, the receiving contract’s code runs straight away, in the middle of the sender’s function. If the sender has not yet updated its own records, the receiver can call back in and ask again, and again, before the first call finishes. In the animation the buggy bank sends one ether and only then sets the attacker’s balance to zero, so the attacker re enters ten times and drains the bank. This is not a made up example. The DAO was a giant investment fund run by a smart contract, which raised about 150 million dollars in ether in 2016. On 17 June 2016 an attacker used exactly this pattern to move about 3.6 million ether, more than a quarter of its funds, into a child contract. The Ethereum community argued for weeks, and on 20 July 2016 most of it adopted a hard fork that moved the funds back. A minority refused, saying the chain must never be rewritten, and kept the original chain, which still runs today as Ethereum Classic. The fixes are simple once known. Follow the checks, effects, interactions order: check the conditions, update your own state, and only then call outside. Add a reentrancy lock, such as OpenZeppelin’s nonReentrant modifier, so a function cannot be entered while it is already running. Reentrancy still causes losses today in more subtle forms, such as reentering a different function that reads the half updated state, called cross function or read only reentrancy.
The bug in Soliditysolidity
1// Vulnerable: sends ether before updating the ledger2function withdraw() external {3    uint amount = balances[msg.sender];4    require(amount > 0, "nothing to withdraw");5    (bool ok, ) = msg.sender.call{value: amount}("");6    require(ok, "send failed");7    balances[msg.sender] = 0;8}
  1. Line 5 Sending ether hands control to the receiver, whose code can call withdraw again.
  2. Line 7 The balance is cleared only after the send, too late.
The fixsolidity
1// Fixed: checks, then effects, then interactions, plus a lock2function withdraw() external nonReentrant {3    uint amount = balances[msg.sender];          // check4    require(amount > 0, "nothing to withdraw");5    balances[msg.sender] = 0;                    // effect6    (bool ok, ) = msg.sender.call{value: amount}("");   // interaction7    require(ok, "send failed");8}
  1. Line 2 nonReentrant sets a lock for the whole call.
  2. Line 5 The ledger is cleared before any outside call.

Integer overflow and the danger of silent maths

Computers store numbers in a fixed number of bits. A uint8 can hold 0 to 255, and the usual Ethereum number, uint256, holds 0 to about 1.16 times 10 to the 77. Before Solidity version 0.8, going past the top silently wrapped around to zero, and going below zero wrapped to the top, just like an old car odometer rolling from 99999 back to 00000. The animation shows a dial of all 256 values. Wrap arounds turned into real thefts. In April 2018 the BeautyChain token had a function called batchTransfer that multiplied the number of receivers by the amount each should get, then checked the sender had that total. The attacker chose an amount of 2 to the 255 and two receivers. The product 2 to the 256 wrapped to exactly zero, the balance check passed, and each receiver was credited 2 to the 255 tokens, an unimaginably large number. Exchanges froze the token within hours. The fix came in December 2020, when Solidity 0.8 made every addition, subtraction and multiplication checked by default, so an overflow now cancels the transaction with an error called Panic 0x11. Before that, careful teams used the SafeMath library. Overflow bugs are not finished, though. Code inside an unchecked block, older contracts still holding money, and type conversions such as squeezing a uint256 into a uint8 can all still wrap.

Lesson 4 of 10

Access control: who is allowed to call this function

Many of the most expensive contract bugs are the simplest: a function that should be locked was left open. In July 2017 the Parity multisig wallet, a popular wallet that needed several owners to approve a payment, had a function called initWallet that set the owners. It was meant to run once, at creation, but anyone could call it again later. On 19 July an attacker called it on three wallets, made themselves the only owner, and took about 153,000 ether, around 30 million dollars at the time. Parity fixed it with a new shared library contract. Then on 6 November 2017 a user who called themselves devops199 found that the new library itself had never been initialised. They called its init function, became its owner, and then, they said by accident, called its kill function. The library deleted itself, and every wallet that depended on it was frozen forever with about 513,774 ether inside, worth over 150 million dollars then. Nobody stole it, and nobody can ever spend it. Other access mistakes include checking tx dot origin instead of msg dot sender. tx dot origin is the person who started the whole transaction, so if an owner is tricked into calling a malicious contract, that contract can call the wallet and pass a tx dot origin check. Use msg dot sender, the direct caller, and use tested role libraries such as OpenZeppelin’s Ownable and AccessControl.

Lesson 5 of 10

Oracles and flash loans: bending prices for one transaction

A smart contract cannot look at the outside world. If a lending app needs the price of ether, it must ask an oracle, some source that reports a price on chain. Many early apps simply asked a trading pool on chain, because it was easy. A common kind of pool, an automated market maker, holds two tokens and keeps their product constant, x times y equals k. Its price is just the ratio of the two piles, so a big enough trade moves it a lot. Now add flash loans. A flash loan lends any amount, millions of dollars, with no deposit at all, on one condition: it must be repaid before the same transaction ends, or the whole transaction is undone as if it never happened. So an attacker can borrow a fortune, buy heavily from a pool to push its price up, use that inflated price to borrow far more than their deposit is worth from a lending app, sell back, repay the flash loan, and keep the difference, all within one block of about twelve seconds. The animation does exactly this with made up numbers. The bZx attacks of February 2020 were the first famous examples. Harvest Finance lost about 34 million dollars in October 2020, and Mango Markets lost about 110 million in October 2022 when a trader pumped the price of its own token. The defences are better oracles. Use a time weighted average price over many blocks, so a one block pump barely moves it, use several independent price feeds such as Chainlink, set limits on how fast a price may change, and do not treat a thin, easily moved market as the truth.

Lesson 6 of 10

Front running, sandwiches and MEV: the public waiting room

Before a transaction goes into a block it sits in a public waiting room called the mempool, where anyone can read it. Block builders choose the order of transactions, usually putting the highest tips first. That opens a door that does not exist in a normal stock market, where front running a customer is a crime. A bot can see your trade before it happens and act first. The classic case is the sandwich attack in the animation. Priya wants to buy ether with 20,000 USDC. A bot sees her trade, buys just before her with a higher tip, which pushes the price up, lets her buy at the worse price, then sells straight after her at the price she pushed up. The bot’s profit comes out of Priya’s pocket. Her protection is the slippage limit she set, the least she is willing to accept. A tight limit leaves the bot almost no room. In 2020 Philip Daian and colleagues named this whole world MEV, now called maximal extractable value, in a paper titled Flash Boys 2.0, after a book about high speed trading. Since then MEV bots have taken hundreds of millions of dollars. Users can protect themselves with tight slippage limits, by sending trades through private routes that skip the public mempool, and by using apps that batch trades or use commit and reveal schemes, where you first publish a sealed hash of your choice and reveal it later, so nobody can copy it in time.

Lesson 7 of 10

Bridges, signatures and approvals: the biggest thefts

The largest thefts in this field did not come from clever maths inside one contract. They came from the systems that join chains together and from the permissions users hand out. A bridge moves tokens between blockchains. You lock coins in a contract on one chain, and a group of validators confirms it so that matching tokens are created on the other chain. Whoever controls those validators controls everything locked in the bridge. In March 2022 the Ronin bridge, used by the game Axie Infinity, needed five of nine validator signatures. Attackers obtained five keys, partly through a fake job offer sent to an engineer, and took about 625 million dollars. The FBI attributed it to North Korea’s Lazarus Group. In February 2022 the Wormhole bridge lost about 326 million dollars because a signature checking function could be fooled into accepting fake approvals. In August 2022 an upgrade to the Nomad bridge accidentally marked an empty message as valid, so anyone could copy the first attacker’s transaction and change the address to their own, and hundreds of people did, taking about 190 million dollars. Ordinary users face a smaller version of the same problem through token approvals. When you use a trading app it asks permission to spend your tokens, often an unlimited amount. If that app is later hacked, or you sign an approval on a look alike phishing site, the attacker can take everything you hold of that token. Approve only what you need and review old approvals with a revoke tool.

Building contracts safely: patterns, tools and audits

Because a deployed contract is public and hard to change, smart contract teams test far more heavily than most software teams. A good process looks like this. Keep contracts small and reuse audited building blocks such as the OpenZeppelin library instead of writing your own token or access control. Write unit tests for every function and every failure. Run a static analyser such as Slither, which knows hundreds of bug patterns. Run property based fuzzers such as Echidna or Foundry, which hammer the contract with random calls while checking rules that must always hold, called invariants, for example that the sum of all balances equals the total supply. For valuable contracts, use formal verification, which proves mathematically that certain rules always hold. Then hire independent auditors, and after launch run a bug bounty, where ethical hackers are paid to report bugs privately. Platforms for this have paid single rewards of millions of dollars. Plan for failure too: a pause switch, limits on how much can leave per hour, and upgrades that wait behind a timelock so users can see changes coming. The SWC registry and the OWASP Smart Contract Top 10 list the known weaknesses, and they are a good checklist for any review.
A secure release process for a smart contract
  1. Write a short specification and the invariants that must always hold.
  2. Build on audited libraries and the checks effects interactions pattern.
  3. Unit test every function, including every way it should fail.
  4. Run a static analyser (Slither) and a fuzzer with invariants (Echidna or Foundry).
  5. Formally verify the most valuable rules.
  6. Get at least one independent audit and fix every finding.
  7. Launch with deposit caps, a pause switch, a timelock on upgrades and a bug bounty.
  8. Monitor transactions live and keep an incident plan ready.

Practise safely and legally
Practise on deliberately vulnerable training games such as Ethernaut or Damn Vulnerable DeFi, on a local test chain or a public test network with free test ether. Never test an attack on a contract that holds real people’s money. Report real bugs through the project’s bug bounty.

From beginner to expert

A beginner knows that smart contracts are public programs that hold money and cannot easily be fixed. A student can spot reentrancy, overflow, missing access checks and price oracle problems in small examples. A professional writes, tests and audits contracts with standard tools. Experts research new attack classes, formal methods and MEV.
One idea, four depths

A smart contract is a vending machine for money that lives on the blockchain. Everyone can read its code, and if it has a bug, the money can be taken and nobody can give it back.

Gas and EIP-1559 fees, checks effects interactions, uint wrap (a op b) mod 2n, x y = k pools and TWAP, slippage limits and sandwiches, the main incidents.

Write Solidity with OpenZeppelin, test with Foundry, fuzz invariants, run Slither, review against the SWC registry, design oracles, timelocks and pause switches, respond to live incidents.

Research formal verification of DeFi protocols, MEV and fair ordering, cross chain bridge security, and new compiler and EVM level bugs.
