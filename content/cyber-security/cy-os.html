Lesson 1 of 9

What an operating system does for security

An operating system is the big program that runs all the other programs, like Windows, macOS, Linux, Android or iOS. In the early 1960s, computers ran one job at a time, and security barely existed. Then time sharing arrived: many people used one expensive computer at the same time. Suddenly one user’s program could read another user’s files or crash the whole machine. The Multics project in the late 1960s, built by MIT, Bell Labs and General Electric, introduced many ideas we still use, such as protection rings and access control lists. Its younger cousin, Unix, gave us users, groups and the read, write, execute permissions you will learn today. Linux and macOS come straight from that Unix family. The key idea is simple: programs are not trusted to police themselves. A small, trusted core called the kernel checks every request.

Source: Linux man pages chmod(1), umask(2), open(2), passwd(5) and shadow(5), Microsoft Learn on SIDs, ACLs, UAC and audit events, and Silberschatz, Operating System Concepts.

What it is
An operating system (OS) shares the computer’s CPU, memory, disk and network between many programs and users. Its trusted core, the kernel, enforces who may do what.
Why we need it
Without the OS, any program could read any file, watch any keystroke and crash the machine. The OS keeps users apart, keeps programs apart, and keeps them away from the hardware.
How it works
The CPU has at least two modes. Normal programs run in user mode and must ask the kernel, through a system call, to open files, use the network or start programs. The kernel, in kernel mode, checks the request against the user’s identity and the object’s permissions, then does the work or refuses.

Lesson 2 of 9

Users, groups and the all powerful administrator

Every action on a computer happens on behalf of some user. When you log in, the operating system gives your session an identity, and every program you start carries it. On Linux, that identity is a number called the user ID. The user with ID zero, named root, can do almost anything: read every file, kill any program, change any setting. Windows has a similar idea with the Administrator account and security identifiers. Because root is so powerful, attackers always try to become root, and good administrators avoid logging in as root at all. Instead, they use a normal account and borrow root power for one command at a time with sudo on Linux or the User Account Control prompt on Windows. In this lesson we look at where accounts live and how to spot a dangerous one.

Real world scenario: the second root account

During an audit, a security analyst runs a simple check for accounts with UID 0 and finds two: root and a forgotten account named backup. Someone had copied the root line years ago to make a quick backup job. Anyone who guessed its weak password would have full control of the server without ever touching the root password. Checking for UID 0 accounts is one of the first steps after a suspected break in, because attackers like to hide a second root account.

Common mistake
Being in the docker group on Linux is close to being root, because a user who can start containers can mount the whole disk into one. Treat such groups like admin rights.

Linux permissions and the octal maths of chmod

Unix gave every file three kinds of permission, read, write and execute, for three kinds of people: the file’s owner, the members of the file’s group, and everyone else. That is nine switches in total, and Ken Thompson and Dennis Ritchie at Bell Labs found a clever way to write them as just three digits. Each digit is a small sum: read is worth four, write two and execute one. So seven means all three, five means read and execute, and zero means nothing. This is called octal, base eight, because one digit goes from zero to seven. When a security person sees mode 777 on a file, they wince, because it means anyone on the machine can change it. When they see 600 on a private key, they relax. Let us learn to read these numbers at a glance, and learn one surprising rule the kernel follows.
What it is
A Linux mode has three octal digits for the owner, the group and others. Each digit adds read (4), write (2) and execute (1). An optional fourth digit in front holds setuid (4), setgid (2) and sticky (1).
Why we need it
Permissions are the main way a multi user system keeps people out of each other’s files. Wrong permissions, such as a world writable script run by root, are a classic way attackers gain more power.
How it works
On every open the kernel finds the first class that matches you (owner, else group, else other) and uses only that digit. Then it checks the bit you asked for.

Lesson 4 of 9

Windows access control lists

Windows took a different path from Unix. Instead of nine fixed switches, every file, folder, registry key and service in Windows can carry a full list of rules, called an access control list. Each rule, called an access control entry, says that a particular user or group is allowed or denied some right, such as read or modify. This design came from the VMS operating system, because the lead designer of Windows NT, Dave Cutler, had built VMS before joining Microsoft in 1988. Lists are far more flexible than nine bits, but flexibility has a cost: long lists, inherited rules from parent folders, and deny rules can make it hard to see who really has access. Attackers love that confusion. In this lesson you will learn the order in which Windows reads the rules, which decides the answer.
What it is
An access control list (DACL) on a Windows object is an ordered list of access control entries (ACEs). Each ACE allows or denies specific rights to one SID (a user or a group).
Why we need it
Real organisations need fine grained rules: the finance group may edit, auditors may read, contractors may not even list the folder. Nine Unix bits cannot say all that.
How it works
Windows walks the ACEs in order until every requested right is granted or one is denied. In the normal (canonical) order, explicit deny comes first, then explicit allow, then inherited deny, then inherited allow. If no ACE grants a right, it is denied.
icacls output for a folder (Windows)text
1C:\Finance BUILTIN\Administrators:(OI)(CI)(F)2          CORP\Finance:(OI)(CI)(M)3          CORP\Auditors:(OI)(CI)(RX)4          CORP\Contractors:(OI)(CI)(DENY)(RX)
  1. Line 1 Administrators have Full control (F). (OI)(CI) means the rule is inherited by files (object inherit) and subfolders (container inherit).
  2. Line 2 The Finance group may Modify (M): read, write, delete.
  3. Line 3 Auditors may Read and eXecute (RX) only.
  4. Line 4 Contractors are explicitly denied. Explicit deny is checked before any allow, so a contractor who is also in Finance is still blocked.

Remember
Leave the built in Administrator and SYSTEM accounts out of daily work. Use a normal account and let UAC ask for admin rights only when needed, so malware you open by mistake does not start with full power.
Lesson 5 of 9

Processes and privilege escalation

A process is a program that is running. When you open a browser, the operating system creates a process, gives it memory and an identity, and lets it run. Attackers who break into a machine usually land as a weak user, perhaps the web server account. Their next goal is privilege escalation: turning that weak foothold into root or SYSTEM. They look for mistakes. A setuid program that anyone can edit. A service that runs as SYSTEM but reads its settings from a folder normal users can write to. A scheduled task running an old script. A kernel that has not been patched. Penetration testers check exactly these things, and defenders remove them. In this lesson you will audit a list of files for one of the most famous mistakes, the dangerous setuid file.
What it is
Privilege escalation is gaining more rights than you were given. Vertical: a normal user becomes admin. Horizontal: one user reaches another user’s data at the same level.
Why we need it
Most attacks start with low rights (a phished user, a web app account). Escalation turns a small breach into full control, so stopping it limits the damage.
How it works
Attackers look for misconfigured permissions, setuid files, services and scheduled tasks that run as admin but can be changed by users, stored passwords, and unpatched kernel bugs. Defenders follow least privilege, patch quickly and audit these places.

Lesson 6 of 9

Where the OS records security events

When something goes wrong on a computer, the first question an investigator asks is: what do the logs say? Operating systems keep diaries of important events: who logged in, who failed to log in, which programs started, who changed a permission. On Linux, these go to files in the var log folder or to the systemd journal. On Windows, they go to the Event Log, and each kind of event has a number. You will meet event 4624, a successful logon, and 4625, a failed logon, again and again in security work. A long run of 4625 events followed by a 4624 is the classic picture of a password guessing attack that finally worked. Logs are only useful if they are switched on, kept long enough, and protected, because a clever attacker’s first job is to delete them.

Lesson 7 of 9

Security models compared

Not every operating system protects things the same way. The Unix model that Linux and macOS use is called discretionary access control: the owner of a file decides who may use it. That is simple, but it means a careless owner, or malware running as that owner, can give everything away. Military systems in the 1970s and 1980s wanted something stricter, called mandatory access control, where a central policy decides and even the owner cannot override it. Linux later gained mandatory controls too, with SELinux, first released by the American National Security Agency in 2000, and AppArmor. Phones went further still: Android and iOS put each app in its own sandbox and ask you before an app may use the camera or your contacts. Let us compare these models.

Bottom line: Discretionary control trusts owners, mandatory control trusts a central policy. Modern systems layer both: Unix bits or ACLs for daily sharing, and SELinux, AppArmor or app sandboxes to contain programs that get taken over.

Lesson 8 of 9

From beginner to expert

Operating system security goes very deep. A beginner learns that accounts and permissions keep people apart. A college student reads modes like 754, writes umasks and knows the Windows event IDs. A masters student studies how the kernel enforces isolation with virtual memory, page tables and system call filtering, and how containers and virtual machines differ in what they really separate. Researchers formally prove kernels correct, like the seL4 microkernel, whose functional correctness was proved by machine in 2009, or attack the hardware below the kernel, as the Spectre and Meltdown research did in 2018 by showing that the CPU itself can leak memory across the boundaries the OS believes are solid.
One idea, four depths

Each person has their own account. Files have rules about who may read or change them. The administrator can do everything, so we use that account only when we must.

Read and set modes in octal, use umask, know that the first matching class decides, audit UID 0 accounts and setuid files, read Windows ACLs in canonical order, and watch events 4624, 4625 and 1102.

The kernel enforces isolation with virtual memory (each process has its own page tables), privilege rings and system call checks. Containers share one kernel and are separated by namespaces, cgroups, capabilities and seccomp filters, so a kernel bug can break out. Virtual machines are separated by a hypervisor and are stronger. Mandatory access control (SELinux type enforcement) limits even root processes.

The seL4 microkernel has a machine checked proof (Klein et al., 2009) that its C code matches its specification, and later proofs of integrity and confidentiality. Spectre and Meltdown (2018) showed that speculative execution in CPUs leaks data across process and kernel boundaries through cache timing, breaking assumptions of the OS model and leading to fixes such as kernel page table isolation.

Beginner
Explain users, the administrator and why we avoid using it daily.
Intermediate
Decode chmod modes, apply umask, audit accounts and setuid files, and read Windows ACLs and logon events.
Expert
Explain containers versus virtual machines, seccomp and SELinux, formally verified kernels and CPU side channels.

Chapter summary

  1. The kernel runs in kernel mode (ring 0). Programs run in user mode (ring 3) and must use system calls, so the kernel checks every request.
  2. Linux identities are UIDs. UID 0 (root) can do almost anything. Windows uses SIDs, Administrator and SYSTEM. Use sudo or UAC instead of logging in as admin.
  3. /etc/passwd lists accounts, /etc/shadow holds the hashes and is readable only by root (and group shadow on Ubuntu).
  4. Mode digits add r = 4, w = 2, x = 1 for owner, group and other. 600 private, 644 public read, 755 programs, 777 a mistake.
  5. The kernel uses only the first matching class (owner, else group, else other). Root skips read and write checks.
  6. umask removes bits: new mode = default AND NOT umask. umask 022 gives 644 files and 755 folders. setuid 4000, setgid 2000, sticky 1000.
  7. Windows ACL order: explicit deny, explicit allow, inherited deny, inherited allow, then implicit deny.
  8. Watch 4624 (logon), 4625 (failed logon), 4672, 4688, 4720, 4740 and 1102 (log cleared). Privilege escalation hunts writable root scripts, setuid files, weak services and old kernels.
