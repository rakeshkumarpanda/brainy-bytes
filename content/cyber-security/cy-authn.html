Lesson 1 of 9

Identification, authentication and authorisation

Every login answers three questions in order. Identification is the claim: I am asha. Authentication is the proof: here is something only asha should have. Authorisation, covered in the next chapter, decides what asha may then do. Proofs come in three kinds, called factors: something you know, such as a password or PIN, something you have, such as a phone or security key, and something you are, such as a fingerprint or face. Using two different kinds is multi factor authentication. Passwords are the oldest method in computing. MIT’s Compatible Time Sharing System used them in 1961, and in 1962 a researcher printed the system’s whole password file to get more computer time, perhaps the first password breach. Stolen and reused passwords remain one of the most common ways attackers get in, because people reuse them across sites and fall for phishing pages. This chapter follows the path from passwords to one time codes, to passkeys that cannot be phished, and then to the systems that let one login reach many services: Kerberos inside companies, and OAuth, OpenID Connect and SAML on the web.

Source: NIST SP 800-63B-4, Digital Identity Guidelines: Authentication (2025), RFC 4226 (HOTP, 2005), RFC 6238 (TOTP, 2011), W3C Web Authentication Level 2 (2021), FIDO Alliance CTAP 2.1, RFC 4120 (Kerberos V5), RFC 6749 (OAuth 2.0), RFC 7636 (PKCE), OpenID Connect Core 1.0 (2014), OASIS SAML 2.0 (2005), RFC 7519 (JWT), RFC 8725 (JWT best current practices).

What it is
Authentication verifies a claimed identity using one or more factors: knowledge, possession or inherence. It is different from identification (the claim) and authorisation (the permissions).
Why we need it
Every other control assumes the system knows who is asking. Weak authentication lets an attacker become a real user, and most monitoring then sees normal activity.
How it works
Check a secret against a stored verifier (a slow salted hash), a code from a shared key (TOTP), a signature from a private key (passkeys), or a trusted third party’s statement (Kerberos tickets, OpenID Connect tokens, SAML assertions).

Lesson 2 of 9

Passwords done right

Password advice changed a lot in the last decade, mostly because of evidence about how people behave. Old rules forced a capital letter, a digit and a symbol, and a change every 90 days. People responded with predictable patterns such as Summer2024 followed by an exclamation mark, then Autumn2024. NIST’s guidance, SP 800-63B, now says the opposite: favour length over complexity, allow all characters including spaces, do not force periodic changes unless there is a sign of compromise, and check new passwords against lists of breached and common passwords. The 2025 revision asks for at least 15 characters when a password is the only factor, and at least 8 when it is part of multi factor login. A clever way to check breach lists without revealing the password is k anonymity: the Have I Been Pwned service receives only the first five hex characters of the password’s SHA-1 hash and returns every breached hash with that prefix, and the check finishes on the user’s own device. On the server, passwords must be stored with a slow salted hash such as Argon2id, scrypt or bcrypt, covered in the hashing chapter, and login attempts must be rate limited. Rate limits matter enormously: a six digit PIN with ten tries is nearly impossible to guess online. Password managers make long unique passwords practical, and credential stuffing, where attackers try passwords leaked from one site on many others, only works when passwords are reused.

What it is
Password policy: rules for choosing, checking, storing and limiting attempts on passwords.
Why we need it
Passwords remain the most common first factor, and reuse plus phishing make them the most common way in.
How it works
Require length (15 or more alone, 8 or more with MFA), block breached and common passwords, never force pointless changes, hash with Argon2id or bcrypt, rate limit and lock out gradually, and encourage password managers.

One time codes and multi factor authentication

Multi factor authentication asks for a second proof of a different kind, so a stolen password alone is not enough. The most common second factor is a one time code. HOTP, defined in RFC 4226 in 2005, computes an HMAC of a shared secret key and a counter, then cuts it down to six digits by a step called dynamic truncation. TOTP, RFC 6238 from 2011, uses the number of 30 second slots since 1970 as the counter, so the code changes every half minute. Authenticator apps and servers share the secret once, usually through a QR code, and then compute the same codes independently. SMS codes are weaker: attackers can take over a phone number by convincing a mobile carrier to move it to their SIM card, a SIM swap, which hijacked Twitter’s chief executive’s own account in 2019, and NIST classes SMS as a restricted authenticator. Push notifications that ask “Is this you?” are convenient but suffer from fatigue attacks, where attackers send prompts until a tired user approves, as happened at Uber in 2022. Number matching helps. But all of these share one weakness: a phishing page can ask the user for the code and relay it to the real site within seconds. Only phishing resistant methods, covered next, stop that.

What it is
TOTP: code = Truncate(HMAC(K, floor(t / 30))) mod 10digits. HOTP uses a counter instead of time.
Why we need it
It blocks attacks that use only a stolen or guessed password, works offline on the phone, and needs no extra hardware.
How it works
HMAC the 8 byte counter, take offset = last byte & 0x0F, read 4 bytes there, clear the top bit, take the remainder mod 106. Servers accept one slot either side for clock drift and block reuse of a code.
HOTPExam favourite
HOTP(K, C) = (DT(HMAC-SHA-1(K, C)) & 0x7FFFFFFF) mod 10d
RFC 4226 key "12345678901234567890": C = 0 gives 755224, C = 1 gives 287082.
TOTPExam favourite
T = floor((t − T0) / X), X = 30 s, then HOTP(K, T)
RFC 6238 SHA-256 at t = 59: T = 1, code 46119246 (8 digits).
Guessing a code
P = window slots × tries / 10d
3 slots, 1 try, 6 digits: 3 in a million. With 5 tries before lockout: 15 in a million.

Passkeys: phishing resistant login

Passkeys replace a shared secret with a key pair. When you register with a site, your device creates a new private key that never leaves it, usually protected by a secure chip, and sends the site only the public key. To log in, the site sends a random challenge, and your device signs it after you unlock it with a fingerprint, face or PIN. The site checks the signature with the stored public key. A breach of the site leaks only public keys, which are useless to attackers. The key to phishing resistance is that the browser includes the origin it is really talking to, such as https colon slash slash bank.example, in the data that is signed, and the private key is tied to the site it was created for. A look alike phishing domain cannot get a valid signature for the real bank, however convincing the page looks, and the user cannot be tricked into making one. The standards are FIDO2 from the FIDO Alliance, founded in 2013, and the W3C’s Web Authentication API, a Recommendation since 2019. In 2022 Apple, Google and Microsoft announced passkeys that sync across a user’s devices. Google reported in 2018 that after moving its employees to security keys, none of its more than 85000 staff had their work accounts phished.
Download this program (.py)Save it, open it in any editor and run it with python3 passkey.py.
What it is
A passkey is a FIDO2 / WebAuthn credential: a per site key pair, with the private key held by the user’s device and the public key stored by the site.
Why we need it
It removes shared secrets from servers, stops credential stuffing, and is phishing resistant because signatures are bound to the real origin.
How it works
Registration: the authenticator makes (sk, pk) for this relying party and returns pk. Login: the site sends a challenge, the browser builds client data with the challenge and origin, and the authenticator signs it after user verification.
A WebAuthn login
  1. The site sends a fresh random challenge and its relying party ID (bank.example).
  2. The browser checks the page’s real origin matches that ID and builds client data: challenge, origin, type.
  3. The authenticator asks for a fingerprint, face or PIN, then signs the authenticator data and a hash of the client data.
  4. The site checks the signature with the stored public key, the challenge, the origin and a counter or flags.
  5. A phishing domain fails at step 2 or the site rejects the origin at step 4.
Common mistake
Passkeys move the weak point to account recovery. If a lost passkey can be reset by email or SMS alone, attackers will target that path. Offer several passkeys or a recovery key, and protect recovery as strongly as login.

Single sign on: Kerberos, SAML, OAuth and OpenID Connect

Single sign on lets a user log in once and use many services. Inside companies the classic system is Kerberos, designed at MIT for Project Athena in the 1980s and the basis of Microsoft Active Directory since Windows 2000. A trusted Key Distribution Centre shares a key with every user and service. After one login the user holds a ticket granting ticket and exchanges it for tickets to individual services, so passwords never cross the network. Two famous attacks show its limits: Kerberoasting, described by Tim Medin in 2014, requests service tickets that are encrypted with service account passwords and guesses them offline, and a stolen krbtgt key lets attackers forge golden tickets. On the web, SAML 2.0, from 2005, sends signed XML assertions from an identity provider to business applications. OAuth 2.0, RFC 6749 from 2012, is about authorisation: it lets an app act for a user on an API with an access token, without ever seeing the password. Because OAuth on its own does not say who the user is, OpenID Connect, finished in 2014, adds an ID token, usually a signed JSON Web Token, for login. Public clients such as phone apps must use PKCE so a stolen authorisation code is useless. Many breaches come from small verification mistakes, such as accepting a token signed with the “none” algorithm, so libraries must pin the expected algorithm and check every claim.

Biometrics and their error rates

Biometric systems measure a body feature, compare it with a stored template, and accept if the match score passes a threshold. No match is perfect, so there are always two kinds of error. A false accept lets the wrong person in, and its rate is the FAR. A false reject turns away the right person, the FRR. Moving the threshold trades one for the other, and the point where they are equal is the equal error rate, a common single number for comparing systems. Apple, for example, states about a 1 in 50000 chance that a random person could unlock a phone with Touch ID and about 1 in 1000000 for Face ID. Biometrics have special risks. You cannot change your fingerprint if a template leaks, so templates should stay on the device in a secure chip, as phones do. Sensors can be fooled by fakes, so liveness detection matters. And laws such as India’s Digital Personal Data Protection Act 2023, Europe’s GDPR and Illinois’ BIPA treat biometric data as especially sensitive. On phones, biometrics usually unlock a local key, such as a passkey, rather than being sent to a server.
False accept rateExam favourite
FAR = impostor attempts accepted / impostor attempts
3 accepts in 10000 impostor tries: FAR = 0.03%.
False reject rateExam favourite
FRR = genuine attempts rejected / genuine attempts
50 rejects in 2000 genuine tries: FRR = 2.5%.
Equal error rate
EER = the rate at the threshold where FAR = FRR
Lower is better. Raising the threshold lowers FAR and raises FRR.
Expected false accepts
E = attempts × FAR
A thief trying 5 random fingers against FAR 1/50000: 5/50000 = 0.01%.
Remember
A biometric is an identifier, not a secret: your face is in photos and your fingerprints are on every glass. Treat it as a convenient way to unlock a key held on the device, combined with a PIN fallback and attempt limits.
Lesson 7 of 9

Authentication methods compared

When comparing methods, ask three questions: can it be guessed, can it be stolen in a breach, and can it be phished. Passwords fail all three unless managed well. One time codes stop guessing and breach reuse but can be phished. Passkeys and security keys resist all three, which is why governments and large companies now ask for phishing resistant MFA. Kerberos, SAML and OpenID Connect are not factors themselves but ways to carry the result of one strong login to many services.

Lesson 8 of 9

From beginner to expert

A beginner uses a password manager, turns on two step login and prefers passkeys. A college student can implement TOTP from the RFC, explain why SMS and push can be phished, set password policy by NIST, and describe Kerberos, OAuth and OpenID Connect flows. A masters student studies protocol details and attacks: OAuth redirect and mix up attacks, SAML signature wrapping, Kerberos delegation abuse, JWT key confusion, WebAuthn attestation and the security of account recovery. Researchers work on formal verification of authentication protocols, usable security studies of how people actually log in, password hardening services that resist offline cracking, and post quantum signatures for passkeys.
One idea, four depths

Use long unique passwords in a manager, turn on MFA, prefer passkeys, and never type a code into a page you reached from an email link.

NIST password rules and k anonymity checks, HOTP and TOTP maths, why codes can be relayed, WebAuthn origin binding, Kerberos tickets, OAuth versus OpenID Connect, JWT checks, FAR and FRR.

OAuth mix up and redirect attacks, PKCE, SAML wrapping, Kerberos delegation and golden tickets, JWT key confusion, attestation, risk based authentication and recovery design.

Formal proofs of OAuth and FIDO2, usable security research, password hardening (PHE), threshold and post quantum authenticators, and continuous behavioural authentication.

Chapter summary

  1. Three steps: identify, authenticate, authorise. Factors: know, have, are. MFA uses two kinds.
  2. Passwords: length over complexity (15 or more alone), block breached ones (k anonymity), no forced changes, Argon2id or bcrypt, rate limits.
  3. TOTP: HMAC(K, floor(t/30)), dynamic truncation, mod 106. RFC vectors 755224 and 46119246. SMS, codes and push can be relayed.
  4. Passkeys: per site key pairs, challenge signed with the origin. Phishing resistant, breaches leak only public keys. Protect recovery.
  5. Kerberos: KDC, TGT, service tickets, no password on the wire. Kerberoasting and golden tickets.
  6. Web SSO: SAML assertions, OAuth for API access, OpenID Connect ID tokens for login, PKCE for apps. Pin JWT algorithms, check every claim.
  7. Biometrics: FAR, FRR, EER trade off by threshold. Keep templates on the device, use them to unlock a key.
