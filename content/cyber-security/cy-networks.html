How computers talk: packets and layers

In the 1960s the US Department of Defense funded a network called ARPANET. Its designers had a bold idea called packet switching. Instead of holding a phone line open for a whole call, a message is chopped into small pieces called packets, each with an address, and every piece finds its own way through the network. If one path breaks, packets take another. In 1974 Vint Cerf and Bob Kahn described TCP and IP, and on the first of January 1983 ARPANET switched over to them. That day is often called the birthday of the internet. The protocols were designed for a small group of trusted researchers, so they had almost no security built in. Addresses could be faked, and anyone on the path could read the traffic. Almost every network attack you will study comes from that early trust, and almost every network defence was added later on top.

Source: RFC 791, RFC 9293, RFC 1918, RFC 4632, RFC 1034 and 1035, RFC 9110, the IANA port registry and Kurose and Ross, Computer Networking.

What it is
A network lets computers send data to each other in small pieces called packets. The work is split into layers: each layer does one job and uses the layer below it.
Why we need it
An attacker who understands the layers knows where to listen, fake or flood. A defender who understands them knows where to filter, encrypt and watch. Every firewall rule and every packet capture is written in the language of layers.
How it works
Going down the layers, each one wraps the data in its own header (encapsulation): the application data, then a TCP or UDP header with ports, then an IP header with addresses, then an Ethernet or Wi-Fi header for one link. The receiver removes them in reverse.

Lesson 2 of 10

Addresses: MAC, IPv4, IPv6, private ranges and NAT

Every device on a network needs an address, just like every house needs one for the post. Networks actually use two kinds. The MAC address is burned into the network card by the maker. It is like a person’s name, and it is only used on the local network. The IP address is like a postal address: it tells routers across the whole internet where to deliver. The first internet addresses, IPv4, have 32 bits, which allows about 4.3 billion addresses. That sounded like plenty in 1981 but ran out as phones and laptops spread. Two fixes followed. One was private addresses with NAT, which lets a whole home share one public address. The other was IPv6, with 128 bits, enough to give every grain of sand on Earth many addresses. Security people must know these ranges by heart, because firewall rules and logs are full of them.

Real world scenario: your home router and NAT

Your phone, laptop and TV all have private addresses like 192.168.1.x. Your router has one public address from your internet provider. When your laptop opens a website, the router swaps the private address for its public one and remembers the swap in a table, so the reply finds its way back. This is network address translation (NAT). As a side effect, a computer on the internet cannot start a connection to your laptop, because the router has no table entry for it. NAT is not a firewall, but it blocks a lot of unwanted traffic by accident.

In the exam
172.32.0.1 is public, not private. The private block is 172.16.0.0/12, which ends at 172.31.255.255. This is a favourite trick question.
Lesson 3 of 10

Subnet maths with CIDR

Big networks are cut into smaller pieces called subnets, the same way a city is cut into neighbourhoods. Subnets keep traffic local, make addresses easier to manage, and, most importantly for security, let us put walls between parts of a company: the guest Wi-Fi in one subnet, the servers in another, the payment machines in a third. Since 1993, networks have been written with CIDR notation, a slash and a number, like slash twenty four. The number tells how many of the 32 address bits are the network part. Everything else is a little binary maths with AND and OR, exactly the bit operations from the maths chapter. Network engineers and penetration testers do this maths in their heads, and it is asked in every networking and security exam.
What it is
CIDR notation a.b.c.d/n says the first n bits of the address are the network part and the remaining 32 − n bits are the host part. The subnet mask is n ones followed by zeros.
Why we need it
Firewall rules, routing tables, cloud security groups and access lists are all written as networks like 10.0.0.0/16. To read or write them, you must know which addresses a prefix covers.
How it works
Network address = address AND mask (host bits set to 0). Broadcast = network with all host bits set to 1. Usable hosts = 232 − n − 2.

Bit operations on the 32 bit numbers.
Mask from prefix
mask = 232 − 232 − n
/24 = 255.255.255.0, /26 = 255.255.255.192, /16 = 255.255.0.0.
Block size
block = 232 − n = 256 − (last non 255 mask byte)
/26: 256 − 192 = 64, so networks start at .0, .64, .128, .192.
Worked example: which network is 10.1.5.200/22 in?
  1. /22 leaves 10 host bits. The third byte has 6 network bits and 2 host bits, so the block size there is 22 = 4.
  2. Third byte 5 lies in the block 4 to 7 (multiples of 4: 0, 4, 8, ...).
  3. network = 10.1.4.0/22
  4. Broadcast: the last address of the block, 10.1.7.255.
  5. hosts = 210 − 2 = 1,022
  6. So a firewall rule for 10.1.4.0/22 covers 10.1.4.0 to 10.1.7.255.
Lesson 4 of 10

Ports, TCP and UDP

An IP address gets a packet to the right computer, but a computer runs many programs at once: a browser, a mail app, a game. Ports tell the computer which program the packet is for. Think of an apartment building: the IP address is the building, and the port is the flat number. Servers listen on well known ports, so the web is on port 443, secure shell on 22, and so on. Attackers scan ports to see which doors are open, because each open port is a program that could have a bug. There are two main transport protocols. TCP is like a phone call: it sets up a connection, numbers every byte and resends anything lost. UDP is like dropping postcards in a box: fast and simple, but with no promise that they arrive. Both have their place, and both have their own attacks.

The TCP handshake and reading a packet

TCP has to solve a hard problem: deliver every byte in order across a network that loses, delays and repeats packets. Its answer is to number every byte. At the start, each side picks a starting number and tells the other in a short three step greeting, called the three way handshake: SYN, SYN ACK, ACK. After that, each side acknowledges the next byte it expects. If an acknowledgement does not come back, the sender resends. This handshake matters for security in two ways. First, a SYN flood sends thousands of first steps and never finishes them, filling the server’s memory. Second, in the 1980s many systems picked predictable starting numbers, and in 1994 Kevin Mitnick famously used guessed sequence numbers to inject fake packets into a trusted connection. Today starting numbers are random. Let us watch the numbers move.

  1. Line 1 Flags [S] is a SYN from the client’s port 51514 to the server’s port 443.
  2. Line 2 Flags [S.] is SYN plus ACK (the dot means ACK). ack 1001 = 1000 + 1.
  3. Line 3 Flags [.] is the final ACK. The connection is established.
Common mistake
A checksum is not security. It detects random damage, but an attacker who changes a packet simply recomputes it. Protection against tampering needs a keyed MAC or a signature, which the Cryptography section teaches.
Lesson 6 of 10

DNS, ARP and DHCP: the helpers that trust too much

Three small helper protocols make networks easy to use, and all three were designed to trust whoever answers first. DNS turns names like example dot com into IP addresses, so you never have to remember numbers. It was designed by Paul Mockapetris in 1983. ARP, from 1982, lets a computer on a local network find the MAC address that owns an IP address by simply shouting a question and believing the reply. DHCP, from 1993, hands a new device its IP address, its router and its DNS server automatically. Because none of them checks who is answering, an attacker on the same network can lie. A fake ARP reply puts the attacker in the middle of your traffic. A fake DNS answer sends you to a copy of your bank. A fake DHCP server can make every device use the attacker’s DNS. Knowing how they work tells you exactly what the attacker fakes.

DHCP in four messages (DORA)
  1. Discover: a new laptop broadcasts "is there a DHCP server?"
  2. Offer: the server offers an address, say 192.168.1.20, with the router and DNS server.
  3. Request: the laptop asks to take that offer.
  4. Acknowledge: the server confirms. The laptop now uses those settings, which is why a fake server that answers first can control them.

HTTP and HTTPS in one page

The web runs on HTTP, the HyperText Transfer Protocol, which Tim Berners Lee created at CERN between 1989 and 1991. HTTP is a simple conversation: your browser sends a request, such as get this page, and the server sends a response with a status code and the content. Plain HTTP travels as readable text, so anyone on the path, such as the owner of a cafe Wi-Fi, can read your passwords and change the pages. HTTPS is the same HTTP conversation wrapped inside TLS encryption, which keeps it secret and proves you are talking to the real site. Today almost all web traffic is HTTPS. The Application Security section goes deep into web attacks. Here you only need to read a request and a response.

Lesson 8 of 10

Comparing the models and protocols

Two models describe networks. The OSI model, published by the International Organization for Standardization in 1984, has seven neat layers and is used to teach and to talk about where a problem sits. The TCP IP model has four layers and describes what the internet actually runs. Security people use both: you will hear that a web application firewall works at layer seven, while a simple packet filter works at layers three and four. Next to these models, we compare IPv4 with IPv6. IPv6 is not just bigger. It removed broadcasts, made a neighbour discovery protocol that replaces ARP, and is often switched on by default even when nobody manages it, which can open a door that the IPv4 firewall does not cover.

Lesson 9 of 10

From beginner to expert

Networking for security goes from simple to very deep. A beginner knows that data travels in packets with addresses. A college student reads headers, calculates subnets and knows the common ports and their risks. A masters student studies routing protocols such as BGP, the system that ties the internet’s networks together, and how a single false route announcement can pull a country’s traffic into the wrong place. Researchers measure the whole internet, build programmable networks and design protocols with formal proofs. In 2008, for example, the security researcher Dan Kaminsky found a way to poison DNS caches at scale, and the whole industry patched DNS servers together in secret before announcing it. Pick your level and keep climbing.
One idea, four depths

Computers send data in small packets. Each packet has an address so it reaches the right computer, and a port so it reaches the right app. Some traffic is locked (HTTPS) and some is not (HTTP).

Use the four TCP/IP layers, compute subnets with CIDR, read IP and TCP headers, know the handshake and the common ports, and explain ARP, DNS and DHCP spoofing.

The internet is a network of autonomous systems that exchange routes with BGP, which by default trusts announcements. Prefix hijacks (for example the 2008 Pakistan Telecom YouTube incident) send traffic the wrong way. RPKI signs which network may announce which prefix. TCP congestion control, QUIC (HTTP/3 over UDP with built in TLS 1.3) and DNS over HTTPS change what defenders can see.

Research measures attacks across the whole internet (network telescopes that watch unused address space see scans and backscatter from spoofed floods), builds verified protocol implementations, and studies traffic analysis: even encrypted packets leak which site you visit through sizes and timing, which motivates padding and anonymity networks such as Tor.

Beginner
Explain packets, addresses and ports, and why HTTPS is safer than HTTP.
Intermediate
Calculate subnets, read packet headers, trace a TCP handshake and explain ARP, DNS and DHCP attacks.
Expert
Explain BGP hijacks and RPKI, QUIC and encrypted DNS, and traffic analysis on encrypted traffic.

Chapter summary

  1. Data travels in packets. Each layer adds a header (encapsulation): application data, TCP or UDP (ports), IP (addresses), Ethernet or Wi-Fi (MAC addresses).
  2. TCP/IP has 4 layers, OSI has 7. Memory aid: Please Do Not Throw Sausage Pizza Away.
  3. MAC 48 bits, IPv4 32 bits, IPv6 128 bits, port 16 bits. Private ranges: 10/8, 172.16/12, 192.168/16. Loopback 127/8.
  4. CIDR /n: network = IP AND mask, broadcast = all host bits 1, hosts = 232−n − 2.
  5. TCP is reliable with a SYN, SYN-ACK, ACK handshake and numbered bytes. ack = next expected byte. UDP is fast with no handshake, easy to spoof.
  6. Know the ports: 22 SSH, 23 Telnet, 25 SMTP, 53 DNS, 80 HTTP, 443 HTTPS, 445 SMB, 3389 RDP.
  7. ARP, DNS and DHCP trust the first answer, so attackers spoof them. Defences: dynamic ARP inspection, DNSSEC, DHCP snooping and TLS everywhere.
  8. HTTP status classes 1xx to 5xx. 401 means log in, 403 means not allowed. Secure, HttpOnly and SameSite protect cookies.
