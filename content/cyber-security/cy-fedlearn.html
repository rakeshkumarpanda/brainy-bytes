Lesson 1 of 10

Federated learning: bring the model to the data

Machine learning usually starts by collecting everyone’s data on one server. For phones, hospitals and banks that is often a bad idea or simply not allowed. Typing history, medical scans and financial records are sensitive, laws such as GDPR and India’s DPDP Act limit moving them, and one central pile of data is a tempting target for attackers. In 2016 Brendan McMahan and colleagues at Google proposed a different approach and named it federated learning. Instead of sending the data to the model, send the model to the data. A server holds a shared model. In each round it picks some devices, sends them the current model, each device trains on its own data for a few steps, and only the updated model weights come back. The server averages them into a better shared model, and the raw data never leaves the device. Google used it in 2017 to improve next word suggestions in the Gboard keyboard on Android phones. Apple has described using it with differential privacy for features such as Siri. In medicine, the FeTS study published in 2022 trained a brain tumour boundary model across 71 hospitals on six continents without moving patient scans. In 2021 Peter Kairouz and more than fifty co authors summarised the field and its open problems. This chapter covers the full picture: the FedAvg algorithm and its maths, why communication drives the design, what happens when clients have very different data, the different ways data can be split, secure aggregation so the server sees only the sum, and how real systems are built. The next chapter covers attacks on federated learning and the defences.

What it is
Federated learning (FL) trains one shared model across many devices or organisations that keep their data where it is, sending only model updates to a coordinating server.
Why we need it
Data may be private, regulated or too big to move, and a central copy is a single target for breaches. FL lets many parties benefit from each other’s data without pooling it.
How it works
Repeat rounds: the server sends the global model to selected clients, each trains locally for E steps, sends back its new weights, and the server takes a weighted average. Add secure aggregation and differential privacy for stronger protection.

Lesson 2 of 10

The FedAvg algorithm and its maths

Federated averaging, or FedAvg, is the algorithm from the 2017 paper and still the baseline every new method is compared with. The goal is the same as ordinary training: find weights that minimise the average loss over all the data. The trick is to write that global loss as a weighted sum of each client’s own loss, weighted by how much data each client has. Then each client can work on its own part. In every round the server picks a fraction C of the clients, sends them the current weights, and each runs E passes over its data in mini batches of size B with learning rate eta. The server then averages the returned weights, weighting client k by nk over n, its share of the data. If every client takes exactly one full batch gradient step, this is called FedSGD, and it is exactly ordinary gradient descent on the pooled data, because a weighted average of the clients’ gradients is the gradient of the global loss. FedAvg simply lets clients take more local steps before averaging, which saves rounds. In our program three hospitals with patients of different ages learn the line y = 2x + 1. No hospital alone sees the whole age range, yet after enough rounds the federated model reaches almost the same answer as a model trained on pooled data.

FedAvg, one step at a time
  1. Server starts with weights w0.
  2. Each round t: pick a set St of m = max(C · K, 1) clients out of K.
  3. Send wt to every client in St.
  4. Each client k sets w ← wt and, for E epochs over its nk examples in batches of B, does w ← w − η ∇ℓ(w, batch).
  5. Each client sends back its final wt+1k.
  6. Server sets wt+1 = Σk in St (nk / nS) wt+1k, where nS is the data held by the chosen clients.

Going deeper: Why weight by data size

The pooled loss is an average over all n examples. Grouping the examples by client gives F = Σ (nk/n) Fk. A plain unweighted average of client models would give a phone with 10 examples as much say as one with 10000 and would optimise a different objective. Some systems cap the weight per client on purpose, to limit the influence of any one client, which also helps against poisoning and is needed for user level differential privacy.

Lesson 3 of 10

Communication is the bottleneck

In a data centre, sending numbers between machines is fast. In federated learning, clients are phones on mobile networks or hospitals behind slow links, and uploads are much slower than downloads. A modern model has millions or billions of numbers, and every round sends the model down and the update back up. So the number of rounds, and the size of each message, decide the cost. FedAvg cuts rounds by doing more work locally. McMahan and colleagues reported 10 to 100 times fewer rounds than FedSGD on their tasks. Our program shows the same effect: 42 rounds with one local step, 9 rounds with twenty. The second lever is to shrink each update. Top k sparsification sends only the largest values with their positions. Quantisation rounds each value to a few bits, for example 8 bits instead of 32. Error feedback keeps what was not sent and adds it to the next update, so the errors do not pile up. Real deployments also choose clients carefully. Google’s 2019 system design paper describes phones joining only when they are idle, charging and on an unmetered Wi-Fi network, so users do not notice, and the server over selects clients because some always drop out.

Lesson 4 of 10

Non IID data, client drift and fixes

In ordinary training we assume the examples are independent and identically distributed, IID for short: every batch looks like a small copy of the whole dataset. Federated data almost never looks like that. One phone types mostly in Hindi, another in English. One hospital sees mostly children, another mostly older patients. One bank serves farmers, another city workers. This is called non IID data, and it comes in several kinds: different label mixes, different feature distributions, and very different amounts of data. With non IID data, many local steps cause client drift: each client’s model runs towards the best model for its own data, and the average of those models is not the best model for everyone. Our program uses two clients whose losses are simple parabolas with different centres and steepness. The best global point is 8. With one local step per round, FedAvg finds 8. With 50 steps, each client nearly reaches its own optimum, at 0 and 10, and the average sits near 5. Two well known fixes follow. FedProx, by Tian Li and colleagues in 2020, adds a penalty that keeps each local model close to the global one. SCAFFOLD, by Sai Praneeth Karimireddy and colleagues in 2020, keeps a correction term per client that estimates how its gradient differs from the global one, and removes the drift entirely in our example. A third answer is personalisation: accept that clients differ, and fine tune the shared model locally for each one.

Lesson 5 of 10

Cross device, cross silo, horizontal and vertical

Federated learning comes in two sizes. Cross device FL involves millions of phones or sensors, each with a little data, unreliable connections and no ability to keep state between rounds. Only a small fraction take part in each round. Cross silo FL involves a handful to a few hundred organisations, such as hospitals or banks, each with a lot of data, reliable servers and legal agreements between them. Every silo usually joins every round. Qiang Yang and colleagues in 2019 also named FL by how the data table is split. In horizontal FL the parties have the same columns for different people, as with hospitals recording the same tests. In vertical FL they have different columns for the same people, as with a bank and an online shop that share customers. Vertical FL needs two extra steps. First the parties find their shared customers with a private set intersection protocol, so neither learns the other’s non shared customers. Then they train a model split across them: each computes a partial score on its own columns, and the party with the labels sends back the errors, which real systems protect with homomorphic encryption such as Paillier, covered in the cryptography section. WeBank’s open source FATE platform was built for this in Chinese banking. Federated transfer learning covers the hard case where both people and columns barely overlap.

Common mistake
A salted hash, as in the program, is only a sketch of matching customers. Customer IDs and phone numbers are easy to guess, so an attacker can hash every possible value. Real systems use a private set intersection protocol built on Diffie-Hellman style cryptography or oblivious transfer.
Lesson 6 of 10

Secure aggregation: the server sees only the sum

Federated learning keeps raw data on the device, but the updates themselves can leak a lot. In 2019 Ligeng Zhu, Zhijian Liu and Song Han showed that training images and text can sometimes be rebuilt almost exactly from a single client’s gradients, an attack the next chapter studies. So a careful system makes sure the server never sees any single update, only the sum over many clients. Secure aggregation, published by Keith Bonawitz and colleagues at Google in 2017, does this with pairwise masks. Every pair of clients agrees a shared random mask using a Diffie-Hellman key exchange. The lower numbered client of each pair adds the mask to its update and the higher numbered one subtracts it. Each masked update looks like random noise, but when the server adds them all up, every mask appears once with a plus and once with a minus, so they cancel and only the true sum remains. The hard part is drop outs: phones vanish mid round, and then their masks no longer cancel. The protocol handles this by having each client split its secret keys into Shamir secret shares and give one share to every other client in advance. If a client drops out, enough survivors send their shares so the server can rebuild that client’s pairwise masks and remove them, while masks between survivors stay secret. A second layer of self masks stops the server from cheating by claiming a client dropped out when it did not. The cost grows with the number of pairs, so large systems group clients into smaller sets.

Common mistake
Secure aggregation hides individual updates from the server, but the sum itself can still leak information when few clients take part, and it cannot spot a poisoned update it cannot see. That is why it is combined with a minimum number of clients per round, differential privacy, and careful defences against poisoning, as the next chapters show.
Lesson 7 of 10

Real systems, privacy layers and tools

A production federated system has more parts than the averaging step. On the client side there is an eligibility check, so training runs only when the phone is idle, charging and on Wi-Fi, a local training runtime, and safeguards on how much data and battery are used. On the server side there are client selection, round timeouts and over selection to handle drop outs, secure aggregation, versioned models, and evaluation on held out clients before a new model is shipped. Privacy comes in layers. Keeping data local is only the first. Secure aggregation hides individual updates. Differential privacy, added to federated averaging by Brendan McMahan and colleagues in 2018 as DP-FedAvg, clips each client’s update to a maximum size and adds calibrated noise to the sum, so the final model provably reveals little about any one user. Trusted execution environments can protect the aggregation code itself. On the threat side, the usual starting assumption is an honest but curious server, one that follows the protocol but would like to learn about users, plus some clients that may be malicious and try to poison the model. Several open source frameworks make this practical: TensorFlow Federated from Google, Flower from the University of Cambridge and Adap, NVIDIA FLARE for hospitals, PySyft from OpenMined, and FATE from WeBank for vertical FL. The next two chapters go deeper on attacks against FL and on differential privacy.

From beginner to expert

A beginner knows that phones can help train a shared model without sending their data. A student can write FedAvg, compute weighted averages and communication costs, explain client drift and run secure aggregation by hand. A professional builds cross silo and cross device systems with secure aggregation and differential privacy. Experts research convergence on non IID data, personalisation, and attacks and defences.

Chapter summary

  2. FedAvg: F = Σ (nk/n) Fk, wt+1 = Σ (nk/n) wk, uk = E nk / B. FedSGD (one full step) equals gradient descent.

  5. Types: cross device and cross silo. Horizontal (same columns), vertical (same people, PSI then split model with encrypted errors), transfer.
  6. Secure aggregation: yi = xi + Σ mij − Σ mji, masks cancel, Shamir shares for drop outs, n(n − 1)/2 pairs. Plus DP-FedAvg and robust aggregation.
