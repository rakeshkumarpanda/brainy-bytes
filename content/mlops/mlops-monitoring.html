Lesson 1 of 7

What to watch once a model is live

Source: Google, Site Reliability Engineering (2016), chapters on service level objectives, and Huyen, Designing Machine Learning Systems (2022) chapter 8.

What it is
Monitoring means measuring a live model all the time on four layers: the service (latency, errors, traffic), the data (missing values, schema, drift), the model (prediction distribution, accuracy once labels arrive) and the business (the metric the model exists to move).
Why we need it
A model can fail silently. The API keeps answering 200 while the data underneath has changed and the predictions have become useless. Normal software monitoring sees nothing wrong, so ML needs extra checks.
How it works
Set a target for each layer, such as 99 percent of requests under 200 ms (a service level objective, SLO). Collect the numbers from every request, look at percentiles rather than averages, and alert only on sustained problems that need a person.
LayerExamplesNeeds true labels?
Servicep50, p95, p99 latency, error rate, requests per secondNo
Datamissing share, unseen categories, out of range values, PSI per featureNo
Modelprediction mean and spread, PSI of the scores, accuracy, calibrationAccuracy needs labels
Businessfraud losses, click through rate, churnUsually, and with delay

Common mistake
The average latency is 24.5 ms, which sounds fine, but the 99th percentile is 292 ms, so 1 request in 100 is ten times slower than typical. Only 98.27 percent of requests met the 200 ms target, below the 99 percent SLO, while errors used 65 percent of the day’s budget.
PercentileExam favourite
p99 = the value that 99 percent of requests stay below
Tail latency is what users notice.
Error budgetExam favourite
allowed failures = (1 − SLO) × requests
99.9 percent of 100,000 leaves a budget of 100 errors.
Burn rate
actual error rate / allowed error rate
A burn rate of 5 uses a 30 day budget in 6 days.
Lesson 2 of 7

Drift: when live data stops looking like training data

Source: Rabanser, Guennemann and Lipton, Failing loudly (2019), Siddiqi, Credit risk scorecards (2006), and SciPy, scipy.stats.ks_2samp.

What it is
Data drift (covariate shift) means the inputs change, for example younger customers after a marketing campaign. Label shift means the share of each class changes. Concept drift means the link between inputs and label changes, for example fraudsters change tactics. Drift tests compare a live window with the training data.
Why we need it
A model only knows the world it was trained on. Drift is the early warning that its answers may be getting worse, often weeks before enough true labels arrive to measure accuracy.
How it works
For each numeric feature compute the PSI (size of the change, thresholds 0.1 and 0.25) and the KS test (is there any change at all). For categories use a chi square test and watch for unseen values. Track the model’s own score distribution too.
Download this program (.py)Save it, open it in any editor and run it with python3 drift_tests.py.
In the exam
A shift of 8 in the mean gives PSI 0.610, clear drift. A wider spread gives 0.246 with no change in the mean, which a check on averages would miss. With 200,000 rows a harmless shift of 0.3 already has a KS p value of 1.3e−12, while PSI is 0.001. Use the size of the change to decide, and the p value only as a hint.
Population stability indexExam favourite
PSI = Σbins (qi − pi) ln(qi / pi)
p training shares, q live shares. Below 0.1 stable, 0.1 to 0.25 watch, above 0.25 drift.
Kolmogorov Smirnov statisticExam favourite
D = maxx |Ftrain(x) − Flive(x)|
Largest gap between the two cumulative curves.
PSI and KL divergence
PSI = KL(q || p) + KL(p || q)
For two normals with the same spread: (Δμ / σ)².
Lesson 3 of 7

Concept drift, label delay and retraining

Source: Gama and colleagues, A survey on concept drift adaptation (2014).

What it is
Input checks cannot see concept drift, because the inputs look the same. It only shows in the model’s accuracy, which needs true labels, and labels often arrive late: a loan default shows up months later, a churn label after the customer leaves.
Why we need it
Teams that only watch input drift miss the most damaging failure, and teams that retrain on every drift alarm waste effort on changes that did no harm.
How it works
Collect labels wherever you can (user feedback, manual review of a sample, later outcomes). Watch proxies while waiting, such as the score distribution. Retrain on a schedule, or when performance drops past a threshold, always through the tested pipeline and the registry gate of MLOps 3.1.
Download this program (.py)Save it, open it in any editor and run it with python3 decay_sim.py.
In the exam
Under concept drift accuracy fell from 0.95 to 0.57 in a year while the PSI of the input stayed at 0.01. Retraining every 3 months kept it between 0.86 and 0.94. Under data drift the PSI reached 6.20 but accuracy stayed at 0.94 to 0.95, because the model’s rule still held.
Retraining strategyWhen it fitsCost
On a schedule (weekly, monthly)Steady, slow drift and labels arrive regularlySimple, may retrain without need
On a trigger (accuracy or drift past a threshold)Irregular changesNeeds reliable monitoring
Online or continual learningFast changing data such as ads or newsComplex, risk of learning from bad data

Run a drift check every day on your computer

Source: crontab(5), Apple launchd documentation, Microsoft schtasks documentation, and GitHub Actions, Events that trigger workflows (schedule).

What it is
A scheduled job runs the drift check by itself every day, writes a report, and exits with an error code when something drifted, so the scheduler or CI can alert you.
Why we need it
A check that you must remember to run is a check that stops running. A schedule makes monitoring automatic.
How it works
Download the job, run it once by hand, then register it with the scheduler of your system below, or with a GitHub Actions schedule that works the same for everyone.
Run this one on your own computer. It is meant to be started every day by your computer’s scheduler, which a browser page cannot do. The output above comes from a real run with CPython when this page was built.
Download this program (.py)Run it with python3 daily_drift_job.py.
Remember
On the demo data the income column moved (PSI 0.472) and 6 percent of ages went missing, above the 5 percent limit, so both are flagged. The score column needs watching (0.155). With --strict the job exits with code 1, which schedulers and CI treat as a failure.
Schedule the job every morning at 06:00
macOS

macOS has two schedulers. cron is simple and the same as on Linux. launchd is Apple’s own, and unlike cron it runs a job that was missed while the Mac was asleep once it wakes up.

  1. Run the job once by hand and check that drift_report.json appears.
  2. Open your crontab and add the line below (use your own folder). The five fields are minute, hour, day of month, month and day of week.
  3. If the project lives in Documents, Desktop or Downloads, macOS privacy protection blocks cron. Give /usr/sbin/cron Full Disk Access in System Settings, Privacy and Security, or keep the project in another folder such as ~/ml-project.
Terminal (macOS)shell
cd ~/ml-project && .venv/bin/python daily_drift_job.py
crontab -e
# add this line, save and close:
0 6 * * * ~/ml-project/.venv/bin/python ~/ml-project/daily_drift_job.py --strict >> ~/ml-project/drift.log 2>&1
crontab -l                      # check it is there
Windows 10 and 11

Windows uses Task Scheduler. The schtasks command creates a task without clicking through the Task Scheduler window. The job changes to its own folder first, so the task can start anywhere.

PowerShell (Windows)shell
cd $HOME\ml-project
.venv\Scripts\python.exe daily_drift_job.py      # once by hand

schtasks /Create /SC DAILY /ST 06:00 /TN "DriftCheck" /TR "$HOME\ml-project\.venv\Scripts\python.exe $HOME\ml-project\daily_drift_job.py --strict"
schtasks /Run /TN "DriftCheck"        # run it now to test
schtasks /Query /TN "DriftCheck" /V /FO LIST   # Last Result 0 means no drift, 1 means drift

The task only runs while you are signed in, unless you open it in Task Scheduler and choose Run whether user is logged on or not. A laptop that is off at 06:00 skips the run unless you also tick Run task as soon as possible after a scheduled start is missed.

Linux (Ubuntu, Debian, Fedora)

Use cron, or a systemd timer on servers. With Persistent=true a timer also catches up on runs missed while the machine was off.

Terminal (Linux)shell
cd ~/ml-project && .venv/bin/python daily_drift_job.py
crontab -e
0 6 * * * ~/ml-project/.venv/bin/python ~/ml-project/daily_drift_job.py --strict >> ~/ml-project/drift.log 2>&1
grep CRON /var/log/syslog | tail      # Ubuntu and Debian: did it run
journalctl -u cron --since today      # or ask systemd (the service is crond on Fedora)
ChromeOS (Chromebook)

The Linux environment on a Chromebook only runs while it is open, so a cron job there misses runs while the Chromebook sleeps. Use it to test the job, and run the real schedule in GitHub Actions (below), which works the same whatever computer you use.

sudo apt install cron                 # cron is not installed by default
sudo service cron start

Lesson 5 of 7

When an alert fires

A drift and decay playbook
  1. Check the pipeline first: a broken join, a renamed column or a unit change causes most sudden drift.
  2. Measure the impact: did accuracy, calibration or the business metric move, or only an input?
  3. If the model is wrong and a previous version was fine, roll back the champion alias (MLOps 3.1).
  4. If the world changed, retrain on recent labelled data through the tested pipeline and the promotion gate.
  5. Write down the cause and add a test or a monitor so the same failure is caught earlier next time.

Lesson 7 of 7

Chapter summary

  1. Monitor four layers: service (p99 latency, errors), data, model and business. The mean latency hid a 292 ms p99.
  2. PSI measures how much a feature moved (0.1 watch, 0.25 drift). KS flags any change, and with huge samples it flags harmless ones.
  3. Concept drift leaves inputs alone and destroyed accuracy (0.95 to 0.57). Data drift raised PSI to 6.2 with no loss of accuracy.
  4. Schedule the drift job with cron or launchd (macOS), Task Scheduler (Windows), cron or systemd (Linux), or GitHub Actions on any system.
  5. On an alert: check the pipeline, measure impact, roll back or retrain through the gate, then add a test.
