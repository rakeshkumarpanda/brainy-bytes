Lesson 1 of 8

A model behind a web API

Source: Flask documentation (Quickstart and Testing), RFC 9110 HTTP Semantics (methods and status codes), and Chip Huyen, Designing Machine Learning Systems (2022) chapter 7.

What it is
A model API is a small web service. A client sends an HTTP request with JSON, the service checks it, runs the saved pipeline and sends back a JSON response with a status code. A route such as POST /predict connects a URL and a method to one Python function.
Why we need it
A model inside a notebook helps one person. Behind an API, any website, phone app or other service can use it in any programming language, and you can update the model without touching those clients.
How it works
Load the pipeline once when the server starts. Add a /health route that says the service is alive, and a /predict route that validates the input, predicts and returns JSON. Test it in the same process with the framework’s test client before starting a real server.
StatusMeaningWhen a model API sends it
200 OKSuccessThe prediction is in the body
400 Bad RequestThe request itself is brokenThe body is not valid JSON at all
405 Method Not AllowedWrong method for this routeGET sent to a POST only route
422 Unprocessable ContentValid JSON but the content fails the checksA word instead of a number, a missing field
500 Internal Server ErrorA bug or crash inside the serviceNever on purpose. Log it and fix it.

Start the server and call it from a second terminal
macOS
  1. Open Terminal, go to your project folder and activate its environment (MLOps 1.1).
  2. Install the packages and start the Flask server. It keeps running and prints each request it receives.
  3. Open a second Terminal window (Command and N) and call the API with curl, which macOS already has.
  4. Stop the server with Control and C in the first window.
Terminal 1 (macOS)shell
cd ml-project && source .venv/bin/activate
pip install flask scikit-learn
python flask_serve.py serve        # Running on http://127.0.0.1:8000
Terminal 2 (macOS)shell
curl http://127.0.0.1:8000/health
curl -X POST http://127.0.0.1:8000/predict -H 'Content-Type: application/json' -d '{"features": [5.9, 3.0, 5.1, 1.8]}'

The examples use port 8000 on purpose. On macOS 12 and later the AirPlay Receiver already listens on port 5000, the old Flask default, and answers 403 Forbidden. If you ever need port 5000, turn AirPlay Receiver off in System Settings, General, AirDrop and Handoff. To see what holds a port, run lsof -i :8000.

Windows 10 and 11
  1. Open PowerShell, go to your project folder and activate its environment (MLOps 1.1).
  2. Install the packages and start the server. If Windows Defender Firewall asks about Python, allow it on private networks only. The server listens on 127.0.0.1, so nothing outside your computer can reach it.
  3. Open a second PowerShell window and call the API. Invoke-RestMethod is built in and turns the JSON answer into an object.
  4. Stop the server with Control and C.
PowerShell 1 (Windows)shell
cd ml-project
.venv\Scripts\Activate.ps1
pip install flask scikit-learn
python flask_serve.py serve
PowerShell 2 (Windows)shell
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/predict -ContentType 'application/json' -Body '{"features": [5.9, 3.0, 5.1, 1.8]}'

# curl also ships with Windows 10 and 11. Type curl.exe, because in Windows PowerShell 5.1
# the word curl is a different command (an alias of Invoke-WebRequest).
curl.exe http://127.0.0.1:8000/health

To see what holds a port, run netstat -ano | findstr :8000. The last column is the process id, which Task Manager shows on its Details tab.

FastAPI: the input contract written as a class

Source: FastAPI documentation: Request Body, Testing, and the automatic interactive docs. Pydantic documentation: Fields and validation errors.

What it is
FastAPI is a web framework built on type hints. You describe the input as a Pydantic class, for example four floats that must be above 0 and below 20, and FastAPI checks every request against it, converts the types, and writes the error messages for you. It also builds interactive documentation at /docs.
Why we need it
The input contract from MLOps 2.1 becomes a few lines instead of a page of if statements. The documentation always matches the code, because it is generated from the same class. FastAPI also supports async code for services that wait on databases or other APIs.
How it works
Write one class for the input and one for the output, and use them as the type of the function argument and as response_model. Accept a list for a batch route so many rows go through the model in one call. Run it with Uvicorn.
Run this one on your own computer. It needs Flask, FastAPI or Django, which the browser version of Python cannot install or run as a web server. The output above comes from a real run with CPython when this page was built.

In the exam
One bad request produced three precise errors at once: sepal_length must be greater than 0, sepal_width is not a number, and petal_width is missing. The batch route scored two flowers in a single predict_proba call, virginica at 0.703 and setosa at 0.981.
Terminal (macOS, Linux, ChromeOS and PowerShell on Windows)shell
pip install "fastapi[standard]" scikit-learn
uvicorn fastapi_serve:app --port 8000
# then open http://127.0.0.1:8000/docs in the browser and press Try it out

The JSON body for FastAPI uses named fields: {"sepal_length": 5.9, "sepal_width": 3.0, "petal_length": 5.1, "petal_width": 1.8}. The same curl and Invoke-RestMethod commands from the Flask lesson work with this body.

Going deeper: Sync or async route functions

A plain def route runs in a thread pool, which suits scikit-learn because predict is ordinary CPU work. An async def route runs on the event loop, so a slow predict inside it blocks every other request on that worker. Use async def only when the function awaits network or database calls, and keep heavy CPU work in plain def routes or in separate worker processes.

Django: when the model joins a full web application

Source: Django documentation: Using settings without DJANGO_SETTINGS_MODULE (settings.configure), the test client, CSRF protection, and How to deploy with WSGI.

What it is
Django is a full web framework with a database layer, an admin site, user accounts, forms and security features. A JSON view returns a JsonResponse. The program here fits a whole Django service in one file by calling settings.configure instead of creating a project with many files.
Why we need it
Choose Django when the model is one feature of a larger site that already needs logins, a database and an admin, for example a clinic portal that shows a risk score next to each patient. For a model that only answers predictions, Flask or FastAPI is smaller.
How it works
Write a view that reads request.body, validates it, predicts and returns JsonResponse. Mark it @require_POST so other methods get 405. Mark it @csrf_exempt only because programs, not browser forms, call it, and protect it with an API key or token instead.

Common mistake
Django gives the same answers as Flask (200 with virginica at 0.703, 422 for bad JSON), and @require_POST turns a GET into 405 without running the view. In a real project the view lives in an app inside django-admin startproject, and the settings come from environment variables, never a SECRET_KEY written in the code.

Lesson 4 of 8

Online against batch prediction

Source: Chip Huyen, Designing Machine Learning Systems (2022) chapter 7, Model deployment and prediction service, and the pandas documentation for read_csv with chunksize.

What it is
Online (real time) prediction answers each request the moment it arrives, through an API like the ones above. Batch prediction runs on a schedule, scores a whole table at once and stores the answers for the application to look up later.
Why we need it
Online gives fresh answers during the user’s visit but needs a server running all the time and fast features. Batch is cheaper and simpler, and one predict call on many rows is far faster than many calls on one row each, but the answers are only as fresh as the last run.
How it works
Ask how soon the answer is needed. During the visit (fraud checks, search ranking) means online. By tomorrow (churn lists, weekly demand forecasts, email campaigns) means batch. Read big files in chunks so memory stays small.
Download this program (.py)Save it, open it in any editor and run it with python3 batch_predict.py.
Remember
20,000 rows are scored in 4 chunks of 5,000. The last line times both styles on your own device, so the numbers change from run to run, but one call per row is always many times slower because each call pays the same fixed overhead.
Real world scenario: A bank fraud check and a churn list

A card payment must be approved or stopped within about 100 ms, so the fraud model runs online behind an API. The same bank also wants a list of customers likely to close their accounts. Nobody needs that list within 100 ms, so a batch job scores every customer at 2 am and writes the result to a table that the retention team reads in the morning.

From the development server to production

Source: Flask documentation, Deploying to Production. FastAPI documentation, Deployment concepts and Server Workers. Gunicorn, Waitress and Uvicorn documentation. Little, A proof for the queuing formula L = λW (1961).

What it is
app.run() and runserver are development servers: one process, made for debugging, and the docs say not to use them in production. A production server (Gunicorn or Waitress for Flask and Django, which speak WSGI, and Uvicorn for FastAPI, which speaks ASGI) runs several workers and restarts any that crash.
Why we need it
One development server handles requests slowly and stops at the first crash. Workers serve requests in parallel, and a reverse proxy in front adds HTTPS, timeouts and limits on request size.
How it works
Pick the server for your system below. Start with 2 workers per CPU core as a first guess, then measure. Each worker loads its own copy of the model, so memory grows with the number of workers.
Run a production server
macOS

Gunicorn runs Flask and Django with several worker processes. Uvicorn runs FastAPI and has its own --workers option. Both work on macOS and Linux.

Terminal (macOS)shell
pip install gunicorn "uvicorn[standard]"

gunicorn -w 2 -b 127.0.0.1:8000 flask_serve:app            # Flask: file flask_serve.py, object app
gunicorn -w 2 -b 127.0.0.1:8000 django_serve:application   # Django: the WSGI application object
uvicorn fastapi_serve:app --host 127.0.0.1 --port 8000 --workers 2   # FastAPI
Windows 10 and 11

Gunicorn does not run on Windows, because it depends on Unix process features. Use Waitress, a pure Python production server, for Flask and Django. Uvicorn works on Windows as it is. A second choice is to run the Linux commands inside WSL (MLOps 1.1), or inside Docker, which a coming chapter covers.

PowerShell (Windows)shell
pip install waitress "uvicorn[standard]"

waitress-serve --listen=127.0.0.1:8000 flask_serve:app            # Flask
waitress-serve --listen=127.0.0.1:8000 django_serve:application   # Django
uvicorn fastapi_serve:app --host 127.0.0.1 --port 8000 --workers 2   # FastAPI

Waitress uses threads instead of processes (4 by default, change it with --threads=8).

Linux (Ubuntu, Debian, Fedora)

The same commands as macOS. On a Linux server, a systemd service keeps the command running and restarts it after a crash or a reboot. The more common choice today is a Docker container, which a coming chapter covers.

Terminal (Linux)shell
pip install gunicorn "uvicorn[standard]"

gunicorn -w 2 -b 127.0.0.1:8000 flask_serve:app
gunicorn -w 2 -b 127.0.0.1:8000 django_serve:application
uvicorn fastapi_serve:app --host 127.0.0.1 --port 8000 --workers 2
ChromeOS (Chromebook)

Use the Linux commands inside the Linux development environment. A Chromebook is fine for learning and testing, but a real service runs on a server or in the cloud, usually in a Docker container.

Terminal (ChromeOS Linux)shell
pip install gunicorn "uvicorn[standard]"
gunicorn -w 2 -b 127.0.0.1:8000 flask_serve:app
A checklist before real users call the API
  1. Load the model once at start up and keep it in memory.
  2. Keep a /health route for the load balancer, and return the model version in each response.
  3. Validate every input and cap the request size.
  4. Require an API key or token, and rate limit each caller.
  5. Put HTTPS in front with a reverse proxy such as nginx or Caddy, or the cloud’s load balancer.
  6. Log each request with its latency and status code, without personal data.
  7. Set a timeout so one slow request cannot hold a worker forever.
Little’s lawExam favourite
L = λ × W
L requests in progress, λ arrivals per second, W seconds each request spends in the system.
Workers neededExam favourite
workers = λ × latency / target use
Aim for about 70 to 80 percent use so short bursts do not build a queue.
Waiting time for one worker (M/M/1 queue)
W = 1 / (μ − λ)
μ requests per second the worker can serve. W shoots up as λ nears μ.
In the exam
A queue does not grow in a straight line. One worker that can serve 50 requests per second answers in 25 ms at 10 per second, 100 ms at 40 per second, and 1 full second at 49 per second. That is why services keep spare capacity.

From beginner to expert

One idea, four depths

Put the model in a small program that waits for questions over the internet and answers each one with a prediction.

Build /health and /predict routes in Flask, FastAPI or Django, validate inputs, return the right status codes, and test with the test client.

Lesson 8 of 8

Chapter summary

  1. A model API loads the saved pipeline once and answers POST /predict with JSON and a status code: 200 for success, 422 for bad content, 405 for the wrong method.
  2. Flask is small and simple. FastAPI checks inputs from Pydantic classes and writes docs at /docs. Django fits when the model joins a full web app.
  3. Test with the framework’s test client, then call the running server with curl, or with Invoke-RestMethod in Windows PowerShell.
  4. Online prediction answers during the visit. Batch prediction scores everything on a schedule, cheaper but less fresh.
  5. Production uses Gunicorn (macOS, Linux), Waitress (Windows, any system) or Uvicorn (FastAPI, any system) with several workers, sized with Little’s law.
