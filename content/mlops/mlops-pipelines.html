Lesson 1 of 7

One pipeline from raw columns to prediction

Source: scikit-learn user guide, 6.1 Pipelines and composite estimators (Pipeline, ColumnTransformer) and 6.3 Preprocessing data.

What it is
A Pipeline chains preprocessing steps and a model into one object with fit and predict. A ColumnTransformer sends different columns to different steps, for example imputing and scaling the numbers while one hot encoding the categories. Each step fits on training data (learns a median, a mean, a list of categories) and then transforms any data with what it learned.
Why we need it
Without a pipeline, the same preprocessing is written twice: once in the training notebook and again in the serving code, and the two copies drift apart. A pipeline keeps the whole recipe in one object that is trained, saved, loaded and served together, and it makes cross validation honest because every step refits inside each fold.
How it works
List the numeric and categorical columns, build one small pipeline for each kind, combine them in a ColumnTransformer, and put the model last. Set handle_unknown='ignore' on the encoder so a category never seen in training does not crash the service. Call fit once on the training data, and only predict afterwards.

Lesson 2 of 7

Leakage: why every learning step belongs inside the pipeline

Source: Hastie, Tibshirani and Friedman, The Elements of Statistical Learning (2009) section 7.10.2, Kaufman and colleagues, Leakage in data mining (2012), and scikit-learn user guide section 11.2, Data leakage.

What it is
Data leakage is when information that will not be available at prediction time gets into training or evaluation. A common form is preprocessing or feature selection fitted on all the rows before splitting, so the test rows influence the model that is then tested on them.
Why we need it
Leakage gives scores that look excellent in the notebook and collapse in production. It is one of the most common reasons ML projects fail, because nothing crashes: the numbers are simply wrong.
How it works
Split first. Put every step that learns from data (imputers, scalers, encoders, feature selection, resampling) inside the pipeline, and cross validate the whole pipeline. Also check features for values recorded after the event you predict, such as a cancellation date in a churn model.
Download this program (.py)Save it, open it in any editor and run it with python3 leakage_pipeline.py.
In the exam
On 100 rows of random noise with random labels, choosing the 20 best of 5000 columns before cross validation reports an accuracy of 0.85. Doing the same selection inside the pipeline reports 0.48, the honest answer for labels that are pure chance.

Saving and loading a trained pipeline

Source: scikit-learn user guide, 10 Model persistence, the joblib documentation, the skops documentation, and the ONNX and sklearn-onnx documentation.

What it is
Serialising a model writes the fitted object to a file so another program can load it and predict. scikit-learn models are usually saved with joblib, which uses Python’s pickle format and handles NumPy arrays efficiently. A small metadata file next to it records the features, classes and library versions.
Why we need it
Training happens once, prediction happens millions of times in another process, often on another machine. The file is the hand over between the two. The metadata makes sure the loading side uses compatible versions and sends the features in the right order.
How it works
Save the whole pipeline, never just the model, with joblib.dump, and load it with joblib.load in the serving code. Load only files you trust, because loading a pickle can run code. Use the same scikit-learn version to load. For safer or cross language formats, use skops or convert to ONNX.

Lesson 4 of 7

An input contract for the model

Source: Breck and colleagues, The ML test score (2017), data and feature tests, Google, Rules of machine learning rule 10, and the pydantic documentation.

What it is
An input contract (or schema) says which fields a request must have, their types and their allowed ranges. Requests that break it are rejected with a clear message, in a web API usually with status code 422 (unprocessable content), before they reach the model.
Why we need it
A model will happily return a number for nonsense input: a negative age, a price sent as text, a missing field silently filled with a default. Those wrong answers flow into decisions. Checking inputs turns silent errors into loud, fixable ones.
How it works
Write the schema once, check every field for presence, type and range, warn about unknown categories, and reject extra fields. In FastAPI, a pydantic model does this automatically, as chapter 2.2 shows.

Lesson 7 of 7

Chapter summary

  1. A Pipeline plus a ColumnTransformer holds imputing, scaling, encoding and the model in one object with fit and predict.
  2. Steps fit on training data only and transform new rows with what they learned. handle_unknown='ignore' keeps unseen categories from crashing.
  3. Leakage: any step fitted on all rows (scaling, selection) lets test rows shape the model. Selection outside cross validation scored 0.85 on noise, inside it scored 0.48.
  4. Save the whole pipeline with joblib plus a metadata file with features, classes and versions. Load only trusted files, with the same library versions.
  5. Check every request against an input contract and reject bad ones with status 422.
