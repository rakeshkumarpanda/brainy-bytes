Lesson 1 of 7

Experiment tracking: a record of every run

Source: MLflow documentation, Tracking. Sculley and colleagues, Hidden technical debt in machine learning systems (2015).

What it is
An experiment tracker stores, for every training run, the parameters (settings such as C), the metrics (such as validation AUC), the artifacts (the model file, plots), and the context: code version, data fingerprint, time and who ran it. Runs are grouped into experiments and can be searched, sorted and compared.
Why we need it
After a week of trying ideas nobody remembers which settings gave the good score, which data it used, or where the model file went. A spreadsheet of results drifts away from the real runs. A tracker records everything automatically, so any result can be found, compared and reproduced.
How it works
Wrap each training run in a tracked run, log parameters before training and metrics after, save the model as an artifact, and tag the data version and the Git commit. Compare runs only when they used the same data and the same validation split.
Download this program (.py)Save it, open it in any editor and run it with python3 tracker_lite.py.
Remember
Each line of runs.jsonl is one complete record: settings, score, a 12 character fingerprint of the training data and the Git commit. Because every run has the same data fingerprint, their scores are comparable. MLflow stores the same facts in a database instead of a text file.
What to logExampleWhy
ParametersC = 1.0, class_weight = NoneTo know what produced the result
Metricsval_auc = 0.9952To compare and rank runs
Artifactsmodel file, confusion matrix plotTo reuse the exact model later

Lesson 2 of 7

MLflow on your own computer

Source: MLflow 3 documentation: Tracking quickstart, mlflow.search_runs, mlflow.sklearn.log_model, Model Registry and model aliases.

What it is
MLflow is an open source platform for tracking runs, packaging models and keeping a model registry. Runs go into a backend store (here a SQLite file) and model files into an artifact store (here the folder mlruns). mlflow ui shows them in the browser.
Why we need it
It is free, works offline on one laptop, and grows into a shared team server without changing your training code. Many cloud platforms (Databricks, Azure ML) speak the same MLflow API.
How it works
Point MLflow at a store, choose an experiment, and inside with mlflow.start_run() log parameters, metrics and the model. Then search the runs, register the best model and give it an alias.
Run this one on your own computer. It needs the mlflow package and writes a database and model files, which the browser version of Python cannot install or keep. The output above comes from a real run with CPython when this page was built.
Download this program (.py)Run it with python3 mlflow_track.py.
In the exam
Four runs were logged and sorted by validation AUC. C = 1.0 won with 0.9952, was registered as version 1 of breast-cancer-classifier with the alias champion, and loading models:/breast-cancer-classifier@champion gave back exactly the same AUC.
Install MLflow, run the program and open the MLflow page
macOS
  1. Activate your project environment and install MLflow. It is a big package, so the install takes a minute.
  2. Run the program, then start the MLflow web page on port 5001. On macOS 12 and later port 5000, the MLflow default, is taken by the AirPlay Receiver and answers 403.
  3. Open http://127.0.0.1:5001, click the breast-cancer experiment, tick the four runs and press Compare.

Going deeper: From one laptop to a team server

A team runs one tracking server with a real database and shared artifact storage, for example mlflow server --backend-store-uri postgresql://... --artifacts-destination s3://bucket/mlflow --host 0.0.0.0, behind a login. Everyone sets MLFLOW_TRACKING_URI to its address and the training code stays the same. The MLflow project also publishes an official Docker image (ghcr.io/mlflow/mlflow) for running that server in a container (MLOps 2.3).

Choosing the best run without fooling yourself

Source: Cawley and Talbot, On over-fitting in model selection and subsequent selection bias in performance evaluation (2010), and Bergstra and Bengio, Random search for hyper-parameter optimization (2012).

What it is
When you compare many runs on one validation set and keep the best, part of its lead is luck. This selection bias, also called the winner’s curse, makes the champion’s validation score too optimistic.
Why we need it
Trackers make it easy to try hundreds of runs. The more you try, the larger the bias, until a model that learned nothing can look good.
How it works
Keep a test set that no run ever sees and score only the final champion on it, once. Use cross validation for the comparison, prefer simpler settings when scores are within noise, and report how many runs you tried.
Download this program (.py)Save it, open it in any editor and run it with python3 winners_curse.py.
Common mistake
The labels are coin flips, so every model is truly 50 percent accurate. The best of 1000 runs still showed 0.615 on validation, then 0.530 on fresh test data. With 200 validation rows one standard error is 0.035, and the best of 1000 lands about three standard errors above the truth.
Random search coverageExam favourite
P(at least one of n runs in the top q) = 1 − (1 − q)n
60 random runs reach the top 5 percent with 95 percent chance.
Expected best of n noisy scoresExam favourite
about σ √(2 ln n) above the mean
With σ = 0.02 and n = 100: 0.061, close to the 0.064 drop in the animation.
Lesson 4 of 7

The model registry: versions, aliases and promotion

Source: MLflow documentation, Model Registry and model aliases. Google, MLOps: Continuous delivery and automation pipelines in machine learning.

What it is
A model registry keeps every approved model as a numbered, unchangeable version with its lineage (which run, data and code made it). Aliases such as champion and challenger are movable labels, and services load a model by alias, for example models:/breast-cancer-classifier@champion.
Why we need it
Without a registry, the model in production is a file somebody copied, and nobody can say which run made it or how to go back. With versions and aliases, promotion and rollback are one recorded action, and the service code never changes.
How it works
Register candidates as new versions, evaluate a challenger against the champion on the same held out data, promote only past a margin and after review, and roll back by moving the alias. Never edit a version, register a new one.
Download this program (.py)Save it, open it in any editor and run it with python3 registry_lite.py.
In the exam
v2 (AUC 0.8844) was kept but not promoted. v3 (0.9942) beat v1 (0.9555) and became champion. After the incident, champion moved back to v1 in one line, with no retraining and no rebuild.
A promotion checklist
  1. The challenger was trained by the pipeline from tracked code and data, not by hand.
  2. It beats the champion on the same held out data by more than the noise (the gate).
  3. It passes the behaviour tests of MLOps 2.3 and a fairness check by group (MLOps 3.3).
  4. Latency and memory fit the service.
  5. A person approves, the alias moves, and the change is logged with the reason.

Chapter summary

  1. An experiment tracker stores parameters, metrics, artifacts, data fingerprint and code version for every run.
  2. MLflow logs runs inside mlflow.start_run(), searches them with search_runs, and shows them with mlflow ui (port 5001 on macOS because of AirPlay).
