Lesson 1 of 7

Containers, images and the Dockerfile

Source: Docker documentation: Dockerfile reference, Build cache, and Best practices for writing Dockerfiles.

What it is
A Docker image is a sealed package with an operating system layer, Python, the pinned packages, your code and the trained model. A container is a running copy of an image. A Dockerfile is the recipe that builds the image, one instruction per line, and a registry such as Docker Hub or GitHub Container Registry stores images so servers can pull them.
Why we need it
A virtual environment pins Python packages, but not the operating system, the system libraries or the Python build. An image pins all of it, so the model runs the same on your laptop, in CI and on the server, and on macOS, Windows, Linux and ChromeOS alike.
How it works
Start from a small official base image, copy and install the requirements first, then copy the code. Train or copy the model, switch to a user that is not root, open the port, add a health check and say which command starts the server.
WordWhat it isCommand
ImageA read only package built from a Dockerfile, made of layersdocker build -t iris-api:1.0.0 .
ContainerA running copy of an image, with its own file system and networkdocker run -p 8000:8000 iris-api:1.0.0
TagA name and version for an imageiris-api:1.0.0

  1. Line 2 The official slim Python image: Debian with Python 3.14 and little else. Alpine is smaller but uses musl instead of glibc, so scientific packages may need compiling.
  2. Line 5 Do not write .pyc files, and send print output straight to the logs.
  3. Line 6 Every later path is inside /app.
  4. Line 9 Only requirements.txt first. This layer changes rarely.
  5. Line 10 The slow step. Because it comes before the code, Docker reuses it from the cache after a code change.
  6. Line 13 A value you can pass at build time with --build-arg, here the model version.
  7. Line 15 The code comes after the packages.
  8. Line 16 Train inside the image, so the model and the library versions always match. Bigger models are trained elsewhere and copied in.
  9. Line 19 Create a normal user.
  10. Line 20 Run the server as that user, not as root, so a bug in the app cannot take over the container.
  11. Line 22 Documents the port the app listens on.
  12. Line 23 Docker calls /health every 30 seconds and marks the container healthy or unhealthy. The slim image has no curl, so Python does the call.
  13. Line 24 The command that starts when the container starts: Uvicorn with 2 workers on all network interfaces inside the container.

Build and run the model container on your computer

Source: Docker documentation: Docker Desktop for Mac and for Windows (WSL 2 backend), Docker Engine for Ubuntu, Debian and Fedora, Post installation steps for Linux, and the Compose file reference.

What it is
One download, make_project.py, creates the whole project of this chapter: the training script, the FastAPI app, the tests, the requirements, the Dockerfile, the Compose file and the GitHub Actions workflow.
Why we need it
Running the real thing once on your own computer makes every later idea concrete: images, containers, ports, health checks and logs.
How it works
Run make_project.py, build the image, start a container in the background, call it, read its logs, and stop it. Then do the same with one Compose command.
Download this program (.py)Save it, open it in any editor and run it with python3 make_project.py.

Terminal (macOS, Apple silicon)shell

Lesson 3 of 7

Testing a model, not only the code

Source: Breck, Cai, Nielsen, Salib and Sculley, The ML Test Score: A Rubric for ML Production Readiness (2017), and Ribeiro, Wu, Guestrin and Singh, Beyond Accuracy: Behavioral Testing of NLP Models with CheckList (2020).

What it is
Normal tests check that code does what it should. A model also needs behaviour tests: a quality gate (accuracy must stay above a line), known examples that any good model gets right, invariance (tiny changes that should not change the answer) and directional checks (a change that should push the answer one way).
Why we need it
A training run can finish without any error and still produce a useless model, for example after a data bug shuffles the labels. Without behaviour tests, CI stays green and the bad model ships.
How it works
Write the tests with pytest next to the app. Keep them fast, so they run on every push. Choose the gate from the current model’s score and its uncertainty, not from a wish.
TestQuestion it answersIn this project
API testDo the routes answer correctly?test_health, test_known_flower
Input testIs bad input rejected?test_bad_input_is_rejected (422)
Quality gateIs the model good enough to ship?test_accuracy_gate (at least 0.90)
InvarianceDoes tiny noise leave the answer alone?test_small_noise_keeps_the_class
DirectionalDoes a change push the answer the right way?test_longer_petals_mean_virginica
LatencyIs it fast enough?test_latency_budget (under 50 ms)

Common mistake
The broken model scored 0.2 and failed three of the four checks, so CI blocks it. Look closely: it still passed the invariance test, because a model that ignores its input is perfectly stable. One kind of test is never enough.
tests/test_app.pypython
1# Tests that CI runs on every push: python -m pytest -q2import time3 4from fastapi.testclient import TestClient5 6from app import app, meta, model7 8client = TestClient(app)9SETOSA = {'sepal_length': 5.0, 'sepal_width': 3.4, 'petal_length': 1.5, 'petal_width': 0.2}10 11 12def test_health():13    r = client.get('/health')14    assert r.status_code == 200 and r.json()['status'] == 'ok'15 16 17def test_known_flower():18    r = client.post('/predict', json=SETOSA)19    assert r.status_code == 200 and r.json()['species'] == 'setosa'20 21 22def test_bad_input_is_rejected():23    r = client.post('/predict', json={'sepal_length': -1})24    assert r.status_code == 42225 26 27def test_accuracy_gate():28    assert meta['test_accuracy'] >= 0.90            # a worse model must not ship29 30 31def test_small_noise_keeps_the_class():32    a = model.predict([[5.0, 3.4, 1.5, 0.2]])[0]33    b = model.predict([[5.02, 3.38, 1.51, 0.2]])[0]34    assert a == b35 36 37def test_longer_petals_mean_virginica():38    p_small = model.predict_proba([[6.0, 3.0, 4.0, 1.2]])[0][2]39    p_large = model.predict_proba([[6.0, 3.0, 6.0, 2.2]])[0][2]40    assert p_large > p_small41 42 43def test_latency_budget():44    start = time.perf_counter()45    for _ in range(100):46        client.post('/predict', json=SETOSA)47    assert (time.perf_counter() - start) / 100 < 0.05     # under 50 ms per request
  1. Line 4 TestClient calls the app in the same process, no server needed.
  2. Line 6 Importing app also loads the model, exactly as the server does.
  3. Line 9 A flower that every good model calls setosa.
  4. Line 28 The quality gate. A model below 0.90 fails CI and cannot be merged.
  5. Line 31 Invariance: a change of a few hundredths of a centimetre must not change the class.
  6. Line 37 Directional: longer, wider petals should make virginica more likely.
  7. Line 43 A rough latency budget. Real load tests use tools such as Locust on the running container.
Chance a suite of flaky tests is greenExam favourite
P(green) = (1 − p)n
n independent tests that each fail at random with probability p. Ten tests at 2 percent: 0.9810 = 0.817.
Uncertainty of a test accuracyExam favourite
SE = √(p(1 − p) / n)
With p = 0.9111 on n = 45 test rows, SE = 0.042, so a gate at 0.90 is less than one standard error away.

CI/CD with GitHub Actions

Source: GitHub Actions documentation: Workflow syntax, Building and testing Python, and Publishing Docker images. Humble and Farley, Continuous Delivery (2010).

What it is
Continuous integration (CI) runs the same checks on a clean machine for every push and pull request. Continuous delivery (CD) turns every green change on main into a released artefact, here a container image in a registry, ready to deploy. GitHub Actions runs both from a YAML file in .github/workflows.
Why we need it
Checks that only run on your laptop get skipped on a busy day, and a laptop has packages a clean server does not. CI catches a broken model or a missing file before anyone merges it, and CD makes every release the same few steps.
How it works
Commit the workflow file. Make the pull request wait for the green check (branch protection). Tag each image with the commit id, keep passwords in repository secrets, and roll back by running the previous tag.
.github/workflows/ci.ymlyaml
1name: model-ci2 3on:4  push:5    branches: [main]6  pull_request:7 8jobs:9  test:10    runs-on: ubuntu-latest11    steps:12      - uses: actions/checkout@v413      - uses: actions/setup-python@v514        with:15          python-version: "3.14"16          cache: pip17      - run: pip install -r requirements-dev.txt18      - run: python train.py19      - run: python -m pytest -q20 21  image:22    needs: test23    runs-on: ubuntu-latest24    permissions:25      contents: read26      packages: write27    steps:28      - uses: actions/checkout@v429      - name: Build the image30        run: docker build --build-arg MODEL_VERSION=${{ github.sha }} -t iris-api:ci .31      - name: Smoke test the container32        run: |33          docker run -d --name api -p 8000:8000 iris-api:ci34          for i in $(seq 1 20); do curl -fs http://127.0.0.1:8000/health && break || sleep 1; done35          curl -fs -X POST http://127.0.0.1:8000/predict -H 'Content-Type: application/json' \36            -d '{"sepal_length": 5.0, "sepal_width": 3.4, "petal_length": 1.5, "petal_width": 0.2}'37      - name: Push to GitHub Container Registry38        if: github.ref == 'refs/heads/main'39        run: |40          echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin41          IMAGE=ghcr.io/${{ github.repository }}:${{ github.sha }}42          docker tag iris-api:ci $IMAGE43          docker push $IMAGE
  1. Line 3 When to run: every push to main and every pull request.
  2. Line 9 The first job installs, trains and tests.
  3. Line 10 A fresh Ubuntu machine for every run.
  4. Line 16 Cache downloaded packages between runs to save time.
  5. Line 17 The same pinned versions as on your computer.
  6. Line 19 Any failing test turns the run red.
  7. Line 22 The image job only starts when the test job passed.
  8. Line 26 Allows this job to push to GitHub Container Registry with the built in token.
  9. Line 30 The commit id becomes the model version inside the image.
  10. Line 34 Wait up to 20 seconds for the container to answer /health.
  11. Line 35 curl -f fails on any 4xx or 5xx status, so a broken /predict also turns the run red.
  12. Line 38 Only main publishes an image. Pull requests stop after the smoke test.
  13. Line 40 GITHUB_TOKEN is created for every run. Never write a password in the file itself.
  14. Line 41 Image names in ghcr.io must be lower case, so use a lower case repository name.

Turn it on for your repository
  1. Create a repository on GitHub and push the iris-api folder, including .github/workflows/ci.yml.
  2. Open the Actions tab. The workflow named model-ci starts on its own for the push.
  3. In Settings, Branches, add a rule for main that requires the test and image checks to pass before merging.
  4. Open a pull request that lowers the gate or breaks the model, and watch the check turn red.
  5. After a merge to main, find the new image under Packages on the repository page.
Going deeper: Continuous training, canary releases and rollbacks

CI/CD for ML often adds a third loop, continuous training: a schedule or a drift alarm retrains the model on fresh data, and the new model goes through the same gate. Releases are safer as a canary: send 5 percent of traffic to the new image, compare its errors with the old one, and only then move everyone over. Because every image is tagged with its commit id, a rollback is one command that runs the previous tag.

Lesson 7 of 7

Chapter summary

  1. An image packs the OS layer, Python, the pinned packages, the code and the model. A container is a running copy. The same image runs the same on every system.
  2. Order the Dockerfile for the layer cache: requirements and pip install first, code later. A code change then rebuilt in 2.2 s instead of 32 s.
  3. Run as a user that is not root, add a HEALTHCHECK, and start with docker run -p 8000:8000 or docker compose up.
  4. Test the model, not only the code: a quality gate, known examples, invariance and directional checks. The broken model still passed invariance, so use several kinds.
  5. GitHub Actions runs install, train, test, build, smoke test and push on every change, and the first failure blocks the release.
