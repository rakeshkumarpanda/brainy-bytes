Lesson 1 of 8

Start with the problem, then size the system

Source: Huyen, Designing Machine Learning Systems (2022) chapters 1 and 2, and Kleppmann, Designing Data-Intensive Applications (2017) chapter 1.

A framework for any ML system design question
  1. Clarify the goal: the business metric (for example watch time or fraud losses) and the ML task that serves it (ranking, classification).
  2. Write the requirements: how many users, how fast an answer must be, how fresh the data, what a wrong answer costs, privacy and fairness limits.
  3. Design the data: where labels come from, which features, how they are computed for training and for serving.
  4. Choose the model: start with a simple baseline, then the model that fits the latency and the data.
  5. Design serving: batch or online, one stage or retrieval then ranking, and how many replicas.
  6. Plan evaluation: offline metrics first, then a shadow run, a canary and an online A/B test.
  7. Plan operations: monitoring, retraining and rollback (MLOps 3.1 and 3.2).
What it is
ML system design is the plan for everything around a model: data pipelines, features, training, serving, evaluation and monitoring, sized for real traffic.
Why we need it
In production the model is a small part of the code. Most failures come from the system around it: slow serving, features that differ between training and serving, or a rollout with no way back. Interviews at large companies test exactly this.
How it works
Turn every requirement into a number, do quick arithmetic for traffic, latency and storage, and let those numbers choose the design.

In the exam
Ten million daily users with 20 requests each average 2,315 requests per second and peak at 6,944. One replica with 4 workers at 40 ms handles 100 per second, so 116 replicas keep each at 60 percent load. Ranking a million items per request would take a full second, which is why recommenders retrieve 500 candidates first.
Average loadExam favourite
QPS = daily requests / 86,400
A day has 86,400 seconds.
Little’s lawExam favourite
L = λ × W
Requests in the system = arrival rate × time each one spends. So throughput = workers / latency.
Replicas
replicas = ⌈ peak QPS / (per replica QPS × target load) ⌉
A target load of 0.6 leaves room for spikes and a failed replica.

Batch, online and streaming predictions

Source: Huyen (2022) chapter 7, Covington, Adams and Sargin, Deep neural networks for YouTube recommendations (2016), and Breck and colleagues, The ML test score (2017).

Three ways to deliver predictions
BatchOnline (on request)Streaming
When it predictsOn a schedule, for everyoneWhen a request arrivesWhen an event arrives
LatencyHours, results read from a tableMillisecondsSeconds
Feature freshnessAs old as the last runRequest data plus stored featuresFeatures updated from the event stream
ExampleNightly churn scores for the sales teamFraud check during a paymentLive delivery time estimates

Bottom line: Many systems mix them: batch for heavy features, online for the final score.

What it is
Training-serving skew means the model sees features in production that were computed differently from the ones it was trained on. A feature store keeps one definition of each feature and serves it both to training jobs (as of a past date) and to the live service (the latest value).
Why we need it
Skew is silent. The service answers, the offline score looked great, and the live accuracy is poor. It is one of the most common reasons why a model that won offline loses online.
How it works
Compute every feature with one shared function or a feature store, log the features the service actually used, and add a parity test that sends the same raw rows through the training path and the serving path.
Download this program (.py)Save it, open it in any editor and run it with python3 skew_check.py.
Common mistake
The model scored 0.730 offline. The serving code filled missing spend with 0 instead of the training median and received spend in pence, not pounds, so live accuracy fell to 0.550 and the mean predicted churn collapsed from 0.435 to 0.124. A parity test on the same raw rows finds the difference on 100 percent of rows before release.
Going deeper: Two stage recommenders

Large recommenders answer in two stages. Retrieval picks a few hundred candidates out of millions with a cheap method, such as nearest neighbours of a user embedding in a vector index. Ranking scores only those candidates with a heavier model that uses many features. Some systems add a third re-ranking step for business rules such as diversity and freshness. The capacity program above shows why: at 1 microsecond an item, ranking everything takes 1,000 ms, ranking 500 candidates takes 0.5 ms.

Lesson 3 of 8

Shadow, canary and rollback

Source: Google, The Site Reliability Workbook (2018), chapter 16, Canarying releases.

What it is
A shadow deployment sends a copy of live requests to the new model and logs its answers without showing them. A canary gives the new model to a small share of users and grows the share step by step. A guardrail is a metric with a limit, such as error rate or latency, checked after every step.
Why we need it
Offline tests never cover everything real users do. A gradual rollout limits how many people a bad model can hurt, and an automatic rollback fixes it in seconds instead of hours.
How it works
Run in shadow first to compare answers and latency. Then route 1, 5, 25, 50 and 100 percent of traffic, check the guardrails at each step, and keep the old version deployed until the new one has been stable for a while.
StrategyUsers see the new modelGood forWatch out for
ShadowNoLatency, crashes, agreement with the old modelCannot measure user reactions, doubles compute
CanaryA small growing shareCatching bugs with little harmSmall shares need time to show rare problems
Blue-greenAll at once, with an instant switch backSimple, fast rollbackNo gradual exposure
A/B testA fixed random half (or share)Measuring the effect on a business metricNeeds enough users and a fixed plan
Multi-armed banditMore traffic to the version that is winningMany variants, short campaignsHarder to read the final effect
Lesson 4 of 8

A/B testing a new model

Source: Kohavi, Tang and Xu, Trustworthy Online Controlled Experiments (2020) chapters 2, 17 and 18.

What it is
An A/B test assigns users at random to the old model (A) or the new one (B) and compares a metric such as conversion. A two proportion z test says whether the difference is larger than chance. The sample size is fixed before the test from the smallest lift worth detecting.
Why we need it
Offline gains often vanish online, because users react to the model and the offline metric is only a proxy. A randomised test is the only reliable way to measure the real effect, but only if it is run honestly.
How it works
Choose the metric, the smallest lift that matters (minimum detectable effect, MDE), α and power. Compute n per group, run until both groups reach n, then test once. Watch guardrail metrics during the test, but do not stop early because the p value looks good.
Download this program (.py)Save it, open it in any editor and run it with python3 ab_test.py.
In the exam
To detect a lift from 5.0 to 5.5 percent with α = 0.05 and 80 percent power you need 31,235 users per group. In 2,000 A/A tests a single look at the end gave 4.4 percent false alarms, close to the promised 5. Stopping on the first day with p < 0.05 gave 22.0 percent, more than four times as many.
Sample size per groupExam favourite
n = (z1−α/2 + z1−β)² · 2 p̄(1 − p̄) / δ²
p̄ is the average rate, δ the lift. Halving δ needs four times the users.
Two proportion z testExam favourite
z = (pB − pA) / √( p(1 − p)(1/nA + 1/nB) )
p is the pooled rate of both groups.
Many looks
P(at least one false alarm) ≤ 1 − (1 − α)k
An upper limit for k looks. Real looks share data, so the true rate is lower but still far above α.

Load test your model service on your own computer

Source: Python documentation: http.server, urllib.request and concurrent.futures.

What it is
A load test sends many requests at once to a service and records throughput (requests per second) and latency percentiles at growing numbers of simultaneous users.
Why we need it
Capacity plans are guesses until you measure. A load test shows the real requests per second of one replica, the number you divide the peak by, and the point where latency starts to climb.
How it works
Start the service from MLOps 2.2 or the Docker image from MLOps 2.3, run the load test against it, and find the number of users where requests per second stop growing. Use that, with headroom, in the capacity plan.
Run this one on your own computer. A load test needs real network calls to a server on your machine, which a browser page cannot make. The output above comes from a real run with CPython when this page was built.
Download this program (.py)Run it with python3 load_test.py.
In the exam
The built-in demo server can work on 4 requests at once, each taking 20 ms, so Little’s law predicts 4 / 0.020 = 200 requests per second. The test gets close to 200 with 4 users and stays just under 200 with 8 and 16 users, while the median latency rises from about 21 ms to about 40 ms and then higher. Past the saturation point, more users only add waiting time. Timings change a little on every run.

  3. Compare the table with the real run below. Apple Silicon Macs are usually faster than the cloud machine used for this page.

  1. Start Docker Desktop (it uses WSL 2), then run the container in PowerShell. Or start the FastAPI service with uvicorn as in MLOps 2.2, which also runs on Windows.
  2. Use 127.0.0.1 rather than localhost. On Windows localhost may try the IPv6 address first, which adds a delay to every request and spoils the timings.

Worked design: real time fraud detection

Real world scenario: A payment company asks for a fraud model

Every card payment must be approved or blocked within 100 ms, at a peak of 3,000 payments a second. Fraud is about 0.1 percent of payments. A missed fraud costs the full amount, and a wrongly blocked payment costs an angry customer. Fraud labels arrive weeks later, when customers dispute charges.

Part of the designChoiceWhyChapter
MetricFraud losses saved, with a cap on wrongly blocked good paymentsAccuracy is useless at 0.1 percent fraudML 2.x metrics
FeaturesPayment amount, merchant, card history counts over 1 hour and 30 daysHistory counts come from a feature store, updated from the payment streamThis chapter
ModelGradient boosted trees, a few milliseconds per paymentStrong on tabular data, fast, explainable with SHAPMLOps 3.3
ServingOnline, inside the payment flow, rules as a fallbackMust decide before the payment completesMLOps 2.2
RolloutShadow for two weeks, then canary with guardrails on block rateFraud labels are slow, so start with safe signalsThis chapter
MonitoringScore PSI, block rate, latency p99, dispute rate when labels arriveFraudsters adapt, so concept drift is certainMLOps 3.2
RetrainingWeekly through the tested pipeline and the registry gateNew fraud patterns appear all the timeMLOps 3.1
Remember
Interviewers look for the trade-offs, not one right answer. Say what you would measure, what you would try first, and how you would know it failed.

Lesson 8 of 8

Chapter summary

  1. Turn requirements into numbers: 10 million users × 20 requests is 2,315 per second on average, 6,944 at peak, 116 replicas at 60 percent load.
  2. Choose batch, online or streaming serving. Retrieve cheaply, then rank: 500 candidates take 0.5 ms instead of 1,000 ms.
  3. Training-serving skew took accuracy from 0.730 to 0.550. Share one feature function or a feature store and add a parity test.
  4. Release in steps: shadow, canary with guardrails, automatic rollback. A/B test with a fixed n (31,235 per group). Peeking raised false alarms from 4.4 to 22 percent.
  5. Load test on your own computer: throughput levels off at workers / latency, and after that only waiting time grows.
