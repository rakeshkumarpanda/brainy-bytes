Lesson 1 of 7

What MLOps is

Source: Google Cloud, MLOps: Continuous delivery and automation pipelines in machine learning, Sculley and colleagues, Hidden technical debt in machine learning systems (NeurIPS 2015), and Kreuzberger, Kuhl and Hirschl (IEEE Access 2023).

What it is
MLOps (machine learning operations) is the set of practices that take a model from an experiment to a product and keep it working: versioning data, code and models, automated training pipelines, testing, deployment, monitoring and retraining. It extends DevOps, which does this for ordinary software, with the parts that are special to ML.
Why we need it
In ML the behaviour comes from data as much as from code. A model can be correct on launch day and wrong a month later because the world changed, with no code change at all. Sculley and colleagues (2015) showed that the model code is a small box in a real ML system, surrounded by data collection, feature pipelines, serving and monitoring, and that most of the long term cost lives there.
How it works
Treat the loop as the product: define the problem and metric, version the data, train in a repeatable pipeline that logs everything, evaluate against the current model, register the winner, deploy it, monitor it, and retrain when monitoring says so. Automate one stage at a time, starting with training.

Real world scenario: A churn model that went stale
A telecom company launched a model that predicted which customers would leave, with 90 percent precision. Six months later a competitor launched a cheap plan, customer behaviour changed and precision fell to 60 percent, but nobody noticed because nothing watched the model. With MLOps, a monitor would have flagged the change in input data within days and triggered retraining on recent customers.

Reproducibility: seeds and run records

Source: Pineau and colleagues, Improving reproducibility in machine learning research (JMLR 2021), the scikit-learn glossary entry for random_state, and the MLflow tracking documentation.

What it is
A run is reproducible when the same code, data, configuration and environment give the same result. Randomness hides in data splits, model initialisation, bagging and shuffling, and a random seed fixes it. A run record stores everything about one run: data version, parameters, metrics and package versions.
Why we need it
Without reproducibility you cannot tell whether a change helped, debug a model that misbehaves in production, or prove to an auditor how a decision was made. With it you can rerun any past model exactly and roll back to it.
How it works
Set random_state (or seed NumPy, Python and PyTorch) and keep the seed in the configuration. Report the spread over several seeds, not one lucky number. Save a run record for every training run, which tools such as MLflow do for you.

In the exam
The first block changes every time you run it, which is the point. With the seed fixed at 42, five runs give exactly the same accuracy, 0.972, five times. Lesson 3 of 7

Versioning data and models

Source: The DVC documentation (Data Version Control), Google, Rules of machine learning (rule 4 onwards), and the MLflow model registry documentation.

What it is
Data versioning gives every dataset a fixed identity, usually a content fingerprint (a hash), so you always know which data trained which model. Tools such as DVC keep large files outside Git and store their hashes in Git. A model registry stores each trained model with its version, metrics, data version and stage (for example staging or production). Lineage is the chain from raw data to deployed model.
Why we need it
Data changes silently: a new export drops rows, a labelling mistake flips classes, a column changes its units. The code stays the same but the model changes, and without versions nobody can explain why accuracy moved or go back to the last good model.
How it works
Hash the data at every pipeline step and save the hash in the run record. Commit small data and DVC pointer files to Git. Register every model that passes evaluation, with tags for the code commit and the data fingerprint, and promote or roll back by changing the registry stage, not by copying files.
Download this program (.py)Save it, open it in any editor and run it with python3 data_versions.py.
In the exam
The original breast cancer data gives a 5 fold accuracy of 0.981. Flipping 40 labels (7 percent) drops it to 0.882 with the same number of rows. Losing about 30 percent of the rows (399 left) gives 0.975. Each version has a different fingerprint, so the run record shows exactly which one a model saw.

A project layout that grows into production

Source: Cookiecutter Data Science (DrivenData), Breck and colleagues, The ML test score: a rubric for ML production readiness (2017), and Huyen, Designing machine learning systems (2022) chapter 10.

What it is
A good ML project separates data, notebooks for exploring, source code for anything that must run again, configs for parameters, tests, and models or reports produced by runs. Settings live in config files, not inside the code.
Why we need it
Notebooks are perfect for exploring and terrible for production: cells run out of order, results hide in outputs, and they are hard to test or review. Moving reusable steps into small functions in src makes them testable and lets a pipeline call them.
How it works
Start from a standard layout, keep raw data read only, put every step (load, clean, features, train, evaluate) in its own function, and test data and model as well as code. The ML test score asks for tests of features, data, the model and the infrastructure.
A layout that works on every systemshell
ml-project/
  data/raw/            # never edited, versioned with DVC
  data/processed/
  notebooks/           # exploring only
  src/
    data.py            # load and clean
    features.py
    train.py           # reads configs/train.yaml, writes a run record
    evaluate.py
  configs/train.yaml
  tests/
    test_data.py       # schema, ranges, missing values
    test_model.py      # accuracy above a floor, invariance checks
  models/              # outputs, not in Git
  requirements.txt
  README.md

Chapter summary

  1. MLOps versions, tests, deploys, monitors and retrains ML systems. It adds data and model concerns to DevOps.
  2. The lifecycle loops: problem, data, train, evaluate, register, deploy, monitor, retrain. Levels 0, 1 and 2 automate more of it.
  3. Fix random seeds, report the spread over several seeds, and save a run record with data fingerprint, parameters, metrics and versions.
  4. Version data by hash (DVC), models in a registry, code in Git and the environment in requirements or images, so every model has a lineage.
  5. Keep a clean project layout, move notebook code into tested functions, and test data, features, model and infrastructure.
