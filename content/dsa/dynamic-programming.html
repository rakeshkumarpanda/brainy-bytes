Part 1

🧠Same question twice? Remember the answer

Dynamic programming solves a big problem by solving smaller versions of it, saving each small answer, and reusing it whenever the same question comes up again. Fibonacci shows why this matters. Plain recursion for fib(n) calls fib(n − 1) and fib(n − 2), and those calls repeat the same work over and over. Watch the red counts grow, then switch on the memo.

Dynamic programming fits when a problem has overlapping subproblems, so the same smaller question is asked many times, and optimal substructure, so the best answer is built from best answers to smaller questions.
fib(n) = fib(n − 1) + fib(n − 2)    plain: about 1.6ⁿ calls    with a memo: 2n − 1 calls
Saving answers inside a recursive function is called memoisation, or the top down style. In Python, @functools.cache adds a memo to a function in one line.
Part 2

🐸Fill a table from the bottom up

Instead of recursing from the top and remembering, you can start from the smallest case and fill a table in order, so every value you need is already there. This is tabulation, or the bottom up style. To count the ways to climb stairs with jumps of 1 or 2, the ways to reach a stair are the ways to reach the two stairs below it, added.

Every dynamic programming solution answers four questions. What does one box mean? Which boxes does it depend on? Which boxes are known at the start? In which order are the boxes filled? For the stairs: ways[i], from ways[i − 1] and ways[i − 2], with ways[0] = 1, filled from 1 up to n.
When a box only needs the last two boxes, two variables can replace the whole table. That turns O(n) space into O(1).
Part 3

🦹Take it or skip it

Many problems come down to one decision per item: take it or skip it. A robber walks down a street and cannot rob two neighbouring houses. At each house there are only two choices. Rob it, and add the best from two houses back. Or skip it, and keep the best so far. The larger of the two is the new best.

best(i) = max( best(i − 1), best(i − 2) + money[i] )
The table gives the best value, not which houses. To recover the choices, walk back from the end and check which option made each box. This walk back works the same way in almost every dynamic programming problem.
Part 4

🪙Coin change done right

In the Greedy chapter, grabbing the biggest coin failed for coins 1, 3 and 4 and the amount 6. Dynamic programming fixes it by solving every amount from 0 up. The best way to make amount a is one coin c plus the best way to make a − c, for whichever coin gives the fewest. Try amounts that cannot be made at all, too.

best(0) = 0    best(a) = 1 + min over coins c ≤ a of best(a − c)
Counting the ways to pay is a different question. To count each mix of coins once, put the coins in the outer loop. With the amounts in the outer loop, 1 + 2 and 2 + 1 would be counted as two different ways.
Part 5

🗺️Walking across a grid

Now the table has two dimensions. You walk from the top left square of a grid to the bottom right, moving only right or down, and every square costs its number. A square can only be entered from above or from the left, so its cheapest total is the cheaper of those two totals plus its own cost. Fill the table row by row.

cost(r, c) = grid(r, c) + min( cost(r − 1, c), cost(r, c − 1) )
Change min to a sum and the same table counts the number of paths instead, which is LeetCode 62 in the Practice section.
Part 6

🎒The 0/1 knapsack

In the Greedy chapter, splitting items made the knapsack easy. When every item must be taken whole or left behind, greedy can miss the best answer. The fix is a table with one row per item and one column per bag size. Each box decides one item for one bag: leave it out and copy the box above, or put it in and add its value to the box above that has room for it.

best(i, w) = max( best(i − 1, w), best(i − 1, w − weight(i)) + value(i) )
Bag of 50 kgGreedy by value per kgDynamic programming
Gold 10 kg 60, silver 20 kg 100, bronze 30 kg 120160220
The table has n × W boxes, where W is the bag size. That is fast for small bags. When W is huge, the table gets huge too, which is why the knapsack is still a hard problem in general.
