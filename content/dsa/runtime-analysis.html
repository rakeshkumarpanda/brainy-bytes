Run Time Analysis

Two programs can give the same answer while one finishes instantly and the other runs for years. Run time analysis predicts which is which before you run anything, for time and for memory. By the end you will read a loop or a recursive function and state its cost with confidence.

Part 1

🧮Why count steps instead of timing

Timing a program with a stopwatch tells you about one machine, one language, one input and one moment. Change any of these and the number changes. We want a measure that belongs to the algorithm itself.

So we count basic operations: an assignment, a comparison, an arithmetic step, reading an array element, a function call or return. In the RAM model (random access machine) each basic operation costs one unit of time, and any memory cell can be read in one step. The count is written as a function of the input size n.

The count is exactly T(n) = n + 2 The "+ 2" barely matters once n is large, and a different machine would only multiply every step by some constant. What remains is the shape: the work grows in step with n.

Run time analysis asks one question: as n grows, how fast does the number of steps grow? Constants and small terms are ignored because they do not change that answer.

From best to worst: 1 < log n < √n < n < n log n < n² < n³ < 2ⁿ < n!

The base of the logarithm does not matter inside Big O, because log₂ n = log₁₀ n ÷ log₁₀ 2 and dividing by a constant is ignored. Computer scientists usually mean log₂.
Doubling n adds one step to a logarithmic algorithm, doubles a linear one, multiplies a quadratic one by four, and squares the work of an exponential one.
Part 3

🔣Big O, Big Omega and Big Theta

Asymptotic notation compares how two functions grow when n becomes large. Here f(n) is the step count and g(n) is a simple reference such as n².

NotationMeaningFormal definition
f(n) = O(g(n))upper bound: f grows no faster than gthere exist c > 0 and n₀ with 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀
f(n) = Ω(g(n))lower bound: f grows at least as fast as gthere exist c > 0 and n₀ with f(n) ≥ c·g(n) ≥ 0 for all n ≥ n₀
f(n) = Θ(g(n))tight bound: same growthboth O(g(n)) and Ω(g(n)): c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀
f(n) = o(g(n))strictly slower growthf(n) ÷ g(n) → 0 as n → ∞
f(n) = ω(g(n))strictly faster growthf(n) ÷ g(n) → ∞ as n → ∞

A worked proof

Claim: 3n² + 5n + 2 = O(n²) We need constants c and n₀. Try c = 4:

3n² + 5n + 2 ≤ 4n² ⟺ n² − 5n − 2 ≥ 0

The positive root of n² − 5n − 2 is about 5.37, so the inequality holds for every n ≥ 6. With c = 4 and n₀ = 6 the claim is proved. For the lower bound, 3n² + 5n + 2 ≥ 3n² for all n ≥ 1, so it is also Ω(n²), and therefore Θ(n²).

A common mix-up. Big O is not the same thing as "worst case". Big O is an upper bound on a function. The worst case running time, the best case running time and the average running time are three different functions, and each one can be described with O, Ω or Θ.
If an algorithm is O(n), it is also O(n²) and O(2ⁿ), since those are still upper bounds. When people say "the complexity is O(n)" they mean the tightest bound, which is really Θ(n).

Part 5

🎲Best, worst, average and amortized

CaseQuestion it answersLinear search on n items
Bestthe luckiest input of size ntarget first: 1 check, Θ(1)
Worstthe unluckiest input of size ntarget last or missing: n checks, Θ(n)
Averagethe expected cost over a stated distribution of inputs(n + 1) ÷ 2 checks if every position is equally likely, Θ(n)
The worst case is the most useful by default. It is a guarantee: the algorithm never does worse, whatever input arrives.

Amortized analysis

Some operations are usually cheap and occasionally expensive. Amortized analysis spreads the rare expensive cost over the whole sequence. A dynamic array that doubles its capacity when full copies all its elements on those rare appends, yet the total cost of n appends stays below 3n.

The copies add up to 1 + 2 + 4 + … < 2n so the cost per append is O(1) amortized, even though a single append can cost O(n).

Amortized is not the same as average case. Average case depends on random inputs. Amortized cost is guaranteed for every sequence of operations.
Part 6

💾Space complexity

Space complexity measures how the memory an algorithm uses grows with n. It has two parts:

Total space = input space + auxiliary space

Input space

The memory that holds the input itself, such as the n elements of the array you were given.

Auxiliary space

The extra memory the algorithm creates: variables, new arrays, hash maps, and the call stack used by recursion.

Every program also needs a fixed part (code, constants, a few simple variables) that does not depend on n. It counts as O(1).

Trading space for time

Extra memory often buys speed. Finding a duplicate by comparing all pairs needs no extra structure but O(n²) time. Remembering what you have seen in a hash set needs O(n) extra space but only O(n) time.

ApproachTimeAuxiliary space
Compare every pairO(n²)O(1)
Sort first, then check neighbours (in place heap sort)O(n log n)O(1)
Hash set of seen valuesO(n) averageO(n)
Part 7

🧰Auxiliary space in depth

When someone asks for the space complexity of an algorithm, they almost always mean its auxiliary space. The input has to be stored anyway, so including it would make every algorithm at least O(n) and hide the real differences.

An algorithm is in place when its auxiliary space is O(1), or O(log n) by some definitions that allow a small recursion stack.

Things that count as auxiliary space

  • New arrays, lists, strings, maps and sets the algorithm builds.
  • Copies, such as slices a[:mid] in Python or Arrays.copyOfRange in Java.
  • The call stack: every active recursive call keeps a frame with its parameters and local variables. A recursion that goes d levels deep uses O(d) space, even if each frame is small.
Sorting algorithmTime (worst)Auxiliary spaceIn place
Bubble, insertion, selectionO(n²)O(1)yes
Heap sortO(n log n)O(1)yes
Quick sortO(n²), O(n log n) averageO(log n) stack on average, O(n) worstyes, by the relaxed definition
Merge sort (arrays)O(n log n)O(n) bufferno
Counting sortO(n + k)O(n + k)no

For 16 items the largest buffer holds all 16 values, which is O(n), and the recursion goes 5 levels deep, which is log₂ 16 + 1 = 5 The buffer dominates, so merge sort on arrays needs O(n) auxiliary space.

Part 8

🌳Recurrences and the recursion tree

A recursive function's cost is described by a recurrence: the cost for n written in terms of the cost for smaller inputs. For merge sort:

T(n) = 2T(n/2) + n, T(1) = 1

The recursion tree method

Draw every call as a node. Write the non-recursive work beside each node, add up each level, then add up the levels. For merge sort each level does n work in total, and halving n reaches 1 after log₂ n levels:

T(n) = n + n + … + n (log₂ n levels) = n log₂ n = Θ(n log n)
RecurrenceTypical algorithmSolution
T(n) = T(n − 1) + 1factorial, walking a linked list recursivelyΘ(n)
T(n) = T(n/2) + 1binary searchΘ(log n)
T(n) = 2T(n/2) + 1visiting every node of a balanced treeΘ(n)
T(n) = 2T(n/2) + nmerge sortΘ(n log n)
T(n) = T(n − 1) + nselection sort written recursivelyΘ(n²)
T(n) = 2T(n − 1) + 1towers of Hanoi, all subsetsΘ(2ⁿ)
T(n) = T(n − 1) + T(n − 2) + 1plain recursive FibonacciΘ(φⁿ), φ ≈ 1.618

The master theorem

For divide and conquer recurrences of the form T(n) = a·T(n/b) + f(n), a ≥ 1, b > 1 compare f(n) with n^(log_b a) the total work done by the leaves.

CaseConditionResultExample
1. Leaves dominatef(n) grows polynomially slower than n^(log_b a)Θ(n^(log_b a))T(n) = 4T(n/2) + n gives Θ(n²)
2. Balancedf(n) = Θ(n^(log_b a))Θ(n^(log_b a) · log n)merge sort: Θ(n log n). Binary search: Θ(log n)
3. Root dominatesf(n) grows polynomially faster, and a·f(n/b) ≤ k·f(n) for some k < 1Θ(f(n))T(n) = T(n/2) + n gives Θ(n)
Karatsuba multiplication, T(n) = 3T(n/2) + n, falls in case 1: Θ(n^(log₂ 3)) ≈ Θ(n^1.585). That beats the school method's Θ(n²).
Part 9

🥞Recursion depth and the call stack

Every function call pushes a stack frame holding its parameters, local variables and the place to return to. The frame is popped when the call returns. The recursion depth is the largest number of frames on the stack at the same moment, which is the length of the longest root to leaf path in the recursion tree.

Time counts all the calls. Auxiliary space for recursion counts only the calls that are active at the same time: the depth.

Look at fib(10): 177 calls in total, but never more than 10 on the stack at once. Its time is exponential while its stack space is only O(n). Binary search on 1000 items needs just 11 frames, O(log n).

When the stack runs out

LanguageWhat happensTypical limit
PythonRecursionError: maximum recursion depth exceeded1000 frames by default (sys.getrecursionlimit())

A recursive factorial or list walk on a million items will crash with a stack overflow, even though its time is fine. Convert deep linear recursion into a loop, which needs O(1) stack space.
Tail recursion means the recursive call is the very last action. Some languages reuse the frame for it, but Python and Java never do, and among JavaScript engines only Safari does. Do not rely on it. Write the loop yourself.
Part 10

🎯From constraints to complexity

A rough rule: a typical judge or server does about 10⁸ simple steps per second. The input limits then tell you which complexity is acceptable for a one second limit.

Largest nAcceptable complexityTypical technique
about 10O(n!)try all permutations
about 20 to 25O(2ⁿ), O(n·2ⁿ)all subsets, bitmask DP
about 500O(n³)triple loops, Floyd-Warshall
about 5,000 to 10,000O(n²)all pairs, simple DP tables
about 10⁶O(n log n)sorting, heaps, binary search on the answer
about 10⁸O(n)one pass, two pointers, prefix sums
largerO(log n) or O(1)maths formulas, binary search, fast power

The doubling experiment

When the code is too tangled to analyse, measure it. Double n and look at the ratio of step counts: about 2 means linear, about 4 means quadratic, about 8 means cubic, and slightly above 2 means n log n.

The ratios settle just above 2, the signature of n log n. Reading the code confirms it: the outer loop halves i (about log₂ n rounds) and each round runs the inner loop n times.

Hidden costs that trip people up

  • Slicing and copying: a[1:] in Python creates a new list, O(n), not O(1).
  • Membership in a list: x in my_list is O(n). Use a set for O(1) on average.
  • String building: adding to a string in a loop can be O(n²) overall. Collect the pieces and join them once, or use StringBuilder in Java.
  • Removing from the front: list.pop(0) and JavaScript shift() are O(n). Use a deque.
  • Library sorts cost O(n log n) each time you call them. Sorting inside a loop multiplies that.
