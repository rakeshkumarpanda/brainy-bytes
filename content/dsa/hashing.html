Part 1

🗄️Hashing: a locker number for every key

Imagine a school with 100 lockers and a rule that turns any student's name into a locker number. To find Riya's books you do not search all 100 lockers. You run the rule on "Riya" and walk straight to her locker. That rule is a hash function, the locker number is the hash, and the row of lockers is a hash table.

WordWhat it means
Keywhat you look things up by, like a name or a phone number
Hash functionturns a key into a big whole number, always the same number for the same key
Bucketone slot of the table, chosen with hash % m for a table of m slots
Collisiontwo different keys that land in the same bucket

A simple and common string hash mixes the letters one by one: h = h × 31 + code of the letter. Java's String.hashCode uses exactly this formula with 32 bit overflow.

Same key, same hash, every time. Different keys should usually get different hashes, but they are allowed to collide, and with more keys than buckets they must.
Part 2

⛓️Collisions and separate chaining

"cat", "act" and "tac" all landed in bucket 2 above. That is a collision. The pigeonhole principle says it cannot be avoided: put 11 letters into 10 boxes and some box gets two. So a hash table needs a plan for sharing.

Separate chaining lets every bucket hold a small list. To insert, add the pair to the list of its bucket, or update it if the key is already there. To search, hash the key and scan only that one short list. If the key is not in its own bucket, it is nowhere in the table.

⚡ Average case

With n keys spread over m buckets, a chain holds about n / m keys. Keep that ratio small and every operation is O(1) on average.

🐢 Worst case

If every key lands in the same bucket, the table becomes one long list and each operation costs O(n). Java 8 turns a chain of more than 8 entries into a small red black tree to cap the damage at O(log n).

Part 3

🚪Open addressing: find the next free seat

Another plan keeps one key per slot. If your slot is taken, you probe other slots in a fixed order until you find an empty one, like walking along a row of cinema seats until one is free.

ProbingSlots tried for hash hGood and bad
Linearh, h + 1, h + 2, ...friendly to the CPU cache, but keys bunch into long runs (primary clustering)
Quadratich, h + 1, h + 4, h + 9, ...breaks up the runs, may not reach every slot unless the size is chosen carefully
Double hashingh, h + g, h + 2g, ... with a second hash gthe best spread, a little more work per probe
Deleting is tricky. Emptying a slot would cut a probe chain and hide keys behind it. Real tables leave a tombstone marker that searches step over and inserts may reuse.

Python's dict uses open addressing with a perturbed probe sequence. Java's HashMap uses chaining.

Part 4

🎈Load factor and growing the table

The load factor is α = n ÷ m, the number of keys divided by the number of slots. As α rises, chains get longer and probe runs get longer. With linear probing the expected probes for a failed search grow like ½ (1 + 1 ÷ (1 − α)²), which explodes as α gets close to 1.

So tables resize: when α passes a limit, they allocate about twice as many slots and insert every key again, because hash % m changes when m changes. Java's HashMap grows at 0.75, Python's dict at about two thirds.

One resize costs O(n), but doubling makes resizes rare. Spread over all inserts, each insert is still O(1) amortized, the same argument as for dynamic arrays.

🧰Hash maps and sets in everyday code

You rarely build a hash table yourself. Every language ships one, and a handful of patterns solve a huge share of interview and work problems.

🔢 Count things

Word counts, letter counts for anagrams, votes. One pass, one map.

👀 Seen before

Duplicates, cycles, visited nodes in a graph. A set answers "have I met this" in O(1).

💞 Find the partner

Two sum: for each x, look up target − x among the numbers already passed.

🗂️ Group by a key

Group anagrams by their sorted letters, orders by customer, files by size.

In JavaScript a plain object turns every key into a string, so obj[1] and obj["1"] are the same entry. Use Map when keys are numbers or objects.
Part 6

🎯Good hash functions, bad ones and attacks

A good hash function spreads keys evenly and changes a lot when the key changes a little. A lazy one that looks only at the first letter sends "sun", "sea", "sky" and "star" all to the same bucket.

🛡️ Hash flooding

In 2011 researchers showed that a web server could be frozen by sending thousands of form fields whose names all collide. Python (since 3.3) and many others now add a random secret to string hashes each time the program starts, so attackers cannot predict the buckets.

🔑 Keys must not change

If a key's hash changes after it is stored, the table looks in the wrong bucket and the entry is lost. That is why Python refuses lists as dictionary keys, and why Java objects used as keys must keep equals and hashCode consistent.

Java contract: if a.equals(b) then a.hashCode() == b.hashCode(). Equal hash codes do not mean equal objects. Override both or neither.
Part 7

🌍Hashing in real systems

Hash tables are everywhere, and the same idea of a short fingerprint for big data powers many systems you use daily.

⚡ Caches

Websites keep recently computed pages in a map from address to page. Your browser does the same with images. Remembering answers in a map is called memoization, and it turns slow recursive code into fast code.

🔒 Passwords

Sites store a slow, salted hash such as bcrypt or Argon2, never the password itself. At login they hash what you type and compare.

🌿 Git

Every file and commit is named by a cryptographic hash of its content, so identical files are stored once and any change gives a new name.

🧬 Deduplication

Cloud storage hashes uploaded blocks. If a block's hash is already stored, it keeps only a pointer instead of a second copy.

Cryptographic hashes like SHA-256 are designed so nobody can find two inputs with the same hash. Hash table hashes only need to be fast and well spread.
