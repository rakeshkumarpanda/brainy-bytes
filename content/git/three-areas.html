The three areas of a Git project

Picture a photo studio. The stage is where you place the people who should be in the next photo. The camera takes the photo and puts it in the album. People can walk around the studio without being in the photo.

AreaAlso calledWhat it holdsStudio picture
Working treeworking directoryThe files you see and edit in your folderthe studio floor
Staging areathe indexThe exact snapshot your next commit will savethe stage
Repository.git directory, HEADEvery commit ever madethe album
  1. editchange files in the working tree
  2. git addcopy the change to the staging area
  3. git commitsave the staging area as a new commit
  4. git pushsend commits to a remote, covered in step 4

Why have a staging area at all? Because you often change several things at once. Staging lets you commit the bug fix now and the half done feature later, as two clean commits instead of one messy one.

Common mistake
git commit saves what is staged, not what is in your file. If you edit a file after git add, the newer edit is not in the commit until you add it again.

File states and git status

Every file in your folder is either tracked (Git knows it from the last snapshot or the index) or untracked (new, Git has never seen it). Tracked files are unmodified, modified or staged.

StateMeaningHow it gets thereShort code
UntrackedNew file Git is not watchingYou create it??
UnmodifiedSame as the last commitAfter a commit or checkout(not listed)
ModifiedChanged, not stagedYou edit a tracked file M
StagedChange is in the indexgit addM or A
Staged and modified againIndex has one version, the folder a newer oneedit after git addMM
Short statusExam favourite
git status -s → XY path
X compares the index with HEAD (what is staged). Y compares the working tree with the index (what is not staged yet). ?? means untracked.
Long status
git status
Lists staged changes, unstaged changes and untracked files, with the command to undo each.
Read the short status
git status -s
What you will see
 M README.md
MM app.py
 D old.txt
A  new.py
?? notes.txt
Read each line
  1. README.md has a space then M: changed in the folder, nothing staged.
  2. app.py has MM: one change staged, and another change made after that.
  3. old.txt has D in the second column: deleted from the folder but not staged.
  4. new.py has A: a new file added to the index.
  5. notes.txt has ??: untracked, git add notes.txt to start tracking it
Lesson 3 of 4

Adding and committing well

StageExam favourite
git add <file>, git add ., git add -p
git add . stages everything under the current folder. -p asks about each changed piece (hunk) so you can stage part of a file.
CommitExam favourite
git commit -m "message"
Saves the staging area. Without -m Git opens your editor for a longer message.
Stage tracked files and commit
git commit -am "message"
-a stages every change to tracked files first. New untracked files are not included.
Remove and rename
git rm <file>, git mv <old> <new>
Changes the folder and stages the change in one step. git rm --cached keeps the file on disk but stops tracking it.
Two clean commits from one messy afternoon

A good commit message

RuleGoodBad
Short summary line, about 50 charactersFix crash when the password is emptyfixed stuff
Imperative mood, as if giving an orderAdd search by priceAdded search, adding search
Blank line, then the why in the bodyUsers saw a 500 error on empty input...(nothing)
One logical change per commitOne bug fixBug fix plus renaming plus new feature
Remember
Conventional Commits is a popular format: feat: add search by price, fix: handle empty password, docs: update README. Tools read it to make changelogs and choose the next version number.
Real world scenario: the 2 a.m. bug hunt

A shop site breaks at night. The on call developer runs git log and sees "Fix rounding of discount prices" from yesterday. One command, git show, displays the exact lines. Twenty minutes later the cause is found. With a message like "update" and a commit that touched forty files, the same search takes hours.

Lesson 4 of 4

From intuition to research

One idea, four depths

Your folder is your desk. The staging area is a tray where you put the pages you want to send. A commit is putting the tray in an envelope with a note and filing it forever.

The index is a binary file, .git/index, that lists every tracked path with its blob id, mode and file metadata. git add writes blobs and updates the index. git commit turns the index into tree objects and makes a commit that points to the top tree and to its parent.

Because the index caches file size and modification time, git status can skip hashing unchanged files, which keeps it fast on large repositories. During a merge the index can hold up to three versions of a path (stages 1, 2 and 3 for base, ours and theirs), which is how Git tracks a conflict.

Studies of commit history show that tangled commits, which mix unrelated changes, hurt tools that find the commit that caused a bug and tools that predict defects. Research tools try to untangle such commits automatically, which is one reason the habit of small commits matters beyond style.

Going deeper: git add -p in practice

Git shows one hunk at a time and asks Stage this hunk [y,n,q,a,d,s,e,?]. y stages it, n skips it, s splits it into smaller hunks, e lets you edit the hunk by hand, q quits. Afterwards git diff --staged shows what is staged and git diff what is left.
