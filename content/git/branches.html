Lesson 1 of 4

A branch is just a movable label

In many old tools a branch meant copying the whole project into a new folder. In Git a branch is tiny: a file inside .git/refs/heads/ that holds one commit id, 41 bytes. Creating a branch is instant because nothing is copied.

Think of a bookmark in a book you are writing. The book is the chain of commits. The bookmark called main sits on the last page you wrote. When you write a new page with the bookmark in your hand, the bookmark moves to the new page. HEAD is the answer to "which bookmark am I holding right now?".

Create
git branch <name> [<start>]
Makes a new pointer at HEAD, or at start. You stay where you are.
SwitchExam favourite
git switch <name>
Moves HEAD to that branch and updates your files to its snapshot.
Create and switchExam favourite
git switch -c <name>
The same as the older git checkout -b <name>.
See branches
git branch -vv, git branch -a
-vv shows the tip commit and the upstream of each branch, -a adds remote tracking branches.
Remember
Only the branch HEAD points to moves when you commit. Other branches stay exactly where they are. That is the whole trick behind parallel work.
Lesson 2 of 4

switch, checkout and what happens to your files

Git 2.23 split the old all in one git checkout into two clearer commands: git switch for branches and git restore for files. checkout still works and you will see it in older guides.

JobNewer commandOlder command
Go to a branchgit switch featuregit checkout feature
Create a branch and go to itgit switch -c featuregit checkout -b feature
Go back to the previous branchgit switch -git checkout -
Look at an old commitgit switch --detach a1b2c3dgit checkout a1b2c3d
Throw away edits in a filegit restore app.pygit checkout -- app.py

When you switch, Git rewrites the files in your folder to match the other branch. Uncommitted changes come along if they do not clash. If a change would be overwritten, Git refuses:

Git protects uncommitted work
git switch main
What you will see
error: Your local changes to the following files would be overwritten by checkout:
        app.py
Please commit your changes or stash them before you switch branches.
Aborting
Common mistake
Commit or stash (chapter 3.2) before switching when Git complains. Never fix it with a hard reset unless you really want to lose the edits.
Lesson 3 of 4

Detached HEAD, without fear

Normally HEAD points to a branch, and the branch points to a commit. If you check out a commit id or a tag directly, HEAD points straight at the commit. That is detached HEAD. You can look around, build and even commit. But new commits belong to no branch, so when you switch away they are only reachable through the reflog, and Git will eventually clean them up.

Detached HEAD, then save the work
git switch --detach v1.0# try something, commit itgit commit -am "experiment"# keep it: give it a branch namegit switch -c experiment
What you will see
HEAD is now at 3f2a9c1 Release 1.0
[detached HEAD 8d1e004] experiment
Switched to a new branch 'experiment'
Typical reasons to be detached
  1. Testing an old release to see if a bug was already there.
  2. git bisect checks out commits for you in this state.
  3. CI systems often check out the exact commit, so jobs run with a detached HEAD.
  4. Fix: git switch -c name keeps the commits, git switch main leaves them behind
Remember
If you already left the detached commits, run git reflog, find the id, and run git branch rescue <id>.
Lesson 4 of 4

Naming, renaming and deleting branches

Rename
git branch -m <old> <new>
With one name it renames the current branch.
Delete safelyExam favourite
git branch -d <name>
Refuses if the branch has commits not merged into the current branch or its upstream.
Force delete
git branch -D <name>
Deletes even unmerged work. The commits survive in the reflog for a while.
Merged or not
git branch --merged, --no-merged
Lists branches whose tips are (or are not) contained in HEAD. Good for clean up.
Naming habitExample
type and short descriptionfeature/search-by-price, fix/login-crash
ticket numberfeature/SHOP-142-search
no spaces, lowercase, dashesrelease/2.4
One idea, four depths

A branch is a sticky note with a name on one page of the history. Making one is free. You can have as many as you like and throw them away when the work is merged.

A branch is a ref under refs/heads. HEAD is a symbolic ref, usually "ref: refs/heads/main". Committing creates a commit whose parent is the old tip and updates the ref HEAD points to.

Refs may be loose files or lines in .git/packed-refs. Updates are atomic: Git writes a lock file and renames it. Branch names are restricted by git check-ref-format (no spaces, no .., no ~ ^ : ? * [).

The reftable backend stores refs in a binary sorted table, which scales to millions of refs and fixes problems such as two names that differ only in case on case insensitive file systems. The Git project plans to make it the default for new repositories in Git 3.0.

Real world scenario: the long lived branch

A team keeps a branch called new-design open for four months. When they finally merge, hundreds of files conflict. Short branches that merge within days avoid this, which is why most teams aim for small pull requests.
