Refs and HEAD are small text files

Objects have ugly ids, so Git keeps refs: names that hold an id. A branch is a ref under refs/heads/, a tag under refs/tags/, and what you last fetched under refs/remotes/. HEAD usually does not hold an id. It holds the name of a branch, which makes it a symbolic ref.

Common mistake
Never edit ref files with a text editor. Use git update-ref, which writes safely, checks the old value if you ask and records the change in the reflog.
Going deeper: reftable

Thousands of loose ref files are slow on some file systems and cannot be updated atomically as a group. The reftable format, added in Git 2.45 with git init --ref-format=reftable, stores all refs in a few sorted binary files. The plans for Git 3.0 make it the default. Commands do not change, which is one more reason to use git update-ref rather than touching files.

add and commit done by hand

Commands like add and commit are porcelain: friendly commands for people. Each is built from plumbing commands that do one small step. Running the steps yourself shows exactly what a commit is.

The index (.git/index) is a binary file that lists every tracked path with its mode, blob id and a stage number. Stage 0 is normal. During a merge conflict one path has stages 1 (base), 2 (ours) and 3 (theirs), which is how git status knows what is unmerged.

In the exam
Plumbing output is stable and meant for scripts. Porcelain output such as git status can change between versions, so scripts should use plumbing or the --porcelain options.

Packfiles, deltas and garbage collection

A new object is first written as a loose object: one zlib file per object. That is fast to write but wasteful when there are thousands. git gc, which Git also runs automatically now and then, bundles them into a packfile. Inside a pack, an object that is similar to another can be stored as a delta: instructions to copy parts of a base object plus the few new bytes.

Common mistake
Commits you can still see in the reflog are reachable from it, so gc keeps them until the reflog entry expires (90 days by default, 30 for entries that are not reachable from the branch). That is the safety net from chapter 3.1. --prune=now on a repository you care about removes that net for loose objects nothing points to.

Real world scenario: CI clones and the .git folder

CI runners clone the repository for every job. With actions/checkout the default is fetch-depth: 1, a shallow clone of one commit, which is fast but has no history. A job that runs git describe, counts commits for a version number, or diffs against main then fails with a confusing error. The fix is fetch-depth: 0 for the full history, or fetching just the refs you need. GitLab sets the clone depth with the GIT_DEPTH variable for the same reason.

One idea, four depths

Branches and HEAD are tiny files with ids or names in them. The index is the list for the next commit. Git packs many objects into one file to save space and throws away what nothing points to.

Refs live in refs/ or packed-refs, HEAD is a symbolic ref. Porcelain is built on plumbing: hash-object, update-index, write-tree, commit-tree, update-ref. gc packs, fsck checks, unreachable objects are pruned after the grace period.

Packs hold objects as zlib data or deltas against a base, with an .idx for lookup and a .rev for reverse lookup. Delta choice uses heuristics on type, name and size, not history order, so a delta can point backward in time.

Large hosts add commit-graph files, multi-pack indexes, bitmaps and reftable to answer reachability questions quickly. Research on Git storage studies delta selection and how partial clone and protocol version 2 reduce what a client downloads.
