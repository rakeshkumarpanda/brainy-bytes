Baby steps: an empty project to a green pipeline

The same calc-app project runs on GitLab with one file, .gitlab-ci.yml. GitLab.com provides instance runners, so you do not install anything on a server. Tick each step as you finish it.

Download calc-app-starter.zip and unzip it, then run the unit tests once as in chapter 7.2: python -m venv .venv, pip install -r requirements.txt, python -m pytest -q tests/unit. You should see 5 passed.

On gitlab.com select New project, then Create blank project. Name it calc-app and clear the option to initialise the repository with a README, because you will push an existing repository. Select Create project and copy the HTTPS or SSH clone URL.

First push to GitLab
git init -b maingit add .git commit -m "Start calc-app with GitLab CI"git remote add origin https://gitlab.com/YOUR-NAME/calc-app.gitgit push -u origin main

If you already pushed the folder to GitHub in chapter 7.2, add GitLab as a second remote instead: git remote add gitlab URL, then git push -u gitlab main.

In the project, go to Build, Pipelines. A pipeline started as soon as .gitlab-ci.yml arrived on main. Select it to see four stages, lint, test, build and qa, with one job each. Each job log starts by pulling the python:3.13-slim image, then runs the script lines. All four turn green.

On the pipeline page, the Tests tab lists the 5 unit tests and 3 smoke tests read from the JUnit reports. Open the build job: on the right side, Job artifacts offers Download and Browse, and the archive holds dist/calc-app.zip.

Go to Build, Pipeline editor. It shows .gitlab-ci.yml with syntax checks as you type. The Validate tab simulates a pipeline for a branch and lists the jobs it would create, and the Visualize tab draws the stages and needs. Use them before every commit to the file.

A broken branch
git switch -c broken-add# in app/calc.py change: return a + b   to: return a - bgit commit -am "Break add on purpose"git push -u origin broken-add

The push output prints a link to create a merge request. Open it. The workflow rules now run a merge request pipeline for this branch, unit-tests fails, build and smoke-tests do not start, and the merge request shows the failed test test_add from the JUnit report without opening the log.

Change the line back, commit and push. The merge request pipeline runs again and turns green. Merge it, and a branch pipeline runs on main.

Go to Settings, Merge requests, Merge checks and select Pipelines must succeed. Then Settings, Repository, Protected branches: for main set Allowed to merge to Maintainers (or Developers and Maintainers) and Allowed to push and merge to No one. Now every change reaches main through a merge request with a green pipeline.

Go to Build, Pipeline schedules, New schedule. Enter a description, the interval pattern 30 2 * * 1-5, a time zone, and main as the target branch, then save. Each night the pipeline source is schedule, so the nightly-regression job is added and runs the full suite on the build of that pipeline.

What each marked line does and why
  1. Line 1workflow:workflow:rules decide which pipelines exist at all.
  2. Line 3- if: $CI_PIPELINE_SOURCE == "merge_request_event"Merge request pipelines for every merge request.
  3. Line 4- if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTSNo branch pipeline when the branch has an open merge request, which prevents duplicate pipelines.
  4. Line 6- if: $CI_COMMIT_BRANCHBranch pipelines otherwise, including main. Tag pushes create no pipeline.
  5. Line 8stages:The four stages, in order.
  6. Line 15image: python:3.13-slimEvery job runs in this Docker image on the instance runner.
  7. Line 18PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"pip keeps downloads here, inside the project folder, because GitLab can only cache paths inside the project directory.
  8. Line 23- python -m compileall -q appThe cheapest check first.
  9. Line 27cache:Cache pip downloads. The key changes when requirements.txt changes.
  10. Line 35- python -m pytest -q tests/unit --junitxml=reports/unit.xmlpython -m pytest so the project folder is on the import path. The JUnit file feeds the Tests tab.
  11. Line 37when: alwaysKeep the report even when tests fail.
  12. Line 41junit: reports/unit.xmlreports:junit makes GitLab parse the file and show results in the merge request and the Tests tab.
  13. Line 42expire_in: 14 daysReports are short lived. Without expire_in the instance default applies.
  14. Line 48- python -m zipfile -c dist/calc-app.zip appBuild the package once.
  15. Line 50name: "calc-app-$CI_COMMIT_SHORT_SHA"The downloaded archive gets this name, with the short commit id, so files from different pipelines do not get mixed up.
  16. Line 53expire_in: 30 daysKeep the build for 30 days.
  17. Line 57needs:needs with artifacts: true: start right after build and download its artifacts, here dist/calc-app.zip.

In the exam
GitLab uploads artifacts of all jobs and passes them on to jobs in later stages automatically. needs and dependencies control which ones a job downloads. dependencies: [] downloads none, which saves time in jobs that do not need files.
Lesson 3 of 4

What Dev and QA change on GitLab, and why

The same thing, seen by Dev and by QA
Developer view

Goal: quick, cheap feedback on every push and merge request.

  • Use needs so jobs start as soon as their inputs exist.
  • Set interruptible: true so a new push cancels the old pipeline.
  • Cache dependencies with a key on the lock file.
  • Move shared setup into a hidden job with extends.
  • Use protected variables so branches cannot read deploy keys.
QA view

Goal: repeatable evidence about the exact build.

  • Download the build artifact with needs, never rebuild.
  • Split long suites with parallel and CI_NODE_INDEX.
  • Publish JUnit reports so failures show in the merge request.
  • Schedule regression with pipeline schedules and rules on CI_PIPELINE_SOURCE.
  • Keep release builds with longer expire_in or the Keep button.

One idea, four depths

Push a .gitlab-ci.yml and GitLab runs it on its own runners. Use the Pipeline editor to check it first, and make green pipelines a merge rule.

workflow rules pick branch or merge request pipelines, four stages run in order, build keeps calc-app.zip, smoke-tests pulls it with needs, JUnit reports show in merge requests, and a schedule adds the regression job.

Dev tunes speed with needs, interruptible and caches. QA tunes evidence with parallel suites, reports, schedules and retention. Pinning image digests makes runs repeatable.

Large organisations move the shared parts into CI/CD components with versioned inputs, enforce required pipelines through compliance frameworks, and sign build provenance for the artifacts they release.
