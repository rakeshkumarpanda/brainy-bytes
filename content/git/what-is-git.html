Lesson 1 of 5

Why version control exists

Think of writing a school project on a computer. You save it as project.docx, then you are scared to break it, so you save project_v2.docx, then project_final.docx, then project_final_REAL.docx. After a week you have a folder full of copies and no idea which one has the good introduction.

Version control is a tool that remembers every saved version of your files for you, together with who saved it, when, and a short note on why. You keep one folder. The tool keeps the history. You can look at any old version, compare two versions, or undo a mistake, at any time.

Now add a team. Five people edit the same website. Without a tool, they email files around and overwrite each other's work. Version control lets everyone work at the same time and then merges their changes, and it warns when two people changed the same line.

Problem without version controlWhat version control gives you
Many copies with confusing namesOne folder, a clean history of saved snapshots
No idea what changedAn exact list of changed lines between any two versions
A mistake ruins the only copyGo back to any earlier version
Two people overwrite each otherSeparate branches that are merged with checks
Nobody knows why a line existsEvery change carries an author, a date and a message
Real world scenario: Google Docs version history

If you have opened File, Version history in Google Docs, you have used a simple version control system. Git does the same for whole folders of code, with much more control: you decide when a version is saved, you write the note, and you can keep several lines of work going at once.

Where Git came from and how it is different

Version control systems came in three waves.

KindExamplesWhere the history livesWeak spot
LocalRCSOne computerNo teamwork, one disk failure loses everything
CentralisedCVS, Subversion (SVN), PerforceOne central serverServer down means nobody can commit or read history
DistributedGit, MercurialEvery clone has the full historyMore ideas to learn at the start

Git was written by Linus Torvalds in 2005 for the Linux kernel. The kernel team had used a closed tool called BitKeeper for free, and when that free licence ended they needed a replacement. The goals were speed, a simple design, strong support for thousands of parallel branches, being fully distributed, and handling a project as big as Linux. Today Git is the most widely used version control system, and GitHub, GitLab and Bitbucket are all built around it.

Snapshots, not lists of differences

Older tools store a file plus a list of changes to it. Git thinks differently. Every time you commit, Git takes a snapshot of what all your files look like at that moment and stores a reference to it. If a file did not change, Git does not store it again. It just points to the copy it already has.

Going deeper: Three promises Git keeps

Almost everything is local. Your clone has the whole history, so log, diff and commit read your own disk and are fast, even on a plane.

Git has integrity. Everything is identified by a checksum (a SHA-1 hash today) of its content. You cannot change a file, a folder or an old commit without Git noticing, because the name would change.

Git generally only adds data. Almost every action adds to the database. Once something is committed it is very hard to lose, especially if you push it somewhere else too.

Install Git and tell it who you are

Git runs on Windows, macOS and Linux. Install it, then check the version.

SystemHow to install
WindowsDownload Git for Windows from git-scm.com. It includes Git Bash, a terminal where every command on these pages works.
macOSRun git --version. If Git is missing, macOS offers to install the Xcode command line tools. Homebrew users can run brew install git.
Linux (Debian, Ubuntu)sudo apt install git
Linux (Fedora)sudo dnf install git
Check that Git works
git --version
What you will see
git version 2.43.0

Every commit records an author name and email, so set them once. --global means for every repository of your user account.

First time setup
git config --global user.name "Asha Rao"git config --global user.email "asha@example.com"git config --global init.defaultBranch maingit config --global core.editor "code --wait"# check what Git will use, and from which filegit config --list --show-origin
Set a value for your userExam favourite
git config --global <key> "<value>"
Stored in ~/.gitconfig. Use --local (the default inside a repository) to set it for one repository only.
Which value winsExam favourite
system < global < local
Git reads /etc/gitconfig, then ~/.gitconfig, then .git/config. A later file overrides an earlier one, so the most specific setting wins.
Get help
git help <command> or git <command> -h
The first opens the full manual page, the second prints a short list of options in the terminal.
Remember
init.defaultBranch decides the name of the first branch in new repositories. Git 2.28 added this setting. If it is not set, current Git still uses master and prints a hint, and the Git project has said that new repositories will use main by default in Git 3.0.
Remember
Using a work laptop for personal projects? Set your personal email globally and your work email with git config user.email inside each work repository. The local value wins there.

Your first repository in two minutes

A repository (repo) is a project folder that Git watches. The history lives in a hidden folder called .git inside it. Delete that folder and the files stay, but the history is gone.

Make a repository and the first commit
mkdir shop && cd shopgit initecho "# Shop" > README.mdgit statusgit add README.mdgit commit -m "Add README"git log --oneline
What you will see
Initialized empty Git repository in /home/asha/shop/.git/
On branch main
No commits yet
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md
[main (root-commit) 1a2b3c4] Add README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
1a2b3c4 (HEAD -> main) Add README
  1. git initcreates the .git folder, an empty history
  2. edit filesyour normal work in any editor
  3. git addchoose which changes go in the next snapshot
  4. git commitsave the snapshot with a message
  5. git logread the history

The short id 1a2b3c4 will be different on your computer, because it is a hash of the content, the author and the time. That is normal.

Common mistake
Running git init in the wrong folder, for example your whole home folder, makes Git track everything. If that happens, delete the new .git folder in that place. Your files are not touched.
What you can do with these five commands
  1. Save versions of any text project: code, notes, a book, configuration files.
  2. See exactly what changed with git diff before you commit.
  3. Go back to an older version when you break something.
  4. Together with git push, keep a backup of the whole history on GitHub or GitLab
Lesson 5 of 5

From intuition to research

One idea, four depths

Git is a time machine for a folder. Every time you press save in Git, called a commit, it takes a photo of all your files and writes a note on the back. You can flip back through the photos whenever you like, and friends can work on their own copies and later put the work together.

Git is a distributed version control system. A repository holds a directed acyclic graph of commits, each one a full snapshot of the project tree identified by a cryptographic hash. Clones are complete, so most work is offline, and collaboration means exchanging commits between repositories.

Git is a content addressable object store (blobs, trees, commits, annotated tags) plus a set of references. Storage is deduplicated by hash and packed with delta compression. Merges are three way, based on the merge base of the commit graph. Integrity follows from hashing: a commit id fixes its whole history, a Merkle tree structure.

Open questions and current work include the move from SHA-1 to SHA-256 object names with interoperability between the two, the reftable format for references in very large repositories, partial clone and sparse checkout for monorepos, and merge algorithms. Research on mining software repositories uses Git histories to study how developers work and where bugs come from.

Real world scenario: the Linux kernel

The kernel has well over a million commits from thousands of people. No central server decides anything. Maintainers pull from each other's repositories, and Linus pulls from his lieutenants. That is the distributed model working at the largest scale.

In the exam
Git and GitHub are not the same thing. Git is the tool on your computer. GitHub, GitLab and Bitbucket are websites that host Git repositories and add pull requests, issues and CI/CD pipelines.
