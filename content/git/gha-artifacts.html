Lesson 1 of 4

Publishing artifacts: upload-artifact

An artifact is a file or folder that a job saves at the end so that later jobs, people and other workflows can use it. On GitHub you publish it with actions/upload-artifact.

upload-examples.yml
- name: Publish the build  id: up  uses: actions/upload-artifact@v7  with:    name: calc-app    path: |      dist/calc-app.zip      !dist/**/*.tmp    if-no-files-found: error    retention-days: 30- run: echo "Artifact ${{ steps.up.outputs.artifact-id }} at ${{ steps.up.outputs.artifact-url }}"
What each marked line does and why
  1. Line 5name: calc-appThe name later downloads use. It must be unique within the run.
  2. Line 6path: |One or more paths, wildcards allowed. A line starting with ! excludes files.
  3. Line 9if-no-files-found: errorerror, warn (the default) or ignore when nothing matches.
  4. Line 10retention-days: 30Days to keep it, from 1 up to the repository or organisation limit (90 by default). Without it the repository setting applies, 90 days by default.
  5. Line 11- run: echo "Artifact ${{ steps.up.outputs.artifact-id }} at ${{ steps.up.outputs.artifact-url }}"Outputs: artifact-id for the REST API, artifact-url for people, artifact-digest (SHA-256) to check the content.
FactDetail
ImmutableSince version 4 an artifact cannot be changed after upload. Uploading the same name twice in one run fails, unless you set overwrite: true, which deletes the old one and gives a new id.
ZippedBy default the files are zipped. archive: false uploads one file as it is.
Hidden filesFiles and folders starting with a dot are skipped unless include-hidden-files: true, so .env files are not leaked by accident.
PermissionsZipped artifacts lose file permissions: files become 644, so an executable bit is lost. Put a tar file inside if you need it.
LimitsAt most 500 artifacts per job. Storage counts against the account quota.
Common mistake
A matrix job that uploads with a fixed name fails from the second combination on, because names must be unique. Add the matrix values: name: report-${{ matrix.os }}-${{ matrix.python }}.

Pulling artifacts: five ways

"Pulling" an artifact means getting the file back. Who needs it and from where decides the method.

WhoFrom whereHow
A later jobthe same runactions/download-artifact with name, plus needs on the uploading job
A job in another workflowanother run, same repositorydownload-artifact with github-token, run-id (and repository), or gh run download
A personany runthe Artifacts section at the bottom of the run summary page
A person or script with a terminalany rungh run download <run-id> -n calc-app -D dir
Any toolany runthe REST API: list, then download the zip
download-examples.yml
# 1. Same run: one artifact into a folder- uses: actions/download-artifact@v8  with:    name: calc-app    path: dist# 2. Same run: every report of a matrix, into one folder- uses: actions/download-artifact@v8  with:    pattern: report-*    merge-multiple: true    path: reports# 3. Another run or repository: needs a token with actions read access there- uses: actions/download-artifact@v8  with:    name: calc-app    github-token: ${{ secrets.GH_PAT }}    repository: OWNER/calc-app    run-id: 1234567890
What each marked line does and why
  1. Line 4name: calc-appWithout path the files land in the working directory.
  2. Line 9pattern: report-*pattern selects several artifacts by name.
  3. Line 10merge-multiple: truemerge-multiple puts their files in one folder instead of one folder per artifact.
  4. Line 16github-token: ${{ secrets.GH_PAT }}By default download-artifact only sees the current run. A token opens other runs.
  5. Line 18run-id: 1234567890The run id is the number in the run page URL: /actions/runs/1234567890.
From a terminal with the GitHub CLI
gh run list --workflow ci.yml --branch main --status success --limit 1gh run download 1234567890 -n calc-app -D downloadedls downloaded
What you will see
calc-app.zip
With the REST API (any language, curl shown)
# list artifacts named calc-app, newest firstcurl -H "Authorization: Bearer $TOKEN" \  "https://api.github.com/repos/OWNER/calc-app/actions/artifacts?name=calc-app"# download one by id: GitHub answers with a redirect to a short lived URL, -L follows itcurl -L -H "Authorization: Bearer $TOKEN" -o calc-app.zip \  "https://api.github.com/repos/OWNER/calc-app/actions/artifacts/ARTIFACT_ID/zip"
Who pulls artifacts and how
Developer view

Developers mostly use way 1: build uploads, the next job downloads, all inside one run. They also grab an artifact from a failed pull request run to reproduce a bug locally.

QA view

QA uses ways 2 to 5: a scheduled regression workflow pulls the last green build with gh run download, testers download builds from the run page, and test management tools use the REST API to attach reports to test cycles.

In the exam
Artifacts are for files of one run, kept for a limited time. For a release that users install, publish it to GitHub Releases or GitHub Packages, which keep it until you delete it.
Lesson 3 of 4

Caching dependencies: actions/cache

A cache stores files that are slow to download or build, such as pip packages, so the next run can restore them. Unlike an artifact, losing a cache only makes a run slower.

cache-example.yml
- uses: actions/setup-python@v7  with:    python-version: '3.13'    cache: pip# the same idea written out by hand with actions/cache- uses: actions/cache@v6  id: pipcache  with:    path: ~/.cache/pip    key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}    restore-keys: |      ${{ runner.os }}-pip-- run: pip install -r requirements.txt
What each marked line does and why
  1. Line 4cache: pipThe easy way: setup-python builds the key from your requirements file for you.
  2. Line 9path: ~/.cache/pipThe folder to save and restore.
  3. Line 10key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}The key changes whenever requirements.txt changes, so a new set of packages gets a new cache.
  4. Line 11restore-keys: |If there is no exact match, take the newest cache whose key starts with this prefix, then pip installs only what is new.
  5. Line 13- run: pip install -r requirements.txtStill run the install. With a cache it is fast, without one it is correct.
RuleDetail
ScopeA run can restore caches from its own branch and from the default branch. A pull request can also use its base branch. Branches do not see each other's caches.
SaveA cache is saved at the end of the job only when the key had no exact hit. An existing key is never overwritten.
Limits10 GB per repository by default. Entries not used for 7 days are removed, and the oldest go first when the limit is reached.
Outputcache-hit is true only for an exact key match.
SecurityWorkflows from low trust triggers such as fork pull requests get read only access to the default branch cache, to prevent cache poisoning.
Common mistake
Never cache secrets or build outputs that must be correct. Caches can be restored from a partial match, so they may hold stale files. If a job must use exactly these files, it needs an artifact, not a cache.

Real world scenario: the expired build

A common support story: a customer reports a bug in last quarter's release, and the team wants the exact binary. The pipeline only uploaded it as an artifact with default retention, so after 90 days it is gone, and a rebuild from the tag pulls newer dependencies and behaves differently. The fix teams adopt is to attach release builds to a GitHub Release or a package registry at tag time, and to record the artifact digest so the file can be verified later.

One idea, four depths

An artifact is a file a job keeps for later, a cache is a shortcut that makes the next run faster. You can download artifacts from the web page, the terminal or the API.

upload-artifact needs a unique name and sets retention. download-artifact pulls from the same run, or from other runs with a token and run-id. actions/cache restores by exact key, then by restore-keys prefixes, within branch scope.

Artifacts are immutable and carry a SHA-256 digest. Caches are never overwritten and are evicted after 7 days unused or beyond 10 GB. Fork triggers get read only cache access to stop poisoning.

Artifact attestations sign a statement that a given workflow run built a file with a given digest, which a consumer can verify before deploying. This is the SLSA provenance idea built into the platform.
