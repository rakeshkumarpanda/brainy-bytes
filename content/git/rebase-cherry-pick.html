Lesson 1 of 4

Rebase: move your work onto a new base

You started a feature from main on Monday. By Wednesday main has new commits. Merging would add a merge commit. Rebasing instead takes your commits, sets them aside, moves your branch to the new tip of main, and replays your commits there one by one. History becomes one straight line, as if you had started today.

Rebase the current branchExam favourite
git rebase <upstream>
Replays the commits of HEAD that are not in upstream on top of upstream.
Continue, skip or stopExam favourite
git rebase --continue, --skip, --abort
After fixing a conflict: git add, then --continue. --abort returns to before the rebase.
Move a range somewhere else
git rebase --onto <newbase> <oldbase> [<branch>]
Takes the commits after oldbase and replays them on newbase.
Update stacked branches too
git rebase --update-refs
Also moves other branches that point at commits being rewritten (Git 2.38 and later).
Common mistake
Rebased commits are copies with new ids, because their parent changed. Anyone who had the old ones now has commits that no longer exist on the branch.
Lesson 2 of 4

The golden rule, and merge versus rebase

Do not rebase commits that exist outside your repository and that people may have based work on. Rebasing your own local branch before you share it is fine. Rebasing main after the team pulled it forces everyone to untangle duplicate commits.

MergeRebase
HistoryTrue record, with merge commitsClean straight line, rewritten
Commit idsUnchangedNew ids for replayed commits
Safe on shared branchesYesNo, only on your own branch
ConflictsSolved once, in the merge commitMay be solved once per replayed commit
Good forBringing a finished feature into mainUpdating your feature branch with main before review
A common, safe habit
git switch feature/searchgit fetch origingit rebase origin/main# fix conflicts if any, run the testsgit push --force-with-lease
Common mistake
After rebasing a branch you already pushed, a normal push is rejected. Use --force-with-lease, never plain --force, and only on a branch that is yours. Chapter 4.1 explains why.
Real world scenario: the pull request that went stale

A reviewer asks Ravi to update his pull request because main moved. He rebases onto origin/main, reruns the tests locally, and force pushes with lease. The pull request shows his three commits neatly on top of the latest main, and the CI checks run again on code that matches what will be merged.

Interactive rebase: tidy your commits before review

git rebase -i HEAD~4 opens a list of your last four commits, oldest at the top. You change the word in front of each line and save.

The todo list Git opens
pick a1b2c3d Add search boxpick b2c3d4e WIPpick c3d4e5f fix typo in searchpick d4e5f6a Add search by price
CommandEffect
pickkeep the commit as it is
rewordkeep the change, edit the message
editstop after this commit so you can amend it or split it
squashmeld into the previous commit and combine the messages
fixupmeld into the previous commit and throw this message away
dropremove the commit
(change the order of lines)reorder the commits
Prepare a fixup now, squash laterExam favourite
git commit --fixup=<commit> then git rebase -i --autosquash <base>
The fixup! commit is moved next to its target and marked fixup automatically.
Remember
Interactive rebase rewrites history. Use it on commits that only you have, usually right before opening or updating a pull request.
Lesson 4 of 4

Cherry-pick: copy one commit

git cherry-pick <commit> applies the change of one commit on top of your current branch as a new commit. It is how a bug fix made on main reaches an older release branch without bringing everything else along.

Copy commitsExam favourite
git cherry-pick <commit>..., git cherry-pick A..B
Each picked commit becomes a new commit with a new id. -x adds "(cherry picked from commit ...)" to the message.
Undo a commit by adding its opposite
git revert <commit>
Covered in chapter 3.1. Safe on shared branches because nothing is rewritten.
One idea, four depths

Rebase is like copying your homework neatly onto a fresh page after the teacher changed the first page. Cherry-pick is copying one good paragraph into another notebook.

Rebase and cherry-pick both apply the diff of a commit to a new parent, creating a new commit. Rebase does it for a range and then moves the branch. Rebase skips commits whose change is already upstream.

Git detects already applied changes by patch id, a hash of the diff ignoring line numbers and whitespace. rebase --onto takes three points: new base, old base (exclusive) and branch. Rebase by default drops merge commits, and --rebase-merges recreates them.

Rewriting public history breaks the assumption that a commit id names a stable history. Tools like git range-diff compare two versions of a patch series, which is how mailing list based projects such as Git itself review rebased series.
