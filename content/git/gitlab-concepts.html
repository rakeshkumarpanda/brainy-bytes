Lesson 1 of 4

One file, stages and jobs

GitLab reads one file, .gitlab-ci.yml, at the root of the repository. Every top level key that is not a reserved keyword is a job. A job needs a script and belongs to a stage. Jobs in the same stage run in parallel, and by default a stage starts only after every job of the previous stage succeeded.

.gitlab-ci.yml
stages:  - build  - test default:  image: python:3.13-slim variables:  APP_NAME: calc-app build-job:  stage: build  script:    - echo "Building $APP_NAME at $CI_COMMIT_SHORT_SHA" test-job:  stage: test  script:    - python --version
What each marked line does and why
  1. Line 1stages:The order of stages. Without this key GitLab uses .pre, build, test, deploy, .post.
  2. Line 5default:default applies settings to every job, here the Docker image each job runs in.
  3. Line 8variables:Variables for all jobs. Read them as $NAME in scripts.
  4. Line 11build-job:A job. The name is yours, it appears in the pipeline graph.
  5. Line 14- echo "Building $APP_NAME at $CI_COMMIT_SHORT_SHA"CI_COMMIT_SHORT_SHA is one of many predefined variables GitLab sets in every job.
KeywordWhereDoes
stagestoporder of stages
defaulttopimage, before_script, after_script, cache, retry and more for every job
variablestop or jobCI/CD variables
workflowtopwhether the whole pipeline is created
includetoppull in YAML from other files, projects, templates or components

artifacts, cachejobfiles to keep and pass on, files to reuse between pipelines
In the exam
script lines run in order, and the job fails at the first command that exits with a non zero code. after_script still runs, but its result does not change the job status.
Lesson 2 of 4

rules, workflow and pipeline types

rules decide if a job is added to a pipeline. GitLab reads them top to bottom and the first rule that matches decides. If none matches, the job is left out. Change the pipeline source and branch in the animation and see which rule wins.

Pipeline typeStarted byUseful variables
Branch pipelinea push to a branchCI_COMMIT_BRANCH (not set in merge request or tag pipelines)
Tag pipelinepushing a tagCI_COMMIT_TAG
Merge request pipelinecreating or updating a merge request, when a job has rules for itCI_PIPELINE_SOURCE == "merge_request_event", CI_MERGE_REQUEST_TARGET_BRANCH_NAME
Scheduled pipelineBuild, Pipeline schedulesCI_PIPELINE_SOURCE == "schedule"
Manual runBuild, Pipelines, New pipelineCI_PIPELINE_SOURCE == "web"
workflow-rules.yml
workflow:  rules:    - if: $CI_PIPELINE_SOURCE == "merge_request_event"    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS      when: never    - if: $CI_COMMIT_BRANCH
What each marked line does and why
  1. Line 1workflow:workflow:rules decide whether a pipeline is created at all, before any job rules.
  2. Line 3- if: $CI_PIPELINE_SOURCE == "merge_request_event"Always run for merge requests.
  3. Line 4- if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTSA push to a branch that already has an open merge request: skip the branch pipeline, because the merge request pipeline covers it.
  4. Line 6- if: $CI_COMMIT_BRANCHEvery other branch push gets a branch pipeline. Tags match no rule, so tag pushes create no pipeline with this block.
Common mistake
Add a rule for merge requests to one job without workflow:rules and a single push to a branch with an open merge request can start two pipelines, a branch pipeline and a merge request pipeline. The workflow block above is the documented fix.
Lesson 3 of 4

needs, parallel, extends and include

Skip waiting for the stageExam favourite
needs: [build]
The job starts as soon as build is done, even if other jobs of the build stage still run. needs: [] starts at once. Up to 50 jobs in one needs list.
Run a job many timesExam favourite
parallel: 3 or parallel: matrix:
parallel: 3 gives jobs 1/3, 2/3, 3/3 with CI_NODE_INDEX and CI_NODE_TOTAL for test splitting. parallel:matrix sets variables, at most 200 combinations.
Reuse a job template
.python-job: then extends: .python-job
Jobs whose name starts with a dot are hidden and never run, so they work as templates.
Split the file
include: local:, project:, remote:, template:, component:
Share one pipeline definition between many projects.
reuse-example.yml
.python-job:  image: python:3.13-slim  before_script:    - pip install -r requirements.txt unit-tests:  extends: .python-job  stage: test  script:    - python -m pytest -q tests/unit e2e:  extends: .python-job  stage: test  needs: [build]  parallel: 3  script:    - python -m pytest -q tests/e2e --shard $CI_NODE_INDEX/$CI_NODE_TOTAL
What each marked line does and why
  1. Line 1.python-job:A hidden job: the leading dot means GitLab never runs it on its own.
  2. Line 7extends: .python-jobCopies image and before_script from the template, then adds its own keys.
  3. Line 15needs: [build]Starts right after build, without waiting for the rest of the stage.
  4. Line 16parallel: 3Three copies of the job run in parallel.
  5. Line 18- python -m pytest -q tests/e2e --shard $CI_NODE_INDEX/$CI_NODE_TOTALEach copy picks its share of tests. The --shard option here belongs to a pytest plugin you would add, it is not built into pytest.

Runners, executors and variables

A runner is the agent that picks up jobs and runs them. On GitLab.com, GitLab hosted instance runners are ready for every project, so you can skip setting up your own. You can still register your own runner for a project or group, for example to reach machines inside your network.

Runner scopeAvailable to
Instanceevery project on the GitLab instance (GitLab hosted runners on GitLab.com are instance runners)
Groupevery project in a group
Projectone project
ExecutorRuns each jobNote
Dockerin a fresh container from the job imagethe most common, clean for each job
Shelldirectly on the runner machinesimple, but jobs share the machine and its leftovers
Kubernetesin a pod in a clusterscales out for many parallel jobs
Project variablesExam favourite
Settings, CI/CD, Variables
Masked hides the value in job logs. Protected passes it only to pipelines on protected branches and tags.
Predefined variables
$CI_COMMIT_SHA, $CI_PROJECT_DIR, $CI_JOB_TOKEN, $CI_API_V4_URL
Set by GitLab in every job.
Pick a runner
tags: [linux, docker]
A job only runs on runners that have all of its tags.
GitLab features each side reaches for
Developer view
  • Uses needs to get feedback faster.
  • Keeps secrets protected so feature branches cannot read production keys.
  • Moves shared setup into a template with extends or include.
QA view
  • Uses parallel to split slow suites across runners.
  • Uses scheduled pipelines and rules on CI_PIPELINE_SOURCE for nightly regression.
  • Keeps test environments in protected variables and uses services for a test database.
One idea, four depths

One YAML file lists stages and jobs, and runners run them. rules decide which jobs appear in each pipeline.

Jobs need script and stage. default, variables, image and services set the environment. rules match top down with when, workflow:rules control whole pipelines and prevent duplicates. needs makes a graph, parallel splits work, extends and include reuse YAML.

Pipeline source, branch, tag and merge request variables drive the rules. Protected and masked variables limit secret exposure. Executors trade isolation against speed.

CI/CD components and the catalog version pipeline building blocks like libraries, with inputs and semantic versions, so many projects can share one tested pipeline definition.
