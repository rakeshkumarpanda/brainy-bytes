In the exam
When asked "how do you undo", first say where the mistake is (working tree, staging area, local commit, pushed commit) and whether others have it. The right command follows from those two facts.

Scenario questions with worked answers

1. You committed to main instead of a feature branch, and have not pushed
  1. The commit exists only locally, so rewriting is safe.
  2. git branch feature/x keeps a pointer to the commit.
  3. git reset --hard HEAD~1 moves main back (no uncommitted work to lose, check git status first).
  4. git switch feature/x and continue. Main is clean, the commit lives on the branch.
2. A bad commit was pushed to main and teammates have pulled it
  1. Shared history must not be rewritten.
  2. git revert <id> creates a new commit that undoes it.
  3. Push it through a pull request so CI checks the revert too.
  4. For a merge commit, revert with -m 1 to keep the main line.
3. git push is rejected with fetch first
  1. Someone pushed commits you do not have, so your push is not a fast forward.
  2. git pull --rebase (or fetch then rebase) puts your commits on top.
  3. Fix conflicts if any, run the tests, then git push.
  4. Never use --force here, it would delete their commits.
4. The pipeline is green on the branch but red after merge
  1. Two changes that each passed can break together (a semantic conflict).
  2. Run CI on the merge result: pull_request runs test the merge commit on GitHub, merged results pipelines do it on GitLab.
  3. Merge queues (GitHub) or merge trains (GitLab) test each change on top of the ones queued before it.
  4. Meanwhile revert the merge on main to get green again.
5. QA reports the build they tested differs from production
  1. Each environment rebuilt from source, so the bytes differ.
  2. Build once, upload the artifact, and promote that file through every environment.
  3. Name artifacts with the commit id and record the digest.
  4. Keep release builds in a release or package registry, not only in expiring artifacts.
6. A secret was committed and pushed an hour ago
  1. Rotate the secret immediately: assume it is leaked.
  2. Remove it from the code and add the file to .gitignore.
  3. If required, rewrite history with a tool such as git filter-repo and coordinate a force push, knowing clones may keep it.
  4. Add secret scanning in a pre-commit hook and in CI.
Lesson 4 of 4

Spot the bug: pipeline files

bug-1.yml
on:  push:    branches: [main]jobs:  test:    runs-on: ubuntu-latest    steps:      - uses: actions/setup-python@v7        with:          python-version: 3.10      - run: python -m pytest
What each marked line does and why
  1. Line 8- uses: actions/setup-python@v7Bug: no actions/checkout before this, so the runner has no code to test.
  2. Line 10python-version: 3.10Bug: unquoted 3.10 is read as the number 3.1. Write '3.10'.
  3. Line 11- run: python -m pytestBug: nothing installed pytest. A fresh Python has no pytest, so add pip install -r requirements.txt first.
bug-2.yml
jobs:  test:    strategy:      matrix:        os: [ubuntu-latest, windows-latest]    runs-on: ${{ matrix.os }}    steps:      - uses: actions/checkout@v7      - run: pytest --junitxml=report.xml      - uses: actions/upload-artifact@v7        with:          name: report          path: report.xml
What each marked line does and why
  1. Line 10- uses: actions/upload-artifact@v7Bug: no if: always(), so the report is lost exactly when tests fail.
  2. Line 12name: reportBug: both matrix jobs upload the name report. The second upload fails. Use report-${{ matrix.os }}.
bug-3.gitlab-ci.yml
stages: [build, test]build:  stage: build  script:    - make disttest:  stage: test  rules:    - if: $CI_PIPELINE_SOURCE == "merge_request_event"    - if: $CI_COMMIT_BRANCH  script:    - ./run-tests dist/app
What each marked line does and why
  1. Line 5- make distBug: no artifacts: paths, so dist/ is lost when the build job ends and the test job cannot find it.
  2. Line 8rules:Bug: rules for merge requests and branches with no workflow:rules, so a push to a branch with an open MR creates two pipelines.
Remember
In exams and reviews, read a pipeline file in this order: triggers, checkout or clone, versions, what each job needs from another job, what is kept, and what runs with which permissions.
