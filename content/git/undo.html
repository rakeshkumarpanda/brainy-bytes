Lesson 1 of 4

Undo at each of the three levels

Every undo answers one question: where is the thing I want to undo? In your files, in the staging area, or already in a commit? And has that commit been shared?

What you want to undoCommandSafe?
Edits in a file you have not stagedgit restore app.pyThe edits are gone for good
A file you staged by mistakegit restore --staged app.pyYes, the edits stay in the file
The message or content of your last commit (not pushed)git commit --amendYes, rewrites one local commit
Your last commits (not pushed)git reset <commit>Yes with --soft or --mixed, careful with --hard
A commit already pushed and sharedgit revert <commit>Yes, adds a new commit, rewrites nothing
Something you reset or deleted by mistakegit reflog then reset or branchUsually rescues it
Common mistake
git restore app.py without --staged overwrites your file from the index. Uncommitted edits it removes are not in any commit, so the reflog cannot bring them back.
Lesson 2 of 4

git reset: soft, mixed and hard

git reset <commit> moves the current branch (and HEAD with it) to another commit. The mode says how much else follows:

ModeMoves the branchResets the indexResets your filesUse it to
--softyesnonoredo the last commits as one: changes stay staged
--mixed (default)yesyesnounstage and recommit differently: changes stay in your files
--hardyesyesyesthrow everything away and match the commit exactly
Undo the last commit, keep the work stagedExam favourite
git reset --soft HEAD~1
Then git commit again, for example to combine two commits.
Undo the last commit, keep the work unstaged
git reset HEAD~1
Same as --mixed.
Discard all local workExam favourite
git reset --hard HEAD
Tracked files go back to the last commit. Untracked files stay. Uncommitted edits are lost.
Fix the last commit
git commit --amend
Replaces the last commit with a new one: new message and anything newly staged.
Common mistake
git reset --hard with uncommitted changes is the most common way people lose work in Git. Run git status and git stash first if in doubt.
Lesson 3 of 4

git revert: undo in public

On a shared branch you cannot remove a commit without rewriting history. git revert instead makes a new commit that does the opposite of the old one. History stays true: it shows the mistake and its undo.

Undo a pushed commitExam favourite
git revert <commit>
Creates "Revert ..." as a new commit. --no-edit keeps the default message.
Undo a merge commit
git revert -m 1 <merge>
-m 1 says parent 1 (the main line) is the side to keep.
Real world scenario: Friday deploy rollback

A release goes out and checkout payments fail. The team does not reset main, because twenty people have pulled it and CI deployed from it. They run git revert on the bad merge commit, push, and the pipeline deploys the reverted code. On Monday they fix the bug properly and, because the revert is a normal commit, they can even revert the revert to bring the feature back.

Lesson 4 of 4

The reflog: your safety net

Every time HEAD moves (commit, reset, switch, rebase, merge, pull) Git writes a line in the reflog. It is local to your clone and is not pushed. It lets you find commits that no branch points to any more.

Rescue after a bad hard reset
git reset --hard HEAD~2# oh no, those two commits were neededgit refloggit reset --hard HEAD@{1}
What you will see
HEAD is now at 51de0f4 Fix typo
51de0f4 HEAD@{0}: reset: moving to HEAD~2
a41f0c2 HEAD@{1}: commit: Add search by price
7c9e1d0 HEAD@{2}: commit: Add search box
51de0f4 HEAD@{3}: commit: Fix typo
HEAD is now at a41f0c2 Add search by price
Going deeper: How long does the reflog keep things?

By default reflog entries for commits that are no longer reachable from any branch expire after 30 days (gc.reflogExpireUnreachable) and other entries after 90 days (gc.reflogExpire). git gc then may delete the unreachable commits. Uncommitted work was never in any commit, so it was never in the reflog either. git fsck --lost-found can sometimes find blobs you once staged with git add.

One idea, four depths

restore is an eraser for your page, reset is moving your bookmark back, revert is writing a new page that says "ignore what page 7 said", and the reflog is a diary of every place your bookmark has been.

reset moves the branch ref and optionally the index and working tree. revert creates an inverse commit. restore copies a file from the index or a commit. The reflog records old values of HEAD and of each branch.

reset with a path (git reset -- file) does not move HEAD: it copies that file's entry from a commit into the index, the opposite of git add. Pro Git calls the three trees HEAD, index and working directory, and every undo command is a copy between them.

Version control research treats history as an append mostly log. Systems that forbid rewriting (for example some audit or regulated environments) rely on revert only, while Git allows rewriting locally and leaves policy to the server, where protected branches block force pushes.
