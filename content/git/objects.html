Four kinds of objects

Under every command you have learned sits a simple database. Git stores everything as objects, and each object is named by the hash of its content. There are only four kinds.

ObjectHoldsPoints to
blobthe bytes of one file, with no name and no permissionsnothing
treeone folder: a list of names, each with a mode and an object idblobs and other trees
commitone tree id, parent ids, author, committer, dates and the messageone tree and zero or more parent commits
tag (annotated)object id, type, tag name, tagger, date and messageusually a commit

Remember
A blob has no file name. The name lives in the tree. That is why renaming a file creates a new tree but reuses the same blob, and why Git detects renames by comparing contents.
Lesson 2 of 4

How an object gets its name

To name an object, Git writes a small header, the type, a space, the size in bytes and a zero byte, puts the content after it and hashes the whole thing with SHA-1. The 40 hex digits are the object id. Type your own content in the animation and watch the id change.

The same id three ways
echo hello > hello.txtgit hash-object hello.txtprintf 'blob 6\0hello\n' | sha1sumgit add hello.txt && find .git/objects -type f
Real output: every computer in the world gets this id for hello
ce013625030ba8dba906f756967f9e9ca394464a
ce013625030ba8dba906f756967f9e9ca394464a  -
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
Hash without storingExam favourite
git hash-object <file>
Add -w to also write the object into .git/objects.
Read any objectExam favourite
git cat-file -t <id>, -s, -p
-t prints the type, -s the size, -p the content in readable form.
Where it is stored
.git/objects/ce/013625...
First 2 hex digits are the folder, the other 38 the file name. The file is zlib compressed.
Short ids
git rev-parse --short HEAD
Any unique prefix works, usually 7 or more digits.
In the exam
The id depends only on the content, never on the file name, date or computer. Ten copies of the same file in a repository are stored once.
Lesson 3 of 4

Why history cannot be changed quietly

A commit holds the id of its tree and the ids of its parents. A tree holds the ids of its blobs and subtrees. So the id of a commit depends on every file and every earlier commit. Change one byte in an old file and every id above it changes, all the way to the newest commit. This structure is a Merkle tree, the same idea used in blockchains and certificate transparency logs.

One byte changes everything above it
  1. You change hello.txt from "hello" to "hallo". The blob id changes.
  2. The tree lists that blob, so the tree content changes and the tree id changes.
  3. The commit lists that tree, so the commit id changes.
  4. Every later commit lists its parent id, so every later commit id changes too.
  5. Anyone comparing the newest commit id with their own copy sees at once that history was changed. This is why rebase and amend always create new ids.
Real world scenario: SHAttered, 2017

In February 2017 researchers from CWI Amsterdam and Google published two different PDF files with the same SHA-1 hash, the first practical SHA-1 collision. Git reacted the same year: since Git 2.13 it uses a hardened SHA-1 implementation (SHA-1DC) that detects the known collision attack and refuses such objects. Git 2.29 added an experimental SHA-256 object format, and the plans for Git 3.0 make SHA-256 the default for new repositories.

A SHA-256 repository
git init --object-format=sha256 democd demo && echo hello > hello.txtgit hash-object hello.txt
Real output: 64 hex digits
2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4
Common mistake
SHA-1 and SHA-256 repositories cannot simply push to each other yet, and some hosting services do not accept SHA-256 repositories. Check your server before you switch.

Annotated tags as objects, and the full picture

An annotated tag is its own object
git tag -a v1.0 -m "Release 1.0"git cat-file -t v1.0git cat-file -p v1.0
Real output
tag
object aa1cc961b5f90c399a85465ec3ca67ad215a0b47
type commit
tag v1.0
tagger Asha Rao <asha@example.com> 1793593800 +0530

Release 1.0

A lightweight tag is only a ref file that holds a commit id. An annotated tag is an object with its own id that points to the commit, which is why it can carry a message and a signature.

One idea, four depths

Git keeps every version of every file as an object, named by a fingerprint of its content. Folders are lists of names and fingerprints, and a commit is a note that points at a folder and at the commit before it.

Four object types: blob, tree, commit, tag. Ids are SHA-1 of the type, the size, a zero byte and the content. Objects are zlib compressed in .git/objects/xx/ and are immutable. Identical content is stored once.

The commit graph is a Merkle DAG, so one id authenticates the whole history below it. A signature on a commit or tag signs exactly that content, so it covers every file through the tree id.

The hash function transition keeps a translation table between SHA-1 and SHA-256 ids so that repositories can interoperate during the change. Research on version control as content addressed storage influenced systems such as IPFS and Nix.
