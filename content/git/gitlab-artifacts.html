Keeping files: the artifacts keyword

artifacts-examples.yml
build:  stage: build  script:    - mkdir -p dist    - python -m zipfile -c dist/calc-app.zip app  artifacts:    name: "calc-app-$CI_COMMIT_SHORT_SHA"    paths:      - dist/    exclude:      - dist/**/*.tmp    expire_in: 30 days    when: on_success    access: developer unit-tests:  stage: test  script:    - python -m pytest -q tests/unit --junitxml=reports/unit.xml  artifacts:    when: always    reports:      junit: reports/unit.xml
What each marked line does and why
  1. Line 7name: "calc-app-$CI_COMMIT_SHORT_SHA"Name of the downloaded archive. Variables are allowed.
  2. Line 8paths:Files and folders to keep, relative to the project folder. Paths outside it are not allowed.
  3. Line 10exclude:Leave out matching files.
  4. Line 12expire_in: 30 daysHow long to keep. Without it the instance default applies, 30 days on GitLab.com. Examples: 1 week, 3 mos, never.
  5. Line 13when: on_successon_success (default), on_failure or always.
  6. Line 14access: developerWho may download: all, developer, maintainer or none.
  7. Line 21when: alwaysalways keeps the report when tests fail, which is when you need it.
  8. Line 23junit: reports/unit.xmlGitLab parses the file and shows results in the merge request and the Tests tab. Reports are stored separately from the archive.
RuleDetail
Latest keptArtifacts from the most recently completed pipeline and the most recent successful pipeline on each branch or tag are kept regardless of expire_in, until a newer pipeline replaces them (a project setting can turn this off).
Keep buttonOn a job page, Keep stops one job's artifacts from expiring.
SizeGitLab.com limits a job's artifacts to 1 GB.
untracked: trueadds every file Git does not track, handy for build folders, risky for secrets.
Common mistake
reports such as junit are not inside the downloadable archive. To keep the XML as a file too, also list it under paths, as the sample project does.
Lesson 2 of 4

Passing artifacts between jobs

By default a job downloads the artifacts of every job in earlier stages. Two keywords narrow that down.

Setting on the jobDownloads
nothingartifacts of all jobs in earlier stages
dependencies: [build]only build's artifacts (build must be in an earlier stage)
dependencies: []nothing, the job starts faster
needs: [build]only build's artifacts, and the job starts as soon as build is done
needs: [{job: build, artifacts: false}]waits for build but downloads nothing
needs: project: OWNER/other, job: build, ref: main, artifacts: trueartifacts of the latest successful build job on main of another project, up to five such jobs (Premium and Ultimate)
Artifacts inside the pipeline
Developer view

The build job uploads one archive, and later jobs in the same pipeline pick it up automatically or through needs. Developers rarely think about it until a job cannot find a file.

QA view

QA jobs use needs: [build] so the tests always run against the build of the same pipeline. A separate QA project can pull the latest green build of the app project with needs:project or with the API and the job token.

Pulling artifacts: UI, API, glab and job token

GitLab gives you several ways to get a build back, from a click to a script in another pipeline.

FromWhere to click
A pipelines listDownload artifacts, then pick the job
A jobs listDownload artifacts next to the job
A job pageDownload or Browse in the Job artifacts panel
A merge requestArtifacts on the Overview page, for the latest pipeline
Build, Artifactsevery artifact in the project, with Download and Browse
REST API: latest successful build on main, by job name
curl --location --header "PRIVATE-TOKEN: $TOKEN" \  --output calc-app.zip \  "https://gitlab.com/api/v4/projects/PROJECT_ID/jobs/artifacts/main/download?job=build"# one file out of the archivecurl --location --header "PRIVATE-TOKEN: $TOKEN" --output calc-app-only.zip \  "https://gitlab.com/api/v4/projects/PROJECT_ID/jobs/artifacts/main/raw/dist/calc-app.zip?job=build"
REST API: a report file from a specific job
curl --location --header "PRIVATE-TOKEN: $TOKEN" --output unit.xml.gz \  "https://gitlab.com/api/v4/projects/PROJECT_ID/jobs/JOB_ID/artifacts?file_type=junit"
The GitLab CLI
glab auth loginglab job artifact main buildglab job artifact main build --path downloaded/
qa-project/.gitlab-ci.yml
pull-latest-build:  stage: test  script:    - apt-get update && apt-get install -y curl unzip    - >      curl --location --fail --header "JOB-TOKEN: $CI_JOB_TOKEN"      --output build.zip      "$CI_API_V4_URL/projects/$APP_PROJECT_ID/jobs/artifacts/main/download?job=build"    - unzip build.zip    - ls dist/
What each marked line does and why
  1. Line 4- apt-get update && apt-get install -y curl unzipThe slim Python image has no curl or unzip, so install them.
  2. Line 6curl --location --fail --header "JOB-TOKEN: $CI_JOB_TOKEN"CI_JOB_TOKEN is created for each job and expires when the job ends. It can call the artifact download endpoints.
  3. Line 8"$CI_API_V4_URL/projects/$APP_PROJECT_ID/jobs/artifacts/main/download?job=build"CI_API_V4_URL is the API root of this GitLab instance. APP_PROJECT_ID is a variable you set to the app project's id.
RuleDetail
ref_namea branch or tag name. For merge request pipelines use refs/merge-requests/IID/head, the variable CI_MERGE_REQUEST_REF_PATH holds it.
Reportsnot in the archive. Use the job id endpoint with file_type=junit, or list the file under paths.
Job tokenthe other project must add the calling project to its CI/CD job token allowlist (Settings, CI/CD, Job token permissions).
--locationGitLab.com may redirect through a CDN, so curl must follow redirects.
In the exam
The finished release belongs in the package registry or a release asset, not in a job artifact that may expire. For example, publish a Python wheel to the project's PyPI registry in a tag pipeline with the CI_JOB_TOKEN.
Lesson 4 of 4

Caching on GitLab

cache-examples.yml
variables:  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip" unit-tests:  cache:    key:      files:        - requirements.txt      prefix: $CI_JOB_NAME    paths:      - .cache/pip    policy: pull-push
What each marked line does and why
  1. Line 2PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"Make pip write its downloads inside the project folder, because only paths there can be cached.
  2. Line 7files:The key is computed from the content of these files, by default up to two files.
  3. Line 9prefix: $CI_JOB_NAMEAn optional prefix keeps separate caches per job.
  4. Line 11- .cache/pipWhat to save and restore.
  5. Line 12policy: pull-pushpull-push (default) restores and saves. pull only restores, push only saves. Many jobs use pull to save upload time.

Keywordartifacts:cache:
One idea, four depths

Artifacts keep the results of a job so others can use them, caches make the next run faster. You can download artifacts from many places in GitLab or with a script.

artifacts: paths, name, when, expire_in, reports. Later stages fetch earlier artifacts, needs and dependencies narrow it. Pull with the UI, the API by ref and job name, glab job artifact, or CI_JOB_TOKEN from another project on the allowlist.

The latest successful artifacts per ref are kept beyond expire_in. Reports live outside the archive and need file_type. Cache keys from files and per job prefixes keep caches correct, policies limit uploads.

Fine grained job token permissions and signed build provenance make cross project artifact flows auditable, which matters when a QA or release project consumes builds from many application projects.
