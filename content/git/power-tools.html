Lesson 1 of 4

git bisect: find the commit that broke it

The tests passed at release v1.0 and fail today, 15 commits later. Reading every diff is slow. git bisect checks out the commit in the middle and asks you whether it is good or bad. Each answer throws away half of the suspects, so even 1000 commits need only about 10 tests.

Bisect by hand
git bisect startgit bisect bad              # the current commit is brokengit bisect good v1.0        # this tag was fine# Git checks out a commit in the middle. Test it, then say:git bisect good             # or: git bisect bad, or: git bisect skip# repeat until Git prints the first bad commitgit bisect reset            # go back to where you started
Let a script do the testing
git bisect start HEAD v1.0git bisect run sh test.sh
Real output, shortened: 4 tests for 15 commits

Remember
Bisect works best when every commit builds and passes tests on its own. Huge commits that mix many changes also make the answer less useful. This is one more reason for small, atomic commits.
Lesson 2 of 4

worktree and submodules

git worktree gives one repository several working folders, each on its own branch. You can fix a bug on a hotfix branch in one folder while a long build or test run continues in another, without stashing or cloning again.

A second folder for a hotfix
git worktree add ../hotfix -b hotfix v1.0git worktree list# when donegit worktree remove ../hotfix
Real output, paths shortened
Preparing worktree (new branch 'hotfix')
HEAD is now at 45a81bb change 1
/work/calc-app  cac7ede [main]
/work/hotfix    45a81bb [hotfix]
Remember
A branch can be checked out in only one worktree at a time. All worktrees share the same .git objects, so a commit made in one is visible in the others at once.

A submodule puts another repository inside yours at a fixed commit, for example a shared library. The parent repository does not store the library files. It stores the library URL in .gitmodules and one commit id for the folder.

.gitmodules
[submodule "libs/shared"]	path = libs/shared	url = https://github.com/OWNER/shared.git
What each marked line does and why
  1. Line 2path = libs/sharedWhere the other repository appears in your working tree.
  2. Line 3url = https://github.com/OWNER/shared.gitWhere to clone it from. The exact commit is stored in the parent commit, not here.
Add and cloneExam favourite
git submodule add <url> <path>, git clone --recurse-submodules <url>
A plain clone leaves submodule folders empty.
After a pullExam favourite
git submodule update --init --recursive
Checks out the commit each submodule is pinned to.
In CI
actions/checkout with submodules: recursive, GitLab variable GIT_SUBMODULE_STRATEGY: recursive
Both platforms skip submodules unless asked.
Going deeper: Submodule or something else

Submodules pin an exact version, which is safe, but every update needs a commit in the parent and every clone needs the extra flag. git subtree copies the other project into a folder as normal files with history, so clones need nothing special. For libraries that have releases, a package manager (pip, npm, Maven) is usually the simplest choice.

Lesson 3 of 4

Hooks: scripts Git runs for you

A hook is a script that Git runs at a fixed moment, such as before a commit is made or before a push is sent. If a pre hook exits with a code other than 0, Git stops the action. Pick a hook in the animation and make it fail.

.git/hooks/pre-commit
#!/bin/sh# Block commits that still contain debug printsif git diff --cached | grep -q 'print("DEBUG'; then  echo "Remove DEBUG prints before committing"  exit 1fi
What each marked line does and why
  1. Line 1#!/bin/shA hook is any executable file with the exact hook name. chmod +x is required on macOS and Linux.
  2. Line 3if git diff --cached | grep -q 'print("DEBUG'; thengit diff --cached shows what is about to be committed.
  3. Line 5exit 1A non zero exit code stops the commit.
The hook in action
git commit -am "try"echo $?git commit -am "try" --no-verify
Real output: --no-verify skips the hook
Remove DEBUG prints before committing

Common mistake
Files in .git/hooks are not committed and not cloned, and anyone can skip them with --no-verify. Use hooks for fast feedback on your laptop, and run the same checks again in CI, which no one can skip.
Going deeper: Sharing hooks with the team

Commit the scripts to a folder such as .githooks and ask everyone to run git config core.hooksPath .githooks once. Many teams use the pre-commit framework instead: a .pre-commit-config.yaml file lists checks by repository and version, pre-commit install writes the hook, and the same command runs in CI with pre-commit run --all-files.

Lesson 4 of 4

grep, sparse checkout, signing and archive

Search tracked filesExam favourite
git grep -n "def add"
Faster than grep on big repositories and ignores untracked junk. Add a commit or tag to search an old version: git grep -n TODO v1.0.
Work on part of a monorepo
git sparse-checkout set app tests
Only these folders appear in the working tree. git sparse-checkout disable brings everything back.
Sign a commit or tagExam favourite
git commit -S, git tag -s v1.0.0
Proves who made it. Set commit.gpgsign true to sign every commit.
Export a release
git archive --format=zip -o calc-app.zip v1.0.0
Writes the files of a tag or commit to a zip or tar, without the .git folder.
Sign with your SSH key (Git 2.34 or newer)
git config --global gpg.format sshgit config --global user.signingkey ~/.ssh/id_ed25519.pubgit config --global commit.gpgsign truegit commit -m "Signed change"git log --show-signature -1

Add the same public key to GitHub or GitLab as a signing key, and the platform shows the commit as Verified. Anyone can type any name in user.name, so a signature is the only proof that a commit came from the key holder.

Real world scenario: the xz utils backdoor, 2024

In March 2024 Andres Freund noticed that SSH logins on a test system used more CPU than expected, and traced it to a backdoor in xz utils versions 5.6.0 and 5.6.1 (CVE-2024-3094). A maintainer account that had earned trust over about two years had added obfuscated binary test files to the repository, and the release tarballs contained a modified build script that was not in the Git repository at all. Lessons that teams took: build releases from the tagged Git commit inside CI, compare tarballs with the repository, review changes to build and test files carefully and sign tags.

One idea, four depths

bisect finds the bad commit by halving, worktree gives you extra folders, submodules pin another project, and hooks run checks at the right moment.

bisect run uses exit codes (0 good, 125 skip, other 1 to 127 bad). Submodules are stored as a gitlink entry with mode 160000. Client hooks live in .git/hooks or core.hooksPath and can be skipped, server hooks cannot.

Bisect needs about log2(n) tests. Sparse checkout in cone mode matches whole folders, which keeps it fast. Commit signatures are stored inside the commit object in a gpgsig header and cover the tree, parents, author and message.

Software supply chain work (SLSA, Sigstore gitsign, reproducible builds) builds on these tools: signed commits and tags say who wrote the code, CI provenance says how the artifact was built from that exact commit.
