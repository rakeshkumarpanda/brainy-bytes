Four branching workflows

Git lets you branch any way you like, so teams agree on a workflow: which branches live long, where new work starts and how it gets back. Pick one in the animation and watch the commits move.

WorkflowLong lived branchesBest forMain risk
GitHub flowmain onlyweb apps that deploy oftenneeds good CI, because main must always work
Gitflowmain and developproducts with numbered, scheduled releases and several supported versionsmany branches and slow, painful merges
Trunk basedmain (the trunk)teams with strong automated tests who merge at least dailyunfinished work must hide behind feature flags
Forkingyour fork plus the original (upstream)open source, where outsiders cannot pushkeeping the fork in sync
In the exam
Gitflow was published by Vincent Driessen in 2010. In 2020 he added a note to the article saying that for software delivered continuously, such as web apps, a simpler workflow like GitHub flow is usually a better fit. Gitflow still suits software with explicit versions.

Lesson 2 of 4

Pull requests and merge requests

A pull request (GitHub) or merge request (GitLab) is a page that asks to merge one branch into another. It is not a Git feature: it lives on the server. It shows the diff, runs CI on every push, and collects review comments and approvals.

  1. Push the branchgit push -u origin feature/percent
  2. Open the PR or MRtitle, description, linked issue, reviewers
  3. CI runsthe pipeline result appears as a status check on the page
  4. Reviewcomments on lines, change requests, approvals
  5. Fix and push againthe PR updates itself and CI runs again
  6. Mergewith the method the project allows, then delete the branch
GitHub merge buttonGitLab merge methodResulting history
Create a merge commitMerge commitall branch commits plus a merge commit, the same as git merge --no-ff
Squash and mergeSquash commits option (with the merge commit methods a merge commit is added too)one new commit holding the whole change
Rebase and mergeFast-forward mergethe branch commits replayed on top, straight line, no merge commit
(no equivalent)Merge commit with semi-linear historymerge commit, but only allowed when the branch is already rebased on the target
A pull request, seen by Dev and by QA
Developer view

Keep the PR small and focused, write what changed and why, link the issue, and make CI green before asking for review. Answer every comment, by changing code or explaining.

QA view

Read the description for what to test, pull the branch or download the build artifact from its pipeline, test on a test environment, and add test cases for the edge cases you found. A green pipeline is necessary, not sufficient.

Common mistake
Squash and merge makes main easy to read, but the branch commits do not appear on main. If someone keeps working on the old branch afterwards, Git does not know those commits were merged and conflicts follow. Start a fresh branch after a squash merge.

Protect main: branch rules and code owners

A workflow is only a promise until the server enforces it. Both platforms let you protect a branch so that changes arrive only through reviewed, tested pull requests.

RuleGitHub (Settings, Branches or Rules)GitLab (Settings, Repository, Protected branches)
No direct pushesRequire a pull request before mergingAllowed to push and merge: No one
ReviewsRequired approvals, require review from Code OwnersApproval rules, Require approval from code owners (Premium)
Tests must passRequire status checks to pass, pick the CI jobsSettings, Merge requests, Merge checks: Pipelines must succeed
No history rewritesForce pushes are blocked by default in a ruleAllowed to force push: off
No deleting the branchDeletions are blocked by default in a ruleA protected branch cannot be deleted with git push, only by a Maintainer in the UI or API
Straight historyRequire linear historyMerge method: Fast-forward merge
.github/CODEOWNERS
# Default owners for everything*                 @OWNER/maintainers# Python code*.py              @OWNER/backend# The pipelines need a CI owner to approve/.github/workflows/ @OWNER/ci-team/.gitlab-ci.yml     @OWNER/ci-team# Protect this file itself/.github/CODEOWNERS @OWNER
What each marked line does and why
  1. Line 2* @OWNER/maintainersThe first rule matches every file.
  2. Line 4*.py @OWNER/backendThe last matching pattern wins, so a .py file goes to backend, not maintainers.
  3. Line 6/.github/workflows/ @OWNER/ci-teamChanges to pipelines can leak secrets or skip tests, so they get their own reviewers.
  4. Line 9/.github/CODEOWNERS @OWNERGitHub recommends owning the CODEOWNERS file itself, otherwise anyone could remove themselves from review.

GitHub looks for CODEOWNERS in .github/, the repository root, then docs/, and uses the first one it finds. Owners are requested for review automatically when a pull request touches their files. GitLab reads the same file name, and Code Owners there is a Premium and Ultimate feature.

Common mistake
If your branch rule requires a status check called unit-tests, the job name in the workflow must stay unit-tests. Renaming the job makes the required check wait forever. GitHub also advises keeping job names unique across workflows for this reason.

Good commit messages and Conventional Commits

A commit message is a letter to the person who reads it in two years. The common convention: a short summary line of about 50 characters in the imperative ("Add percent function", not "added"), a blank line, then a body that explains why.

Conventional Commits (version 1.0.0 of the specification) adds a type in front so that tools can read the history: type(scope): description.

MessageMeaningSemver effect
fix(calc): handle divide by zeroa bug fixPATCH
feat(calc): add percent()a new featureMINOR
feat!: drop Python 3.9 or a footer BREAKING CHANGE: ...a breaking changeMAJOR
docs:, test:, ci:, refactor:, chore:allowed extra typesnone by default
Real world scenario: release notes from history

Projects such as Angular adopted structured commit messages so that changelogs could be generated from Git history, and that convention grew into the Conventional Commits specification. Release tools read the messages since the last tag, pick the next version and write the release notes, which is why a CI job often checks message format on every pull request.

One idea, four depths

A workflow is the team agreement on how branches are used. Pull requests are where code is checked by people and by CI before it reaches main.

GitHub flow keeps one long lived branch, Gitflow two, trunk based development merges small changes daily. Branch protection turns the rules into server checks: reviews, required status checks, no force pushes.

Merge methods change the shape of main: merge commits keep context, squash gives one commit per PR, rebase or fast forward gives a straight line. Merge queues (GitHub) and merge trains (GitLab) test each change against the result of the ones queued before it.

The DORA research programme links short lived branches, trunk based development and fast feedback from CI to better delivery performance. Supply chain frameworks such as SLSA go further and ask that every change to the source be reviewed and that builds run on trusted CI, not on a laptop.
