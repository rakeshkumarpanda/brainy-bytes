Baby steps: from nothing to a green build

Follow these steps once, in order, and you will have a real repository on GitHub where every commit starts a pipeline that lints, tests, builds a package, smoke tests that package and keeps it as a downloadable artifact. Tick each step as you finish it. Your ticks are saved in this browser.

You need Git (git --version should print 2.28 or newer, for init -b), Python 3.12 or newer and a free GitHub account. Optional: the GitHub CLI gh, for downloading artifacts from the terminal.

Download calc-app-starter.zip and unzip it. It holds a tiny calculator, its tests and both pipeline files. You can also type the files yourself from the next lessons.

What you should have
cd calc-appfind . -type f | sort
What you will see

./.github/workflows/qa-regression.yml
./.gitignore
./.gitlab-ci.yml
./README.md

./app/calc.py
./requirements.txt
./tests/smoke/test_smoke.py
./tests/unit/test_calc.py

A pipeline only repeats what works locally. If it fails here, it fails there.

Run the unit tests locally
python -m venv .venv. .venv/bin/activate          # Windows: .venv\Scripts\activatepip install -r requirements.txtpython -m pytest -q tests/unit
Real output

5 passed in 0.02s

On github.com press New repository. Name it calc-app, choose Public or Private, and do not add a README, .gitignore or license, because the project already has them. Press Create repository and copy the URL it shows.

Turn the folder into a repository and push
git init -b maingit add .git commit -m "Start calc-app with CI"git remote add origin https://github.com/YOUR-NAME/calc-app.gitgit push -u origin main
The last line
branch 'main' set up to track 'origin/main'.

Open the repository, then the Actions tab. A run of CI has started because you pushed to main. Click it. You see four jobs joined by lines: lint, then unit-tests, then build, then smoke-tests. Each turns green in about a minute. The commit on the Code tab now shows a green check mark.

On the run page scroll to the Artifacts section. You will see calc-app, unit-report and smoke-report. Click calc-app to download a zip that contains calc-app.zip, the exact file that the smoke tests used.

Or with the GitHub CLI
gh run list --workflow ci.yml --limit 3gh run download RUN_ID -n calc-app -D downloaded

A pipeline you have never seen fail is a pipeline you do not trust.

Change add() so it subtracts
git switch -c broken-add# in app/calc.py change: return a + b   to: return a - bgit commit -am "Break add on purpose"git push -u origin broken-add

Open a pull request from broken-add to main. CI runs because of the pull_request trigger, unit-tests turns red and build and smoke-tests are skipped because they need it. Open the failed step to read the same message you would see locally:

From the unit-tests log
python -m pytest -q tests/unit --junitxml=reports/unit.xml
Real pytest output
FAILED tests/unit/test_calc.py::test_add - assert -1 == 5
1 failed, 4 passed
Fix and push to the same branch
# change it back to: return a + bgit commit -am "Fix add"git push

The pull request updates and CI runs again. When it is green, merge it. The push to main runs CI once more on the merged code.

In the repository open Settings, then Branches (or Rules, Rulesets), and add a rule for main: require a pull request before merging and require status checks to pass, choosing unit-tests and smoke-tests. From now on nobody can merge a red change into main.

What each marked line does and why
  1. Line 3on:Three triggers: pushes to main, pull requests into main, and a manual Run workflow button.
  2. Line 10permissions:The GITHUB_TOKEN of this run may only read the code. Nothing here needs more.
  3. Line 14group: ci-${{ github.ref }}One run per branch or PR. A new push cancels the older, now useless, run.
  4. Line 21- uses: actions/checkout@v7Every job starts on a fresh machine with no files, so every job checks out the code.
  5. Line 24python-version: '3.13'Quoted so that YAML keeps it a string.
  6. Line 26run: python -m compileall -q appcompileall fails on any syntax error, the cheapest possible check, so it goes first.
  7. Line 29needs: lintunit-tests starts only when lint is green.
  8. Line 36cache: pipsetup-python caches pip downloads, keyed on requirements.txt.
  9. Line 39run: python -m pytest -q tests/unit --junitxml=reports/unit.xmlpython -m pytest puts the project folder on the import path. --junitxml writes a machine readable report.
  10. Line 41if: always()always() keeps the report even when tests fail, which is exactly when you need it.
  11. Line 46retention-days: 14Reports are small and only useful for a while, so 14 days.
  12. Line 59python -m zipfile -c dist/calc-app.zip appBuild the package once. Every later test uses this exact file.
  13. Line 63name: calc-appThe artifact name other jobs and workflows use to find it.
  14. Line 65if-no-files-found: errorFail the job if the zip was not made, instead of uploading nothing with a warning.
  15. Line 69needs: buildsmoke-tests waits for build, so the artifact exists.
  16. Line 79uses: actions/download-artifact@v8Pull the artifact made earlier in this run into dist/.
  17. Line 84run: PYTHONPATH=dist/calc-app.zip pytest -q tests/smoke --junitxml=reports/smoke.xmlPYTHONPATH points at the zip, so the tests import the packaged app, not the source folder.

Lesson 3 of 4

What Dev and QA change, and why

The sample file is a safe start. Real teams change it, and developers and testers change different things for different reasons.

The same thing, seen by Dev and by QA
Developer view

Goal: the fastest trustworthy answer to "did I break something?".

  • Keep lint and unit tests under a few minutes.
  • Run on every push to every branch so feedback comes before the pull request.
  • Use caches for dependencies.
  • Cancel outdated runs.
  • Build once and publish the artifact for others.
QA view

Goal: evidence that this exact build works, kept long enough to show later.

  • Test the artifact, never a rebuild.
  • Run long suites on a schedule or on demand, not on every push.
  • Use fail-fast: false so one failure does not hide others.
  • Keep reports with if: always() and longer retention.
  • Make suites selectable with workflow_dispatch inputs.

Remember
Change one thing at a time and push it on a branch with a pull request. The pull request runs the workflow file from the branch, so you see the result before main is affected.
Lesson 4 of 4

The QA regression workflow and common errors

QA runs the full suite every weekday night and whenever someone presses Run workflow, always against a build that CI already made. It finds the newest green CI run on main, or takes a run id you type in, and pulls the calc-app artifact from it.

.github/workflows/qa-regression.yml
name: QA regression on:  schedule:    - cron: '30 2 * * 1-5'  workflow_dispatch:    inputs:      ci_run_id:        description: 'ID of the CI run whose build you want to test (empty means the latest green run on main)'        required: false        type: string permissions:  contents: read  actions: read jobs:  regression:    runs-on: ubuntu-latest    env:      GH_TOKEN: ${{ github.token }}    steps:      - uses: actions/checkout@v7      - uses: actions/setup-python@v7        with:          python-version: '3.13'          cache: pip      - run: pip install -r requirements.txt      - name: Find the CI run to test        id: pick        env:          RUN_ID: ${{ inputs.ci_run_id }}        run: |          if [ -z "$RUN_ID" ]; then            RUN_ID=$(gh run list --workflow ci.yml --branch main --status success --limit 1 --json databaseId --jq '.[0].databaseId')          fi          echo "Testing the build from run $RUN_ID"          echo "run_id=$RUN_ID" >> "$GITHUB_OUTPUT"      - name: Pull the build artifact from that run        run: gh run download "${{ steps.pick.outputs.run_id }}" --name calc-app --dir dist      - name: Run the regression suite on that build        run: PYTHONPATH=dist/calc-app.zip pytest -q tests --junitxml=reports/regression.xml      - name: Keep the regression report        if: always()        uses: actions/upload-artifact@v7        with:          name: regression-report          path: reports/regression.xml
What each marked line does and why
  1. Line 5- cron: '30 2 * * 1-5'02:30 UTC, Monday to Friday.
  2. Line 6workflow_dispatch:The Run workflow button, with an optional input.
  3. Line 15actions: readactions: read lets gh read runs and artifacts of other workflow runs in this repository.
  4. Line 21GH_TOKEN: ${{ github.token }}The gh CLI is installed on GitHub hosted runners and reads its token from GH_TOKEN.
  5. Line 32RUN_ID: ${{ inputs.ci_run_id }}The input arrives through an environment variable, never pasted into the script, so a strange value cannot become a command.
  6. Line 35RUN_ID=$(gh run list --workflow ci.yml --branch main --status success --limit 1 --json databaseId --jq '.[0].databaseId')The newest successful CI run on main, as a run id.
  7. Line 38echo "run_id=$RUN_ID" >> "$GITHUB_OUTPUT"Save the id as a step output for the next step.
  8. Line 40run: gh run download "${{ steps.pick.outputs.run_id }}" --name calc-app --dir distDownload one named artifact from that other run into dist/.
  9. Line 42run: PYTHONPATH=dist/calc-app.zip pytest -q tests --junitxml=reports/regression.xmlThe whole suite, unit and smoke, against the packaged build.

One idea, four depths

Put the YAML file in .github/workflows/, push, and GitHub runs your tests on every commit. Break it once on purpose so you know what red looks like.

The CI workflow chains lint, unit-tests, build and smoke-tests with needs, builds one artifact and tests it. Branch protection turns the green checks into a merge rule. QA pulls the same artifact into a scheduled workflow.

Each choice trades speed against evidence: triggers, caches and cancel-in-progress make Dev feedback fast, while retention, fail-fast: false and separate scheduled suites give QA durable results.

Mature setups add reusable workflows shared across repositories, artifact attestations that sign which workflow built which file, and test impact analysis that runs only the tests a change can affect.
