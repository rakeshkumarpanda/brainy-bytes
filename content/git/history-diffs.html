Lesson 1 of 4

Reading history with git log

git log lists commits newest first. Each entry has the commit id, the author, the date and the message. Its options turn it into a search tool.

Compact historyExam favourite
git log --oneline --graph --decorate --all
One line per commit, a text drawing of branches and merges, branch and tag names, every branch not just the current one.
Filter
git log -n 5, --author=Asha, --since="2 weeks ago", --grep=login
Last 5 commits, by one person, in a time window, or with a word in the message.
What a change touched
git log -p, git log --stat, git log -- path/file
-p adds the full diff, --stat lists changed files with counts, and -- path limits history to one file.
Find codeExam favourite
git log -S "price_limit"
The pickaxe: commits that added or removed that text. Great for "when did this function appear?".
One commit in full
git show <commit>
Message plus diff. git show HEAD:app.py prints the file as it was in that commit.
Typical log output
git log --oneline --graph -6
What you will see
*   a41f0c2 (HEAD -> main) Merge branch 'feature/search'
|\
| * 7c9e1d0 (feature/search) Add search by price
| * 33b2a91 Add search box
* | 51de0f4 Fix typo on checkout page
|/
* 0b8e3a7 Add product list
Real world scenario: who broke the price filter?

A tester finds that the price filter ignores decimals. Instead of reading every file, the developer runs git log -S "round(" -- src/filter.py and gets two commits. git show on the newer one shows a round() call added last Tuesday. Bug found in five minutes.

Lesson 2 of 4

git diff: three comparisons and how to read a hunk

CommandComparesAnswers
git diffworking tree with the indexWhat have I changed but not staged?
git diff --stagedindex with HEADWhat will my next commit contain?
git diff HEADworking tree with HEADEverything since the last commit
git diff main featuretwo commitsHow do these branches differ?
git diff main...featuremerge base of the two with featureWhat did feature add since it split off?
Hunk headerExam favourite
@@ -a,b +c,d @@
The old file from line a for b lines became the new file from line c for d lines. Lines start with space (context), - (removed) or + (added).
Word level and stats
git diff --word-diff, git diff --stat
Shows changed words inside a line, or only counts per file.
Common mistake
git diff with no arguments shows nothing after git add. The changes did not vanish: they moved to the index. Use git diff --staged.
Going deeper: How Git finds the differences

Git compares lines. It finds a longest common subsequence of lines (the default Myers algorithm finds a shortest edit script), keeps those lines as context and marks the rest as removed or added. Options --patience and --histogram give diffs that are easier to read when code blocks move. A changed line is always one deletion plus one addition.

Lesson 3 of 4

Naming commits: HEAD, ~, ^ and ranges

You can name a commit by its id (full or a unique prefix like a41f0c2), by a branch or tag name, or by HEAD, which means "the commit I am on now". From any of those you can walk backwards.

AncestorsExam favourite
X~n = n first parents back. X^n = the n-th parent of X
HEAD~1 is the parent, HEAD~2 the grandparent. For a merge commit, X^1 is the branch you were on and X^2 is the branch you merged in.
Two dotsExam favourite
A..B = reachable from B but not from A
git log main..feature lists what feature has that main does not.
Three dots
A...B = reachable from either but not both
With git log --left-right each commit is marked < or > for its side.
Where HEAD was
HEAD@{n}
The n-th previous position of HEAD, from the reflog. HEAD@{1} is where you were before the last move.
Work it out: G is a merge with parents E (first) and D (second)
  1. G~1 follows the first parent: E.
  2. G^2 is the second parent: D.
  3. G~3 is G, E, C, B going back three first parents: B.
  4. D..G = commits reachable from G minus those from D = E, G
In the exam
HEAD~2 and HEAD^^ name the same commit. HEAD^2 is different: it is the second parent of HEAD and only exists if HEAD is a merge commit.
Lesson 4 of 4

Who wrote this line and why

Line by line authors
git blame -L 10,20 app.py
For each line: the commit, author and date that last changed it. -w ignores whitespace changes, -C finds lines moved from other files.
Ignore big reformat commits
git blame --ignore-revs-file .git-blame-ignore-revs
Skip commits listed in the file, such as a project wide formatting run, so blame shows the real author. GitHub reads this file too.
Blame a few lines
git blame -L 3,5 src/cart.py
What you will see
5d2c11e3 (Asha 2026-10-02 10:14:21 +0530 3) def total(items):
9f0aa71c (Ravi 2026-10-20 16:40:02 +0530 4)     s = sum(i.price for i in items)
9f0aa71c (Ravi 2026-10-20 16:40:02 +0530 5)     return round(s, 2)

Blame is not about blaming people. It finds the commit, and the commit message tells you why the line exists. Read it before you delete something that looks useless.

One idea, four depths

git log is the diary of the project, git diff shows what changed between two pages of the diary, and git blame tells you who wrote each sentence.

Revisions name commits, ranges name sets of commits. A..B is the set difference of the ancestor sets, A...B the symmetric difference. Most history commands accept both.

Range arithmetic is defined on the commit graph: ^A B, A..B and B --not A are the same set. Merge commits make first parent history special: git log --first-parent shows only the commits made on the branch itself, a clean view of a main branch that receives merges.

Line tracking across renames and moves (blame -C -C) is a hard problem studied as code provenance. Tools like SZZ use blame to find the commits that introduced a bug from the commits that fixed it, a core method in empirical software engineering research.
