Lesson 1 of 4

git stash: put work aside for a moment

You are halfway through a feature when an urgent bug comes in. Your work is not ready to commit, and Git will not let you switch branches if your edits clash. git stash saves your uncommitted changes on a stack and gives you a clean working tree. Later you take them back.

Save and cleanExam favourite
git stash or git stash push -m "note"
Saves staged and unstaged changes to tracked files. -u also saves untracked files.
Bring backExam favourite
git stash pop, git stash apply
pop applies the newest stash and drops it. apply keeps it on the stack.
Look and tidy
git stash list, git stash show -p stash@{1}, git stash drop
stash@{0} is the newest.
Turn a stash into a branch
git stash branch <name>
Creates a branch at the commit where you stashed and applies the stash there, avoiding conflicts.
Remember
A stash is easy to forget. If it holds real work, a work in progress commit on a branch is often safer and shows up in git log.
Going deeper: git clean

git clean removes untracked files. Always run git clean -n first, a dry run that lists what would go. -d also removes untracked folders, -x also removes ignored files such as build output. -f is required to actually delete. Files removed by clean were never in Git, so nothing can restore them.

Lesson 2 of 4

Tags and version numbers

A tag is a name for one commit that never moves, unlike a branch. Teams tag the commit they release: v1.0.0, v1.1.0. CI pipelines often start a release job when a tag is pushed.

KindCommandStoresUse for
Lightweightgit tag v1.0.0Only a ref pointing at the commitprivate or temporary marks
Annotatedgit tag -a v1.0.0 -m "Release 1.0.0"A tag object with tagger, date, message (and optional signature)releases
Push tagsExam favourite
git push origin v1.0.0, git push --tags
git push alone does not send tags. --follow-tags sends annotated tags that point at pushed commits.
List and inspect
git tag -l "v1.*", git show v1.0.0, git describe
git describe names HEAD by the nearest tag, for example v1.0.0-3-g7c9e1d0 (3 commits after the tag).
Semantic versioningExam favourite
MAJOR.MINOR.PATCH
MAJOR for breaking changes, MINOR for new backwards compatible features, PATCH for backwards compatible bug fixes.
Common mistake
Moving a tag that others have fetched is like changing a published book's edition number. Do not do it. Make a new tag instead.
Lesson 3 of 4

.gitignore: keep junk out

Some files must never be committed: build output, dependency folders, logs, editor files and above all secrets such as .env files with passwords. A .gitignore file lists patterns, and git status stops showing matching untracked files.

.gitignore
# Python__pycache__/*.pyc.venv/# build output and test reportsdist/reports/# logs, but keep one example*.log!example.log# secrets: only the file in the top folder/.env
What each marked line does and why
  1. Line 2__pycache__/A trailing slash matches folders only, at any depth.
  2. Line 3*.pycA star matches any characters except a slash.
  3. Line 10!example.logA leading ! re-includes a file an earlier rule ignored. The last matching rule wins.
  4. Line 12/.envA leading slash anchors the rule to the folder that holds this .gitignore.
PatternMatches
*.logany .log file in any folder
/todo.txtonly todo.txt next to the .gitignore
build/any folder called build, and everything inside
docs/**/*.pdfPDFs anywhere under docs
!keep.logbrings keep.log back, unless its parent folder is ignored
Why is this file ignored?Exam favourite
git check-ignore -v <path>
Prints the .gitignore file, line number and pattern that matched.
Already committed by mistakeExam favourite
git rm --cached <file> then commit
.gitignore only affects untracked files. A tracked file stays tracked until you remove it from the index.
Common mistake
If a secret was ever committed and pushed, removing it in a new commit is not enough: it is still in history. Treat it as leaked and rotate the password or key at once.
Going deeper: Other ignore files

.git/info/exclude works like .gitignore but is never shared. core.excludesFile (often ~/.config/git/ignore) holds personal patterns for every repository, a good place for .DS_Store or editor folders. Order of precedence: patterns on the command line, .gitignore files from the folder of the path up to the top, .git/info/exclude, then core.excludesFile.

Lesson 4 of 4

.gitattributes, line endings and big files

Windows ends lines with CRLF, macOS and Linux with LF. Without rules, a whole file can look changed because only the line endings differ. .gitattributes fixes this per path and is committed, so the whole team follows it.

.gitattributes
* text=auto*.sh text eol=lf*.bat text eol=crlf*.png binary*.psd filter=lfs diff=lfs merge=lfs -text
What each marked line does and why
  1. Line 1* text=autoLet Git detect text files and store them with LF inside the repository.
  2. Line 2*.sh text eol=lfShell scripts must keep LF even on Windows, or bash fails.
  3. Line 4*.png binarybinary means no line ending changes and no text diff.
  4. Line 5*.psd filter=lfs diff=lfs merge=lfs -textWritten by git lfs track "*.psd": the content goes to Git LFS storage, the repository keeps a small pointer.
One idea, four depths

stash is a drawer for unfinished work, tags are name labels on finished versions, and .gitignore is a list of things that should never go in the box.

A stash is stored as commits under refs/stash. Annotated tags are tag objects, lightweight tags are plain refs. .gitignore patterns follow the rules in gitignore(5), last match wins, and a file cannot be re-included if a parent folder is excluded.

Line ending normalisation happens in the clean and smudge steps between the working tree and the index. Git LFS uses the same filter mechanism: clean replaces large content with a pointer file, smudge downloads it on checkout.

Signed tags (git tag -s) and signed commits, now also with SSH keys, are part of software supply chain security. Projects such as Sigstore and reproducible builds aim to prove that a released artifact really came from a given tagged commit.
