Lesson 1 of 7

How a conflict arises

A conflict needs three things: a common starting point, and two branches that each change the same lines of that starting point in different ways. Here is the exact setup used in every example on this page.

  1. Base commit Bshop.yml has title: Shop, colour: blue, price: 10
  2. feature branchCommit F changes colour: blue to colour: red
  3. main branchCommit M changes colour: blue to colour: green
  4. git merge featureBoth sides changed line 2 differently. Git stops and asks you.
Recreate it yourself in an empty folder
git init -b main shop && cd shopprintf 'title: Shop\ncolour: blue\nprice: 10\n' > shop.ymlgit add shop.yml && git commit -m "Start shop"git switch -c featuresed -i 's/blue/red/' shop.yml && git commit -am "Make it red"git switch mainsed -i 's/blue/green/' shop.yml && git commit -am "Make it green"git merge feature
What you will see
Auto-merging shop.yml
CONFLICT (content): Merge conflict in shop.yml
Automatic merge failed; fix conflicts and then commit the result.

Press Play below and step through it. Then change the two lines, pick another way out, and play it again. Make both lines identical to see that the same change on both sides is not a conflict at all.

VS Code, IntelliJ and Meld do the same job with buttons such as Accept Current, Accept Incoming and Accept Both. Accept Current means ours and Accept Incoming means theirs.

Common mistake
git checkout --ours and git merge -X ours are different. The first acts on a whole file after the stop. The second acts on each clashing hunk during the merge, and still keeps their changes in every other place. git merge -s ours (a strategy, with a small s) is different again: it throws away all of their changes.

Remember
A rebase replays commits one by one, so a branch with five commits can stop up to five times, once for each commit that clashes. A merge stops at most once. That is a fair reason to merge long lived branches, or to squash before rebasing.

Resolving in GitHub and GitLab

When a pull request or merge request cannot merge, both sites can resolve simple conflicts in the browser.

Common mistake
The web resolver merges main into your branch. If your team requires a linear history or rebased branches, do not use it. Rebase locally instead and push with git push --force-with-lease.
Real world scenario: Dev and QA on the same config file

A developer raises the retry count in config.yml from 3 to 5 on a feature branch. A QA engineer lowers it to 2 on main so flaky tests fail faster. The pull request shows This branch has conflicts. The developer opens the file locally with zdiff3, sees the base was 3, talks to QA, and they agree on 3 for CI and 5 for production through an environment variable. One hand edited merge commit later, CI runs on the merged result and the pull request goes green.

Note that rerere fixes the file but still leaves it unstaged, so you look at it, then git add and commit as usual.

A calm routine for any conflict
  1. Run git status. Read which operation is in progress and which files are unmerged.
  2. For each file, read ours, theirs and, with zdiff3, the base. Ask who made each change and why.
  3. Pick a way: edit by hand, take one side, or use a tool. Delete every marker line.
  4. Run git diff --check, then build and run the tests locally.
  5. git add the files, then git commit, or git rebase --continue, or git cherry-pick --continue
One idea, four depths

Two people changed the same sentence of a shared story in two different ways. Git will not guess which one is right, so it shows both and asks you to choose or write a new sentence.

A conflict happens when both sides of a three way merge change overlapping lines differently. Git writes markers into the file and keeps base, ours and theirs as index stages 1, 2 and 3. git add collapses them to stage 0.

The merge is line based. Adjacent edits form one hunk, so changes that touch each other clash even if they are logically separate. During a rebase the replayed commit is theirs. rerere stores a preimage and postimage keyed by the conflict text and replays the fix later.

Research on structured merge parses files into syntax trees to avoid false conflicts, for example two methods added at the same place, and empirical studies of open source projects find that a noticeable share of merges are textual conflicts, while some clean merges still contain semantic conflicts that only tests reveal.
