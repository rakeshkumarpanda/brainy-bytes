Lesson 1 of 4

What CI and CD mean, and why teams need them

Continuous integration (CI) means every developer merges small changes into the shared branch often, and a server automatically builds and tests every push. Problems show up within minutes, while the change is still fresh in the author's head.

Continuous delivery (CD) means every change that passes the pipeline is packaged and ready to release, and a person presses the button. Continuous deployment goes one step further: a green pipeline releases to production with no human step.

  1. Commit and pusha developer pushes a branch or opens a pull request
  2. Pipeline startsthe CI server reads the YAML file in the repository
  3. Build and testlint, unit tests, build a package (the artifact)
  4. Deploy to testQA and automated tests check the same artifact
  5. Releasea person approves (delivery) or it goes out by itself (deployment)
Real world scenario: Knight Capital, 1 August 2012

Knight Capital deployed new trading code by hand to eight servers. According to the US Securities and Exchange Commission, a technician did not copy the new code to one of the eight. That server still had old, unused code, and a reused flag in the new orders switched the old code on. In about 45 minutes it sent millions of unintended orders, and the firm lost about 460 million US dollars. The SEC order points to the lack of written deployment procedures and of a second person checking. An automated pipeline that deploys the same package to every server, and verifies the result, is the standard defence.

Lesson 2 of 4

Inside a pipeline: jobs, stages, runners and YAML

A pipeline is a set of jobs. Each job runs on a fresh machine called a runner, so jobs share nothing unless you pass files on as artifacts. Jobs either wait for a whole stage to finish (the GitLab default) or only for the jobs they need. Try both modes and make one job fail.

Both platforms describe pipelines in YAML: indentation with spaces shows what belongs to what, key: value makes a map and - item makes a list. Break the file in the animation and read the error.

Common mistake
YAML guesses types. python-version: 3.10 is read as the number 3.1, and the job installs the wrong Python. Always quote versions: python-version: "3.10". Old YAML 1.1 parsers also read a bare no or off as false.

Jobs start on clean machines, so you decide what moves between them and how.

Pin third party actionsExam favourite
uses: owner/action@<full commit SHA>
A tag such as @v4 can be moved to new code. A full commit id cannot.
Real world scenario: Codecov, 2021

Codecov offered a Bash script that thousands of CI pipelines downloaded and ran on every build to upload coverage. In January 2021 an attacker changed that script on Codecov's server so that it also sent the environment variables of each CI job, which often held tokens and keys, to the attacker. It went unnoticed until April 2021, when a customer compared the script with its published checksum. Lessons: check downloaded scripts against a checksum, give CI jobs as few secrets as possible, and rotate credentials after such a leak.

Real world scenario: tj-actions/changed-files, March 2025

An attacker gained access to the popular GitHub Action tj-actions/changed-files and moved its version tags to a malicious commit that printed the CI runner's secrets into the job log (CVE-2025-30066). Public repositories with public logs exposed their secrets. Workflows that pinned the action to a full commit SHA kept running the old, safe code. GitHub's own security guidance recommends pinning third party actions to a full length commit SHA.

Lesson 4 of 4

Dev and QA in a pipeline, and build once, promote many

The same pipeline serves two groups with different questions. Developers ask "did my change break anything, and how fast can I know?". QA asks "is this exact build good enough to release, and can I prove it?".

The same thing, seen by Dev and by QA
Developer view
  • Fast feedback on every push: lint and unit tests in a few minutes.
  • Builds the artifact once and tags it with the commit id.
  • Uses cache to keep the pipeline fast.
  • Fixes a red pipeline before starting new work.
  • Deploys automatically to a dev environment.
QA view
  • Tests the artifact the pipeline built, never a fresh build from a laptop.
  • Runs slower suites: API, end to end, regression, often on a schedule or before release.
  • Keeps test reports as artifacts so failures can be shown later.
  • Owns the quality gate: which checks must pass before production.
  • Tracks flaky tests instead of pressing retry until green.
  1. Build onceone job builds calc-app.zip from commit 7c9e1d0
  2. Dev environmentdeployed automatically, developers check it
  3. QA environmentthe same zip, QA runs regression and end to end tests
  4. Stagingthe same zip with production like settings
  5. Productionthe same zip after approval
In the exam
If each environment rebuilds from source, QA tested a different file from the one users get. Build once, store it as an artifact or in a package registry, and promote that same file.
One idea, four depths

CI is a robot that builds and tests every change you push. CD makes sure every good change is ready to ship. Dev uses the pipeline for quick answers, QA uses it to prove a build is ready.

A pipeline is a graph of jobs on fresh runners, written in YAML. Artifacts pass results on, caches speed up dependency downloads, secrets live outside the YAML. Build once and promote the same artifact.

Pipeline time is the longest path through the job graph, so needs and parallel jobs shorten it. Every third party step runs with your secrets, so pin by SHA, restrict permissions and treat CI as production.

DORA research measures delivery with lead time, deployment frequency, change failure rate and time to restore. SLSA defines levels of build integrity, from documented builds to hosted, isolated builds with signed provenance.
