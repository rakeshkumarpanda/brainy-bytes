Lesson 1 of 4

Fast-forward or a real merge

To bring a feature into main you run git merge feature while on main. What Git does depends on the shape of the history.

SituationWhat Git doesNew commit?
main has not moved since feature startedFast-forward: main just slides up to the tip of featureNo
Both branches have new commitsThree way merge: compares both tips with their merge base and makes a merge commit with two parentsYes
feature is already contained in mainAlready up to dateNo
Merge a branch into the current oneExam favourite
git merge <branch>
Fast-forwards when it can, otherwise makes a merge commit.
Always make a merge commit
git merge --no-ff <branch>
Keeps the feature visible as its own bubble in history, even when a fast-forward was possible.
Refuse anything but a fast-forward
git merge --ff-only <branch>
Fails instead of making a merge commit. Safe default for updating a branch you do not work on.
Squash
git merge --squash <branch> then git commit
Stages all changes of the branch as one new ordinary commit. The branch itself is not recorded as merged.
Merge baseExam favourite
git merge-base main feature
Prints the best common ancestor that a three way merge uses as its base.
Lesson 2 of 4

How a three way merge decides

Git looks at three versions of every file: the base (the merge base), ours (the branch you are on) and theirs (the branch you merge in). For each part of the file:

BaseOursTheirsResult
xxxx (nobody changed it)
xyxy (only we changed it)
xxzz (only they changed it)
xyyy (we both made the same change)
xyzCONFLICT, you decide

That is why Git can merge most work by itself. It only stops when the same lines were changed in two different ways, or when one side deleted a file the other side edited.

Going deeper: The ort strategy

Since Git 2.34 the default merge strategy is ort (Ostensibly Recursive's Twin), a rewrite of the older recursive strategy that is much faster and handles renames better. When there is more than one best common ancestor (a criss cross history), ort first merges those ancestors into a virtual base. Other strategies: octopus merges more than two branches at once if there are no conflicts, ours records a merge but keeps our tree completely. Do not confuse the ours strategy (-s ours) with the option -X ours, which only picks our side for conflicting hunks.

Inside the file Git writes conflict markers:

What the file looks like
<<<<<<< HEADcolour: green=======colour: red>>>>>>> feature
Resolve it
  1. Read both sides. Above ======= is ours (HEAD), below is theirs (feature).
  2. Edit the text to what it should be. It may be one side, the other, or a mix.
  3. Delete every marker line. A left over <<<<<<< will break your code.
  4. git add the file to mark it resolved, then git commit to finish the merge.
  5. Changed your mind? git merge --abort returns to the state before the merge
AbortExam favourite
git merge --abort
Puts everything back as it was before git merge started.
Take one whole side for a file
git checkout --ours file or --theirs file
Then git add file. Useful for generated files such as lock files.
See the base too
git config merge.conflictStyle diff3
Markers then also show the base version between ||||||| and =======. zdiff3 is a tidier variant.
Remember resolutions
git config rerere.enabled true
Reuse recorded resolution: when the same conflict comes back, Git applies your earlier fix.
Common mistake
A file with conflict markers still compiles in some languages, for example inside a YAML string or a Markdown file. Search for <<<<<<< before committing, or let a pre-commit check do it.
Real world scenario: two testers, one config file

Asha raises a timeout to 30 seconds for slow test machines. Ravi lowers it to 10 to make failures show faster. Both edit the same line, so the merge stops. Git cannot know which is right. The team talks, picks 20, writes it, and commits the merge. Conflicts are a conversation, not an error.

Lesson 4 of 4

From intuition to research

One idea, four depths

Two friends edit copies of the same story. Git compares both copies with the original. If they changed different sentences, Git combines them. If they changed the same sentence differently, Git asks you which to keep.

A merge commit has two parents. A fast-forward only moves the pointer. A three way merge combines base, ours and theirs, and conflicts happen when both sides change overlapping lines differently.

The merge base is a lowest common ancestor in the commit DAG. With several best common ancestors, ort merges them recursively into a virtual base. Rename detection pairs deleted and added files by similarity so changes follow moved files.

Line based three way merge knows nothing about code structure. Research on structured and semistructured merge parses the code into syntax trees to merge more safely, and studies show many textual merges that succeed still introduce semantic conflicts that only tests catch, which is a strong argument for running CI on the merge result.

In the exam
A clean merge is not a correct merge. Two changes can merge without any conflict and still break the program together. That is why CI on pull requests tests the merged code, not only the branch.
