Lesson 1 of 4

Remotes and git clone

Until now every commit lived only on your laptop. A remote is another copy of the same repository, usually on a server such as GitHub or GitLab, that the team shares. Because Git is distributed, your clone holds the full history, and the remote is simply the copy everyone agrees to meet at.

  1. git clone URLdownloads every commit, creates a remote called origin and checks out the default branch
  2. git fetchasks origin what is new and downloads it, without touching your files
  3. git pullfetch, then merge or rebase the new commits into your branch
  4. git pushuploads your new commits and moves the branch on the server
Clone, then look at what you got
git clone https://github.com/OWNER/calc-app.gitcd calc-appgit remote -vgit branch -a
What you will see
origin  https://github.com/OWNER/calc-app.git (fetch)
origin  https://github.com/OWNER/calc-app.git (push)
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main

CloneExam favourite
git clone <url> [folder]
Creates origin, copies all branches as origin/*, checks out the default branch and sets it to track origin.
Manage remotes
git remote -v, git remote add upstream <url>, git remote set-url origin <url>
A repository can have many remotes. upstream is the usual name for the original project when you work on a fork.
Fast clones for CI
git clone --depth 1, git clone --filter=blob:none
--depth 1 is a shallow clone with only the newest commit. --filter=blob:none is a partial clone that fetches file contents only when needed.
Common mistake
origin/main does not update by itself. It is a snapshot from your last fetch. If git status says "up to date", it means up to date with that snapshot, not with the server right now.
Going deeper: HTTPS or SSH

Both work. With HTTPS, GitHub stopped accepting account passwords for Git operations on 13 August 2021, so you use a personal access token or a credential manager that signs you in through the browser. With SSH you create a key pair with ssh-keygen -t ed25519, add the public key to your account, and use a URL like git@github.com:OWNER/calc-app.git. GitLab works the same way with personal access tokens or SSH keys.

Lesson 3 of 4

Upstream branches, force pushes and pruning

Each local branch can have an upstream: the remote-tracking branch it compares with and pulls from. Clone sets it for the default branch. For a new branch you set it on the first push.

Publish a new branch
git switch -c feature/logingit commit -am "Add login form"git push -u origin feature/login
The last line of the output
branch 'feature/login' set up to track 'origin/feature/login'.
Set upstreamExam favourite
git push -u origin <branch>
After this, plain git push and git pull know where to go. -u is short for --set-upstream.
Safer force pushExam favourite
git push --force-with-lease
Overwrites the server branch only if it still points where your origin/branch says. Otherwise it is rejected with stale info.
Delete a remote branch
git push origin --delete feature/login
Removes the branch on the server, for example after the pull request merged.
Clean up old remote-tracking branches
git fetch --prune
Removes origin/* names whose branch was deleted on the server. git config --global fetch.prune true does it on every fetch.

After a rebase or amend of a branch you already pushed, a normal push is rejected because it is not a fast forward. --force would overwrite whatever is on the server, including a teammate's new commit. --force-with-lease checks first.

Ben pushed while Asha was rebasing
git push --force-with-lease
Real output: the lease protected Ben's commit
To github.com:OWNER/calc-app.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to 'github.com:OWNER/calc-app.git'
Common mistake
The lease compares with origin/branch. If an editor or a script runs git fetch in the background, origin/branch is already updated and the lease passes without you ever seeing Ben's work. Git 2.30 added --force-if-includes, used together with --force-with-lease, to also check that you had integrated what you fetched.
Real world scenario: one force push, many repositories

In November 2013 a contributor to the Jenkins project ran git push --force while push.default was set to matching, so Git force pushed every local branch, many of them weeks old, to more than a hundred of the project's GitHub repositories at once. Git 2.0 later changed the default of push.default to simple, which pushes only the current branch. The project recovered the lost commits from the reflogs of developers who had fresh clones and from GitHub support. This is why most teams now forbid force pushes to main with branch protection, and allow them only on personal feature branches with --force-with-lease.

Going deeper: Refspecs: the rule behind fetch and push

.git/config holds the line fetch = +refs/heads/*:refs/remotes/origin/*. Read it as source:destination. Every branch on the server (refs/heads/anything) is copied to refs/remotes/origin/anything on your side. The leading + allows the copy to move even when it is not a fast forward. git push origin feature/login is short for the refspec refs/heads/feature/login:refs/heads/feature/login. You can push one branch to another name, as in git push origin HEAD:refs/heads/test-run, which CI scripts sometimes use.

Lesson 4 of 4

A day with a remote, step by step

Asha and Ben share calc-app
  1. Morning: git switch main then git pull. Asha starts from the newest main.
  2. git switch -c feature/percent, edit, git commit -am "Add percent()".
  3. git push -u origin feature/percent. The branch now exists on the server, and CI starts testing it.
  4. She opens a pull request. Ben reviews it and asks for a change. She commits again and runs plain git push.
  5. Meanwhile main moved. She runs git fetch then git rebase origin/main, fixes one conflict, and pushes with git push --force-with-lease.
  6. The pull request is merged on the server. She runs git switch main, git pull, git branch -d feature/percent and git fetch --prune.
One idea, four depths

The remote is the shared copy. fetch looks, pull brings the changes in, push sends yours out. The server only accepts a push that does not throw away anyone's commits.

origin/main is a remote-tracking ref updated only by network commands. Ahead and behind are counts of commits reachable from one tip and not the other. pull is fetch plus merge or rebase, chosen by pull.rebase or pull.ff.

The fetch protocol negotiates which objects each side already has and sends one packfile with the rest. Refspecs map server refs to local refs. --force-with-lease is a compare and swap on the remote ref, the same idea used in lock free programming.

Large monorepos use partial clone (--filter=blob:none), sparse checkout and protocol version 2, which lets the client ask only for the refs it needs. Git 3.0 plans to make SHA-256 and reftable defaults, which affects how servers and clients interoperate.
