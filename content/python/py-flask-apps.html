Lesson 1 of 11

From one file to a real app

Source: Flask 3.1 tutorial (flaskr), Flask configuration, error handling, logging, testing and deployment documentation, and the Werkzeug 3.1 security helpers.

What it is
A real Flask app is the same Flask, organised so it can grow: an application factory that builds the app, blueprints that split it into parts, a database, logins with hashed passwords, tests, configuration from the environment and a way to deploy it.
Why we need it
One app.py with global objects is fine for 50 lines. At 2,000 lines it gets hard to find things, tests change each other's data, secrets end up in git, and two people cannot work on it at the same time without conflicts.
How it works
create_app() builds a fresh app each time, so tests and production get their own settings. Blueprints put each feature in its own file. The database connection lives on g for one request and is closed by teardown. Passwords are stored only as salted hashes. pytest fixtures give every test a clean app and database.

Bottom line: Use the factory and blueprints for anything you will keep. It costs a few lines and saves a lot when the app grows.

The connection rules in the example
  1. get_db() opens one connection the first time a request needs it and keeps it on g. g lives for one request only.
  2. sqlite3.Row lets you read row["title"] and turn a row into a dict with dict(row).
  3. Always pass values as ? placeholders. The SQL injection attempt above is stored as harmless text.
  4. Call commit() after changes. teardown_appcontext closes the connection after every request, even after an error.
  5. @app.cli.command adds flask init-db, and app.test_cli_runner() runs it from a test.

Remember
Flask turns an exception in a view into a 500 answer. An errorhandler(Exception) can log it and send a friendly message, but must pass HTTPExceptions such as 404 through unchanged, as the example does. Use app.logger, never print, so logs get levels and can go to files or a log service.
Lesson 7 of 11

Deploying a Flask app

From your computer to a public server
  1. List the dependencies in pyproject.toml or requirements.txt (pip freeze > requirements.txt).
  2. Never use flask run --debug in public. Run the app with a WSGI server: gunicorn -w 4 -b 0.0.0.0:8000 "shop:create_app()".
  3. Put nginx (or the hosting platform) in front: it serves HTTPS, static files and passes the rest to Gunicorn.
  4. Set SECRET_KEY, the database URL and other secrets as environment variables on the server.
  5. Use PostgreSQL or MySQL instead of SQLite when many users write at the same time, and run migrations on each release.
  6. Add a health check URL such as /health that returns 200, so the platform can restart the app when it stops answering.
Way to hostYou manageExample
A platform (PaaS)Only the code and settingsRender, Railway, Fly.io, Google App Engine
A containerA Dockerfile, the platform runs itDocker image on Cloud Run, AWS ECS, Kubernetes

Real world scenario: a small team ships every day

A team keeps its Flask shop in git. Every push runs the pytest suite in CI (see the Git and CI/CD subject). When the tests pass on the main branch, CI builds a Docker image with Gunicorn inside and the platform swaps it in. SECRET_KEY and DATABASE_URL live in the platform settings, never in the repository.

The maths: hashing cost, commits and capacity

Guesses per second against a slow hashExam favourite
guesses/s = raw hashes per second / iterations
10 million SHA-256 per second, 1,000,000 PBKDF2 iterations: 10 guesses per second.
Number of passwords
N = (letters in the alphabet)length
8 lower case letters: 268 ≈ 2.09 × 1011.
Average time to guessExam favourite
time ≈ N / 2 / guesses per second
2.09 × 1011 / 2 / 10 per second ≈ 331 years.
Commits
many commits cost n × commit time, one transaction costs one
200 inserts with a 5 ms commit each: 1,000 ms. In one transaction: about 15 ms.
Salt collisions (birthday bound)
n ≈ 1.18 × √(number of salts) for a 50 % chance
32 bit salts: 1.18 × 65,536 ≈ 77,000 users. Werkzeug uses 16 random characters, far more.
Test suite time
time = tests × time per test
120 tests at 15 ms: 1.8 s, fast enough to run on every save.
Worked example: why a fast hash is not enough
  1. A leaked database stores SHA-256 of each password with no salt. A graphics card computes about 10 billion SHA-256 a second.
  2. All 268 ≈ 2.09 × 1011 lower case passwords of 8 letters take about 21 seconds.
  3. With PBKDF2 and 1,000,000 iterations each guess costs a million hashes: 10,000 guesses a second.
  4. The same search now takes 2.09 × 1011 / 10,000 ≈ 2.1 × 107 s, about 242 days, and a salt stops one search from cracking every user at once.
  5. slow, salted hashes turn seconds into months

Going deeper: Application context and request context

current_app and g work only inside an application context, and request and session only inside a request context. Flask pushes both for every request, and the test client does the same. In a script or a test without a request, use with app.app_context(): to get current_app and g.

Lesson 11 of 11

Chapter summary

  1. create_app() builds a fresh app with layered config. Blueprints split features into files, and current_app replaces a global app.
  2. get_db() keeps one sqlite3 connection on g per request, teardown_appcontext closes it, and values always go in as ? placeholders.
  3. Store only salted slow hashes (generate_password_hash), clear the session at login, and protect views with a login_required decorator.
  4. Test with pytest fixtures that build a new app and client for each test. Run commands with test_cli_runner.
  5. Configure from the environment, log with app.logger, and deploy with Gunicorn behind HTTPS, never with the debug server.
