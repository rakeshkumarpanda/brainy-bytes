Lesson 1 of 9

Logging: a diary for your program

Source: Python 3.14 documentation of logging, the Logging HOWTO and Cookbook, logging.config, logging.handlers, pdb, breakpoint() (PEP 553) and the assert statement. The pdb session is a real run.

What it is
Logging means your program writes short messages about what it is doing, each with a level that says how important it is: DEBUG, INFO, WARNING, ERROR or CRITICAL. Debugging is finding out why a program does the wrong thing, with tools such as print, logging, assert and the pdb debugger.
Why we need it
When a program runs on a server at 3 am, nobody is watching the screen. print messages vanish, cannot be switched off without editing code, and say nothing about when or where they came from. Logs are kept in files, can be turned up or down without changing code, and carry the time, module and line, so you can find out later what happened.
How it works
You ask for a logger by name and call logger.info(...) and friends. The logger drops messages below its level. Passing messages become LogRecords that go to handlers (screen, file, email, network), each with its own level and a formatter that decides the text layout.

Remember
Loggers form a tree by name: shop.cart is a child of shop, which is a child of root. A record goes to the handlers of its logger and then, unless propagate is False, up to the parents. Good logging habits

Download this program (.py)Save it, open it in any editor and run it with python3 habits.py.
In the exam
Pass values as arguments: logger.debug("total %s", total). The text is only built if the record passes the level checks. An f-string is always built, even when the message is thrown away, as the first slow __str__ line shows.
Common mistake
Inside except, logger.exception("...") logs at ERROR level and adds the full traceback. Never log passwords, card numbers or personal data: logs are read by many people and kept for a long time.

Bottom line: print is for the output your user asked for. Messages about how the program is doing belong in logging.

Remember
Configure logging once, at program start, with dictConfig (or a file read into a dict, often YAML or TOML). Libraries must never call basicConfig: they only call getLogger(__name__), and the application decides what to show. dictConfig switches off loggers that already exist unless you set "disable_existing_loggers": False.

Bottom line: reproduce the bug first, then use a debugger to watch it happen. Keep logging in place for the bugs you cannot reproduce.

Common mistake
assert checks a condition you believe is always true and raises AssertionError if not. Python started with -O skips every assert, so never use assert to check user input. Raise ValueError for that.

The maths: log volume, rotation and bisecting

Log volumeExam favourite
bytes = lines per second × bytes per line × seconds
50 lines a second of 200 bytes for a day (86,400 s) is 864,000,000 bytes, about 864 MB.
Disk used by a rotating logExam favourite
max size = (backupCount + 1) × maxBytes
maxBytes 1 MB with backupCount 4: at most 5 MB, for ever.
Levels shown for a given level L
shown = levels with number ≥ L
With WARNING (30): WARNING, ERROR and CRITICAL, 3 of 5.
Sampling
lines kept = events / N when keeping 1 in N
1 in 100 of 2,000,000 requests: 20,000 lines.
Bisecting a bug (halving the suspect code)
checks = ⌈log2 n⌉
64 suspect lines: 6 checks with well placed prints or breakpoints.
Error budget
allowed failures = requests × (1 − target)
1,000,000 requests at 99.99 % success allow 100 failures. 120 ERROR lines use 120 % of the budget.
Worked example: how much disk does a month of logs need?
  1. 50 lines per second × 200 bytes = 10,000 bytes per second.
  2. One day: 10,000 × 86,400 = 864,000,000 bytes = 864 MB.
  3. Thirty days: 864 MB × 30.
  4. 25,920 MB, about 25.9 GB, unless you rotate and delete old files

From beginner to expert

One idea, four depths

Use logging.basicConfig and the five levels, and debug with print and f"{x=}".

Use named loggers with getLogger(__name__), handlers with their own levels and formatters, %s arguments and logger.exception.

Configure a whole app with dictConfig and rotating files, use pdb and breakpoint() with breakpoints, stepping and the call stack, and use assert correctly.

Design logs for machines: structured JSON lines with request ids, central collection (ELK, Loki, CloudWatch), sampling and error budgets. Use QueueHandler for slow sinks, post mortem debugging with pdb.pm(), and remote or conditional breakpoints.

Beginner
Log with levels and print debug.
Intermediate
Build loggers, handlers and formatters.
Expert
Configure, debug and run logging in production.

Chapter summary

  1. Five levels: DEBUG 10, INFO 20, WARNING 30 (the default), ERROR 40, CRITICAL 50.
  2. basicConfig for small scripts. Named loggers with getLogger(__name__), handlers with their own levels and formatters for real programs.
  3. Records pass the logger level, go to its handlers (each filters again), then propagate to parent loggers.
  4. Pass values as %s arguments so text is only built when needed. Use logger.exception inside except. Never log secrets.
  5. Configure once with dictConfig. Rotate files so logs do not fill the disk. Libraries only call getLogger.
  6. Debug with f"{x=}", assert for things that must always be true (off with -O), and pdb or breakpoint() to stop and look.
