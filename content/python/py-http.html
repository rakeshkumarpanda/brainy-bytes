How the web works: one request, one response

Source: RFC 9110 (HTTP semantics), RFC 9111 (caching), RFC 3986 (URLs) and the Python 3.14 documentation of urllib, http.server and http.client.

What it is
HTTP (HyperText Transfer Protocol) is the language that browsers, apps and servers use to talk. A client sends a request (a method such as GET, a path and some headers) and the server sends back a response (a status code, headers and usually a body). HTTPS is the same thing inside an encrypted TLS connection.
Why we need it
Programs written in different languages on different computers need one shared, simple set of rules to ask for data and send it. Without a standard every website and app would need its own protocol.
How it works
HTTP messages are plain text lines sent over a TCP connection: a first line, headers, a blank line, then the body. Because the format is so simple, any language can read and write it, and Python has it in the standard library.

In the exam
URLs may only contain a small set of characters. Others, like spaces, é or & inside a value, must be percent encoded: each byte becomes % and two hex digits, so a space is %20 and é (2 bytes in UTF-8) is %C3%A9. Use urlencode or let requests do it with params=, never glue query text together by hand.

Rules of a good REST API
  1. Paths name things (nouns): /books, /books/2/reviews. The method says the action, so there is no /getBook or /deleteBook.
  2. Use the status code that fits: 201 after creating, 404 for missing, 400 or 422 for bad input, never 200 with an error inside.
  3. Send and accept JSON with Content-Type: application/json, and give errors a JSON body such as {"error": "..."}.
  4. Keep every request stateless: it carries everything the server needs, such as an auth token, so any server in a group can answer it.
  5. Add a version (/v1/books) and paging (?page=2&size=50) before many clients depend on the API.
In the exam
urllib.request.urlopen raises HTTPError for 4xx and 5xx answers. The requests library in the next chapters does not: it returns the response, and you call raise_for_status() when you want an exception.

Common mistake
HTTP itself has no memory between requests. Logins work because the server gives the browser a session cookie or a token, and the client sends it back every time. Mark session cookies HttpOnly, Secure and SameSite, as in the example.

The maths: latency, bandwidth and caching

Time to first byteExam favourite
about (TCP 1 + TLS 1 + request 1) round trips × RTT
RTT 50 ms: 3 × 50 = 150 ms before the first byte of the answer, however small it is.
Transfer time
time = size × 8 / bandwidth
2 MB at 40 Mbit/s: 16 Mbit / 40 = 0.4 s.
Average time with a cacheExam favourite
average = hit rate × hit time + (1 − hit rate) × miss time
80 % hits at 5 ms, misses at 200 ms: 0.8 × 5 + 0.2 × 200 = 44 ms.
Little's law
requests in progress = arrival rate × time per request
200 requests a second, 50 ms each: 10 requests at the same moment.
Bandwidth delay product
bits in flight = bandwidth × RTT
100 Mbit/s and 80 ms: 8 Mbit (1 MB) on the wire at once.
Percent encoding size
a byte outside the allowed set becomes 3 characters
"é" is 2 bytes in UTF-8, so it becomes 6 characters: %C3%A9.
Worked example: why do small requests feel slow far away?
  1. A server in another continent has an RTT of 150 ms. A new HTTPS connection needs about 3 round trips: 450 ms.
  2. The answer is only 5 KB. At 50 Mbit/s that takes 40,000 / 50,000,000 s, less than 1 ms.
  3. So almost all the time is waiting for round trips, not sending data.
  4. Keeping the connection open (requests.Session, HTTP keep alive) saves the 2 handshake round trips on later requests: 150 ms instead of 450 ms.
  5. Latency, not bandwidth, decides the speed of small requests

From beginner to expert

One idea, four depths

Read a URL, know GET and POST, the main status codes and what JSON in a body looks like.

Design REST paths and status codes, use headers for content type, auth and caching, and run a small server with http.server.

Understand safe and idempotent methods, conditional requests, cookies and CORS, and measure latency in round trips.

Know HTTP/2 multiplexing and HTTP/3 over QUIC, TLS 1.3, CDNs, caching rules from RFC 9111, and how to design APIs that evolve for years.

Read and send simple requests.
Intermediate
Design REST endpoints and use headers well.
Expert
Tune latency, caching and protocol versions.

Lesson 9 of 9

Chapter summary

  1. HTTP is a request (method, path, headers, optional body) and a response (status, headers, body) as text lines over TCP. HTTPS adds TLS encryption.
  2. A URL has a scheme, host, port, path, query and fragment. Build query strings with urlencode, never by hand.
  3. GET reads, POST creates, PUT replaces, PATCH changes, DELETE removes. GET, PUT and DELETE are idempotent, POST is not.
  4. Status codes: 2xx success, 3xx redirect, 4xx client mistake, 5xx server failure. REST paths are nouns, methods are verbs.
  5. Headers carry the content type, auth tokens, cookies and caching rules. ETag with If-None-Match gives a cheap 304.
