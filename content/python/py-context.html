Context managers and the with statement

Source: Python 3.14 language reference (the with statement), the data model section on context managers, the contextlib documentation, PEP 343 and PCPP-32-101 block 1.

What it is
A context manager is an object that sets something up at the start of a block and cleans it up at the end, whatever happens in between. The with statement uses it: with open(path) as f: opens a file and promises to close it.
Why we need it
Programs borrow things that must be given back: files, network connections, locks, temporary folders, changed settings. If an error happens halfway, or a return leaves early, the clean up line is easy to skip. A leaked file or a lock that is never released can crash a server hours later. Writing try and finally everywhere works but is long and easy to get wrong.
How it works
with X as v: calls X.__enter__() and stores its return value in v. The body runs. When the body ends, normally, by return, or by an exception, Python calls X.__exit__(type, error, traceback). If __exit__ returns a true value the exception is suppressed, otherwise it continues.

Remember
A file object is its own context manager: its __exit__ calls close(). Always open files with with. In CPython an unclosed file is usually closed by garbage collection, but other Pythons (PyPy) and long running programs can run out of file handles first.

Suppressing exceptions

Common mistake
Only return True from __exit__ on purpose and only for the exact errors you expect. Hiding every error makes bugs invisible. contextlib.suppress(SomeError) is the clear, ready made way to say "this error is fine here".

Several managers and ExitStack

Download this program (.py)Save it, open it in any editor and run it with python3 many.py.
In the exam
Managers are entered left to right and exited in the reverse order, like a stack: the last one opened is the first one closed. That is what you want: an inner resource that depends on an outer one is cleaned up first.
Download this program (.py)Save it, open it in any editor and run it with python3 exitstack.py.
Remember
ExitStack is for when the number of managers is only known while the program runs. enter_context adds a manager, callback adds any function to call at the end, and everything is cleaned up in reverse order, even if opening the third file fails.
Going deeper: async with

Async code uses async with and the methods __aenter__ and __aexit__ (or @contextlib.asynccontextmanager), so the set up and clean up can await network calls. Advanced 5.2 uses it with asyncio.

The maths: leaks, failures and exit order

Exit order of n nested managersExam favourite
the k-th one entered is the (n − k + 1)-th one exited
with A, B, C: A is entered 1st and exited 3rd.
Chance that at least one of n steps failsExam favourite
1 − (1 − p)n
Each of 10 steps fails with p = 0.01: 1 − 0.9910 ≈ 9.6 %. Errors are common, so clean up must not depend on success.
Expected leaks without with
leaks = calls × p (chance a path forgets to close)
1000 calls with p = 0.02 leak about 20 files. With with: 0.
Time until a leaking server runs out of file handles
requests = free handles / leaks per request
1024 handles and 2 leaks per request: 512 requests.
Elapsed time with a timer context manager
elapsed = texit − tenter
Entered at 1.50 s, exited at 2.75 s: 1.25 s.
Worked example: a server that leaks file handles
  1. 2000 requests per minute, and 5 % of them forget to close a file: 2000 × 0.05 = 100 leaks per minute.
  2. The limit is 1024 open handles and 24 are in use: 1000 are free.
  3. Minutes until the limit: 1000 / 100.
  4. 10 minutes, then every open() fails. A with statement makes the leak rate 0.

From beginner to expert

One idea, four depths

Open files with with and know the file is closed afterwards, even after an error.

Write context manager classes with __enter__ and __exit__, and generator based ones with @contextmanager and try and finally.

Suppress exact errors on purpose, use several managers in one with, ExitStack for a dynamic number, and the standard ones: locks, temporary folders, chdir, redirect_stdout, localcontext.

with is defined by PEP 343: Python looks up __enter__ and __exit__ on the TYPE (not the object), calls __exit__ with the exception triple, and treats a true result as suppression. @contextmanager wraps the generator and throws the body exception in at the yield. ExitStack unwinds callbacks in LIFO order and chains exceptions raised during clean up.

Beginner
Use with for files.
Intermediate
Write context managers both ways.
Expert
Combine managers and explain the protocol exactly.

Chapter summary

  1. with X as v: runs X.__enter__() (its return value goes into v), then the body, then X.__exit__(type, error, traceback), whatever happens.
  2. Clean up in __exit__ runs after errors, return and break, so resources are never leaked.
  3. __exit__ returning True hides the exception. Use contextlib.suppress for the exact errors you expect.
  4. @contextmanager: code before yield is set up, after yield is clean up. Wrap the yield in try and finally.
  5. Standard managers: open, locks, TemporaryDirectory, chdir, redirect_stdout, localcontext, closing, nullcontext, mock.patch.
  6. Several managers enter left to right and exit right to left. ExitStack handles a number known only at run time.
