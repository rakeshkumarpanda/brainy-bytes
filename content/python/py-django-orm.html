The ORM: asking the database in Python

Source: Django 6.1 documentation: making queries, the QuerySet API, aggregation, query expressions, database access optimization, migrations, forms and ModelForms, validation, authentication and permissions, transactions and testing tools.

What it is
An ORM (object relational mapper) lets you read and change database rows as Python objects. In Django you write Book.objects.filter(year__gte=1900) and Django writes, sends and reads the SQL for you.
Why we need it
Writing SQL by hand for every page is slow, easy to get wrong and easy to make unsafe. Each database (SQLite, PostgreSQL, MySQL) also speaks a slightly different SQL. And the code that turns rows into objects is the same boring work every time.
How it works
A QuerySet collects your conditions step by step and runs one SQL query only when you read the results. Values always travel as parameters, so input cannot change the SQL. The same Python works on every supported database, and migrations keep the tables in step with the models.
Three ways to talk to a database from Python
Raw SQL (sqlite3)Django ORMSQLAlchemy
You writeSQL text with ? placeholdersBook.objects.filter(...)select(Book).where(...) or the ORM
Changes to tablesALTER TABLE by handmakemigrations and migrateAlembic
JoinsWritten by handauthor__name follows the ForeignKeyjoin() or relationships
Hard reportsFull SQL powerannotate, Subquery, Window, or raw() when neededVery close to SQL
Used withSmall scriptsDjangoFlask, FastAPI, scripts

Bottom line: Use the ORM for almost everything in Django. Look at the SQL it writes with str(queryset.query) or the query count in tests, and drop to raw SQL only for the rare report the ORM cannot express.

What the example shows
  1. Building the QuerySet ran no SQL. Reading it in the list comprehension ran exactly one query.
  2. Q objects combine conditions with | (OR) and ~ (NOT). distinct() removes the copies that a join through tags can make.
  3. F("stock") means "the value in this row". update(stock=F("stock") + 10) runs inside the database, so two users at the same time cannot overwrite each other.
  4. aggregate returned one dict. annotate gave every author an n, and filter(n__gte=2) after it became HAVING.
  5. The printed SQL shows the LEFT OUTER JOIN, GROUP BY and HAVING that Django wrote.
Remember
The QuerySet keeps the rows it read. Looping twice over the same QuerySet runs one query, but calling filter() again builds a new QuerySet and runs new SQL. Save a QuerySet in a variable when you need it twice.

Rules that keep migrations safe
  1. Commit the migration files to git together with the model change. Never edit a migration that others have already run, write a new one instead.
  2. A new column on a table with rows needs a default or null=True, otherwise Django asks what to put into the old rows.
  3. Split big changes: add the new column, fill it with a data migration (RunPython), and only then remove the old column in a later release.
  4. Inside RunPython use apps.get_model("books", "Book"), the model as it was at that migration, never an import of the current model.
  5. Give RunPython a reverse function (or RunPython.noop) so the migration can be undone.
Remember
SQLite cannot change most column types in place, so the SQL above makes a new table, copies the rows and renames it. PostgreSQL runs a short ALTER TABLE instead. Django picks the right way for each database.

The maths: query counts, indexes and transactions

Queries in a loopExam favourite
N + 1 without help, 1 with select_related, 2 with prefetch_related
20 books: 21, 1 and 2 queries.
Time of a pageExam favourite
time ≈ queries × round trip + work
21 queries at 1.5 ms: 31.5 ms. 1 query: 1.5 ms plus a bigger row.
Search without an index
rows read = n
1,000,000 books: the database reads all of them.
Search with a B-tree indexExam favourite
steps ≈ logb(n)
With about 100 keys per page: log100(1,000,000) = 3 page reads.
Rows from a join table (many to many)
pairs = books × average tags
20 books with 2 tags each: 40 rows in book_tags.
Weighted average (LeetCode 1251)
average = Σ(price × units) / Σunits
(5 × 100 + 20 × 15) / 115 = 800 / 115 ≈ 6.96.
Worked example: is the index worth it?
  1. A shop has 1,000,000 orders and the page filters by customer_id.
  2. Without an index the database scans every row: 1,000,000 rows.
  3. A B-tree index with about 100 keys per page needs log100(106) = 6 / 2 = 3 page reads to find the first match.
  4. The cost: every INSERT also updates the index, and the index takes disk space. For a column you filter on often, that is a good deal.
  5. 1,000,000 rows → about 3 page reads

Going deeper: Subquery and OuterRef

A Subquery puts one query inside another. OuterRef("id") inside it means "the id of the row in the outer query". The LeetCode solutions use it to find the unique id of each employee and the price that was valid on each sale date. Django writes it as a correlated subquery in one SQL statement.

Going deeper: Zero downtime migrations

On a busy site the old code keeps running while the new one starts. So a migration must work with both: first add a nullable column and deploy code that writes it, then fill old rows, then make the column required, and only in a later release remove what the old code needed. This is called expand and contract.

Chapter summary

  1. A QuerySet is lazy: filter, exclude and order_by build one SQL query that runs when you read it. Q gives OR and NOT, F uses column values inside the database.
  2. aggregate gives one answer, annotate gives one per row with GROUP BY. select_related (a JOIN) and prefetch_related (one more query) fix the N + 1 problem.
  3. makemigrations writes the changes into a file for git, migrate runs them, and RunPython moves data. Old rows need a default.
  4. Forms turn text into checked Python values: field checks, clean_<field>, clean, then cleaned_data or save(). Always redirect after a save.
  5. Users store only password hashes, login_required and permissions protect views, atomic() keeps changes all or nothing, and TestCase rolls back after every test.
