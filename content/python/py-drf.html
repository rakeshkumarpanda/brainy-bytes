What Django REST framework adds

Source: Django REST framework 3.18 documentation: tutorial, serializers, views, generic views, viewsets and routers, authentication, permissions, throttling, filtering, pagination, status codes and testing.

What it is
Django REST framework (DRF) is a library on top of Django for building JSON APIs. It adds serializers that turn models into JSON and check incoming JSON, views and ViewSets made for APIs, routers that write the URLs, and ready parts for logins, permissions, rate limits, filters and pages.
Why we need it
A mobile app or a JavaScript front end does not want HTML pages, it wants JSON. With plain Django you would parse JSON by hand, check every field, turn objects into dicts, pick status codes and write the same list, create, read, update and delete views for every model.
How it works
A serializer does for JSON what a form does for HTML: it checks the input and gives clean data, and it turns objects into dicts. A ModelViewSet plus a router gives all the usual endpoints of a model in a few lines, and settings switch on token logins, permissions, throttles and pagination for every view.

Real world scenario: a mobile app and a shop

A shop has a Django site with the admin for staff. The new mobile app needs the same products and orders. The team adds DRF: a ModelViewSet for products (read only for everyone), one for orders (only the owner, token login), pagination of 20, and a throttle of 60 requests a minute per user. The admin and the web pages keep working on the same models, and the tests check every endpoint with APIClient.

The maths: pages, limits and payload size

Number of pagesExam favourite
pages = ⌈ count / page size ⌉
5 books at 2 a page: ⌈2.5⌉ = 3 pages.
Requests allowedExam favourite
rate = requests / window
3/minute: the 4th request in 60 s gets 429.
Wait time in a sliding windowExam favourite
Retry-After = oldest + window − now
Requests at 0, 10 and 20 s, a 4th at 30 s: 0 + 60 − 30 = 30 s.
Requests per day at a limit
per day = rate × windows per day
100/hour: 100 × 24 = 2,400 a day.
Payload size
bytes ≈ rows × bytes per row
20 books of 120 bytes: 2,400 bytes. All 50,000: 6 MB.
Requests to read everything
requests = ⌈ count / page size ⌉
50,000 rows at 100 a page: 500 requests.
Worked example: choosing a page size
  1. A list has 50,000 books of about 120 bytes each in JSON.
  2. Without pages one answer is 50,000 × 120 = 6,000,000 bytes, about 6 MB, too much for a phone.
  3. At 20 per page an answer is 2,400 bytes, and the first screen appears at once.
  4. A client that really needs everything makes ⌈50,000 / 100⌉ = 500 requests at a page size of 100, so allow a larger page_size (with max_page_size) for such clients.
  5. small pages for people, larger pages with a limit for programs

Going deeper: What happens inside a DRF view

APIView.dispatch wraps the Django request in a DRF Request, then runs initial(): perform_authentication, check_permissions and check_throttles, in this order. Then it calls the handler for the method (get, post, or the ViewSet action). An exception anywhere goes to handle_exception, which turns APIException, Http404 and PermissionDenied into JSON answers. Finally the Response is rendered by the renderer the client asked for.

Chapter summary

  1. DRF adds serializers, API views, ViewSets, routers, authentication, permissions, throttles, filters and pagination on top of Django.
  2. A serializer turns objects into dicts and checks incoming data: field checks, validate_<field>, validate, then save().
  3. A ModelViewSet and router.register give list, create, retrieve, update, partial_update and destroy. get_queryset and perform_create change the details.
  4. Authentication finds the user, permissions decide (401 or 403), throttles limit the rate (429). Set the owner on the server, never from the body.
  5. Nested serializers need your own create(). Test every endpoint with APITestCase and keep the query count fixed.
