Lesson 1 of 9

Doing many things at once

Source: Python 3.14 documentation of threading, queue, concurrent.futures and multiprocessing, the GIL, and the free-threaded build (PEP 703 and PEP 779). Terminal outputs are real runs on a 4 core machine.

What it is
Concurrency means a program deals with several jobs during the same period, switching between them. Parallelism means jobs really run at the same moment on different CPU cores. A thread is a path of execution inside one process that shares its memory. A process is a separate running program with its own memory.
Why we need it
Most programs spend time waiting: for the network, the disk or a database. While one job waits, the computer could do another. Other programs do heavy calculations, and a modern computer has 4 to 16 cores that sit idle if the program uses only one. Doing jobs one after another wastes both.
How it works
Threads let other work run while one job waits for I/O. Processes run Python code on several cores at once. concurrent.futures gives both the same simple interface: a pool of workers, submit or map, and futures that hold results.

Common mistake
Every thread in a process shares the same global variables and objects. That makes it easy to pass data, and also easy to break data: two threads changing the same object at the same time is a race condition.

Common mistake
counter = counter + 1 is really three steps: read, add, write. If another thread writes between your read and your write, your write wipes out its update. time.sleep(0) here forces a switch at the worst moment, but real programs hit the same bug by chance, often only under heavy load.
ToolUse it to
LockLet only one thread at a time run a block (use with lock:)
RLockA lock the same thread may take again, for recursive code
Semaphore(n)Let at most n threads in at once, for example 5 connections
EventLet threads wait until one sets a flag: event.set(), event.wait()
ConditionWait until some state is true, with wait_for and notify_all
Barrier(n)Wait until n threads have all arrived
queue.QueuePass data between threads safely, with no lock code of your own
In the exam
A deadlock happens when thread 1 holds lock A and waits for lock B while thread 2 holds B and waits for A. Neither can go on. Prevent it by always taking locks in the same order, holding them briefly, or using a timeout.

Lesson 5 of 9

The GIL and processes

The GIL (global interpreter lock) lets only one thread run Python bytecode at a time in the normal CPython build. It keeps the interpreter simple and fast for one thread, but it means threads cannot use several cores for pure Python work. This file does the same CPU heavy work one by one, with threads and with processes:

cpu_bound.pypython
1import time2from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor3 4 5def count_primes(limit):6    count = 07    for n in range(2, limit):8        is_prime = True9        d = 210        while d * d <= n:11            if n % d == 0:12                is_prime = False13                break14            d += 115        if is_prime:16            count += 117    return count18 19 20def timed(label, run):21    start = time.perf_counter()22    results = run()23    print(f"{label:<12} {time.perf_counter() - start:5.2f} s  {results}")24 25 26if __name__ == "__main__":27    jobs = [200_000] * 428    timed("one by one", lambda: [count_primes(n) for n in jobs])29    with ThreadPoolExecutor(max_workers=4) as pool:30        timed("4 threads", lambda: list(pool.map(count_primes, jobs)))31    with ProcessPoolExecutor(max_workers=4) as pool:32        timed("4 processes", lambda: list(pool.map(count_primes, jobs)))
  1. Line 26 Child processes import this file again, so the start code must sit under the if __name__ == "__main__" guard.
  2. Line 31 A ProcessPoolExecutor has the same interface as the thread pool. The function and its arguments are pickled and sent to the child processes.

In the exam
With the GIL, 4 threads are no faster than one (1.37 s against 1.30 s). 4 processes are 3.3 times faster. The free-threaded build python3.14t (officially supported since 3.14) has no GIL, so there 4 threads are fast too.

Bottom line: threads for waiting, processes for calculating. Measure, because the overhead of processes can be bigger than the gain for small jobs.

Going deeper: Start methods and new options in 3.14

multiprocessing can start children by fork (copy the parent, Unix only), spawn (start a fresh Python, the default on Windows and macOS) or forkserver (ask a small clean server process to fork, the default on Linux since 3.14). With spawn and forkserver the child imports your main file, which is why the __main__ guard is required. Python 3.14 also added concurrent.interpreters and InterpreterPoolExecutor: several interpreters in one process, each with its own GIL (PEP 734).

The maths: speedup, Amdahl and pool sizes

Speedup and efficiencyExam favourite
S = T1 / Tn, E = S / n
1.30 s alone, 0.40 s with 4 processes: S = 3.25, E = 0.8125 (about 81 %).
Amdahl's lawExam favourite
S(n) = 1 / ((1 − p) + p / n)
p = 0.9 of the work can run in parallel, n = 4: S = 1 / (0.1 + 0.225) ≈ 3.08.
The limit of Amdahl's law
S(∞) = 1 / (1 − p)
With p = 0.9, even a million cores give at most 10 times.
Gustafson's law
S(n) = n − (1 − p)(n − 1)
If the problem grows with the cores: n = 4, p = 0.9 gives 3.7.
Threads for I/O workExam favourite
threads ≈ cores × (1 + wait time / compute time)
4 cores, 90 ms waiting and 10 ms computing per job: 4 × 10 = 40 threads.
Little's law
L = λ × W
200 requests per second that each take 0.25 s: 50 requests in progress, so about 50 workers.
Lost updates
final = expected − lost
4 threads × 100 additions should give 400. Every overwrite loses one.
Worked example: is it worth buying 8 more cores?
  1. A job takes 100 s. Profiling shows 80 s can run in parallel, so p = 0.8.
  2. With 4 cores: S = 1 / (0.2 + 0.8 / 4) = 1 / 0.4 = 2.5, so 40 s.
  3. With 12 cores: S = 1 / (0.2 + 0.8 / 12) = 1 / 0.2667 ≈ 3.75, so about 26.7 s.
  4. The 20 s serial part never shrinks. Making it faster helps more than more cores.
  5. 8 more cores: from 40 s to about 26.7 s, never below 20 s

From beginner to expert

One idea, four depths

Run I/O jobs in a ThreadPoolExecutor and know that threads help with waiting, not with calculating.

Start and join threads, protect shared data with a Lock, pass work through queue.Queue, use futures with as_completed, and use a ProcessPoolExecutor with the __main__ guard for CPU work.

Explain the GIL, race conditions and deadlocks, choose between Event, Condition, Semaphore and Barrier, and size pools with Amdahl and Little.

Use the free-threaded build and know which C extensions are ready for it, use subinterpreters, shared memory (multiprocessing.shared_memory) and lock free designs, and reason about memory ordering and contention.

Lesson 9 of 9

Chapter summary

  1. Threads share memory inside one process. Processes have their own memory and their own interpreter.
  2. I/O bound work: threads (they let go of the GIL while waiting). CPU bound work: processes, or python3.14t without the GIL.
  3. ThreadPoolExecutor and ProcessPoolExecutor share one interface: submit, map, as_completed and futures whose result() raises errors.
  4. Shared data needs a Lock (use with lock:). queue.Queue passes work safely. Take locks in one order to avoid deadlocks.
  5. Process code needs the if __name__ == "__main__" guard, and its data must be picklable.
  6. Amdahl's law: the serial part limits the speedup, S(n) = 1 / ((1 − p) + p / n).
