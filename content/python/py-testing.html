Lesson 1 of 11

Why we test, and a first test suite

Source: Python 3.14 documentation of unittest and unittest.mock, and the documentation of pytest 9.2, coverage.py and Hypothesis. Terminal outputs are real runs.

What it is
A test is a small piece of code that calls your code with known inputs and checks the result. A test suite is all of them together, and a test runner (unittest or pytest) finds them, runs them and reports what passed and what failed.
Why we need it
Without tests you check by hand, once, and every later change can silently break something that used to work. Tests check the same things in a second, every time, so you can change and improve code without fear. They also show how the code is meant to be used, and a failing test points straight at the bug.
How it works
Each test follows Arrange, Act, Assert: set up the inputs, call the code, and assert what must be true. The runner records PASSED, FAILED (an assert was false) or ERROR (the test crashed). In test driven development you write the failing test first (red), make it pass (green), then clean up the code (refactor) with the tests watching.

In the exam
unittest is built into Python. A test is a method whose name starts with test_ inside a class that inherits from unittest.TestCase. assertEqual, assertTrue, assertIn, assertRaises and assertAlmostEqual (for floats) check results and give a clear message when they fail.

Common mistake
Tests must not depend on each other or on their order. test_add_more added a book, but test_total still saw only the pen, because setUp made a new cart for each test.

pytest: the most used test runner

pytest needs plain functions and plain assert, and gives much more detail when something fails. Install it with pip install pytest. Here is a small module and its tests:

Property based testing

Instead of picking examples yourself, you state a rule that must hold for EVERY input, and the Hypothesis library (pip install hypothesis) searches for an input that breaks it. Rule: a 100 % discount makes any price free.

test_props.pypython
1from hypothesis import given, strategies as st2 3from shop import discount4 5 6@given(st.floats(min_value=0, max_value=1e6))7def test_full_discount_is_free(price):8    assert discount(price, 100) == 0

In the exam
All 8 example tests passed with 100 % coverage, yet price − price × 100 / 100 can come out a tiny bit below zero because of float rounding. The fix is price × (100 − percent) / 100, which gives exactly 0 at 100 %. The failing price changes from run to run, because Hypothesis tries random inputs.

What to test and how much

Kind of testChecksSpeedHow many
Unit testOne function or class, dependencies mockedMillisecondsMost of them
Integration testSeveral parts together: code plus a real database or fileSecondsSome
End to end testThe whole program as a user uses it (for web apps: Selenium or Playwright)SlowA few for the main journeys
Always testExample for discount(price, percent)
A normal casediscount(80, 50) is 40
The edges of every rangepercent 0 and 100, price 0
Just outside the rangepercent −1 and 101 raise ValueError
Awkward valuesfloats like 0.3, very large prices
Every bug you fixedA regression test that would have caught it
Remember
This shape, many fast unit tests at the bottom and few slow end to end tests at the top, is called the test pyramid. Run the fast tests on every save and all tests in CI (see the Git and CI/CD subject).

The maths: coverage, boundaries and binary search

Line coverageExam favourite
coverage = lines run / total lines × 100 %
17 of 19 lines run: 17 / 19 ≈ 89.5 %.
Boundary value tests for a range a to bExam favourite
test a − 1, a, b, b + 1 (and one value inside)
percent from 0 to 100: test −1, 0, 100, 101 and 50, five tests.
Combinations of k options with v values each
all combinations = vk
3 settings with 4 values each: 64 tests. Pairwise testing covers every pair of values with far fewer, about v2 = 16.
Binary search steps (the LeetCode set)Exam favourite
steps ≤ ⌈log2(n + 1)⌉
n = 1000 sorted items: at most 10 steps. This is also how git bisect finds the commit that broke a test.
Chance a random test hits a bug that needs one value out of N
1 − (1 − 1/N)t after t tests
N = 1000 and t = 100: about 9.5 %. Picking edge cases on purpose beats random luck.
Worked example: how many commits does git bisect test?
  1. A test passed 1000 commits ago and fails now.
  2. Each check halves the commits that could contain the bug.
  3. 210 = 1024 is the first power of 2 that is at least 1000.
  4. at most 10 test runs to find the commit that broke it
Lesson 9 of 11

From beginner to expert

One idea, four depths

Write unittest test cases with assertEqual and assertRaises and run them.

Use setUp, subTest and skip, read failures and errors, and write pytest tests with fixtures, parametrize, approx and raises.

Mock dependencies with Mock, side_effect and patch, measure coverage, test edge cases on purpose, and work test first.

Design for testability (dependency injection, pure functions), write property based tests with Hypothesis, use mutation testing to check that the tests themselves catch bugs, and build a pyramid of unit, integration and end to end tests that runs in CI.

Beginner
Write and run tests.
Intermediate
Use fixtures, parametrize and mocks.
Expert
Design testable code and test the tests.

Chapter summary

  1. A test arranges inputs, acts by calling the code and asserts the result. A runner reports PASSED, FAILED or ERROR.
  2. unittest: TestCase classes, assertEqual, assertRaises, assertAlmostEqual, setUp for a fresh start, subTest for loops, skip.
  3. Mocks replace slow or outside dependencies: return_value, side_effect, assert_called_once_with, patch and patch.object.
  4. pytest: plain assert, fixtures, parametrize, approx, raises, tmp_path, monkeypatch, and detailed failure messages.
  5. Coverage shows which lines ran, not whether the checks are good. Hypothesis searches for inputs that break a rule.
  6. Test normal cases, edges, just outside the edges and every fixed bug. Many unit tests, fewer integration and end to end tests.
