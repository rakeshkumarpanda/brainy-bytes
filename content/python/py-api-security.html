Lesson 1 of 12

What API security is and why every endpoint needs it

Source: RFC 7519 (JWT), RFC 6749 (OAuth 2.0), RFC 7636 (PKCE), RFC 6750 (Bearer tokens), the WHATWG Fetch standard (CORS), the OWASP API Security Top 10 2023, the OWASP Password Storage and Secrets Management cheat sheets, the FastAPI security tutorial, PyJWT 2.15 and the Django 6.1 password hashers.

What it is
API security is the set of checks that decide who is calling (authentication), what they may do (authorization), and how much they may ask for. It also covers how secrets such as passwords and keys are stored, and what a browser is allowed to share between sites.
Why we need it
An API is open to the whole internet. Anyone can send any request with curl, change an id in the URL, add a field to the JSON or send a million requests. Most real breaches of APIs are not clever cryptography attacks. They are a missing check on one endpoint.
How it works
Passwords are stored as slow salted hashes. A login gives a signed token (often a JWT) that each request carries in the Authorization header. Every endpoint checks the token, the scope and the owner of the object. CORS tells browsers which other sites may read the answers. Rate limits, input models and secret keys outside the code close the rest.

Storing passwords and secrets

Way to store a passwordVerdictWhy
Plain textNeverOne leak shows every password, and people reuse them on other sites
EncryptedNeverWhoever has the key can read them all
sha256(password)NeverBillions of guesses a second on a graphics card, and the same password gives the same hash
sha256(salt + password)WeakThe salt stops shared tables, but the hash is still fast
PBKDF2, bcrypt, scrypt, Argon2idYesSalted and slow on purpose. Argon2id and scrypt also need memory
What the example shows
  1. The two sha256 lines for sunshine are identical, so one cracked hash cracks every user with that password.
  2. With a random salt the same password gave two different PBKDF2 strings. The stored string keeps the algorithm, rounds and salt, exactly in the format Django uses (Django's own hasher produced the same string in a check).
  3. 600,000 rounds took about 120 ms. The OWASP Password Storage cheat sheet asks for at least 600,000 rounds of PBKDF2-SHA256, and Django 6.1 uses 1,500,000.
  4. hmac.compare_digest compares in constant time, so the response time leaks nothing.
  5. Tokens, keys and reset codes come from the secrets module. The random module is for games and simulations only.
In the exam
Keep secret keys out of the code: read them with os.environ["SECRET_KEY"], keep a local .env file in .gitignore, and use a vault (AWS Secrets Manager, HashiCorp Vault) in production. A key that was ever pushed to git is burnt: rotate it, because deleting the commit does not remove copies.

What the example shows
  1. A JWT is three base64url parts. The first two are plain JSON that anyone can decode, so a JWT hides nothing. It only proves who made it.
  2. Changing role to admin without the secret made the signature check fail. So did a token signed with another key.
  3. A token past its exp was refused even though the signature was fine.
  4. The verify function decides the algorithm itself. A token that says "alg": "none" is refused instead of trusted.
  5. PyJWT, the library used next, made the exact same token from the same claims and key, byte for byte.
Going deeper: HS256 or RS256

HS256 uses one shared secret to sign and to check, so every service that checks tokens could also make them. RS256 and ES256 sign with a private key and check with a public key, which an auth server publishes as a JWKS (a JSON list of public keys, chosen by the kid in the header). Use them when many services must check tokens but only one may issue them.

Remember
In a browser, an HttpOnly, Secure, SameSite cookie is the safest place for a token, because JavaScript (and so an XSS bug) cannot read it. localStorage is readable by any script on the page.

What the example shows
  1. For the listed origin the answer carried Access-Control-Allow-Origin with that exact origin, plus Vary: Origin so caches keep one copy per origin.
  2. For an unknown origin the header was missing, so a browser hides the answer. The server still ran the request, which is why CORS never replaces a login.

What the example shows
  1. The f-string query turned the input into SQL and returned every user. The ? placeholder sent it as a value and returned nothing. Injection is on the main OWASP Top 10 list, and the fix is the same in every database driver and ORM.
  2. A model with extra="forbid" refused is_admin instead of saving it.
  3. The URL check refused http, 127.0.0.1, the cloud metadata address 169.254.169.254 and a private 10.x address.
  4. A client that asked for a million rows got at most 100.
Real world scenario: a bug bounty report

A tester signs up for a delivery app and opens their own order: GET /api/orders/81234. They change the number to 81233 and see a stranger's name, address and phone. Every endpoint checked that the token was valid, and none checked who owned the order. The fix was to write Order.objects.get(id=order_id, customer=request.user), and a test now calls every id endpoint with a second user and expects 404.

A security checklist before an API goes live
  1. Every endpoint has an authentication dependency, and public ones are marked public on purpose.
  2. Every endpoint that takes an id filters by the caller, and a test with a second user proves it.
  3. Input models forbid extra fields, response models hide secret fields, and page sizes are capped.
  4. Passwords use a slow salted hash, tokens are short lived and checked with pinned algorithms, aud and iss.
  5. CORS lists exact origins, security headers are set, DEBUG is off and keys come from the environment.
  6. Login and expensive endpoints have rate limits, and logs never contain tokens.

The maths: guessing, entropy, hashing cost and rate limits

Entropy of a random secretExam favourite
bits = length × log2(alphabet size)
12 random lower case letters: 12 × log2 26 ≈ 56.4 bits.
Guesses to try every valueExam favourite
guesses = 2bits
A 6 digit code: 106 = 1,000,000 values.
Time to crackExam favourite
time = guesses × cost per guess / machines
With PBKDF2 at 0.12 s, one million guesses take 120,000 s on one core.
Chance to guess with a rate limit
P = attempts / values
5 tries on a 6 digit code: 5 / 1,000,000 = 0.0005 %.
Token bucket
allowed in t seconds ≤ capacity + rate × t
Capacity 10, rate 2 per second: at most 10 + 2 × 60 = 130 requests in a minute.
Birthday bound for random ids
P(any repeat) ≈ n2 / 2bits + 1
1 billion random 128 bit ids: about 1018 / 2129, practically zero.
Worked example: is a 6 digit login code safe?
  1. There are 106 = 1,000,000 codes, which is about 20 bits.
  2. Without a limit a script tries them all in minutes, because each guess costs only one HTTP request.
  3. With 5 attempts per code and a new code each time, the chance of a lucky guess is 5 / 1,000,000.
  4. The code also expires after 10 minutes, so an attacker cannot collect tries over days.
  5. short codes are only safe together with attempt limits and expiry
Going deeper: Why HMAC and not sha256(secret + message)

SHA-256 is built so that from sha256(secret + message) anyone can compute sha256(secret + message + more) without knowing the secret. This is the length extension attack. HMAC hashes twice with two derived keys, which closes it. That is why JWTs, webhooks and signed cookies all use HMAC.

From beginner to expert

One idea, four depths

Never store passwords in plain text, keep secrets out of code, use HTTPS and know 401 from 403.

Hash passwords with PBKDF2 or Argon2, issue and check JWTs with PyJWT, protect FastAPI endpoints with OAuth2PasswordBearer and scopes, and set CORS correctly.

Add owner checks everywhere, refresh token rotation, key rotation with kid, rate limits and security headers, and test each with a second user.

Run an OAuth 2.0 server with PKCE and RS256 keys published as JWKS, threat model each API against the OWASP list, and audit logs and dependencies in CI.

Going deeper: OpenID Connect

OAuth 2.0 only says what an app may do. OpenID Connect adds who the user is: the auth server also returns an ID token, a JWT with the user's id, name and e-mail, signed with RS256. "Log in with Google" is OpenID Connect. Libraries such as Authlib handle the flow in Flask, Django and FastAPI.

Lesson 12 of 12

Chapter summary

  1. Store passwords with a slow salted hash (PBKDF2, bcrypt, scrypt or Argon2id), compare with hmac.compare_digest and make tokens with the secrets module.
  2. A JWT is header.payload.signature in base64url. Anyone can read it, only the key holder can sign it. Pin the algorithm and check exp, aud and iss.
  3. Use short access tokens, refresh tokens that work once, and a kid for key rotation. OAuth 2.0 with PKCE is the standard login flow.
  4. Authentication is not authorization: check scopes (403) and the owner of every object (404) on every endpoint.
  5. CORS lets listed origins read answers in a browser, CSRF needs SameSite cookies and tokens, and the OWASP API Top 10 lists the common holes.
