Lesson 1 of 10

What changes when an API is real

Source: requests, urllib3 Retry, httpx and pydantic 2 documentation, RFC 9110 and RFC 6585 (429 and Retry-After), and the AWS Architecture Blog article on exponential backoff and jitter.

What it is
Real APIs are bigger and less polite than examples. Answers come in pages, servers sometimes fail for a moment, they limit how many calls you may make, and the data does not always have the shape the documentation promises. Real API work means handling all four.
Why we need it
A script that reads only the first page misses data. A script that gives up after one 503 fails for no good reason. One that retries too fast makes the outage worse or gets blocked. One that trusts every field crashes deep inside the program on the first odd record.
How it works
Loop over pages with a generator, retry only temporary errors with exponential backoff and random jitter, respect 429 and Retry-After, check the data at the door with pydantic, and use an async client such as httpx when you need many calls at once.

Bottom line: Use exponential backoff with jitter, a maximum wait, a maximum number of tries, and only for errors that may go away.

Rules for good retries
  1. Retry only temporary errors, and only for safe or idempotent requests.
  2. Wait base × 2attempt, pick a random wait between 0 and that number (full jitter), and never more than a cap such as 30 s.
  3. If the server sends Retry-After, wait exactly that long.
  4. Stop after a fixed number of tries and raise a clear error, so the caller knows.
  5. With requests you can mount HTTPAdapter(max_retries=Retry(...)) on a Session, and urllib3 does all of this for you.

Real world scenario: a script that syncs orders every night

A shop syncs 20,000 orders from a partner API that allows 10 calls per second. The script keeps its own token bucket with rate 10, so it never sends faster than allowed. When the partner is busy and sends 429 with Retry-After: 5, the script waits 5 seconds and goes on. The sync takes about 35 minutes and never gets the API key blocked.

In the exam
A token bucket holds up to capacity tokens and refills rate tokens every second. Each call takes one token, and with no token the call must wait or gets 429. So it allows short bursts but keeps the average at the rate. Servers use it to protect themselves, and clients can use it to stay polite.

What happened
  1. One by one, 5 calls of 0.2 s take 5 × 0.2 = 1.0 s, because each call waits for the one before.
  2. With httpx.AsyncClient and asyncio.gather, all 5 wait at the same time, so the total is about one call: 0.2 s.
  3. An asyncio.Semaphore(2) lets only 2 run at once: ⌈5 / 2⌉ = 3 rounds of 0.2 s = 0.6 s.
  4. Always limit how many calls run at once. Without a limit, 10,000 tasks would open 10,000 connections and hit every rate limit.

The maths: backoff, limits and pages

Backoff waitExam favourite
waitn = min(cap, base × 2n)
base 0.5 s: 0.5, 1, 2, 4, 8 s for n = 0 to 4.
Total backoff time
base × (2k − 1) for k waits
base 1 s, 4 waits: 1 + 2 + 4 + 8 = 15 s.
Full jitter
wait = random(0, base × 2n), mean = base × 2n / 2
n = 3, base 1 s: random between 0 and 8 s, 4 s on average.
Token bucket in time TExam favourite
at most capacity + rate × T calls
rate 5/s, capacity 20, 10 s: 20 + 50 = 70 calls.
Rows skipped by an offset
skipped = (page − 1) × size
page 50, size 20: 980 rows read and thrown away.
Calls in flight (Little's law)Exam favourite
L = rate × time per call
100 calls/s at 0.25 s each: 25 at the same moment.
Worked example: how many tries are enough?
  1. A call fails for a short time with probability 0.2, and each try is independent.
  2. With 1 try the call fails with probability 0.2.
  3. With 4 tries all must fail: 0.24 = 0.0016, that is 16 in 10,000.
  4. With backoff base 0.5 s the 3 waits add up to 0.5 + 1 + 2 = 3.5 s at most, which is fine for a nightly job but too long for a web page.
  5. P(all k tries fail) = pk

From beginner to expert

One idea, four depths

Loop over pages until there are no more, and know which errors are worth a retry.

Write page generators, retries with backoff and jitter, respect 429 and Retry-After, and check answers with pydantic.

Run many calls at once with httpx and a Semaphore, keep a client side token bucket, and use cursors for data that changes.

Design clients with idempotency keys, circuit breakers and timeouts on every layer, and measure them with logs and metrics.

Beginner
Read every page safely.
Intermediate
Retry, limit and validate.
Expert
Build clients that stay up when the API does not.
Going deeper: Circuit breaker

If an API keeps failing, every caller still waits for timeouts and retries. A circuit breaker counts failures, and after too many it "opens": calls fail at once for a while without touching the network. After a pause it lets one test call through and closes again if that works. Libraries such as pybreaker do this, and service meshes do it for whole systems.

Lesson 10 of 10

Chapter summary

  1. APIs answer in pages. Walk them with a generator. Cursors stay correct while data changes, page numbers do not.
  2. Retry only temporary errors (timeouts, 429, 502, 503, 504) and only safe requests, with exponential backoff, jitter and a cap.
  3. Respect 429 and Retry-After. A token bucket allows bursts but keeps the average rate.
  4. Check answers at the door with pydantic: types, required fields and nested data, with clear errors.
  5. httpx.AsyncClient with asyncio.gather runs many calls at once. Always limit them with a Semaphore.
