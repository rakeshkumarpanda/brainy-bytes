Lesson 1 of 15

When things go wrong: exceptions

Source: Python 3.14 tutorial chapter 8, library reference Built-in Exceptions, PCEP-30-02 section 4.4 and PCAP-31-03 section 3.

What it is
An exception is an object Python raises when something goes wrong while the program runs: text that is not a number, a missing key, a file that is not there, dividing by zero. If nobody handles it, the program stops and prints a traceback.
Why we need it
Real programs meet bad input, broken networks and missing files every day. A program that crashes on the first typo is useless. Exceptions separate the normal path from the error path, so you can say "try this, and if this kind of problem happens, do that instead", and keep running.
How it works
You put risky code in a try block. When an exception is raised, Python stops that block at once and looks for an except clause whose class matches. If it finds one, that handler runs and the program carries on after the try statement. If not, the exception travels up to the caller, then its caller, until something handles it or the program ends.
Real world scenario: a payment that fails

You pay for a train ticket and your bank declines the card. A good app does not freeze or close. It catches the "payment declined" error, shows "Please try another card", keeps your booking details, and lets you try again. That is an except clause. Closing the payment window in every case, success or failure, is the finally clause.

An unhandled exception (real Python 3.14 output)shell
$ python3 crash.py
Traceback (most recent call last):
  File "/tmp/crash.py", line 3, in <module>
    print(total / len(marks))
          ~~~~~~^~~~~~~~~~~~
ZeroDivisionError: division by zero
Remember
Read a traceback from the bottom up. The last line names the exception and the reason. The lines above show where it happened, with the newest call last. Python 3.11 and later mark the exact part of the line with ^ and ~ characters.

The exception hierarchy and the order of handlers

Download this program (.py)Save it, open it in any editor and run it with python3 order.py.
What it is
Exceptions are classes arranged in a family tree. ZeroDivisionError is a child of ArithmeticError, which is a child of Exception, which is a child of BaseException.
Why we need it
Sometimes you want to handle one exact problem, sometimes a whole family of related problems. The tree lets one except clause do either.
How it works
except SomeClass catches that class and all its children. Python tries the handlers from top to bottom and runs the first match only. So put the most specific classes first. A handler for a parent placed first would catch everything and the specific handlers below it would never run.
Common mistake
Avoid a bare except: or except BaseException:. They also catch KeyboardInterrupt and SystemExit, so Ctrl+C stops working. Catch Exception at most, and only where you log or report the error.

In the exam
The order is fixed: try, then except clauses, then else, then finally. You need at least one except or a finally. else keeps code out of the try block, so you do not accidentally catch errors from it.

Remember
A low level function often cannot know what the right reaction is. average should not print "No marks yet" because it may be used in a web page or a report. Let it raise, and handle the exception at the level that knows what to tell the user. This is called delegating responsibility.

Since Python 3.11 a program can raise several unrelated exceptions at once in an ExceptionGroup, for example when ten network tasks run together and three fail (Advanced 5.1). except* picks out the parts of the group it can handle and lets the rest travel on.

Counting and reasoning about failures

Handlers checked before a matchExam favourite
position of the first matching except clause
Python stops at the first match, so order decides the cost and the meaning.
Chance that at least one of n independent steps failsExam favourite
1 − (1 − p)n
With p = 1 percent per network call, 50 calls fail at least once with chance 1 − 0.9950 ≈ 39 percent. Errors are normal at scale, so handle them.
Expected tries until success (retry loop)
1 / q
If each try succeeds with chance q = 0.8, you need 1.25 tries on average (a geometric distribution).
Exponential back off before retry k
wait = base × 2k
1, 2, 4, 8 seconds. Used by web clients so a busy server is not flooded (Web 2.2).
Worked example: a 3 step booking with failure chances 2, 5 and 1 percent
  1. Chance that every step works: 0.98 × 0.95 × 0.99.
  2. 0.98 × 0.95 = 0.931, and 0.931 × 0.99 = 0.92169.
  3. Chance of at least one failure: 1 − 0.92169 ≈ 7.8 percent
  4. About 1 booking in 13 meets an error, so every step needs a clear except path.
Lesson 13 of 15

From beginner to expert

One idea, four depths

An exception is an error while the program runs. try runs risky code, except handles a problem, and the program goes on.

Catch specific classes, most specific first. Use as err to read the message. else runs when nothing failed, finally always runs. Exceptions travel up through function calls until something handles them.

Raise your own errors with raise, re-raise with a bare raise, chain causes with from, write custom exception classes, use assert only for programmer checks, prefer EAFP, and close resources with with.

CPython 3.11 made try blocks zero cost: entering a try does nothing at run time, and only raising looks up an exception table. Tracebacks are linked frame objects (__traceback__), which can keep large objects alive if you store an exception. Exception groups and except* support structured concurrency in asyncio TaskGroup.

Beginner
Wrap a risky line in try and except ValueError and keep the program running.
Intermediate
Order several handlers, use else and finally, and let errors propagate to the right level.
Expert
Design an exception hierarchy for a program, chain causes, and choose between EAFP and LBYL.

Chapter summary

  1. An exception is raised when something goes wrong while the program runs. Unhandled, it stops the program with a traceback. Read tracebacks from the bottom.
  2. try holds risky code. except X handles X and its child classes. as err gives the exception object.
  3. Handlers are checked top to bottom and only the first match runs, so put specific classes first.
  4. else runs when try raised nothing. finally always runs, even after return.
  5. Exceptions travel up the call stack until handled. Handle them where you know what to do.
  6. raise X("message") raises, a bare raise re-raises, and raise ... from err records the cause.
  7. Write your own exceptions as subclasses of Exception. Use assert only for programmer checks.
  8. Prefer EAFP for files and conversions, and with for anything that must be closed.
