Lesson 1 of 10

Big O: how the work grows

Source: Python 3.14 documentation of timeit, cProfile, pstats, tracemalloc, sys.getsizeof and functools.lru_cache, and the TimeComplexity page of the Python wiki. Terminal outputs are real runs with CPython 3.14.

What it is
Time complexity says how the number of steps of an algorithm grows when the input gets bigger. We write it in Big O notation: O(1), O(log n), O(n), O(n log n), O(n²). Space complexity says the same about memory.
Why we need it
A program that is quick with 100 items can take hours with 1,000,000. Timing it on your laptop does not tell you that, because the time depends on the computer and the data you tried. Big O tells you, before you run anything, how the program will behave when the data grows.
How it works
Count the basic steps (a comparison, an addition, a lookup) as a function of n, the size of the input. Keep only the part that grows fastest and drop constant factors: 3n² + 5n + 7 becomes O(n²). Then check with real measurements (timeit) and find the slow part with a profiler (cProfile).

Lesson 2 of 10

Finding the Big O of code

Four rules
  1. Drop constants. 2n + 10 steps is O(n). Big O is about the shape of the growth, not the exact count.
  2. Keep the biggest term. n² + n is O(n²), because for large n the n² part is almost all the work.
  3. Loops one after another add. A loop over n, then another loop over n: O(n + n) = O(n).
  4. Loops inside loops multiply. A loop over n inside a loop over m: O(n × m). Over the same list: O(n²).
Common mistake
Hidden loops count too. x in my_list, my_list.index(x), my_list.remove(x), my_list.insert(0, x), "".join and slicing a[i:j] each walk through items. Putting one of them inside a loop is the most common way Python code becomes quadratic by accident.

Average case versus worst case: a dict lookup is O(1) on average, but if many keys had the same hash it could take O(n). Python adds random salt to str hashes so attackers cannot cause this on purpose. For interviews and exams, dict and set operations are O(1).

Remember

In the exam
sys.getsizeof is shallow. For a list it counts the list and its slots, not the objects inside, which is why a list holding a huge number has the same size as one holding a small number. tracemalloc counts every allocation made while it runs, so it shows the real memory a piece of code needed.

Amortized cost and trading memory for time

Download this program (.py)Save it, open it in any editor and run it with python3 amortized.py.
Remember
Most appends cost one step. Now and then the array is full and must copy everything, which costs n steps. But because the space doubles each time, the copies add up to less than n in total, so the average (amortized) cost per append stays about 1. That is why list.append is called O(1) amortized.

Lesson 7 of 10

The maths behind Big O

Definition of Big OExam favourite
f(n) = O(g(n)) if there are numbers c > 0 and n0 with f(n) ≤ c · g(n) for every n ≥ n0
3n + 5 = O(n): take c = 4 and n0 = 5, since 3n + 5 ≤ 4n when n ≥ 5.
Big Omega and Big Theta
Ω(g) is a lower bound, Θ(g) means both O(g) and Ω(g)
Comparison sorting is Ω(n log n): no comparison sort can do better.
Sum of a loop inside a loopExam favourite
1 + 2 + ... + n = n(n + 1) / 2 = O(n²)
Comparing each item with the ones after it: 1000 items give 499,500 comparisons.
Geometric sum (doubling)Exam favourite
1 + 2 + 4 + ... + n = 2n − 1 < 2n
Copies for 1024 appends with doubling: 1 + 2 + ... + 512 = 1023, about 1 per append.
Halving
steps = ⌊log2 n⌋ + 1
Binary search in 1,000,000 sorted items: at most 20 steps.
Master theoremExam favourite
T(n) = a·T(n/b) + O(nd) gives O(nd) if d > logb a, O(nd log n) if d = logb a, O(nlogb a) if d < logb a
Merge sort: a = 2, b = 2, d = 1. log2 2 = 1 = d, so O(n log n).
Time estimate
seconds ≈ steps / (about 107 simple Python steps per second)
n = 105 with O(n²) is 1010 steps: about 1000 s. With O(n log n) it is 1.7 × 106: about 0.17 s.
Worked example: is this fast enough for 100,000 items?
  1. The code compares every pair: n(n − 1) / 2 comparisons.
  2. n = 100,000 gives 100,000 × 99,999 / 2 = 4,999,950,000, about 5 × 109.
  3. At about 107 simple steps per second in Python: 5 × 109 / 107 = 500 seconds.
  4. Sorting first (n log2 n ≈ 100,000 × 17 = 1.7 × 106) and then one scan takes well under a second.
  5. O(n²): about 8 minutes. O(n log n): under 1 second
Going deeper: Why log n has no base in Big O

log2 n = log10 n / log10 2, so logs with different bases differ only by a constant factor, and Big O drops constant factors. O(log2 n), O(ln n) and O(log10 n) are the same class.

From beginner to expert

One idea, four depths

Know O(1), O(n) and O(n²), see that a loop inside a loop is slow, and use a set for "is it there" questions.

Work out the Big O of functions with the four rules, know the costs of list, dict, set and deque operations, measure with timeit and find the slow function with cProfile.

Use amortized analysis, the master theorem and recurrences, measure memory with tracemalloc, and trade memory for time with caching and dynamic programming.

Reason about lower bounds (Ω(n log n) for comparison sorting), cache misses and memory layout, hash collision attacks, sampling profilers in production, and when C extensions, NumPy or PyPy change the constants.

Beginner
Spot slow loops and pick the right container.
Intermediate
Analyse, measure and profile.
Expert
Prove bounds and tune real systems.

Chapter summary

  1. Big O says how steps grow with n. Drop constants, keep the biggest term. Loops in a row add, loops inside loops multiply.
  2. O(1) dict and set lookups, O(log n) binary search, O(n) one pass, O(n log n) sorting, O(n²) nested loops.
  3. Watch for hidden loops: x in list, remove, insert(0, x) and slicing inside a loop make code quadratic.
  4. Measure with timeit (best of several runs, realistic n). Find the slow function with cProfile before optimising.
  5. getsizeof is shallow. tracemalloc shows real memory. Generators save memory.
  6. list.append is O(1) amortized because space doubles. lru_cache trades memory for time.
