Part 1🌱 Beginner

🗺️From source code to output

When you run python main.py, the computer does not understand Python directly. A program called the interpreter reads your file and does the work for you. The interpreter almost everyone uses is CPython, written in the C language and published by the Python Software Foundation. It is the one you download from python.org, and it is what this chapter describes.

CPython works in two stages, just like Java. First it compiles your text into bytecode, a list of small instructions. Then the Python Virtual Machine runs that bytecode one instruction at a time. The big difference from Java is that you never call the compiler yourself. Python does both stages every time you press Run, in a fraction of a second.

hello.py · ▶ Runs
# hello.py: a small bill, the kind of program every learner writes first
name = "Asha"
items = 3
price = 40
total = items * price
print("Hi", name + "!", "Your bill is", total, "rupees")
Output
Hi Asha! Your bill is 120 rupees

Here is the same journey for this small bill, in plain words:

  1. Read. CPython opens hello.py and reads it as text, using UTF-8 by default.
  2. Tokenize. The characters are grouped into tokens such as total, =, items, *.
  3. Parse. The tokens are checked against Python's grammar and arranged into a tree.
  4. Compile. The tree becomes bytecode inside a code object.
  5. Run. The evaluation loop runs the bytecode. print is a built in function written in C, and it writes the text to your screen.

People often say "Python is interpreted" and "Java is compiled". Both statements are half true. CPython compiles your code to bytecode and then interprets the bytecode. Python the language is a set of rules. An implementation is a program that follows those rules. There are several:

Part 4🌿 Intermediate

🔤Step 1: the tokenizer

The tokenizer, also called the lexer, reads characters from left to right and groups them into tokens, the smallest pieces that mean something. It is the same thing you do when you read a sentence: you see words, not single letters.

Python has a special job here that most languages do not have. Indentation is part of the grammar, so the tokenizer keeps a stack of indentation levels. When a line is indented more than the previous one, it produces an INDENT token. When the indentation goes back, it produces a DEDENT token. The parser never sees spaces, only these tokens.

The tokens Python sees, including INDENT and DEDENT · ▶ Runs
import io, tokenize

source = """if total > 100:
    discount = 10
print(discount)
"""
for tok in tokenize.generate_tokens(io.StringIO(source).readline):
    kind = tokenize.tok_name[tok.type]
    print(f"{kind:<9} {tok.string!r:<14} line {tok.start[0]}")
Output

  • NEWLINE ends a logical line of code. NL is a line break that does not end a statement, such as a blank line or a line inside brackets.
  • OP covers operators and punctuation like >, =, : and brackets.
  • Mixing tabs and spaces so that the meaning is unclear raises TabError right here, before anything runs.
You can see the tokens of any file from a terminal with python -m tokenize main.py.
Part 5🌿 Intermediate

🌳Step 2: the parser and the syntax tree

The parser takes the tokens and checks them against Python's grammar. Since Python 3.9, CPython uses a PEG parser (Parsing Expression Grammar), generated from a grammar file that lives in the CPython source. The result is an abstract syntax tree, or AST. "Abstract" means that brackets, spaces and commas are gone. Only the meaning is kept.

The syntax tree of one line · ▶ Runs
import ast

tree = ast.parse("total = price * qty + 5")
print(ast.dump(tree, indent=2))
Output
Module(
  body=[
    Assign(
      targets=[
        Name(id='total', ctx=Store())],
      value=BinOp(
        left=BinOp(
          left=Name(id='price', ctx=Load()),
          op=Mult(),
          right=Name(id='qty', ctx=Load())),
        op=Add(),
        right=Constant(value=5)))])

Read the tree from the bottom up. price * qty is a BinOp with Mult. That whole node is the left side of another BinOp with Add. The tree already encodes that multiplication happens before addition, so the later stages never think about operator precedence again.

The parser reads the whole file before anything runs. That is why one syntax error stops the program completely, even the lines above it that are fine:

A syntax error stops the program before line 1 runs · 💥 Raises an error
print("Step 1: this line never runs")
total = 100
if total > 50
    print("big order")
Output
  File "main.py", line 3
    if total > 50
                 ^
SyntaxError: expected ':'
Tools you use every day read this tree: pytest rewrites assert statements in it, linters such as Ruff and Pylint walk it to find bugs, and formatters like Black rebuild your file from it. The ast module lets your own code do the same.
Part 6🌿 Intermediate

🏭Step 3: the compiler and code objects

The compiler walks the tree and produces a code object. It does this in three small steps:

  1. Symbol table. For every function, the compiler decides whether each name is local, global, from an enclosing function or free. This decision is made once, here, and never changes while the program runs.
  2. Code generation. Each node of the tree becomes one or more instructions.
  3. Optimisation. A peephole optimiser cleans up the instruction list. It removes dead code, shortens jumps and folds constants.

Every function has its own code object, stored in __code__. It is a plain Python object you can inspect:

Inside a code object · ▶ Runs
def add_tax(price, rate=0.18):
    tax = price * rate
    return round(price + tax, 2)

code = add_tax.__code__
print("name:         ", code.co_name)
print("arguments:    ", code.co_argcount)
print("local names:  ", code.co_varnames)
print("constants:    ", code.co_consts)
print("other names:  ", code.co_names)
print("bytecode size:", len(code.co_code), "bytes")
print(add_tax(100))
Output
name:          add_tax
arguments:     2
local names:   ('price', 'rate', 'tax')
constants:     (2,)
other names:   ('round',)
bytecode size: 54 bytes
118.0

The dis module (short for disassembler) prints the bytecode in a readable form. The first column is the source line, then the instruction name, its argument, and in brackets what the argument means.

Read the bytecode with dis · ▶ Runs
import dis

def add_tax(price, rate):
    tax = price * rate
    return price + tax

dis.dis(add_tax)
Output
  3           RESUME                   0

  4           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (price, rate)
              BINARY_OP                5 (*)
              STORE_FAST               2 (tax)

  5           LOAD_FAST_BORROW_LOAD_FAST_BORROW 2 (price, tax)
              BINARY_OP                0 (+)
              RETURN_VALUE

Notice LOAD_FAST_BORROW_LOAD_FAST_BORROW. Local variables live in a small array inside the frame, so reading one is just an index, which is fast. Here the compiler even joined two local loads into one superinstruction. STORE_FAST writes to that array. Global names need slower dictionary lookups.

Look at the code object again: the default value 0.18 is not among the constants. Defaults are worked out once, when the def line runs, and kept on the function in add_tax.__defaults__. The 2 in the constants is the second argument of round.

Constant folding is the easiest optimisation to see. Arithmetic on plain numbers is done once by the compiler, not every time the line runs:

Constant folding · ▶ Runs

# The compiler does arithmetic on plain numbers once, before the program runs
dis.dis("seconds_per_day = 60 * 60 * 24")
Output

  1           LOAD_CONST               2 (86400)
              STORE_NAME               0 (seconds_per_day)
              LOAD_CONST               1 (None)
              RETURN_VALUE
Bytecode changes in every Python release. LOAD_SMALL_INT and LOAD_FAST_BORROW are new in 3.14, and 3.15 will change more. Bytecode is an internal detail. Use it to understand Python, never as something your programs depend on.
Part 7🌿 Intermediate

💾__pycache__ and .pyc files

Compiling is quick, but a big project imports hundreds of modules. To save that work, CPython writes the bytecode of every imported module to a .pyc file in a folder named __pycache__, next to the source. The next run checks that the .pyc is still fresh and loads it directly, skipping the tokenizer, the parser and the compiler.

Watch __pycache__ appear, then read a .pyc header · 🧪 Run in a terminal
📄 shop.py
GST = 0.18

def bill(amount):
    return round(amount * (1 + GST), 2)
📄 main.py
import shop

print("Bill for 100 rupees:", shop.bill(100))

What the example shows:

  • Only shop.py got a .pyc. The script you start, main.py, is compiled in memory every time and never cached.
  • The name shop.cpython-314.pyc holds the cache tag, so Python 3.13 and 3.14 can share a folder without breaking each other.
  • The 16 byte header starts with a magic number that changes whenever the bytecode format changes. If it does not match, the file is ignored and rebuilt.
  • By default the header also stores the source file's modification time and size. If you edit shop.py, they no longer match and Python compiles it again.
  • python -B or the environment variable PYTHONDONTWRITEBYTECODE=1 stops Python from writing .pyc files. PYTHONPYCACHEPREFIX moves them all to one separate folder.
ToolWhat it does
python -m py_compile shop.pyCompile one file to its .pyc
python -m compileall src/Compile a whole folder, used when building Docker images and installers
--invalidation-mode checked-hashStore a hash of the source instead of the time, for builds that must be reproducible
A .pyc file is not faster to run. It only starts faster, because the compile step is skipped. It also does not hide your code: tools can turn it back into readable Python. Always add __pycache__/ to .gitignore.
Part 8🔥 Advanced

🔁Step 4: the evaluation loop

Now the code object meets the evaluation loop, the heart of CPython. It is a C function that repeats three things for as long as the program runs: read the next instruction, do what it says, move on. Each instruction works with a value stack. Loading a name pushes its value on top. An operator pops its inputs and pushes its result. Storing a name pops the top value.

Every instruction has an offset · ▶ Runs
import dis

code = compile("total = price * qty", "<bill>", "exec")
for ins in dis.get_instructions(code):
    print(f"{ins.offset:>3}  {ins.opname:<16} {ins.argrepr}")
Output
  0  RESUME           
  2  LOAD_NAME        price
  4  LOAD_NAME        qty
  6  BINARY_OP        *
 18  STORE_NAME       total
 20  LOAD_CONST       None
 22  RETURN_VALUE

The offsets go up by 2 because every instruction takes two bytes: one for the instruction and one for its argument. Some instructions also keep hidden cache entries after them, which is why offsets can jump by more.

The loop itself is surprisingly simple. Here is the whole idea in a few lines of Python. Press Line by line to watch the stack change.

Build your own evaluation loop in 15 lines · ▶ Runs
# A tiny stack machine that works the way the CPython evaluation loop does
program = [("LOAD", "price"), ("LOAD", "qty"), ("MULTIPLY", None), ("STORE", "total")]
names = {"price": 40, "qty": 3}
stack = []

for op, arg in program:
    if op == "LOAD":
        stack.append(names[arg])
    elif op == "MULTIPLY":
        right = stack.pop()
        left = stack.pop()
        stack.append(left * right)
    elif op == "STORE":
        names[arg] = stack.pop()
    print(f"{op:<9} {str(arg):<6} stack = {stack}")

print(names)
Output
LOAD      price  stack = [40]
LOAD      qty    stack = [40, 3]
MULTIPLY  None   stack = [120]
STORE     total  stack = []
{'price': 40, 'qty': 3, 'total': 120}

The real loop knows about 150 instructions (see dis.opmap) plus more than 80 specialized forms of them, and many tricks for speed, but this is honestly how it works. Between instructions, CPython also checks for a few things: a pending signal such as Ctrl + C, a request to switch threads, and the hooks used by debuggers.

Part 9🔥 Advanced

🧱Frames, the call stack and tracebacks

Every time a function is called, CPython creates a frame. A frame holds everything that one call needs: which code object it is running, the current instruction, the local variables and its own value stack. Frames sit on the call stack. The newest one is on top and is the one running. When a function returns, its frame is thrown away and the one below continues from where it paused.

A traceback is a print of the call stack at the moment an error happened. Python prints it with the oldest frame first, which is why it says "most recent call last". Read it from the bottom up: the last lines show the error and the exact place it happened.

A traceback is the call stack, printed · 💥 Raises an error
def apply_coupon(total, code):
    discounts = {"SAVE10": 10, "SAVE20": 20}
    return total - discounts[code]

def checkout(cart_total, coupon):
    return apply_coupon(cart_total, coupon)

print(checkout(500, "SAVE10"))
print(checkout(500, "FREE100"))
Output

Walk the frames, then hit the recursion limit · ▶ Runs
import sys

def inner():
    frame = sys._getframe()
    chain = []
    while frame:
        chain.append(frame.f_code.co_name)
        frame = frame.f_back
    return chain

def middle():
    return inner()

print(middle())
print("recursion limit:", sys.getrecursionlimit())

def countdown(n):
    return 0 if n == 0 else countdown(n - 1)

try:
    countdown(5000)
except RecursionError as e:
    print("RecursionError:", e)
Output
['inner', 'middle', '<module>']
recursion limit: 1000
RecursionError: maximum recursion depth exceeded

Since Python 3.11, frames are small C structures inside the interpreter. A full Python frame object, the one sys._getframe() returns, is only built when someone asks for it. This change made function calls much cheaper.

The recursion limit (1000 by default) protects your program from running out of stack memory. You can raise it with sys.setrecursionlimit, but a loop is usually the better fix for deep recursion.
Part 10🔥 Advanced

🔎Names and scopes: the LEGB rule

When the evaluation loop needs a name, it searches up to four places in a fixed order: Local, Enclosing, Global and Built-in. The first match wins.

Local, Enclosing, Global, Built-in · ▶ Runs
rate = 0.18                        # global name

def make_bill(price):
    discount = 5                   # enclosing name, seen by the inner function
    def final():
        total = price - discount   # local name
        return round(total * (1 + rate), 2)   # round is found in builtins
    return final()

print(make_bill(100))

import builtins
print("round lives in builtins:", builtins.round is round)
Output
112.1
round lives in builtins: True

Here is the part that surprises people. The decision "is this name local" is made by the compiler, not while the program runs. If a function assigns to a name anywhere in its body, that name is local everywhere in the function, even on lines before the assignment.

Why UnboundLocalError happens · ▶ Runs
import dis

visits = 0

def add_visit():
    visits = visits + 1    # the compiler sees an assignment, so visits is local here
    return visits

try:
    add_visit()
except UnboundLocalError as e:
    print("UnboundLocalError:", e)

dis.dis(add_visit)
Output
UnboundLocalError: cannot access local variable 'visits' where it is not associated with a value
  5           RESUME                   0

  6           LOAD_FAST_CHECK          0 (visits)
              LOAD_SMALL_INT           1
              BINARY_OP                0 (+)
              STORE_FAST               0 (visits)

  7           LOAD_FAST_BORROW         0 (visits)
              RETURN_VALUE

The bytecode shows the reason: the compiler used LOAD_FAST_CHECK for visits, an instruction for local names, so Python never looked at the global. Add global visits at the top of the function to tell the compiler you mean the module level name, or better, pass the value in and return the new one.

Part 11🌿 Intermediate

📦Everything is an object

In Python, every value is an object that lives in memory: numbers, strings, lists, functions, classes, even modules. Every object has three things: an identity (its address, shown by id()), a type (shown by type()) and a value.

A variable is not a box that holds a value. It is a name that points at an object. Two names can point at the same object. This is the single most useful fact for understanding Python's behaviour.

Names point at objects · ▶ Runs
a = [1, 2, 3]
b = a                  # a second name for the same list
b.append(4)
print(a, a is b, id(a) == id(b))

c = [1, 2, 3, 4]
print(a == c, a is c)  # equal values, two different objects

x = 256
y = int("256")
print("256 is shared:", x is y)
x = 257
y = int("257")
print("257 is shared:", x is y)

print(type(5), type(type(5)), isinstance(print, object))
Output
[1, 2, 3, 4] True True
True False
256 is shared: True
257 is shared: False
<class 'int'> <class 'type'> True
  • == asks "do these have the same value". is asks "are these the very same object".
  • CPython creates the integers from -5 to 256 once at startup and shares them, because they are used everywhere. That is why 256 is 256 is true and the same test with 257 can be false. Never use is to compare numbers or strings. Use it only for None, True and False.
  • Strings that look like names are often interned: kept once and shared. Python does this for its own identifiers to make attribute and dictionary lookups faster.
Part 12🔥 Advanced

🧹Memory: reference counting and the garbage collector

CPython frees memory in two ways.

Reference counting. Every object keeps a count of how many references point at it. A new name, a list slot or a function argument adds one. When a reference goes away, the count drops. When it reaches zero, the object is freed at once. This frees the vast majority of objects, and it does so immediately, which is why a file object that nobody uses any more gets closed straight away in CPython.

The cycle collector. Reference counting has one weak spot: a reference cycle. If object A points at B and B points back at A, both counts stay above zero even when your program can no longer reach either of them. The gc module finds such groups of unreachable objects and frees them.

Reference counts and a reference cycle · ▶ Runs
import sys, gc

order = {"id": 1042}
before = sys.getrefcount(order)
alias = order
print("one more name adds one reference:", sys.getrefcount(order) - before)
del alias
print("del removes it again:", sys.getrefcount(order) - before)

class Node:
    def __init__(self, name):
        self.name = name
        self.partner = None
    def __del__(self):
        print("freed", self.name)

a, b = Node("a"), Node("b")
a.partner, b.partner = b, a    # a cycle: each keeps the other alive
del a, b
print("names deleted, but nothing was freed yet")
found = gc.collect()
print("the cycle collector found unreachable objects:", found > 0)
print("collector thresholds:", gc.get_threshold())
Output
one more name adds one reference: 1
del removes it again: 0
names deleted, but nothing was freed yet
freed a
freed b
the cycle collector found unreachable objects: True
collector thresholds: (2000, 10, 10)

The collector runs automatically when enough new container objects have been created since the last run. The thresholds above control how often that happens. It sorts objects into generations, because most objects die young: new objects are checked often, and objects that survive several collections are checked rarely.

A 3.14 story worth knowing. Python 3.14.0 shipped an incremental collector, which spreads the work over many small steps. Users then reported that some production systems used a lot more memory, so Python 3.14.5 went back to the generational collector from 3.13. Real projects found a problem that tests had not, and the core team chose the safe option.

Small objects (up to 512 bytes) do not come straight from the operating system. CPython's own allocator, pymalloc, takes memory in 1 MiB arenas, splits them into 16 KiB pools, and splits each pool into equal sized blocks. Many tiny objects can then be created and freed very quickly.

Part 13🔥 Advanced

🔒The GIL, threads and free-threaded Python

The Global Interpreter Lock (GIL) is a lock inside CPython. A thread must hold it to run Python bytecode, so in a normal build only one thread runs Python code at any moment. Reference counting is the main reason it exists: without the lock, two threads could change the same count at the same time and break it.

Four threads share one counter safely · ▶ Runs
import sys, threading

print("GIL enabled:", sys._is_gil_enabled())
print("switch interval:", sys.getswitchinterval(), "seconds")

counter = 0
lock = threading.Lock()

def work():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1

threads = [threading.Thread(target=work) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("counter:", counter)
Output
GIL enabled: True
switch interval: 0.005 seconds
counter: 400000
  • The running thread is asked to give up the GIL every 5 milliseconds, the switch interval, so other threads get a turn.
  • Waiting for a network reply, a file or time.sleep releases the GIL. That is why threads still speed up programs that mostly wait, such as API tests or web scraping.
  • Pure Python number crunching does not get faster with threads in the normal build. Use processes (multiprocessing, concurrent.futures.ProcessPoolExecutor) or libraries like NumPy, which do their heavy work in C without the GIL.
  • The GIL does not make your code thread safe. counter += 1 is several instructions, and a switch can happen between them. The example uses a Lock for that reason.

Free-threaded Python. Python 3.13 added an experimental build without the GIL, installed as python3.13t. In Python 3.14 it is officially supported, though still optional. Threads then run Python code truly in parallel on several CPU cores. Single threaded code runs a little slower in that build, and some C extensions are not ready yet, so measure your own program before you switch.

Python 3.14 also added the concurrent.interpreters module. It runs several interpreters inside one process, each with its own modules and its own GIL, so they can work in parallel while staying isolated.

A second interpreter in the same process (new in 3.14) · ▶ Runs
from concurrent import interpreters

worker = interpreters.create()
worker.exec("total = sum(range(1, 101))\nprint('inside the second interpreter, total =', total)")
print("the main interpreter has its own globals:", "total" not in globals())
worker.close()
Output
inside the second interpreter, total = 5050
the main interpreter has its own globals: True
Part 14🧠 Expert

🚀Faster CPython: specialization and the JIT

Since Python 3.11, CPython watches your code while it runs. This is the specializing adaptive interpreter. When an instruction keeps seeing the same kind of data, CPython swaps it for a specialized version that skips the general checks. A BINARY_OP that always multiplies two small integers becomes BINARY_OP_MULTIPLY_INT. If the data changes later, it goes back to the general form.

The specializing interpreter rewrites hot code · ▶ Runs
import dis

def price_with_tax(price):
    return price * 118 // 100

print("Before warming up:")
dis.dis(price_with_tax, adaptive=True)

for p in range(1000):
    price_with_tax(p)

print("After 1000 calls:")
dis.dis(price_with_tax, adaptive=True)
Output
Before warming up:

              LOAD_SMALL_INT         118
              BINARY_OP                5 (*)
              LOAD_SMALL_INT         100
              BINARY_OP                2 (//)
              RETURN_VALUE
After 1000 calls:
  3           RESUME_CHECK             0

  4           LOAD_FAST_BORROW         0 (price)

This happens on its own. You do not change anything in your code, and programs got noticeably faster between 3.10 and 3.11 just from this work.

The JIT compiler. Python 3.13 added an experimental just in time compiler. It uses a technique called copy and patch: ready made pieces of machine code are copied and filled in for hot sequences of instructions. In 3.14 it is included in the official Windows and macOS installers but stays off by default. You switch it on with the environment variable PYTHON_JIT=1. Whether it is available at all depends on how your Python was built.

Is the JIT here, and is it on · 🧪 Run in a terminal

Python 3.14 also brought a new way to build the interpreter loop itself, called the tail-call interpreter. When CPython is built with a recent Clang compiler, each instruction becomes its own small C function. The gain is a few percent, and you get it simply by using a Python built that way.

The order of what helps speed, from biggest to smallest, is almost always: a better algorithm, a library that does the work in C (NumPy, pandas, polars), a newer Python version, and only then tricks like the JIT.

📥What import really does

import greet looks like one small step, but it is a whole process, and it explains many real bugs.

What import really does · ▶ Runs
📄 greet.py
print("greet.py is running its top level code")
WELCOME = "Namaste"

    return f"{WELCOME}, {name}!"

if __name__ == "__main__":
    print("this line runs only when greet.py is started directly")
📄 main.py
import sys
import greet          # first import: find greet.py, compile it, run it once
import greet          # second import: already in sys.modules, nothing runs

print(greet.hello("Ravi"))
print("cached in sys.modules:", "greet" in sys.modules)
print("loaded from:", greet.__spec__.origin.split("/")[-1])
print("this file's __name__:", __name__)
Terminal
$ python main.py
Output

Namaste, Ravi!
cached in sys.modules: True
loaded from: greet.py
this file's __name__: __main__
  • A module's top level code runs once, on the first import. Later imports reuse the same module object from sys.modules.
  • if __name__ == "__main__": works because the file you start gets the name "__main__", while an imported file gets its own module name.
  • sys.path is the list of folders Python searches. The folder of the script you started comes first, then the standard library, then site-packages, where pip installs packages.
  • The finders and loaders are ordinary Python objects in importlib. Tools such as pytest add their own to change how modules are loaded.
Part 16🔥 Advanced

🏁What happens before your first line runs

Between pressing Enter on python main.py and your first line, CPython does a lot of setup work:

  1. Reads the command line options and environment variables such as PYTHONPATH.
  2. Creates the main interpreter, its memory allocators and the builtins module with print, len and friends.
  3. Imports the modules it needs for itself, mostly from frozen copies built into the program, so they load very fast.
  4. Builds sys.path and imports the site module, which adds site-packages and processes .pth files.
  5. Compiles main.py as the module __main__ and starts the evaluation loop on it.
What is ready before your first line runs · ▶ Runs
import sys

print("folder of this script is first on sys.path:", sys.path[0] != "")
print("modules loaded before line 1 ran:", len(sys.modules) > 20)
print("optimize flag:", sys.flags.optimize, "| -B flag:", sys.flags.dont_write_bytecode)
print("builtins ready:", callable(print), callable(len))
Output
folder of this script is first on sys.path: True
modules loaded before line 1 ran: True
optimize flag: 0 | -B flag: 0
builtins ready: True True

sys.monitoring arrived in Python 3.12. Tools switch on only the events they need, so coverage tools and profilers slow your program down much less than with settrace.

sys.monitoring: low cost events (3.12 and later) · ▶ Runs
import sys

mon = sys.monitoring
TOOL = mon.PROFILER_ID
calls = {}

def on_start(code, offset):
    calls[code.co_name] = calls.get(code.co_name, 0) + 1

mon.use_tool_id(TOOL, "call counter")
mon.register_callback(TOOL, mon.events.PY_START, on_start)
mon.set_events(TOOL, mon.events.PY_START)

def tax(amount):
    return amount * 0.18

def bill(amount):
    return amount + tax(amount)

for price in (100, 200, 300):
    bill(price)

mon.set_events(TOOL, 0)
mon.free_tool_id(TOOL)
print(calls)
Output
{'bill': 3, 'tax': 3}

🧪Python internals in test automation

🧪 QA essentialpytestSeleniumPlaywrightAssertion messages, import side effects and parallel runs all come straight from how CPython compiles and imports code.

Knowing how Python runs explains several things testers meet every week.

pytest rewrites your asserts. A plain assert only says "AssertionError". pytest installs its own import hook, reads each test module's syntax tree, and rewrites every assert so that it records the values involved. The rewritten bytecode is cached with its own tag, as you can see in the file name.

pytest rewrites assert before your test runs · 🧪 Run in a terminal

    return sum(prices) - discount

from cart import total

def test_total_with_discount():
    prices = [120, 80, 50]
    assert total(prices, discount=20) == 200

  • python -O removes every assert at compile time. Never use assert for checks your application needs in production.
  • Import side effects run once per process. Code at the top level of conftest.py or a page object module runs during collection, before any test. Put setup in fixtures instead.
  • pytest-xdist runs tests in several worker processes, not threads, so CPU heavy tests really run in parallel even with the GIL. Each worker has its own sys.modules and its own memory, so global state is not shared between workers.
  • A stale __pycache__ copied between machines with a different Python version is ignored safely, because of the magic number and the cache tag. Still, keep it out of Git.

🎬Real world scenario: "it works on my machine"

🧪 QA essentialShadowed modules and wrong sys.path order cause failures that only happen on some machines, which testers are often first to see.
The situationA dice game test suite passes on one laptop and fails in CI with AttributeError: module 'random' has no attribute 'randint'. Nobody changed the code that rolls the dice. Someone had added a small settings file to the project and named it random.py.
A file named random.py breaks import random · 🧪 Run in a terminal
📄 random.py
# The team kept its dice settings in a file called random.py
FACES = 6
📄 main.py
import random

roll = random.randint(1, 6)
print("rolled a number from 1 to 6:", 1 <= roll <= 6)
Terminal
$ python main.py
$ mv random.py dice_settings.py
$ python main.py
Terminal output
Traceback (most recent call last):
  File "main.py", line 3, in <module>
    roll = random.randint(1, 6)
           ^^^^^^^^^^^^^^
AttributeError: module 'random' has no attribute 'randint' (consider renaming 'random.py' since it has the same name as the standard library module named 'random' and prevents importing that standard library module)
--- after renaming random.py to dice_settings.py
rolled a number from 1 to 6: True

The import system explains it. The folder of the script comes first on sys.path, so import random found the team's file before the standard library one. Python 3.13 and later even say so in the error message. On the laptop that passed, the tests happened to be started from a different folder, so the standard module won.

How the team fixed it for good:

  1. Renamed the file to dice_settings.py and deleted the old __pycache__ folders.
  2. Moved the code into a package folder (src/dice/), so its modules have unique names such as dice.settings.
  3. Added a lint rule that flags module names that hide standard library modules.
  4. Added python -c "import random; print(random.__file__)" to the CI log, so the next time anything shadows a module, the log shows where it came from.
