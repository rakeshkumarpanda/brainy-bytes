What Django is and why it has so much built in

Source: Django 6.1 documentation: tutorial parts 1 to 7, URL dispatcher, views, class based views, templates, models, the admin site, settings, middleware, CSRF protection and the deployment checklist.

What it is
Django is a Python web framework with everything a website needs in one package: URL routing, views, a template language, an ORM that turns Python classes into database tables, migrations, users and logins, forms, an admin site and strong security defaults.
Why we need it
With a small framework you choose and connect many libraries yourself: one for the database, one for migrations, one for logins, one for forms, one for an admin page. Each choice takes time, and the parts do not always fit together. Most business websites need all of these parts.
How it works
Django gives one tested way to do each job, and all parts know each other. A model you write is used by migrations, forms, the admin and the ORM at the same time. You write models.py, views.py, urls.py and templates, and Django does the rest of the work around them.
Three popular Python web frameworks
FlaskDjangoFastAPI
StyleSmall core, add what you needEverything built inBuilt for JSON APIs, uses type hints
DatabaseYour choice (sqlite3, SQLAlchemy)The Django ORM with migrationsYour choice (SQLAlchemy, SQLModel)
Users and adminExtensions such as Flask-LoginBuilt in: auth and a full admin siteWrite them or add libraries
HTML pagesJinja templatesDjango templatesPossible, but not its focus
Good forSmall apps, services, learningShops, news sites, internal tools, big projectsFast APIs with automatic docs

Bottom line: Pick Django when the site has users, data and an admin team. Pick Flask or FastAPI for a small service or an API without pages. Step 5 shows Django REST framework and FastAPI.

In the exam
Django calls its pattern MTV: the Model holds the data, the Template shows it, and the View decides what to show. It is the same idea as MVC, only the names differ: the Django view does the job of an MVC controller.

The commands you use every day
  1. django-admin startproject mysite makes the project once. python manage.py startapp books makes each app.
  2. Add the app to INSTALLED_APPS, write the models, then run python manage.py makemigrations and python manage.py migrate.
  3. python manage.py createsuperuser makes an admin user. python manage.py runserver starts the development server at http://127.0.0.1:8000/.
  4. python manage.py shell opens Python with your project loaded, which is handy to try ORM queries.
  5. python manage.py check --deploy lists settings that are not safe for production.
Remember
A project is the whole website with its settings. An app is one feature, such as books, accounts or payments. A good app does one thing, so you could even reuse it in another project.

Bottom line: Start with functions, because you can read them from top to bottom. Use generic class based views such as ListView and DetailView when a page is a standard list or detail page.

What the example shows
  1. Django tries urlpatterns from top to bottom and calls the first view that matches. The names, such as "book-detail", let reverse() and the template tag url build links, so a URL can change in one place.
  2. request.GET holds the query string and request.POST the form fields. HttpResponse sends text, JsonResponse sends JSON.
  3. Raising Http404 gives a 404 answer. @require_http_methods(["POST"]) gives 405 to every other method.
  4. redirect("book-detail", book_id=3) sends a 302 to the new page. This is the Post, Redirect, Get pattern again.
  5. /hello/Ann without the last slash gets a 301 to /hello/Ann/, because CommonMiddleware with APPEND_SLASH adds it.
In the exam
The test client does not check CSRF tokens unless you ask it to, so the POST in the example works without one. In a real project CsrfViewMiddleware is on, and every POST form needs {% csrf_token %}. The animation above shows what happens without it.

What the example shows
  1. Each model class becomes a table named app label plus model name, here shop_book. Django adds an id column as the primary key.
  2. Book.objects is the manager. create() inserts a row, all() and filter() give a QuerySet, get() returns exactly one object.
  3. Lookups such as year__gte=1900 or author__name__startswith="Frank" become WHERE clauses. The double underscore can even follow a ForeignKey into the other table.
  4. related_name="books" gives the other direction: herbert.books.all().
  5. update() and delete() on a QuerySet change many rows with one SQL statement. str(queryset.query) shows the SQL Django wrote.
In the exam
In a project you never call schema_editor yourself. You change models.py, run makemigrations to write a migration file, and migrate to run it. Chapter 4.2 goes much deeper into the ORM and migrations.

Real world scenario: a small shop with an office team

A bookshop keeps its stock in Django. The developers write the models and three lines of admin.py for each. The office team logs in at /admin/, searches books, fixes prices and adds new titles. Each person gets only the permissions they need, for example "can change book" but not "can delete book", and the admin keeps a history of every change.

Remember
The admin is for trusted staff, not for customers. Use a long random password for the superuser, keep DEBUG off in production, and consider a less obvious address than /admin/.

The maths: URL matching, pages, queries and hashing

URL matching
checks for a URL ≤ number of patterns
Django tries patterns from the top: with 40 patterns the worst case is 40 checks, still well under a millisecond.
Number of pagesExam favourite
pages = ⌈ n / per page ⌉
1,234 books at 50 a page: ⌈24.68⌉ = 25 pages.
OFFSET of a pageExam favourite
OFFSET = (page − 1) × per page
Page 3 at 50 a page: LIMIT 50 OFFSET 100.
The N + 1 problemExam favourite
queries = 1 + n
A list of 50 books that reads book.author in the template: 1 + 50 = 51 queries. select_related makes it 1.
Hashing cost
guesses/s = hashes per second / iterations
Django 6.1 uses PBKDF2 with 1,500,000 iterations: 109 hashes per second give about 667 guesses per second.
Workers needed (Little's law)
busy workers = requests per second × seconds per request
200 requests per second at 0.05 s each keep 10 workers busy.
Worked example: why the list page is slow
  1. A page shows 50 books with their authors. The view uses Book.objects.all() and the template shows book.author.name.
  2. The first query reads the 50 books. Each book.author then runs one more query, 50 in total.
  3. At 2 ms a query that is 51 × 2 = 102 ms only for the database.
  4. Book.objects.select_related("author") joins the two tables, so one query reads everything: about 3 ms.
  5. 51 queries → 1 query, about 34 times faster

Going deeper: How Django starts

django.setup() reads the settings, then fills the apps registry: it imports each app in INSTALLED_APPS, then each app's models module. Only after that can you use models, which is why the programs on this page import models after django.setup(). manage.py and wsgi.py do the same thing for you, using the DJANGO_SETTINGS_MODULE environment variable to find settings.py.

Going deeper: Middleware is an onion

Each middleware wraps the next one. A request passes them from the top of MIDDLEWARE to the bottom, and the response passes them from the bottom to the top. A middleware can also answer at once, as CommonMiddleware does with the 301 and CsrfViewMiddleware with the 403. That is why the order in settings.MIDDLEWARE matters: SessionMiddleware must come before AuthenticationMiddleware, which needs the session.

Chapter summary

  1. Django includes routing, views, templates, an ORM with migrations, users and an admin site. Its MTV pattern is MVC with other names.
  2. startproject makes the project, startapp makes each app, and manage.py runs every command. Add each app to INSTALLED_APPS.
  3. urlpatterns are tried from the top. Converters such as int: change the type, and names let reverse() and the url tag build links.
  4. render() fills a template with a context. Values are escaped, filters change them, and extends with blocks shares one layout.
  5. A model class is a table, makemigrations writes the changes and migrate runs them. QuerySets with lookups become SQL, and admin.register gives a full admin page.
