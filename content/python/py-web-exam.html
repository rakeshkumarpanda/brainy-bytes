This Flask service has eight problems. Find them before you read onpython
1import sqlite32 3import requests4from flask import Flask, jsonify, request5 6app = Flask(__name__)7app.config["SECRET_KEY"] = "dev"8db = sqlite3.connect("shop.db", check_same_thread=False)9 10 11@app.get("/orders/<int:order_id>")12def get_order(order_id):13    row = db.execute(f"SELECT id, customer, total FROM orders WHERE id = {order_id}").fetchone()14    return jsonify(row)15 16 17@app.post("/users")18def create_user():19    data = request.get_json()20    db.execute("INSERT INTO users (name, is_admin) VALUES (?, ?)", (data["name"], data.get("is_admin", 0)))21    return jsonify(data), 20022 23 24@app.get("/rate")25def rate():26    answer = requests.get("https://rates.example/eur")27    return answer.json()28 29 30@app.get("/orders")31def list_orders():32    limit = int(request.args.get("limit", 20))33    rows = db.execute("SELECT id, total FROM orders LIMIT ?", (limit,)).fetchall()34    return jsonify(rows)35 36 37if __name__ == "__main__":38    app.run(debug=True, host="0.0.0.0")
The eight problems
  1. A secret in the code. SECRET_KEY = "dev" signs the session cookies, so anyone who reads the repository can forge them. Read it from os.environ (6.1).
  2. No owner check. Any caller can read any order by changing the number. Filter by the logged in user and answer 404 for other people's orders (6.1, OWASP API1).
  3. SQL built with an f-string. Here int: happens to protect it, but the habit leads to injection. Always use ? placeholders (4.2, 6.1).
  4. Mass assignment. is_admin comes from the request body, so anyone can make themselves an admin. Accept only the fields you expect (6.1, OWASP API3).
  5. No commit and the wrong status. The INSERT is never committed, and a create should answer 201 with the new id, not echo the input with 200 (3.1, 4.2).
  6. No timeout and no status check. requests.get without timeout= can hang the worker for ever, and a 500 from the partner is passed on as if it were data. Use timeout=5 and raise_for_status() (2.1).
  7. No upper limit. limit=10000000 makes the database send every row. Cap it, for example min(limit, 100), and refuse values that are not numbers with 400 (6.1, OWASP API4).
  8. Debug mode on every network interface. debug=True with host 0.0.0.0 offers the interactive debugger, which can run code, to anyone who can reach the port, with only a PIN in the way. Use a real server such as gunicorn with debug off (3.2).

A system design answer: a link shortener API

Interviews for backend roles often end with a design question. Here is a model answer for "Design an API that shortens links", using only what this part taught.

The answer, step by step
  1. Requirements. POST /links with a long URL gives a short code. GET /{code} redirects. Owners can list and delete their links. Expect 100 new links and 10,000 redirects a second.
  2. API. POST /links (201, Location header), GET /{code} (301 or 302 with Location), GET /links?cursor=... (cursor pagination), DELETE /links/{code} (204). Pydantic or a DRF serializer checks the URL (5.1, 5.2).
  3. Codes. 7 characters from 62 letters and digits give 627 ≈ 3.5 × 1012 codes. Make them from secrets or a counter turned into base 62, and retry on the rare clash (6.1).
  4. Storage. A table code (primary key), url, owner, created. Redirects read by primary key, which is one index lookup (4.2).
  5. Speed. Reads are 100 times the writes, so put a cache (Redis) in front: most redirects never touch the database. Answer 301 when links never change, so browsers cache them too (1.1).
  6. Safety. Only http and https URLs, a block list for known bad sites, a login for POST and DELETE, an owner check on delete, and a rate limit per user (6.1).
  7. Async. The redirect does no slow work, so plain workers are fine. Click counting goes to a queue so the redirect never waits for it (5.2).
Codes availableExam favourite
codes = alphabetlength
627 ≈ 3.52 × 1012.
Storage per year
rows = writes per second × seconds per year
100 × 31,536,000 ≈ 3.2 × 109 rows.
Load on the database with a cache
reads to the database = reads × (1 − hit rate)
10,000 × (1 − 0.99) = 100 a second.

Ten problems with the shape of backend work: the slowest call in a log, a request queue on one server, migration order, conversion rates in a graph, a connection pool, a stable latency window, a lock with only 10,000 codes, a deployment pipeline, paid batch jobs and deadlines. No.ProblemLevelPatternHint
1629Slowest KeyEasyOne pass over the gaps between timesLike finding the slowest request in an access log: each duration is the gap to the previous time. Keep the longest, and on a tie the larger letter.
1701Average Waiting TimeMediumSimulate one worker with a clockOne server handles requests in the order they arrive. The clock is the time the server becomes free. A request starts at max(clock, arrival), and its waiting time is the finish time minus the arrival.
210Course Schedule IIMediumTopological sort with in-degrees (Kahn)The same problem as running database migrations or loading apps in dependency order. Start with every item that depends on nothing, and each time one is done, lower the count of the items waiting for it. A cycle leaves items behind, so the answer is empty.
399Evaluate DivisionMediumA weighted graph and a searchLike a currency API that only knows some rates: a / b = 2 is an edge from a to b with weight 2 and from b to a with 0.5. A query multiplies the weights along any path, or gives -1.0 when there is none.
1942The Number of the Smallest Unoccupied ChairMediumTwo heaps: free chairs and busy chairs by leaving timeThis is exactly how a connection pool hands out the lowest free connection number. Go through arrivals in time order, first free every chair whose guest has left, then give the smallest free one.
1438Longest Continuous Subarray With Absolute Diff Less Than or Equal to LimitMediumSliding window with a max deque and a min dequeLike finding the longest stretch where response times stayed within a band. Two deques keep the window's maximum and minimum in O(1). When max minus min is too big, move the left edge.
752Open the LockMediumBreadth first search over 10,000 statesA 4 digit lock has only 104 codes, which is why short codes need attempt limits. BFS from 0000 turns one wheel up or down at each step and skips the dead ends, so the first time it reaches the target is the fewest turns.
2050Parallel Courses IIIHardLongest path in a DAG, in topological orderLike a deployment pipeline where jobs run in parallel once their needs are done: a job finishes at its own time plus the latest finish among the jobs it waits for. The answer is the latest finish of all.
1235Maximum Profit in Job SchedulingHardSort by end time, DP with binary searchLike choosing which paid batch jobs a single worker should run. Sort jobs by end time. The best profit up to a job is either the best without it, or its profit plus the best among jobs that end by its start, found with bisect.
630Course Schedule IIIHardGreedy by deadline with a max heap of durationsTake tasks in order of their deadline. When the total time passes a deadline, drop the longest task taken so far, because that frees the most time while keeping the count. A max heap (negative numbers in heapq) finds it.

Chapter summary

  1. HTTP: the fragment stays in the browser, status class is code // 100, POST and PATCH are not idempotent, JSON keys become strings.
  2. Flask: a bad int: value gives 404, a wrong method 405, dicts become JSON, blueprints add prefixes, and debug=True never goes to production.
  3. Django and DRF: QuerySets are lazy, F updates in SQL, select_related stops N + 1, templates escape by default, serializers list every error.
  4. FastAPI and Pydantic: hints convert and check, every error has a location, async def must not block.
  5. Security: slow salted hashes, signed short lived tokens with pinned algorithms, owner checks on every object, timeouts and limits everywhere.
