Lesson 1 of 11

What a socket is

Source: RFC 9293 (TCP), RFC 768 (UDP), RFC 791 and RFC 4632 (IPv4 and CIDR) and the Python 3.14 documentation of socket, struct, ipaddress and asyncio streams.

What it is
A socket is one end of a network connection inside your program. You give it an address (an IP address and a port), and then you can send and receive bytes through it. Python has the socket module for this, and every web library, from requests to Django, uses sockets underneath.
Why we need it
Two programs on different computers have no shared memory. They need a way to move bytes across the network to the right program, in the right order, even when the network loses or delays packets.
How it works
The operating system does the hard part. The IP address finds the computer, the port finds the program on it, and the protocol decides the rules: TCP gives a reliable, ordered stream of bytes, UDP sends single packets fast with no promises. Your program only calls connect, send and recv.

In the exam
A socket only knows bytes. Turn text into bytes with .encode("utf-8") before sending and back with .decode("utf-8") after receiving. "é" is one letter but 2 bytes, so always measure the length of the bytes, never of the text.
Real world scenario: a network game sends positions

A game sends the x and y position of a player 30 times a second. As text, "1023,887" is 8 bytes and the receiver must split and convert it. With struct.pack("!HH", 1023, 887) it is always exactly 4 bytes, and struct.unpack gives the two numbers back at once. Fixed size binary data is smaller and faster to read, which is why real network protocols use it for their headers.

The life of a TCP server and client
  1. Server: socket(AF_INET, SOCK_STREAM) makes an IPv4 TCP socket. bind((host, port)) claims a port. listen() starts accepting connections.
  2. Server: accept() waits for a client. It returns a NEW socket for that one client plus the client address. The listening socket keeps listening for others.
  3. Client: socket.create_connection((host, port), timeout=5) finds the address, makes the socket and connects in one call.
  4. Both: sendall(data) sends every byte (plain send() may send only part of it). recv(n) returns between 1 and n bytes, or b"" when the other side has closed.
  5. Both: close(), or a with block that closes for you. Always set a timeout, so a dead network cannot make your program wait for ever.

Common mistake
Host "127.0.0.1" (localhost) only accepts connections from the same computer. "0.0.0.0" accepts them from every network card, so other computers can connect. Use 127.0.0.1 while you learn.

Common mistake
A very common bug: the sender calls sendall twice and the receiver expects two recv calls to return the two messages. On a fast local test it often works, and then it fails on a real network. recv only promises "some bytes", so always loop until you have a whole message.
Going deeper: Why TCP cuts the stream

TCP puts your bytes into segments that fit the network. A segment is at most the MSS (usually 1,460 bytes on Ethernet). Nagle's algorithm may join small writes into one segment, and the receiver may read two segments at once. So the borders you see in recv have nothing to do with the borders of your sendall calls.

Bottom line: TCP is better when every byte matters, such as files, web pages and payments. UDP is better when old data is useless anyway, such as the position of a player a second ago, or when one small question needs one small answer, such as DNS.

Remember
A UDP datagram larger than the path allows (about 1,472 bytes of data on normal Ethernet) gets split by IP, and if one piece is lost the whole datagram is lost. Keep UDP messages small.

Bottom line: For new network code use asyncio, or a framework built on it. Threads are fine for small tools, and the one at a time server is only for learning.

What asyncio does in the example
  1. asyncio.start_server opens a listening socket and calls handle() for every new client.
  2. When handle() reaches await asyncio.sleep(0.1) or await reader.readline(), it pauses and the event loop runs another client.
  3. So the three clients wait at the same time, and the whole run takes about 0.1 s instead of 0.3 s.
  4. Under the hood the event loop uses selectors (epoll on Linux, kqueue on macOS) to learn which sockets have data.

A /24 network has 232 − 24 = 256 addresses. The first is the network address and the last is the broadcast address, so 254 are left for computers. Ports go from 0 to 65,535, and ports below 1024 usually need admin rights.

The maths: windows, round trips and loss

Addresses in a networkExam favourite
addresses = 232 − prefix, usable = addresses − 2
/24: 256 addresses, 254 usable. /20: 4,096 addresses.
Data in one packet
MSS = MTU − IP header − TCP header
1,500 − 20 − 20 = 1,460 bytes of your data.
Window limit on speedExam favourite
throughput ≤ window / RTT
A 64 KB window with RTT 100 ms: 65,535 × 8 / 0.1 ≈ 5.2 Mbit/s, however fast the line is.
Window needed
window = bandwidth × RTT (the bandwidth delay product)
100 Mbit/s and 50 ms: 100,000,000 × 0.05 / 8 = 625,000 bytes.
TCP with loss (Mathis formula)Exam favourite
throughput ≈ (MSS / RTT) × 1.22 / √p
MSS 1,460 B, RTT 100 ms, loss p = 0.0001: about 14.2 Mbit/s.
Chance of at least one loss
P = 1 − (1 − p)n
100 packets with p = 0.01: 1 − 0.99100 ≈ 0.634.
Worked example: why a fast line can still be slow
  1. A server is 100 ms away (RTT) on a 1 Gbit/s line. The receive window is 64 KB.
  2. TCP may only have one window of data on the way before it waits for an ACK, so each RTT moves at most 65,535 bytes.
  3. That is 65,535 × 8 / 0.1 ≈ 5.2 Mbit/s, about 0.5 % of the line.
  4. To fill the line the window must be bandwidth × RTT = 1,000,000,000 × 0.1 / 8 = 12.5 MB. Modern systems grow the window with window scaling.
  5. throughput ≤ window / RTT

From beginner to expert

One idea, four depths

Know that a socket is an IP address plus a port, that text must become bytes, and the difference between TCP and UDP.

Write a TCP client and server with timeouts and error handling, use struct for binary data, and frame messages with a length prefix.

Serve many clients with asyncio or selectors, compute subnets with ipaddress, and reason about windows, RTT and loss.

Tune TCP options (TCP_NODELAY, keep alive, buffer sizes), understand TIME_WAIT, congestion control and QUIC, and design binary protocols that can change over time.

Beginner
Send and receive bytes.
Intermediate
Write reliable clients and servers.
Expert
Tune and design network protocols.
Going deeper: TIME_WAIT and SO_REUSEADDR

After a TCP connection closes, the side that closed first keeps the address in the TIME_WAIT state for up to a few minutes, so late packets from the old connection cannot be confused with a new one. If you restart a server quickly, bind can fail with "Address already in use". Setting SO_REUSEADDR before bind allows the restart. socket.create_server sets it for you on Linux and macOS.

Chapter summary

  1. A socket is one end of a connection: an IP address finds the computer, a port finds the program. Sockets send and receive bytes, so encode text first.
  2. TCP server: socket, bind, listen, accept (a new socket per client). Client: create_connection. Use sendall, loop on recv, and always set a timeout.
  3. TCP is a reliable stream with no message borders, so frame messages with a length prefix (struct.pack("!I", n)) or an end marker.
  4. UDP sends single datagrams with sendto and recvfrom: fast, keeps borders, but may lose or reorder them.
  5. Serve many clients with asyncio (start_server, open_connection). Speed is limited by window / RTT and by packet loss.
